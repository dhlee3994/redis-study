# 팔로우 피드: 글을 쓸 때 나눠 넣을까, 읽을 때 모을까

> **핵심 질문**: 팔로우한 사람들의 글을 최신순으로 모아 보여 주는 피드를 Redis로 만들 때, 글이 쓰일 때 팔로워마다의 타임라인에 미리 넣을지(쓸 때 나눠 넣기) 피드를 열 때 모을지(읽을 때 모으기)를 무엇으로 판단하는가? 팔로워가 아주 많은 계정은 어떻게 다루고, 삭제·언팔로우·유실처럼 사본이 원본과 어긋나는 경우는 어떻게 맞추는가?
>
> **범위**: 팔로우한 계정의 글을 최신순으로 보여 주는 홈 피드를 다룹니다. 추천이나 점수로 순서를 다시 매기는 피드, 좋아요 수 같은 집계, 글 본문 캐시의 설계는 다루지 않습니다. Sorted Set의 내부 구조와 점수의 정밀도는 [Redis 랭킹](./ranking.md)에서 다루며, 이 문서는 피드에 필요한 만큼만 한 줄로 씁니다.
>
> **출처와 설계의 구분**: 명령의 동작과 복잡도, 설정 기본값, Spring Data Redis의 메서드는 "근거"에 적은 소스와 공식 문서로 확인했습니다. 키 이름, 타임라인 상한, 스타 계정의 기준, 비활성 사용자의 기준, 예시의 수치는 공식 문서에 있는 규칙이 아니라 이 문서의 설계이며, 그런 문장에는 그 자리에 "이 문서의 설계"라고 적었습니다. DB 쪽 비용은 흔한 B-tree 인덱스를 가정한 추론입니다. 재현해 보지는 않았습니다.

## 배경 지식

### 이 문서의 예시: 작성자 셋, 독자 셋, 글 여섯 개

문서 끝까지 다음 장면 하나를 씁니다.

- 글을 쓰는 계정은 셋입니다. 앨리스(`a`), 밥(`b`), 그리고 팔로워가 아주 많은 스타(`s`)입니다.
- 피드를 읽는 사용자도 셋입니다. 각자 다음 계정을 팔로우합니다.

| 독자 | 팔로우하는 계정 | 비고 |
| --- | --- | --- |
| u1 | a, b, s | |
| u2 | a, s | |
| u3 | b, s | 40일째 접속하지 않은 비활성 사용자 |

- 거꾸로 보면 a의 팔로워는 u1, u2이고, b의 팔로워는 u1, u3이며, s의 팔로워는 셋 모두입니다.
- 글은 DB에 저장될 때 자동 증가 번호로 ID를 받습니다. 아침에 다음 순서로 글 다섯 개가 쓰입니다. 여섯 번째 글 106은 페이지 넘기기를 다루는 곳에서 u1이 피드를 읽는 도중에 쓰입니다.

| 글 ID | 작성자 | 시각 |
| --- | --- | --- |
| 101 | a | 09:00 |
| 102 | s | 09:05 |
| 103 | b | 09:10 |
| 104 | a | 09:20 |
| 105 | s | 09:30 |
| 106 | b | 09:40 |

- 화면은 한 번에 **2개**씩 보여 주고, 사용자마다 Redis에 두는 타임라인은 **최근 3개**까지만 남깁니다. 실제 서비스라면 한 페이지 20개, 상한 수백 개쯤이겠지만, 손으로 따라가려고 줄였습니다(이 문서의 설계).
- 글, 팔로우 관계, 사용자의 마지막 접속 시각의 원본은 DB입니다. Redis에 두는 것은 그 원본에서 언제든 다시 계산할 수 있는 사본입니다(이 문서의 설계). 왜 그렇게 나누는지는 "원본은 DB이고, 사라진 타임라인은 다시 만듭니다"에서 다룹니다.

Redis에 두는 키는 다음과 같습니다(이 문서의 설계).

| 키 | 내용 | 자료형 |
| --- | --- | --- |
| `tl:u1`, `tl:u2`, `tl:u3` | 그 사용자가 볼 글 ID들(홈 타임라인) | Sorted Set. 원소는 글 ID, 점수도 글 ID |
| `posts:s` | 스타 s가 쓴 최근 글 ID들 | Sorted Set. 같은 방식 |

```text
 write path                                         Redis
 author --post--> API --save--> DB (post, follow)
                                  |
                                  | event (async)
                                  v
                            fan-out worker --ZADD per follower--> tl:u1, tl:u2, ...
                                                       (star) --> posts:s

 read path
 u1 --feed--> API --ZRANGE tl:u1, ZRANGE posts:s--> merge --> post bodies --> screen
```

그림의 `fan-out worker`(나눠 넣기 워커)는 글이 저장됐다는 사건을 받아, 그 글의 ID를 작성자의 팔로워마다의 타임라인 키에 넣는 별도 프로세스입니다. 왜 글쓰기 API가 직접 하지 않고 따로 두는지는 "흐름: 글을 DB에 저장하고, 나눠 넣기는 메시지로 맡깁니다"에서 다룹니다.

위쪽 화살표는 글이 쓰인 사실이 흘러가는 방향이고, 아래쪽은 피드 조회 요청이 가는 방향입니다. 글 본문을 어디서 가져오는지(DB, 본문 캐시)는 그림에서 뺐습니다. 타임라인에 본문을 넣지 않는 이유는 "본문이 아니라 글 ID를 담습니다"에서 다룹니다.

비용을 계산하는 곳에서만 장면을 키웁니다. 손으로 따라가기에는 셋이면 충분하지만, 어느 방식이 비싼지는 숫자가 커야 보이기 때문입니다. **키운 장면**에서는 사용자가 1,000만 명이고 그중 30일 안에 접속한 활성 사용자가 100만 명입니다. 일반 계정의 팔로워는 평균 200명, 독자 한 명이 팔로우하는 계정도 평균 200개, 스타 s의 팔로워는 1,000,000명입니다. 최고 시점에 글이 초당 1,000건, 피드 조회가 초당 50,000건 옵니다. 타임라인 상한은 500개, 한 페이지는 20개입니다. 키운 장면의 숫자는 모두 가상 예시입니다.

### 이 문서가 기대는 원리들

- **Sorted Set**: 원소마다 숫자 점수가 붙고, 원소가 중복 없이 점수 순으로 늘어선 Redis 자료형입니다. 이미 있는 원소를 `ZADD`로 다시 넣으면 원소가 하나 더 생기지 않고 점수만 바뀌며, 같은 점수로 다시 넣으면 아무것도 바뀌지 않습니다. 이 주제에서는 타임라인이 "최신순으로 늘어선, 같은 글이 두 번 들어가지 않는 글 ID 목록"이어야 해서 씁니다. 원소가 적을 때(기본 설정에서 128개 이하이고 원소가 모두 64바이트 이하)는 한 덩어리의 메모리(listpack)에 이어 담고, 넣으려는 원소 때문에 이 기준을 넘게 되면 원소마다 따로 담는 구조(스킵 리스트와 해시 테이블)로 바뀝니다. 자세한 구조는 [Redis 랭킹](./ranking.md)의 배경 지식에서 다룹니다.
- **점수는 64비트 부동소수점 수**: Sorted Set의 점수는 Kotlin의 `Double`과 같은 수이며, 정수는 -(2^53)~2^53(약 9천조) 안에서만 정확하게 담깁니다. 이 주제에서는 글 ID를 점수로 쓰므로, ID가 이 범위 안인지가 설계의 전제가 됩니다. 원리는 [Redis 랭킹](./ranking.md)의 "점수는 64비트 부동소수점 수입니다"에서 다룹니다.
- **복잡도 표기**: O(…)는 데이터가 커질 때 작업량이 늘어나는 모양입니다. 이 문서에서 N은 그 키의 원소 수, M은 명령이 돌려주거나 지우는 원소 수입니다. O(1)은 N과 상관없이 일정하고, O(log N)은 N이 두 배가 될 때 한 단계쯤 늘며, O(log N + M)은 "자리를 찾는 데 log N, 거기서 M개를 읽는 데 M"이라는 뜻입니다. 실제 시간이 아니며, 클라이언트가 느끼는 지연에는 네트워크 왕복과 대기가 더해집니다. 표기의 자세한 뜻은 [Redis 랭킹](./ranking.md)의 "복잡도 표기"에 있습니다.
- **왕복과 파이프라이닝**: 왕복은 명령을 보내고 응답을 받기까지 네트워크를 한 번 오가는 일이고, 파이프라이닝은 응답을 기다리지 않고 명령 여러 개를 이어 보내는 방식입니다. 이 주제에서는 글 하나를 팔로워 수백 명의 타임라인에 넣을 때 명령 수백 개를 보내야 하므로, 하나씩 보내면 왕복 수가 걸리는 시간의 대부분을 차지합니다. 묶어 보내도 서버가 실행할 명령 수는 그대로입니다. 원리는 [왕복과 배치](../cs/round-trip-and-batching.md), Redis와 Spring에서의 동작은 [Redis 파이프라이닝](./pipelining.md)에서 다룹니다.
- **메시지 큐, 재전달, 멱등성**: 일을 메시지로 맡겨 두면 처리하는 쪽(워커)이 죽거나 응답이 사라졌을 때 같은 메시지가 다시 처리될 수 있습니다. 같은 일을 여러 번 해도 결과가 한 번 한 것과 같은 성질을 멱등성이라고 합니다. 이 주제에서는 글을 팔로워들에게 나눠 넣는 일을 메시지로 맡기고, 다시 처리돼도 타임라인이 틀어지지 않게 만듭니다. 원리는 [메시지 큐 기초](../cs/message-queue.md)에서 다룹니다.
- **메인 스레드와 해시 슬롯**: Redis 노드 하나는 명령을 메인 스레드라는 실행 흐름 하나에서 차례로 실행하므로, 한 노드에 몰린 명령은 그 노드에서 줄을 섭니다. 클러스터는 데이터를 여러 노드에 나눠 담는 구성이며, 키 이름으로 계산한 해시 슬롯 번호가 그 키가 놓일 노드를 정합니다. 노드 하나가 슬롯 여러 개를 맡으므로, 서로 다른 키도 같은 노드에 놓일 수 있습니다. 이 주제에서는 타임라인 키들이 노드에 흩어지는 것과, 모두가 읽는 키 하나가 한 노드에 몰리는 것을 구분하는 데 쓰입니다. 자세한 동작은 [Redis 이벤트 루프](./event-loop.md)와 [Redis Cluster](./cluster.md)에서 다룹니다.

### 팬아웃과 쓰기 증폭

- **한 줄**: 팬아웃(fan-out)은 하나의 사건을 여러 받는 쪽에 나눠 보내는 일이고, 쓰기 증폭은 그 결과 원래 쓰기 한 번이 저장소에서는 여러 번의 쓰기가 되는 현상입니다.
- **비유**: 동네 소식지를 만드는 두 방법입니다. 하나는 기사가 나올 때마다 구독자 집집마다 우편함에 한 부씩 넣어 두는 것입니다(쓸 때 나눠 넣기). 구독자는 우편함만 열면 되지만, 구독자가 만 명이면 기사 하나에 만 번 배달합니다. 다른 하나는 기사를 각 기자의 게시판에만 붙이고, 구독자가 읽고 싶을 때 자기가 구독하는 기자들의 게시판을 돌며 모아 읽는 것입니다(읽을 때 모으기). 배달은 없지만 읽을 때마다 게시판 수만큼 돌아야 합니다. 예시라면 앨리스의 글 104를 u1과 u2의 우편함(`tl:u1`, `tl:u2`)에 넣는 것이 앞의 방법입니다.
- **실제로는**:
  - 쓸 때 나눠 넣기에서 글 하나의 쓰기 수는 작성자의 팔로워 수에 비례합니다. 예시의 글 104는 DB 저장 1번에 Redis 쓰기 2번이 붙습니다.
  - 읽을 때 모으기에서 피드 한 페이지의 읽기 수는 독자가 팔로우하는 계정 수에 비례합니다. u1이 피드를 열면 a, b, s 세 계정의 글을 각각 읽고 합칩니다.
  - **비유와 다른 점**: 우편함에 넣은 소식지는 기사가 취소돼도 이미 배달된 채 남습니다. 타임라인도 같아서, 나눠 넣은 사본은 원본에서 글이 지워져도 따로 지우지 않으면 남습니다. 반대로 소식지와 달리 타임라인에는 기사 본문이 아니라 기사 번호만 넣고, 읽을 때 원본에서 본문을 가져옵니다. 그래서 "남아 있는 번호를 읽을 때 걸러 내는" 방법이 생깁니다("지우기, 언팔로우, 공개 범위 변경은 읽을 때 한 번 더 거릅니다").
- **이 주제에서는**: 피드 설계의 첫 질문은 "글 한 건의 비용을 쓸 때 낼 것인가, 읽을 때 낼 것인가"입니다. 어느 쪽이 싼지는 쓰기와 읽기의 비율과 팔로워 수의 분포가 정합니다.

## DB 쿼리 하나로 피드를 만들면 왜 비싸지는가

Redis 없이 DB만으로도 피드를 만들 수 있습니다. u1의 첫 페이지는 "u1이 팔로우하는 계정들이 쓴 글을 ID 역순으로 2개"이고, SQL로는 다음 모양입니다.

```text
SELECT * FROM post
 WHERE author_id IN (a, b, s)      -- u1's followees
 ORDER BY id DESC
 LIMIT 2
```

예시에서는 바로 105, 104가 나옵니다. 문제는 규모가 커질 때입니다. 아래는 `(author_id, id)` 인덱스를 둔 흔한 B-tree 인덱스를 가정한 이 문서의 추론이며, 실제 비용은 DB 제품과 실행 계획으로 확인해야 합니다.

- **읽는 양이 팔로우 수에 비례합니다.** 인덱스는 작성자별로 글 ID 순서를 갖고 있지만, 여러 작성자에 걸친 "전체 최신순"은 갖고 있지 않습니다. 그래서 DB는 작성자마다 최신 글을 몇 개씩 읽어 합친 뒤 위에서 자르거나, 글 ID 순서로 훑으며 팔로우하는 작성자의 글만 고릅니다. 앞의 방법은 팔로우 200개면 작성자 200명의 인덱스 구간을 열고, 뒤의 방법은 팔로우한 작성자가 최근에 글을 적게 썼을수록 오래 훑습니다.
- **조회마다, 사용자마다 같은 일을 반복합니다.** u1과 u2는 팔로우 목록이 달라 결과를 서로 다시 쓸 수 없고, 같은 u1도 새로고침할 때마다 다시 계산합니다. 키운 장면이라면 초당 50,000번의 조회가 각각 작성자 200명의 구간을 엽니다.
- **뒤 페이지일수록 더 비쌉니다.** `OFFSET`으로 넘기면 앞 페이지의 결과를 매번 다시 만들어 버립니다.

Redis를 쓰는 이유는 DB가 못 하는 일을 하기 때문이 아니라, **"여러 작성자에 걸친 최신순"을 미리 만들어 두는 자리**가 되기 때문입니다. 이 사본을 언제 만드느냐가 다음 절의 선택입니다. 팔로우 수가 적고 조회가 드문 서비스라면 위 쿼리로 충분할 수 있고, 그때는 사본을 맞추는 비용이 더 큽니다.

## 쓸 때 나눠 넣기와 읽을 때 모으기는 비용을 어디에 두는가

### 쓸 때 나눠 넣기(push): 글마다 팔로워 수만큼 씁니다

글이 저장되면 작성자의 팔로워 목록을 읽어, 팔로워마다 타임라인에 글 ID를 넣습니다. 예시의 다섯 글을 모두 이 방식으로 넣으면(스타의 예외와 비활성 사용자의 예외는 아직 두지 않습니다) 다음과 같습니다.

| 글 | 작성자 | 넣는 곳 | Redis 쓰기 |
| --- | --- | --- | --- |
| 101 | a | `tl:u1`, `tl:u2` | 2 |
| 102 | s | `tl:u1`, `tl:u2`, `tl:u3` | 3 |
| 103 | b | `tl:u1`, `tl:u3` | 2 |
| 104 | a | `tl:u1`, `tl:u2` | 2 |
| 105 | s | `tl:u1`, `tl:u2`, `tl:u3` | 3 |

넣을 때마다 상한 3개를 넘는 오래된 글을 잘라 내면, 다섯 글이 끝난 뒤 `tl:u1`은 {103, 104, 105}입니다. u1의 첫 페이지는 `tl:u1`에서 점수가 높은 쪽부터 2개를 읽는 명령 하나로 끝나고, 결과는 105, 104입니다. 읽기는 팔로우 수와 상관없이 키 하나입니다.

- **얻는 것**: 읽기가 키 하나, 명령 하나로 끝납니다. 조회가 쓰기보다 훨씬 많은 피드에서는 이것이 가장 큰 이점입니다.
- **치르는 것**: 글 하나의 쓰기가 팔로워 수만큼 늘어납니다. 키운 장면에서 일반 계정의 글이 초당 1,000건이고 팔로워가 평균 200명이면, 타임라인에 글을 넣는 일이 초당 약 200,000건입니다. 뒤에서 보듯 넣을 때마다 상한 자르기와 TTL 갱신을 함께 보내므로, Redis 명령으로는 초당 약 600,000건입니다. 팔로워 수가 고르지 않다는 것이 더 큰 문제입니다. 스타 s의 글 하나는 혼자 1,000,000건의 쓰기를 만들고, 마지막 팔로워의 타임라인에 들어갈 때까지 그만큼 늦게 보입니다.
- **또 치르는 것**: 사용자마다 타임라인 하나씩 메모리를 씁니다. 그리고 원본과 따로 사는 사본이 팔로워 수만큼 생기므로, 삭제와 팔로우 변경을 사본에 전하는 일이 생깁니다.

### 읽을 때 모으기(pull): 피드를 열 때 팔로우 수만큼 읽습니다

글이 저장되면 작성자의 글 목록 하나에만 넣습니다. 피드를 열면 팔로우한 계정들의 글 목록을 각각 읽어 최신순으로 합칩니다. 예시라면 u1의 첫 페이지는 a, b, s의 글 목록에서 각각 최신 2개를 읽어(a: 104, 101 / b: 103 / s: 105, 102) 합친 뒤 위에서 2개, 곧 105, 104를 고릅니다.

- **얻는 것**: 글 하나의 쓰기가 한 번입니다. 팔로워가 백만 명이어도 같습니다. 삭제와 팔로우 변경은 원본 목록만 바꾸면 다음 조회부터 반영됩니다.
- **치르는 것**: 피드 한 페이지에 팔로우 수만큼 읽고, 그 결과를 앱에서 합칩니다. 키운 장면에서 조회 초당 50,000건이 각각 200개의 글 목록을 읽으면, 목록 읽기가 초당 약 10,000,000건입니다. 파이프라이닝으로 왕복은 줄일 수 있어도 서버가 실행할 명령 수는 줄지 않습니다. DB 쿼리의 문제(읽는 양이 팔로우 수에 비례)가 Redis로 옮겨 왔을 뿐, 구조는 같습니다.

### 무엇으로 고르는가

| 판단 기준 | 쓸 때 나눠 넣기가 유리 | 읽을 때 모으기가 유리 |
| --- | --- | --- |
| 읽기와 쓰기의 비율 | 조회가 글보다 훨씬 많음 | 글이 많고 조회가 드묾 |
| 팔로워 수의 분포 | 대부분 계정의 팔로워가 수백~수천 명으로 고름 | 팔로워가 아주 많은 계정이 흔함 |
| 새 글이 보이기까지의 시간 | 나눠 넣기가 끝날 때까지 늦어도 됨 | 쓰자마자 보여야 함 |
| 메모리 예산 | 활성 사용자 수 × 타임라인 크기를 감당 | 사용자별 사본을 둘 여유가 없음 |
| 사본을 맞추는 일 | 삭제·언팔로우를 비동기로 전하고, 읽을 때 걸러 낼 수 있음 | 사본을 두지 않음 |

키운 장면에서는 조회(초당 50,000건)가 글(초당 1,000건)보다 50배 많으므로, 비용을 쓰기 쪽에 두는 편이 전체 명령 수가 훨씬 적습니다(초당 약 600,000건 대 약 10,000,000건, 가상의 계산). 다만 스타 계정 하나가 이 계산을 깹니다. 그래서 대부분의 피드는 둘을 섞습니다.

## 팔로워가 아주 많은 계정은 읽을 때 섞습니다

### 일반 계정은 나눠 넣고, 스타의 글은 읽을 때 합칩니다

팔로워 수가 기준 이상인 계정을 스타로 분류하고, 스타의 글은 팔로워들에게 나눠 넣지 않습니다(이 문서의 설계). 스타의 글은 그 스타의 글 목록 `posts:s`에만 넣고, 피드를 읽을 때 "내 타임라인 + 내가 팔로우하는 스타들의 글 목록"을 합칩니다. 예시에서는 s를 스타로 둡니다. 손 예시의 팔로워는 셋뿐이지만, 키운 장면에서 팔로워가 1,000,000명이라 기준을 넘는 계정이기 때문입니다.

다섯 글이 지난 뒤 Redis의 상태는 다음과 같습니다. 비활성 사용자 u3을 빼는 이유는 "비활성 사용자에게는 넣지 않고, 돌아오면 다시 만듭니다"에서 다룹니다.

| 키 | 원소(글 ID) | 들어온 경로 |
| --- | --- | --- |
| `tl:u1` | 101, 103, 104 | a, b의 글을 나눠 넣음 |
| `tl:u2` | 101, 104 | a의 글을 나눠 넣음 |
| `tl:u3` | (없음) | 비활성이라 넣지 않음 |
| `posts:s` | 102, 105 | 스타의 글은 자기 목록에만 |

Redis 쓰기는 일반 계정의 글 101, 103, 104에서 2 + 1 + 2 = 5번, 스타의 글 102, 105에서 1번씩 2번입니다. 스타를 나눠 넣었다면 키운 장면에서 글 하나에 1,000,000번이 들었을 자리입니다.

u1의 첫 페이지는 키 두 개를 읽어 합칩니다.

```text
tl:u1   top 2  ->  104, 103
posts:s top 2  ->  105, 102
merge (desc)   ->  105, 104, 103, 102  ->  page 1 = 105, 104
```

읽기 비용은 "키 하나 + 팔로우하는 스타 수"입니다. 스타를 많이 팔로우하는 사용자일수록 읽을 키가 늘어나므로, 기준을 너무 낮게 잡으면 읽을 때 모으기의 문제가 되살아납니다. 기준은 "글 하나의 나눠 넣기가 얼마나 오래 걸려도 되는가"와 "사용자 한 명이 팔로우하는 스타가 몇 명쯤인가"를 같이 보고 정합니다.

### 기준을 넘나드는 계정과 합칠 때의 중복

- **합칠 때는 글 ID로 중복을 없앱니다.** 어떤 계정이 스타가 되기 전에 쓴 글은 이미 팔로워들의 타임라인에 들어가 있고, 스타가 된 뒤에는 `posts:s`에도 있을 수 있습니다. 같은 글이 두 경로에서 오므로, 합칠 때 같은 ID는 한 번만 남깁니다. 글 ID를 점수로 쓰면 같은 글은 두 경로에서 같은 점수로 오므로 합친 순서도 흔들리지 않습니다.
- **기준 근처에서 오가지 않게 문턱을 둘로 둡니다.** 팔로워가 기준을 조금 넘었다 내려왔다 하면 나눠 넣기와 읽을 때 합치기가 번갈아 바뀝니다. 스타로 바꾸는 기준과 일반으로 되돌리는 기준을 떨어뜨려 둡니다(이 문서의 설계).
- **일반으로 되돌릴 때 빈틈이 생깁니다.** 스타였던 동안의 글은 팔로워 타임라인에 없습니다. 되돌린 뒤에도 그 계정의 `posts:` 목록을 얼마간 읽을 때 합치거나, 팔로워들의 타임라인에 최근 글을 채워 넣습니다(뒤의 "언팔로우와 새 팔로우"의 채워 넣기와 같은 방법).

### 스타의 글 목록은 모두가 읽는 핫키가 됩니다

스타의 팔로워 1,000,000명 중 피드를 여는 사람은 모두 `posts:s`를 읽습니다. 쓰기를 백만 개의 타임라인에 흩뜨리는 대신, 읽기를 키 하나에 모은 셈입니다. 키 하나는 노드 하나의 메인 스레드에서만 처리되므로, 노드를 늘려도 이 부하는 나뉘지 않습니다. 이 성질과 대응은 [Hot Key와 Big Key](./hot-key-big-key.md)에서 다룹니다.

다행히 `posts:s`는 모든 팔로워에게 같은 내용입니다. 사용자마다 다른 타임라인과 달리 앱 서버의 메모리에 짧게(예: 1초) 캐시해 둘 수 있습니다(이 문서의 설계). 대가는 스타의 새 글이 그 시간만큼 늦게 보이는 것입니다. 복제본에서 읽는 방법도 있으며, 대가는 복제 지연만큼 늦게 보이는 것입니다.

## 타임라인은 글 ID를 점수로 둔 Sorted Set에 담습니다

### 본문이 아니라 글 ID를 담습니다

타임라인 원소는 글 ID뿐입니다(이 문서의 설계). 본문을 넣지 않는 이유는 셋입니다.

- **메모리**: 글 104가 u1과 u2의 타임라인에 들어가듯, 같은 글이 팔로워 수만큼 복제됩니다. 본문을 넣으면 그 크기가 팔로워 수만큼 곱해집니다.
- **수정과 삭제**: 앨리스가 글 104를 고치면, 본문을 넣은 경우 모든 사본을 고쳐야 합니다. ID만 넣으면 원본 한 곳만 바뀝니다.
- **원소 크기와 내부 표현**: Sorted Set은 원소가 하나라도 64바이트를 넘으면(기본 설정) 한 덩어리 표현을 버리고 원소마다 따로 담는 구조로 바뀝니다. 짧은 ID는 이 기준에 걸리지 않습니다.

대가는 읽을 때 한 번 더 가져오는 일입니다. 타임라인에서 ID 2개를 얻은 뒤 본문을 DB나 본문 캐시에서 가져옵니다(이 단계를 이 문서에서는 "본문 붙이기"라고 부릅니다). 이 단계가 뒤에서 "읽을 때 걸러 내기"를 하는 자리가 됩니다.

### 점수로 글 ID를 씁니다

점수 후보는 "글이 쓰인 시각"과 "글 ID" 둘입니다. 이 문서는 글 ID를 고릅니다(이 문서의 설계). 이유는 셋입니다.

- **점수가 겹치지 않습니다.** 시각을 밀리초로 써도 두 글이 같은 밀리초에 쓰이면 점수가 같고, 그때 순서는 원소 문자열의 바이트 순서가 정합니다. 무엇보다 "마지막으로 본 점수보다 작은 것"으로 다음 페이지를 읽을 때, 같은 점수의 글이 경계에 걸리면 빠지거나 두 번 나옵니다. 글 ID는 하나뿐이므로 이 문제가 없습니다("커서: 마지막으로 본 글 ID보다 작은 것부터 읽습니다").
- **같은 글은 언제 누가 넣어도 같은 점수입니다.** 나눠 넣기를 다시 해도, 타임라인을 DB에서 다시 만들어도, 새로 팔로우한 계정의 글을 채워 넣어도 글 104는 점수 104입니다. 이 성질이 재시도를 안전하게 만듭니다("재시도가 안전한 이유: 같은 원소, 같은 점수").
- **ID는 대체로 쓰인 순서를 따릅니다.** 자동 증가 번호는 먼저 받은 글이 작은 번호입니다. 다만 번호를 받은 순서와 저장이 확정된 순서는 다를 수 있습니다. 103이 104보다 늦게 확정되면 104가 먼저 보인 뒤 103이 그 아래에 끼어듭니다. 아래쪽에 끼므로 이미 본 페이지가 밀리거나 같은 글이 두 번 나오지는 않습니다. 대신 독자가 이미 커서를 103 아래로 내린 뒤에 103이 나타나면, 이번 스크롤에서는 103을 보지 못하고 맨 위로 돌아와 다시 내려갈 때 봅니다. 확정이 몇 초 늦는 정도라면 피드에서는 대개 받아들입니다.

**글 ID가 2^53을 넘으면 이 방법을 쓸 수 없습니다.** 점수는 double이라 2^53을 넘는 정수는 일부만 정확히 담기고, 서로 다른 ID가 같은 점수가 될 수 있습니다. 1부터 1씩 늘리는 자동 증가 번호라면 이 상한까지 가기 어렵지만, 시작값과 증가 폭을 바꿨거나 상위 비트에 시각을 담는 64비트 ID 생성기처럼 큰 값을 만드는 방식이라면 넘을 수 있습니다. 어느 쪽이든 실제로 만들어지는 값의 범위를 먼저 확인합니다. 넘는다면 점수를 시각으로 두고 원소를 글 ID로 두되, 페이지 커서를 "점수와 글 ID의 쌍"으로 다뤄야 해서 읽기가 복잡해집니다.

### List가 아니라 Sorted Set인 이유

Redis 공식 문서의 Twitter 클론 예시는 팔로워마다 List에 `LPUSH`로 글 ID를 넣는 방식을 보여 줍니다(공식 문서 twitter-clone). 순서대로 쌓기만 한다면 List도 됩니다. 이 문서는 Sorted Set을 고릅니다(이 문서의 설계). 갈리는 지점은 다음과 같습니다.

| 하고 싶은 일 | List | Sorted Set |
| --- | --- | --- |
| 새 글 넣기 | `LPUSH`, O(1) | `ZADD`, O(log N) |
| 같은 글을 다시 넣음(재시도) | 두 번 들어감 | 원소가 하나뿐이라 그대로 |
| 늦게 온 글, 채워 넣는 옛 글 | 맨 앞에만 넣을 수 있어 순서가 틀어짐 | 점수대로 제자리에 들어감 |
| 글 하나 지우기 | `LREM`, 앞에서부터 훑음 O(N + M) | `ZREM`, O(log N) |
| 다음 페이지 | 위치(index)로만 읽음 | 마지막으로 본 ID 기준으로 읽을 수 있음 |
| 상한으로 자르기 | `LTRIM` | `ZREMRANGEBYRANK` |
| 메모리 | 원소만 | 원소와 점수 |

재시도, 늦게 온 글, 채워 넣기는 비동기 나눠 넣기에서 늘 생기는 일입니다. List로는 이 셋을 자료형이 막아 주지 않아 앱이 따로 막아야 합니다. 대가는 원소마다 점수를 더 담는 메모리와 `ZADD`의 O(log N)이며, 상한이 수백 개라 log N은 작습니다.

### 길이 상한은 넣을 때마다 자릅니다

타임라인을 끝없이 키우지 않고 상한(예시 3개)을 둡니다. 사용자 대부분은 최근 글 몇 페이지만 보고, 상한이 메모리 추정의 기준이 되기 때문입니다. 넣을 때마다 다음 두 명령을 보냅니다.

1. `ZADD tl:u1 104 104`: 점수 104로 원소 "104"를 넣습니다.
2. `ZREMRANGEBYRANK tl:u1 0 -4`: 점수가 낮은 쪽부터 센 순위 0부터 "높은 쪽 끝에서 네 번째"까지를 지웁니다. 음수 순위는 점수가 높은 쪽 끝에서 셉니다. 곧 최신 3개를 뺀 나머지를 지웁니다. 상한이 500이면 `0 -501`입니다.

`ZREMRANGEBYRANK`의 복잡도는 O(log N + M)이고, 넣을 때마다 자르면 M은 대개 0이나 1입니다. 두 명령 사이에 다른 요청이 끼어 잠깐 원소가 4개가 되어도 다음 자르기에서 맞춰지므로, 둘을 원자적으로 묶을 필요는 없습니다(이 문서의 판단).

상한의 크기는 메모리 표현도 바꿉니다. 기준 버전의 기본 설정에서는 새 원소를 넣어 원소가 128개를 넘게 되면(`zset-max-listpack-entries`) 넣기 전에 한 덩어리 표현에서 원소마다 따로 담는 구조로 바뀝니다. 그 뒤 `ZREM`이나 `ZREMRANGEBYRANK`로 원소를 줄여도 한 덩어리로 돌아가지 않습니다. **잘라 내기는 넣은 뒤에 하므로, 넣는 순간에는 원소가 상한보다 하나 많아집니다.** 그래서 상한이 128이면 꽉 찬 타임라인에 129번째 글이 들어오는 순간 바뀌어 버리고, 한 덩어리를 유지하려면 상한을 127 이하로 둬야 합니다. 상한을 500으로 두면 타임라인이 차 가는 도중에 원소마다 따로 담는 구조가 됩니다. 원소마다 따로 담으면 원소 수만큼 할당과 관리 정보가 붙어 메모리가 커집니다. 그 원리는 [메모리 할당](../cs/memory-allocation.md)에서 다룹니다. 상한을 정할 때는 이 메모리 차이와, 상한 너머를 DB로 읽는 빈도를 함께 봅니다("사용자와 글이 늘면 무엇이 달라지는가").

## 페이지는 offset이 아니라 마지막으로 본 글 ID로 넘깁니다

### offset은 새 글이 끼면 밀립니다

u1이 09:35에 첫 페이지 105, 104를 봤습니다. 09:40에 밥이 글 106을 쓰고, 나눠 넣기가 `tl:u1`에 106을 넣은 뒤 상한으로 잘라 냅니다.

```text
before 106:  tl:u1 = {101, 103, 104}
ZADD 106  -> {101, 103, 104, 106}  --ZREMRANGEBYRANK 0 -4-->  {103, 104, 106}
```

이제 u1이 둘째 페이지를 "앞에서 2개 건너뛰고 2개"로 읽으면, 합친 목록이 106, 105, 104, 103, 102이므로 104, 103이 나옵니다. **104가 두 번 보입니다.** 새 글이 맨 위에 하나 끼면서 전체가 한 칸씩 밀렸기 때문입니다. 반대로 위쪽 글이 지워지면 한 칸씩 당겨져 글 하나를 건너뜁니다.

키 두 개를 합치는 피드에서는 offset이 하나 더 비쌉니다. 합친 목록에서 앞의 2개를 건너뛰려면 각 키에서 몇 개를 건너뛰어야 하는지 알 수 없으므로, 키마다 "건너뛸 수 + 페이지 크기"만큼 읽어야 합니다. 뒤 페이지일수록 읽는 양이 늘어납니다.

### 커서: 마지막으로 본 글 ID보다 작은 것부터 읽습니다

화면이 마지막으로 보여 준 글 ID(커서)를 다음 요청에 넘기고, 각 키에서 그보다 작은 글을 높은 쪽부터 읽습니다. 첫 페이지와 다음 페이지는 다음 명령입니다.

```text
page 1:  ZRANGE tl:u1 +inf -inf BYSCORE REV LIMIT 0 2
page 2:  ZRANGE tl:u1 (104 -inf BYSCORE REV LIMIT 0 2      (same for posts:s)
```

- `BYSCORE`는 순위가 아니라 점수 구간으로 읽고, `REV`는 높은 쪽부터 읽습니다. `REV`와 `BYSCORE`를 함께 쓰면 앞의 값이 구간의 높은 쪽 끝, 뒤의 값이 낮은 쪽 끝입니다.
- `(104`의 `(`는 경곗값 104를 빼라는 뜻입니다. 기본은 경곗값을 포함합니다.
- `LIMIT 0 2`는 구간에서 0개를 건너뛰고 2개를 돌려줍니다. 커서 방식은 건너뛰는 수가 늘 0이라, 페이지가 깊어져도 각 키에서 읽는 양이 페이지 크기로 같습니다. 공식 문서는 `LIMIT`의 건너뛰는 수가 크면 그만큼 원소를 지나가야 해서 O(N)까지 늘 수 있다고 적습니다.
- 명령의 공식 복잡도는 O(log N + M)이고, M은 돌려주는 원소 수(페이지 크기)입니다.

09:40의 106이 들어온 뒤에도 둘째 페이지는 `tl:u1`에서 103, `posts:s`에서 102를 읽어 합친 103, 102입니다. 이미 본 104는 다시 나오지 않고, 새로 들어온 106은 커서 위쪽이라 이번 탐색에 끼지 않습니다. 106은 u1이 맨 위로 돌아와 새로고침할 때 보입니다.

커서가 이렇게 깔끔한 것은 점수가 겹치지 않기 때문입니다. 시각을 점수로 썼다면 같은 밀리초의 두 글 중 하나가 첫 페이지 끝에 걸릴 때 `(` 경계에서 다른 하나가 빠집니다.

### 상한 너머는 DB로 이어 읽습니다

셋째 페이지는 커서 102로 읽습니다. `tl:u1`에는 102보다 작은 글이 없고(101은 106이 들어올 때 상한으로 잘렸습니다), `posts:s`에도 없습니다. 그런데 글 101은 DB에 있습니다. **타임라인이 비었다는 것은 피드가 끝났다는 뜻이 아닙니다.** 타임라인은 최근 일부만 들고 있는 사본이기 때문입니다.

"합친 결과로 페이지가 덜 찼을 때만 DB를 본다"는 규칙으로는 부족합니다. 목록 하나가 잘렸어도 다른 목록이 페이지를 채우면 빈틈이 드러나지 않기 때문입니다. 예를 들어 `tl:u1`이 104까지 잘려 나간 상태에서 `posts:s`에 103, 102가 남아 있으면, 합친 페이지는 103, 102로 꽉 차고 커서는 102로 내려갑니다. 그 뒤로는 `id < 102`만 읽으므로 DB에 있는 104는 다시 나오지 않습니다.

그래서 판단을 **목록마다** 합니다(이 문서의 설계). 어느 목록이 커서 아래에서 페이지 크기만큼 돌려주지 못하면, 그 목록이 맡은 작성자들(`tl:u1`이면 u1이 팔로우하는 일반 계정들, `posts:s`면 s)의 글을 커서 아래에서 페이지 크기만큼 DB로 읽어 대신 씁니다. 그런 다음 모든 결과를 글 ID로 중복을 없애며 합치고 위에서 페이지 크기만큼 자릅니다. DB는 그 작성자들의 글을 빠짐없이 갖고 있으므로, 잘린 글이 커서를 지나쳐 버리는 일이 없습니다.

예시처럼 목록이 아주 짧으면 둘째 페이지부터 이 보충이 일어납니다. 커서 104에서 `tl:u1`은 103 하나만 돌려주므로 DB에서 u1이 팔로우하는 일반 계정(a, b)의 `id < 104` 글 103, 101을, `posts:s`도 102 하나뿐이므로 DB에서 s의 글 102를 읽습니다. 합치면 103, 102, 101이고 둘째 페이지는 103, 102로 앞의 결과와 같습니다. 상한이 500인 타임라인이라면 이 보충은 500개 가까이 내려간 드문 요청에서만 일어나므로, 비싼 쿼리라도 전체 부하에서는 작습니다. 대가는 목록이 원래 짧은 사용자, 그리고 정말 끝에 닿은 사용자도 이 쿼리를 치른다는 점입니다. 끝인지 확인하는 비용으로 받아들입니다. `posts:s`도 끝없이 키우지 않고 상한을 두므로(이 문서의 설계) 같은 규칙이 필요합니다.

## 쓰기는 비동기로 나눠 넣고, 다시 해도 같은 결과가 되게 합니다

### 흐름: 글을 DB에 저장하고, 나눠 넣기는 메시지로 맡깁니다

글쓰기 API가 팔로워 수만큼의 쓰기를 요청 안에서 다 하면, 팔로워가 많은 작성자의 글쓰기 응답이 그만큼 늦어집니다. 그래서 다음처럼 나눕니다(이 문서의 설계).

1. 글쓰기 API는 글을 DB에 저장하고, 같은 트랜잭션에 "나눠 넣을 글" 기록을 남깁니다. 저장과 메시지 발행 사이에서 한쪽만 성공하는 틈을 이렇게 DB 하나로 닫는 방식을 아웃박스라고 부르며, 원리는 [두 저장소에 나눠 쓰기](../cs/dual-write.md)에서 다룹니다.
2. 이 기록이 메시지 큐(Redis Streams나 Kafka 등)를 거쳐 나눠 넣기 워커에 전달됩니다. Redis Streams로 전달할 때의 소비자 그룹, 처리 완료 표시(ACK), 회수는 [Redis Streams](./streams.md)에서 다룹니다.
3. 워커는 작성자의 팔로워 목록을 DB에서 1,000명씩 끊어 읽고, 활성 사용자만 골라, 한 묶음마다 `ZADD`, `ZREMRANGEBYRANK`, `EXPIRE`를 팔로워별로 파이프라이닝으로 보냅니다. `EXPIRE`를 함께 보내는 이유는 "비활성 사용자에게는 넣지 않고, 돌아오면 다시 만듭니다"에서 다룹니다.
4. 모든 묶음이 끝나면 메시지 처리를 완료로 표시합니다.

예시의 글 104라면 팔로워 u1, u2에게 다음 여섯 명령이 한 묶음으로 나갑니다(TTL 30일은 이 문서의 설계).

```text
ZADD tl:u1 104 104
ZREMRANGEBYRANK tl:u1 0 -4
EXPIRE tl:u1 2592000
ZADD tl:u2 104 104
ZREMRANGEBYRANK tl:u2 0 -4
EXPIRE tl:u2 2592000
```

묶음을 1,000명 단위로 끊는 이유는 묶음 하나가 너무 크면 클라이언트가 결과를 들고 있는 메모리, 명령 타임아웃, 실패했을 때 어디까지 실행됐는지 모르는 범위가 모두 커지기 때문입니다. 이 비용은 [Redis 파이프라이닝](./pipelining.md)의 "묶음이 너무 크면 무엇이 문제인가"에서 다룹니다. 팔로워가 수십만 명인 작성자라면 메시지 하나를 "팔로워 1~1,000번째", "1,001~2,000번째"처럼 여러 하위 작업으로 나눠, 한 하위 작업이 실패해도 그 부분만 다시 하게 합니다(이 문서의 설계).

파이프라이닝은 왕복을 줄일 뿐 서버가 실행할 명령 수는 그대로입니다. 스타를 나눠 넣지 않는 이유도 여기에 있습니다. 묶어 보내도 1,000,000번의 `ZADD`는 서버 어딘가에서 실행되어야 합니다.

### 재시도가 안전한 이유: 같은 원소, 같은 점수

워커가 묶음을 보내다 연결이 끊기면 어디까지 실행됐는지 모릅니다. 메시지 큐도 워커가 처리 중에 죽으면 같은 메시지를 다시 전달합니다. 그래서 같은 글의 나눠 넣기가 두 번 실행된다고 가정합니다.

글 104를 `tl:u1`에 두 번 넣으면, 두 번째 `ZADD tl:u1 104 104`는 이미 같은 점수로 있는 원소라 아무것도 바꾸지 않습니다. 자르기도 이미 상한 안이면 지울 것이 없습니다. **같은 명령을 몇 번 실행해도 결과가 같으므로, 처리 표시 키 없이도 다시 하면 됩니다.**

이 성질은 점수를 "글에서 정해지는 값"으로 둔 덕분입니다. 점수를 "워커가 처리한 시각"으로 두면, 다시 처리할 때마다 같은 글의 점수가 바뀌어 옛 글이 맨 위로 올라옵니다. [Redis 랭킹](./ranking.md)의 `ZINCRBY`처럼 "더하는" 갱신은 재시도하면 두 번 더해져 처리 표시가 필요했지만, 피드의 `ZADD`는 "이 값으로 둔다"는 갱신이라 그 문제가 없습니다.

다만 재시도가 늦게 오면 생기는 문제가 하나 남습니다. 글 104의 나눠 넣기가 실패해 다시 전달되기 전에 앨리스가 104를 지웠다면, 늦은 재시도가 지운 글을 다시 넣습니다. 워커가 넣기 전에 글이 아직 있는지 확인하면 줄일 수 있지만, 확인과 넣기 사이에 지워지는 경우까지 막지는 못합니다. 그래서 다음 절의 "읽을 때 걸러 내기"가 최종 방어선입니다.

### 작성자 자신의 글

나눠 넣기는 비동기라, 앨리스가 글 104를 쓰고 바로 자기 피드를 열면 아직 없을 수 있습니다. 자기 글이 보이지 않으면 사용자는 글쓰기가 실패했다고 느낍니다. 그래서 작성자 자신의 타임라인에는 글쓰기 API가 요청 안에서 바로 넣거나, 피드를 읽을 때 자기 최근 글을 함께 합칩니다(이 문서의 설계).

## 지우기, 언팔로우, 공개 범위 변경은 읽을 때 한 번 더 거릅니다

타임라인은 "보여 줄 후보 글 ID 목록"이고, 보여 줘도 되는지는 본문 붙이기 단계에서 원본으로 다시 확인합니다(이 문서의 설계). 사본을 고치는 일은 비동기라 늦을 수 있고, 늦게 온 재시도가 고친 것을 되돌릴 수도 있기 때문입니다.

### 글 삭제

09:50에 앨리스가 글 104를 지웁니다. 104는 `tl:u1`과 `tl:u2`에 들어 있습니다.

- **읽을 때 거르기(정확성)**: 본문 붙이기에서 104가 지워진 글로 확인되면 화면에 넣지 않습니다. 페이지가 2개보다 적게 채워지므로, 모자라면 커서를 이어 한 번 더 읽습니다. 이 확인은 사본이 아무리 늦어도 지운 글이 보이지 않게 합니다.
- **이어 읽을 때의 커서(이 문서의 설계)**: 이어 읽는 기준은 마지막으로 보여 준 글이 아니라 마지막으로 검사한 후보 ID입니다. 여기서 검사한 후보는 키들에서 읽어 와 최신순으로 합친 목록을 위에서부터 차례로 확인한 마지막 것이며, 읽어 온 것 전체의 가장 작은 ID가 아닙니다. 페이지가 찬 뒤 확인하지 않고 남은 후보까지 건너뛰면 그 글을 놓치기 때문입니다. 예를 들어 읽어 온 후보 2개가 모두 지운 글이면 보여 준 글이 하나도 없으므로, "마지막으로 보여 준 글"을 기준으로 삼으면 같은 두 후보를 다시 읽기를 되풀이합니다. 지운 글이 몰린 구간에서 끝없이 읽지 않도록 요청 하나의 이어 읽기 횟수에도 상한을 둡니다. 상한에 닿으면 덜 찬 페이지를 그대로 돌려주고, 다음 커서로는 마지막으로 검사한 후보 ID를 줍니다. 다음 요청은 그 아래에서 이어 읽습니다.
- **사본에서 지우기(정리)**: 삭제도 나눠 넣기와 같은 경로로 메시지를 남기고, 워커가 팔로워들의 타임라인에서 `ZREM tl:u1 104`, `ZREM tl:u2 104`를 보냅니다. `ZREM`은 원소 하나에 O(log N)이고, 없는 원소를 지워도 에러 없이 넘어가므로 다시 해도 안전합니다. 하지 않아도 정확성은 읽을 때 거르기가 지키지만, 지운 글이 타임라인 자리를 차지해 한 페이지를 채우려고 여러 번 읽게 됩니다.

### 언팔로우와 새 팔로우

10:00에 u2가 앨리스를 언팔로우합니다. `tl:u2`의 101과 104는 앨리스의 글입니다. 그런데 타임라인에는 글 ID만 있으므로, 그 ID가 누구의 글인지는 Redis만으로 알 수 없습니다. 워커가 DB에서 앨리스의 글 중 `tl:u2`의 가장 오래된 점수(101) 이후의 ID를 찾아 `ZREM tl:u2 101 104`를 보냅니다(이 문서의 설계). 이 정리가 끝날 때까지 몇 초간 앨리스의 글이 u2에게 보이는 것은 받아들입니다. 언팔로우는 권한 문제가 아니기 때문입니다.

정리가 끝난 뒤에 앨리스의 옛 글에 대한 나눠 넣기 재시도가 늦게 오면 다시 들어갈 수 있습니다. 재시도가 팔로워 목록을 DB에서 다시 읽게 하면, 언팔로우가 확정된 뒤의 재시도는 u2를 넣지 않습니다. 남는 틈은 워커가 언팔로우 전에 팔로워 목록을 읽고 정리가 끝난 뒤에 `ZADD`를 보내는 짧은 경우입니다. 이것까지 막아야 한다면 본문 붙이기에서 팔로우 관계를 원본으로 확인합니다(이 문서의 설계).

새로 팔로우할 때는 반대로 채워 넣습니다. u2가 밥을 팔로우하면 밥의 최근 글 103, 106을 `tl:u2`에 `ZADD`로 넣고 상한으로 자릅니다. 점수가 글 ID라 옛 글이 제자리에 끼어들고, 그 결과 `tl:u2`는 {103, 104, 106}이 됩니다(앨리스 언팔로우 전이라면). List였다면 맨 앞에만 넣을 수 있어 순서가 틀어집니다.

### 공개 범위와 차단

앨리스가 계정을 비공개로 바꾸거나 u1을 차단하면, 이미 `tl:u1`에 들어간 앨리스의 글이 더는 u1에게 보이면 안 됩니다. 이것은 권한 문제라 "몇 초 늦게 지워짐"을 받아들일 수 없습니다. 본문 붙이기에서 글의 공개 범위와 차단 관계를 원본으로 확인해 거릅니다. 사본 정리는 그 뒤 비동기로 해도 됩니다.

정리하면 다음과 같습니다.

| 변경 | 읽을 때 거르기 | 사본 정리 |
| --- | --- | --- |
| 글 삭제 | 필수. 늦은 재시도까지 막는 유일한 방법 | 권장. 빈자리를 줄임 |
| 언팔로우 | 선택. 몇 초 보이는 것을 받아들이면 생략 | 필수. 안 하면 계속 보임 |
| 공개 범위 변경·차단 | 필수. 권한이라 늦으면 안 됨 | 권장 |

## 원본은 DB이고, 사라진 타임라인은 다시 만듭니다

타임라인 키가 사라지거나 틀어지는 경우는 여럿입니다. 재시작 때 영속성 설정에 따라 마지막 몇 초의 쓰기를 잃을 수 있고, 장애 조치로 복제본이 주 서버가 되면 아직 복제되지 않은 쓰기를 잃을 수 있으며, 메모리 한도와 축출 정책에 따라 키가 지워질 수 있습니다. 각각의 조건은 [Redis 영속성](./persistence.md), [Redis 복제](./replication.md), [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.

그래서 타임라인은 DB의 글과 팔로우 관계로 언제든 다시 계산할 수 있게 둡니다(이 문서의 설계).

- **다시 만드는 방법은 읽을 때 모으기 한 번입니다.** 그 사용자가 팔로우하는 일반 계정들의 최근 글을 DB에서 상한만큼 읽어, `ZADD` 하나에 원소 여러 개를 넣고, 이어서 `ZREMRANGEBYRANK`로 상한에 맞춰 자르고 `EXPIRE`로 TTL을 겁니다. 스타의 글은 원래 읽을 때 합치므로 다시 만들 필요가 없습니다.
- **다시 만드는 중에 나눠 넣기가 와도 됩니다.** 다시 만들기와 나눠 넣기가 같은 글을 넣어도 같은 원소, 같은 점수라 결과가 같습니다. 서로 다른 글이 섞여 잠깐 상한을 넘을 수는 있습니다. DB에서 3개를 읽은 사이 새 글이 나눠 넣기로 먼저 들어오면 `ZADD` 직후 4개가 되므로, 다시 만들기도 넣은 뒤 반드시 자릅니다. 자르기는 점수 순으로 오래된 것을 지우므로 누가 먼저 넣었든 최신 3개가 남습니다. 그래서 [Redis 랭킹](./ranking.md)처럼 새 키에 채운 뒤 바꿔 끼울 필요 없이 원래 키에 바로 채웁니다. 타임라인 하나는 상한만큼만 원소가 있어 작습니다.
- **비어 있는 타임라인과 없는 타임라인을 구분합니다.** Sorted Set은 마지막 원소가 지워지면 키도 사라집니다. 팔로우가 하나도 없는 사용자는 다시 만들어도 키가 생기지 않아, 매 조회마다 다시 만들게 됩니다. "다시 만들었음" 표시를 짧은 TTL(키가 사라질 때까지 남은 시간)과 함께 따로 둡니다(이 문서의 설계).
- **한꺼번에 사라지면 DB가 한꺼번에 맞습니다.** Redis 노드 하나를 통째로 잃으면 그 노드의 활성 사용자 타임라인이 모두 사라지고, 이들이 피드를 열 때마다 DB 쿼리가 몰립니다. 다시 만들기를 조회 시점에 하면 접속 시각만큼 퍼지지만, 출근 시간처럼 접속이 몰리는 때에는 다시 만들기의 동시 실행 수에 상한을 두고, 넘는 요청에는 잠시 DB 쿼리로 바로 답하거나 짧은 피드를 보여 줍니다(이 문서의 설계). 같은 키에 요청이 몰리는 문제의 일반적인 대응은 [캐시 스탬피드](./cache-stampede.md)에서 다룹니다.
- **키는 남고 일부 글만 빠지면 다시 만들기가 시작되지 않습니다.** 장애 조치로 아직 복제되지 않은 쓰기만 잃으면 타임라인 키는 그대로 있고 그 사이에 넣은 글만 빠집니다. 다시 만들기는 키가 없을 때 시작되고, "상한 너머는 DB로 이어 읽습니다"의 보충도 목록이 페이지를 채우지 못할 때만 일어나므로, 빠진 글 아래로 목록이 페이지를 채우면 빈틈이 드러나지 않습니다. 메우려면 장애 조치 앞뒤로 나눠 넣기가 실행된 구간의 메시지를 다시 처리합니다(이 문서의 설계). 구간은 글이 저장된 시각이 아니라 워커가 나눠 넣은 시각으로 잡아야 합니다. 워커가 밀렸거나 재시도했다면 장애 조치 훨씬 전에 저장된 글이 그 구간에 나눠 넣어졌을 수 있기 때문입니다. 그러려면 처리를 마친 아웃박스 기록이나 메시지를 지우지 않고 남겨 둬야 합니다. 보관 기간은 기록을 만들거나 발행한 시각이 아니라 워커가 나눠 넣기를 끝낸 시각부터 세고, 장애 조치를 알아차려 다시 처리하기 시작할 수 있는 시점까지 남도록 잡습니다. 이미 들어간 글은 같은 원소, 같은 점수라 다시 넣어도 바뀌지 않고, 그사이 지워진 글은 읽을 때 거르기가 막습니다. 다시 넣을 때도 상한으로 자르므로, 돌아오는 것은 상한 안의 최신 후보뿐이고 잃은 글이 모두 돌아오지는 않습니다. 다시 처리하지 않고 받아들일 수도 있습니다. 그때는 지금 사본의 누락이 저절로 드러나지 않을 뿐이고, 나중에 상한 너머 DB 보충이나 TTL·축출 뒤 다시 만들기를 거치면 빠진 글이 다시 나올 수 있습니다.

## 비활성 사용자에게는 넣지 않고, 돌아오면 다시 만듭니다

키운 장면의 사용자 1,000만 명 중 활성 사용자는 100만 명입니다. 나머지 900만 명의 타임라인에도 나눠 넣으면, 쓰기의 대부분이 아무도 읽지 않는 타임라인을 채우는 데 쓰입니다. 그래서 30일 안에 접속하지 않은 사용자는 나눠 넣기 대상에서 뺍니다(이 문서의 설계). 예시의 u3이 그렇습니다. 밥의 글 103과 106은 u3에게 들어가지 않았습니다.

- **타임라인은 TTL로 사라지게 둡니다.** 피드를 읽을 때와 타임라인에 쓸 때마다 타임라인 키의 TTL을 30일로 다시 겁니다(`EXPIRE`, O(1)). 쓸 때도 거는 이유는 `ZADD`가 키를 새로 만들 때 TTL을 붙이지 않기 때문입니다. 읽을 때만 걸면, 사라졌던 키를 나눠 넣기나 늦게 온 재시도가 다시 만든 뒤 그 사용자가 다시 읽지 않는 경우 TTL 없는 키가 영영 남습니다. 대가는 팔로워마다 명령 하나가 더 붙는 것입니다. 접속이 끊긴 사용자는 30일 뒤 나눠 넣기 대상에서 빠지고, 마지막 쓰기로부터 30일 뒤 타임라인이 저절로 사라져 메모리를 돌려줍니다.
- **돌아오면 다시 만듭니다.** 10:10에 u3이 접속합니다. `tl:u3`이 없으므로 앞 절의 방법으로 다시 만듭니다. u3이 팔로우하는 일반 계정은 b뿐이므로 밥의 최근 글 103, 106을 넣습니다. 스타 s의 글은 읽을 때 합칩니다. 다시 만드는 비용은 읽을 때 모으기 한 번이며, 접속할 때 한 번만 냅니다.
- **순서가 틈을 정합니다.** 다시 만들기는 "활성으로 표시 → DB에서 최근 글 읽기 → `ZADD`" 순서로 합니다. 워커는 글이 DB에 저장된 뒤에 팔로워의 활성 여부를 보므로, DB를 읽기 전에 저장된 글은 다시 만들기가 가져오고, 그 뒤에 저장된 글은 워커가 활성 표시를 보고 넣습니다. 순서를 거꾸로 하면 그 사이에 저장된 글이 양쪽 모두에서 빠질 수 있습니다. 이 결론은 두 전제 위의 이 문서의 추론입니다. 워커가 읽는 활성 여부가 방금 쓴 값을 바로 돌려줄 것, 그리고 다시 만들기의 DB 읽기가 그 순간까지 확정된 글을 모두 볼 것(복제 지연이 있는 DB 복제본이나 오래 열어 둔 트랜잭션의 옛 시점으로 읽지 않을 것)입니다. 둘 중 하나라도 깨지면 틈이 남고, 나눠 넣기 메시지가 유실되는 경우도 이 순서로는 막지 못합니다.

비활성 기준(30일)은 "다시 만드는 비용"과 "나눠 넣는 비용"의 저울입니다. 기준을 짧게 잡으면 나눠 넣기와 메모리가 줄고 다시 만들기가 잦아지며, 길게 잡으면 그 반대입니다.

## 사용자와 글이 늘면 무엇이 달라지는가

키운 장면(활성 사용자 100만 명, 글 초당 1,000건, 조회 초당 50,000건, 상한 500)으로 봅니다.

- **명령 하나의 작업량은 거의 늘지 않습니다.** 타임라인 하나의 원소 수는 상한(500)으로 묶여 있으므로, `ZADD`, `ZREMRANGEBYRANK`, 커서 읽기의 log N도 묶여 있습니다. 늘어나는 것은 명령의 수입니다. 쓰기는 "글 수 × 평균 활성 팔로워 수", 읽기는 "조회 수 × (1 + 팔로우하는 스타 수)"로 늘어납니다.
- **나눠 넣기가 밀리면 새 글이 늦게 보입니다.** 글이 몰리는 시간에 워커가 따라가지 못하면 메시지 큐에 일이 쌓이고, 팔로워가 글을 보는 시각이 그만큼 늦어집니다. 관찰할 것은 큐에 쌓인 메시지 수와, 글 저장부터 마지막 묶음 완료까지의 시간입니다.
- **스타 계정이 늘면 읽기가 무거워집니다.** 팔로우하는 스타 수만큼 읽을 키가 늘어납니다. 스타 기준을 올리면 읽기가 줄고 나눠 넣기가 늘어납니다.

### 메모리는 타임라인 수와 타임라인 하나의 크기의 곱입니다

타임라인 하나의 크기는 원소 수, 글 ID의 길이, 내부 표현(한 덩어리인가 원소마다 따로인가), 메모리 할당기와 빌드에 따라 다르므로 재서 추정합니다. 이 문서는 재지 않았습니다.

1. 실제 글 ID 형식으로 상한만큼 찬 표본 타임라인을 만들고 `MEMORY USAGE tl:표본`으로 키 하나의 크기를 잽니다. `OBJECT ENCODING`으로 내부 표현도 확인합니다. 기본 설정에서 상한이 127 이하면 `listpack`, 그보다 크면 `skiplist`로 나옵니다("길이 상한은 넣을 때마다 자릅니다").
2. 그 값에 "타임라인을 들고 있는 사용자 수"를 곱합니다. 비활성 사용자를 넣지 않고 TTL로 지우므로 이 수는 전체 가입자가 아니라 대략 활성 사용자 수입니다.
3. 서버 전체에는 할당기의 단편화 같은 키 바깥의 메모리가 더해지므로, 실제 사용량은 `INFO memory`의 `used_memory`로 확인합니다. 지표의 뜻은 [Redis 메모리 지표](./memory-metrics.md)에서 다룹니다.

상한을 500에서 127로 줄이면 원소 수가 약 4분의 1이 될 뿐 아니라 내부 표현이 한 덩어리로 바뀌어, 원소 하나당 메모리도 줄어듭니다. 다만 이미 원소마다 따로 담긴 타임라인은 서버가 도는 동안 새 상한으로 잘라도 그 구조로 남습니다. 한 덩어리가 되는 것은 TTL로 사라졌다가 새로 만들어지는 타임라인과, 서버 재시작이나 복제본의 전체 동기화로 RDB 파일을 읽어 들일 때 기준 안에 드는 타임라인입니다. 그래서 상한을 바꾼 직후 표본을 재면 원소 수가 준 만큼은 줄어 보이지만, 표현이 바뀌어 원소 하나당 줄어드는 몫은 아직 보이지 않습니다. 대가는 127개 너머를 DB로 이어 읽는 요청이 늘어나는 것입니다. 상한 너머 스크롤이 얼마나 되는지 재 보고 정합니다. `zset-max-listpack-entries`를 상한보다 크게(상한 500이면 501 이상) 올려 한 덩어리를 유지하는 방법도 있지만, 한 덩어리 표현은 원소를 넣고 찾을 때 앞에서부터 훑으므로 원소마다 작업량이 늘어납니다. 이 설정은 서버의 모든 Sorted Set에 걸리므로, 바꾼다면 다른 Sorted Set까지 함께 재야 합니다.

### 클러스터: 타임라인은 흩어지고, 스타의 글 목록은 몰립니다

- **타임라인 키는 해시 태그 없이 둡니다.** `tl:u1`, `tl:u2`는 서로 다른 슬롯에 놓여 여러 노드에 고르게 흩어집니다. 한 명령이 키 하나만 다루므로 같은 슬롯에 모을 이유가 없습니다. 모든 타임라인에 같은 태그를 붙이면 전부 한 노드에 모여 클러스터를 쓰는 의미가 사라집니다. 태그의 규칙과 대가는 [Redis Cluster](./cluster.md)의 "해시 태그는 슬롯을 맞추는 대신 부하를 한 노드에 모읍니다"에 있습니다.
- **나눠 넣기의 파이프라인은 노드별로 갈립니다.** Lettuce는 파이프라인의 명령을 키의 슬롯에 맞는 노드로 따로 보내므로, 팔로워 1,000명의 묶음은 노드 수만큼의 작은 묶음이 되어 동시에 흐릅니다. 쓰기 부하가 노드들에 나뉘는 셈입니다. 묶음 전체의 시간은 가장 늦은 노드가 정합니다. 세부는 [Redis 파이프라이닝](./pipelining.md)의 "클러스터에서는 슬롯별로 갈립니다"에 있습니다.
- **스타의 글 목록은 노드 하나에 몰립니다.** `posts:s`를 읽는 모든 조회가 그 키가 있는 노드로 갑니다. 이 노드만 CPU가 높다면 슬롯별 통계로 원인 슬롯을 좁히고, 앱 캐시로 읽기를 줄입니다.
## Spring에서 타임라인을 다룰 때

- **명령과 메서드**: Spring Data Redis의 `ZSetOperations`(`opsForZSet()`)에서 다시 만들기는 `add(key, Set<TypedTuple>)`로 원소 여러 개를 `ZADD` 하나에 담아 보냅니다. 커서 읽기는 `reverseRangeByScore(key, min, max, offset, count)`이고, `ZREVRANGEBYSCORE`로 나갑니다. 결과는 Set이지만 점수 순서를 지켜 오므로, 타임라인과 스타 글 목록의 결과를 그 순서대로 합칠 수 있습니다.
- **커서의 경계**: 위의 `reverseRangeByScore`는 `min`과 `max`를 모두 포함하는 구간으로 보냅니다. `(104`처럼 경곗값을 빼는 표현이 이 메서드에는 없으므로, 점수가 정수인 이 설계에서는 `max`를 "커서 − 1"(103)로 줍니다. 점수가 정수가 아니라면 연결 수준의 `zRevRangeByScore`에 `Range`와 `Limit`을 넘겨 경계를 뺍니다.
- **나눠 넣기의 파이프라이닝**: `executePipelined`로 팔로워 1,000명분의 `add`와 `removeRange`를 한 번에 보냅니다. 콜백 안의 명령은 결과를 돌려주지 않고, 파이프라인은 그 호출 동안 전용 연결을 씁니다. 연결 풀이 없으면 호출마다 연결을 새로 맺으므로, 워커처럼 자주 부르는 곳에서는 풀을 켭니다. 결과 목록에는 명령마다 결과가 들어가 묶음 크기만큼 메모리를 씁니다. 세부는 [Redis 파이프라이닝](./pipelining.md)의 "파이프라이닝: executePipelined"에 있습니다.
- **원소와 키의 직렬화**: 원소는 글 ID 문자열 그대로 저장해야 합니다. `RedisTemplate`의 기본 Java 직렬화를 쓰면 원소 앞에 직렬화 머리 바이트가 붙어, 다른 서비스나 `redis-cli`가 평문 글 ID로 `ZREM`을 보내도 같은 원소를 찾지 못합니다. 키와 원소에는 `StringRedisTemplate`을 씁니다. 직렬화기의 차이는 [직렬화기 고르기](./serializer.md)에서 다룹니다.
- **점수의 타입**: 점수는 `Double`로 오갑니다. 글 ID를 `Long`에서 `Double`로 바꿀 때 2^53 안이면 값이 그대로입니다. 넘을 수 있는 ID라면 "점수로 글 ID를 씁니다"의 경고를 먼저 확인합니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 본문 |
| --- | --- | --- |
| Redis에 피드를 두면 DB 쿼리의 비용이 사라진다 | 읽을 때 모으기를 Redis로 옮기면 읽는 양이 팔로우 수에 비례하는 구조는 그대로입니다. 비용을 쓰기 쪽으로 옮기는 것이 핵심입니다 | 쓸 때 나눠 넣기와 읽을 때 모으기는 비용을 어디에 두는가 |
| 파이프라이닝으로 보내면 스타도 나눠 넣을 수 있다 | 왕복이 줄 뿐 서버가 실행할 명령 수는 그대로입니다. 1,000,000번의 `ZADD`는 어딘가에서 실행됩니다 | 흐름: 글을 DB에 저장하고, 나눠 넣기는 메시지로 맡깁니다 |
| 나눠 넣기를 재시도하면 같은 글이 두 번 들어간다 | Sorted Set에 같은 원소, 같은 점수로 다시 넣으면 아무것도 바뀌지 않습니다. 점수를 처리 시각으로 두면 이 성질이 깨집니다 | 재시도가 안전한 이유: 같은 원소, 같은 점수 |
| offset으로 페이지를 넘기면 충분하다 | 새 글이 위에 끼면 한 칸씩 밀려 같은 글이 두 번 보이고, 키를 합치는 피드에서는 뒤 페이지일수록 읽는 양이 늘어납니다 | offset은 새 글이 끼면 밀립니다 |
| 타임라인이 비면 피드가 끝난 것이다 | 타임라인은 최근 일부만 든 사본입니다. 상한 너머는 DB에 있습니다 | 상한 너머는 DB로 이어 읽습니다 |
| 사본에서 지우면 삭제가 끝난다 | 늦게 온 재시도가 지운 글을 다시 넣을 수 있습니다. 읽을 때 원본으로 확인해야 합니다 | 글 삭제 |
| 시각을 점수로 쓰는 편이 자연스럽다 | 같은 시각의 글이 커서 경계에서 빠지거나 두 번 나옵니다. 겹치지 않는 글 ID가 커서에 맞습니다. 단 2^53 안이어야 합니다 | 점수로 글 ID를 씁니다 |

**Redis 소스(8.2.10)**

- [`src/t_zset.c`](https://github.com/redis/redis/blob/8.2.10/src/t_zset.c)
  - `zsetAdd`: 이미 있는 원소면 새 점수가 현재 점수와 다를 때만 지우고 다시 넣으며, 같으면 바꾸지 않음("같은 점수로 다시 넣으면 아무것도 바뀌지 않습니다", "두 번째 `ZADD tl:u1 104 104`는 … 아무것도 바꾸지 않습니다"). listpack에 새 원소를 넣기 전에 "현재 원소 수 + 1"이 `zset_max_listpack_entries`를 넘거나 원소 길이가 `zset_max_listpack_value`를 넘으면 스킵 리스트로 전환("새 원소를 넣어 원소가 128개를 넘게 되면 … 넣기 전에", "상한이 128이면 꽉 찬 타임라인에 129번째 글이 들어오는 순간 바뀌어", "원소가 하나라도 64바이트를 넘으면")
  - `zaddGenericCommand`: 응답은 새로 더한 원소 수(`CH`가 없을 때). 같은 원소·같은 점수는 더한 수에도 바뀐 수에도 들어가지 않음. 키가 없으면 새 Sorted Set을 만들어 추가할 뿐 만료 시각을 붙이지 않음("`ZADD`가 키를 새로 만들 때 TTL을 붙이지 않기 때문입니다")
  - `zremrangeGenericCommand`, `genericZrangebyscoreCommand`: 순위 구간 삭제, 점수 구간을 `REV`와 `LIMIT`으로 읽는 경로
  - `zsetConvertToListpackIfNeeded`: listpack으로 되돌리는 변환은 집합 연산 결과를 저장하는 `zunionInterDiffGenericCommand`(와 GEO 명령)에서만 부르고, `ZREM`·`ZREMRANGEBYRANK` 경로에는 없음("`ZREM`이나 `ZREMRANGEBYRANK`로 원소를 줄여도 한 덩어리로 돌아가지 않습니다", "이미 원소마다 따로 담긴 타임라인은 서버가 도는 동안 새 상한으로 잘라도 그 구조로 남습니다")
  - `zsetTypeCreate`, `zaddGenericCommand`: 키가 없을 때 `ZADD`가 넣을 원소 수가 `zset_max_listpack_entries` 이하이고 첫 원소의 길이가 `zset_max_listpack_value` 이하이면 listpack으로 새 Sorted Set을 만듦("새로 만들어지는 타임라인 … 부터" 한 덩어리)
- [`src/rdb.c`](https://github.com/redis/redis/blob/8.2.10/src/rdb.c): `rdbLoadObject`가 Sorted Set을 읽어 들인 뒤 원소 수와 원소 길이가 `zset-max-listpack-*` 기준 안이면 listpack으로 바꿈. [`src/replication.c`](https://github.com/redis/redis/blob/8.2.10/src/replication.c)의 `readSyncBulkPayload`도 전체 동기화 때 같은 RDB 읽기 경로를 씀("서버 재시작이나 복제본의 전체 동기화로 RDB 파일을 읽어 들일 때 기준 안에 드는 타임라인")
- [`src/config.c`](https://github.com/redis/redis/blob/8.2.10/src/config.c): `zset-max-listpack-entries` 기본 128, `zset-max-listpack-value` 기본 64("기본 설정에서 128개 이하이고 원소가 모두 64바이트 이하")

| 필수 | 스타 기준과 되돌리는 기준 | 기준이 없으면 팔로워 수백만 명의 계정 글 하나가 나눠 넣기 큐를 막습니다. 너무 낮으면 읽을 키가 늘어납니다 |
| 필수 | 점수로 쓸 값과 그 범위 | 글 ID가 겹치지 않고 2^53 안이어야 커서와 재시도가 단순해집니다 |
| 필수 | 읽을 때 원본으로 무엇을 확인할지 | 삭제와 공개 범위·차단은 사본이 늦어도 지켜져야 합니다 |
| 필수 | 원본과 다시 만드는 방법 | 재시작, 장애 조치, 축출로 타임라인은 사라질 수 있습니다 |
| 알면 유리 | 타임라인 상한 | 메모리, 내부 표현(기본 설정에서 상한 127 이하면 한 덩어리), 상한 너머 DB 읽기 빈도를 함께 정합니다 |
| 알면 유리 | 비활성 기준과 타임라인 TTL | 쓰기와 메모리를 활성 사용자에 맞춥니다 |
| 참고 | `zset-max-listpack-entries` 조정 | 서버의 모든 Sorted Set에 걸리므로 다른 키까지 재고 바꿉니다 |

## 말로 설명하기

### 30초 버전

팔로우 피드는 "여러 작성자에 걸친 최신순"을 미리 만들어 두는 문제입니다. 글을 쓸 때 팔로워마다의 타임라인에 글 ID를 넣으면 읽기가 키 하나로 끝나지만, 쓰기가 팔로워 수만큼 늘어납니다. 조회가 글보다 훨씬 많으니 보통은 쓸 때 넣고, 팔로워가 아주 많은 계정만 읽을 때 합칩니다. 타임라인은 글 ID를 점수로 둔 Sorted Set이라 재시도해도 같은 결과이고, 마지막으로 본 ID를 커서로 페이지를 넘깁니다. 원본은 DB이고, 삭제와 권한은 읽을 때 원본으로 다시 확인합니다.

### 2분 버전

DB 쿼리 하나로 피드를 만들면 팔로우하는 작성자 수만큼 인덱스 구간을 읽고 합치는 일을 조회마다 반복합니다. Redis에 타임라인을 두는 이유는 이 합친 결과를 미리 만들어 두는 자리이기 때문입니다. 언제 만드는지가 선택입니다. 쓸 때 나눠 넣으면 읽기는 키 하나지만 글 하나가 팔로워 수만큼의 쓰기가 되고, 읽을 때 모으면 쓰기는 한 번이지만 조회마다 팔로우 수만큼 읽습니다. 조회가 글보다 수십 배 많으면 쓸 때 넣는 쪽이 전체 명령 수가 적습니다. 다만 팔로워 백만 명인 계정의 글 하나는 백만 번의 쓰기라, 그런 계정은 자기 글 목록에만 두고 읽을 때 합칩니다. 그 목록은 모두가 읽는 핫키가 되므로 앱에서 짧게 캐시합니다.

타임라인은 글 ID를 원소와 점수로 쓰는 Sorted Set입니다. 같은 원소를 같은 점수로 다시 넣으면 아무것도 바뀌지 않아 나눠 넣기의 재시도가 안전하고, 새로 팔로우한 계정의 옛 글도 제자리에 들어갑니다. 넣을 때마다 상한으로 자르고, 넣는 순간 하나가 더 많아지므로 상한을 127 이하로 두면 한 덩어리로 담겨 메모리가 작습니다. 페이지는 offset 대신 마지막으로 본 ID보다 작은 글을 읽어, 새 글이 끼어도 밀리지 않습니다. 타임라인은 후보 목록일 뿐이라 삭제와 공개 범위는 본문을 붙일 때 원본으로 확인하고, 사라진 타임라인은 DB에서 다시 만듭니다. 비활성 사용자에게는 넣지 않고 TTL로 지우며, 돌아오면 다시 만듭니다.

### 예상 질문과 꼬리 질문

**Q. 피드를 왜 DB 쿼리가 아니라 Redis 타임라인으로 만드나요?**
DB 인덱스는 작성자별 최신순은 갖고 있지만 여러 작성자에 걸친 최신순은 갖고 있지 않아, 조회마다 팔로우한 작성자 수만큼 구간을 읽어 합쳐야 할 수 있습니다. 사용자마다 팔로우 목록이 달라 결과를 서로 다시 쓰지도 못합니다. 타임라인은 그 합친 결과를 미리 만들어 둔 사본입니다. DB 쪽 비용은 흔한 B-tree를 가정한 추론이라 실행 계획으로 확인해야 하고, 팔로우가 적고 조회가 드물면 DB 쿼리로 충분합니다. (본문: "DB 쿼리 하나로 피드를 만들면 왜 비싸지는가")

- **꼬리: 그럼 Redis에서 읽을 때 모으면 되지 않나요?**
  읽는 양이 팔로우 수에 비례하는 구조는 그대로입니다. 명령 하나가 싸질 뿐이고, 키운 장면처럼 조회가 초당 5만 건에 팔로우가 200개면 목록 읽기가 초당 천만 건이 됩니다. 파이프라이닝은 왕복을 줄이지 명령 수를 줄이지 않습니다.

**Q. 쓸 때 나눠 넣기와 읽을 때 모으기는 무엇으로 고르나요?**
비용을 어디에 둘지의 선택입니다. 읽기와 쓰기의 비율, 팔로워 수의 분포, 새 글이 보이기까지 허용되는 시간, 메모리 예산을 봅니다. 조회가 글보다 훨씬 많고 팔로워 수가 대체로 고르면 쓸 때 넣고, 팔로워가 아주 많은 계정만 읽을 때 합칩니다. (본문: "무엇으로 고르는가")

- **꼬리: 스타 기준은 어떻게 정하나요?**
  글 하나의 나눠 넣기가 얼마나 늦어도 되는지와, 사용자가 팔로우하는 스타가 몇 명쯤인지를 같이 봅니다. 기준이 높으면 큰 나눠 넣기가 큐를 막고, 낮으면 조회마다 읽을 키가 늘어납니다. 기준 근처에서 오가지 않게 들어가는 기준과 나오는 기준을 떨어뜨립니다.
- **꼬리: 스타 글 목록이 핫키가 되면요?**
  모든 팔로워에게 같은 내용이라 앱 메모리에 짧게 캐시할 수 있습니다. 그 시간만큼 새 글이 늦게 보입니다. 복제본에서 읽는 방법도 있고, 대가는 복제 지연입니다. 노드를 늘려도 키 하나의 부하는 나뉘지 않습니다.

**Q. 타임라인을 List가 아니라 Sorted Set으로 두는 이유는요?**
비동기 나눠 넣기에서는 재시도, 늦게 온 글, 새 팔로우의 옛 글 채워 넣기가 늘 생깁니다. Sorted Set은 같은 원소가 하나뿐이라 재시도가 중복을 만들지 않고, 점수대로 제자리에 넣으며, 지우기가 O(log N)이고, 점수로 커서를 걸 수 있습니다. List는 넣기가 O(1)이고 메모리가 작지만 이 넷을 앱이 따로 막아야 합니다. (본문: "List가 아니라 Sorted Set인 이유")

**Q. 점수로 시각이 아니라 글 ID를 쓰는 이유는요?**
글 ID는 겹치지 않아 커서 경계에서 글이 빠지거나 두 번 나오지 않고, 같은 글은 언제 누가 넣어도 같은 점수라 재시도와 다시 만들기가 같은 결과를 냅니다. 대신 ID가 2^53 안이어야 합니다. 점수는 double이라 그보다 큰 정수는 일부만 정확히 담기고, 서로 다른 ID가 같은 점수가 될 수 있습니다. (본문: "점수로 글 ID를 씁니다")

- **꼬리: ID 순서와 실제 저장 순서가 다르면요?**
  번호를 먼저 받은 글이 늦게 확정되면 이미 보인 글 아래에 끼어듭니다. 이미 본 페이지보다 아래쪽이라 페이지가 밀리지는 않습니다. 다만 독자의 커서가 이미 그 아래로 내려갔다면 이번 스크롤에서는 그 글을 놓치고 다시 처음부터 내려갈 때 봅니다. 확정이 몇 초 늦는 정도라면 피드에서는 대개 받아들입니다.
- **꼬리: 시각을 점수로 쓰면 무엇을 더 해야 하나요?**
  원소를 글 ID로 두고 커서를 "점수와 글 ID의 쌍"으로 다뤄야 합니다. 같은 점수의 글이 경계에 걸릴 때를 따로 처리해야 해서 읽기가 복잡해집니다. 처리 시각을 점수로 쓰면 재시도할 때마다 점수가 바뀌어 옛 글이 위로 올라옵니다.

**Q. 나눠 넣기 워커가 같은 메시지를 두 번 처리하면 어떻게 되나요?**
같은 원소, 같은 점수로 다시 넣는 `ZADD`는 아무것도 바꾸지 않고, 상한 자르기도 이미 상한 안이면 지울 것이 없습니다. 그래서 처리 표시 키 없이 다시 하면 됩니다. 랭킹의 `ZINCRBY`처럼 더하는 갱신과 달리 "이 값으로 둔다"는 갱신이기 때문입니다. (본문: "재시도가 안전한 이유: 같은 원소, 같은 점수")

- **꼬리: 그럼 재시도로 생기는 문제는 전혀 없나요?**
  늦게 온 재시도가 그사이 지워진 글을 다시 넣을 수 있습니다. 넣기 전에 글이 있는지 확인해도 확인과 넣기 사이의 삭제는 막지 못하므로, 본문 붙이기에서 원본으로 걸러 내는 것이 최종 방어선입니다.
- **꼬리: 팔로워 백만 명을 파이프라인 하나로 보내면 안 되나요?**
  클라이언트가 결과를 들고 있는 메모리, 명령 타임아웃, 실패했을 때 어디까지 됐는지 모르는 범위가 모두 커집니다. 1,000명씩 끊고, 큰 작성자는 하위 작업으로 나눠 실패한 부분만 다시 합니다. 그리고 묶어도 서버가 실행할 명령 수는 그대로입니다.

**Q. 페이지를 offset으로 넘기면 무엇이 문제인가요?**
새 글이 맨 위에 끼면 전체가 한 칸씩 밀려 이미 본 글이 다음 페이지에 다시 나오고, 위쪽 글이 지워지면 글 하나를 건너뜁니다. 키 두 개를 합치는 피드에서는 각 키에서 "건너뛸 수 + 페이지 크기"만큼 읽어야 해서 뒤 페이지일수록 비쌉니다. 마지막으로 본 글 ID보다 작은 글을 읽는 커서는 새 글이 위에 끼어도 영향을 받지 않고, 키마다 페이지 크기만큼만 읽습니다. (본문: "페이지는 offset이 아니라 마지막으로 본 글 ID로 넘깁니다")

- **꼬리: 타임라인에서 더 읽을 게 없으면 피드 끝인가요?**
  아닙니다. 타임라인은 상한만큼의 최근 글만 든 사본이라, 상한 너머는 DB에서 커서 조건을 붙인 쿼리로 이어 읽습니다. 이 판단은 합친 결과가 아니라 목록마다 해야 합니다. 잘린 목록이 있어도 다른 목록이 페이지를 채우면 빈틈이 드러나지 않은 채 커서가 지나가 버리기 때문입니다. 상한 가까이 내려간 드문 요청에서만 일어나므로 전체 부하는 작습니다.
- **꼬리: Spring에서 `(104` 같은 제외 경계는 어떻게 주나요?**
  `reverseRangeByScore(key, min, max, offset, count)`는 양 끝을 포함하는 구간으로 보내므로, 점수가 정수인 이 설계에서는 최댓값으로 커서 − 1을 줍니다. 정수가 아니라면 연결 수준의 `zRevRangeByScore`에 `Range`와 `Limit`을 넘깁니다.

**Q. 글이 지워지거나 언팔로우하면 타임라인은 어떻게 맞추나요?**
타임라인은 후보 목록이고, 보여 줘도 되는지는 본문을 붙일 때 원본으로 확인합니다. 삭제와 공개 범위·차단은 늦으면 안 되므로 읽을 때 거르기가 필수이고, 사본에서 `ZREM`하는 정리는 빈자리를 줄이는 용도입니다. 언팔로우는 권한 문제가 아니라 몇 초 보이는 것을 받아들이고 비동기로 그 작성자의 글을 `ZREM`합니다. 타임라인에는 글 ID만 있어 작성자를 모르므로, 지울 ID는 DB에서 찾습니다. 정리 뒤 늦은 나눠 넣기 재시도가 다시 넣지 않도록 재시도는 팔로워 목록을 DB에서 다시 읽게 하고, 남는 짧은 틈까지 막으려면 읽을 때 팔로우 관계를 확인합니다. (본문: "지우기, 언팔로우, 공개 범위 변경은 읽을 때 한 번 더 거릅니다")

- **꼬리: 걸러 내면 페이지가 덜 채워지지 않나요?**
  모자라면 합친 최신순에서 마지막으로 검사한 후보 ID 아래에서 한 번 더 읽어 채웁니다. 마지막으로 보여 준 글을 기준으로 삼으면 후보가 모두 걸러졌을 때 같은 후보를 되풀이해 읽기 때문입니다. 이어 읽기 횟수에는 상한을 두고, 닿으면 덜 찬 페이지와 함께 마지막으로 검사한 후보 ID를 다음 커서로 돌려줍니다. 사본 정리를 함께 하면 이런 추가 읽기가 줄어듭니다.

**Q. Redis에서 타임라인이 사라지면요?**
DB의 글과 팔로우 관계로 다시 만듭니다. 팔로우하는 일반 계정의 최근 글을 상한만큼 읽어 `ZADD` 하나로 넣으며, 같은 원소·같은 점수라 그사이 나눠 넣기가 와도 결과가 같아서 새 키에 채워 바꿔 끼울 필요가 없습니다. 다만 그사이 들어온 다른 글 때문에 상한을 넘을 수 있으므로, 넣은 뒤 반드시 상한으로 자릅니다. 노드 하나를 통째로 잃으면 다시 만들기가 DB에 몰리므로 동시 실행 수에 상한을 둡니다. (본문: "원본은 DB이고, 사라진 타임라인은 다시 만듭니다")

- **꼬리: 팔로우가 하나도 없는 사용자는요?**
  넣을 글이 없어 키가 생기지 않으므로 매 조회마다 다시 만들게 됩니다. Sorted Set은 원소가 없으면 키도 없기 때문입니다. "다시 만들었음" 표시를 짧은 TTL로 따로 둡니다.
- **꼬리: AOF를 `always`로 켜면 원본으로 써도 되지 않나요?**
  재시작 때의 유실은 줄지만, 비동기 복제의 장애 조치 유실과 축출은 막지 못합니다. 그리고 공개 범위와 삭제는 어차피 원본 확인이 필요합니다.

**Q. 비활성 사용자는 어떻게 다루나요?**
30일 안에 접속하지 않은 사용자에게는 나눠 넣지 않고, 타임라인은 읽고 쓸 때마다 거는 TTL로 저절로 사라지게 둡니다. 쓸 때도 거는 것은 `ZADD`가 새로 만든 키에는 TTL이 없기 때문입니다. 돌아오면 다시 만듭니다. 다시 만들기는 활성 표시를 먼저 하고 DB를 읽어야, 그 사이에 저장된 글이 양쪽에서 빠지지 않습니다. 이 결론은 워커가 활성 여부를 최신 값으로 읽고, 다시 만들기의 DB 읽기가 그 순간까지 확정된 글을 모두 본다는 전제의 추론입니다. (본문: "비활성 사용자에게는 넣지 않고, 돌아오면 다시 만듭니다")

- **꼬리: 비활성 기준은 어떻게 정하나요?**
  나눠 넣는 비용과 다시 만드는 비용의 저울입니다. 짧으면 쓰기와 메모리가 줄고 다시 만들기가 잦아지며, 길면 반대입니다.

**Q. 타임라인 메모리는 어떻게 추정하나요?**
"타임라인을 들고 있는 사용자 수 × 타임라인 하나의 크기"입니다. 크기는 원소 수, ID 길이, 내부 표현, 할당기에 따라 다르므로 상한만큼 찬 표본 키를 `MEMORY USAGE`로 재고 `OBJECT ENCODING`으로 표현을 확인합니다. 비활성 사용자를 빼고 TTL로 지우므로 곱할 수는 대략 활성 사용자 수입니다. 기본 설정에서 상한을 127 이하로 두면 한 덩어리로 담겨 원소당 메모리도 줄지만, 상한 너머 DB 읽기가 늘어납니다. (본문: "메모리는 타임라인 수와 타임라인 하나의 크기의 곱입니다")

- **꼬리: `zset-max-listpack-entries`를 올리면요?**
  상한 500도 한 덩어리로 담을 수 있지만, 한 덩어리 표현은 넣고 찾을 때 앞에서부터 훑어 원소마다 작업량이 늘고, 설정이 서버의 모든 Sorted Set에 걸립니다. 바꾼다면 다른 키까지 함께 잽니다.

**Q. 클러스터에서는 무엇이 달라지나요?**
타임라인은 사용자마다 다른 키라 해시 태그 없이 두면 노드들에 고르게 흩어지고, 나눠 넣기의 파이프라인은 Lettuce가 노드별로 나눠 보내 쓰기도 나뉩니다. 한 명령이 키 하나만 다루므로 슬롯을 맞출 일이 없습니다. 반대로 스타의 글 목록은 키 하나라 노드 하나에 읽기가 몰리므로, 그 노드만 바쁘면 슬롯별 통계로 확인하고 앱 캐시로 줄입니다. (본문: "클러스터: 타임라인은 흩어지고, 스타의 글 목록은 몰립니다")

- **꼬리: 사용자 타임라인과 관련 키를 해시 태그로 묶으면 안 되나요?**
  한 번의 실행으로 함께 다뤄야 할 키가 없으므로 묶을 이유가 없습니다. 모든 타임라인에 같은 태그를 붙이면 전부 한 노드에 모여 클러스터를 쓰는 의미가 사라집니다.

**Q. Spring에서 주의할 점은요?**
원소는 `StringRedisTemplate`처럼 문자열 직렬화기로 글 ID를 그대로 저장해야 다른 서비스와 `redis-cli`가 같은 원소를 찾습니다. 점수는 `Double`로 오가므로 2^53 안의 ID인지 확인합니다. 나눠 넣기는 `executePipelined`로 묶되 전용 연결을 쓰므로 워커에는 연결 풀을 켜고, 묶음 크기만큼 결과 목록이 메모리를 쓴다는 점을 기억합니다. 커서 읽기의 `reverseRangeByScore`는 양 끝을 포함하므로 커서 − 1을 최댓값으로 줍니다. (본문: "Spring에서 타임라인을 다룰 때")

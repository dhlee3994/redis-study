# 메시지 큐 기초: 맡긴 일은 왜 사라지거나 두 번 처리되는가

> **핵심 질문**: 일을 바로 처리하지 않고 메시지로 맡겨 두면 무엇을 얻고 무엇을 잃는가? 맡긴 메시지는 어느 순간에 사라지거나 두 번 처리되며, 메시지를 받아 처리하는 쪽은 이를 어떻게 다뤄야 하는가?
>
> **범위**: 특정 제품에 묶이지 않는 공통 원리를 다룹니다. Kafka, RabbitMQ, Redis는 방식의 차이를 보여 주는 예로만 쓰며, 각 제품의 설정과 기본값은 다루지 않습니다. 메시지 순서 보장, 브로커 자체의 복제와 장애 조치는 범위 밖입니다. 제품에 관한 서술은 "근거"에 적은 Kafka 4.3, RabbitMQ 4.3 공식 문서, Redis 공식 문서(redis/docs 커밋 `e53775d`), Spring Framework 6.2.19·Spring Boot 3.5.16 소스로 확인했습니다.

## 배경 지식

### 이 문서의 예시: 주문 완료 메시지 3건

문서 끝까지 다음 장면 하나를 씁니다.

- 주문 API는 주문이 끝날 때마다 "주문 완료" 메시지를 하나 남깁니다. 메시지는 #101, #102, #103 세 건이고, #101의 내용은 `{주문 ID: 101, 회원 ID: 7, 금액: 30000}`입니다.
- 이 메시지로 해야 할 일은 두 가지입니다.
  - **포인트 적립**: 워커 서버 두 대(P1, P2)가 나눠 처리하고, 결과를 포인트 DB에 씁니다.
  - **알림 발송**: 워커 서버 한 대(N1)가 외부 알림 API를 호출합니다.
- 주문 API와 워커 사이에는 메시지를 맡아 두는 별도 서버(브로커)가 있습니다.

```text
주문 API ──(#101, #102, #103)──▶ [ 브로커 ] ──▶ 포인트 워커 P1, P2 ──▶ 포인트 DB
                                      │
                                      └──────▶ 알림 워커 N1 ──▶ 외부 알림 API
```

화살표는 메시지가 흘러가는 방향입니다. 브로커가 워커에게 메시지를 밀어 주는지(push), 워커가 브로커에서 가져가는지(pull)는 시스템마다 다르지만 이 문서의 결론은 어느 쪽이든 같습니다. 그림에는 주문을 저장하는 주문 DB를 뺐습니다. 주문 저장과 메시지 남기기 사이의 틈은 "보내는 쪽과 브로커에도 같은 틈이 있습니다"에서 따로 다룹니다.

### 이 문서에 필요한 용어

- **메시지**: "이런 일이 일어났다" 또는 "이 일을 해 달라"를 담은 데이터 한 건입니다. 예시의 #101이 메시지 하나입니다.
- **생산자(producer)**: 메시지를 남기는 쪽입니다. 예시에서는 주문 API입니다.
- **소비자(consumer)**: 메시지를 받아 처리하는 쪽입니다. 예시에서는 워커 P1, P2, N1입니다.
- **브로커(broker)**: 생산자와 소비자 사이에서 메시지를 받아 보관하고 소비자에게 전달하는 별도 서버입니다. 생산자와 소비자는 서로를 직접 호출하지 않고 브로커하고만 통신합니다.
- **메시지 큐**: 이 말은 두 가지 뜻으로 쓰입니다. 넓게는 브로커를 두고 메시지로 일을 넘기는 방식 전체를 가리키고, 좁게는 뒤에서 볼 "처리하면 지워지는" 방식 하나를 가리킵니다. 이 문서 제목은 넓은 뜻이고, 본문에서는 좁은 뜻을 **큐형**이라고 따로 부릅니다.

### 워커는 죽을 수 있다고 가정합니다

- **한 줄**: 프로세스는 자기만의 메모리 공간을 가진 실행 단위입니다. 원리는 [프로세스와 스레드](./process-and-thread.md)에서 다룹니다.
- **이 주제에서는**: 워커 프로세스가 배포 중 강제 종료, 메모리 부족, 서버 장애로 하던 일을 마치지 못하고 끝나면(비정상 종료), 그 메모리에 들고 있던 메시지와 처리 중이던 상태도 함께 사라집니다. 이 문서의 유실과 중복은 대부분 "하필 그 사이에 죽으면"에서 나옵니다.

### 서로 다른 프로세스와 저장소 사이에서 생기는 세 가지 문제

원리는 모두 [경쟁 상태와 원자성](./race-condition-and-atomicity.md)에서 다룹니다. 여기서는 한 줄 정의와 이 주제에서 어디에 나타나는지만 적습니다.

- **경쟁 상태**: 여러 실행 흐름이 같은 데이터를 읽고 바꿀 때, 실행 순서에 따라 결과가 틀어지는 문제입니다. 이 주제에서는 워커 두 대가 같은 메시지를 동시에 처리하게 될 때 나타납니다.
- **다른 저장소와는 묶이지 않는 원자성**: 저장소 하나가 보장하는 원자성은 그 저장소 안에서만 통합니다. 이 주제에서는 "포인트 DB에 적립"과 "브로커에 처리 완료 알림"이 서로 다른 저장소에 보내는 요청이라, 둘 중 하나만 성공한 상태가 생길 수 있습니다.
- **응답을 받지 못한 요청과 멱등성**: 요청을 보낸 쪽은 응답을 받지 못하면, 요청이 실행되지 않았는지 실행된 뒤 응답만 사라졌는지 구분할 수 없습니다. 같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질을 멱등성이라고 합니다. 이 주제에서는 생산자와 브로커 사이, 브로커와 소비자 사이 모두에서 이 문제가 생기고, 멱등성이 그 해결의 중심이 됩니다.

### 동기 처리와 비동기 처리

- **한 줄**: 동기 처리는 일을 요청한 쪽이 결과가 나올 때까지 기다리는 방식이고, 비동기 처리는 일을 맡겨 두고 결과를 기다리지 않은 채 다음으로 넘어가는 방식입니다.
- **비유**: 동기 처리는 민원 창구에서 서류 처리가 끝날 때까지 서서 기다리는 것입니다. 비동기 처리는 접수함에 신청서를 넣고 돌아가면 담당자가 나중에 처리하는 것입니다. 접수함이 브로커이고, 신청서가 메시지입니다.
- **실제로는**:
  - 주문 API가 포인트 서비스를 직접 호출하면(동기), 주문 요청을 처리하는 스레드는 포인트 적립이 끝날 때까지 묶여 있습니다. 포인트 서비스가 느려지면 주문 응답도 느려지고, 포인트 서비스가 죽으면 주문 API도 오류를 받습니다.
  - 브로커를 쓰면(비동기) 주문 API는 "메시지를 남기는 요청" 한 번만 기다립니다. 이것도 네트워크 왕복이므로 공짜는 아닙니다. 달라지는 것은 기다리는 대상입니다. 포인트 적립 완료가 아니라 **브로커가 메시지를 받았다는 응답**을 기다립니다.
  - Spring의 `@Async`도 비동기이지만, 맡긴 일이 머무는 곳이 다릅니다.
    - `@Async`를 붙인 메서드를 호출하면, 호출한 스레드는 끝나기를 기다리지 않고 바로 다음 줄로 넘어갑니다. 메서드 본문은 같은 JVM 안의 다른 스레드가 실행합니다.
    - 그 다른 스레드가 어디서 나오는지는 실행기(executor) 설정이 정합니다. Spring Boot 3.5.16의 기본 자동 구성에서는 스레드 풀(`ThreadPoolTaskExecutor`, 기본 core 8개, 대기열 크기 `Integer.MAX_VALUE`)에서 나옵니다. 스레드 풀은 일을 마친 스레드를 없애지 않고 다음 일에 다시 쓰는 장치이며, 원리는 [프로세스와 스레드](./process-and-thread.md)에서 다룹니다. 이 구성에서는 8개가 모두 바쁘면 남는 일이 차례가 올 때까지 대기열에서 기다립니다.
    - 가상 스레드(JVM이 관리하는 가벼운 스레드) 설정(`spring.threads.virtual.enabled`)을 켜거나, Spring Boot 없이 실행기 빈을 두지 않으면 사정이 다릅니다. 작업마다 새 스레드를 만드는 `SimpleAsyncTaskExecutor`가 쓰여 풀도 대기열도 없습니다(Spring Framework 6.2.19 `AsyncExecutionInterceptor.getDefaultExecutor`, Spring Boot 3.5.16 `TaskExecutorConfigurations`).
    - 어느 경우든 실행 중인 일도, 대기열이 있다면 거기서 기다리는 일도 결국 주문 API JVM의 메모리에 있는 객체입니다. 그래서 주문 API 프로세스가 죽으면 함께 사라집니다.
    - 브로커를 쓰는 핵심 이유는 맡긴 일을 이렇게 **생산자 프로세스 바깥에** 두는 데 있습니다.
- **이 주제에서는**: 주문 API는 #101을 브로커에 남긴 뒤 바로 "주문 완료"를 응답합니다. 포인트가 언제 적립될지는 주문 API가 모릅니다.

## 메시지를 맡기면 생산자가 소비자의 장애와 속도에서 분리됩니다

브로커를 사이에 두면 주문 API와 포인트 워커가 서로를 직접 기다리지 않게 됩니다. 여기서 세 가지를 얻습니다.

- **장애 분리**: P1, P2가 모두 배포 중이라 멈춰 있어도 주문은 성공합니다. #101~#103은 브로커에 남아 있다가 워커가 돌아오면 처리됩니다.
- **속도 분리(완충)**: 주문이 순간적으로 몰려도 워커는 자기 속도로 처리합니다. 몰린 만큼은 브로커에 쌓였다가 천천히 줄어듭니다.
- **생산자 변경 없이 소비자 추가**: 알림 발송을 나중에 붙여도 주문 API 코드는 바뀌지 않습니다. 대신 메시지의 형식이 생산자와 모든 소비자 사이의 약속이 되므로, 형식을 바꿀 때는 모든 소비자를 함께 고려해야 합니다.

대가도 분명합니다.

- **결과가 바로 확정되지 않습니다.** 사용자가 주문 직후 포인트를 조회하면 아직 적립 전일 수 있습니다. 시간이 지나면 결국 맞춰지는 상태를 받아들여야 합니다.
- **운영 대상이 하나 늘어납니다.** 브로커가 죽거나 느려지면 주문 API가 메시지를 남기지 못합니다.
- **유실·중복·지연을 설계해야 합니다.** 메시지가 프로세스 사이를 오가므로, 배경 지식에서 본 "응답을 받지 못한 요청" 문제가 구간마다 생깁니다. 이 문서의 나머지가 이 문제입니다.
- **흐름을 따라가기 어려워집니다.** 요청 하나의 처리가 여러 프로세스로 흩어집니다. 주문 ID 같은 공통 식별자를 모든 로그에 남기지 않으면 원인을 추적하기 어렵습니다.

그래서 결과가 응답에 꼭 필요한 일은 맡기지 않습니다. 예를 들어 결제 승인 여부는 주문 성공 여부를 결정하므로 동기로 확인합니다. 포인트 적립과 알림처럼 "주문은 이미 성공이고, 조금 늦게 처리돼도 되는 일"이 맡기기에 맞습니다.

## 큐형은 처리된 메시지를 지우고, 로그형은 읽어도 남깁니다

- **한 줄**: 큐형 브로커는 소비자가 처리를 끝낸 메시지를 지웁니다. 로그형 브로커는 메시지를 뒤에 덧붙이기만 하고, 읽었다고 지우지 않습니다.
- **비유**: 큐형은 접수함입니다. 담당자가 신청서를 꺼내 처리하면 접수함에서 없어집니다. 로그형은 접수 대장입니다. 신청이 올 때마다 대장에 한 줄씩 적고, 부서마다 "몇 번째 줄까지 처리했다"는 책갈피를 따로 끼워 둡니다. 대장의 줄은 처리해도 지워지지 않습니다.
- **실제로는**:
  - 큐형은 Kotlin `ArrayDeque`의 `removeFirst()`와 비슷합니다. 다른 점은, 꺼내는 순간 바로 지우지 않고 소비자가 처리를 끝냈다고 알릴 때까지 보관한다는 것입니다. 이 알림은 다음 절의 ACK입니다. RabbitMQ의 일반 큐가 이 방식입니다.
  - 로그형은 `ArrayList`에 `add`만 하고, 소비자마다 "다음에 읽을 인덱스"를 따로 들고 있는 것과 비슷합니다. 이 위치를 **오프셋(offset)**이라고 부르는 시스템이 많습니다. 다른 점은, 위치를 소비자 메모리에만 두지 않고 브로커 쪽에 기록해 둔다는 것입니다. 그래야 소비자가 죽었다 살아나도 이어 읽을 수 있습니다. Kafka가 이 방식입니다.
  - 로그형에서 메시지를 지우는 기준은 "다 읽었는가"가 아니라 보존 정책입니다. 정해 둔 기간이나 크기를 넘은 오래된 메시지부터 잘라 냅니다.
- **이 주제에서는**: P1이 #101을 처리한 직후의 상태를 비교하면 다음과 같습니다.

```text
큐형: 목적마다 큐를 따로 두고, 브로커가 메시지를 각 큐에 복사해 넣습니다.
  포인트용 큐   [#102, #103]          ← 처리된 #101은 지워짐
  알림용 큐     [#101, #102, #103]    ← 알림은 아직 처리 전

로그형: 로그 하나를 두고, 목적마다 위치만 따로 둡니다.
  로그          [#101, #102, #103]    ← 처리해도 그대로 남음
  포인트 위치   → #102 차례
  알림 위치     → #101 차례
```

이 차이에서 다음 결과가 나옵니다.

| 질문 | 큐형 | 로그형 |
| --- | --- | --- |
| 같은 메시지를 여러 목적이 읽으려면 | 목적마다 큐를 두고 메시지를 복사 | 목적마다 위치만 추가 |
| 처리한 메시지를 다시 처리하려면(버그 수정 후 재처리 등) | 이미 지워져 불가능. 생산자가 다시 보내야 함 | 위치를 되돌리면 가능. 단, 보존 기간 안에 있는 메시지만 |
| 저장 공간 | 처리된 만큼 줄어듦. 소비가 멈추면 쌓임 | 처리와 상관없이 보존 기간만큼 쌓임 |
| 추가로 정해야 하는 것 | 목적별 큐 구성 | 보존 기간과 크기 |

### 저장하지 않는 방송(Pub/Sub)과 구분합니다

브로커가 메시지를 보관하지 않고, 그 순간 연결되어 듣고 있는 소비자에게만 전달하는 방식도 있습니다. 라디오 방송처럼, 꺼져 있던 동안의 방송은 다시 들을 수 없습니다. 예시에서 N1이 재시작하는 몇 초 사이에 #102가 나왔다면 N1은 #102를 영영 받지 못합니다. 브로커가 저장 공간을 쓰지 않고 전달이 단순한 대신, 놓친 메시지를 되찾을 방법이 없습니다.

"Pub/Sub(발행/구독)"이라는 이름은 제품마다 뜻이 다릅니다. 이름에 Pub/Sub이 들어가도 메시지를 저장해 두는 서비스가 있습니다. 이름이 아니라 **소비자가 없던 동안의 메시지를 저장하는가**로 구분합니다.

### Redis 안에도 세 방식이 모두 있습니다

Redis는 메시지를 넘기는 데 쓸 수 있는 기능을 셋 제공하고, 각각 이 절에서 본 방식에 대응합니다.

- **Pub/Sub**: 저장하지 않는 방송입니다. Redis 공식 문서는 Pub/Sub이 최대 한 번 전달이며, 구독자가 처리하지 못한 메시지는 영영 사라진다고 밝힙니다.
- **List**: 생산자가 넣고 소비자가 꺼내는 큐형입니다. 다만 꺼내는 순간 원소가 리스트에서 빠지므로, ACK를 기다리지 않고 지우는 큐형입니다. 공식 문서는 소비자가 메시지를 받은 직후 처리 전에 죽으면 메시지를 잃을 수 있다고 설명하고, 꺼내면서 "처리 중" 리스트에 옮겨 두었다가 처리 뒤 지우는 패턴을 제시합니다.
- **Streams**: 로그형입니다. 읽어도 지우지 않고, 소비자 그룹과 "전달했지만 끝나지 않은 메시지" 기록을 Redis가 관리합니다.

그래서 Redis로 메시지를 넘길 때도 이 문서의 판단을 그대로 씁니다. 소비자가 없던 동안의 메시지를 저장해야 하는지, 큐형과 로그형 중 무엇이 맞는지, ACK를 언제 보내는지를 먼저 정하고 기능을 고릅니다.

## 소비자가 여럿이면 나눠 받기와 모두 받기를 구분합니다

예시에는 성격이 다른 두 관계가 있습니다.

- **나눠 받기**: P1과 P2는 같은 일을 합니다. 한 메시지는 둘 중 하나만 받아야 합니다. 둘 다 받으면 포인트가 두 번 적립됩니다. 목적은 처리량을 늘리는 것입니다.
- **모두 받기**: 포인트 적립과 알림 발송은 다른 일입니다. 각자 모든 메시지를 받아야 합니다.

실제 시스템은 둘을 함께 씁니다. 같은 일을 하는 소비자를 하나의 **소비자 그룹**으로 묶고, 그룹 안에서는 나눠 받고, 그룹끼리는 모두 받습니다.

```text
메시지         #101   #102   #103
포인트 그룹     P1     P2     P1      ← 그룹 안에서는 나눠 받기
알림 그룹       N1     N1     N1      ← 그룹마다 모든 메시지 받기
```

그림의 배정(#101은 P1, #102는 P2)은 가능한 한 가지일 뿐이며, 누가 어떤 메시지를 받는지는 시스템이 정합니다. 큐형에서는 목적별 큐 하나에 소비자를 여럿 붙이면 그 큐 안에서 나눠 받게 되고, 로그형에서는 그룹마다 위치를 하나씩 둡니다.

나누는 단위는 시스템마다 다릅니다. 메시지 하나씩 나눠 주는 시스템도 있고, Kafka의 소비자 그룹처럼 로그를 여러 조각(파티션)으로 쪼개 두고 조각 단위로 그룹 안의 소비자에게 배정하는 시스템도 있습니다. 조각 단위로 나누면 한 조각은 그룹 안의 소비자 하나만 읽으므로, 그룹 안에서 동시에 일하는 소비자 수가 조각 수를 넘지 못합니다. 같은 Kafka라도 share group은 한 조각을 여러 소비자가 나눠 읽을 수 있어, 소비자 수가 조각 수를 넘을 수 있습니다(Kafka 4.3 Design "The Share Consumer").

나눠 받기에는 대가가 있습니다. P1이 #101을, P2가 #102를 동시에 처리하면 #102가 먼저 끝날 수 있습니다. 메시지 사이에 순서 의존이 있으면(같은 회원의 적립과 적립 취소처럼) 문제가 됩니다. 순서를 지키는 방법은 이 문서의 범위 밖입니다.

## 받았다와 처리했다는 다릅니다: ACK

- **한 줄**: ACK(acknowledgement, 확인 응답)는 소비자가 브로커에 "이 메시지 처리를 끝냈다"고 알리는 신호입니다.
- **비유**: 접수함 비유를 이어 갑니다. 담당자가 신청서를 꺼내 가면 관리자는 "누가 몇 번 신청서를 가져갔다"고 장부에 적어 둡니다. 담당자가 처리 완료 도장을 받아 오면 그 줄을 지웁니다. 담당자가 도장 없이 사라지면, 관리자는 그 신청서를 다른 담당자에게 다시 줍니다.
- **실제로는**:
  - 브로커는 메시지를 소비자에게 넘긴 뒤 ACK가 올 때까지 그 메시지를 "전달했지만 끝나지 않은 메시지"로 따로 기록합니다. 시스템마다 pending, unacked 같은 이름을 씁니다.
  - ACK가 오면 큐형은 메시지를 지우고, 로그형은 그 그룹의 진행 상황을 앞으로 옮깁니다. 로그형에서는 메시지마다 ACK를 보내는 시스템도 있고, "여기까지 처리했다"는 위치 하나를 기록(커밋)해 ACK를 대신하는 시스템도 있습니다. Kafka의 소비자 그룹(consumer group)은 뒤쪽입니다. Kafka 4.3에는 레코드마다 ACK하고 전달 시도 횟수를 세는 share group도 따로 있습니다(Design "The Share Consumer").
  - 비유와 다른 점이 중요합니다. 비유의 관리자는 담당자가 사라진 것을 바로 압니다. 브로커는 소비자가 죽었는지, 느리게 처리하고 있을 뿐인지 바로 구분하지 못합니다. 연결이 끊기거나 정해 둔 시간 동안 ACK가 없을 때 "아마 죽었다"고 판단할 뿐입니다. 이 판단은 "처리 중에 사라진 소비자의 메시지는 다시 전달됩니다"에서 다룹니다.
- **이 주제에서는**: P1이 #101을 받고 포인트 DB에 쓰기 전에 죽으면, ACK가 없으므로 #101은 끝나지 않은 메시지로 남고 결국 P2에게 다시 전달됩니다. 포인트는 빠지지 않습니다.

## ACK를 언제 보내는가가 유실과 중복을 가릅니다

P1이 #101을 처리하는 일은 세 단계입니다.

1. 브로커에서 #101을 받습니다.
2. 포인트 DB에 적립합니다.
3. 브로커에 ACK를 보냅니다.

2번은 포인트 DB에, 3번은 브로커에 보내는 요청입니다. 배경 지식에서 본 대로 서로 다른 저장소에 대한 요청은 하나의 원자적 단위로 묶이지 않습니다. 그래서 두 요청 사이에 P1이 죽는 순간은 언제나 있을 수 있고, 무엇을 먼저 하느냐에 따라 결과가 갈립니다.

```text
ACK를 먼저:  받기 → ACK → ✕ 죽음      브로커는 끝난 줄 앎. 적립은 안 됨          → 유실
적립을 먼저: 받기 → 적립 → ✕ 죽음     적립은 됐지만 브로커는 모름. P2가 다시 받음 → 중복
```

여기서 화살표는 실행 순서입니다.

| ACK 시점 | 그 사이에 죽으면 | 전달 보장의 이름 | 맞는 일 |
| --- | --- | --- | --- |
| 처리 전 | 처리되지 않은 채 끝남(유실) | 최대 한 번(at-most-once) | 일부 빠져도 되는 일. 예: 곧 다음 값이 덮어쓰는 실시간 접속자 수 |
| 처리 후 | 다시 전달되어 또 처리됨(중복) | 최소 한 번(at-least-once) | 빠지면 안 되는 일. 예: 포인트 적립 |

Kafka 문서도 같은 구분을 씁니다. 위치를 처리 전에 저장하면 최대 한 번, 처리 후에 저장하면 최소 한 번이라고 설명합니다. RabbitMQ 문서는 메시지를 보내는 즉시 전달 완료로 치는 자동 ACK를 두고, 처리량을 얻는 대신 전달의 안전성을 내준다고 설명합니다.

### 정확히 한 번은 전달만으로 만들 수 없습니다

"이 메시지가 정확히 한 번(exactly-once) 처리된다"는 결과는 브로커 혼자 보장할 수 없습니다. 처리 결과가 브로커 바깥(포인트 DB, 외부 알림 API)에 남기 때문에, 브로커는 그 결과가 실제로 남았는지 볼 수 없습니다.

일부 시스템은 범위를 좁혀 정확히 한 번을 제공합니다. 예를 들어 Kafka 문서는 Kafka의 토픽에서 읽어 다시 Kafka의 토픽에 쓰는 경우에 한해 트랜잭션으로 이를 제공하고, 다른 저장소가 목적지라면 그 저장소의 협조가 필요하다고 밝힙니다. 그래서 실무에서 "정확히 한 번 처리한 것과 같은 결과"는 보통 **최소 한 번 전달 + 소비자의 멱등 처리**로 얻습니다.

### 보내는 쪽과 브로커에도 같은 틈이 있습니다

유실과 중복은 소비자 쪽에서만 생기지 않습니다.

- **생산자 → 브로커**: 주문 API가 #101을 보냈는데 응답을 받지 못했다고 합시다. 다시 보내면 브로커에 #101이 두 건 생길 수 있고(중복), 다시 보내지 않으면 사라질 수 있습니다(유실).
- **브로커의 보관**: 브로커가 "받았다"고 응답한 시점에 메시지가 디스크나 다른 서버에 안전하게 남았는지는 브로커와 설정마다 다릅니다. 메모리에만 있다가 브로커가 죽으면 사라질 수 있습니다.
- **주문 저장 → 메시지 남기기**: 주문은 주문 DB에, 메시지는 브로커에 남기므로 이것도 서로 다른 저장소입니다. 주문 저장 직후 주문 API가 죽으면 주문은 있는데 메시지가 없습니다. 이 틈을 메우는 대표적인 방법은, 보낼 메시지를 주문과 **같은 DB 트랜잭션**으로 기록해 두고 별도 과정이 그 기록을 읽어 브로커로 보내는 것입니다(트랜잭셔널 아웃박스). 이 방법도 보내기를 재시도하므로 같은 메시지가 두 번 갈 수 있습니다. 세부는 이 문서의 범위 밖입니다.

그래서 "이 브로커는 메시지를 잃지 않는다"는 말을 들으면 어느 구간에 대한 말인지, 어떤 설정을 전제로 하는지 확인해야 합니다. 유실을 막는 장치는 대개 "확실하지 않으면 다시 보낸다"이므로, 유실을 줄이면 그 대가로 중복이 생깁니다.

## 중복은 막기보다 견디게 만듭니다: 멱등한 소비자

최소 한 번 전달을 고르면, 같은 메시지가 두 번 오는 것을 고장이 아니라 정상 동작으로 받아들여야 합니다. 그리고 두 번 처리해도 결과가 한 번과 같도록 소비자를 만듭니다.

- **같은 메시지인지는 업무 ID로 판단합니다.** 브로커가 붙이는 메시지 ID보다 주문 ID 101이 안전합니다. 주문 API가 응답을 못 받아 #101을 다시 보내면, 브로커 입장에서는 새 메시지이므로 메시지 ID가 달라질 수 있습니다. 주문 ID는 같습니다. "주문 101의 포인트 적립"이라는 일 단위로 생각하면 기준이 정해집니다.
- **"처리했다"는 기록과 처리를 한 원자적 단위로 남깁니다.** 포인트 DB에 "적립을 끝낸 주문 ID" 기록을 두고, 적립과 그 기록을 같은 DB 트랜잭션에서 남깁니다. 주문 ID에 유니크 제약을 걸어 두면, 두 번째 시도는 기록 단계에서 실패하고 트랜잭션 전체가 취소되어 적립도 일어나지 않습니다. 그러면 #101을 다시 받은 P2는 이미 처리된 주문임을 확인하고 ACK만 보냅니다.
- **확인과 처리를 따로 하면 안 됩니다.** 뒤에서 볼 처리 제한 시간 때문에, P1이 아직 처리 중인 #101이 P2에게도 전달될 수 있습니다. 두 워커가 같은 메시지를 동시에 처리하는 것입니다. 이때 "기록이 있나?"를 조회한 뒤 적립하면, 둘 다 "없음"을 보고 둘 다 적립합니다. 배경 지식에서 본 경쟁 상태입니다.
- **멱등하게 만들기 어려운 일도 있습니다.** 알림 발송은 결과가 외부 API에 남습니다. N1이 알림을 보낸 직후, 발송 기록을 남기기 전에 죽으면 다시 보내게 됩니다. 외부 API가 요청 ID(멱등 키)를 받아 같은 요청을 한 번만 처리해 주면 그 기능을 쓰고, 그렇지 않으면 드문 중복 알림을 받아들일지 정해야 합니다.

## 처리 중에 사라진 소비자의 메시지는 다시 전달됩니다

ACK 없이 남은 메시지를 다른 소비자에게 넘기는 계기는 두 가지입니다.

- **연결이 끊긴 것을 감지했을 때**: RabbitMQ 문서는 소비자의 연결이나 채널이 닫히면 ACK되지 않은 메시지를 자동으로 다시 큐에 넣는다고 설명합니다. 다시 전달되는 메시지에는 "재전달"이라는 표시가 붙습니다.
- **정해 둔 시간 동안 ACK가 없을 때**: 연결은 살아 있지만 처리가 멈춘 경우를 잡기 위한 기준입니다. 이 문서에서는 이 시간을 **처리 제한 시간**이라고 부릅니다. 시스템마다 이름과 방식이 다릅니다.

누가 메시지를 넘기는지도 시스템마다 다릅니다. 브로커가 자동으로 다시 내놓는 시스템도 있고, 살아 있는 소비자가 "오래 처리 중인 메시지를 내가 가져가겠다"고 직접 요청해야 하는 시스템도 있습니다. 뒤쪽이라면, 그 회수 작업을 누군가 실행하지 않는 한 메시지는 영영 끝나지 않은 상태로 남습니다.

처리 제한 시간은 양쪽으로 대가가 있습니다.

| 처리 제한 시간 | 생기는 일 |
| --- | --- |
| 너무 짧게 | P1이 느릴 뿐인데 #101을 P2에게도 넘깁니다. 같은 메시지를 둘이 동시에 처리해 중복이 늘고, 일이 몰릴수록 느려져 더 자주 넘어가는 악순환이 생길 수 있습니다. |
| 너무 길게 | P1이 정말 죽었을 때 #101이 그만큼 늦게 처리됩니다. |

그래서 정상 처리 시간 중 느린 쪽보다 넉넉하게 잡고, 그래도 생기는 중복은 멱등 처리로 견딥니다.

### 계속 실패하는 메시지는 따로 떼어 냅니다

- **독 메시지(poison message)**: 형식이 잘못됐거나 코드 버그를 건드려 처리할 때마다 실패하는 메시지입니다. 예를 들어 #103의 금액 필드가 비어 있어 적립 코드가 매번 예외를 던진다고 합시다.
- **그냥 두면**: 실패 → ACK 없음 → 재전달 → 실패가 끝없이 반복됩니다. 워커의 시간을 계속 쓰고, 순서대로 처리해야 하는 구조라면 뒤의 메시지까지 막습니다.
- **대응**: 메시지마다 몇 번 전달됐는지 세어, 정한 횟수를 넘으면 별도 보관 장소(데드 레터 큐, dead letter queue)로 옮기고 원래 흐름에서는 끝난 것으로 처리합니다. 사람이 원인을 고친 뒤 다시 넣습니다. 옮기기만 하고 아무도 들여다보지 않으면 그것은 조용한 유실이므로, 옮겨진 메시지 수에 알림을 겁니다.

## 소비가 생산보다 느리면 밀린 양이 쌓이고, 결국 무언가를 잘라 내야 합니다

- **밀린 양(backlog)**: 아직 처리되지 않은 메시지의 양입니다. 로그형에서는 마지막 메시지와 그룹 위치의 차이라는 뜻으로 lag라고도 부릅니다. 가상의 숫자로 예를 들면, 주문 메시지가 초당 100건 들어오고 P1, P2가 합쳐 초당 80건을 처리하면 1분마다 1,200건씩 밀립니다. 이 숫자는 설명을 위해 지어낸 값입니다.
- **무엇으로 보나**: 밀린 건수와 **가장 오래된 미처리 메시지가 기다린 시간**을 함께 봅니다. 건수만으로는 얼마나 늦어졌는지 알기 어렵습니다. 처리 속도가 빠르면 만 건도 금방 줄고, 느리면 백 건도 오래 걸리기 때문입니다. 기다린 시간은 "주문 후 몇 분 뒤에 포인트가 들어가는가"라는 사용자 체감 지연에 바로 대응합니다.
- **대응과 부작용**:
  - 소비자를 늘립니다. 나누는 단위의 한계(조각 수), 포인트 DB 같은 공유 자원의 부하 증가, 순서 문제를 함께 봐야 합니다.
  - 처리 자체를 빠르게 합니다. 메시지 하나당 DB 왕복을 줄이거나 여러 건을 묶어 처리합니다. 묶으면 그중 하나가 실패했을 때의 처리가 복잡해집니다.
  - 생산을 늦춥니다. 주문 자체를 늦추는 것이므로 마지막 수단입니다.

밀린 양이 계속 늘면 저장 공간이 문제가 됩니다.

- **큐형**: 큐가 커지며 브로커의 메모리나 디스크를 씁니다. 한계에 닿았을 때 브로커가 새 메시지를 거부할지, 생산자를 늦출지, 오래된 메시지를 버릴지는 브로커와 설정에 따릅니다.
- **로그형**: 처리와 상관없이 보존 정책에 따라 오래된 메시지를 잘라 냅니다. 소비가 너무 밀려 **아직 읽지 않은 메시지가 잘려 나가면 유실**입니다. 브로커는 보존 정책대로 했을 뿐이므로 이것을 오류로 알리지 않을 수 있습니다. 그래서 보존 기간은 소비자가 가장 오래 멈춰 있을 수 있는 시간(장애 복구, 긴 배포)보다 길게 잡습니다.

## 흔한 오해 모아 보기

| 오해 | 실제 |
| --- | --- |
| Kafka 같은 로그형 브로커를 쓰면 메시지가 유실되지 않는다 | 읽었다고 지우지 않으므로 "읽어서 사라지는" 일은 없습니다. 하지만 생산자 전송, 브로커 보관, 소비자의 위치 기록 시점, 보존 기간마다 유실 지점이 있고 설정과 처리 방식에 달려 있습니다. 유실을 막으면 대신 중복이 생깁니다. |
| 메시지를 받았으면 처리된 것이다 | 받기와 처리 완료는 다릅니다. ACK를 언제 보내느냐에 따라 유실이나 중복이 생깁니다. |
| 정확히 한 번 전달을 켜면 중복 처리가 없다 | 그런 보장은 범위가 정해져 있고, 바깥 DB 쓰기나 외부 API 호출까지 덮지 않습니다. 소비자를 멱등하게 만들어야 합니다. |
| `@Async`로 비동기 처리하면 메시지 큐와 같다 | 맡긴 일이 같은 JVM 메모리에 있으므로 프로세스가 죽으면 함께 사라집니다. 브로커는 일을 생산자 프로세스 바깥에 둡니다. |
| 소비자를 늘리면 처리량이 그만큼 는다 | 나누는 단위(조각 수)가 상한이 될 수 있고, 공유 DB가 병목이 될 수 있습니다. 순서도 깨질 수 있습니다. |
| 이름이 Pub/Sub이면 저장하지 않는다(또는 저장한다) | 제품마다 다릅니다. 소비자가 없던 동안의 메시지를 저장하는지로 구분합니다. |

### Spring과 연결되는 지점

- Spring의 메시지 리스너(`@KafkaListener`, `@RabbitListener` 등)는 보통 리스너 메서드가 끝난 뒤 ACK나 위치 기록을 하도록 구성됩니다. 정확한 기본 동작과 예외가 났을 때의 처리(재시도 횟수, 재시도를 다 쓴 메시지를 건너뛸지 격리할지)는 라이브러리, 버전, 설정마다 다르므로 사용하는 버전에서 확인합니다. 이 문서는 리스너의 기본값을 특정 버전으로 확인하지 않았습니다.
- 어떤 방식이든 리스너 메서드 안에서 실제 처리를 다른 스레드(`@Async`, 코루틴 `launch` 등)로 넘기면, 메서드는 처리가 끝나기 전에 반환됩니다. 그러면 사실상 처리 전에 ACK하는 것이 되어, 워커가 죽을 때 메시지를 잃습니다.
- 메시지를 직렬화한 형식은 생산자와 모든 소비자의 약속입니다. 필드 이름을 바꾸거나 필수 필드를 추가하면, 배포 순서에 따라 옛 소비자가 새 메시지를 처리하지 못해 독 메시지가 됩니다.

### 증상과 확인 순서

**"포인트가 두 번 들어갔다"**

1. 같은 주문 ID를 처리한 기록이 두 번 있는지 로그에서 봅니다.
2. 두 번 처리된 원인이 재전달인지(워커 재시작이나 처리 제한 시간 초과 시점과 겹치는가), 생산자가 두 번 보낸 것인지(두 메시지의 브로커 ID가 다른가) 구분합니다.
3. 멱등 처리 기록이 적립과 같은 트랜잭션에서 남는지, 조회 후 처리하는 구조는 아닌지 봅니다.

대응으로 처리 제한 시간을 늘리면 중복은 줄지만 장애 시 지연이 늘어납니다. 근본 대응은 멱등 처리입니다.

**"포인트가 들어오지 않았다"**

1. 메시지가 브로커에 있는지 봅니다. 없으면 생산자 쪽 유실(주문 저장 후 전송 실패 등)입니다.
2. 있다면 그 그룹에서 처리 완료로 기록됐는지 봅니다. 기록됐는데 적립이 없으면 처리 전 ACK를 의심합니다(리스너 안의 스레드 넘김 등).
3. 끝나지 않은 메시지로 남아 있는지 봅니다. 남아 있다면 회수가 동작하지 않는 것입니다.
4. 격리 장소(데드 레터 큐)에 옮겨졌는지, 로그형이라면 보존 정책으로 잘려 나갔는지 봅니다.

## 말로 설명하기

### 30초 버전

메시지 큐는 일을 바로 처리하지 않고 브로커라는 별도 서버에 메시지로 맡겨, 생산자를 소비자의 장애와 속도에서 분리하는 방식입니다. 대신 결과가 바로 확정되지 않고, 프로세스 사이에서 메시지가 사라지거나 두 번 처리될 수 있습니다. 핵심은 소비자가 "처리를 끝냈다"는 ACK를 언제 보내느냐입니다. 처리 전에 보내면 유실을, 처리 후에 보내면 중복을 감수합니다. 빠지면 안 되는 일은 보통 처리 후 ACK를 고르고, 소비자를 멱등하게 만들어 중복을 견딥니다.

### 2분 버전

주문 API가 포인트 적립을 직접 호출하면 포인트 서비스가 느리거나 죽을 때 주문도 함께 느려지거나 실패합니다. 브로커에 "주문 완료" 메시지를 남기면 주문 API는 브로커가 받았다는 응답만 기다리고, 워커가 나중에 자기 속도로 처리합니다. `@Async`와 달리 맡긴 일이 주문 API 프로세스 바깥에 있으므로, 주문 API가 죽어도 일이 남습니다.

브로커는 크게 두 방식입니다. 큐형은 처리된 메시지를 지우고, 로그형은 덧붙이기만 하고 소비자마다 읽은 위치를 따로 기록합니다. 로그형은 같은 메시지를 여러 목적이 각자 읽거나 되돌려 다시 처리하기 쉽지만, 보존 기간을 관리해야 합니다. 같은 일을 하는 소비자는 그룹으로 묶어 그룹 안에서는 나눠 받고, 다른 일을 하는 그룹끼리는 모든 메시지를 각자 받습니다.

받기와 처리 완료는 다릅니다. 처리는 DB에, ACK는 브로커에 보내는 별개의 요청이라 둘을 원자적으로 묶을 수 없습니다. 그래서 그 사이에 소비자가 죽으면, ACK를 먼저 보낸 경우는 유실(최대 한 번), 처리를 먼저 한 경우는 재전달로 인한 중복(최소 한 번)이 생깁니다. 브로커는 처리 결과가 바깥에 남았는지 볼 수 없으므로 정확히 한 번을 혼자 보장하지 못합니다. 그래서 최소 한 번 전달에 업무 ID 기준의 멱등 처리를 더합니다.

운영에서는 처리 제한 시간을 정상 처리 시간보다 넉넉히 잡고, 계속 실패하는 메시지는 횟수 제한 뒤 격리하고, 밀린 건수와 가장 오래 기다린 메시지의 시간을 봅니다. 로그형이라면 아직 읽지 않은 메시지가 보존 정책으로 잘려 나가지 않게 보존 기간을 잡습니다.

### 예상 질문과 꼬리 질문

**Q. 메시지 큐는 왜 쓰나요?**
생산자를 소비자의 장애와 속도에서 분리하기 위해서입니다. 포인트 워커가 죽어 있어도 주문은 성공하고, 주문이 몰려도 워커는 자기 속도로 처리하며, 새 소비자를 붙여도 주문 API는 바뀌지 않습니다. 대가로 결과가 바로 확정되지 않고, 브로커라는 운영 대상이 늘며, 유실과 중복을 설계해야 합니다. (본문: "메시지를 맡기면 생산자가 소비자의 장애와 속도에서 분리됩니다")

- **꼬리: 그럼 언제 쓰면 안 되나요?**
  결과가 응답에 필요한 일입니다. 결제 승인처럼 주문 성공 여부를 결정하는 일은 맡기면 응답 시점에 결과를 알 수 없으므로 동기로 처리합니다.

**Q. `@Async`로 비동기 처리하는 것과 무엇이 다른가요?**
`@Async`는 같은 JVM 안의 다른 스레드에 일을 넘기므로, 맡긴 일이 그 프로세스 메모리에 있습니다. 프로세스가 죽으면 아직 처리되지 않은 일이 사라집니다. 브로커는 맡긴 일을 생산자 프로세스 바깥에 보관하므로 생산자가 죽어도 일이 남고, 다른 서버의 워커가 처리할 수 있습니다.

**Q. 큐형과 로그형은 어떻게 다른가요?**
큐형은 소비자가 처리를 끝낸 메시지를 지웁니다. 로그형은 메시지를 지우지 않고 덧붙이기만 하며, 소비자 그룹마다 어디까지 읽었는지 위치를 기록합니다. 그래서 로그형은 같은 메시지를 여러 목적이 위치만 달리해 읽을 수 있고, 위치를 되돌려 다시 처리할 수 있습니다. 대신 처리와 상관없이 쌓이므로 보존 기간을 정해 오래된 것을 잘라 내야 합니다. (본문: "큐형은 처리된 메시지를 지우고, 로그형은 읽어도 남깁니다")

- **꼬리: 버그 때문에 어제 처리한 메시지를 다시 처리해야 한다면?**
  로그형이고 그 메시지가 보존 기간 안에 있다면 그룹의 위치를 되돌려 다시 읽을 수 있습니다. 이때 이미 반영된 메시지도 다시 처리되므로 소비자가 멱등해야 합니다. 큐형이라면 이미 지워졌으므로 생산자 쪽에서 다시 보내야 합니다.
- **꼬리: Redis로 메시지를 넘긴다면 어느 방식인가요?**
  기능마다 다릅니다. Pub/Sub은 저장하지 않는 방송이라 듣지 않던 소비자는 메시지를 놓칩니다. List는 꺼내는 순간 원소가 빠지는 큐형이라, ACK 없이 지우는 셈이고 꺼낸 직후 소비자가 죽으면 잃습니다. Streams는 로그형이고 소비자 그룹과 끝나지 않은 메시지 기록을 Redis가 관리합니다. 그래서 저장이 필요한지, ACK를 언제 보낼지를 먼저 정하고 기능을 고릅니다. (본문: "Redis 안에도 세 방식이 모두 있습니다")

**Q. 같은 메시지를 포인트 워커와 알림 워커가 각각 받게 하려면 어떻게 하나요? 포인트 워커 두 대가 중복 없이 나눠 받게 하려면요?**
같은 일을 하는 소비자를 하나의 그룹으로 묶습니다. 그룹 안에서는 한 메시지를 소비자 하나만 받고, 그룹끼리는 각자 모든 메시지를 받습니다. 포인트 워커 두 대는 포인트 그룹, 알림 워커는 알림 그룹으로 두면 됩니다. Kafka의 소비자 그룹(consumer group)에서는 서로 다른 그룹이 같은 토픽을 읽으면 각 그룹이 모든 메시지를 받고, 같은 그룹 안의 소비자들은 파티션을 나눠 맡습니다. (본문: "소비자가 여럿이면 나눠 받기와 모두 받기를 구분합니다")

- **꼬리: 그룹 안의 소비자를 계속 늘리면 처리량도 계속 늘어나나요?**
  아닙니다. 조각(파티션) 단위로 나누는 시스템에서는 동시에 일하는 소비자 수가 조각 수를 넘지 못합니다. 또 포인트 DB처럼 소비자들이 함께 쓰는 자원이 병목이 될 수 있고, 나눠 처리하면 끝나는 순서가 바뀔 수 있습니다.

**Q. ACK는 언제 보내야 하나요?**
무엇을 감수할지에 따라 다릅니다. 처리 전에 보내면 그 뒤 소비자가 죽을 때 메시지가 처리되지 않은 채 끝나고(최대 한 번), 처리 후에 보내면 그 사이에 죽을 때 메시지가 다시 전달되어 두 번 처리됩니다(최소 한 번). 처리는 DB에, ACK는 브로커에 보내는 별개의 요청이라 둘을 원자적으로 묶을 수 없으므로 어느 쪽이든 틈이 남습니다. 빠지면 안 되는 일은 처리 후 ACK를 고르고 소비자를 멱등하게 만듭니다. (본문: "ACK를 언제 보내는가가 유실과 중복을 가릅니다")

- **꼬리: Spring 리스너에서 처리를 `@Async`로 넘기면 어떻게 되나요?**
  리스너 메서드가 처리가 끝나기 전에 반환됩니다. 메서드가 끝난 뒤 ACK하는 구성이라면 사실상 처리 전 ACK가 되어, 워커가 죽을 때 메시지를 잃습니다.

**Q. Kafka는 메시지가 유실되지 않는다고 들었는데 맞나요?**
절반만 맞습니다. Kafka는 읽은 메시지를 지우지 않으므로 "읽었더니 사라지는" 유실은 없습니다. 하지만 생산자가 응답을 못 받았을 때 다시 보내는가, 브로커가 메시지를 어떻게 보관하도록 설정했는가, 소비자가 위치를 처리 전과 후 중 언제 기록하는가, 아직 읽지 않은 메시지가 보존 기간에 잘리는가에 따라 유실이 생길 수 있습니다. 유실을 막는 쪽으로 설정하면 대신 중복이 생기므로 소비자의 멱등 처리가 필요합니다. (본문: "보내는 쪽과 브로커에도 같은 틈이 있습니다")

**Q. 정확히 한 번 처리는 어떻게 보장하나요?**
브로커 혼자서는 보장할 수 없습니다. 처리 결과가 DB나 외부 API처럼 브로커 바깥에 남아, 브로커가 그 결과를 볼 수 없기 때문입니다. 일부 시스템은 자기 안에서 읽고 쓰는 범위에 한해 정확히 한 번을 제공하지만 바깥 저장소까지 덮지는 않습니다. 실무에서는 최소 한 번 전달과 멱등한 소비자를 조합해 "정확히 한 번 처리한 것과 같은 결과"를 만듭니다. (본문: "정확히 한 번은 전달만으로 만들 수 없습니다")

**Q. 중복 메시지는 어떻게 처리하나요?**
주문 ID 같은 업무 ID를 기준으로 "이미 처리했다"는 기록을 남기되, 그 기록을 처리와 같은 DB 트랜잭션에서 남깁니다. 유니크 제약을 걸어 두면 두 번째 시도는 기록 단계에서 실패하고 처리도 함께 취소됩니다. (본문: "중복은 막기보다 견디게 만듭니다: 멱등한 소비자")

- **꼬리: 브로커가 주는 메시지 ID를 기준으로 하면 안 되나요?**
  생산자가 응답을 못 받아 같은 내용을 다시 보내면 브로커 입장에서는 새 메시지라 ID가 달라질 수 있습니다. 같은 일인지 판단하려면 업무 ID가 안전합니다.
- **꼬리: 처리 기록을 먼저 조회하고 없으면 처리하면 되지 않나요?**
  같은 메시지가 두 워커에 동시에 전달되면, 둘 다 조회에서 "없음"을 보고 둘 다 처리합니다. 조회와 처리 사이에 틈이 있는 경쟁 상태입니다. 기록과 처리를 한 원자적 단위로 묶어야 합니다.
- **꼬리: 외부 API 호출처럼 멱등하게 만들기 어려운 일은요?**
  외부 API가 멱등 키를 지원하면 그것을 씁니다. 지원하지 않으면 호출 직후 기록 전에 죽는 틈은 없앨 수 없으므로, 드문 중복을 받아들일지 결정해야 합니다.

**Q. 처리 중이던 소비자가 죽으면 그 메시지는 어떻게 되나요?**
ACK되지 않은 메시지로 남아 있다가, 연결이 끊긴 것이 감지되거나 처리 제한 시간이 지나면 다른 소비자에게 다시 전달됩니다. 브로커가 자동으로 다시 내놓는 시스템도 있고, 살아 있는 소비자가 직접 회수를 요청해야 하는 시스템도 있습니다. 뒤쪽이라면 회수 작업을 실행하지 않는 한 메시지가 영영 끝나지 않습니다. (본문: "처리 중에 사라진 소비자의 메시지는 다시 전달됩니다")

- **꼬리: 처리 제한 시간은 어떻게 정하나요?**
  너무 짧으면 느릴 뿐인 소비자의 메시지를 다른 소비자에게도 넘겨 같은 메시지를 동시에 처리하게 되고, 너무 길면 소비자가 정말 죽었을 때 처리가 늦어집니다. 정상 처리 시간 중 느린 쪽보다 넉넉하게 잡고, 남는 중복은 멱등 처리로 견딥니다.

**Q. 어떤 메시지가 처리할 때마다 실패하면 어떻게 하나요?**
그대로 두면 실패와 재전달이 끝없이 반복되어 워커 시간을 쓰고, 순서대로 처리하는 구조라면 뒤의 메시지까지 막습니다. 전달 횟수를 세어 정한 횟수를 넘으면 데드 레터 큐 같은 별도 장소로 옮기고, 옮겨진 메시지에 알림을 걸어 사람이 원인을 고친 뒤 다시 넣습니다. 옮기고 방치하면 조용한 유실이 됩니다.

**Q. 메시지가 계속 밀리면 무엇을 보고 어떻게 대응하나요?**
밀린 건수와 가장 오래된 미처리 메시지가 기다린 시간을 봅니다. 기다린 시간이 "주문 후 몇 분 뒤에 포인트가 들어가는가"라는 사용자 체감 지연에 바로 대응합니다. 대응은 소비자 추가, 처리 속도 개선, 생산 제한 순으로 검토하는데, 소비자 추가는 조각 수와 공유 DB 부하, 순서 문제를 함께 봐야 합니다. 로그형이라면 밀린 메시지가 보존 기간에 잘려 나가기 전에 대응해야 합니다. (본문: "소비가 생산보다 느리면 밀린 양이 쌓이고, 결국 무언가를 잘라 내야 합니다")

**Q. 주문은 저장됐는데 메시지가 안 갔다면 무엇이 문제인가요?**
주문 DB 저장과 브로커 전송은 서로 다른 저장소에 대한 요청이라 원자적으로 묶이지 않습니다. 저장 직후 주문 API가 죽으면 주문만 남습니다. 보낼 메시지를 주문과 같은 DB 트랜잭션으로 기록해 두고 별도 과정이 브로커로 보내는 방식(트랜잭셔널 아웃박스)으로 틈을 메울 수 있습니다. 이 방식도 전송을 재시도하므로 소비자는 여전히 중복을 견뎌야 합니다.

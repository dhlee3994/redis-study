# 재시도와 서킷 브레이커: 실패한 요청을 언제, 어떻게 다시 보내야 장애를 키우지 않는가

> **핵심 질문**: 원격 저장소에 보낸 요청이 실패했을 때, 다시 보내도 되는지는 무엇으로 판단하는가? 다시 보낸다면 간격과 횟수는 어떻게 정하며, 실패가 이어질 때 아예 부르지 않는 장치(서킷 브레이커)는 무엇을 지키고 무엇을 대가로 치르는가? 타임아웃, 재시도, 서킷 브레이커는 어떤 순서로 겹쳐야 하는가?
>
> **범위**: 언어와 저장소에 공통인 원리를 다룹니다. 특정 재시도·서킷 브레이커 라이브러리의 설정과 기본값은 다루지 않습니다. 타임아웃 값을 정하는 원리는 [타임아웃](./timeout.md)에, 응답을 받지 못한 쓰기를 멱등하게 만드는 방법은 [경쟁 상태와 원자성](./race-condition-and-atomicity.md)에 있습니다.

## 배경 지식

### 이 문서의 예시: 요청 스레드 200개, 초당 500건, 저장소 하나

[타임아웃](./timeout.md)의 장면을 이어서 씁니다. 문서 끝까지 이 장면 하나를 씁니다.

- 주문 API 서버는 요청 스레드 200개로 사용자 요청을 처리합니다. 초당 500건의 요청이 원격 저장소 S에 "재고 조회"를 보내고, 주문이 성립하면 "재고 차감"을 한 번 더 보냅니다.
- S에 대한 응답 타임아웃은 100ms이고, 사용자 요청 하나에 쓸 수 있는 시간(바깥 기한)은 1초입니다. 100ms는 [타임아웃](./timeout.md)의 "값은 무엇을 기준으로 정하는가"에서 고른 범위 안의 값입니다.
- S는 세 가지 방식으로 실패합니다.

| 실패 | S에서 일어나는 일 | 주문 API가 보는 것 |
| --- | --- | --- |
| (가) 재시작 중 | S가 요청을 받지만 "준비 중이라 지금은 처리하지 않는다"고 곧바로 거절합니다. 준비가 끝나면 정상으로 돌아옵니다 | 즉시 오는 거절 응답 |
| (나) 쓰기 거부 | 디스크 문제로 S가 쓰기를 거절합니다. 읽기는 처리합니다. 사람이 디스크를 고쳐야 풀립니다 | 차감에만 즉시 오는 거절 응답 |
| (다) 응답 없음 | 요청이 S에 닿았는지, S가 실행했는지 알 수 없습니다 | 100ms 뒤 타임아웃 |

```text
사용자 500건/초 ──▶ 주문 API (요청 스레드 200개) ── 재고 조회, 재고 차감 ──▶ 저장소 S
                     타임아웃 100ms, 바깥 기한 1초              ◀── 응답 또는 거절
```

화살표는 요청과 응답이 가는 방향입니다. 주문 API 앞에서 사용자 요청을 다시 보낼 수 있는 계층(모바일 앱, API 게이트웨이)은 그림에서 뺐습니다. 이 계층은 아래 "재시도는 공짜가 아닙니다: 부하가 곱해집니다"에서 다룹니다.

이 문서의 숫자(200개, 500건, 100ms, 1초, 재시도 횟수와 간격)는 계산을 보여 주기 위한 **가상의 숫자**이며, 이 문서에서 재지 않았습니다.

### 타임아웃은 일을 취소하지 않습니다

- **한 줄**: 타임아웃은 기다리는 쪽이 기다림을 그만두는 것일 뿐, 상대의 실행을 취소하지 않습니다. 그래서 타임아웃이 난 요청은 실행되지 않았을 수도, 이미 실행됐을 수도, 나중에 실행될 수도 있습니다. 원리는 [타임아웃](./timeout.md)의 "타임아웃은 기다림을 그만둘 뿐, 일을 취소하지 않습니다"에 있습니다.
- **이 주제에서는**: 예시의 (다)에서 주문 API는 차감이 실행됐는지 모릅니다. 다시 보내도 되는지가 이 문서의 첫 질문입니다.

### 멱등성

- **한 줄**: 같은 요청을 여러 번 실행해도 한 번 실행한 것과 효과가 같은 성질입니다. 방법은 [경쟁 상태와 원자성](./race-condition-and-atomicity.md)의 "원자성이 보장하지 않는 것"에 있습니다.
- **이 주제에서는**: 재고 조회는 여러 번 실행해도 재고를 바꾸지 않으므로 다시 보내도 됩니다. 재고 차감은 두 번 실행되면 두 번 줄어듭니다. 주문 번호로 "이미 처리했는가"를 확인하고 기록하는 일을 차감과 함께 한 번에 하면, 다시 보내도 한 번만 줄어듭니다.

### 재시도

- **한 줄**: 실패한 요청을 같은 내용으로 다시 보내는 것입니다.
- **비유**: 전화를 걸었는데 통화 중이면 잠시 뒤 다시 겁니다. 통화 중이라는 신호가 오면 상대가 내 말을 듣지 못했다는 것을 확실히 압니다. 반면 말하던 중 전화가 끊기면, 상대가 내 주문을 받아 적었는지 모릅니다. 다시 걸어 같은 주문을 말하면 두 번 적힐 수 있습니다.
- **실제로는**: 재시도는 실패의 원인이 시간이 지나면 사라진다는 기대 위에서만 의미가 있습니다. 원인이 남아 있으면 같은 실패를 한 번 더 얻을 뿐이고, 그 요청만큼 상대의 일이 늘어납니다. **비유와 다른 점**: 사람은 다시 걸기 전에 상황을 판단하지만, 프로그램의 재시도는 정해 둔 규칙대로 기계적으로 일어납니다. 서버 수백 대가 같은 규칙으로 같은 순간에 다시 보내면, 상대는 한 사람이 아니라 수만 통의 전화를 동시에 받습니다.
- **이 주제에서는**: (가), (나), (다)는 재시도의 결과가 모두 다릅니다. 이 문서는 그 차이를 두 질문으로 나눕니다.

## 다시 보내기 전에 묻는 두 질문: 실행됐는가, 기다리면 풀리는가

실패를 재시도 관점에서 나누면 두 질문이 남습니다.

1. **그 요청이 상대에서 실행됐는지 아는가?** 실행되지 않았다고 확실히 알면 다시 보내도 중복이 생기지 않습니다. 모르면 다시 보낸 요청이 두 번째 실행이 될 수 있습니다.
2. **기다리면 원인이 풀리는가?** 풀린다면 얼마 만에 풀리는가? 풀리지 않거나 사람이 고쳐야 풀린다면 재시도는 부하만 더합니다.

예시의 세 실패를 대입하면 다음과 같습니다.

| 실패 | 실행됐는지 | 기다리면 풀리는가 | 재시도의 성질 |
| --- | --- | --- | --- |
| (가) 재시작 중 거절 | 실행되지 않음(거절 응답이 증거) | 풀림. 다만 준비 시간만큼 걸림 | 중복 걱정은 없지만, 준비 시간이 바깥 기한보다 길면 요청 안의 재시도로는 넘기지 못함 |
| (나) 쓰기 거부 | 실행되지 않음 | 사람이 고칠 때까지 풀리지 않음 | 중복 걱정은 없지만 재시도의 효용이 거의 없음 |
| (다) 응답 없음 | 모름 | 원인에 따라 다름(일시적 지연이면 곧, 상대가 멈췄으면 오래) | 읽기는 다시 보내도 되지만, 쓰기는 멱등할 때만 다시 보냄 |

두 질문은 서로 독립입니다. 흔한 잘못은 하나만 묻는 것입니다.

- "일시적인 오류니까 재시도한다"는 두 번째 질문만 묻습니다. (다)의 차감을 다시 보내면 재고가 두 번 줄 수 있습니다.
- "실행되지 않았다는 응답이니 재시도해도 안전하다"는 첫 번째 질문만 묻습니다. (나)는 안전하지만 몇 번을 다시 보내도 같은 거절을 받습니다.

여기서 거절 응답은 (가)·(나)처럼 상대가 **실행하기 전에** 거절했다는 응답을 말합니다. 실행 도중에 난 오류는 그 전까지 한 일이 남아 있을 수 있으므로 이 판단에 넣지 않습니다.

**실행 전 거절은 "그 전송"이 실행되지 않았다는 증거일 뿐입니다.** 이 점을 잘못 읽기 쉽습니다. 클라이언트 라이브러리 중에는 연결이 끊기면 다시 연결한 뒤, 응답을 받지 못한 요청을 앱이 모르게 다시 보내는 것이 있습니다. 라이브러리가 이렇게 같은 요청을 스스로 다시 보냈다면, 앱이 받은 거절은 두 번째 전송에 대한 것입니다. 첫 번째 전송은 끊기기 직전에 실행됐을 수 있습니다. 그래서 "거절 응답이면 실행되지 않았다"는 판단은 그 요청이 한 번만 전송됐다는 전제가 있을 때만 맞습니다. 쓰는 라이브러리가 재연결 때 이런 재전송을 하는지, 끄거나 거를 수 있는지를 문서와 설정에서 확인해야 하는 이유입니다.

## 재시도는 공짜가 아닙니다: 부하가 곱해집니다

### 상대가 아플 때 요청이 가장 많아집니다

예시에서 주문 API가 실패마다 최대 3번 재시도(첫 시도까지 4번)한다고 합시다.

- 평소에는 실패가 드물어 재시도가 거의 없습니다. S가 받는 재고 조회는 초당 약 500건입니다.
- S가 (가) 상태라 모든 요청을 거절하면, 요청마다 4번씩 보내므로 S가 받는 요청은 초당 약 2,000건입니다. **S가 가장 약할 때 평소의 4배를 받습니다.**

재시도는 실패가 드물고 일시적이라는 전제에서 정상 요청을 구해 냅니다. 실패가 모든 요청에 일어나는 장애에서는 같은 규칙이 부하를 몇 배로 늘리는 장치가 됩니다.

### 계층마다 재시도하면 곱해집니다

모바일 앱, API 게이트웨이, 주문 API가 각자 시도를 3번(첫 시도 1번 + 재시도 2번)까지 하면 사용자 요청 하나가 S에 최대 3 × 3 × 3 = 27번 닿습니다. 각 계층은 자기 몫만 보고 "3번쯤은 괜찮다"고 정했지만, 합치면 장애 동안 S가 받는 요청이 27배가 됩니다. 그래서 **재시도는 한 계층에서만 합니다.** 보통 실패의 종류를 가장 잘 아는 계층, 곧 저장소를 직접 부르는 계층(예시의 주문 API)이 맡고, 바깥 계층은 그 결과를 받아 다시 보내지 않게 합니다. 클라이언트 라이브러리가 연결 수준에서 스스로 다시 보내는 것도 한 계층으로 셉니다.

### 즉시 오는 거절은 스스로 속도를 늦추지 않습니다

(다)의 타임아웃은 실패하기까지 100ms가 걸리므로, 스레드 하나가 재시도로 보낼 수 있는 요청은 초당 최대 10번입니다. 반면 (가)와 (나)의 거절은 왕복 시간만에 돌아옵니다. 왕복이 1ms라면 간격 없이 재시도하는 반복문 하나가 초당 약 1,000번을 보냅니다. **실패가 빠를수록, 간격 없는 재시도는 더 많은 요청을 만듭니다.** 평소에는 응답을 기다리며 저절로 속도가 조절되던 작업자(대기열에서 일을 꺼내는 반복문 등)가, 거절이 즉시 오는 순간 상대를 두드리는 반복문으로 바뀝니다.

### 회복하는 순간 한꺼번에 몰립니다

S가 (가)에서 회복하는 순간을 봅시다. 모든 주문 API가 같은 간격(예: 정확히 1초)으로 재시도하고 있었다면, 회복 직후 같은 박자로 한꺼번에 몰립니다. 막 준비를 마친 S가 평소보다 큰 요청 더미를 한순간에 받아 다시 느려질 수 있습니다. 같은 박자를 깨려면 간격에 무작위 폭을 섞어야 합니다.

## 간격을 두고, 흩고, 횟수와 시간에 상한을 둡니다

### 지수 백오프와 지터

- **지수 백오프(exponential backoff)**: 재시도할수록 간격을 두 배씩 늘립니다. 기준 50ms라면 50ms, 100ms, 200ms, …처럼 늘리고, 상한(예: 2초)을 둡니다. 실패가 짧으면 빨리 다시 시도하고, 길어지면 상대를 덜 두드립니다.
- **지터(jitter)**: 계산한 간격 안에서 무작위로 고릅니다. 예를 들어 이번 간격이 200ms라면 0~200ms 사이의 임의 값만큼 기다립니다. 같은 순간에 실패한 요청들이 서로 다른 순간에 다시 오므로, 회복 직후의 몰림이 시간축으로 흩어집니다.

두 가지는 함께 씁니다. 백오프만 있으면 같은 순간에 실패한 요청들이 같은 간격을 계산해 다시 함께 옵니다. 지터만 있으면 실패가 길어져도 두드리는 속도가 줄지 않습니다.

### 시도 횟수보다 남은 시간이 먼저입니다

요청 경로의 재시도는 바깥 기한 안에 들어가야 합니다. 시도 하나가 최대 "타임아웃 + 기다린 간격"을 쓰므로, 예시에서 S를 두 번(조회, 차감) 부르고 각각 한 번씩 재시도한다면 최악의 경우는 다음과 같습니다.

```text
조회 (100ms 타임아웃) + 간격 50ms + 조회 재시도 (100ms)
+ 차감 (100ms)       + 간격 50ms + 차감 재시도 (100ms)  = 500ms
```

바깥 기한 1초 안에 S 말고도 DB 저장과 응답 만들기가 들어가야 하므로, 이 이상 재시도를 늘리기 어렵습니다. 재시도 직전에는 **바깥 기한에서 남은 시간이 "다음 시도 전에 기다릴 간격 + 시도의 타임아웃"보다 긴지** 확인하고, 짧으면 다시 보내지 않습니다. 사용자가 이미 떠난 요청을 위해 S를 두드리는 일을 막기 위해서입니다.

이 계산에서 판단 하나가 나옵니다. **요청 경로의 재시도가 넘길 수 있는 장애는 수백 ms짜리뿐입니다.** (가)처럼 준비에 수십 초가 걸리는 장애는 요청 하나가 기다려서 넘길 수 없습니다. 이런 장애에서는 요청은 빨리 실패하고, "언제 다시 부를지"는 요청 바깥에서 정합니다. 실패가 이어지면 한동안 상대를 부르지 않고 곧바로 실패하는 장치인 서킷 브레이커가 이 일을 맡으며, 아래 "서킷 브레이커: 실패가 이어지면 한동안 부르지 않습니다"에서 다룹니다. 반대로 사용자를 기다리게 하지 않는 백그라운드 작업은 바깥 기한이 없거나 길므로, 백오프 상한까지 오래 재시도해도 됩니다.

### 재시도 예산

장애 동안 재시도가 부하를 몇 배로 키우는 것을 막는 또 하나의 방법은, 재시도의 총량을 원래 요청(재시도가 아닌 첫 시도) 수에 대한 비율로 제한하는 것입니다. 예를 들어 "최근 원래 요청 수의 10%까지만 재시도한다"고 정하면, 실패가 드물 때는 실패한 요청 대부분을 구하고, 모든 요청이 실패하는 장애에서는 S가 받는 요청이 평소의 약 1.1배를 넘지 않습니다. 시도 횟수 상한은 요청 하나의 비용을 막고, 재시도 예산은 서비스 전체의 비용을 막습니다.

## 서킷 브레이커: 실패가 이어지면 한동안 부르지 않습니다

### 개념

- **한 줄**: 최근 호출의 실패가 정해 둔 기준을 넘으면, 한동안 상대를 부르지 않고 곧바로 실패를 돌려주는 장치입니다.
- **비유**: 집의 차단기(두꺼비집)와 같습니다. 전선에 과전류가 계속 흐르면 차단기가 내려가 전기를 끊어, 문제가 집 전체로 번지지 않게 합니다. 원인을 고친 뒤 차단기를 다시 올려 봅니다.
- **실제로는**: 세 상태를 오갑니다.

  | 상태 | 하는 일 | 다음 상태로 가는 조건 |
  | --- | --- | --- |
  | 닫힘 | 평소처럼 부르고, 최근 호출의 결과를 셉니다 | 센 호출이 최소 개수 이상 모였고, 실패 비율(또는 느린 호출 비율)이 기준을 넘으면 열림 |
  | 열림 | 부르지 않고 곧바로 "열려 있음" 실패를 돌려줍니다 | 정해 둔 시간이 지나면 반열림 |
  | 반열림 | 시험 삼아 몇 개만 부릅니다 | 시험 호출의 결과가 좋으면 닫힘, 나쁘면 다시 열림. 시험 호출 한 건으로 정하는 구현도, 정해 둔 개수를 모아 비율로 정하는 구현도 있습니다 |

  느린 호출은 실패는 아니지만 정해 둔 시간(타임아웃보다 짧게 잡는 기준)보다 오래 걸린 호출입니다. 상대가 멈추기 전에 느려지기부터 하는 경우 미리 알아채려고 따로 셉니다. 판정 방식(비율 또는 연속 실패 수, 최소 개수)은 구현마다 다릅니다. 또 브레이커의 상태는 보통 앱 인스턴스(서버 프로세스)마다 따로 유지됩니다. 주문 API가 10대면 브레이커도 10개이고, 각자 자기가 본 결과로 열고 닫습니다.

  **비유와 다른 점**: 집의 차단기는 사람이 올리지만, 서킷 브레이커는 정해 둔 시간 뒤 스스로 시험해 봅니다. 또 차단기는 전류라는 한 가지 기준으로 내려가지만, 서킷 브레이커는 **무엇을 실패로 셀지**를 사람이 정해야 합니다. 이 선택이 잘못되면 멀쩡한 기능까지 끊습니다.
- **이 주제에서는**: (가)처럼 수십 초 이어지는 장애에서, 요청마다 S를 불러 실패를 확인하는 대신 S를 부르지 않고 바로 실패합니다. "기다리면 풀리는" 장애를 요청이 아니라 브레이커가 대신 기다립니다.

### 무엇을 지키는가

- **요청 스레드**: (다)처럼 응답이 없는 장애에서 닫힌 브레이커 아래의 요청은 하나하나 100ms씩 기다립니다. 동시에 묶이는 스레드 수는 대략 "초당 요청 수 × 한 요청이 기다리는 시간"이므로([타임아웃](./timeout.md)의 리틀의 법칙), 재시도가 없다면 약 500 × 0.1 = 50개입니다. 재시도를 붙이면 한 요청이 기다리는 시간이 시도 수와 간격만큼 늘어 더 많이 묶입니다. 한 번 재시도하고 간격이 50ms면 약 500 × 0.25 = 125개입니다. 브레이커가 열리면 기다림이 0이 되어 묶이는 스레드도 거의 없어집니다.
- **상대의 회복**: 열린 동안 S가 받는 요청이 반열림의 시험 호출 몇 개(인스턴스마다)로 줄어듭니다. 재시도보다 확실하게 부하를 걷어 냅니다.
- **빠른 대체 처리**: 실패가 곧바로 오므로, 앱은 바깥 기한 안에 대체 경로(다른 저장소에서 읽기, "잠시 후 다시 시도" 응답)로 갈 시간을 법니다.

### 무엇을 대가로 치르는가

- **열린 동안에는 성공했을 요청도 실패합니다.** 장애가 이미 끝났어도, 반열림이 오기 전까지는 부르지 않습니다. 열림 시간을 길게 두면 회복을 늦게 알아채고, 짧게 두면 아직 아픈 S에 시험 호출을 자주 보냅니다.
- **열리기까지 시간이 걸립니다.** 실패 비율을 최근 몇 건(또는 몇 초) 안에서 셀지에 따라 열리는 속도가 다릅니다. 이렇게 비율을 세는 범위를 판정 창이라고 부릅니다. 창이 작으면 우연한 실패 몇 건에 열리고, 크면 장애가 시작된 뒤에도 한동안 닫혀 있습니다.
- **무엇을 셀지 잘못 고르면 기능을 통째로 끕니다.** 아래에서 따로 봅니다.

### 무엇을 실패로 셀 것인가

브레이커는 **상대의 상태**를 판단하는 장치입니다. 그래서 상대가 아프다는 신호만 실패로 셉니다.

| 실패의 종류 | 예시에서 | 셀 것인가 |
| --- | --- | --- |
| 응답 없음(타임아웃), 연결 실패 | (다) | 셉니다. 상대나 경로가 아프다는 신호입니다 |
| 일시적 거절(준비 중) | (가) | 셉니다. 상대 전체가 지금 일을 받지 못합니다 |
| 일부 기능만 거절 | (나) 쓰기 거부 | 그 기능의 브레이커에서만 셉니다. 읽기까지 막으면 멀쩡한 재고 조회를 끊습니다 |
| 요청 자체가 잘못됨 | 잘못된 인자, 없는 상품 | 세지 않습니다. 상대는 정상이고, 고칠 곳은 앱입니다 |

(나)를 읽기와 쓰기가 함께 쓰는 브레이커 하나에서 세면, 차감 실패만으로 실패 비율이 기준을 넘어 브레이커가 열리고 재고 조회까지 막힙니다. 이런 실패는 기능별로 브레이커를 나누거나, 그 기능만 막는 별도 표시(예: "지금은 주문을 받지 않음")로 다룹니다.

## 어떤 순서로 겹치는가

네 장치는 감싸는 순서가 결과를 바꿉니다. 안쪽부터 바깥쪽으로 다음 순서를 기본으로 삼습니다.

```text
바깥 기한 (사용자 요청 하나, 1초)
└─ 재시도 (다시 보낼 실패만, 남은 시간 안에서, 백오프 + 지터)
   └─ 서킷 브레이커 (시도마다 결과를 셈, 열리면 즉시 실패)
      └─ 시도별 타임아웃 (100ms)
         └─ S 호출 1번
```

선은 실행 순서가 아니라 포함 관계입니다. 아래 줄의 장치 전체가 위 줄의 장치 안에서 "한 번의 호출"로 실행됩니다. 예를 들어 재시도가 두 번 시도하면, 그 아래의 브레이커·타임아웃·호출이 두 번 실행됩니다.

| 위치 | 이유 |
| --- | --- |
| 시도별 타임아웃이 가장 안쪽 | 시도 하나가 쓰는 시간에 상한을 둬야, 바깥 장치들이 남은 시간을 계산할 수 있습니다 |
| 브레이커가 재시도 안쪽 | 브레이커가 **시도마다** 결과를 세므로 장애를 빨리 알아챕니다. 열리면 재시도의 다음 시도도 곧바로 실패해 S에 닿지 않습니다 |
| 재시도가 브레이커 바깥 | 재시도는 "다시 보낼 실패"만 다시 보냅니다. 브레이커가 돌려준 "열려 있음"은 다시 보낼 실패로 치지 않습니다. 다시 보내 봐야 즉시 같은 실패를 받습니다 |
| 바깥 기한이 가장 바깥 | 재시도가 몇 번 남았든 기한이 지나면 멈춥니다 |

**뒤집으면 어떻게 되는가**: 브레이커를 재시도 바깥에 두면 브레이커는 "재시도까지 다 끝난 사용자 요청" 하나를 결과 하나로 셉니다. 세 가지가 나빠집니다.

- **결과가 늦게 기록됩니다.** 모든 시도가 실패하는 장애에서는 실패 비율이 어느 순서든 100%로 같지만, 결과 하나가 기록되기까지 시도 전체와 간격만큼 시간이 걸리고, 판정에 필요한 최소 개수도 그만큼 늦게 찹니다. 그래서 늦게 열립니다.
- **일부만 실패하는 장애가 가려집니다.** 시도 하나가 실패할 확률이 30%이고 3번까지 시도한다면, 사용자 요청이 끝내 실패할 확률은 약 0.3 × 0.3 × 0.3 ≈ 2.7%입니다. S가 시도의 30%를 실패시키는 상태인데도 브레이커는 2.7%만 보고 열리지 않을 수 있습니다.
- **닫혀 있는 동안 재시도가 S를 시도 횟수만큼 두드립니다.** 뒤집는 순서를 쓰는 이유가 있다면 "사용자 요청 단위의 실패율"을 기준으로 삼고 싶을 때인데, 그때도 재시도가 만드는 부하는 재시도 예산으로 따로 막아야 합니다.

라이브러리마다 이 장치들을 감싸는 기본 순서가 정해져 있을 수 있습니다. 쓰는 라이브러리의 기본 순서가 위와 같은지, 브레이커의 "열려 있음" 실패가 재시도 대상에서 빠지는지 문서로 확인합니다.

| 서킷 브레이커는 모든 오류를 세면 된다 | 상대가 아프다는 신호만 셉니다. 일부 기능의 실패를 전체 브레이커에서 세면 멀쩡한 기능까지 끊습니다 | 무엇을 실패로 셀 것인가 |

## 실무 포인트

### 이 원리가 Redis와 백엔드 판단에 연결되는 곳

| 중요도 | 판단 | 이유 |
| --- | --- | --- |
| 필수 | 실패마다 "실행됐는지 아는가"와 "기다리면 풀리는가"를 따로 분류한다 | 같은 예외 종류 안에 두 성질이 섞여 있는 경우가 많습니다. 저장소가 실행 전에 거절한 응답은 그 전송이 실행되지 않았음을 뜻하지만, 실행 도중의 오류는 일부가 반영됐을 수 있고, 타임아웃과 연결 끊김은 결과를 모릅니다 |
| 필수 | 값을 바꾸는 요청은 멱등하게 만든 뒤에만 재시도한다 | 앱이 재시도하지 않아도 클라이언트 라이브러리가 연결 수준에서 다시 보낼 수 있습니다 |
| 필수 | 재시도는 한 계층에서만, 바깥 기한에서 남은 시간 안에서만 한다 | 계층마다 곱해지고, 기한을 넘긴 재시도는 떠난 사용자를 위해 상대를 두드립니다 |
| 필수 | 간격 없는 재시도 반복문을 만들지 않는다 | 즉시 오는 거절에서 반복문 하나가 왕복 시간마다 한 번, 왕복 1ms라면 초당 약 1,000번을 보냅니다. 대기열 작업자처럼 평소 응답을 기다리며 속도가 조절되던 코드가 특히 위험합니다 |
| 알면 유리 | 서킷 브레이커를 기능(읽기·쓰기)별로 나눌지 정한다 | 일부 기능만 거절하는 장애에서 전체를 끊지 않습니다 |
| 알면 유리 | 재시도 예산을 둔다 | 장애 동안 재시도가 만드는 부하에 서비스 전체 상한을 둡니다 |
| 참고 | 라이브러리의 장치 중첩 순서를 확인한다 | 브레이커가 재시도 바깥에 있으면 장애를 늦게 알아챕니다 |

### 관찰할 것

- **시도 수 ÷ 요청 수**: 평소 1에 가깝고 장애 때 얼마까지 오르는지 봅니다. 시도 횟수 상한에 가까이 오르면 재시도가 부하를 키우고 있습니다.
- **실패의 종류별 수**: 타임아웃, 연결 실패, 거절 응답을 나눠 셉니다. 한데 모으면 어느 재시도 규칙이 효과가 있는지 알 수 없습니다.
- **브레이커 상태 변화**: 열림·반열림·닫힘의 시각과 횟수입니다. 장애가 없는데 자주 열리면 판정 창이 작거나 셀 실패를 잘못 골랐습니다.

## 말로 설명하기

### 30초 버전

실패한 요청을 다시 보내기 전에는 두 가지를 따로 물어야 합니다. 그 요청이 실행됐는지 아는가, 그리고 기다리면 원인이 풀리는가입니다. 실행됐는지 모르는 쓰기는 멱등할 때만 다시 보내고, 기다려도 안 풀리는 실패는 재시도하지 않습니다. 재시도는 장애 때 부하를 몇 배로 늘리므로 한 계층에서만, 남은 기한 안에서, 백오프와 지터를 붙여 합니다. 긴 장애는 요청이 아니라 서킷 브레이커가 기다립니다.

### 2분 버전

재시도는 실패가 드물고 일시적이라는 전제에서 정상 요청을 구합니다. 그런데 저장소가 아플 때는 모든 요청이 실패하므로, 같은 규칙이 저장소에 평소의 몇 배를 보냅니다. 계층마다 재시도하면 곱해지고, 즉시 오는 거절에 간격 없이 재시도하면 반복문 하나가 왕복 1ms 기준 초당 약 1,000번을 보냅니다.

그래서 먼저 실패를 분류합니다. 실행 전에 거절했다는 응답은 그 전송이 실행되지 않았다는 증거라 중복 걱정이 없지만, 기다려서 풀리는지는 따로 봐야 합니다. 타임아웃과 연결 끊김은 실행됐는지 모르므로 읽기만 다시 보내고 쓰기는 멱등할 때만 보냅니다. 다시 보낸다면 지수 백오프로 간격을 늘리고 지터로 흩어 회복 순간의 몰림을 막고, 바깥 기한에서 남은 시간이 다음 간격과 시도 타임아웃의 합보다 짧으면 멈춥니다. 이 계산상 요청 경로의 재시도는 수백 ms짜리 실패만 넘깁니다.

그보다 긴 장애에는 서킷 브레이커를 씁니다. 실패가 기준을 넘으면 한동안 부르지 않고 바로 실패해, 요청 스레드를 지키고 저장소의 회복을 돕습니다. 대가는 열린 동안 성공했을 요청도 실패한다는 것이고, 무엇을 실패로 셀지를 잘못 고르면 멀쩡한 기능까지 끊습니다. 순서는 안쪽부터 시도별 타임아웃, 브레이커, 재시도, 바깥 기한입니다.

### 예상 질문과 꼬리 질문

- **Q. "일시적인 오류는 재시도한다"는 규칙이 왜 부족한가요?**
  - 실행 여부를 묻지 않기 때문입니다. 타임아웃은 일시적일 수 있지만, 그 쓰기가 이미 실행됐다면 다시 보낸 요청이 두 번째 실행이 됩니다. 두 질문을 따로 물어야 합니다. 본문 "다시 보내기 전에 묻는 두 질문: 실행됐는가, 기다리면 풀리는가".
  - **꼬리: 그럼 거절 응답이면 언제나 안전한가요?**
    - 실행 도중에 난 오류라면 그 전까지 한 일이 남아 있을 수 있어 처음부터 해당하지 않습니다. 실행 전 거절이라도 그 전송이 실행되지 않았다는 것만 압니다. 클라이언트 라이브러리가 연결이 끊긴 뒤 같은 요청을 스스로 다시 보냈다면, 받은 거절은 두 번째 전송의 것이고 첫 전송은 실행됐을 수 있습니다. 그래서 쓰기는 거절 응답을 받았더라도 재전송 가능성이 있는 경로라면 멱등성을 전제로 다룹니다.
- **Q. 재시도 3번은 왜 위험한가요? 성공률이 오르잖아요.**
  - 실패가 드물 때는 그렇습니다. 모든 요청이 실패하는 장애에서는 저장소가 받는 요청이 평소의 4배가 됩니다. 저장소가 가장 약할 때 가장 많이 받습니다. 본문 "상대가 아플 때 요청이 가장 많아집니다".
  - **꼬리: 그럼 재시도를 아예 끄면 되나요?**
    - 짧은 네트워크 흔들림 같은 드문 실패에서 구할 수 있는 요청을 버리게 됩니다. 끄기보다 상한을 둡니다. 요청 하나는 시도 횟수와 남은 기한으로, 서비스 전체는 재시도 예산으로 막습니다.
- **Q. 지수 백오프만 있으면 되지 않나요? 지터는 왜 필요한가요?**
  - 같은 순간에 실패한 요청들은 같은 간격을 계산해 다시 같은 순간에 옵니다. 회복 직후 한꺼번에 몰려 저장소를 다시 넘어뜨릴 수 있습니다. 지터는 간격 안에서 무작위로 골라 그 몰림을 시간축으로 흩습니다. 본문 "지수 백오프와 지터".
- **Q. 재시작에 30초 걸리는 저장소라면, 재시도 간격을 늘려 30초를 버티게 하면 되지 않나요?**
  - 사용자 요청은 바깥 기한(예시 1초) 안에 끝나야 하므로 요청 하나가 30초를 기다릴 수 없습니다. 그동안 스레드도 묶입니다. 요청은 빨리 실패하거나 대체 경로로 가고, 회복을 기다리는 일은 서킷 브레이커가 요청 바깥에서 맡습니다. 백그라운드 작업이라면 오래 재시도해도 됩니다. 본문 "시도 횟수보다 남은 시간이 먼저입니다".
- **Q. 서킷 브레이커가 열려 있는 동안 저장소가 이미 회복했다면요?**
  - 반열림이 오기 전까지는 그 사실을 모르므로 성공했을 요청도 실패합니다. 열림 시간이 그 대가의 크기를 정합니다. 짧게 두면 회복을 빨리 알지만 아직 아픈 저장소에 시험 호출을 자주 보냅니다.
- **Q. 쓰기만 거부하는 장애에서 서킷 브레이커 하나로 Redis 호출 전체를 감싸면 무슨 일이 생기나요?**
  - 쓰기 실패만으로 실패 비율이 기준을 넘어 브레이커가 열리고, 정상으로 동작하던 읽기까지 막힙니다. 브레이커는 상대의 상태를 판단하는 장치이므로, 일부 기능만 거절하는 실패는 그 기능의 브레이커에서만 셉니다. 본문 "무엇을 실패로 셀 것인가".
- **Q. 브레이커와 재시도 중 무엇이 바깥에 있어야 하나요?**
  - 재시도가 바깥입니다. 브레이커가 시도마다 결과를 세야 장애를 빨리 알아채고, 열리면 재시도의 다음 시도도 저장소에 닿지 않습니다. 재시도는 브레이커의 "열려 있음" 실패를 다시 보내지 않습니다. 본문 "어떤 순서로 겹치는가".
  - **꼬리: 반대로 두면 무엇이 나빠지나요?**
    - 브레이커가 재시도까지 끝난 사용자 요청 하나를 결과 하나로 셉니다. 결과가 기록되기까지 시도 전체의 시간이 걸려 늦게 열리고, 일부만 실패하는 장애에서는 재시도가 실패를 가려 실패 비율이 낮게 보여 아예 열리지 않을 수 있습니다. 닫혀 있는 동안에는 재시도가 저장소를 시도 횟수만큼 두드립니다.
- **Q. 대기열 작업자의 반복문에 재시도를 넣을 때 무엇을 조심하나요?**
  - 평소 작업자는 일을 기다리는 동안 저절로 속도가 조절됩니다. 그런데 저장소가 즉시 거절을 돌려주면 기다림이 사라져, 간격 없는 반복문이 왕복 1ms 기준 초당 약 1,000번을 보냅니다. 실패하면 반드시 백오프와 지터로 쉬게 합니다. 본문 "즉시 오는 거절은 스스로 속도를 늦추지 않습니다".

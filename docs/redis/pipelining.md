# Redis 파이프라이닝과 다중 키 명령: 반복문 안의 Redis 호출은 무엇을 느리게 하고, 묶으면 무엇이 보장되지 않는가

> **핵심 질문**: Spring 앱이 반복문 안에서 Redis를 N번 부르면 무엇이 느려지는가? 다중 키 명령(`MGET`, `MSET`, `HMGET` 등), 파이프라이닝, `MULTI`/`EXEC`, Lua는 각각 무엇을 줄이고, 무엇을 보장하지 않는가?
>
> **범위**: 단일 Redis 서버를 기준으로 하고, 클러스터에서 달라지는 점은 따로 다룹니다. Spring Data Redis와 Lettuce의 기본 구성을 기준으로 합니다. `MULTI`/`EXEC`와 Lua의 원자성 자체는 [Redis 원자성](./atomicity.md), 메인 스레드가 명령을 처리하는 순서는 [Redis 이벤트 루프](./event-loop.md)에서 다루고, 여기서는 "여러 명령을 한 번에 보내는 방법"으로서의 차이만 씁니다.

## 배경 지식

### 이 문서의 예시: 주문 내역 화면의 상품 100개

문서 끝까지 다음 장면 하나를 씁니다.

- 주문 API(Spring Boot, Spring Data Redis, Lettuce)가 Redis 서버 한 대를 기본 설정으로 씁니다. 연결 설정은 Spring Boot 기본값 그대로입니다.
- Redis에는 상품 정보 캐시 `product:1` … `product:100`이 있습니다. 자료형은 String이고, 값은 상품 정보를 JSON으로 직렬화한 수백 바이트입니다. 각 키에는 10분 TTL이 붙어 있습니다.
- 주문 내역 화면은 상품 ID 100개를 알고 있고, 이 100개의 캐시를 Redis에서 읽어야 합니다. 첫 구현은 반복문에서 `redisTemplate.opsForValue().get("product:$id")`를 100번 부릅니다.

```text
주문 API (JVM)                               Redis 서버
요청 스레드 ── GET product:1 ──────────────▶  메인 스레드: 실행
            ◀────────────── 응답(JSON) ──
            ── GET product:2 ──────────────▶  실행
            ◀────────────── 응답(JSON) ──
               ... 100번 반복
```

화살표는 명령과 응답이 네트워크로 이동하는 방향이고, 위에서 아래로 시간이 흐릅니다. 연결 풀, 다른 요청 스레드, Redis의 다른 연결은 그림에서 뺐습니다. 다른 요청 스레드가 같은 연결을 함께 쓰는 모습은 아래 "Spring 앱의 명령은 공유 연결 하나로 나갑니다"에서 다룹니다.

이 문서의 시간 숫자는 흐름을 보여 주기 위한 **가상의 숫자**입니다. 주문 API와 Redis 사이의 왕복 시간을 0.5ms, `GET` 하나의 서버 실행 시간을 수 마이크로초(1ms의 1/1000 단위)로 둡니다. 실제 값은 네트워크, CPU, 값 크기에 따라 다르며 이 문서에서 재지 않았습니다.

배치 크기의 대가를 보는 "묶음이 너무 크면 무엇이 문제인가"에서는 같은 상품 캐시를 밤마다 10만 개 미리 채우는 적재 작업으로 예시를 키웁니다. 100개로는 묶음 크기의 문제가 드러나지 않기 때문입니다.

### 왕복 시간과 묶어 보내기

- **한 줄**: 왕복 시간은 요청을 보내고 응답이 돌아오기까지 상대가 일하는 시간을 뺀 나머지, 곧 오가며 기다리는 시간입니다. 요청을 하나씩 기다리며 보내면 전체 시간은 요청 수 × 왕복 시간에 비례하고, 여러 요청을 묶어 보내면 왕복 수가 줄어드는 대신 메모리와 실패했을 때 모르는 범위가 묶음 크기만큼 커집니다.
- **이 주제에서는**: 예시의 반복문은 왕복 100번이고, Redis가 일한 시간은 그중 아주 작은 몫입니다. 이 문서의 네 가지 방법은 모두 이 왕복 수를 줄이는 방법이며, 줄이는 대가와 덤으로 주는 보장이 서로 다릅니다. 원리와 대가는 [왕복과 묶어 보내기](../cs/round-trip-and-batching.md)에 있습니다.

### Redis는 명령을 메인 스레드 하나에서 하나씩 실행합니다

- **한 줄**: Redis 서버 프로세스에서 키를 읽고 바꾸는 명령은 메인 스레드 하나가 실행하고, 명령 하나를 끝낸 뒤 다음 명령을 시작합니다. 메인 스레드는 "데이터가 도착한 연결 고르기 → 그 연결의 명령 실행 → 응답을 버퍼에 담기"를 반복하는 이벤트 루프로 여러 연결을 차례로 맡습니다. 여기서 소켓은 운영체제가 연결마다 내주는 통신 출입구이고, 버퍼는 Redis가 연결마다 두는 임시 메모리입니다. 입력 버퍼에는 소켓에서 읽어 온 바이트가, 응답 버퍼에는 보낼 응답이 담깁니다.
- **이 주제에서는**: 명령 하나가 오래 걸리면 다른 모든 연결이 기다립니다. 그래서 "한 번에 보낸 묶음이 메인 스레드를 한 덩어리로 잡는가, 명령 하나씩 잡는가"가 방법마다 다르고, 이 차이가 다른 요청의 지연을 정합니다. 원리는 [I/O 다중화와 이벤트 루프](../cs/io-multiplexing-and-event-loop.md), Redis에서의 동작은 [Redis 이벤트 루프](./event-loop.md)에 있습니다.

### 시간은 세 가지로 나눠 셉니다

[Redis 이벤트 루프](./event-loop.md)의 "시간은 세 가지로 나눠 셉니다"와 같은 구분을 씁니다. **실행 시간**은 메인 스레드가 그 명령 자체를 실행한 시간, **기다린 시간**은 명령이 도착했지만 메인 스레드가 다른 일을 하느라 손대지 못한 시간, **클라이언트가 본 지연**은 앱이 명령을 보내고 응답을 받기까지의 전체 시간입니다. 클라이언트가 본 지연에는 왕복 시간과 기다린 시간이 들어가고, Redis의 `SLOWLOG`나 명령 통계에는 실행 시간만 들어갑니다. 이 문서의 "느리다"가 어느 시간을 말하는지 매번 밝힙니다.

### 원자성: 실행 도중 끼어들지 않는다는 뜻입니다

- **한 줄**: Redis 문서가 말하는 원자적 실행은 그 실행 도중에 다른 연결의 명령이 끼어들지 않는다는 뜻입니다. 실패했을 때 앞의 변경을 되돌린다(롤백)는 뜻이 아닙니다.
- **이 주제에서는**: 명령 하나, `EXEC` 하나, 스크립트 하나는 원자적으로 실행됩니다. 명령 두 개 사이에는 다른 연결의 명령이 끼어들 수 있습니다. 파이프라이닝으로 이어 보내도 이 틈은 그대로입니다. 자세한 내용은 [Redis 원자성](./atomicity.md)에 있습니다.

### Spring 앱의 명령은 공유 연결 하나로 나갑니다

- **한 줄**: Spring Data Redis의 기본 구성에서 `RedisTemplate`의 일반 명령은 모든 요청 스레드가 함께 쓰는 Lettuce 연결 하나로 나가고, 파이프라인·트랜잭션처럼 공유하면 안 되는 작업은 그 작업 동안만 쓰는 전용 연결로 나갑니다.
- **이 주제에서는**: Lettuce는 공유 연결 위에서 여러 스레드의 명령을 응답을 기다리지 않고 이어 보냅니다. 그러니 연결 하나가 왕복마다 막히지는 않습니다. 하지만 예시의 요청 스레드 **하나**는 `get()`이 결과를 돌려줄 때까지 다음 줄로 가지 않으므로, 그 스레드 입장에서는 왕복 100번을 차례로 기다립니다. 연결 구성과 전용 연결의 비용은 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)에 있습니다.

## 반복문 100번은 왜 느린가: 지연의 대부분은 왕복입니다

예시의 반복문이 상품 100개를 읽는 시간을 나눠 보면 다음과 같습니다.

| 무엇 | 계산(가상의 숫자) | 합계 |
| --- | --- | --- |
| 왕복 시간 | 100번 × 0.5ms | 50ms |
| Redis 실행 시간 | 100번 × 수 마이크로초 | 1ms 미만 |
| 주문 API가 본 지연 | | 약 50ms |

이 지연은 Redis 쪽 지표로는 잘 보이지 않습니다. Redis가 보기에는 아주 짧은 `GET`을 100번 실행했을 뿐이고, `SLOWLOG`에는 아무것도 남지 않습니다. 명령 사이 0.5ms 동안 이 연결에서는 아무것도 오지 않아서 메인 스레드는 다른 연결을 처리합니다. 느림은 **주문 API에서 Redis 호출 횟수와 전체 시간을 함께 재야** 드러납니다. 이 문서에서 호출 횟수는 요청 스레드가 Redis 응답을 기다린 횟수, 곧 왕복 수를 셉니다. Redis가 실행한 명령 수와는 다릅니다. 예를 들어 파이프라이닝으로 바꾸면 왕복 수는 줄지만 명령 수는 그대로입니다.

판단에 필요한 결론은 셋입니다.

- **Redis를 빠르게 해도 거의 줄지 않습니다.** 서버를 더 좋은 장비로 바꿔도 실행 시간 1ms 미만이 줄 뿐입니다.
- **호출 수가 데이터에 비례하면 지연도 비례합니다.** 상품이 1,000개인 주문 내역은 같은 코드로 약 500ms가 걸립니다.
- **요청 스레드를 그만큼 오래 붙잡습니다.** 같은 요청량에서 필요한 스레드 수가 늘어납니다([타임아웃](../cs/timeout.md)의 "처리량, 머무는 시간, 동시에 머무는 수").

해결은 왕복 하나에 더 많은 일을 싣는 것입니다. Redis에서 그 방법은 넷입니다.

## 네 가지 방법은 각각 무엇을 줄이고 무엇을 보장하는가

### 다중 키 명령: 명령 하나로 여러 키를 다룹니다

`MGET product:1 … product:100`은 키 100개를 명령 하나로 읽습니다. 왕복은 1번이고, 응답은 키 순서대로 값 100개를 담은 배열 하나입니다. 같은 모양의 명령으로 여러 키에 값을 쓰는 `MSET`, 해시 하나의 여러 필드를 읽는 `HMGET`, 여러 필드를 쓰는 `HSET`(필드·값 쌍을 여러 개 받음), 여러 키를 지우는 `DEL`·`UNLINK` 등이 있습니다.

**얻는 것**

- **왕복 1번, 명령 1개.** 서버가 명령을 해석하고 응답을 만드는 고정 비용도 한 번입니다.
- **한 번의 실행입니다.** 서버 한 대에서 `MGET`은 100개 키를 다른 명령이 끼어들지 않은 한 시점에 읽고, `MSET`은 모든 키를 한 번에 씁니다. 다른 연결은 일부만 바뀐 상태를 보지 못합니다.

**잘못 읽기 쉬운 점**

- **`MGET`은 없는 키와 String이 아닌 키에 똑같이 nil을 돌려줍니다.** 에러가 나지 않으므로, 실수로 Hash인 키를 섞어도 "캐시 미스"로 보입니다.
- **`MSET`에는 TTL 옵션이 없습니다.** 예시의 캐시처럼 키마다 10분 TTL이 필요하면 `MSET`으로는 쓸 수 없고, 키마다 `SET … EX 600`을 보내야 합니다. 그 `SET` 100개의 왕복을 줄이는 것이 다음 절의 파이프라이닝입니다.
- **명령 하나의 작업량은 키 수에 비례합니다.** `MGET`과 `MSET`의 공식 복잡도는 O(N)이고, N은 키 수입니다. O(N)은 작업량이 N에 비례해 늘어난다는 표기로, 실제 시간은 말하지 않습니다. 키 100개라면 짧지만, 키 수가 커지면 이 명령 하나가 메인 스레드를 그만큼 오래 잡습니다(아래 "묶음이 너무 크면 무엇이 문제인가").
- **같은 종류의 일만 묶을 수 있습니다.** `MGET`으로는 String만 읽습니다. "상품 캐시 읽기 + 재고 해시 읽기 + 조회수 증가"처럼 다른 명령이 섞이면 다중 키 명령으로는 묶을 수 없습니다.

### 파이프라이닝: 명령 여러 개를 응답을 기다리지 않고 이어 보냅니다

파이프라이닝은 `GET product:1`, `GET product:2`, … 100개를 응답을 기다리지 않고 연달아 보내고, 응답 100개를 보낸 순서대로 받는 방식입니다. Redis가 한 연결에서 받은 명령을 받은 순서대로 실행하고 같은 순서로 응답하기 때문에, 클라이언트는 "n번째 응답은 n번째 명령의 것"으로 짝지을 수 있습니다. 명령의 종류는 섞어도 됩니다.

**서버에서는 이렇게 처리됩니다.** 서버는 파이프라인이라는 묶음을 알지 못합니다. 그 연결의 소켓에서 바이트를 읽어 입력 버퍼에 담고, 그 안에 완성된 명령이 있는 만큼 **중간에 멈추지 않고** 차례로 실행합니다. 한 번 읽는 양은 그때의 버퍼 크기로 정해져 끝이 있으므로, 100개가 한 번에 읽히지 않으면 남은 명령은 이벤트 루프의 다음 바퀴에 읽혀 실행됩니다. 반대로 한 번에 다 읽히면 100개가 연달아 실행됩니다. 실행된 명령의 응답은 그 연결의 응답 버퍼에 차례로 쌓였다가 소켓으로 나갑니다.

```text
메인 스레드 │ 연결 1의 입력: GET×40 실행 │ 다른 연결의 명령 │ 연결 1의 다음 입력: GET×60 실행 │ ...
```

화살표 대신 칸으로 실행 순서를 나타냈고, 칸 길이는 시간을 비율대로 나타내지 않습니다. 40과 60은 읽힌 양에 따라 나뉠 수 있다는 것을 보여 주는 가상의 숫자입니다.

**얻는 것**

- **왕복이 약 1번으로 줄어듭니다.** 첫 명령을 보낸 뒤 마지막 응답을 받기까지 기다림이 한 번 겹쳐 지나갑니다. 예시라면 50ms가 약 0.5ms + 실행 시간 + 바이트 전송 시간이 됩니다.
- **서버의 처리량도 늘 수 있습니다.** 명령 여러 개가 한 번의 읽기 시스템 콜로 들어오고 응답 여러 개가 한 번의 쓰기로 나가므로, 명령마다 붙는 시스템 콜 비용이 줄어듭니다(Redis 공식 문서 pipelining, "It's not just a matter of RTT"). 얼마나 느는지는 환경마다 재야 합니다.
- **명령의 종류와 옵션을 자유롭게 섞을 수 있습니다.** `SET … EX 600` 100개처럼 다중 키 명령이 없는 일도 묶입니다.

**보장하지 않는 것**

- **원자성이 없습니다.** 명령 100개는 각각 따로 실행되고, 그 사이에 다른 연결의 명령이 끼어들 수 있습니다(공식 문서 eval-intro: "The commands in a pipelined request run in the order they are sent, but other clients' commands may be interleaved"). 위 그림에서 "다른 연결의 명령" 칸이 그 틈입니다. 그래서 예시의 100개 `GET` 결과는 한 시점의 값이 아닐 수 있습니다. 캐시 읽기라면 보통 문제가 없지만, "100개가 서로 맞아야 하는" 데이터라면 문제가 됩니다.
- **중간 결과로 다음 명령을 정할 수 없습니다.** 묶음의 명령은 응답을 보기 전에 모두 정해서 보내므로, "`GET` 결과가 없으면 `SET`" 같은 분기를 같은 묶음 안에 넣을 수 없습니다.
- **명령 하나의 실패가 나머지를 멈추지 않습니다.** 50번째 명령이 `WRONGTYPE` 같은 에러를 받아도 51번째부터는 그대로 실행됩니다. 앞의 변경도 되돌리지 않습니다. 묶음의 일부만 반영된 상태가 정상적인 결과로 남을 수 있습니다.

**대신 묶음 전체를 한 덩어리로 잡지는 않습니다.** 서버가 연달아 실행하는 단위는 묶음이 아니라 "한 번에 읽힌 범위"이므로, 큰 파이프라인이라면 읽기와 읽기 사이에 다른 연결의 명령이 끼어들 기회가 생깁니다. 아래 `MULTI`/`EXEC`, Lua는 묶음 전체가 한 실행 단위라 그런 기회가 없습니다. 다만 **얼마나 자주 끼어들 수 있는지는 보장되지 않습니다.** 한 번에 읽히는 범위는 버퍼 크기와 네트워크에 따라 달라지고, 그 범위 안의 명령이 다 끝날 때까지는 다른 연결이 기다립니다. 이 설명은 기준 버전 소스의 읽기·실행 경로에서 끌어낸 것이며, 실제로 몇 개씩 나뉘는지는 재지 않았습니다.

### MULTI/EXEC: 대기열에 쌓았다가 끊김 없이 실행합니다

`MULTI` 뒤의 명령은 바로 실행되지 않고 그 연결의 대기열에 쌓이며, `EXEC`를 받으면 대기열 전체를 다른 명령이 끼어들지 않게 차례로 실행하고 결과를 배열 하나로 돌려줍니다. 동작과 에러 처리의 세부는 [Redis 원자성](./atomicity.md)의 "MULTI/EXEC는 명령을 묶어 실행하지만, 중간 결과로 판단할 수 없습니다"에 있습니다.

배치 도구로 볼 때의 차이는 다음과 같습니다.

- **왕복 수는 보내는 방식에 달려 있습니다.** `MULTI`, 명령 100개, `EXEC`를 하나씩 기다리며 보내면 왕복이 102번입니다. 파이프라이닝으로 함께 보내야 1번이 됩니다. **`MULTI`/`EXEC` 자체는 왕복을 줄이지 않습니다.** 줄이는 것은 파이프라이닝입니다.
- **원자성을 더합니다.** 100개가 다른 명령이 끼어들지 않고 실행됩니다. 단, 실행 중에 난 에러는 그 명령만 실패하고 나머지는 반영되며 되돌리지 않습니다.
- **중간 결과로 분기할 수는 여전히 없습니다.** 결과는 `EXEC`의 응답으로 한꺼번에 옵니다.
- **메인 스레드를 한 덩어리로 잡습니다.** `EXEC`는 명령 하나이므로, 대기열 100개를 모두 실행할 때까지 다른 연결은 기다립니다. 파이프라이닝과 반대입니다. 묶음이 크면 그만큼 다른 요청의 지연이 늘어납니다.
- **대기열이 서버 메모리에 머뭅니다.** `EXEC` 전까지 쌓인 명령과 인자를 서버가 들고 있습니다. `CLIENT LIST`의 `multi`(쌓인 명령 수)와 `multi-mem`(그 인자가 차지하는 메모리)으로 보입니다.

### Lua 스크립트: 판단까지 서버 안에서 합니다

`EVAL`로 보낸 스크립트는 서버 안에서 여러 명령을 실행하고, 앞 명령의 결과를 보고 다음 명령을 정할 수 있습니다. 명령 하나(`EVAL`)이므로 왕복은 1번이고, 스크립트 전체가 다른 명령이 끼어들지 않게 실행됩니다.

- **유일하게 중간 결과로 분기할 수 있습니다.** "재고가 있을 때만 차감" 같은 "읽고 판단하고 쓰기"를 왕복 1번에 끝냅니다. 파이프라이닝으로는 읽기와 그 결과에 따른 쓰기를 한 묶음에 넣을 수 없습니다. 여러 건이라면 읽기를 모은 묶음 하나, 판단 후 쓰기를 모은 묶음 하나로 왕복 2번까지 줄일 수 있지만, 두 묶음 사이에 다른 요청이 값을 바꿀 수 있습니다.
- **메인 스레드를 스크립트 전체 동안 잡습니다.** `MULTI`/`EXEC`와 같습니다. 스크립트 안에서 키 10만 개를 돌면 그동안 모든 연결이 기다립니다.
- **에러가 나도 앞의 쓰기를 되돌리지 않습니다.** 스크립트 안의 명령이 에러를 내고 스크립트가 그 에러를 처리하지 않으면, 스크립트는 그 자리에서 멈추고 뒤의 명령은 실행되지 않습니다. 명령 하나만 실패하고 나머지가 실행되는 `EXEC`와 다릅니다.

대가와 클러스터 제약은 [Redis 원자성](./atomicity.md)의 "Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다"에 있습니다. 이 문서에서는 "왕복을 줄이는 도구로 Lua를 고를 이유는 중간 결과로 분기해야 할 때"라는 점만 기억하면 됩니다. 분기가 필요 없으면 같은 왕복 1번을 메인 스레드를 덜 잡는 파이프라이닝이나 다중 키 명령으로 얻을 수 있습니다.

### 한 표로 비교합니다

예시의 상품 100개를 기준으로 합니다.

| 방법 | 왕복 | 끼어들기 없음(원자성) | 중간 결과로 분기 | 일부 명령이 에러일 때 | 메인 스레드를 잡는 단위 |
| --- | --- | --- | --- | --- | --- |
| 반복문(하나씩 기다림) | 100번 | 명령 하나씩만 | 가능(앱에서, 왕복마다) | 그 명령만 실패 | 명령 하나 |
| 다중 키 명령(`MGET`, `MSET`) | 1번 | 예(한 노드 안) | 불가 | 명령 전체가 에러이거나 성공 | 명령 하나(키 수에 비례) |
| 파이프라이닝 | 약 1번 | 아니오 | 불가 | 그 명령만 실패, 나머지 실행 | 한 번에 읽힌 범위씩, 범위 사이에 다른 연결 |
| `MULTI`/`EXEC`(파이프라이닝으로 보냄) | 약 1번 | 예 | 불가 | 실행 중 에러는 그 명령만 실패, 나머지 반영 | 대기열 전체 |
| Lua(`EVAL`) | 1번 | 예 | 가능(서버에서) | 처리하지 않은 에러에서 멈춤, 에러 이전의 쓰기는 남음 | 스크립트 전체 |

고르는 순서는 다음과 같습니다. 같은 종류의 일을 여러 키에 하면 **다중 키 명령**이 가장 단순합니다. 종류가 섞이거나 옵션(TTL 등)이 필요하면 **파이프라이닝**입니다. 다른 요청이 중간 상태를 보면 안 되면 **`MULTI`/`EXEC`를 파이프라이닝으로** 보냅니다. 앞 결과로 다음 명령을 정해야 하면 **Lua**입니다. 뒤로 갈수록 보장이 늘어나는 대신, 메인 스레드를 한 덩어리로 잡는 시간이 늘어납니다.

## Spring Data Redis에서는 어떻게 나가는가

### 다중 키 명령: 템플릿 메서드 하나

- `opsForValue().multiGet(keys)`는 `MGET` 하나를 공유 연결로 보냅니다. 결과 목록은 키 순서와 같고, 없는 키 자리는 `null`입니다.
- `opsForValue().multiSet(map)`은 `MSET` 하나입니다. TTL을 붙일 수 없습니다.
- `opsForHash().multiGet(key, fields)`는 `HMGET`, `opsForHash().putAll(key, map)`은 여러 필드를 한 번에 쓰는 `HMSET` 하나입니다.

예시라면 반복문을 `multiGet` 한 번으로 바꾸는 것이 가장 작은 변경입니다. 전용 연결을 쓰지 않으므로 연결을 새로 맺는 비용도 없습니다.

### 파이프라이닝: executePipelined

`redisTemplate.executePipelined(RedisCallback)`은 콜백 안에서 보낸 명령을 파이프라이닝으로 보내고, 결과를 보낸 순서대로 담은 목록을 돌려줍니다. 동작에서 판단에 필요한 점은 다음과 같습니다.

- **결과 목록이 명령과 하나씩 맞지는 않습니다.** `OK` 같은 상태 응답만 돌려주는 일부 명령(예: `putAll`이 보내는 `HMSET`)은 결과 목록에서 빠집니다. 예시의 `SET … EX 600`은 성공 여부(`true`)로 들어갑니다. 바이트 값은 템플릿의 값 직렬화기(또는 인자로 준 직렬화기)로, 해시 결과(Map)는 해시 키·값 직렬화기로 역직렬화되고, 숫자 같은 결과는 그대로 들어갑니다. 결과를 목록 위치로 꺼낸다면 어떤 명령이 목록에 들어가는지 먼저 확인합니다.

- **콜백 안의 명령은 결과를 돌려주지 않습니다.** 콜백 안에서 부른 `get()`은 `null`을 돌려주고, 진짜 결과는 `executePipelined`가 끝난 뒤 목록으로 받습니다. 콜백 자체도 `null`을 돌려줘야 하며, 아니면 예외가 납니다. 이것이 "중간 결과로 분기할 수 없다"가 코드에 드러나는 모습입니다.
- **전용 연결로 나갑니다.** 파이프라인은 공유 연결이 아니라 그 호출 동안만 쓰는 전용 연결을 씁니다. **연결 풀이 없으면 호출할 때마다 TCP 연결을 새로 맺고 닫습니다.** 연결을 맺고 준비하는 데 왕복이 몇 번 들므로, 예시처럼 API 요청마다 100개를 읽는 데 쓰면 아낀 왕복을 연결 맺기에 다시 쓸 수 있습니다. 요청 경로에서 자주 쓴다면 풀을 켜거나, 다중 키 명령으로 바꿀 수 있는지 먼저 봅니다. 풀의 기본값과 대가는 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)의 "연결 풀은 언제 필요하고, 무엇을 대가로 치르는가"에 있습니다.
- **기본 설정에서도 명령은 응답을 기다리지 않고 나갑니다.** Lettuce는 명령을 맡기는 즉시 소켓에 써 보내는 것이 기본(자동 플러시)이고, Spring Data Redis의 파이프라인 기본 정책(`PipeliningFlushPolicy.flushEachCommand()`)도 이를 그대로 둡니다. 명령 하나씩 내보내지만 응답을 기다리지 않으므로 왕복은 약 1번입니다. `LettuceConnectionFactory.setPipeliningFlushPolicy`로 `flushOnClose()`(끝에 한 번에 내보냄)나 `buffered(n)`(n개마다 내보냄)을 고르면 명령을 모았다가 한 번에 내보냅니다. 이것은 왕복이 아니라 내보내는 횟수를 바꾸며, 실제로 시스템 콜이나 패킷이 얼마나 줄어드는지는 네트워크 라이브러리와 운영체제에 달려 있어 확인하지 않았습니다.
- **명령 타임아웃의 시계가 둘 걸립니다.** 하나는 명령마다 Lettuce에 맡긴 순간부터 가는 명령 타임아웃(`spring.data.redis.timeout`)입니다. 다른 하나는 콜백이 끝난 뒤 결과를 모을 때, 남은 명령 전체의 완료를 같은 값 하나를 기한으로 기다리는 시계입니다. 그래서 묶음이 커서 뒤쪽 명령의 응답이 늦으면, 어느 쪽 시계가 먼저 다하든 묶음 전체가 `RedisPipelineException`으로 실패합니다. 감싼 원인은 어느 시계였는지에 따라 다를 수 있습니다. **타임아웃은 클라이언트가 기다림을 그만둘 뿐이라, 서버는 이미 받은 명령을 계속 실행합니다.**
- **일부 명령이 에러면 묶음 전체가 예외가 됩니다.** 에러를 받은 명령이 하나라도 있으면 `RedisPipelineException`이 납니다. 서버에서는 나머지 명령이 실행됐습니다. 이 예외의 `getPipelineResult()`는 명령별 결과와 예외를 담도록 만들어져 있지만, Redis 에러 응답을 받은 경우에는 목록이 비어 있을 수 있습니다(소스로 추론했으며 재현하지 않았습니다). 그러니 **예외에서 "어느 명령이 실패했고 어느 것이 반영됐는가"를 알아낼 수 있다고 기대하지 않습니다.** 다시 보내도 안전하게 설계하는 것이 먼저입니다(아래 "연결이 끊기면 파이프라인의 어디까지 실행됐는지 모릅니다").

### MULTI/EXEC와 Lua

`MULTI`/`EXEC`는 `SessionCallback` 안에서 같은 연결로 보내야 하고, 스크립트는 `RedisTemplate.execute(RedisScript, keys, args…)`로 보냅니다. 파이프라인이나 트랜잭션 안에서 스크립트를 실행하면 결과로 `null`을 받습니다. 이 세부는 [Redis 원자성](./atomicity.md)의 "Spring에서 확인할 것"에 있습니다.

## 묶음이 너무 크면 무엇이 문제인가

예시를 키웁니다. 밤마다 상품 캐시 10만 개를 미리 채우는 적재 작업이 `SET product:{id} <JSON> EX 600`을 보냅니다. 상품 하나의 JSON을 수백 바이트로 두면, 10만 개의 명령은 수십 MB입니다(가상의 계산). 이 작업이 10만 개를 파이프라인 하나에 담는 경우와 1,000개씩 100번 나눠 담는 경우를 비교합니다.

| 무엇이 커지는가 | 10만 개 한 묶음에서 | 누가 언제 부담하는가 |
| --- | --- | --- |
| 클라이언트 메모리 | Lettuce가 보낸 명령 10만 개와 그 결과를, Spring Data Redis가 결과 목록 10만 칸을 끝날 때까지 들고 있음 | 적재 작업의 JVM 힙. 묶음이 끝날 때까지 |
| Redis의 응답 버퍼 | 클라이언트가 응답을 읽는 속도보다 서버가 실행하는 속도가 빠르면 응답이 쌓임 | Redis 메모리. 일반 클라이언트에는 기본 한도가 없음 |
| 명령 타임아웃 | 뒤쪽 명령의 응답이 명령 타임아웃 안에 와야 함 | 넘으면 묶음 전체가 예외, 서버는 계속 실행 |
| 실패했을 때 모르는 범위 | 끊기면 10만 개 중 어디까지 실행됐는지 모름 | 다시 보낼 때 |
| 첫 결과까지의 시간 | 10만 개가 다 끝나야 결과 목록을 받음 | 적재 작업 |

나눠 보내도 왕복은 100번뿐이라 전체 시간 차이는 작습니다(1,000개 묶음 하나에 왕복 0.5ms씩, 가상의 숫자). 반면 위 표에서 명령 수에 비례해 들고 있는 것, 곧 클라이언트가 들고 있는 명령과 결과, 실패했을 때 모르는 범위, 첫 결과까지 기다리는 명령 수는 묶음 하나의 크기로 줄어듭니다. Redis 응답 버퍼가 실제로 얼마나 쌓이는지는 클라이언트가 읽는 속도에 달려 있어 묶음 크기만으로 정해지지 않습니다. Redis 공식 문서도 큰 파이프라인은 예를 들어 1만 개처럼 적당한 크기로 나눠 보내고, 응답을 읽은 뒤 다음 묶음을 보내라고 권합니다. 속도는 거의 같고 응답을 쌓는 메모리가 그 묶음만큼으로 제한된다는 이유입니다(Redis 공식 문서 pipelining, IMPORTANT NOTE). 1만이라는 숫자는 예시일 뿐이고, 응답이 클수록 묶음을 작게 잡아야 합니다.

### Redis 응답 버퍼는 Redis 메모리입니다

응답 버퍼의 메모리는 Redis 서버의 메모리 사용량에 들어가고, `maxmemory` 판정에서도 빠지지 않습니다. 그래서 응답이 쌓이면 메모리 한도에 닿아 키가 지워지거나(eviction 정책일 때) 쓰기가 거부될 수 있습니다. 8.2.10 기본 설정에서 일반 클라이언트의 응답 버퍼 한도는 없고(`client-output-buffer-limit normal 0 0 0`), 연결 전체의 메모리 한도(`maxmemory-clients`)도 꺼져 있습니다(기본 0). 관찰은 `CLIENT LIST`의 `omem`(응답 버퍼가 쓰는 메모리)·`tot-mem`(그 연결이 쓰는 메모리 전체), `INFO memory`의 `mem_clients_normal`로 합니다.

응답 버퍼는 클라이언트가 응답을 제때 읽으면 크게 쌓이지 않습니다. Lettuce는 응답을 받는 대로 읽으므로 보통은 문제가 작습니다. 쌓이는 것은 클라이언트가 바쁘거나(긴 GC 멈춤 등), 응답 자체가 클 때입니다. 예를 들어 `GET` 10만 개처럼 **큰 응답을 많이 받는 파이프라인**이 이 경우입니다.

### 한 덩어리로 실행되는 묶음은 다른 요청을 기다리게 합니다

같은 10만 개라도 어떤 방법으로 보내느냐에 따라 다른 연결이 받는 영향이 다릅니다.

- **파이프라이닝**: 서버는 읽힌 범위씩 실행하므로, 읽기와 읽기 사이에 다른 요청이 끼어들 기회가 있습니다. 다른 요청이 기다리는 시간은 묶음 전체가 아니라 한 번에 읽힌 범위의 실행 시간 정도이지만, 그 범위의 크기는 보장되지 않습니다. 또 서버가 해야 할 전체 일은 같으므로, 적재 작업이 도는 동안 서버 CPU는 그만큼 바쁩니다.
- **`MSET` 10만 개 키 하나**, **`MULTI`/`EXEC` 10만 개**, **스크립트 하나로 10만 개**: 명령 하나 또는 실행 단위 하나라서, 끝날 때까지 다른 모든 연결이 기다립니다. 주문 API의 짧은 `GET`도 그 뒤에 줄을 섭니다. 이 기다림은 주문 API의 지연으로 나타나고, 원인은 적재 작업에 있어 찾기 어렵습니다([Redis 이벤트 루프](./event-loop.md)의 "명령 하나가 모두를 멈추는 과정").

그래서 대량 적재는 **원자성이 필요 없으면 적당한 크기로 나눈 파이프라이닝**이 기본입니다. 원자성이 필요하면 원자적으로 묶어야 하는 범위를 가능한 작게 줄입니다.

### 공유 연결에서 큰 응답은 다른 스레드의 응답을 늦춥니다

`executePipelined`는 전용 연결을 쓰므로 공유 연결의 다른 명령을 막지 않습니다. 반면 `multiGet`은 공유 연결로 나가므로, 키 수만 개의 `MGET`처럼 큰 응답을 받는 명령은 그 응답을 다 받을 때까지 같은 연결의 다른 스레드 응답을 뒤에 줄 세웁니다. 원인과 대응은 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)의 "공유 연결의 대가: 앞 응답이 늦으면 뒤 응답도 늦습니다"에 있습니다. 예시의 100개 `MGET`은 응답이 수십 KB라 이 걱정이 작지만, 키 수가 데이터에 따라 커질 수 있다면 상한을 두고 나눠 보냅니다.

## 클러스터에서는 슬롯별로 갈립니다

Redis Cluster는 키를 슬롯 하나에 배정하고, 슬롯을 여러 주 서버에 나눠 맡깁니다. 한 번의 실행(명령 하나, `EXEC` 하나, 스크립트 하나)이 다루는 키는 모두 같은 슬롯이어야 하고, 아니면 `CROSSSLOT` 에러가 납니다. 원리는 [Redis Cluster](./cluster.md)에 있습니다. 예시의 상품 100개가 주 서버 3대에 흩어져 있다고 하면 방법마다 다음처럼 달라집니다.

- **다중 키 명령**: Lettuce는 `MGET`, `MSET`, `DEL` 등 일부 다중 키 명령을 받으면 키를 슬롯별로 나눠 각 노드에 따로 보내고 결과를 합칩니다. 에러는 나지 않지만, 슬롯이 모두 다르면 `MGET` 100개로 나뉘고, 한 번의 실행이 주던 보장(`MGET`의 한 시점 값, `MSET`의 한 번에 쓰기)도 사라집니다. 세부는 [Redis Cluster](./cluster.md)의 "클라이언트가 나눠 보내면 에러는 사라지지만 원자성도 사라집니다"에 있습니다.
- **파이프라이닝**: 서버는 파이프라인을 모르므로 슬롯 제약이 없습니다. Lettuce가 명령마다 키의 슬롯을 보고 해당 노드의 연결로 보냅니다. 그래서 묶음은 노드 수만큼의 작은 묶음으로 갈려 노드마다 따로 흐르고, 전체 시간은 가장 늦은 노드가 정합니다. 순서는 한 노드로 가는 명령끼리만 지켜집니다. Spring Data Redis는 결과를 보낸 순서대로 모아 돌려주므로 결과 목록의 순서는 그대로입니다. 다만 Spring Data Redis 참조 문서는 클러스터에서 슬롯이 다른 키를 받는 일부 명령(`rename`, `sInter` 등)이 파이프라인에서 지원되지 않는다고 적고 있습니다.
- **`MULTI`/`EXEC`**: 같은 슬롯의 키만 묶을 수 있고, Spring Data Redis의 클러스터 연결은 `MULTI`를 지원하지 않습니다.
- **Lua**: 스크립트의 키를 모두 같은 슬롯에 둬야 합니다.

같은 슬롯에 모으는 방법은 해시 태그(키의 `{…}` 부분만으로 슬롯을 정함)입니다. 예시의 상품 키를 `{product}:1`처럼 바꾸면 100개 `MGET`이 노드 하나로 가지만, 상품 캐시 전체가 노드 하나에 몰립니다. 캐시 읽기처럼 원자성이 필요 없는 일에는 태그로 모으지 말고, 슬롯별로 나뉘는 비용을 받아들이거나 파이프라이닝을 씁니다.

## 연결이 끊기면 파이프라인의 어디까지 실행됐는지 모릅니다

적재 작업이 1,000개 `SET` 파이프라인을 보내는 도중 연결이 끊겼다고 합시다. 그 순간 1,000개는 다음 중 하나입니다.

| 상태 | 서버에서 | 클라이언트가 아는가 |
| --- | --- | --- |
| 응답을 받음 | 실행됨 | 압니다 |
| 보냈지만 응답을 받지 못함 | 실행됐을 수도(응답이 오는 길에 끊김), 실행되지 않았을 수도(서버에 닿지 못했거나 실행 전에 끊김) 있음 | 모릅니다 |
| 아직 보내지 못함 | 실행되지 않음 | 압니다 |

응답을 받지 못한 명령에는 실행된 것과 안 된 것이 섞여 있습니다. 여기에 두 가지 다시 보내기가 겹칩니다.

- **Lettuce가 스스로 다시 보냅니다.** 기본 설정의 Lettuce는 연결이 끊기면 응답을 받지 못한 명령을 버리지 않고 다시 연결된 뒤 다시 보냅니다. 앱 코드에 재시도가 없어도 이미 실행된 명령이 한 번 더 실행될 수 있습니다. 세부는 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)의 "연결이 끊기면 Lettuce가 응답 못 받은 명령을 다시 보냅니다"에 있습니다.
- **앱이 묶음을 통째로 다시 보냅니다.** `RedisPipelineException`이나 타임아웃을 받고 `executePipelined`를 다시 부르면, 이미 반영된 명령도 다시 실행됩니다.

판단 기준은 **묶음 안의 명령이 두 번 실행돼도 결과가 같은가(멱등한가)** 입니다.

- **`SET key value EX 600`처럼 값을 정하는 명령**은 같은 값을 다시 써도 결과가 같습니다(TTL은 다시 실행한 시점부터 다시 셉니다). 단, 첫 실행과 다시 보내기 사이에 다른 요청이 더 새로운 값을 썼다면 다시 보낸 `SET`이 그 값을 옛 값으로 덮어씁니다. 예시의 캐시 적재처럼 "잠깐 옛 값이 보여도 다음 갱신이나 TTL 만료로 바로잡히는" 데이터라면 묶음을 통째로 다시 보내도 됩니다. 그렇지 않은 데이터라면 버전을 비교해 더 새 값일 때만 쓰는 방식이 필요합니다.
- **`INCR`, `RPUSH`, `HINCRBY`처럼 현재 값에 더하는 명령**은 다시 실행하면 두 번 반영됩니다. 조회수 증가나 이벤트 기록을 파이프라인으로 몰아 보낸다면, 다시 보내기 전에 멱등하게 만들어야 합니다. 요청마다 처리 기록을 남기고 기록이 있으면 건너뛰는 방법은 [Redis 멱등 키](./idempotency-key.md)에 있습니다.

`MULTI`/`EXEC`는 이 불확실성의 모양을 바꿉니다. 서버는 연결이 끊긴 클라이언트의 `MULTI` 대기열을 버리므로, `EXEC`가 실행되지 않았다면 대기열의 명령은 하나도 실행되지 않습니다. `EXEC`가 실행됐다면 대기열 전체가 실행됐습니다(실행 중 에러가 난 명령은 빼고). 그래서 "어디까지"가 아니라 "실행됐는가, 안 됐는가" 둘 중 하나가 됩니다. Lua 스크립트는 실행되지 않았거나 실행됐거나인 점은 같지만, 실행 중 처리하지 않은 에러가 나면 그 자리에서 멈추므로 "실행됐다"가 "끝까지 실행됐다"를 뜻하지는 않습니다. 어느 쪽이든 응답을 받지 못하면 실행 여부를 구분하지 못하므로, 다시 보낸다면 여전히 멱등성이 필요합니다.

## 흔한 오해 모아 보기

- **"Redis가 빠르니 반복문으로 불러도 된다."** 반복문의 지연은 Redis 실행 시간이 아니라 왕복 시간 × 호출 수가 정합니다. Redis 지표에는 보이지 않습니다("반복문 100번은 왜 느린가: 지연의 대부분은 왕복입니다").
- **"파이프라인으로 보내면 한 덩어리로 실행된다."** 명령마다 따로 실행되고, 사이에 다른 연결의 명령이 끼어들 수 있습니다. 한 명령의 에러가 나머지를 멈추지 않습니다("파이프라이닝: 명령 여러 개를 응답을 기다리지 않고 이어 보냅니다").
- **"`MULTI`/`EXEC`를 쓰면 왕복이 줄어든다."** 왕복을 줄이는 것은 함께 쓰는 파이프라이닝입니다. 하나씩 기다리며 보내면 명령 수 + 2번입니다("MULTI/EXEC: 대기열에 쌓았다가 끊김 없이 실행합니다").
- **"큰 묶음은 파이프라인이든 `EXEC`든 서버에 주는 영향이 같다."** 파이프라인은 읽힌 범위씩 실행돼 읽기 사이에 다른 연결이 끼어들 기회가 있지만, `EXEC`와 스크립트는 끝날 때까지 다른 연결을 기다리게 합니다. 다만 파이프라인도 한 번에 읽힌 범위만큼은 연달아 실행합니다("한 덩어리로 실행되는 묶음은 다른 요청을 기다리게 합니다").
- **"`executePipelined`는 언제나 반복문보다 빠르다."** 풀 없이 쓰면 호출마다 연결을 새로 맺으므로, 묶음이 작을 때는 아낀 왕복보다 연결 맺기의 왕복이 클 수 있습니다("파이프라이닝: executePipelined").
- **"클러스터에서 `MGET`이 에러 없이 되니 한 노드와 같다."** Lettuce가 슬롯별로 나눠 보낸 결과일 수 있고, 그러면 한 시점의 값이 아닙니다("클러스터에서는 슬롯별로 갈립니다").
- **"파이프라인이 실패하면 예외에 담긴 결과로 실패한 명령만 다시 보내면 된다."** 결과 목록이 비어 있을 수 있고, 응답을 못 받은 명령 중에도 실행된 것이 섞여 있습니다("연결이 끊기면 파이프라인의 어디까지 실행됐는지 모릅니다").

## 실무 포인트

### 어떤 방법을 고를까

| 요구 | 고를 방법 | 대안과 그 대가 |
| --- | --- | --- |
| 여러 키의 값을 한꺼번에 읽기(예시의 상품 100개) | `opsForValue().multiGet` | `executePipelined`: 풀이 없으면 호출마다 연결을 맺음 |
| 한 해시의 여러 필드 읽기 | `opsForHash().multiGet`(`HMGET`) | 전체 읽기(`HGETALL`)는 필요 없는 필드까지 응답이 커짐 |
| 여러 키에 TTL과 함께 쓰기(캐시 적재) | 적당한 크기로 나눈 `executePipelined` + `SET … EX` | `multiSet` 뒤 `expire`를 따로 보내면 TTL 없는 순간이 생기고 왕복이 늘어남 |
| 여러 쓰기를 다른 요청이 중간 상태로 보지 않게 | `SessionCallback` 안의 `MULTI`/`EXEC`(파이프라이닝으로) | 묶음 동안 메인 스레드를 잡으므로 묶음을 작게 |
| 앞 결과를 보고 다음 명령을 정함 | Lua 스크립트 | 한 묶음으로는 불가. 여러 건이면 읽기 묶음과 쓰기 묶음으로 왕복 2번까지 줄지만, 그 사이에 다른 요청이 끼어듦 |

### 개발자가 정할 수 있는 것과 관찰해야 하는 것

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | 반복문 안의 `RedisTemplate` 호출을 찾고, 호출 수가 무엇에 비례하는지 본다 | 지연이 왕복 × 호출 수이고, 데이터가 늘면 그만큼 늘어납니다. Redis 지표로는 보이지 않습니다 |

| 알면 유리 | `executePipelined`를 요청 경로에서 자주 쓰면 풀 설정을 확인한다 | 풀이 없으면 호출마다 연결을 맺어 왕복을 다시 씁니다 |
| 알면 유리 | 명령 타임아웃을 묶음 하나가 끝나는 시간 기준으로도 확인한다 | 묶음 뒤쪽 명령의 응답이 명령 타임아웃 안에 와야 합니다. 타임아웃이 나도 서버는 계속 실행하므로, 늘리기보다 묶음을 줄입니다 |
| 알면 유리 | 클러스터에서 다중 키 명령의 키 분포를 본다 | 슬롯이 흩어지면 슬롯 수만큼 명령으로 나뉘고 원자성이 사라집니다 |

관찰할 지표는 다음과 같습니다.

- **주문 API 쪽**: 요청 하나당 Redis 호출 수와 Redis 호출 전체 시간. 호출 하나의 시간만 보면 정상으로 보이므로 두 값을 함께 기록합니다.
- **Redis 쪽**: `INFO commandstats`의 명령별 호출 수(파이프라인 안의 명령도 하나씩 셉니다), `CLIENT LIST`의 `omem`·`tot-mem`·`multi-mem`, `INFO memory`의 `mem_clients_normal`.

### 증상과 확인 순서

**증상 1: 특정 API만 느린데 Redis `SLOWLOG`는 비어 있다.**

1. 그 API가 요청 하나에 Redis를 몇 번 부르는지 확인합니다. 호출 수 × 왕복 시간이 지연과 비슷하면 원인은 반복 호출입니다.
2. 호출 수가 데이터에 비례하는지 봅니다(장바구니 크기, 주문 상품 수). 느린 요청이 큰 데이터의 사용자에게 몰리면 이 경우입니다.
3. 다중 키 명령이나 파이프라이닝으로 바꿉니다. 바꾼 뒤 왕복 수와 Redis 호출 전체 시간이 줄었는지, 응답 크기가 너무 커지지 않았는지 확인합니다. 다중 키 명령은 Redis의 명령 수(`INFO commandstats`)도 줄이지만, 파이프라이닝은 명령 수를 그대로 두므로 Redis 쪽 명령 수로는 개선을 판정할 수 없습니다.

**증상 2: 야간 적재 작업 시간대에 다른 API의 Redis 지연이 튄다.**

1. 적재 작업이 `MSET`·`MULTI`/`EXEC`·스크립트처럼 한 번의 실행에 많은 키를 담는지 봅니다. 그렇다면 그 실행 동안 다른 요청이 기다린 것입니다([Redis 이벤트 루프](./event-loop.md)).
2. 파이프라이닝이라면 서버 CPU 사용률과 `INFO memory`의 `mem_clients_normal`을 봅니다. 응답 버퍼가 쌓였다면 묶음을 줄입니다.
3. 대응은 묶음을 나누는 것입니다. 부작용은 작업 전체 시간이 조금 늘어나는 것이고, 원자성이 필요했던 작업이라면 원자성의 범위를 다시 정해야 합니다. 원인이 서버 CPU라면 묶음을 나눠도 서버가 할 전체 일은 줄지 않으므로, 동시에 도는 적재 작업 수를 줄이거나 묶음 사이에 간격을 두어 보내는 속도를 낮춥니다. 대가는 적재가 끝나는 시간이 늦어지는 것입니다.

**증상 3: 파이프라인 재시도 후 카운터가 실제보다 크다.**

1. 묶음에 `INCR`, `HINCRBY`, `RPUSH`처럼 더하는 명령이 있는지 봅니다.
2. 같은 시각에 연결이 끊긴 기록(Lettuce 재연결 로그)이나 `RedisPipelineException`·타임아웃 후 재시도가 있었는지 봅니다.
3. 명령을 멱등한 형태로 바꾸거나 처리 기록을 둡니다. 자동 재연결을 끄는 대응은 다시 연결하는 책임이 앱으로 오므로 먼저 고르지 않습니다.

### Spring에서 확인할 것

- **직렬화**: `multiGet`의 결과는 템플릿의 값 직렬화기로 역직렬화됩니다. `executePipelined`의 결과는 바이트 값만 값 직렬화기를 거치고 숫자는 그대로 오므로, `INCR`과 `GET`이 섞이면 결과 목록에 서로 다른 타입이 섞입니다. 상태 응답만 돌려주는 명령은 목록에서 빠지므로, 결과를 목록 위치로 꺼낼 때 위치와 타입을 함께 확인합니다.
- **`@Transactional`과 섞지 않기**: 템플릿에 트랜잭션 지원을 켠 상태에서는 쓰기 명령이 `MULTI` 대기열에 들어갈 수 있습니다. 파이프라인과 트랜잭션을 함께 쓸 때의 결과 처리는 [Redis 원자성](./atomicity.md)의 "Spring에서 확인할 것"을 따릅니다.
- **캐시 미스와 타입 오류를 구분하기**: `multiGet` 결과의 `null`은 "키 없음"과 "String이 아닌 키" 둘 다입니다. 키 이름 규칙이 섞일 수 있는 곳이라면 이 점을 알고 씁니다.

## 말로 설명하기

### 30초 버전

반복문에서 Redis를 N번 부르면 지연은 Redis 실행 시간이 아니라 왕복 시간 × N이 정합니다. Redis 지표에는 보이지 않습니다. 같은 종류를 여러 키에 하면 `MGET` 같은 다중 키 명령, 종류가 섞이거나 TTL이 필요하면 파이프라이닝으로 왕복을 1번으로 줄입니다. 파이프라이닝은 원자성을 주지 않고 중간 결과로 분기할 수도 없습니다. 끼어들기를 막으려면 `MULTI`/`EXEC`, 분기가 필요하면 Lua인데, 이 둘은 실행 동안 메인 스레드를 한 덩어리로 잡습니다. 묶음은 크기에 상한을 두고, 다시 보낼 묶음은 멱등하게 만듭니다.

### 2분 버전

주문 내역에서 상품 100개를 반복문으로 읽으면 왕복 0.5ms가 100번이라 50ms가 걸리고, Redis가 일한 시간은 1ms도 안 됩니다(가상의 숫자). 그래서 `SLOWLOG`는 비어 있고, 앱에서 호출 수를 재야 원인이 보입니다.

왕복을 줄이는 방법은 넷입니다. `MGET`은 명령 하나라 왕복 1번에 한 시점의 값을 주지만, String만 읽고 `MSET`에는 TTL이 없습니다. 파이프라이닝은 명령 여러 개를 응답 없이 이어 보내는 방식이라 종류를 섞을 수 있지만, 명령마다 따로 실행되어 사이에 다른 연결이 끼어들고, 한 명령의 에러가 나머지를 멈추지 않습니다. 대신 서버는 묶음 전체가 아니라 한 번에 읽힌 범위씩 실행하므로, 큰 파이프라인이라도 읽기 사이에 다른 요청이 끼어들 기회가 있습니다. `MULTI`/`EXEC`는 끼어들기를 막지만 왕복은 파이프라이닝과 함께 써야 줄고, Lua는 중간 결과로 분기까지 할 수 있습니다. 이 둘은 실행 단위 전체 동안 메인 스레드를 잡습니다.

Spring에서는 `multiGet`이 공유 연결로 `MGET` 하나를 보내고, `executePipelined`는 전용 연결을 씁니다. 풀이 없으면 호출마다 연결을 맺으므로 요청 경로에서는 `multiGet`이 먼저입니다. 파이프라인은 뒤쪽 명령의 응답까지 명령 타임아웃 안에 와야 하고, 에러가 나면 `RedisPipelineException` 하나로 옵니다. 결과 목록은 상태 응답 명령이 빠져 명령과 하나씩 맞지 않을 수 있습니다.

묶음이 크면 클라이언트 힙과 실패 범위가 커지고, 응답 버퍼가 쌓일 수 있는 상한과 타임아웃을 넘을 위험도 커지므로, 나눠 보냅니다. 나눠도 왕복은 조금만 늘어납니다. 연결이 끊기면 어디까지 실행됐는지 모르고, Lettuce가 응답 못 받은 명령을 다시 보내므로, 같은 값을 다시 쓰는 `SET`은 대체로 괜찮지만(그사이 더 새 값이 쓰였다면 덮어씀) `INCR`류는 처리 기록이 필요합니다. 클러스터에서는 Lettuce가 다중 키 명령과 파이프라인을 슬롯별 노드로 나눠 보내므로, 한 노드에서 주던 원자성이 사라집니다.

### 예상 질문과 꼬리 질문

**Q. 반복문 100번을 `executePipelined`로 바꿨는데 오히려 느려졌습니다. 왜 그럴 수 있습니까?**

연결 풀이 없으면 `executePipelined`는 호출마다 전용 연결을 새로 맺고 닫습니다. 연결을 맺고 준비하는 데 왕복이 몇 번 들기 때문에, 아낀 왕복보다 더 쓸 수 있습니다. 예시처럼 같은 종류의 읽기라면 공유 연결로 나가는 `multiGet`이 먼저이고, 파이프라인이 꼭 필요하면 풀을 켭니다("파이프라이닝: executePipelined").

- **꼬리 Q. 풀을 켜면 공짜입니까?** 아닙니다. 풀의 최대 연결 수와 빌리는 대기 시간이 새 병목이 되고, Redis 쪽 연결 수가 늘어납니다. 풀의 대가는 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)에 있습니다.

**Q. 파이프라인으로 재고 차감 100건을 보내면 한 번에 처리되니 안전하지 않습니까?**

아닙니다. 파이프라인 안의 명령은 각각 따로 실행되고 그 사이에 다른 연결의 명령이 끼어들 수 있습니다. 또 앞 명령의 결과를 보고 다음 명령을 정할 수 없어서, "재고가 있을 때만 차감"을 표현할 수 없습니다. 끼어들기를 막으려면 `MULTI`/`EXEC`, 판단까지 묶으려면 Lua가 필요합니다("파이프라이닝: 명령 여러 개를 응답을 기다리지 않고 이어 보냅니다").

- **꼬리 Q. `MULTI`/`EXEC`로 감싸면 재고 문제가 해결됩니까?** 끼어들기는 막지만 중간 결과로 분기할 수 없어 "있을 때만 차감"은 여전히 안 됩니다. 판단이 필요한 차감은 Lua로 처리합니다. 재고 차감의 다른 방법은 [Redis 원자성](./atomicity.md)에서 비교합니다.

**Q. 그럼 대량 쓰기는 전부 Lua 하나로 보내면 원자성과 왕복 1번을 다 얻지 않습니까?**

얻는 대신 스크립트가 도는 동안 다른 모든 연결이 기다립니다. 키 10만 개를 도는 스크립트라면 그 시간 동안 주문 API의 짧은 `GET`도 줄을 섭니다. 원자성이 필요한 범위를 작게 잡고, 나머지는 나눈 파이프라이닝으로 보냅니다. 파이프라인은 서버가 묶음 전체가 아니라 한 번에 읽힌 범위씩 실행하므로, 읽기 사이에 다른 연결이 끼어들 기회가 있기 때문입니다("한 덩어리로 실행되는 묶음은 다른 요청을 기다리게 합니다").

- **꼬리 Q. 파이프라인은 정말 다른 요청을 막지 않습니까?** 묶음 전체로는 막지 않지만, 한 번에 읽힌 범위는 연달아 실행하므로 그동안은 막습니다. 그 범위가 얼마나 될지는 보장되지 않습니다. 또 서버가 해야 할 전체 일은 같으므로 CPU를 그만큼 쓰고, 응답이 큰 파이프라인은 응답 버퍼 메모리를 늘립니다. 이 설명은 소스 경로에서 끌어낸 것이므로 실제 영향은 적재 시간대의 다른 API 지연으로 확인합니다. 묶음을 나누면 한 번에 읽힐 수 있는 양의 상한도 함께 작아집니다.

**Q. 파이프라인 묶음 크기는 어떻게 정합니까?**

정해진 값은 없습니다. 묶음을 키우면 왕복 절감은 금방 작아지고, 클라이언트 힙, 실패 범위, 명령 타임아웃 위험, Redis 응답 버퍼가 쌓일 수 있는 상한은 계속 커집니다. 공식 문서는 1만 개를 예로 들지만 응답 크기에 따라 줄여야 하고, 실제 환경에서 묶음 크기별 전체 시간과 `omem`을 재서 정합니다("묶음이 너무 크면 무엇이 문제인가").

- **꼬리 Q. 명령 타임아웃을 늘리면 큰 묶음도 되지 않습니까?** 기다림은 길어지지만, 그동안 요청 스레드를 더 오래 붙잡고, 타임아웃이 나도 서버는 계속 실행하므로 재시도하면 중복이 생깁니다. 타임아웃을 묶음에 맞추기보다 묶음을 타임아웃에 맞춥니다.

**Q. 파이프라인이 `RedisPipelineException`으로 실패했습니다. 예외의 결과 목록으로 실패한 명령만 다시 보내면 됩니까?**

기대하면 안 됩니다. Redis 에러 응답이 있으면 결과 목록이 비어 올 수 있습니다(소스로 추론, 재현 안 함). 또 에러를 받은 명령 말고 나머지는 서버에서 이미 실행됐습니다. 묶음을 통째로 다시 보내도 안전하도록 명령을 멱등하게 만드는 것이 기본입니다("파이프라이닝: executePipelined", "연결이 끊기면 파이프라인의 어디까지 실행됐는지 모릅니다").

- **꼬리 Q. 연결이 끊긴 경우라면 앱이 다시 보내지 않으면 중복이 없지 않습니까?** Lettuce가 기본 설정에서 응답을 받지 못한 명령을 재연결 후 스스로 다시 보냅니다. 앱 코드에 재시도가 없어도 이미 실행된 명령이 다시 실행될 수 있습니다([Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)).
- **꼬리 Q. `MULTI`/`EXEC`로 보내면 이 문제가 사라집니까?** "어디까지 실행됐는가"가 "실행됐는가, 안 됐는가"로 좁혀집니다. 서버는 끊긴 연결의 대기열을 버리기 때문입니다. 하지만 응답을 못 받으면 둘을 구분할 수 없는 것은 같아서, 다시 보내려면 여전히 멱등성이 필요합니다.

**Q. 클러스터로 옮겼더니 `MGET`이 여전히 되는데, 무엇이 달라졌습니까?**

Lettuce가 키를 슬롯별로 나눠 노드마다 `MGET`을 따로 보내고 결과를 합친 것입니다. 에러는 없지만 슬롯 수만큼 명령이 늘고, 결과는 한 시점의 값이 아닙니다. `MSET`이라면 일부 노드만 반영될 수 있습니다. 캐시 읽기라면 받아들일 수 있지만, 함께 맞아야 하는 쓰기라면 해시 태그로 슬롯을 맞추고 Lua로 묶어야 합니다("클러스터에서는 슬롯별로 갈립니다").

- **꼬리 Q. 그럼 상품 캐시 키에 모두 `{product}` 태그를 붙이면 되지 않습니까?** `MGET` 하나로 가는 대신 상품 캐시 전체가 노드 하나에 몰려, 그 노드의 메모리와 메인 스레드가 먼저 한계에 닿습니다. 원자성이 필요 없는 캐시 읽기에는 태그로 모으지 않습니다.

**Q. Lettuce는 원래 공유 연결에서 명령을 이어 보낸다면서요. 그런데 왜 반복문이 느립니까?**

공유 연결이 이어 보내는 것은 **여러 스레드의** 명령입니다. 예시의 요청 스레드 하나는 동기 API인 `get()`이 결과를 돌려줄 때까지 다음 줄로 가지 않으므로, 자기 명령 100개를 차례로 기다립니다. 연결은 막히지 않지만 그 스레드의 지연은 왕복 × 100입니다. 한 요청 안의 명령을 묶어야 그 요청의 왕복이 줄어듭니다("Spring 앱의 명령은 공유 연결 하나로 나갑니다").

# Redis 랭킹: 참가자 수백만 명 중 내 순위를 어떻게 바로 세는가

> **핵심 질문**: 실시간 랭킹에서 상위 N명과 "내 순위"를 Sorted Set으로 구하면, 참가자가 늘어도 왜 싸게 셀 수 있는가? 동점, 점수 갱신의 중복, 기간 마감은 어떻게 정해야 하는가? 키 하나에 모든 참가자를 담는 대가는 무엇인가?
>
> **범위**: 점수를 더해 가는 랭킹(포인트, 판매량 합계)을 Sorted Set 키 하나 또는 몇 개에 두는 경우를 다룹니다. 점수를 모아 두었다가 한꺼번에 DB나 Redis에 쓰는 방식, 검색 엔진이나 분석용 DB로 만드는 랭킹은 다루지 않습니다. Sorted Set의 기본 성질(중복 없음, 점수 순 정렬)은 [Redis 입장 대기열](./waiting-queue.md)의 배경 지식에도 있으며, 이 문서는 랭킹에 필요한 만큼 다시 씁니다.
>
> **출처와 설계의 구분**: 명령의 동작과 복잡도, 설정 기본값은 "근거"에 적은 소스와 공식 문서로 확인했습니다. 점수에 시각을 섞는 방식, 키 이름, 예시의 수치는 공식 문서에 있는 패턴이 아니라 이 문서의 설계이며, 그런 문장에는 그 자리에 "이 문서의 설계"라고 적었습니다. 재현해 보지는 않았습니다.

## 배경 지식

### 이 문서의 예시: 주간 구매 이벤트, 회원 5명

문서 끝까지 다음 장면 하나를 씁니다.

- 쇼핑몰이 일주일짜리 구매 이벤트 1회차를 엽니다. 월요일 00:00:00에 시작해 7일 뒤 같은 시각에 끝납니다.
- 주문이 확정될 때마다 회원은 포인트를 얻습니다. 포인트는 정수입니다.
- 화면에는 **상위 3명**과 **내 순위**를 보여 줍니다. 이벤트가 끝나면 상위 3명에게 쿠폰을 줍니다.
- 첫날 오전에 회원 u1~u5가 다음 순서로 포인트를 얻습니다.

| 시각 | 회원 | 얻은 포인트 | 그 회원의 합계 |
| --- | --- | --- | --- |
| 10:00 | u1 | 300 | 300 |
| 10:05 | u2 | 500 | 500 |
| 10:10 | u3 | 300 | 300 |
| 10:20 | u4 | 200 | 200 |
| 10:30 | u5 | 500 | 500 |

- 점수 갱신을 다루는 곳에서만 두 건을 더합니다. 10:50에 u3이 100포인트를, 11:00에 u1이 100포인트를 더 얻어 둘 다 400이 됩니다.
- 포인트의 원본은 DB의 포인트 적립 기록입니다. Redis의 랭킹 키는 그 기록으로 순위를 빨리 보여 주려고 따로 둔 사본입니다(이 문서의 설계). 원본과 사본을 왜 나누는지는 "원본은 DB에 두고, Redis 랭킹은 다시 만들 수 있는 사본으로 둡니다"에서 다룹니다.

랭킹 키는 `rank:ev1`(이벤트 1회차) 하나입니다. 원소는 회원 ID, 점수는 포인트입니다. 점수에 무엇을 더 담을지는 "동점을 어떻게 가를지는 서비스가 정해야 합니다"에서 다시 정합니다.

```text
 order confirmed            API server                  Redis
+----------------+  event  +-------------+  ZINCRBY   +-------------------+
| DB: point log  |-------->| ranking     |----------->| rank:ev1          |
| (source)       |         | updater     |            |  u1 300  u2 500   |
+----------------+         +-------------+            |  u3 300  u4 200   |
                                                      |  u5 500           |
 browser  -- top 3 / my rank -->  API server --ZRANGE / ZREVRANK-->  rank:ev1
```

위쪽 화살표는 포인트가 생긴 사실이 흘러가는 방향이고, 아래쪽 화살표는 조회 요청이 가는 방향입니다. 포인트 적립 기록이 어떤 경로로 랭킹 갱신까지 오는지(같은 트랜잭션 뒤 바로 호출, 메시지 큐 등)는 그림에서 뺐습니다. 경로마다 생기는 중복과 유실은 "점수 갱신은 재시도하면 두 번 더해집니다"에서 다룹니다.

비용을 계산하는 곳에서만 장면을 키웁니다. 손으로 따라가기에는 5명이면 충분하지만, 순위를 세는 비용은 참가자가 많아야 차이가 보이기 때문입니다. **키운 장면**에서는 참가자가 1,000,000명이고, 최고 시점에 초당 포인트 갱신 2,000건과 순위 조회 5,000건이 옵니다. 키운 장면의 숫자는 모두 가상 예시입니다.

### 이 문서가 기대는 원리들

- **경쟁 상태, 원자성, 멱등성**: 경쟁 상태는 실행 순서에 따라 결과가 틀어지는 문제입니다. 원자성은 여러 단계를 남이 중간에 끼어들 수 없게 묶는 성질이고, 멱등성은 같은 요청을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질입니다. 이 주제에서는 "지금 점수를 읽고 새 점수를 쓰는" 갱신이 다른 갱신과 섞이면 안 되고, 응답을 못 받아 다시 보낸 갱신이 포인트를 두 번 더하면 안 됩니다. 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.
- **Redis의 명령과 Lua 스크립트**: Redis는 명령 하나나 Lua 스크립트 하나를 끝까지 실행하며, 그동안 다른 연결의 명령이 끼어들지 않습니다. 명령 두 개 사이에는 끼어들 수 있습니다. 이 주제에서는 점수를 읽고 계산해 다시 쓰는 갱신을 스크립트 하나로 묶습니다. 동작과 대가는 [Redis 원자성](./atomicity.md)에서 다룹니다.
- **메인 스레드와 해시 슬롯**: Redis 노드 하나는 명령을 메인 스레드라는 실행 흐름 하나에서 차례로 실행하므로, 오래 걸리는 일 하나가 그동안 다른 모든 명령을 기다리게 합니다. 큰 값의 메모리 해제 같은 일부 작업은 명령 실행과 따로 도는 백그라운드 스레드에 넘길 수 있습니다. 클러스터는 데이터를 여러 노드에 나눠 담는 구성이며, 키 이름으로 계산한 해시 슬롯 번호가 그 키가 놓일 노드를 정합니다. 한 명령이나 스크립트가 키 여러 개를 다루려면 모두 같은 슬롯이어야 하고, 키 이름에서 `{` `}` 안의 부분(해시 태그)만 계산에 쓰게 해 슬롯을 맞춥니다. 이 주제에서는 큰 랭킹 키를 지우는 비용과, 랭킹 키와 함께 다루는 키의 이름 짓기에 쓰입니다. 자세한 동작은 [Redis 이벤트 루프](./event-loop.md)와 [Redis Cluster](./cluster.md)에서 다룹니다.
- **왕복과 파이프라이닝**: 왕복은 명령을 보내고 응답을 받기까지 네트워크를 한 번 오가는 일이고, 파이프라이닝은 응답을 기다리지 않고 명령 여러 개를 이어 보내는 방식입니다. 이 주제에서는 랭킹을 DB에서 다시 만들 때 명령 수백만 개를 보내야 하므로 왕복 수가 시간을 정합니다. 원리는 [왕복과 배치](../cs/round-trip-and-batching.md)에서 다룹니다.

### Sorted Set: 점수 순으로 늘어선, 중복 없는 집합

- **한 줄**: 원소마다 숫자 점수가 붙어 있고, 원소들이 중복 없이 점수 순서로 늘어서 있는 Redis 자료형입니다.
- **비유**: 학교 게시판에 붙은 성적순 명단입니다. 한 학생은 명단에 한 번만 오르고, 명단은 늘 점수 순으로 정렬되어 있어서 "1등부터 3등까지"와 "u3은 몇 등인가"를 바로 읽을 수 있습니다. 예시의 `rank:ev1`이 이 명단입니다.
- **실제로는**:
  - 원소는 문자열이고 같은 원소는 하나만 있습니다. `ZINCRBY key 증가량 원소`는 그 원소의 점수에 증가량을 더하고 새 점수를 돌려줍니다. 원소가 없으면 점수 0에서 더한 것처럼 새로 넣습니다. 그래서 회원이 처음 포인트를 얻을 때와 다시 얻을 때 같은 명령을 씁니다.
  - 정렬은 늘 되어 있습니다. 원소를 넣거나 점수를 바꿀 때 그 자리를 찾아 끼워 넣으므로, 읽을 때 따로 정렬하지 않습니다. 정렬 비용을 쓰기 때 나눠 내는 셈입니다.
  - **순위는 0부터 셉니다.** `ZREVRANK`는 점수가 높은 쪽부터 센 순위를, `ZRANK`는 낮은 쪽부터 센 순위를 돌려줍니다. 가장 높은 회원의 `ZREVRANK`는 0입니다. 원소가 없으면 nil입니다. 화면에 보여 줄 "n등"은 이 값에 1을 더한 것입니다. `WITHSCORE`를 붙이면 순위와 점수를 한 번에 돌려줍니다.
  - 순위 구간을 읽는 명령은 `ZRANGE`입니다. `ZRANGE rank:ev1 0 2 REV WITHSCORES`는 높은 쪽부터 순위 0~2, 곧 상위 3명을 점수와 함께 돌려줍니다. `REV`가 없으면 낮은 쪽부터입니다.
  - **비유와 다른 점**: 게시판 명단은 점수가 같은 학생에게 같은 등수를 적어 줄 수 있지만, Sorted Set의 순위에는 동점이 없습니다. 점수가 같은 원소도 정해진 규칙으로 한 줄로 세우고 서로 다른 순위를 줍니다. 그 규칙이 이 문서의 첫 번째 쟁점입니다("동점을 어떻게 가를지는 서비스가 정해야 합니다").
- **이 주제에서는**: 랭킹 화면이 요구하는 세 가지, 곧 "점수 더하기", "상위 N명", "내 순위"가 모두 명령 하나씩입니다.

### 점수는 64비트 부동소수점 수입니다

- **한 줄**: Sorted Set의 점수는 Kotlin의 `Double`과 같은 64비트 부동소수점 수(double)이며, 정수는 -(2^53)부터 2^53까지만 정확하게 담깁니다(공식 문서 zadd, "Range of integer scores that can be expressed precisely"). 2^53은 9,007,199,254,740,992로 약 9천조입니다.
- **비유**: 유효 숫자를 16자리 정도까지만 적을 수 있는 계산기입니다. 9천조보다 작은 정수는 끝자리까지 그대로 적히지만, 그보다 크면 끝자리가 반올림되어 서로 다른 수가 같은 수로 적힐 수 있습니다.
- **실제로는**:
  - double은 수를 "유효 숫자 × 2의 거듭제곱"으로 담습니다. 유효 숫자에 쓰는 자리가 53비트뿐이라, 2^53을 넘으면 모든 정수를 담지 못하고 일부 정수만 정확히 담깁니다. 예를 들어 2^53 + 1은 담기지 않아 2^53과 같은 double이 되지만, 2^53 + 2는 정확히 담깁니다. 그래서 넘었다고 반드시 틀리는 것은 아니지만, 어떤 값이 틀릴지 미리 보장할 수 없습니다.
  - 그 범위 안의 정수끼리 더하고 빼는 결과도 그 범위 안이면 정확합니다. 예시의 포인트처럼 정수만 다루고 합계가 9천조를 넘지 않으면 오차가 생기지 않습니다.
  - 0.1처럼 2진수로 끝나지 않는 소수는 처음부터 근삿값으로 담깁니다. 소수 점수를 여러 번 더하면 오차가 쌓여, 같아야 할 두 점수가 미세하게 달라지거나 그 반대가 될 수 있습니다.
  - Redis의 Lua 스크립트에서도 숫자는 같은 double입니다. 스크립트 안에서 계산해도 이 한계는 그대로입니다.
- **이 주제에서는**: 포인트는 정수로만 다룹니다. 그리고 "동점을 어떻게 가를지는 서비스가 정해야 합니다"에서 점수 하나에 포인트와 시각을 함께 담을 때, 합친 수가 2^53을 넘지 않는지가 그 설계의 전제가 됩니다.

### 복잡도 표기

공식 문서는 명령마다 데이터가 커질 때 작업량이 어떻게 늘어나는지를 O(…)로 적습니다. 이 문서에서 N은 그 Sorted Set의 원소 수, 곧 참가자 수이고, M은 명령이 돌려주거나 지우는 원소 수입니다.

- O(1)은 N과 상관없이 작업량이 일정하다는 뜻이고, O(N)은 N에 비례한다는 뜻입니다.
- O(log N)은 N이 두 배가 될 때 단계가 하나 정도 늘어난다는 뜻입니다. 참가자가 1,000명에서 1,000,000명으로 1,000배가 되면, O(N)의 작업량은 1,000배가 되지만 log₂ N은 약 10에서 약 20으로 두 배가 될 뿐입니다. 이 값은 늘어나는 모양을 보여 주는 수이고, 실제 탐색 단계 수는 아닙니다.
- O(log N + M)은 "자리를 찾는 데 log N, 거기서부터 M개를 읽는 데 M"이라는 뜻입니다. 상위 3명을 읽는 `ZRANGE`는 M이 3입니다.
- 이 표기는 작업량이 늘어나는 모양이지 실제 시간이 아닙니다. 명령 하나가 가벼워도 초당 몇 번 오는지가 서버의 부담을 정하고, 클라이언트가 느끼는 지연에는 네트워크 왕복과 대기가 더해집니다.

### 스킵 리스트: 건너뛴 칸 수를 적어 두면 순위를 세지 않고 더할 수 있습니다

- **한 줄**: 정렬된 연결 리스트에 "멀리 건너뛰는 연결"을 몇 층 더 얹은 자료구조입니다. 연결 리스트는 원소마다 이웃 원소의 주소(Kotlin에서 다른 객체를 가리키는 참조에 해당)를 들고 있어서, 원하는 원소에 가려면 그 연결을 하나씩 따라가야 하는 목록입니다. Kotlin에서 쓰는 `LinkedList`도 원소를 이런 연결로 잇습니다. Redis는 큰 Sorted Set을 이 구조로 담고, 연결마다 건너뛰는 원소 수를 함께 적어 둡니다.
- **비유**: 엘리베이터와 계단이 함께 있는 건물입니다. 30층에 가려면 계단으로 한 층씩 오르지 않고, 급행 엘리베이터로 10층 단위로 오른 뒤 마지막 몇 층만 계단을 씁니다. 급행을 탈 때마다 "이번에 몇 층 올랐는지"를 더하면, 도착했을 때 지금이 몇 층인지 이미 압니다.
- **실제로는**:
  - 맨 아래층은 모든 원소를 점수 순으로 잇는 연결 리스트입니다. 원소마다 층수를 무작위로 정해, 높은 층일수록 원소가 드물게 놓입니다. 위층의 연결은 그래서 여러 원소를 한 번에 건너뜁니다.
  - 원소를 찾을 때는 맨 위층에서 시작해, 다음 원소가 찾는 값보다 작으면 건너가고 크면 한 층 내려갑니다. 층마다 몇 걸음만 가므로 평균 O(log N) 단계에 도착합니다. 층수를 무작위로 정하므로 이 단계 수는 평균이며, 운이 나쁜 배치에서는 더 걸릴 수 있습니다.
  - Redis는 연결마다 그 연결이 건너뛰는 원소 수를 적어 둡니다. 찾아가는 동안 건너간 연결에 적힌 수를 더하면, 도착했을 때 그 원소의 순위가 나옵니다. 앞의 원소를 하나하나 세지 않습니다.
  - 순위를 알려면 그 원소의 점수부터 알아야 합니다. 그래서 큰 Sorted Set은 스킵 리스트 옆에 원소에서 점수를 바로 찾는 해시 테이블(Kotlin의 `HashMap`에 해당)을 함께 둡니다. `ZREVRANK u3`은 해시 테이블에서 u3의 점수를 찾고, 그 점수로 스킵 리스트를 내려가며 순위를 더합니다.
  - **비유와 다른 점**: 건물의 급행 엘리베이터는 정해진 층에 서지만, 스킵 리스트의 위층 연결은 무작위로 정해집니다. 그리고 원소가 들어오고 나갈 때마다 그 앞뒤 연결의 "건너뛴 수"를 고쳐야 하므로, 쓰기마다 이 갱신 비용이 붙습니다.

```text
 conceptual skip list of rank:ev1 (ascending score; numbers on links = elements skipped)

 level 2:  head --------------3--------------> u3 ----------------2----------------> nil
 level 1:  head ------2------> u1 -----1-----> u3 -------1------> u2 ------1-----> u5
 level 0:  head --1--> u4 --1--> u1 --1--> u3 --1--> u2 --1--> u5
                      200      300      300      500      500
```

그림은 개념도입니다. 층수 배정은 설명을 위해 임의로 정했고, 실제 층수는 무작위입니다. 화살표는 "다음 원소의 주소를 가리킨다"는 주소 참조이고, 화살표 위의 숫자는 그 연결이 건너뛰는 원소 수입니다. 해시 테이블, 뒤로 가는 연결, 맨 끝의 nil 연결 일부는 그림에서 뺐습니다. 원소가 점수가 낮은 쪽부터 놓인 것은 Redis가 내부에서 오름차순으로 담기 때문이며, 높은 쪽부터 0부터 센 순위는 "전체 원소 수 − 낮은 쪽부터 0부터 센 순위 − 1"로 계산합니다. 같은 300점인 u1과 u3, 같은 500점인 u2와 u5가 이 순서로 놓인 이유는 "아무것도 정하지 않으면 회원 ID의 바이트 순서가 정합니다"에서 다룹니다.

u3의 순위를 세어 봅니다. 2층에서 head → u3 연결 하나로 3칸을 건너면 u3에 도착합니다. 낮은 쪽부터 1부터 센 순위가 3이므로, 0부터 센 `ZRANK`는 2이고, 높은 쪽부터 센 `ZREVRANK`는 5 − 3 = 2입니다. 앞의 u4와 u1을 하나씩 세지 않았습니다.

- **이 주제에서는**: 참가자가 1,000,000명이어도 "내 순위"는 앞의 999,999명을 하나씩 세지 않고 O(log N) 규모의 작업으로 나옵니다. 이것이 랭킹을 Sorted Set에 두는 가장 큰 이유입니다.

### 작을 때는 한 덩어리(listpack)에 담고 앞에서부터 훑습니다

원소가 적은 Sorted Set은 스킵 리스트가 아니라 원소와 점수를 한 덩어리의 메모리에 점수 순으로 이어 적는 listpack이라는 표현으로 담습니다. 원소마다 메모리를 따로 받지 않으므로 메모리를 적게 쓰지만, 순위를 셀 때는 앞에서부터 하나씩 훑습니다. 기준 버전의 기본 설정에서는 원소가 128개를 넘거나(`zset-max-listpack-entries`), 64바이트를 넘는 원소가 하나라도 들어오면(`zset-max-listpack-value`) 스킵 리스트와 해시 테이블로 바뀝니다.

**예시의 `rank:ev1`은 원소가 5개라 실제로는 listpack입니다.** 위의 스킵 리스트 그림은 참가자가 128명을 넘었을 때의 모습을 같은 5명으로 그린 개념도입니다. 원소가 128개 이하일 때는 훑는 길이에 상한이 있으므로, 공식 복잡도의 O(log N)과 경로가 달라도 실무에서는 문제가 되지 않습니다. 한 덩어리와 원소마다 따로 할당하는 방식의 메모리 차이는 [메모리 할당](../cs/memory-allocation.md)에서 다룹니다.

## DB의 ORDER BY 대신 Sorted Set을 쓰면 무엇이 달라지는가

같은 랭킹을 DB 테이블 하나(회원 ID, 포인트 합계)와 포인트 합계 인덱스로 만들 수도 있습니다. 두 방식은 "상위 N명"에서는 비슷하고 "내 순위"에서 갈립니다. 아래 DB 쪽 설명은 흔한 B-tree 인덱스를 가정한 이 문서의 추론이며, 특정 DB로 재지 않았습니다. DB 제품과 실행 계획에 따라 다르므로 실제 판단은 그 DB의 실행 계획으로 확인합니다.

| 하고 싶은 일 | DB(합계 컬럼 + 인덱스) | Sorted Set |
| --- | --- | --- |
| 포인트 더하기 | 합계 행 UPDATE와 인덱스 갱신. 같은 회원의 행에 쓰기가 몰리면 행 잠금 대기 | `ZINCRBY`, O(log N) |
| 상위 3명 | 인덱스를 높은 쪽부터 3개 읽음. 싸다 | `ZRANGE ... 0 2 REV`, O(log N + 3) |
| u3의 순위 | "u3보다 합계가 높은 행의 수"를 셈. 인덱스가 구간의 행 수를 적어 두지 않으면 앞에 있는 사람 수만큼 읽음 | `ZREVRANK`, O(log N) |
| 페이지 넘기기(1001~1010등) | `OFFSET 1000`은 앞의 1,000행을 읽고 버림 | `ZRANGE ... 1000 1009 REV`, O(log N + 10) |
| 새로 생기는 것 | 없음. 원본과 같은 곳 | 사본 하나, 원본과 맞추는 일, Redis 메모리 |

키운 장면에서 순위가 50만 등 근처인 회원이 "내 순위"를 물으면, DB는 그 앞의 약 50만 행을 읽어 세야 할 수 있습니다. 조회가 초당 5,000건이면 이 비용이 그대로 곱해집니다. Sorted Set은 같은 질문에 O(log N), 곧 log₂ N이 약 20인 규모의 작업을 씁니다. 대가는 원본(DB)과 따로 사는 사본을 하나 더 관리하는 일입니다. 순위 조회가 드물거나 상위 N명만 보여 주면 된다면, DB 인덱스만으로 충분할 수 있습니다.

## 동점을 어떻게 가를지는 서비스가 정해야 합니다

### 아무것도 정하지 않으면 회원 ID의 바이트 순서가 정합니다

예시의 다섯 건을 포인트 그대로 `ZINCRBY`로 넣고 높은 쪽부터 전체를 읽으면 다음과 같습니다. 상위 3명은 이 중 앞의 세 줄입니다.

```text
ZRANGE rank:ev1 0 -1 REV WITHSCORES
1) u5  500
2) u2  500
3) u3  300
4) u1  300
5) u4  200
```

점수가 같은 원소는 원소 문자열을 바이트 단위로 비교한 순서로 놓입니다(공식 문서 zadd, "Elements with the same score"). 낮은 쪽부터 셀 때는 바이트 순서가 작은 쪽이 앞이고, `REV`로 높은 쪽부터 셀 때는 그 순서가 뒤집혀 바이트 순서가 큰 쪽이 앞입니다(공식 문서 zrange). 그래서 같은 500점인데 "u5"가 "u2"보다 앞이고, 같은 300점인데 "u3"이 "u1"보다 앞입니다. `ZREVRANK`도 같은 순서를 씁니다.

결과는 상위 3명이 u5, u2, u3입니다. u1은 10:00에 u3보다 10분 먼저 300점을 만들었지만 4등이 되어 쿠폰을 받지 못합니다. 순서를 정한 것은 회원 ID 문자열이지 서비스의 규칙이 아닙니다. 회원 ID가 숫자라면 바이트 비교에서는 "u10"이 "u9"보다 작다는 점도 함께 기억해야 합니다. 문자를 앞에서부터 하나씩 비교하므로 '1'과 '9'에서 이미 갈립니다.

규칙은 대개 둘 중 하나입니다. 어느 쪽이 맞는지는 기술이 아니라 이벤트 약관이 정합니다.

### 규칙 1: 같은 점수는 같은 등수(공동 순위)

점수는 포인트 그대로 두고, 등수를 "나보다 점수가 높은 사람 수 + 1"로 계산합니다. 예시에서는 u2와 u5가 공동 1등, u1과 u3이 공동 3등, u4가 5등입니다.

- **내 순위**: 내 점수를 `ZSCORE`로 읽고, 그보다 높은 점수의 원소 수를 `ZCOUNT rank:ev1 (300 +inf`로 셉니다. `(`는 경곗값을 빼라는 뜻이라 300점은 세지 않고, 결과 2에 1을 더해 u3은 3등입니다. `ZCOUNT`의 공식 복잡도는 O(log N)입니다. 큰 Sorted Set에서는 순위 정보를 써서 범위의 양 끝만 찾기 때문입니다(공식 문서 zcount). 예시처럼 원소가 적은 listpack에서는 범위 안의 원소를 차례로 세지만, 원소 수에 상한이 있어 문제가 되지 않습니다.
- **대가 1, 두 번의 왕복**: 점수를 읽고 세는 사이에 다른 갱신이 끼어들 수 있습니다. 화면 표시용이라면 순간의 어긋남은 대개 받아들일 수 있고, 맞아야 한다면 두 명령을 스크립트 하나로 묶습니다.
- **대가 2, 경계의 동점**: "상위 3명에게 쿠폰"이면 3등이 두 명이라 받는 사람이 4명이 됩니다. 상위 N명을 화면에 보여 줄 때도 N번째와 같은 점수인 사람을 몇 명까지 보여 줄지 정해야 합니다. 이 결정이 없으면 화면과 지급 대상이 달라집니다.
- **화면의 줄 순서**: 같은 등수 안에서 누구를 먼저 그릴지는 여전히 회원 ID 순서입니다. 같은 등수로 표시한다면 줄 순서는 의미가 없다고 안내할 수 있습니다.

### 규칙 2: 같은 점수면 먼저 도달한 사람이 앞(점수에 시각을 섞기)

점수 하나에 "포인트"와 "그 포인트에 도달한 시각"을 함께 담습니다(이 문서의 설계). 포인트를 앞자리에, 시각을 뒷자리에 두되 이른 시각일수록 큰 값이 되게 뒤집어 넣습니다.

```text
score = points × 1,000,000 + (999,999 − t)
t     = seconds since the event started (0 .. 604,799 for 7 days)
```

- 이벤트 기간 7일은 604,800초라 6자리에 들어갑니다. 그래서 시각에 뒷자리 6자리를 줬습니다.
- 앞자리가 포인트이므로 포인트가 다르면 포인트로 순서가 갈립니다. 포인트가 같으면 뒷자리가 큰 쪽, 곧 t가 작아 더 일찍 도달한 쪽이 앞입니다.
- **2^53 확인**: 점수의 최댓값은 대략 포인트 × 1,000,000입니다. 2^53이 약 9.0 × 10^15이므로 포인트 합계가 약 90억을 넘지 않으면 정확합니다. 시각 단위를 밀리초로 바꾸면 뒷자리가 9자리가 되어 포인트 상한이 약 900만으로 줄어듭니다. 상한을 넘으면 서로 다른 점수가 같은 double이 될 수 있어, 동점이 아닌데 동점이 되거나 순서가 바뀔 수 있습니다.

예시의 다섯 건을 이 식으로 넣으면(10:00은 시작 후 36,000초) 다음과 같습니다.

| 회원 | 포인트 | 도달 시각 | t | 점수 |
| --- | --- | --- | --- | --- |
| u2 | 500 | 10:05 | 36,300 | 500,963,699 |
| u5 | 500 | 10:30 | 37,800 | 500,962,199 |
| u1 | 300 | 10:00 | 36,000 | 300,963,999 |
| u3 | 300 | 10:10 | 36,600 | 300,963,399 |
| u4 | 200 | 10:20 | 37,200 | 200,962,799 |

이제 `ZRANGE rank:ev1 0 2 REV`는 u2, u5, u1을 돌려주고, 쿠폰은 먼저 300점을 만든 u1이 받습니다. 예시에서는 점수가 모두 다르므로 회원 ID 순서가 끼어들지 않습니다. 다만 포인트가 같고 같은 초에 도달한 두 회원은 점수도 같아져 다시 회원 ID 바이트 순서로 갈립니다. 같은 초의 동점까지 가려야 한다면 시각 단위를 줄이되 2^53 상한을 다시 계산하고, 그래도 남는 동점을 어떻게 볼지 약관에 정해 둡니다. 화면에 보여 줄 포인트는 점수를 1,000,000으로 나눈 몫입니다.

대가는 셋입니다.

- **갱신이 `ZINCRBY` 하나로 끝나지 않습니다.** 다음 절에서 다룹니다.
- **점수만 보고는 사람이 읽기 어렵습니다.** `redis-cli`로 볼 때도, 다른 서비스가 같은 키를 읽을 때도 이 식을 알아야 합니다. 식은 코드 한 곳에 두고, 식을 바꾸면 키를 새로 만들어야 합니다.
- **기간과 포인트 상한이 식에 묶입니다.** 이벤트를 연장하거나 포인트 규모가 커지면 자리 수를 다시 계산해야 합니다.

| | 그대로 두기 | 규칙 1: 공동 순위 | 규칙 2: 시각 섞기 |
| --- | --- | --- | --- |
| 동점의 순서 | 회원 ID 바이트 순서 | 같은 등수 | 먼저 도달한 사람 |
| 점수 갱신 | `ZINCRBY` | `ZINCRBY` | 스크립트(읽고 계산해 쓰기) |
| 내 순위 | `ZREVRANK` 한 번 | `ZSCORE` + `ZCOUNT` | `ZREVRANK` 한 번 |
| 경계 처리 | 의도하지 않은 탈락 | 상위 N에 N명 넘게 들어올 수 있음 | 늘 정확히 N명 |
| 맞는 경우 | 동점이 상관없는 표시용 | 약관이 공동 순위를 인정 | 약관이 "먼저 달성한 순" |

## 점수 갱신: 시각을 섞으면 읽고 계산해 다시 써야 합니다

### `ZINCRBY`로 더하면 도달 시각이 처음 값에 머뭅니다

규칙 2에서 10:50에 u3이 100포인트, 11:00에 u1이 100포인트를 더 얻었다고 합시다. 두 사람 모두 400점이고, 먼저 400점을 만든 사람은 u3입니다.

포인트만큼 `ZINCRBY rank:ev1 100000000 u3`처럼 앞자리만 더하면 뒷자리의 시각은 처음 값 그대로 남습니다.

| 회원 | `ZINCRBY`로 더한 점수 | 뒷자리가 뜻하는 시각 | 맞는 점수 |
| --- | --- | --- | --- |
| u3 | 400,963,399 | 10:10 | 400,960,999 (10:50) |
| u1 | 400,963,999 | 10:00 | 400,960,399 (11:00) |

`ZINCRBY`만 쓰면 u1이 앞서지만, 규칙대로라면 u3이 앞서야 합니다. 뒷자리가 "지금 포인트에 도달한 시각"이 아니라 "처음 포인트를 얻은 시각"으로 남았기 때문입니다.

### 스크립트 하나로 읽고, 계산하고, 다시 씁니다

갱신을 Lua 스크립트 하나로 만듭니다(이 문서의 설계).

1. `ZSCORE`로 지금 점수를 읽고, 1,000,000으로 나눈 몫으로 지금 포인트를 구합니다. 없으면 0입니다.
2. 더할 포인트를 더해 새 포인트를 구합니다.
3. 새 포인트와 이번 적립의 시각 t로 새 점수를 계산해 `ZADD`로 덮어씁니다.

읽기와 쓰기 사이에 같은 회원의 다른 갱신이 끼어들면 한쪽의 포인트가 사라지므로, 세 단계는 반드시 한 스크립트 안에 둡니다. 스크립트가 도는 동안 다른 명령은 기다리지만, 이 스크립트는 명령 두 개와 계산 몇 번이라 짧습니다.

시각 t는 API 서버의 현재 시각이 아니라 **포인트 적립 기록에 적힌 시각**을 씁니다. 서버마다 시계가 조금씩 다르고, 같은 기록으로 랭킹을 다시 만들 때 같은 점수가 나와야 하기 때문입니다. 적립 이벤트가 늦게 도착해 순서가 뒤바뀔 수 있다면, 저장된 시각과 새 시각 중 늦은 쪽을 쓰도록 스크립트에서 고릅니다.

포인트를 차감하는 경우(주문 취소)는 "도달 시각"의 의미가 애매해집니다. 차감 후의 포인트에 처음 도달했던 시각으로 되돌릴지, 차감 시각으로 둘지는 약관이 정할 일이고, 앞의 경우라면 적립 이력을 보지 않고는 계산할 수 없습니다. 차감이 잦은 랭킹이라면 규칙 1이 단순합니다.

### 점수 갱신은 재시도하면 두 번 더해집니다

`ZINCRBY`도 위의 스크립트도 "더하기"입니다. 같은 적립을 두 번 실행하면 두 번 더해집니다. 그런데 갱신을 보낸 쪽은 응답을 받지 못했을 때 그 갱신이 실행됐는지 알 수 없습니다. 타임아웃 뒤 다시 보내면 실행된 갱신이 한 번 더 실행될 수 있고, 메시지 큐에서 같은 메시지를 다시 받는 경우도 같습니다.

- **적립 기록마다 처리 표시를 남깁니다.** 같은 스크립트 안에서 적립 기록 ID로 처리 표시 키를 `SET NX`로 만들고, 이미 있으면 더하지 않습니다. 표시 키의 TTL(키가 사라질 때까지 남은 시간)은 재시도가 올 수 있는 기간보다 길게 둡니다. 표시 키가 먼저 사라진 뒤 같은 적립이 다시 오면 다시 더해지기 때문입니다. 키가 하나 더 생기고, 클러스터에서는 한 스크립트가 함께 다루므로 랭킹 키와 같은 슬롯에 두어야 합니다. 이 방식의 일반적인 설계와 대가는 [멱등성 키](./idempotency-key.md)에서 다룹니다.
- **합계를 덮어씁니다.** 더하는 대신 DB에서 읽은 그 회원의 포인트 합계로 점수를 계산해 `ZADD`로 덮어씁니다. 같은 합계를 몇 번 써도 결과가 같으므로 멱등합니다. 대가는 갱신마다 DB 합계를 읽어야 하고, 두 갱신이 엇갈려 도착하면 오래된 합계가 새 합계를 덮을 수 있다는 점입니다. 포인트가 늘기만 한다면 `ZADD`의 `GT`(새 점수가 더 클 때만 바꿈)로 이 역전을 막을 수 있지만, 차감이 있으면 쓸 수 없습니다.

어느 쪽이든, 사본은 언젠가 원본과 어긋날 수 있다고 보고 맞추는 수단을 따로 둡니다. 다음 절이 그 이야기입니다.

## 원본은 DB에 두고, Redis 랭킹은 다시 만들 수 있는 사본으로 둡니다

랭킹 키가 사라지거나 틀어지는 경우는 여럿입니다. 재시작 시 영속성 설정에 따라 마지막 몇 초의 쓰기를 잃을 수 있고, 장애 조치로 복제본이 주 서버가 되면 아직 복제되지 않은 쓰기를 잃을 수 있습니다. 메모리 한도와 축출 정책에 따라 키가 지워질 수도 있습니다. 각각의 조건은 [Redis 영속성](./persistence.md), [Redis 복제](./replication.md), [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.

그래서 이 문서의 설계는 다음과 같습니다.

- **포인트의 원본은 DB의 적립 기록입니다.** Redis 랭킹은 그 기록에서 언제든 다시 계산할 수 있는 사본입니다.
- **쿠폰 지급처럼 돈이 걸린 판정은 DB로 합니다.** 이벤트가 끝난 뒤 적립 기록을 같은 동점 규칙으로 집계해 상위 3명을 정합니다. Redis 랭킹은 화면 표시용이고, 지급 직전에 DB 결과와 Redis의 상위 N명이 같은지 비교하면 사본이 틀어진 것을 알 수 있습니다.
- **다시 만들 때는 새 키에 만든 뒤 바꿔 끼웁니다.** 예를 들어 `rank:ev1:rebuild`에 적립 기록을 회원별로 집계한 점수를 `ZADD`로 채우고, 다 채운 뒤 `RENAME`으로 `rank:ev1` 자리에 옮깁니다. 클러스터에서는 `RENAME`의 두 키도 같은 슬롯이어야 하므로, 처음부터 `rank:{ev1}`과 `rank:{ev1}:rebuild`처럼 해시 태그로 이름을 맞춰 둡니다. 채우는 동안 화면은 기존 키를 그대로 읽습니다. 참가자 1,000,000명이면 원소 1,000,000개를 넣어야 하므로, 명령 하나에 원소 여러 개를 넣고 파이프라이닝으로 왕복 수를 줄입니다.
- **다시 만드는 동안 들어온 적립은 각각 한 번만 반영되게 합니다(이 문서의 설계).** 갱신이 더하기라서, 어떤 적립이 집계에 이미 들어갔는지 정하지 않으면 새 키에서 두 번 더해지거나 빠집니다. 그래서 세 가지를 지킵니다. 첫째, 집계의 경계는 "이 시점까지 커밋된 기록"처럼 DB가 보장하는 기준으로 정합니다. 적립 ID의 최댓값은 경계가 되지 못합니다. ID가 작은 기록이 더 늦게 커밋될 수 있기 때문입니다. 둘째, 경계 안의 기록이 늦게 도착하면 새 키에는 더하지 않고, 경계 밖의 기록은 경계 안의 집계를 새 키에 다 채운 뒤에만 더하고, 이번 재구축에만 쓰는 처리 표시를 점수 갱신과 같은 스크립트 안에서 확인해 한 번만 더합니다. 채우기의 `ZADD`는 점수를 덮어쓰므로, 그보다 먼저 더한 몫은 지워지고 처리 표시만 남아 다시 더해지지도 않기 때문입니다. 기존 키의 표시를 함께 쓰면 이미 남은 표시 때문에 새 키에 더하지 못하고, 재구축마다 표시 이름을 바꾸지 않으면 다음 재구축이 이전 표시에 막힙니다. 셋째, 바꿔 끼우는 동안에는 Redis에 갱신을 적용하는 일을 잠시 멈추고, 바꿔 끼운 뒤의 갱신도 새 키에 이미 더한 기록을 알아보게 합니다. 멈춘 동안의 적립을 어디에 쌓아 두었다가 다시 적용할지는 적립 기록이 랭킹 갱신까지 오는 경로(메시지 큐 등)마다 다르므로, 정확한 전환 절차는 그 환경에서 정합니다.
- **`RENAME`의 숨은 비용**: `RENAME`이 덮어쓰는 기존 `rank:ev1`은 그 자리에서 지워집니다. 기본 설정(`lazyfree-lazy-server-del no`)에서는 메인 스레드가 원소 1,000,000개의 메모리를 그 자리에서 해제하므로, 그동안 다른 명령이 기다립니다. 먼저 기존 키를 `UNLINK`로 떼어 낸 뒤 옮기면 해제를 백그라운드로 넘길 수 있지만, 그 사이 잠깐 키가 없는 순간이 생깁니다. 큰 키를 지우는 비용은 [Hot Key와 Big Key](./hot-key-big-key.md)에서 다룹니다.

## 기간 랭킹: 키를 기간마다 나누고, 끝난 키는 조심해서 지웁니다

### 기간마다 키를 따로 둡니다

일간, 주간처럼 기간이 정해진 랭킹은 기간마다 키를 따로 둡니다(이 문서의 설계). 이벤트 1회차는 `rank:ev1`, 2회차는 `rank:ev2`입니다. 한 키의 점수를 기간이 끝날 때 0으로 되돌리는 방식은 참가자 수만큼 원소를 바꿔야 하고, 되돌리는 동안 화면에 지난 기간과 새 기간의 점수가 섞입니다.

일간 랭킹과 주간 랭킹을 함께 보여 준다면 두 가지 방법이 있습니다.

| 방법 | 동작 | 비용 |
| --- | --- | --- |
| 쓸 때 둘 다 갱신 | 적립 하나마다 일간 키와 주간 키를 한 스크립트에서 함께 갱신 | 쓰기가 두 배(각 O(log N)). 클러스터에서는 두 키를 같은 슬롯에 두어야 함 |
| 주간을 나중에 합산 | 일간 키 7개를 `ZUNIONSTORE`로 더해 주간 키를 만듦 | O(N) + O(M log M)(N은 입력 키들의 원소 수 합, M은 결과의 원소 수). 참가자가 많으면 메인 스레드를 오래 잡음. 점수가 포인트만일 때만 쓸 수 있음 |

키운 장면처럼 참가자가 1,000,000명이면 `ZUNIONSTORE`는 원소 수백만 개를 한 번에 처리하는 명령이 되고, 그동안 다른 모든 명령이 기다립니다. 실시간 주간 랭킹이 필요하면 쓸 때 둘 다 갱신하는 쪽이 부하가 고르게 퍼집니다. 그리고 `ZUNIONSTORE`는 점수를 그대로 더하므로, 규칙 2처럼 시각을 섞은 점수에는 쓸 수 없습니다. 뒷자리의 시각끼리 더해져 포인트 자리로 올라가고, 더한 시각은 도달 시각이 아니기 때문입니다. 규칙 2의 주간 랭킹은 적립마다 주간 점수를 따로 계산해 갱신합니다.

### 마감 시각의 적립은 적립 시각으로 판정합니다

이벤트가 끝나는 순간에도 적립 이벤트는 계속 도착합니다. 마감 직전에 확정된 주문의 적립이 마감 뒤에 도착할 수 있고, 마감 뒤에 확정된 주문의 적립이 들어올 수도 있습니다. 랭킹 갱신은 도착 시각이 아니라 적립 기록에 적힌 시각으로 이 이벤트 기간에 속하는지를 판정합니다. 쿠폰 지급을 DB 집계로 정하는 것도 이 경계를 한 곳에서 정하기 위해서입니다.

### 끝난 키를 지우는 비용

끝난 기간의 키는 조회 기간이 지나면 지웁니다. `EXPIRE`로 만료를 걸어 두면 따로 지울 필요가 없지만, 만료로 지울 때도 큰 키의 해제 비용은 그대로입니다. 기준 버전의 기본 설정(`lazyfree-lazy-expire no`)에서는 만료된 키를 메인 스레드가 그 자리에서 해제합니다. 참가자가 많은 랭킹 키라면 만료 시각 전에 `UNLINK`로 지우거나, 서버 설정으로 만료 삭제를 백그라운드에 넘길지 검토합니다.

## 참가자와 요청이 늘면 무엇이 달라지는가

키운 장면(참가자 1,000,000명, 초당 갱신 2,000건, 순위 조회 5,000건)으로 봅니다.

- **명령 하나의 작업량은 거의 늘지 않습니다.** `ZINCRBY`, `ZREVRANK`, 상위 N명의 `ZRANGE`는 모두 O(log N)이거나 O(log N + M)입니다. 참가자가 1,000배로 늘어도 log₂ N은 두 배 정도로만 늡니다.
- **메모리는 참가자 수에 비례해 늡니다.** 128명을 넘은 랭킹은 원소마다 스킵 리스트 노드, 해시 테이블 항목, 회원 ID 문자열을 따로 할당합니다. 원소 하나에 몇 바이트가 드는지는 회원 ID 길이, 메모리 할당기, 빌드에 따라 다르므로, 추정해야 합니다. `MEMORY USAGE`는 키 하나 전체의 크기를 돌려주므로, 128명을 넘는 표본 키(예: 10,000명)를 실제 회원 ID 형식으로 만들어 잰 값을 그 원소 수로 나누고, 그 원소당 크기에 목표 참가자 수를 곱합니다. 이 문서는 재지 않았습니다.
- **큰 범위를 한 번에 읽는 명령이 비쌉니다.** `ZRANGE rank:ev1 0 -1`처럼 전체를 읽으면 M이 1,000,000입니다. 공식 문서도 결과가 수만 개 이상인 `ZRANGE`를 조심하라고 적습니다(공식 문서 sorted-sets, "Performance"). 화면에는 페이지 단위로, 집계는 DB에서 합니다.
- **모든 요청이 키 하나, 곧 노드 하나에 몰립니다.** 키 하나는 Redis 노드 하나에만 있습니다. 초당 7,000건이 모두 같은 노드의 메인 스레드에서 차례로 실행됩니다. 명령 하나가 가벼워 노드 하나로 감당되는 경우가 많지만, 감당하지 못하면 노드를 늘려도 이 키의 부하는 나뉘지 않습니다. 이 성질은 [Hot Key와 Big Key](./hot-key-big-key.md)에서 다룹니다.

### 한 노드로 부족할 때의 선택지

| 선택 | 줄어드는 것 | 대가 |
| --- | --- | --- |
| 순위 조회를 복제본에서 읽기 | 주 서버의 읽기 부하 | 복제 지연만큼 순위가 늦게 보임. 쓰기 부하는 그대로 |
| 상위 N명 결과를 앱에서 짧게 캐시 | 같은 상위 N명 조회의 반복 | 캐시 기간만큼 늦게 보임. "내 순위"는 회원마다 달라 캐시 효과가 작음 |
| 상위 K명만 남기기(`ZREMRANGEBYRANK`로 아래쪽을 잘라 냄) | 메모리와 N | K등 밖의 회원은 "내 순위"를 알 수 없음. 잘린 회원에게 다음 `ZINCRBY`(또는 규칙 2 스크립트)가 오면 점수 0에서 다시 더해져 이전 합계가 에러 없이 사라지므로, 갱신을 DB 합계 덮어쓰기로 바꿔야 함 |
| 랭킹 키를 여러 개로 나누기(회원 ID 해시로 K개) | 노드 하나에 몰리는 쓰기 | 아래 설명 |

랭킹 키를 K개로 나누면 갱신은 그 회원이 속한 키 하나에만 갑니다. 대신 읽기가 비싸집니다.

- **상위 N명**: 각 키에서 상위 N명을 읽어 앱에서 다시 정렬하고 N명을 고릅니다. 키 K개를 읽어야 합니다.
- **내 순위**: 각 키에서 내 점수보다 높은 원소 수를 `ZCOUNT`로 세어 더하고 1을 더합니다. 이 역시 K개 키를 읽습니다. 규칙 1이면 이 값이 공동 순위의 등수입니다. 규칙 2에서도 나와 점수가 같은 사람(같은 포인트를 같은 초에 만든 사람)이 없을 때만 키 하나일 때의 `ZREVRANK` + 1과 같습니다.
- 여러 키를 읽는 동안 다른 키에 갱신이 들어오므로, 읽은 결과는 한 시점의 순위가 아닙니다.

키를 나누면 조회마다 읽을 키가 K개로 늘고, 앱에서 결과를 합치는 코드가 생깁니다. 실제 비용이 몇 배가 되는지는 키별 원소 수, 병렬로 읽는지, 합치는 비용에 따라 다릅니다. 키 하나로 시작해, 그 노드의 CPU가 실제로 한계에 닿는 것을 지표로 확인한 뒤에 나눕니다.

## Spring에서 랭킹 키를 다룰 때

- **명령과 메서드**: Spring Data Redis의 `ZSetOperations`에서 `ZINCRBY`는 `incrementScore`, 높은 쪽부터 구간 읽기는 `reverseRangeWithScores`, `ZREVRANK`는 `reverseRank`, `ZSCORE`는 `score`, `ZCOUNT`는 `count`입니다. 기준으로 확인한 버전의 `ZSetOperations`에는 순위와 점수를 한 번에 받는 `WITHSCORE` 메서드가 없으므로, 둘을 함께 맞게 받아야 하면 스크립트로 묶습니다.
- **원소 직렬화**: 원소는 회원 ID 문자열 그대로 저장해야 합니다. `RedisTemplate`의 기본 직렬화기인 Java 직렬화로 원소를 쓰면 회원 ID 앞에 직렬화 머리 바이트가 붙습니다. `redis-cli`에서는 회원 ID가 아니라 이스케이프된 바이트로 보이고, 다른 서비스가 평문 회원 ID로 `ZSCORE`나 `ZREVRANK`를 보내면 같은 원소로 찾지 못합니다. 같은 직렬화 바이트를 보내야만 찾을 수 있습니다. 동점의 바이트 순서도 이 바이트로 정해집니다. 원소와 키에는 `StringRedisSerializer`를 쓰는 `StringRedisTemplate`이 맞습니다. 직렬화기의 차이는 [직렬화기 고르기](./serializer.md)에서 다룹니다.
- **점수의 타입**: 점수는 `Double`로 오갑니다. 규칙 2의 점수는 2^53 안의 정수이므로 `Long`으로 바꿔도 값이 그대로이고, 포인트는 그 `Long`을 1,000,000으로 나눈 몫입니다. 포인트를 `Double`로 계산하며 소수를 섞지 않습니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 본문 |
| --- | --- | --- |
| 같은 점수면 먼저 들어온 원소가 앞이다 | 들어온 순서는 남지 않습니다. 점수가 같으면 원소 문자열의 바이트 순서이고, `REV`에서는 그 반대입니다 | 아무것도 정하지 않으면 회원 ID의 바이트 순서가 정합니다 |
| `ZREVRANK`의 결과가 곧 등수다 | 0부터 셉니다. 1등은 0입니다 | Sorted Set: 점수 순으로 늘어선, 중복 없는 집합 |
| 점수는 숫자니까 어떤 정수든 정확하다 | double이라 2^53을 넘으면 일부 정수만 정확히 담기고 나머지는 가까운 값으로 반올림됩니다. 시각을 섞을 때 자리 수 계산이 필요합니다 | 점수는 64비트 부동소수점 수입니다 |
| 내 순위를 구하려면 앞사람을 세야 하니 참가자가 많으면 느리다 | 큰 Sorted Set은 연결마다 건너뛴 수를 적어 두어 O(log N)에 순위를 셉니다 | 스킵 리스트: 건너뛴 칸 수를 적어 두면 순위를 세지 않고 더할 수 있습니다 |
| `ZINCRBY`는 원자적이니 재시도해도 안전하다 | 원자적인 것과 멱등한 것은 다릅니다. 다시 보내면 두 번 더해집니다 | 점수 갱신은 재시도하면 두 번 더해집니다 |
| 만료로 지우면 큰 키도 부담이 없다 | 기본 설정에서는 만료된 키도 메인 스레드가 그 자리에서 해제합니다 | 끝난 키를 지우는 비용 |

## 실무 포인트

### 먼저 정할 것

| 중요도 | 결정 | 이유 |
| --- | --- | --- |
| 필수 | 동점 규칙(공동 순위 / 먼저 도달 / 상관없음) | 정하지 않으면 회원 ID 문자열이 순서를 정하고, 상위 N명의 경계에서 보상 대상이 바뀝니다 |
| 필수 | 원본의 위치와 다시 만드는 방법 | Redis 랭킹은 재시작, 장애 조치, 축출로 틀어질 수 있습니다. 원본 없이 Redis만 두면 되돌릴 방법이 없습니다 |
| 필수 | 재시도 때 중복 적립을 막는 방법 | `ZINCRBY`와 갱신 스크립트는 멱등하지 않습니다. 메시지 큐의 재전달과 타임아웃 재시도에서 두 번 더해집니다 |
| 필수 | 보상 판정을 어디서 할지 | 돈이 걸린 판정은 원본(DB) 집계로 하고, Redis 결과와 비교만 합니다 |
| 알면 유리 | 점수에 시각을 섞을 때의 자리 수 | 포인트 상한 × 배수가 2^53을 넘으면 순서가 틀어질 수 있습니다. 기간이나 시각 단위를 바꿀 때 다시 계산합니다 |
| 알면 유리 | 기간 키의 이름과 삭제 방식 | 끝난 큰 키를 만료나 `RENAME`으로 지우면 기본 설정에서 메인 스레드가 해제 비용을 냅니다 |
| 참고 | `zset-max-listpack-*` 조정 | 참가자가 수백만 명인 랭킹에는 상관없습니다. 작은 Sorted Set이 아주 많을 때만 메모리와 함께 잽니다 |

| 포인트가 DB보다 적다 | 재시작·장애 조치 시각, 축출 지표 | 영속성·복제 지연으로 쓰기 유실, 키 축출 | DB에서 다시 만듦. 커밋 기준으로 정한 경계와 재구축마다 따로 두는 처리 표시로, 다시 만드는 동안의 적립을 경계 안의 집계를 다 채운 뒤 한 번씩만 반영함 |
| 동점이 아닌데 순서가 뒤바뀐다 | 점수 최댓값이 2^53을 넘는가 | 점수 식의 자리 수 초과 | 시각 단위를 줄이거나 자리를 다시 배분하고 키를 다시 만듦 |
| 주기적으로 모든 명령이 잠깐 느려진다 | `SLOWLOG`, 그 시각의 만료·`RENAME`·`ZUNIONSTORE` | 큰 키 해제나 큰 범위 명령이 메인 스레드를 잡음 | `UNLINK`로 지우고, 합산은 쓸 때 나눠서 함 |

## 말로 설명하기

### 30초 버전

랭킹은 Redis Sorted Set 하나에 회원 ID와 포인트를 담아 만듭니다. 큰 Sorted Set은 스킵 리스트로 정렬을 늘 유지하고, 연결마다 건너뛴 원소 수를 적어 두어 "내 순위"를 앞사람을 세지 않고 O(log N)에 구합니다. DB에서 같은 질문은 앞에 있는 행을 세야 할 수 있습니다. 대신 동점 순서는 회원 ID 문자열이 정하므로 서비스가 규칙을 정해야 하고, 갱신은 멱등하지 않아 재시도해도 두 번 더해지지 않게 만들어야 하며, 키 하나라 노드 하나에 부하가 몰립니다. 원본은 DB에 두고 Redis는 다시 만들 수 있는 사본으로 씁니다.

### 2분 버전

랭킹 화면이 묻는 것은 포인트 더하기, 상위 N명, 내 순위 세 가지입니다. Sorted Set은 셋을 모두 명령 하나로 답합니다. 쓰기 때 자리를 찾아 끼워 넣어 정렬을 늘 유지하고, 128명을 넘으면 스킵 리스트와 해시 테이블로 담습니다. 스킵 리스트는 연결마다 건너뛴 원소 수를 적어 두므로, 내려가며 그 수를 더하면 순위가 나옵니다. 참가자가 100만 명이어도 작업량은 log N 규모입니다.

첫 번째 쟁점은 동점입니다. 점수가 같으면 원소 문자열의 바이트 순서로 놓이고, 높은 쪽부터 읽으면 그 역순이라 예시에서는 늦게 300점을 만든 u3이 u1보다 앞섭니다. 공동 순위를 인정하면 `ZCOUNT`로 나보다 높은 사람 수를 세고, 먼저 도달한 사람을 앞에 두려면 점수 뒷자리에 뒤집은 시각을 넣습니다. 점수가 double이라 합친 값이 2^53을 넘지 않는지 확인해야 하고, 시각을 넣으면 `ZINCRBY`로는 도달 시각이 갱신되지 않아 읽고 계산해 쓰는 스크립트가 필요합니다.

두 번째는 정확성입니다. 갱신은 더하기라 재시도하면 두 번 더해지므로 적립 ID로 처리 표시를 남기거나 합계를 덮어씁니다. Redis 사본은 재시작이나 장애 조치로 틀어질 수 있으니 원본은 DB에 두고, 보상 판정은 DB 집계로 합니다. 세 번째는 규모입니다. 명령은 가볍지만 모든 요청이 키 하나, 노드 하나로 가고, 끝난 큰 키를 지우거나 `ZUNIONSTORE`로 합산하면 메인 스레드를 오래 잡습니다. 키를 나누는 것은 지표로 한계를 확인한 뒤에 합니다.

### 예상 질문과 꼬리 질문

**Q. 왜 랭킹을 DB가 아니라 Redis에 두나요?**
"내 순위" 때문입니다. 흔한 B-tree 인덱스는 구간의 행 수를 적어 두지 않으므로, 나보다 점수가 높은 사람 수를 세려면 그만큼 읽어야 할 수 있습니다. Sorted Set은 스킵 리스트의 연결마다 건너뛴 수를 적어 두어 O(log N)에 셉니다. 상위 N명만 보여 주거나 순위 조회가 드물면 DB 인덱스만으로 충분할 수 있고, 그때는 사본을 관리하는 비용이 더 큽니다. DB 쪽은 이 문서의 추론이며 실행 계획으로 확인해야 합니다. (본문: "DB의 ORDER BY 대신 Sorted Set을 쓰면 무엇이 달라지는가")

- **꼬리: 그럼 상위 N명만 필요하면 Redis가 필요 없나요?**
  읽기만 보면 그렇습니다. 다만 갱신이 초당 수천 건 같은 행에 몰려 DB의 행 잠금 대기가 문제라면, 쓰기를 받는 쪽으로 Redis를 둘 이유가 생깁니다. 이때도 적립 기록을 DB에 남기는 쓰기는 그대로이고, 줄어드는 것은 같은 회원의 합계 행을 고치는 UPDATE와 그 인덱스 갱신입니다. 이 경우도 원본을 어디에 둘지 먼저 정해야 합니다.

**Q. O(log N)이면 참가자가 늘어도 문제없다는 뜻인가요?**
명령 하나의 작업량은 거의 늘지 않는다는 뜻입니다. 메모리는 참가자 수에 비례해 늘고, 모든 요청이 키 하나가 있는 노드 하나의 메인 스레드에서 차례로 실행됩니다. 전체를 읽는 `ZRANGE`, 큰 키 삭제, `ZUNIONSTORE`처럼 N이나 M에 비례하는 일은 그대로 비쌉니다. (본문: "참가자와 요청이 늘면 무엇이 달라지는가")

**Q. 같은 점수면 누가 앞인가요?**
원소 문자열을 바이트 단위로 비교한 순서이고, 높은 쪽부터 읽으면 그 역순입니다. 먼저 들어온 순서는 남지 않습니다. 회원 ID가 숫자를 담은 문자열이면 "u10"이 "u9"보다 작게 비교되는 것처럼 사람이 기대하는 순서와도 다릅니다. 그래서 동점 규칙을 서비스가 정해야 합니다. (본문: "아무것도 정하지 않으면 회원 ID의 바이트 순서가 정합니다")

- **꼬리: 회원 ID를 0으로 채운 고정 길이로 만들면 되지 않나요?**
  바이트 순서가 회원 번호의 숫자 순서와 같아질 뿐입니다. 그것도 높은 쪽부터 읽는 랭킹에서는 동점일 때 번호가 큰 회원이 앞이고, 번호가 가입 순서라는 보장도 없습니다. 어느 경우든 약관의 "먼저 달성한 순"과는 관계가 없습니다. 규칙이 정하는 기준을 점수에 넣어야 합니다.

**Q. 점수에 시각을 섞는 방식의 위험은 무엇인가요?**
세 가지입니다. 첫째, 점수가 double이라 포인트 × 배수가 2^53을 넘으면 서로 다른 점수가 같아지거나 순서가 바뀔 수 있습니다. 예시의 식은 포인트 약 90억까지 안전하지만, 시각을 밀리초로 바꾸면 약 900만으로 줄어듭니다. 둘째, `ZINCRBY`로 앞자리만 더하면 뒷자리의 시각이 처음 값에 머물러 규칙이 깨지므로, 읽고 계산해 쓰는 스크립트가 필요합니다. 셋째, 식을 바꾸면 기존 점수를 모두 다시 계산해야 합니다. (본문: "규칙 2: 같은 점수면 먼저 도달한 사람이 앞(점수에 시각을 섞기)", "점수 갱신: 시각을 섞으면 읽고 계산해 다시 써야 합니다")

- **꼬리: 스크립트 대신 `WATCH`나 두 명령으로 하면 안 되나요?**
  두 명령 사이에 같은 회원의 다른 갱신이 끼어들면 한쪽 포인트가 사라집니다. `WATCH`(지켜보는 키가 그사이 바뀌었으면 이어지는 `MULTI`/`EXEC` 묶음을 실행하지 않는 기능)로 막을 수는 있지만, 실행되지 않으면 처음부터 다시 시도해야 합니다. 그리고 `WATCH`는 원소가 아니라 키를 지켜보므로, 다른 회원의 갱신이라도 같은 랭킹 키에 들어오면 묶음이 실행되지 않습니다. 키운 장면처럼 모든 갱신이 키 하나에 모이면, `WATCH`부터 `EXEC`까지의 사이가 길수록 그 사이에 다른 갱신이 들어와 재시도가 되풀이되기 쉽습니다. 이 갱신은 명령 두 개짜리라 스크립트가 짧고 단순합니다.
- **꼬리: 시각은 어디서 가져오나요?**
  적립 기록에 적힌 시각입니다. 서버 시계는 서로 다르고, 같은 기록으로 랭킹을 다시 만들 때 같은 점수가 나와야 하기 때문입니다.

**Q. 공동 순위를 쓰면 무엇이 달라지나요?**
점수는 포인트 그대로 두고, 등수는 `ZCOUNT`로 나보다 높은 점수의 수를 세어 1을 더합니다. 갱신은 `ZINCRBY` 그대로라 단순합니다. 대신 "상위 3명"에 3등이 둘이면 4명이 들어오므로 보상 인원과 화면에 보여 줄 범위를 약관에서 정해야 하고, 점수를 읽고 세는 두 명령 사이의 어긋남을 받아들이거나 스크립트로 묶어야 합니다. (본문: "규칙 1: 같은 점수는 같은 등수(공동 순위)")

**Q. `ZINCRBY`는 원자적인데 왜 재시도가 문제인가요?**
원자적이라는 것은 다른 명령이 중간에 끼어들지 못한다는 뜻이지, 두 번 실행해도 결과가 같다는 뜻이 아닙니다. 응답을 못 받은 클라이언트는 실행 여부를 모르고, 다시 보내면 두 번 더해질 수 있습니다. 적립 ID로 처리 표시를 같은 스크립트에서 남기거나, DB 합계로 덮어쓰는 방식으로 멱등하게 만듭니다. (본문: "점수 갱신은 재시도하면 두 번 더해집니다")

- **꼬리: 합계 덮어쓰기는 왜 항상 쓰지 않나요?**
  갱신마다 DB 합계를 읽어야 하고, 두 갱신이 엇갈려 도착하면 오래된 합계가 새 합계를 덮을 수 있습니다. 포인트가 늘기만 하면 `GT`로 막을 수 있지만, 차감이 있으면 그 방법도 쓸 수 없습니다.

**Q. Redis 랭킹이 틀어지면 어떻게 하나요?**
원본인 DB 적립 기록에서 다시 만듭니다. 새 키에 채우고 `RENAME`으로 바꿔 끼웁니다. 그동안 들어온 적립이 두 번 더해지거나 빠지지 않도록, 집계 경계는 적립 ID의 최댓값이 아니라 커밋된 상태로 정하고, 경계 밖의 적립은 경계 안의 집계를 다 채운 뒤에(채우기의 `ZADD`가 점수를 덮어쓰므로) 재구축마다 따로 두는 처리 표시를 점수 갱신과 같은 스크립트에서 확인해 한 번만 더하며, 바꿔 끼우는 동안에는 갱신 적용을 잠시 멈춥니다. 그리고 덮어쓰는 기존 큰 키가 기본 설정에서 메인 스레드에서 해제된다는 점을 고려합니다. 쿠폰처럼 돈이 걸린 판정은 처음부터 DB 집계로 하고, Redis 결과와 비교만 합니다. (본문: "원본은 DB에 두고, Redis 랭킹은 다시 만들 수 있는 사본으로 둡니다")

- **꼬리: Redis에 AOF를 `always`로 켜면 원본으로 써도 되지 않나요?**
  영속성 설정은 재시작 때의 유실을 줄이지만, 비동기 복제의 장애 조치 유실, 축출, 재시도 중복은 막지 못합니다. 무엇을 잃을 수 있는지는 영속성과 복제 문서의 조건을 따로 봐야 하고, 보상 판정에는 여전히 감사 가능한 원본이 필요합니다.

**Q. 주간 랭킹을 일간 랭킹 7개를 `ZUNIONSTORE`로 합쳐 만들면 안 되나요?**
가능하지만 O(N) + O(M log M)이라 참가자가 많으면 명령 하나가 메인 스레드를 오래 잡고, 그동안 다른 모든 명령이 기다립니다. 클러스터에서는 입력 키와 결과 키가 같은 슬롯이어야 합니다. 실시간 주간 랭킹이 필요하면 적립마다 일간 키와 주간 키를 함께 갱신해 비용을 나눕니다. (본문: "기간마다 키를 따로 둡니다")

**Q. 참가자가 너무 많아 노드 하나로 부족하면요?**
순위 조회는 복제본으로 돌리거나 상위 N명을 앱에서 짧게 캐시할 수 있지만, 쓰기는 그대로입니다. 쓰기까지 나누려면 랭킹 키를 회원 ID 해시로 K개로 나누고, 상위 N명은 각 키의 상위 N명을 모아 다시 정렬하고, 내 순위는 각 키의 `ZCOUNT`를 더합니다. 조회마다 읽을 키가 K개로 늘고 결과가 한 시점의 순위가 아니므로, 노드 CPU가 실제로 한계라는 지표를 본 뒤에 합니다. (본문: "한 노드로 부족할 때의 선택지")

- **꼬리: 나눈 키에서 `ZCOUNT`를 더한 값이 정확한 순위인가요?**
  나보다 높은 원소 수의 합에 1을 더하면 규칙 1의 공동 순위 등수이고, 나와 점수가 같은 사람이 없으면 키 하나일 때의 순위와도 같습니다. 다만 키를 차례로 읽는 동안 다른 키에 갱신이 들어오므로, 한 순간의 순위는 아닙니다.

**Q. 끝난 이벤트의 랭킹 키는 만료로 두면 되지 않나요?**
따로 지울 필요가 없어지는 것은 맞습니다. 다만 기본 설정에서는 만료된 키도 메인 스레드가 그 자리에서 해제하므로, 원소 수백만 개짜리 키라면 그 순간 다른 명령이 기다립니다. 만료 전에 `UNLINK`로 지우거나 만료 삭제를 백그라운드로 넘기는 설정을 검토합니다. (본문: "끝난 키를 지우는 비용")

**Q. Spring에서 주의할 점은요?**
원소는 `StringRedisTemplate`처럼 문자열 직렬화기로 회원 ID를 그대로 저장해야 합니다. 기본 Java 직렬화를 쓰면 원소에 머리 바이트가 붙어 다른 서비스와 `redis-cli`가 같은 원소를 찾지 못하고, 동점 순서도 그 바이트가 정합니다. 점수는 `Double`로 오가므로 시각을 섞은 점수는 `Long`으로 바꿔 포인트를 나눠 얻고, 순위와 점수를 한 번에 받는 메서드는 없으니 필요하면 스크립트로 묶습니다. (본문: "Spring에서 랭킹 키를 다룰 때")

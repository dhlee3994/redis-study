# 프로세스와 스레드: 실제로 일을 하는 단위는 무엇인가

> **핵심 질문**: 프로그램이 실행될 때 실제로 일을 하는 단위는 무엇이며, 그 단위들은 메모리와 CPU를 어떻게 나누어 쓰는가? "단일 스레드로 처리한다"는 말은 무엇을 약속하고, 그 대가는 무엇인가?
>
> **범위**: 운영체제에 공통인 일반 원리를 다룹니다. 특정 운영체제의 스케줄러 구현과 메모리 가시성(한 스레드가 쓴 값이 다른 스레드에 언제 보이는가)은 다루지 않습니다. 프로세스 복제(fork)는 [fork와 copy-on-write](./fork-and-copy-on-write.md)에서 다룹니다.

## 배경 지식

### 이 문서의 예시

문서 끝까지 다음 장면 하나를 씁니다.

- 컴퓨터 한 대에 **CPU 코어가 2개** 있습니다.
- 그 위에서 **주문 API 서버(JVM)**와 **Redis 서버**가 실행 중입니다.
- 주문 API에는 사용자 요청 A와 B가 동시에 들어와, 요청 스레드 A와 B가 각각 처리합니다.

```text
컴퓨터 (CPU 코어 2개, 메모리)
│
├─ 프로세스: 주문 API (JVM)
│   ├─ 메모리 공간: 코드, 힙(객체들)  ← 스레드 A와 B가 함께 씀
│   ├─ 스레드 A (요청 A 처리) ── 자기 스택
│   └─ 스레드 B (요청 B 처리) ── 자기 스택
│
└─ 프로세스: Redis 서버
    ├─ 메모리 공간: 코드, 키와 값
    └─ 메인 스레드 (명령 실행)
```

이 그림은 포함 관계를 보여 줄 뿐 크기나 실제 메모리 배치를 나타내지 않습니다. 실제 JVM에는 GC 스레드, JIT 컴파일러 스레드, Tomcat이 연결을 받는 스레드 등이 더 있고, Redis에도 메인 스레드 말고 다른 스레드가 있습니다. 여기서는 "요청을 처리하는 흐름"만 보이려고 뺐습니다. 실무에서는 두 서버가 보통 다른 컴퓨터에서 돌지만, 이 문서의 결론(프로세스끼리는 메모리를 공유하지 않는다)은 같습니다.

### 이 문서에 필요한 하드웨어와 운영체제 용어

- **CPU 코어**: 명령어(instruction)를 하나씩 읽어 실행하는 장치입니다. 명령어는 "메모리에서 값 읽기", "두 수 더하기", "메모리에 값 쓰기"처럼 아주 작은 단위입니다. 코어 하나는 한순간에 하나의 실행 흐름만 진행합니다.
  - 단순화: 한 물리 코어가 두 흐름을 섞어 진행하는 기술(SMT, 인텔에서는 하이퍼스레딩)이 있습니다. 운영체제는 이를 코어 두 개로 봅니다. 이 문서에서 "코어"는 운영체제가 보는 논리 코어를 뜻합니다.
- **메모리(RAM)**: 실행 중인 프로그램의 명령어와 데이터가 놓이는 곳입니다. 칸마다 번호(주소)가 있고, 코어는 주소로 값을 읽고 씁니다.
- **운영체제(OS)**: 프로그램을 실행시키고, 메모리를 나눠 주고, 어느 실행 흐름이 언제 코어를 쓸지 정하는 관리자 프로그램입니다.
- **프로그램과 프로세스**: 프로그램은 디스크에 있는 명령어 파일입니다. 프로세스는 그 프로그램이 실행된 하나의 인스턴스입니다. 같은 `redis-server` 프로그램을 두 번 실행하면 프로세스가 두 개 생기고, 둘은 서로 다른 데이터를 가집니다. Kotlin에 빗대면 프로그램은 클래스, 프로세스는 그 클래스로 만든 객체에 가깝습니다. 다만 객체끼리는 같은 힙을 쓰지만, 프로세스끼리는 메모리가 분리된다는 점이 다릅니다.

## 프로세스는 자기만의 메모리 공간을 가진 실행 단위입니다

- **한 줄**: 프로세스는 운영체제가 실행 중인 프로그램에 나눠 준 "자기만의 메모리 공간과 자원"의 묶음입니다.
- **비유**: 칸막이로 나뉜 작업실입니다. 작업실마다 재료 선반(메모리)이 있고, 다른 작업실의 선반에는 손을 뻗을 수 없습니다. 예시에서는 주문 API 작업실과 Redis 작업실이 따로 있습니다.
- **실제로는**: 프로세스마다 주소 번호가 0부터 시작하는 것처럼 보이는 자기 주소 공간(가상 주소 공간)이 있습니다. 운영체제와 CPU가 이 번호를 실제 메모리 위치로 바꿔 줍니다. 그래서 주문 API가 어떤 주소의 값을 읽어도 Redis의 메모리가 보이지 않습니다. 열어 둔 파일과 네트워크 연결(소켓)도 프로세스 단위로 관리합니다. 비유와 다른 점도 있습니다. 운영체제가 허락하면 두 프로세스가 일부 메모리를 일부러 공유할 수 있습니다(공유 메모리). 이 문서의 예시에는 이런 공유가 없습니다.
- **이 주제에서는**: 주문 API는 Redis의 메모리 안에 있는 재고 값을 직접 읽거나 바꿀 수 없습니다. 반드시 Redis에 요청을 보내고, Redis 프로세스가 대신 읽고 바꿉니다. 이 차이는 뒤의 "프로세스끼리는 메모리가 아니라 통신으로 데이터를 주고받습니다"에서 이어집니다.

## 스레드는 프로세스 안에서 메모리를 함께 쓰는 실행 흐름입니다

- **한 줄**: 스레드는 프로세스 안에서 명령어를 차례로 실행해 나가는 흐름 하나입니다. 한 프로세스에 여러 개 있을 수 있습니다.
- **비유**: 한 작업실 안의 작업자입니다. 같은 작업실의 작업자들은 재료 선반(힙)을 함께 씁니다. 각자 개인 메모장(스택)과 "지금 몇 번째 단계를 하고 있는지" 표시를 따로 가집니다. 예시에서 주문 API 작업실에는 작업자 A와 B가, Redis 작업실에는 작업자 한 명(메인 스레드)이 있습니다.
- **실제로는**: 스레드마다 따로 가지는 것은 다음 두 가지입니다.
  - 다음에 실행할 명령어의 위치(프로그램 카운터)와 계산 중인 값(레지스터)
  - 함수 호출 정보와 지역 변수를 담는 스택

  코드, 힙, 열린 파일과 연결은 같은 프로세스의 모든 스레드가 함께 씁니다. 같은 프로세스의 스레드끼리는 같은 객체를 바로 읽고 쓸 수 있으므로 데이터를 넘기는 비용이 거의 없습니다. 반대로 칸막이가 없으니, 두 스레드가 같은 객체를 동시에 바꿀 때 서로를 망칠 수 있습니다.
- **이 주제에서는**: JVM 하나는 프로세스 하나이고, Tomcat은 요청마다 스레드 풀의 스레드를 하나 배정합니다. Spring의 싱글톤 빈은 힙에 하나만 있으므로 요청 스레드 A와 B가 같은 빈의 필드를 함께 봅니다. 반면 메서드 안의 지역 변수는 각 스레드의 스택에 따로 있어 공유되지 않습니다. "싱글톤 빈에 바뀌는 상태를 두지 말라"는 관례가 여기서 나옵니다.

| 구분 | 프로세스 | 스레드 |
| --- | --- | --- |
| 무엇의 단위인가 | 메모리와 자원의 소유 | 실행(명령어를 차례로 진행) |
| 메모리 | 기본적으로 다른 프로세스와 분리 | 같은 프로세스의 스레드와 힙을 공유, 스택은 따로 |
| 데이터 주고받기 | 운영체제를 거친 통신(소켓, 파이프 등) | 같은 객체를 직접 읽고 씀 |
| 하나가 비정상 종료하면 | 다른 프로세스는 보통 영향이 없음 | 공유하는 것이 망가지면 같은 프로세스 전체가 위험해질 수 있음 |
| 예시에서 | 주문 API, Redis | 요청 스레드 A·B, Redis 메인 스레드 |

표의 "비정상 종료" 행은 잘못 읽기 쉽습니다. JVM에서 아무도 처리하지 않은 예외는 그 예외가 난 스레드만 끝냅니다(JLS SE 21 §11.3: "the current thread (the thread that encountered the exception) is terminated"). 요청 스레드 A에서 예외가 나도 스레드 B와 주문 API 프로세스는 계속 돕니다. 프로세스 전체가 위험해지는 것은 스레드들이 함께 쓰는 것이 망가질 때입니다. 공유 객체가 잘못된 상태로 남거나, 힙 메모리가 바닥나거나, 네이티브 코드가 잘못된 메모리 주소에 접근하는 경우가 그렇습니다.

### 스레드는 버리지 않고 다시 씁니다: 스레드 풀

- **한 줄**: 스레드 풀은 일을 마친 스레드를 바로 없애지 않고 두었다가 다음 일에 다시 맡기는 장치입니다. 기본으로 몇 개를 유지하고 어디까지 늘릴지는 설정이 정합니다.
- **비유**: 작업실이 일을 마친 작업자를 내보내지 않고 상주시키는 것입니다. 새 일은 손이 빈 작업자에게 맡기고, 인원은 정해 둔 한도 안에서만 늘립니다. 더 늘리지 않는 상태에서 모두 바쁘면 남은 일은 작업 대기함에 쌓였다가 손이 빈 작업자가 가져갑니다.
- **실제로는**: 운영체제 스레드(JVM에서는 플랫폼 스레드)를 새로 만들 때마다 운영체제가 스택 공간과 관리 정보를 마련해야 하므로, 일마다 만들고 없애면 그 비용이 반복됩니다. 그래서 만든 스레드를 돌려 씁니다. 다만 모든 스레드를 계속 두지는 않습니다. 기본으로 유지할 수를 넘겨 늘린 스레드는 정해진 시간 동안 일이 없으면 정리합니다. Java SE 21 `ThreadPoolExecutor` 문서는 "excess threads will be terminated if they have been idle for more than the keepAliveTime"이라고 씁니다. Tomcat 10.1 Executor는 `maxIdleTime`(기본 60,000밀리초)이 지나면 정리하되, 활성 스레드가 `minSpareThreads` 이하이면 정리하지 않습니다. 스레드를 미리 만들어 두는지, 일이 처음 올 때 만드는지도 구현과 설정마다 다릅니다. 스레드를 더 늘릴 수 없거나 늘리지 않는 상태에서 모두 바쁘면, 남는 일은 대기열에서 차례를 기다립니다. 대기열에 먼저 넣을지 스레드를 먼저 늘릴지도 구현마다 순서가 다릅니다. 비유와 다른 점은, 이 대기열도 결국 그 프로세스 메모리 안의 자료구조라는 것입니다. 프로세스가 죽으면 실행 중이던 일과 대기열의 일이 함께 사라집니다. 스레드 수와 대기열 크기, 대기열이 찼을 때의 처리는 풀을 만드는 쪽의 설정이 정합니다. 이 설명은 플랫폼 스레드 기준입니다. JDK 21의 가상 스레드는 만드는 비용이 작아 풀로 돌려 쓰지 않는 것이 원칙입니다(JEP 444: "virtual threads are not expensive so there is never a need to pool them").
- **이 주제에서는**: Tomcat은 기본 설정에서 요청 스레드를 풀로 둡니다. 비동기가 아닌 요청에는 그 요청이 끝날 때까지 스레드 하나를 배정합니다(Tomcat 10.1 HTTP Connector: "Each incoming, non-asynchronous request requires a thread for the duration of that request"). 예시의 요청 스레드 A와 B도 그 풀의 스레드입니다. 기본 설정과 다른 경우가 둘 있습니다. 비동기 요청은 처리 도중 스레드를 놓을 수 있습니다. `useVirtualThreads`(기본 false)를 켜면 내부 실행기가 가상 스레드를 씁니다. 풀의 스레드가 모두 바쁠 만큼 요청이 몰리면 남는 요청은 기다리므로, 응답 지연에는 처리 시간뿐 아니라 스레드를 기다린 시간도 들어갑니다.

## 코어는 스레드를 번갈아 실행하고, 언제 바뀔지는 스레드가 정하지 않습니다

- **한 줄**: 실행할 스레드가 코어 수보다 많으면, 운영체제가 짧은 시간씩 번갈아 코어를 배정합니다.
- **비유**: 작업대(코어)가 2개뿐인 공방입니다. 작업자가 셋이면 관리자(운영체제 스케줄러)가 정해진 시간마다 작업자를 바꿔 앉힙니다. 일어서는 작업자는 "어디까지 했는지"를 메모해 두고, 다음 차례에 그 자리부터 다시 합니다.
- **실제로는**:
  - 스케줄러는 스레드에 짧은 실행 시간(타임 슬라이스)을 주고, 시간이 다 되거나 더 급한 스레드가 생기면 실행을 멈춥니다(선점). 이때 멈춘 스레드의 레지스터와 프로그램 카운터를 저장하고, 다음 스레드의 것을 불러옵니다. 이를 **문맥 전환(context switch)**이라고 합니다.
  - 문맥 전환에는 비용이 있습니다. 저장과 복원 자체에 시간이 들고, 새로 올라온 스레드가 쓰는 데이터가 CPU 가까운 임시 저장소(CPU 캐시)에 없어 처음에는 느려질 수 있습니다.
  - 스레드가 디스크나 네트워크 응답을 기다리면(블로킹 I/O) 스스로 코어를 내려놓습니다. 기다리는 동안 다른 스레드가 그 코어를 씁니다.
  - 비유와 다른 점이 가장 중요합니다. 선점은 작업자가 "한 단계를 끝낸 뒤"가 아니라 **거의 아무 명령어 사이에서나** 일어납니다. 코드 한 줄이 명령어 여러 개로 바뀌면 그 줄의 중간에서도 멈출 수 있습니다. 언제 멈출지는 스레드 자신이 정하지 못하고, 실행할 때마다 달라질 수 있습니다.
- **이 주제에서는**: 요청 스레드 A가 재고를 읽은 직후 멈추고, 그사이 스레드 B가 같은 재고를 읽는 순서가 얼마든지 생길 수 있습니다. 그런 순서가 결과를 바꾸는 문제는 경쟁 상태입니다. [경쟁 상태와 원자성](./race-condition-and-atomicity.md)에서 다룹니다.

## 동시성과 병렬성은 다릅니다

- **동시성(concurrency)**: 여러 작업이 **진행 중인 상태로 겹쳐** 있는 것입니다. 코어가 하나라도 번갈아 실행하면 동시성이 있습니다.
- **병렬성(parallelism)**: 여러 작업이 **같은 순간에 실제로** 실행되는 것입니다. 코어가 여러 개 있어야 가능합니다.

예시의 코어 2개에서는 스레드 A와 B가 서로 다른 코어에서 같은 순간에 실행될 수도 있습니다(병렬). 둘 다 한 코어에서 번갈아 실행될 수도 있습니다(동시이지만 병렬은 아님). 같은 데이터를 다루는 두 흐름이 겹치기만 하면, 병렬이든 번갈아 실행이든 경쟁 상태는 생길 수 있습니다. 그래서 "코어가 하나면 안전하다"는 생각은 틀립니다.

## 프로세스끼리는 메모리가 아니라 통신으로 데이터를 주고받습니다

프로세스는 서로의 메모리를 볼 수 없으므로, 데이터를 바꾸려면 운영체제를 거쳐 메시지를 보내야 합니다. 서버 프로그램에서는 주로 **소켓**을 씁니다. 소켓은 네트워크 연결의 한쪽 끝을 프로그램이 다룰 수 있게 운영체제가 제공하는 통로입니다. 두 프로세스가 같은 컴퓨터에 있어도, 다른 컴퓨터에 있어도 방식은 같습니다.

예시에서 주문 API가 재고를 줄이는 과정은 다음과 같습니다.

```text
주문 API 스레드 A                  운영체제·네트워크                 Redis 메인 스레드
  "재고 줄여 줘" 메시지 작성
  소켓에 쓰기 ───────────────────▶ 전달 ───────────────────▶ 소켓에서 읽기
  (응답 기다리며 대기)                                             자기 메모리의 재고 값 변경
  소켓에서 읽기 ◀───────────────── 전달 ◀─────────────────── 결과를 소켓에 쓰기
```

화살표는 메시지(바이트)가 이동하는 방향입니다. 실제로 값을 바꾸는 쪽은 언제나 데이터를 가진 Redis 프로세스입니다. 주문 API는 요청을 보내고 결과를 받을 뿐입니다.

이 구조에서 생기는 결과는 다음과 같습니다.

- **요청 하나마다 왕복이 생깁니다.** 요청이 가고 응답이 돌아오기까지의 시간(왕복 시간)이 들고, 그동안 다른 프로세스의 요청이 먼저 처리될 수 있습니다.
- **JVM 안의 동기화 수단은 다른 프로세스에 닿지 않습니다.** Kotlin의 `synchronized`나 `AtomicInteger`는 같은 JVM 프로세스 안의 스레드끼리만 순서를 맞춥니다. 주문 API를 서버 두 대(프로세스 두 개)로 늘리면, 두 프로세스가 공유하는 데이터는 Redis나 DB처럼 두 프로세스 바깥에 있어야 하고, 순서도 그쪽에서 맞춰야 합니다.

## 단일 스레드 처리는 무엇을 약속하고 무엇을 대가로 치르는가

"단일 스레드 서버"는 보통 스레드가 하나뿐이라는 뜻이 아닙니다. **핵심 데이터를 바꾸는 일을 한 스레드가 차례로 맡는다**는 뜻입니다. 예시의 Redis 프로세스에서는 메인 스레드가 이 일을 맡습니다.

### 약속: 핵심 데이터에 대한 작업이 서로 겹치지 않습니다

- 데이터를 바꾸는 실행 흐름이 하나이므로, 두 작업이 같은 데이터를 같은 순간에 고치는 일이 없습니다.
- 그래서 그 데이터를 지키기 위한 락이 필요 없습니다. 락을 잡고 푸는 비용, 락을 기다리는 시간, 서로 상대의 락을 기다리며 멈추는 교착 상태가 생기지 않습니다.
- 한 작업은 시작하면 다음 작업이 시작되기 전에 끝납니다. 예시에서 Redis 메인 스레드가 A의 요청을 처리하는 도중에는 B의 요청을 처리하지 않습니다.

### 대가: 한 흐름의 속도와 길이가 모두에게 영향을 줍니다

- **처리량의 상한**: 그 일은 코어 하나의 속도로만 처리됩니다. 코어가 여러 개 있어도 메인 스레드는 한 번에 한 코어만 씁니다.
- **앞의 작업이 길면 뒤가 모두 기다립니다**: 작업 하나가 오래 걸리면, 그 뒤에 도착한 모든 요청이 그만큼 기다립니다. 줄 맨 앞이 막히면 줄 전체가 막히는 현상(head-of-line blocking)입니다.
- **대기 중에 멈추면 안 됩니다**: 한 스레드가 많은 연결을 맡으려면, 어떤 연결의 응답을 기다리는 동안 멈춰 있으면 안 됩니다. 그래서 이런 서버는 운영체제에 "지금 읽을 데이터가 도착한 연결이 어느 것인가"를 물어, 준비된 연결만 골라 처리하는 방식을 씁니다(I/O 다중화). 이 방식의 원리와 대가는 [I/O 다중화와 이벤트 루프](./io-multiplexing-and-event-loop.md)에서 다룹니다.

### 다른 스레드가 없다는 뜻은 아닙니다

단일 스레드 서버도 네트워크 읽기·쓰기, 파일 정리, 큰 데이터 해제 같은 보조 작업을 다른 스레드에 맡길 수 있습니다. 판단의 기준은 "스레드가 몇 개인가"가 아닙니다. **"핵심 데이터를 바꾸는 실행을 누가 맡는가"**입니다. 특정 서버에서 이 경계가 어디인지는 그 서버의 문서와 소스로 확인해야 합니다.

| `synchronized`로 막았으니 서버를 늘려도 안전하다 | JVM 안의 동기화는 같은 프로세스 안에서만 통합니다. 서버를 늘리면 프로세스가 늘어납니다. |

| 단일 스레드라서 느리다 | 각 작업이 짧으면 락과 문맥 전환 비용이 없어 유리할 수 있습니다. 불리해지는 것은 긴 작업이 섞이거나 한 코어의 처리량을 넘을 때입니다. |

## 실무 포인트

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | 공유 상태가 어느 프로세스에 있는지 확인 | 같은 JVM 안이면 JVM 동기화로 막을 수 있지만, 서버를 여러 대 띄우면 공유 저장소의 원자적 연산이 필요합니다. |
| 필수 | 싱글톤 빈에 바뀌는 상태를 두지 않기 | 요청 스레드들이 같은 객체를 함께 보므로, 필드 하나가 경쟁 상태의 원인이 됩니다. |
| 필수 | 단일 스레드 서버에 긴 작업을 보내지 않기 | 그 작업 하나가 같은 서버를 쓰는 모든 요청의 지연이 됩니다. |
| 알면 유리 | CPU 사용률을 코어 단위로 읽기 | 한 스레드는 최대 코어 하나만큼만 씁니다. 코어가 8개인 서버의 전체 사용률이 낮아도, 단일 스레드 서버의 그 스레드는 한계에 닿았을 수 있습니다. 도구마다 프로세스 사용률을 표시하는 기준이 다르므로 기준을 먼저 확인합니다. |
| 알면 유리 | 스레드 수를 늘리는 효과의 한계 | 스레드가 코어보다 훨씬 많으면 문맥 전환이 늘어납니다. 대기(I/O)가 많은 작업은 스레드를 늘려 이득을 보지만, 계산이 대부분인 작업은 코어 수 이상에서 이득이 줄어듭니다. |

**증상과 확인 순서의 예**: "다른 서버는 한가한데 단일 스레드 서버의 응답만 느리다."

1. 그 서버의 실행 스레드가 코어 하나를 거의 다 쓰는지 봅니다. 프로세스 전체 사용률이 아니라 스레드 단위로 봐야 합니다.
2. 오래 걸린 작업이 있었는지 봅니다. 서버가 제공하는 느린 작업 기록이 있으면 그것을 씁니다.
3. 요청 수 자체가 한 코어의 처리량을 넘는지 봅니다.

2번이 원인이면 작업을 쪼개거나 다른 곳으로 옮깁니다. 3번이 원인이면 데이터를 여러 서버로 나누는 쪽을 검토합니다. 나누면 서버를 넘나드는 작업은 한 서버 안에서처럼 순서를 보장받지 못한다는 대가가 생깁니다.

## 말로 설명하기

### 30초 버전

프로세스는 운영체제가 실행 중인 프로그램에 나눠 준 자기만의 메모리 공간이고, 스레드는 그 안에서 명령어를 차례로 실행하는 흐름입니다. 같은 프로세스의 스레드는 힙을 공유하므로 같은 객체를 바로 바꿀 수 있지만, 그래서 서로를 망칠 수도 있습니다. 다른 프로세스와는 메모리를 공유하지 않으므로 소켓 같은 통신으로만 데이터를 주고받습니다. 단일 스레드 서버는 핵심 데이터를 한 흐름이 차례로 처리하므로 락 없이 작업이 겹치지 않게 하는 대신, 긴 작업 하나가 모두를 기다리게 하고 처리량이 코어 하나에 묶입니다.

### 2분 버전

CPU 코어는 명령어를 하나씩 실행하고, 운영체제는 실행할 흐름이 코어보다 많으면 짧게 번갈아 배정합니다. 이때 실행 흐름이 스레드이고, 스레드들이 속한 메모리와 자원의 묶음이 프로세스입니다.

같은 프로세스의 스레드는 힙을 공유합니다. 그래서 Tomcat의 요청 스레드들은 같은 싱글톤 빈을 함께 봅니다. 운영체제는 거의 아무 명령어 사이에서나 스레드를 멈추고 다른 스레드를 실행할 수 있습니다. 그래서 한 스레드가 값을 읽고 쓰는 사이에 다른 스레드가 끼어들 수 있습니다. 코어가 하나여도 마찬가지입니다. 번갈아 실행되는 것만으로 흐름이 겹치기 때문입니다.

프로세스끼리는 메모리가 분리되어 있어, 주문 API는 Redis 메모리의 값을 직접 바꾸지 못하고 요청을 보냅니다. 요청마다 왕복이 생기고, 그사이 다른 프로세스의 요청이 먼저 처리될 수 있습니다. 또 JVM의 `synchronized`는 다른 JVM에 닿지 않으므로, 서버를 여러 대로 늘리면 공유 데이터의 순서를 바깥 저장소에서 맞춰야 합니다.

"단일 스레드 서버"는 핵심 데이터를 바꾸는 실행을 한 흐름이 맡는다는 뜻입니다. 작업이 겹치지 않아 락이 필요 없다는 장점이 있습니다. 대신 작업 하나가 길면 뒤의 모든 요청이 기다리고, 그 일의 처리량은 코어 하나의 속도를 넘지 못합니다. 보조 스레드는 있을 수 있으므로, 어디까지가 한 흐름인지는 서버별로 확인해야 합니다.

### 예상 질문과 꼬리 질문

**Q. 프로세스와 스레드의 차이는 무엇인가요?**
프로세스는 메모리와 자원을 소유하는 단위이고, 스레드는 실행하는 단위입니다. 같은 프로세스의 스레드는 힙을 공유하고 스택과 실행 위치만 따로 가집니다. 그래서 스레드끼리는 데이터를 넘기는 비용이 작습니다. 대신 같은 데이터를 함께 바꾸면 경쟁 상태가 생기고, 한 스레드가 공유하는 메모리를 망가뜨리면 프로세스 전체가 위험해질 수 있습니다. 다만 JVM에서 처리되지 않은 예외는 그 스레드만 끝내므로, 예외 하나가 곧 프로세스 종료는 아닙니다. (본문: "스레드는 프로세스 안에서 메모리를 함께 쓰는 실행 흐름입니다")

- **꼬리: 그럼 항상 스레드가 프로세스보다 좋은가요?**
  아닙니다. 공유가 쉬운 만큼 격리가 약합니다. 한 쪽의 장애나 메모리 오염이 다른 쪽에 번지면 안 되는 작업은 프로세스로 나누는 것이 안전합니다. 이때 데이터는 통신으로 주고받아야 하므로 비용이 듭니다.

**Q. Spring 싱글톤 빈에 필드를 두면 왜 위험한가요?**
빈 객체는 힙에 하나만 있고, 요청마다 다른 스레드가 같은 객체를 씁니다. 필드를 읽고 고치는 사이에 다른 요청 스레드가 끼어들 수 있으므로 결과가 실행 순서에 따라 달라집니다. 지역 변수는 스레드마다 스택에 따로 있으므로 이 문제가 없습니다.

**Q. 코어가 1개인 서버에서도 동시성 문제가 생기나요?**
생깁니다. 운영체제가 스레드를 번갈아 실행하면서 거의 아무 명령어 사이에서나 바꿀 수 있기 때문입니다. 병렬로 실행되지 않아도 두 흐름이 겹쳐 진행되면 충분합니다. (본문: "동시성과 병렬성은 다릅니다")

**Q. 문맥 전환은 왜 비용인가요?**
멈추는 스레드의 레지스터와 실행 위치를 저장하고 다음 스레드의 것을 불러오는 작업이 필요합니다. 새로 올라온 스레드가 쓸 데이터가 CPU 캐시에 없어 처음에는 메모리에서 다시 가져와야 할 수도 있습니다. 스레드가 코어보다 훨씬 많으면 이 비용이 커집니다. 정확한 크기는 CPU와 운영체제, 작업 성격에 따라 달라 여기서 수치로 말하지 않습니다.

**Q. 서버를 두 대로 늘렸더니 `synchronized`로 막아 둔 중복 처리가 다시 생겼습니다. 왜인가요?**
서버 두 대는 JVM 프로세스 두 개입니다. `synchronized`는 한 프로세스 안의 스레드끼리만 순서를 맞추므로 다른 프로세스의 스레드를 막지 못합니다. 두 프로세스가 함께 쓰는 데이터는 DB나 Redis 같은 바깥 저장소에 있고, 그 저장소가 제공하는 원자적 연산이나 락으로 순서를 맞춰야 합니다. (본문: "프로세스끼리는 메모리가 아니라 통신으로 데이터를 주고받습니다")

**Q. 단일 스레드 서버의 장점과 단점은 무엇인가요?**
장점은 핵심 데이터를 한 흐름만 바꾸므로 작업이 겹치지 않고, 락과 교착 상태, 그 데이터를 둘러싼 문맥 전환 비용이 없다는 것입니다. 단점은 처리량이 코어 하나에 묶이고, 작업 하나가 길면 뒤의 모든 요청이 기다린다는 것입니다. 그래서 각 작업을 짧게 유지하는 것이 사용하는 쪽의 책임이 됩니다.

- **꼬리: 단일 스레드 서버가 연결 수천 개를 어떻게 처리하나요?**
  한 연결의 데이터를 기다리며 멈추지 않고, 운영체제에 "지금 데이터가 준비된 연결"을 물어 그 연결만 처리하는 방식(I/O 다중화)을 씁니다. 각 작업이 짧으면 많은 연결을 번갈아 처리할 수 있습니다.
- **꼬리: 그럼 스레드가 정말 하나뿐인가요?**
  보통은 아닙니다. 네트워크 입출력이나 정리 작업을 맡는 보조 스레드가 있을 수 있습니다. 중요한 것은 핵심 데이터를 바꾸는 실행을 누가 맡는가입니다.

**Q. 단일 스레드 서버의 CPU 사용률은 어떻게 해석해야 하나요?**
한 스레드는 최대 코어 하나만큼만 쓸 수 있습니다. 코어가 8개인 서버라면 그 스레드가 한계에 닿아도 전체 사용률은 낮게 보일 수 있습니다. 그래서 프로세스나 스레드 단위로, 코어 하나를 기준으로 봐야 합니다. 도구마다 표시 기준이 다르므로 기준을 먼저 확인합니다.

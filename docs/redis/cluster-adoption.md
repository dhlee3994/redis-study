# 클러스터 도입 판단: 주 서버 한 대의 어떤 한계를 넘었을 때 클러스터로 가는가

> **핵심 질문**: 주 서버 한 대(+ 복제본) 구성의 Redis를 언제 Redis Cluster로 옮겨야 하는가? 클러스터가 실제로 풀어 주는 한계는 무엇이고, 풀어 주지 못하는 문제는 무엇인가? 옮기면 애플리케이션은 무엇을 치르며, 그 전에 더 싼 방법은 무엇이고 언제 바닥나는가?
>
> **범위**: 도입 여부를 판단하는 기준, 한계에 닿았는지 재는 지표, 클러스터 전에 시도할 대안, 옮길 때의 비용 목록을 다룹니다. 슬롯·해시 태그·리다이렉트·토폴로지 갱신의 동작은 [Redis Cluster](./cluster.md)에 있고, 이 문서는 그 결론만 판단 재료로 씁니다. 장애 조치 때 클라이언트가 겪는 일과 Sentinel의 클라이언트 동작은 다루지 않습니다.

## 배경 지식

### 이 문서의 예시: 주문 서비스 Redis에 울린 경고 세 개

문서 끝까지 다음 장면 하나를 씁니다.

- 주문 서비스(Spring Boot, Lettuce)가 Redis 한 벌을 씁니다. 주 서버 M 한 대, 복제본 R 한 대, 그리고 M이 죽으면 R을 새 주 서버로 올려 주는 Sentinel이 있습니다.
- M이 도는 서버는 메모리 32GB, 네트워크 10Gbps이고, Redis의 메모리 한도 `maxmemory`는 24GB로 두었습니다. 나머지 8GB는 운영체제와, 저장·동기화 때 필요한 여유입니다(아래 "메모리").
- 키는 세 종류입니다.
  - 장바구니 `cart:user:<사용자 ID>`: 사용자마다 Hash 하나, TTL 30일. 메모리의 대부분을 차지합니다.
  - 재고와 구매자 `stock:item:<상품 ID>`, `buyers:item:<상품 ID>`: 주문 때 Lua 스크립트 하나로 "재고가 남았고 아직 안 샀으면 재고를 줄이고 구매자에 넣기"를 실행합니다([Redis 원자성](./atomicity.md)의 예시와 같은 스크립트입니다).
  - 상품 캐시 `product:<상품 ID>`: 상품 상세 화면이 읽습니다.
- 어느 날 경고가 세 개 울렸고, 팀에서 "이제 클러스터로 가야 하지 않나"라는 말이 나왔습니다.
  1. **메모리**: 사용량이 20GB이고, 장바구니가 늘어 한 달에 약 1.5GB씩 늡니다.
  2. **CPU**: 특가 행사 동안 M의 메인 스레드가 시간의 약 95% 동안 쉬지 않고 루프를 돌았고, 메인 스레드의 CPU 시간도 비슷하게 높았습니다. 평소에는 35% 정도입니다.
  3. **네트워크**: 행사 동안 M의 송신량이 초당 약 450,000KB까지 올라갔습니다.

```text
 주문 API 여러 대 (Spring Boot, Lettuce)
        │ 모든 쓰기와 대부분의 읽기
        ▼
 ┌─────────────────────────────┐   복제 흐름   ┌──────────────┐
 │ 주 서버 M (32GB, 10Gbps)     │ ───────────▶ │ 복제본 R      │
 │  cart:user:*   (대부분의 메모리)│              │ (M과 같은 데이터)│
 │  stock:item:*, buyers:item:* │              └──────────────┘
 │  product:*                   │
 └─────────────────────────────┘
        ▲ 감시                       ▲ 감시
        └──────── Sentinel ──────────┘
```

화살표 중 왼쪽 위는 명령이 가는 방향, 가운데는 M이 R에 쓰기를 보내는 복제 흐름, 아래는 Sentinel이 두 서버의 상태를 확인하는 방향입니다. Sentinel이 몇 대인지와 연결 풀은 판단에 영향이 없어 그림에서 뺐습니다.

이 문서의 용량, 증가 속도, 사용률은 판단 과정을 보여 주기 위한 **가상의 숫자**이고, 이 문서에서 잰 값이 아닙니다.

### 주 서버 한 대가 가진 세 가지 자원

경고 세 개는 서로 다른 자원이 바닥나고 있다는 신호입니다. 클러스터가 늘려 주는 것도 이 세 자원이므로 먼저 나눠 둡니다.

| 자원 | 무엇의 한도인가 | 예시의 경고 |
| --- | --- | --- |
| 메모리 | Redis는 모든 데이터를 메모리에 둡니다. 서버 한 대의 메모리가 담을 수 있는 데이터의 상한입니다 | 1번 |
| 메인 스레드 | 명령을 실행하는 스레드는 하나이므로, 코어 하나가 초당 처리할 수 있는 명령 일감이 상한입니다 | 2번 |
| 네트워크 대역폭 | 서버의 네트워크가 초당 주고받을 수 있는 바이트의 상한입니다 | 3번 |

**메인 스레드**: Redis 서버 프로세스 안에서 키를 읽고 바꾸는 명령은 메인 스레드 하나가 하나씩 끝까지 실행합니다. 스레드 하나는 한 순간에 코어(CPU 안에서 명령어를 실제로 실행하는 단위) 하나에서만 돌기 때문에, 서버에 코어가 16개 있어도 명령 실행에 쓰이는 것은 코어 하나만큼입니다. 이 주제에서는 "서버의 CPU 사용률"이 아니라 "메인 스레드 하나가 얼마나 쉬지 않고 일하는가"를 봐야 한다는 뜻입니다. 서버 전체 CPU가 10%여도 메인 스레드는 100%일 수 있습니다. 스레드의 원리는 [프로세스와 스레드](../cs/process-and-thread.md)에, 메인 스레드가 한 바퀴에 하는 일은 [Redis 이벤트 루프](./event-loop.md)에 있습니다.

**네트워크 대역폭**:

- **한 줄**: 서버가 초당 보낼 수 있는 데이터의 양입니다. 보통 초당 비트(bps)로 적고, 8비트가 1바이트입니다.
- **비유**: 고속도로의 차선 수입니다. 차(응답)를 아무리 빨리 만들어도 차선이 가득 차면 톨게이트 앞에 줄을 섭니다.
- **실제로는**: 서버의 네트워크 카드, 그 앞의 네트워크 장비, 클라우드라면 인스턴스 종류가 상한을 정합니다. 상한에 가까워지면 응답이 보내기 버퍼에 쌓이고 클라이언트가 본 지연이 늘어납니다. 메인 스레드가 한가해도 생기는 일입니다. 주 서버는 클라이언트 응답만이 아니라 복제본에 보내는 복제 흐름도 같은 네트워크로 보냅니다.
- **이 주제에서는**: 예시의 3번 경고는 M 한 대의 네트워크 카드에 대한 경고입니다. 공식 벤치마크 문서는 실제 환경에서 Redis 처리량이 CPU보다 네트워크에서 먼저 막히는 경우가 많다고 적습니다(공식 문서 benchmarks, "Factors impacting Redis performance").

### 복제, Sentinel, 클러스터는 각각 무엇을 늘리는가

"클러스터로 가자"는 말이 나올 때 가장 흔한 혼동은, 세 가지가 늘려 주는 것을 섞는 것입니다.

| 구성 | 한 줄 정의 | 늘려 주는 것 | 늘려 주지 않는 것 |
| --- | --- | --- | --- |
| 복제 | 주 서버가 받은 쓰기를 복제본에 흘려보내 같은 데이터를 유지합니다 | 데이터 사본, 읽기를 나눌 곳 | 메모리(복제본도 전체를 가짐), 쓰기 처리량(모든 쓰기는 주 서버가 받음) |
| Sentinel | 주 서버와 복제본을 감시하다가 주 서버가 죽으면 복제본을 새 주 서버로 올립니다 | 자동 장애 조치 | 메모리, 처리량 |
| 클러스터 | 키를 슬롯 단위로 여러 주 서버에 나눠 담고(샤딩), 주 서버마다 복제본을 둡니다 | 메모리와 쓰기 처리량(주 서버 수만큼), 자동 장애 조치 | 키 하나·태그 하나에 몰린 부하 |

공식 문서도 Sentinel을 "클러스터를 쓰지 않을 때의 고가용성"으로 소개하고(공식 문서 sentinel 첫 문단), 복제를 읽기 확장과 데이터 안전·가용성에 쓴다고 적습니다(공식 문서 replication, "Important facts about Redis replication"). 클러스터만이 주는 것은 **데이터와 쓰기를 여러 주 서버로 나누는 것**입니다(공식 문서 scaling, "Redis Cluster 101"). 그래서 이 문서의 판단은 결국 "내 문제가 나누기로만 풀리는가"로 모입니다.

표의 두 용어를 짧게 정의해 둡니다. **슬롯**은 클러스터가 키를 나누는 칸으로, 키 이름만으로 그중 하나가 정해지고 칸마다 맡는 주 서버가 있습니다. 그래서 키 하나는 늘 주 서버 하나에만 있습니다. **해시 태그**는 키 이름에 `{…}`를 넣어 중괄호 안의 문자열만으로 슬롯을 정하게 하는 규칙으로, 함께 다뤄야 하는 키들을 같은 슬롯, 곧 같은 주 서버에 두는 유일한 방법입니다. 클러스터는 한 명령이나 한 스크립트가 다른 슬롯의 키를 함께 다루는 것을 거부하기 때문에 필요합니다. 복제의 동작과 한계는 [Redis 복제](./replication.md)에, 샤딩과 슬롯은 [Redis Cluster](./cluster.md)에 있습니다.

### 수직 확장과 수평 확장

- **한 줄**: 수직 확장은 서버 한 대를 더 큰 서버로 바꾸는 것이고, 수평 확장은 서버 대수를 늘려 일을 나누는 것입니다.
- **비유**: 수직 확장은 매장을 더 큰 건물로 옮기는 것이고, 수평 확장은 지점을 여는 것입니다. 지점을 열면 손님이 어느 지점에 가야 하는지 정해야 하고, 지점끼리 재고를 한 번에 맞추기 어렵습니다.
- **실제로는**: 수직 확장은 애플리케이션 코드를 바꾸지 않습니다. 대신 살 수 있는 가장 큰 서버라는 천장이 있고, Redis의 메인 스레드는 코어 수가 아니라 코어 하나의 속도를 따르므로 코어를 늘린 큰 서버가 명령 처리량을 늘려 주지는 않습니다. 수평 확장은 천장을 없애는 대신 비유의 두 문제(어디로 갈지, 여러 곳을 한 번에 맞추기)를 애플리케이션이 떠안습니다.
- **이 주제에서는**: Redis Cluster는 수평 확장입니다. 그래서 "더 큰 서버로 풀리는가"를 먼저 묻고, 그 천장이 보일 때 클러스터를 검토하는 순서가 됩니다.

## 클러스터가 푸는 한계: 흩어질 수 있는 부하가 노드 한 대를 넘을 때

클러스터는 키를 슬롯으로, 슬롯을 주 서버에 나눕니다. 공식 문서는 주 서버 N대면 단일 인스턴스 성능의 N배를 기대할 수 있다고 적습니다(공식 문서 cluster-spec, "Performance"). 이 문장에는 숨은 조건이 있습니다. 슬롯은 키 이름만 보고 정해지므로 고르게 나뉘는 것은 **키의 개수**입니다. 키마다 크기와 요청 수가 다르면 메모리와 일감은 고르게 나뉘지 않습니다. 그래서 N배는 "부하가 많은 키에 고르게 퍼져 있고, 노드 사양이 같을 때"의 대략적인 상한으로 읽어야 하며, 이 조건이 이 절의 핵심입니다. 세 자원마다 이 조건이 어떻게 적용되는지 봅니다.

### 메모리: 데이터가 한 대에 들어가지 않을 때

메모리는 클러스터가 가장 직접적으로 푸는 한계입니다. 데이터의 각 키는 주 서버 하나에만 있으므로, 주 서버 3대면 주 서버 한 대가 담는 양은 대략 3분의 1이 됩니다.

다만 "메모리가 찼다"의 기준은 서버 메모리 크기가 아닙니다. 주 서버는 데이터보다 많은 메모리를 씁니다.

- **저장과 동기화 때의 여유**: 백그라운드 RDB 저장(전체 데이터를 한 시점으로 떠서 파일로 남기기), AOF 다시 쓰기(쌓인 쓰기 로그를 현재 데이터 기준으로 새로 쓰기), 복제본 전체 동기화(복제본에 전체 데이터를 처음부터 보내기)는 모두 한 시점의 데이터를 통째로 읽어야 합니다. Redis는 이 일을 자식 프로세스를 만들어(`fork`) 맡기고, 자식이 읽는 동안 부모(메인 스레드)는 계속 쓰기를 받습니다. 둘은 처음에 메모리를 함께 쓰다가, 부모가 바꾸는 부분만 복사합니다(copy-on-write). 그래서 자식이 사는 동안 쓰기가 많을수록 메모리가 더 듭니다. 원리는 [fork와 copy-on-write](../cs/fork-and-copy-on-write.md)에, Redis에서의 영향은 [Redis 영속성](./persistence.md)과 [Redis 복제](./replication.md)에 있습니다. 예시에서 서버 32GB 중 8GB를 남긴 이유입니다.
- **데이터가 클수록 한 대의 일이 길어집니다**: `fork` 호출 자체가 메모리가 클수록 길어지고 그동안 메인 스레드가 멈춥니다. 복제본의 전체 동기화와 재시작 뒤 파일 읽기도 데이터 크기에 비례해 길어집니다([Redis 복제](./replication.md)의 "데이터와 쓰기가 늘면 무엇이 커지는가").

그래서 메모리 한계는 "데이터 + 여유가 살 수 있는 서버에 들어가는가"와 "데이터 크기 때문에 한 대의 `fork`·동기화·재시작 시간이 허용 범위를 넘는가" 두 가지로 판단합니다. 노드마다 데이터가 N분의 1이 되면 이 시간들도 노드마다 줄어드는 방향이라는 것은 이 두 비례 관계에서 끌어낸 이 문서의 추론이며, 재지 않았습니다.

예시의 장바구니는 클러스터에 잘 맞는 데이터입니다. 사용자마다 키가 따로 있고, 두 사용자의 장바구니를 한 번에 다루는 일이 없으므로 해시 태그 없이 슬롯에 고르게 흩어집니다.

한 가지 먼저 확인할 것이 있습니다. **Redis가 캐시라면 메모리가 찬 것이 곧 장애는 아닙니다.** `maxmemory`에 닿았을 때 축출 정책(`maxmemory-policy`)을 켜 두었다면 Redis는 정책이 고른 키(덜 쓰인 키, 무작위 키, 만료가 가까운 키 등)를 지우고 계속 동작합니다. 다만 `volatile-*` 정책은 TTL이 있는 키만 지우므로 그런 키가 없으면 지울 것을 찾지 못하고, 미스가 얼마나 늘지도 데이터와 접근 패턴에 달려 있습니다. 축출 정책이 기본값(`noeviction`)이거나 지울 키를 찾지 못하면, `SET`처럼 메모리를 늘릴 수 있는 명령이 에러로 거부됩니다. `DEL`처럼 메모리를 늘리지 않는 명령은 계속 받습니다(공식 문서 faq, "What happens if Redis runs out of memory?"). 예시의 장바구니처럼 지워지면 안 되는 데이터라면 메모리는 진짜 한계이고, 상품 캐시라면 축출과 적중률의 문제입니다. 축출의 동작은 [TTL과 축출](./ttl-and-eviction.md)에, 적중률로 판단하는 법은 [캐시 효과 측정](./cache-effectiveness.md)에 있습니다.

### 쓰기와 메인 스레드: 흩어진 키들의 일감 합이 코어 하나를 넘을 때

메인 스레드가 쉬지 않고 일한다면 두 경우를 구분해야 합니다.

| 경우 | 메인 스레드를 채운 것 | 클러스터로 풀리는가 |
| --- | --- | --- |
| 흩어진 부하 | 서로 다른 많은 키에 대한 명령의 합 | 풀립니다. 키가 슬롯에 흩어지므로 주 서버마다 일감이 나뉩니다 |
| 몰린 부하 | 소수의 키(또는 함께 다뤄야 해서 같은 태그로 묶을 키)에 대한 명령 | 풀리지 않습니다. 그 키는 어느 한 노드의 메인 스레드에 남습니다 |

쓰기가 많은 경우는 클러스터 말고는 나눌 방법이 거의 없습니다. 복제본은 쓰기를 받지 않고, 주 서버가 보낸 쓰기를 자기 메인 스레드 하나로 다시 적용합니다([Redis 이벤트 루프](./event-loop.md)의 "데이터와 요청이 늘면 무엇이 달라지는가"). 복제본이 하는 일이 주 서버와 똑같지는 않습니다. 예를 들어 Lua 스크립트는 스크립트 자체가 아니라 스크립트가 만든 변경 명령이 전달되므로, 판단에 쓴 읽기는 복제본에서 반복되지 않습니다(공식 문서 eval-intro, "Replicating commands instead of scripts"). 그래서 주 서버가 바쁘다고 복제본이 곧 못 따라간다고 단정하지 않고, 복제 지연과 복제본의 메인 스레드 사용률을 따로 봅니다. 확실한 것은 복제본을 늘려도 쓰기는 나뉘지 않는다는 점입니다.

예시의 2번 경고는 아래 "키 하나, 태그 하나에 몰린 부하"에서 보듯 몰린 부하입니다.

### 네트워크: 여러 키의 응답 합이 노드 한 대의 대역폭을 넘을 때

노드마다 자기 네트워크 카드가 있으므로, 키가 흩어져 있으면 응답 바이트도 노드마다 나뉩니다. 이것도 메인 스레드와 같은 조건이 붙습니다. 응답의 대부분이 키 하나(예: 크고 자주 읽히는 상품 목록 키 하나)에서 나온다면 그 키가 있는 노드의 대역폭만 찹니다([Hot Key와 Big Key](./hot-key-big-key.md)의 "노드를 늘려도 키 하나의 부하는 나뉘지 않습니다").

네트워크는 대안이 많은 자원이기도 합니다. 응답이 대부분 읽기라면 복제본이 각자 네트워크 카드를 갖고 있으므로 읽기를 복제본으로 보내 나눌 수 있고, 앱 로컬 캐시는 바이트가 네트워크를 타지 않게 합니다("클러스터 전에 시도할 것과 그것이 바닥나는 지점").

## 클러스터가 풀지 못하는 것

### 키 하나, 태그 하나에 몰린 부하

예시의 2번 경고를 따라가 봅니다. 행사 동안 M의 명령 통계(`INFO commandstats`의 명령별 누적 실행 시간)를 보면 실행 시간의 대부분이 주문 스크립트이고, 애플리케이션 로그로는 그 주문이 대부분 특가 상품 1, 곧 `stock:item:1`과 `buyers:item:1`에 몰렸습니다. Redis는 키별 요청 수를 세지 않으므로 키를 특정하려면 애플리케이션 쪽 집계가 필요합니다([Hot Key와 Big Key](./hot-key-big-key.md)의 "핫키: Redis는 키별 요청 수를 세지 않습니다").

클러스터로 옮기면 이 두 키는 한 스크립트로 다뤄야 하므로 `stock:{item:1}`, `buyers:{item:1}`처럼 같은 해시 태그를 붙여 같은 슬롯에 두어야 합니다. 그러면 상품 1의 모든 주문은 그 슬롯을 맡은 한 주 서버의 메인 스레드가 처리합니다. 주 서버를 3대로 늘려도 10대로 늘려도 상품 1의 주문 부하는 한 노드에 있습니다([Redis Cluster](./cluster.md)의 "태그 하나는 노드 하나입니다"). 달라지는 것은 그 노드에 함께 있던 **다른** 키들이 다른 노드로 가서 덜 기다리게 된다는 점뿐입니다.

그래서 2번 경고의 대응은 클러스터가 아니라 그 키로 오는 요청을 줄이거나 바꾸는 것입니다. 예를 들어 재고를 미리 토큰으로 나눠 두는 설계([Redis 원자성](./atomicity.md)의 "재고를 '꺼낼 토큰'으로 바꾸기")나, 입장 자체를 줄 세우는 대기열([대기열](./waiting-queue.md))이 후보입니다. 각 대응의 대가는 해당 문서에 있습니다.

### 읽기 확장은 복제본이 이미 줍니다

읽기가 많아 메인 스레드나 네트워크가 찼다면, 복제본에서 읽게 하는 것이 클러스터보다 먼저입니다. 복제본은 각자 메인 스레드와 네트워크 카드를 가지므로 읽기 일감을 나눕니다. Spring Boot에서는 `spring.data.redis.lettuce.read-from`(예: `replica-preferred`)을 두면 Lettuce가 읽기 명령을 복제본으로 보냅니다. 클러스터가 아닌 구성에서 이 값을 두면 Spring Data Redis는 Lettuce의 주 서버·복제본 연결을 씁니다.

대가는 [Redis 복제](./replication.md)의 "복제본에서 읽으면: 늦은 값, 만료, 쓰기 금지"에 있습니다. 방금 쓴 값이 안 보일 수 있으므로, 재고 판단처럼 최신 값이 필요한 읽기는 주 서버에 남깁니다. `read-from`은 그 연결로 가는 일반 읽기 명령 전체에 적용됩니다. Lettuce는 보내는 명령의 이름이 읽기 전용 목록에 있는지로 목적지를 정하고, `EVAL`·`EVALSHA`는 그 목록에 없어 주 서버로 보냅니다(`EVAL_RO`는 읽기로 분류됩니다). 그래서 일부 읽기만 주 서버에 남기려면 연결을 나누거나 그 읽기를 `EVAL`로 실행하는 스크립트 안으로 옮깁니다(아래 "Spring에서 확인할 것"). 또 복제본은 주 서버가 보낸 쓰기도 적용하므로, 쓰기가 많을수록 복제본 하나가 읽기에 쓸 수 있는 시간은 줄어듭니다.

그래서 읽기가 클러스터의 이유가 되는 경우도 있습니다. **최신 값이 필요해 복제본으로 보낼 수 없고 캐시로도 줄일 수 없는 읽기**가 많은 키에 흩어져 주 서버를 채운다면, 그 읽기는 쓰기와 같은 처지이고 클러스터가 키와 함께 나눕니다. 순서의 문제입니다. 늦은 값을 허용하는 읽기는 복제본과 캐시가 먼저입니다.

### 자동 장애 조치는 Sentinel이 이미 줍니다

"주 서버가 죽으면 서비스가 멈춘다"가 걱정이라면 그것은 Sentinel이 푸는 문제입니다. 클러스터도 주 서버마다 복제본을 두고 장애 조치를 하지만, 그것은 클러스터를 도입하는 이유가 아니라 클러스터를 쓰려면 함께 갖춰야 하는 조건입니다. 오히려 클러스터는 장애의 모양을 바꿉니다. 기본 설정(`cluster-require-full-coverage yes`)에서는 주 서버 하나와 그 복제본이 함께 죽어 슬롯 일부를 맡을 노드가 없으면 클러스터 전체가 실패 상태가 됩니다([Redis Cluster](./cluster.md)의 "슬롯 하나가 비면 전체가 멈출 수 있습니다"). 확인 응답한 쓰기를 잃을 수 있다는 점도 같습니다. 주 서버는 복제본이 쓰기를 받았는지 확인하지 않고 클라이언트에 응답하므로(비동기 복제), 복제되기 전에 주 서버가 죽으면 응답한 쓰기가 새 주 서버에 없습니다. 또 네트워크가 갈려 옛 주 서버가 일부 클라이언트와만 닿는 동안(네트워크 분할) 받은 쓰기는, 다른 쪽에서 새 주 서버가 올라오면 버려집니다. 두 위험은 Sentinel 구성(공식 문서 sentinel, "Example 2: basic setup with three boxes")과 클러스터([Redis Cluster](./cluster.md)의 "쓰기 유실: 비동기 복제에 네트워크 분할이 더해집니다")에 모두 있으므로, 클러스터로 옮긴다고 사라지지 않습니다. 달라지는 것은 분할 때 잃을 수 있는 구간의 길이이고, 이것은 설정이 정합니다. 클러스터는 다른 주 서버 다수와 대략 `cluster-node-timeout`만큼 연락이 끊긴 주 서버가 스스로 쓰기를 거부하므로 그 시간 정도로 묶입니다(공식 문서 cluster-spec, "Write safety"). Sentinel 구성의 옛 주 서버는 `min-replicas-to-write`(정해 둔 수의 복제본과 `min-replicas-max-lag`초 안에 연락이 닿지 않으면 쓰기를 거부하게 하는 설정, 기본 0으로 꺼짐)를 두지 않으면 분할이 풀릴 때까지 쓰기를 받습니다(공식 문서 sentinel, 같은 절).

## 한계에 닿았는지 어떻게 재는가

### 자원마다 보는 지표

모두 `INFO`의 필드이며, 대부분 누적값이라 일정 간격으로 두 번 읽어 차이를 시간으로 나눠 봅니다.

| 자원 | 지표 | 읽는 법 |
| --- | --- | --- |
| 메모리 | `used_memory`, `mem_not_counted_for_evict`, `maxmemory`(`INFO memory`) | `used_memory`는 Redis가 할당한 바이트입니다. 한도 판정에서는 복제·AOF 버퍼처럼 `mem_not_counted_for_evict`로 나오는 몫을 뺀 값을 `maxmemory`와 비교하므로, 한도까지의 거리는 그 차이로 봅니다. 증가 속도로 한도에 닿는 날을 예상하되, 증가 속도가 그대로라는 가정이 붙은 예상입니다. `maxmemory`가 0이면 한도가 없다는 뜻이고, 그때는 서버 메모리가 한도입니다 |
| 메모리 | `evicted_keys`(`INFO stats`) | 늘고 있으면 이미 한도에서 축출 중입니다 |
| 메모리 | `latest_fork_usec`(`INFO stats`) | 마지막 `fork`에 걸린 마이크로초. 데이터가 커질수록 늘어나며, 그동안 메인 스레드가 멈춥니다 |
| 메인 스레드 | `eventloop_duration_sum`(`INFO stats`, 마이크로초) | 이벤트 루프가 이벤트 대기에서 깨어나 다시 대기에 들어가기까지 걸린 시간(벽시계 시간)의 누적입니다. 두 번 읽은 차이 ÷ 그 사이의 시간이 메인 스레드가 루프를 붙잡고 있던 비율입니다. CPU 사용률과는 다릅니다(아래 설명) |
| 메인 스레드 | `used_cpu_user_main_thread`, `used_cpu_sys_main_thread`(`INFO cpu`, 초) | 메인 스레드 하나가 쓴 CPU 시간입니다. 두 값의 증가분 합 ÷ 경과 시간이 코어 하나 기준 CPU 사용률이며, "명령 실행에 코어 하나가 모자란가"는 이 값으로 판단합니다. 운영체제가 스레드별 CPU 시간을 제공할 때만 나옵니다(Linux는 제공) |
| 메인 스레드 | `used_cpu_user`, `used_cpu_sys`(`INFO cpu`) | 프로세스 전체(메인 스레드와 다른 스레드의 합)입니다. 메인 스레드 하나의 한계를 보는 데 쓰지 않습니다 |
| 메인 스레드 | `instantaneous_ops_per_sec`, `INFO commandstats` | 초당 명령 수와 명령별 누적 실행 시간. 무엇이 일감을 채웠는지 좁힙니다 |
| 네트워크 | `instantaneous_output_kbps`, `instantaneous_input_kbps`(`INFO stats`) | 이름은 kbps지만 단위는 **초당 KB(1,024바이트)** 입니다. 비트로 바꾸려면 × 1,024 × 8을 합니다 |
| 네트워크 | `instantaneous_output_repl_kbps`, `total_net_repl_output_bytes` | 그중 복제본에 보낸 양입니다. `total_net_output_bytes`에는 복제 흐름이 포함되어 있습니다 |

**루프 점유 비율을 읽는 법**: Redis는 이벤트 루프가 "이벤트를 기다리다 깨어난 순간"부터 "다시 기다리러 들어가기 직전"까지의 시간을 한 바퀴마다 재서 `eventloop_duration_sum`에 더합니다. 빠지는 것은 이벤트를 기다리는 시간뿐이므로, 이 값이 10초 동안 9,500,000마이크로초 늘었다면 메인 스레드는 10초 중 약 9.5초, 곧 약 95% 동안 메인 스레드가 이벤트를 기다리지 않고 루프를 붙잡고 있었습니다(누적값에 더해지는 시점과 두 번 읽은 시점이 정확히 맞지 않으므로 근삿값입니다). 예시의 2번 경고가 이 계산입니다. 단 이 시간은 CPU 시간이 아니라 벽시계 시간이라, 명령 실행 말고도 그 구간 안에서 디스크 쓰기를 기다린 시간(AOF를 켰을 때)이나 운영체제가 스레드를 잠시 쉬게 한 시간도 들어 있습니다. 그래서 이 비율이 높으면 먼저 메인 스레드 CPU 시간(`used_cpu_*_main_thread`)을 함께 보고, CPU 시간도 높으면 명령 일감이, CPU 시간은 낮은데 이 비율만 높으면 디스크나 다른 대기가 원인이라고 좁힙니다. 이 해석은 8.2.10 소스에서 시간을 재는 위치를 보고 판단한 것입니다(근거 절). 여기서 잘못 읽기 쉬운 점은 **100%가 되어야 문제가 아니라는 것**입니다. 메인 스레드는 한 번에 하나만 처리하므로, 일한 비율이 100%에 가까워지기 전부터 요청이 줄을 서서 기다리는 시간이 늘어납니다([Redis 이벤트 루프](./event-loop.md)의 "데이터와 요청이 늘면 무엇이 달라지는가"). 몇 %부터 위험한지는 서비스의 지연 목표에 따라 다르므로, 이 비율과 애플리케이션이 본 Redis 지연을 함께 놓고 정합니다.

**네트워크 단위의 예**: 예시의 3번 경고 450,000KB/s는 450,000 × 1,024 × 8 ≈ 3.7Gbit/s입니다. 10Gbps 네트워크의 약 37%이므로 아직 한계는 아닙니다. 이 비율도 환경에 따라 실제로 쓸 수 있는 상한이 다르므로(클라우드 인스턴스의 대역폭 정책 등), 서버 쪽 네트워크 지표와 함께 봅니다.

### 판정 순서: 무엇이 찼는지, 그다음 어디에 몰렸는지

1. **어느 자원이 찼는가**를 위 지표로 정합니다. 서버 전체 CPU 사용률만 보고 판단하지 않습니다.
2. **그 부하가 흩어져 있는가, 몰려 있는가**를 봅니다. `INFO commandstats`로 명령을, 애플리케이션 집계나 `redis-cli --hotkeys`·`--bigkeys`로 키를 좁힙니다(탐지 도구의 조건은 [Hot Key와 Big Key](./hot-key-big-key.md)의 "어떻게 찾는가"). 소수의 키가 대부분이면 클러스터로 풀리지 않습니다.
3. **읽기인가, 쓰기인가**를 봅니다. 읽기면 복제본과 캐시가 먼저입니다.
4. **증가 추세**를 봅니다. 지금은 괜찮아도 메모리가 "한 달에 1.5GB"처럼 늘면, 한도에 닿는 날보다 옮기는 데 걸리는 시간만큼 먼저 결정해야 합니다(아래 "옮기면 애플리케이션이 치르는 비용").

## 클러스터 전에 시도할 것과 그것이 바닥나는 지점

| 대안 | 푸는 자원 | 대가 | 바닥나는 지점 |
| --- | --- | --- | --- |
| 데이터 줄이기 | 메모리 | 기능 판단이 필요합니다(얼마나 오래 둘지, 무엇을 버릴지) | 줄일 수 있는 것을 다 줄였는데도 남는 데이터가 늘 때 |
| 더 큰 서버 | 메모리, 네트워크, 코어 하나의 속도 | 비용. 데이터가 커질수록 `fork`·전체 동기화·재시작이 길어집니다 | 살 수 있는 가장 큰 서버, 또는 한 대의 `fork`·동기화 시간이 허용 범위를 넘을 때 |
| I/O 스레드 | 메인 스레드 중 소켓 읽기·쓰기 몫 | 코어를 더 씁니다. 바꾸려면 재시작이 필요합니다 | 메인 스레드를 채운 것이 명령 실행 자체일 때 |
| 복제본에서 읽기 | 읽기의 메인 스레드·네트워크 | 늦은 값을 허용하는 읽기만 보낼 수 있습니다 | 쓰기가 많을 때, 최신 값이 필요한 읽기가 많을 때 |
| 앱 로컬 캐시 | 자주 읽는 키의 요청 수·네트워크 | 캐시 시간만큼 낡은 값, 앱 힙 사용 | 자주 바뀌는 키, 요청마다 다른 키 |
| 용도별 인스턴스 분리 | 세 자원 모두(용도 단위로) | 운영할 Redis가 늘고, Spring에 연결 설정을 따로 둬야 합니다 | 한 용도의 데이터나 쓰기만으로 한 대를 넘을 때 |

각 대안의 판단은 다음과 같습니다.

- **데이터 줄이기**: TTL이 실제 필요보다 긴지, 아무도 읽지 않는 키가 쌓이는지, 같은 데이터를 더 작은 자료형으로 담을 수 있는지 봅니다. 예시라면 장바구니 TTL 30일이 정말 필요한지, 오래된 장바구니를 DB로 내릴 수 있는지가 먼저입니다. 자료형에 따른 메모리 차이는 [String과 Hash](./string-vs-hash.md)에, TTL 선택은 [TTL과 축출](./ttl-and-eviction.md)에 있습니다.
- **더 큰 서버**: 애플리케이션 코드를 바꾸지 않고 메모리와 네트워크를 함께 늘리는 방법입니다(I/O 스레드와 복제본 읽기도 설정만으로 켤 수 있지만, 늘려 주는 자원이 다릅니다). 다만 메인 스레드는 코어 하나만 쓰므로, 코어가 많은 서버로 바꿔도 명령 처리량은 코어 하나의 속도만큼만 바뀝니다. 공식 벤치마크 문서도 Redis가 단일 스레드라 코어가 많은 것보다 빠른 CPU를 선호한다고 적습니다(benchmarks, "Factors impacting Redis performance").
- **I/O 스레드**: `io-threads`를 2 이상으로 두면 소켓 읽기·쓰기와 요청 해석을 다른 스레드가 나눠 맡습니다. 8.2.10의 기본값은 1(꺼짐)이고, 실행 중에 바꿀 수 없어 재시작해야 합니다. `redis.conf`는 코어가 4개 이상인 서버에서, 실제로 성능 문제가 있고 Redis가 CPU를 많이 쓸 때만 켜라고 권합니다. 명령 실행은 여전히 메인 스레드 하나이므로, 예시의 2번 경고처럼 스크립트 실행이 메인 스레드를 채운 경우에는 풀리지 않습니다([Redis 이벤트 루프](./event-loop.md)의 "I/O 스레드를 켜도 명령 실행은 한 줄입니다").
- **복제본에서 읽기, 앱 로컬 캐시**: 앞 절 "읽기 확장은 복제본이 이미 줍니다"와 [Hot Key와 Big Key](./hot-key-big-key.md)의 "핫키는 Redis 앞에서 막거나, 복사본에 나눕니다"에 조건이 있습니다.
- **용도별 인스턴스 분리**: 서로 한 번에 다룰 일이 없는 데이터를 다른 Redis로 나누는 방법입니다. 예시라면 장바구니용 Redis와, 재고·구매자·상품 캐시용 Redis를 따로 둡니다. 장바구니와 재고를 한 스크립트로 다루는 일이 없으므로, 여러 키를 다른 요청이 끼어들지 못하게 한 번에 처리하는 원자성이 필요한 곳이 두 Redis에 걸치지 않습니다. 각 Redis는 여전히 주 서버 하나라 `MULTI`(명령 여러 개를 묶어 한 번에 실행), `WATCH`(지켜보던 키가 그사이 바뀌었으면 묶음 실행을 포기), 여러 키 스크립트가 그대로 동작합니다([Redis 원자성](./atomicity.md)). 대가는 애플리케이션이 "어느 용도는 어느 Redis"를 알아야 한다는 것입니다. Spring Boot의 자동 설정은 `RedisConnectionFactory` 빈이 하나도 없을 때만 연결 팩토리 하나를 만듭니다. 그래서 두 번째 Redis의 연결 팩토리를 직접 정의하는 순간 자동 설정의 연결 팩토리도 만들어지지 않으므로, 두 Redis의 연결 팩토리를 모두 직접 정의해야 합니다. 또 `RedisTemplate`·`StringRedisTemplate` 자동 설정은 연결 팩토리 후보가 하나로 정해질 때(일반적인 빈이라면 하나뿐이거나, 여럿 중 하나에 `@Primary`가 붙었을 때)만 동작하므로, 템플릿도 Redis마다 직접 정의하는 편이 분명합니다. 이 분리는 용도라는 굵은 단위로만 나누므로, 장바구니 하나만으로 한 대를 넘으면 다시 같은 문제에 닿습니다.

대안이 바닥나는 지점을 모으면 클러스터의 도입 조건이 됩니다. **한 용도의 데이터나 쓰기가, 줄이고 키운 뒤에도 서버 한 대를 넘고, 그 부하가 서로 독립적인 많은 키에 흩어져 있을 때**입니다.

## 옮기면 애플리케이션이 치르는 비용

### 코드와 키 설계

아래 항목의 동작은 [Redis Cluster](./cluster.md)에서 다루므로 여기서는 결론과 위치만 적습니다.

| 비용 | 무엇을 해야 하는가 | 자세한 곳(cluster.md의 절) |
| --- | --- | --- |
| 같은 슬롯 규칙 | 명령 하나, 트랜잭션 하나, 스크립트 하나에 넘긴 키가 모두 같은 슬롯이어야 합니다(스크립트가 실행 중에 접근하는 키의 세부 규칙과 예외는 cluster.md와 [Redis 원자성](./atomicity.md)에 있으며, 설계 규칙은 "같은 슬롯"으로 둡니다). 예시의 주문 스크립트는 `stock:item:1`, `buyers:item:1` 그대로는 `CROSSSLOT`으로 거부됩니다 | "한 번의 실행이 다루는 키는 모두 같은 슬롯이어야 합니다" |
| 해시 태그 설계 | 함께 다룰 키에 같은 태그를 붙입니다(`stock:{item:1}`). 키 이름이 바뀌므로 기존 데이터를 새 이름으로 옮기거나 다시 만들어야 하고, 태그 하나의 부하는 한 노드에 모입니다 | "해시 태그는 슬롯을 맞추는 대신 부하를 한 노드에 모읍니다" |
| `MULTI`/`WATCH` 사용 불가 | Spring Data Redis의 Lettuce 클러스터 연결은 `multi()`, `watch()`를 부르면 예외를 던집니다. 여러 키의 원자성은 해시 태그 + Lua 스크립트로 바꿔야 합니다 | "원자성: 같은 슬롯 안에서만, Spring에서는 사실상 Lua로" |
| 에러 없는 분할 실행 | Lettuce는 슬롯이 갈린 `MSET`, `DEL`, `MGET` 등을 슬롯별로 나눠 보내므로 에러 없이 원자성이 사라집니다 | "클라이언트가 나눠 보내면 에러는 사라지지만 원자성도 사라집니다" |
| 토폴로지 갱신 | 클러스터 클라이언트는 "어느 슬롯을 어느 노드가 맡는가"의 지도를 들고 직접 노드를 고릅니다. Lettuce는 틀린 노드가 돌려준 MOVED·ASK 안내를 그때그때 따라가지만, 기본값으로는 지도 자체를 다시 받지 않습니다. `spring.data.redis.lettuce.cluster.refresh.adaptive`(사건 기반)나 `period`(주기) 중 하나 이상을 켜야 지도가 바뀌며, cluster.md는 둘을 함께 켜기를 권합니다 | "Lettuce는 지도를 언제 받고, 언제 고치는가" |
| 리샤딩 중 `TRYAGAIN` | 슬롯을 옮기는 동안 여러 키 스크립트가 거부될 수 있고 Lettuce는 다시 보내지 않으므로, 짧은 지연 후 재시도를 붙입니다. 옮기는 순서와 재시도 기준은 클러스터 리샤딩에 있습니다 | "리샤딩 중에는 ASK와 TRYAGAIN이 생깁니다" |
| 노드별로 흩어진 기능 | 서버의 `KEYS`·`SCAN`은 접속한 노드의 키만 훑고(Lettuce의 클러스터 API는 모든 주 서버에 보내 결과를 모읍니다), 키 이벤트 알림은 그 키가 있는 노드에서만 나오고, DB는 0번만 씁니다 | "그 밖에 달라지는 것" |

이 표에서 비용이 가장 큰 것은 대개 위의 세 줄입니다. 공식 문서도 클러스터로 옮길 때 가장 중요한 것은 여러 키 연산·트랜잭션·여러 키 스크립트를 쓰는지, 쓴다면 같은 해시 태그 안에서만 쓰는지라고 적습니다(공식 문서 scaling, "Migrate to Redis Cluster"). 예시라면 장바구니는 키 하나씩만 다루므로 거의 비용이 없고, 주문 스크립트는 키 이름을 바꾸고, 혹시 `WATCH`로 짠 코드가 있다면 스크립트로 다시 짜야 합니다. 코드를 다 읽기 전에 위반 건수를 세는 방법(`cluster-compatibility-sample-ratio`와 `INFO`의 `cluster_incompatible_ops`)은 [Redis Cluster](./cluster.md)의 "클러스터로 옮기기 전에 확인할 것"에 있습니다. 실제로 실행된 명령의 표본만 세므로, 0이 나와도 그 기간에 실행되지 않은 코드 경로(월말 배치 등)는 확인되지 않은 것입니다.

### 구성과 전환

cluster.md가 다루지 않은, 도입 자체의 비용입니다.

- **노드 수**: 공식 문서는 제대로 동작하는 최소 클러스터가 주 서버 3대이고, 운영에는 주 서버 3대와 복제본 3대의 6노드를 강하게 권합니다(공식 문서 scaling, "Requirements to create a Redis Cluster"). 예시의 M + R(+ Sentinel)에서 Redis 서버 6대로 늘어납니다. 메모리를 3배로 늘리고 싶은 것이 아니라면, 처음에는 각 노드를 지금보다 작은 서버로 둘 수 있습니다.
- **클러스터 모드는 실행 중에 켤 수 없습니다**: `cluster-enabled`는 실행 중에 바꿀 수 없는 설정이라 재시작이 필요합니다. 공식 문서가 설명하는 방법은 클러스터 모드로 띄운 빈 인스턴스들로 클러스터를 만든 뒤(공식 문서 scaling, "Requirements to create a Redis Cluster") 기존 데이터를 넣는 것입니다. 그래서 이 문서는 "지금의 M에 설정 하나를 켠다"가 아니라 "새 클러스터를 만들고 데이터를 옮긴다"를 기준으로 계획합니다.
- **데이터를 옮기는 동안의 중단**: 공식 문서가 설명하는 이전 절차는 클라이언트를 멈추고, 기존 서버의 AOF를 만들어 새 클러스터 노드에 넣고, 키를 슬롯에 맞게 옮긴 뒤, 클러스터를 아는 클라이언트로 바꿔 다시 시작하는 순서입니다. 공식 문서는 단일 서버에서 클러스터로 자동으로 실시간 이전하는 방법은 없다고 적습니다. 대신 실행 중인 서버의 키를 클러스터로 옮기는 `redis-cli --cluster import`가 있는데, 이 명령은 옮긴 키를 원본에서 지웁니다(공식 문서 scaling, "Migrate to Redis Cluster"). 어느 쪽이든 "언제, 얼마 동안 쓰기를 멈출 것인가" 또는 "옮기는 동안 앱이 두 곳을 어떻게 볼 것인가"를 애플리케이션 쪽에서 정해야 합니다. 실패하면 기존 서버로 돌아갈 계획이라면 되돌아갈 곳이 남는지도 함께 정합니다. `--cluster import`는 기본으로 옮긴 키를 원본에서 지우므로 원본이 되돌아갈 곳이 되지 못합니다(`--cluster-copy`를 붙이면 원본에 남깁니다). 그리고 어느 방식이든, 새 클러스터가 쓰기를 받기 시작한 뒤에 연결만 되돌리면 그동안의 쓰기는 기존 서버에 없습니다. 예시처럼 캐시가 섞여 있다면 캐시는 옮기지 않고 새 클러스터에서 다시 채우는 것도 선택지입니다.
- **Spring 설정 전환**: Spring Boot는 `spring.data.redis.sentinel.*`가 있으면 Sentinel, 없고 `spring.data.redis.cluster.*`가 있으면 클러스터, 둘 다 없으면 단일 서버로 연결합니다. 그래서 Sentinel 설정을 남겨 둔 채 클러스터 설정을 더하면 여전히 Sentinel로 연결합니다. 전환 배포에서는 Sentinel 설정을 빼고 `spring.data.redis.cluster.nodes`와 토폴로지 갱신 설정을 함께 넣습니다.

### 옮긴 뒤에도 남는 것

클러스터는 노드 한 대의 성질을 바꾸지 않습니다. 각 주 서버는 여전히 메인 스레드 하나, 비동기 복제, 같은 `fork` 비용을 갖습니다. 그래서 이 문서의 지표는 클러스터에서도 **노드마다** 봐야 하고, 노드 사이의 치우침(한 노드만 메인 스레드가 바쁜 상태)이 새로 볼 지표가 됩니다. 어느 슬롯이 치우침의 원인인지는 [Redis Cluster](./cluster.md)의 "몰린 슬롯은 슬롯 통계로 찾습니다"에 있습니다.

연결 수도 늘어납니다. 앱 인스턴스마다 주 서버마다 연결을 열기 때문입니다. 얼마나 늘고 무엇을 정해야 하는지는 Redis Cluster의 연결 수에서 다룹니다.

## 예시의 경고 세 개에 적용하면

| 경고 | 무엇이 찼는가 | 흩어졌는가 | 결론 |
| --- | --- | --- | --- |
| 1. 메모리 20GB, 월 1.5GB 증가 | 메모리 | 흩어짐(사용자별 장바구니) | 약 2~3달 뒤 한도 24GB. 먼저 장바구니 TTL과 오래된 장바구니 정리, 그다음 더 큰 서버. 그래도 늘어나는 추세라면 클러스터의 정당한 이유이며, 장바구니는 태그 없이 흩어지므로 옮기는 비용도 작습니다 |
| 2. 메인 스레드 95% | 메인 스레드 | 몰림(상품 1의 주문 스크립트) | 클러스터로 풀리지 않습니다. 같은 태그로 묶인 두 키는 한 노드에 남습니다. 상품 1로 오는 요청을 줄이거나 바꾸는 설계가 필요합니다 |
| 3. 송신 약 3.7Gbit/s | 네트워크 | 상품 캐시 읽기라면 복제본·로컬 캐시로 나눌 수 있음 | 지금은 10Gbps의 약 37%. 늘어나면 상품 캐시 읽기를 복제본으로 보내거나 로컬 캐시를 둡니다 |

그래서 이 팀의 답은 "지금 당장 클러스터는 아니다. 장바구니가 줄일 수 있는 만큼 줄인 뒤에도 가장 큰 서버를 넘어설 추세라면 그때 간다"입니다. 그리고 그 결정을 내리는 날보다 먼저, 주문 스크립트의 키 이름(해시 태그)과 데이터 이전 방식처럼 오래 걸리는 준비를 시작합니다. 또는 장바구니만 별도 Redis로 떼어 내는 용도별 분리로 시간을 벌 수도 있습니다. 이 경우에도 장바구니 하나가 한 대를 넘는 날에는 클러스터가 필요합니다.

## 데이터와 요청이 늘면 무엇이 달라지는가

- **데이터가 늘면**: 한 대 구성에서는 `fork`, 전체 동기화, 재시작이 함께 길어집니다. 클러스터에서는 노드마다 데이터가 나뉘지만, 해시 태그 하나에 묶인 데이터는 그 태그의 노드에서만 늘어납니다.
- **쓰기가 늘면**: 한 대 구성에서 복제본은 쓰기를 나누지 못하고, 받은 쓰기를 적용하는 일이 늘어납니다. 클러스터는 흩어진 쓰기를 나누지만, 같은 키나 태그로 오는 쓰기는 나누지 못합니다.
- **읽기가 늘면**: 늦은 값을 허용하는 읽기는 복제본과 캐시로 나눕니다. 최신 값이 필요해 주 서버에 남겨야 하는 읽기가 많은 키에 흩어져 늘면, 그 몫은 클러스터가 나눕니다.
- **소수의 키에 요청이 몰리면**: 구성과 상관없이 노드 하나의 한계에 닿습니다. 노드 수가 아니라 키 설계와 요청 경로가 바뀌어야 합니다.
- **클러스터의 노드가 늘면**: 앱 인스턴스마다 노드별 연결과 토폴로지 갱신 요청이 늘고, 장애가 날 수 있는 곳도 늘어납니다([Redis Cluster](./cluster.md)의 "노드와 요청이 늘면 무엇이 달라지는가").

## 흔한 오해 모아 보기

| 오해 | 실제 | 본문 |
| --- | --- | --- |
| 서버 CPU가 낮으니 Redis는 여유가 있다 | 명령 실행은 메인 스레드 하나이므로 코어 하나 기준으로 봐야 합니다 | 주 서버 한 대가 가진 세 가지 자원 |
| 느려지면 클러스터로 노드를 늘리면 된다 | 부하가 소수의 키나 태그에 몰렸다면 노드를 늘려도 그 키의 노드는 그대로입니다 | 키 하나, 태그 하나에 몰린 부하 |
| 읽기가 많아서 클러스터가 필요하다 | 늦은 값을 허용하는 읽기는 복제본과 캐시가 먼저 나눕니다. 클러스터가 필요한 것은 주 서버에 남겨야 하는 읽기가 흩어진 키에서 한 대를 넘을 때입니다 | 읽기 확장은 복제본이 이미 줍니다 |
| 클러스터로 가야 장애 조치가 된다 | 단일 주 서버 구성의 자동 장애 조치는 Sentinel이 줍니다. 클러스터는 오히려 슬롯 하나의 상실이 전체 실패가 될 수 있습니다 | 자동 장애 조치는 Sentinel이 이미 줍니다 |
| 큰 서버로 바꾸면 처리량도 오른다 | 메모리와 네트워크는 오르지만, 명령 처리량은 코어 하나의 속도를 따릅니다 | 클러스터 전에 시도할 것과 그것이 바닥나는 지점 |
| `instantaneous_output_kbps`는 킬로비트다 | 초당 KB(1,024바이트)입니다 | 자원마다 보는 지표 |
| 지금 서버를 설정만 바꿔 클러스터로 만들 수 있다 | 클러스터 모드는 실행 중에 켤 수 없고, 새 클러스터를 만들어 데이터를 옮깁니다 | 구성과 전환 |

### 개발자가 정할 수 있는 것과 관찰해야 하는 것

| 정할 수 있는 것 | 관찰해야 하는 것 |
| --- | --- |
| TTL, 저장할 데이터의 범위, 자료형 | `used_memory`의 증가 속도와 `maxmemory`까지의 거리, `evicted_keys` |
| 읽기를 복제본으로 보낼지(`read-from`), 로컬 캐시를 둘지 | `used_cpu_*_main_thread` 증가분으로 본 메인 스레드 CPU 사용률, `eventloop_duration_sum` 증가분으로 본 루프 점유 비율 |
| 용도별로 Redis를 나눌지 | `instantaneous_output_kbps`(초당 KB)를 비트로 바꾼 값과 대역폭 상한의 비 |
| 여러 키 작업의 해시 태그 단위와 Lua 전환 | `INFO commandstats`의 명령별 실행 시간, 애플리케이션의 키별 요청 수 |
| 클러스터 전환 시 Spring 설정(Sentinel 설정 제거, 클러스터 노드, 토폴로지 갱신) | `latest_fork_usec`, 복제본 전체 동기화 시간 |

### 증상과 확인 순서

**증상 1: Redis 지연이 늘었는데 서버 CPU 사용률은 낮습니다.**

1. `used_cpu_*_main_thread`의 증가분으로 메인 스레드의 CPU 사용률을, `eventloop_duration_sum`의 증가분으로 루프 점유 비율을 봅니다. CPU 사용률이 코어 하나 기준으로 높다면 명령 일감이 한계이고, CPU는 낮은데 루프 점유만 높다면 디스크 같은 대기를 먼저 봅니다.
2. `INFO commandstats`와 애플리케이션 집계로, 그 일감이 소수의 키·명령에 몰렸는지 봅니다.
3. 몰렸다면 그 키의 요청 경로를 바꿉니다. 흩어졌고 쓰기가 대부분이라면 클러스터 검토 대상입니다. **부작용**: 클러스터로 가면 여러 키 작업의 키 이름과 코드를 바꿔야 합니다.

**증상 2: `maxmemory`에 닿아 쓰기 명령이 "-OOM command not allowed when used memory > 'maxmemory'" 에러로 거부됩니다.**

1. 축출 정책이 `noeviction`인지, 그 데이터가 축출되어도 되는 캐시인지 봅니다. 캐시라면 축출 정책을 켜는 것이 먼저입니다([TTL과 축출](./ttl-and-eviction.md)).
2. 축출되면 안 되는 데이터라면 어떤 키 종류가 메모리를 차지하는지, TTL과 정리로 줄일 수 있는지 봅니다.
3. 줄인 뒤에도 늘어나면 더 큰 서버, 그다음 용도별 분리나 클러스터를 정합니다. **부작용**: `maxmemory`만 올리면 `fork`·동기화를 위한 여유가 줄어 저장이나 동기화 중에 서버 메모리가 바닥날 수 있습니다.

**증상 3: 클러스터로 옮겼는데 한 노드만 바쁘고 나머지는 한가합니다.**

1. 그 노드에서 어느 슬롯이 바쁜지 슬롯 통계로 봅니다([Redis Cluster](./cluster.md)의 "몰린 슬롯은 슬롯 통계로 찾습니다"). 기본으로는 슬롯별 키 수만 나오고, 슬롯별 CPU 시간과 네트워크 바이트는 `cluster-slot-stats-enabled`를 켜야 집계됩니다.
2. 그 슬롯의 해시 태그나 키를 키 규칙에서 찾습니다. 옮기기 전에 소수의 키에 몰려 있던 부하라면, 옮긴 뒤에도 같은 키가 그 노드에 남은 것입니다.
3. 바쁜 슬롯이 여러 개라면 그중 일부를 한가한 노드로 옮겨 나눌 수 있습니다. 슬롯 하나가 대부분이라면 태그의 단위를 더 작게 하거나 그 키의 요청을 줄입니다. 그 슬롯을 다른 노드로 옮기면 함께 있던 다른 슬롯의 피해는 줄지만, 몰린 슬롯 자체의 한계는 그대로입니다.

### Spring에서 확인할 것

- 단일 주 서버 구성에서 읽기를 복제본으로 보내려면 `spring.data.redis.lettuce.read-from`을 씁니다. 재고 판단처럼 최신 값이 필요한 읽기도 함께 복제본으로 가므로, 연결 팩토리를 용도별로 나누거나 그 읽기를 스크립트 안에서 하도록 바꿉니다.
- 용도별로 Redis를 나누면, 연결 팩토리 빈을 하나라도 직접 정의하는 순간 Spring Boot의 자동 설정 연결 팩토리는 만들어지지 않습니다. 두 Redis의 연결 팩토리를 모두 직접 정의하고, 템플릿도 Redis마다 정의해 어느 코드가 어느 템플릿을 쓰는지 정합니다. 두 연결 팩토리가 모두 일반적인 주입 후보이고 어느 쪽에도 `@Primary`가 없으면 자동 설정의 템플릿은 만들어지지 않습니다.
- 클러스터로 전환하는 배포에서는 `spring.data.redis.sentinel.*`를 지우고 `spring.data.redis.cluster.nodes`를 넣습니다. Sentinel 설정이 남아 있으면 Spring Boot는 Sentinel로 연결합니다.

## 말로 설명하기

### 30초 버전

클러스터는 데이터와 쓰기를 여러 주 서버로 나누는 방법이라, 메모리나 쓰기 처리량이 주 서버 한 대를 넘고 그 부하가 많은 키에 흩어져 있을 때 씁니다. 늦은 값을 허용하는 읽기는 복제본이, 자동 장애 조치는 Sentinel이 이미 주고, 소수의 키나 한 해시 태그에 몰린 부하는 노드를 늘려도 한 노드에 남습니다. 옮기면 같은 슬롯 규칙, 해시 태그, Lua로의 전환, 토폴로지 갱신, 이전 중단을 치르므로 데이터 줄이기, 더 큰 서버, 복제본 읽기, 용도별 분리를 먼저 봅니다.

### 2분 버전

주 서버 한 대에는 메모리, 메인 스레드, 네트워크라는 세 한계가 있습니다. 메인 스레드는 명령을 실행하는 스레드 하나라서 서버 CPU 사용률이 아니라 메인 스레드 CPU 시간으로 코어 하나 기준의 사용률을 보고, `eventloop_duration_sum`으로 메인 스레드가 루프를 붙잡고 있던 비율을 함께 봅니다.

클러스터는 키를 슬롯으로 나눠 이 세 자원을 주 서버 수만큼 늘려 주지만, 조건이 있습니다. 부하가 많은 키에 흩어져 있어야 합니다. 예를 들어 사용자별 장바구니가 메모리를 채운다면 클러스터가 잘 맞습니다. 반대로 특가 상품 하나의 재고 스크립트가 메인 스레드를 채웠다면, 클러스터에서도 그 재고 키와 구매자 키는 같은 해시 태그로 한 노드에 있어야 하므로 풀리지 않습니다. 늦은 값을 허용하는 읽기가 많아 생긴 문제는 복제본이나 로컬 캐시로 나누는 편이 싸고, 장애 조치가 목적이면 Sentinel로 충분합니다.

그래서 먼저 찬 자원에 맞는 대안을 고릅니다. 메모리라면 데이터 줄이기와 더 큰 서버, 소켓 입출력이 메인 스레드를 채웠다면 I/O 스레드, 늦은 값을 허용하는 읽기라면 복제본과 캐시, 함께 다룰 일이 없는 용도가 섞여 있다면 용도별 인스턴스 분리입니다. 모든 대안을 차례로 거치는 절차가 아닙니다. 이것들이 바닥나는 지점, 곧 한 용도의 데이터나 쓰기가 줄이고 키운 뒤에도 한 대를 넘을 때가 클러스터의 시점입니다. 옮기는 비용은 여러 키 코드를 해시 태그와 Lua로 바꾸는 일, Spring Lettuce 클러스터 연결이 `MULTI`·`WATCH`를 거부하는 것, 토폴로지 갱신과 `TRYAGAIN` 재시도 설정, 그리고 자동 실시간 이전이 없어 데이터를 옮기는 동안의 중단입니다.

### 예상 질문과 꼬리 질문

**Q. 언제 클러스터로 가야 하나요?**
한 용도의 데이터나 쓰기가, 데이터를 줄이고 서버를 키운 뒤에도 주 서버 한 대를 넘고, 그 부하가 서로 독립적인 많은 키에 흩어져 있을 때입니다. 클러스터만이 데이터와 쓰기를 여러 주 서버로 나누기 때문입니다. 복제본이나 캐시로 나눌 수 있는 읽기 문제, 장애 조치 문제, 소수의 키에 몰린 문제는 이유가 되지 않습니다. 최신 값이 필요해 주 서버에 남겨야 하는 읽기가 흩어진 키에서 한 대를 넘는 경우는 쓰기와 같은 이유가 됩니다. (본문: "클러스터 전에 시도할 것과 그것이 바닥나는 지점")

- **꼬리: "한 대를 넘는다"는 걸 무엇으로 판단하나요?**
  메모리는 `used_memory`의 증가 속도와 한도까지의 거리(`mem_not_counted_for_evict`를 뺀 값과 `maxmemory`의 차이), 그리고 `fork`·동기화를 위한 여유를 뺀 서버 메모리로 봅니다. 메인 스레드는 메인 스레드 CPU 시간의 증가분 ÷ 경과 시간으로 코어 하나 기준의 사용률을 보고, `eventloop_duration_sum`의 증가분으로 루프가 붙잡혀 있던 비율을 함께 봅니다. CPU 시간은 낮은데 루프 비율만 높으면 디스크 같은 대기를 의심합니다. 네트워크는 `instantaneous_output_kbps`를 비트로 바꿔 대역폭 상한과 비교합니다. (본문: "자원마다 보는 지표")
- **꼬리: 메인 스레드 사용률이 몇 %면 위험한가요?**
  정해진 숫자는 없습니다. 메인 스레드는 한 번에 하나만 처리하므로 100%에 닿기 전부터 대기 시간이 늘어납니다. 그 비율과 애플리케이션이 본 Redis 지연을 함께 놓고, 서비스의 지연 목표로 정합니다.

**Q. 서버 CPU가 20%인데 Redis가 CPU 한계라는 게 말이 되나요?**
됩니다. 명령은 메인 스레드 하나가 실행하므로 코어 하나만큼이 상한입니다. 코어가 8개인 서버에서 메인 스레드가 코어 하나를 다 써도 서버 전체로는 약 12%로 보일 수 있습니다. `used_cpu_user`·`used_cpu_sys`도 프로세스 전체라서, 메인 스레드만 보려면 `_main_thread`가 붙은 값이나 이벤트 루프 시간을 봅니다. (본문: "주 서버 한 대가 가진 세 가지 자원")

**Q. 특정 상품에 주문이 몰려 Redis가 느립니다. 클러스터로 가면 풀리나요?**
아닙니다. 그 상품의 재고와 구매자 키를 한 스크립트로 다루려면 클러스터에서 같은 해시 태그로 같은 슬롯에 둬야 하고, 그 슬롯은 한 노드에 통째로 있습니다. 노드를 늘려도 그 상품의 주문은 한 노드의 메인 스레드가 처리합니다. 함께 있던 다른 키가 덜 기다리게 될 뿐입니다. 그 키로 오는 요청을 줄이거나 바꾸는 설계가 필요합니다. (본문: "키 하나, 태그 하나에 몰린 부하")

- **꼬리: 태그를 붙이지 않으면 흩어지지 않나요?**
  흩어지지만 두 키를 한 스크립트로 다룰 수 없게 되어 `CROSSSLOT`으로 거부됩니다. 원자성을 포기하고 두 번에 나눠 실행하면 그 사이에 다른 주문이 끼어들 수 있습니다. 원자성과 분산 중 하나를 고르는 문제이고, 핫키에서는 분산을 얻을 방법이 키 설계를 바꾸는 것뿐입니다.

**Q. 읽기 트래픽이 많아서 클러스터를 검토 중입니다.**
늦은 값을 허용하는 읽기라면 복제본이 먼저입니다. 복제본은 각자 메인 스레드와 네트워크를 가지므로 읽기를 나눕니다. Spring Boot에서는 `spring.data.redis.lettuce.read-from`으로 Lettuce가 읽기를 복제본에 보내게 합니다. 대가는 늦은 값이므로 최신 값이 필요한 읽기는 주 서버에 남깁니다. 자주 읽는 소수의 키라면 앱 로컬 캐시가 더 큰 효과를 냅니다. 주 서버에 남긴 읽기만으로 흩어진 키에서 한 대를 넘는다면, 그때는 클러스터가 나눕니다. (본문: "읽기 확장은 복제본이 이미 줍니다")

- **꼬리: 복제본을 계속 늘리면 읽기도 계속 늘어나나요?**
  복제본마다 주 서버가 보낸 쓰기를 자기 메인 스레드로 적용하므로, 쓰기가 많을수록 복제본 하나가 읽기에 쓸 수 있는 시간은 줄어듭니다. 또 주 서버는 직접 붙은 복제본마다 복제 흐름을 보내므로 주 서버의 송신량이 늘어납니다.

**Q. 장애 대비를 위해 클러스터로 가자는 의견은요?**
단일 주 서버 구성에서도 Sentinel이 자동 장애 조치를 줍니다. 클러스터는 장애 조치를 갖추고 있지만 그것이 도입 이유는 아니고, 기본 설정에서는 주 서버 하나와 그 복제본이 함께 죽으면 다른 노드의 키까지 실패하는 새 모양의 장애가 생깁니다. 비동기 복제와 네트워크 분할로 확인 응답한 쓰기를 잃을 수 있다는 점은 두 구성이 같습니다. 다만 분할 때 잃는 구간은 설정이 정합니다. 클러스터는 대략 `cluster-node-timeout`만큼이고, Sentinel 구성은 `min-replicas-to-write`를 두지 않으면 분할이 풀릴 때까지입니다. (본문: "자동 장애 조치는 Sentinel이 이미 줍니다")

**Q. 더 큰 서버로 가면 언제까지 버틸 수 있나요?**
메모리와 네트워크는 서버 크기만큼 늘지만, 명령 처리량은 코어 하나의 속도를 따르므로 코어 수가 많은 서버로 바꿔도 거의 늘지 않습니다. 또 데이터가 커질수록 `fork`, 복제본 전체 동기화, 재시작이 길어집니다. 살 수 있는 가장 큰 서버, 또는 이 시간들이 허용 범위를 넘는 지점이 수직 확장의 끝입니다. (본문: "클러스터 전에 시도할 것과 그것이 바닥나는 지점")

- **꼬리: I/O 스레드를 켜면 처리량이 오르지 않나요?**
  소켓 읽기·쓰기와 요청 해석이 메인 스레드를 채우고 있다면 오릅니다. 명령 실행 자체(긴 스크립트, 원소가 많은 명령)가 채우고 있다면 오르지 않습니다. 명령 실행은 여전히 메인 스레드 하나입니다. 켜려면 재시작이 필요합니다.

**Q. 용도별로 Redis를 나누는 것과 클러스터는 무엇이 다른가요?**
용도별 분리는 서로 함께 다룰 일이 없는 데이터를 사람이 정한 굵은 단위로 다른 Redis에 둡니다. 각 Redis는 주 서버 하나라 `MULTI`, `WATCH`, 여러 키 스크립트가 그대로 동작합니다. 클러스터는 키 단위로 자동으로 나누므로 한 용도의 데이터가 커져도 나눌 수 있지만, 같은 슬롯 규칙과 해시 태그를 치릅니다. 한 용도만으로 한 대를 넘는다면 용도별 분리로는 풀리지 않습니다. (본문: "클러스터 전에 시도할 것과 그것이 바닥나는 지점")

- **꼬리: Spring에서 Redis 두 개를 쓰면 무엇을 해야 하나요?**
  Spring Boot 자동 설정은 연결 팩토리 빈이 하나도 없을 때만 하나를 만들므로, 두 번째를 직접 정의하면 첫 번째도 직접 정의해야 합니다. 자동 설정의 템플릿은 연결 팩토리 후보가 하나로 정해질 때만 만들어지므로, 템플릿도 Redis마다 정의하고 어느 코드가 어느 템플릿을 쓰는지 정합니다.

**Q. 클러스터로 옮길 때 가장 큰 비용은 무엇인가요?**
여러 키를 한 번에 다루는 코드입니다. 같은 슬롯 규칙 때문에 해시 태그로 키 이름을 바꾸고, Spring Lettuce 클러스터 연결은 `MULTI`·`WATCH`를 거부하므로 Lua로 다시 짜야 합니다. 공식 문서도 이 부분을 가장 중요하다고 적습니다. 그다음이 데이터 이전입니다. 단일 서버에서 클러스터로의 자동 실시간 이전은 없으므로, 클라이언트를 멈추고 옮기거나 `redis-cli --cluster import`로 옮기는 방식을 정해야 합니다. (본문: "옮기면 애플리케이션이 치르는 비용")

- **꼬리: 지금 서버에 클러스터 모드를 켜면 되지 않나요?**
  `cluster-enabled`는 실행 중에 바꿀 수 없어 재시작이 필요하고, 공식 문서의 방법은 클러스터 모드로 띄운 빈 인스턴스로 클러스터를 만든 뒤 데이터를 넣는 것입니다. 그래서 설정 하나가 아니라 새 클러스터를 만들고 데이터를 옮기는 작업으로 계획합니다.
- **꼬리: 옮긴 뒤 Spring 설정에서 실수하기 쉬운 곳은요?**
  Sentinel 설정이 남아 있으면 Spring Boot는 클러스터 설정보다 Sentinel을 먼저 고릅니다. 그리고 Lettuce의 토폴로지 갱신은 기본으로 꺼져 있습니다. MOVED·ASK 안내는 따라가지만 슬롯 지도는 고치지 않으므로, `refresh.adaptive`나 `period`를 켜야 지도가 노드 추가와 장애 조치를 따라갑니다. 둘을 함께 켜는 것이 권장입니다([Redis Cluster](./cluster.md)).

**Q. 클러스터로 옮기면 Redis 지표는 어떻게 봐야 하나요?**
같은 지표를 노드마다 봅니다. 각 주 서버는 여전히 메인 스레드 하나, 같은 메모리·네트워크 한계를 가집니다. 새로 볼 것은 노드 사이의 치우침입니다. 한 노드만 바쁘다면 슬롯 통계로 원인이 여러 슬롯의 합인지, 슬롯 하나(소수의 키나 한 해시 태그)인지 가립니다. 여러 슬롯이라면 일부를 다른 노드로 옮겨 나눌 수 있고, 슬롯 하나라면 노드를 더해도 풀리지 않습니다. (본문: "옮긴 뒤에도 남는 것")

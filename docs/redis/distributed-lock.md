# Redis 분산 락: 만료되는 키 하나로 상호 배제를 어디까지 지킬 수 있는가

> **핵심 질문**: 서버 여러 대가 Redis 밖의 자원(DB 행, 외부 API)을 한 번에 한 요청씩만 다루게 하려면 Redis에 무엇을 어떻게 쓰는가? 그 락은 보유자가 멈추거나 Redis가 장애를 겪을 때 어디서 깨지며, 무엇으로 보완하는가? Redlock은 그중 무엇을 메우고 무엇을 남기는가?
>
> **범위**: Redis 주 서버 하나에 락 키를 두는 방식을 중심으로, 복제·재시작·시계 때문에 락이 사라지는 경우와 Redlock 알고리즘까지 다룹니다. 읽기·쓰기 락, 세마포어, 공정 락의 구현은 다루지 않습니다. Redlock의 안전성 논쟁은 공개된 두 글의 주장을 소개할 뿐, 이 문서가 직접 검증하지 않았습니다. 라이브러리 동작은 "근거"에 적은 버전의 소스를 읽어 확인했고, 재현해 보지는 않았습니다.

## 배경 지식

### 이 문서의 예시: 재고 1개는 DB에, 락은 Redis에

문서 끝까지 다음 장면 하나를 씁니다.

- DB에 상품 1의 행이 있고, 재고 `stock`은 **1**입니다.
- 주문 API 서버 1과 서버 2는 각각 JVM 프로세스입니다. 요청 A는 서버 1에서, 요청 B는 서버 2에서 처리됩니다. 두 서버는 같은 Redis 하나와 같은 DB 하나에 연결합니다.
- 락 키는 `lock:item:1`입니다.
- 각 요청은 다음 순서로 일합니다.
  1. Redis에 `lock:item:1` 락을 겁니다.
  2. DB 트랜잭션에서 재고를 읽고, 1 이상이면 "읽은 값 - 1"을 쓰고 주문 행을 저장한 뒤 커밋합니다. 아니면 품절로 끝냅니다.
  3. 락을 풉니다.
- **바라는 결과**: 주문 1건, 재고 0.

```text
 server 1 (JVM)                Redis                    server 2 (JVM)
+--------------+  lock   +------------------+   lock  +--------------+
| request A    |-------->| lock:item:1      |<--------| request B    |
+--------------+         |  = token, expiry |         +--------------+
       |                 +------------------+                |
       |   SQL                                          SQL   |
       |                 +------------------+                |
       +---------------->| DB  item 1       |<---------------+
                         |     stock = 1    |
                         +------------------+
```

화살표는 네트워크로 보내는 요청의 방향입니다. `lock`은 락을 걸고 푸는 Redis 명령, `SQL`은 DB 쿼리입니다. Redis와 DB는 서로 통신하지 않습니다. Redis의 복제본, 연결 풀, DB의 복제는 그림에서 뺐습니다. 복제본은 "장애 조치: 복제되기 전의 락은 새 주 서버에 없습니다"에서 다룹니다.

[Redis 원자성](./atomicity.md)에서는 재고가 Redis 안에 있어서 락 없이 단일 명령이나 Lua 스크립트로 풀었습니다. 이 문서의 재고는 DB에 있으므로 Redis의 원자성이 닿지 않습니다. 2단계의 판단을 "읽고 앱에서 계산해 쓰기"로 둔 것은 손으로 따라가기 위한 단순화입니다. 이 판단 하나만이라면 DB의 조건부 UPDATE로 락 없이 풀 수 있습니다. 이 점은 "락을 걸기 전에: 정말 락이 필요한가"에서 다시 봅니다.

### 경쟁 상태, 리스와 펜싱 토큰

- **경쟁 상태와 원자성**: 경쟁 상태는 실행 순서에 따라 결과가 틀어지는 문제이고, 락은 한 번에 한 흐름만 구간에 들어오게 해 이를 막는 방법입니다. 이 주제에서는 요청 A와 B가 2단계를 동시에 하면 둘 다 재고 1을 읽고 주문이 2건이 됩니다. JVM의 `synchronized`는 서버 하나 안에서만 통하므로, 두 서버가 함께 보는 Redis에 "지금 누가 쓰는 중"을 표시합니다. 자세한 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.
- **리스와 펜싱 토큰**: 리스는 정해진 기간 동안만 유효한 락이고, 펜싱 토큰은 락을 내줄 때마다 커지는 번호를 주어 보호하는 자원이 낡은 보유자의 쓰기를 거절하게 하는 방법입니다. 이 주제에서는 Redis 락이 만료 시간이 붙은 키이므로 리스입니다. 그래서 보유자가 기한보다 오래 멈추면 두 요청이 겹칠 수 있고, 이를 끝까지 막으려면 DB가 토큰을 확인해야 합니다. 보유자가 자기도 모르게 멈추는 이유, 벽시계와 단조 시계의 차이, 효율용 락과 정확성용 락의 구분은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)에서 다룹니다.

### 명령 하나와 Lua 스크립트 하나는 끼어들기 없이 실행됩니다

Redis에서 키를 읽고 바꾸는 명령은 메인 스레드 하나가 하나씩 끝까지 실행합니다. 그래서 명령 하나나 Lua 스크립트 하나가 실행되는 동안에는 다른 연결의 명령이 끼어들지 않습니다. 명령 두 개 사이에는 끼어들 수 있습니다. 이 주제에서는 "키가 없으면 만든다"와 "값이 내 것이면 지운다"를 각각 명령 하나나 스크립트 하나로 만들어야 한다는 뜻입니다. 자세한 동작과 스크립트의 대가는 [Redis 원자성](./atomicity.md)에서 다룹니다.

### Redis의 만료: 키에 절대 시각을 붙이고, 서버의 벽시계로 판정합니다

- **한 줄**: `PX 30000`처럼 만료를 주면 Redis는 "지금 + 30초"라는 절대 시각을 키에 붙여 두고, 서버의 현재 시각이 그 시각을 지나면 키를 없는 것으로 취급합니다.
- **비유**: 유효 시각이 찍힌 주차권입니다. 관리인은 자기 손목시계를 보고, 유효 시각이 지난 주차권을 무효로 봅니다. 주차권이 아직 차 안에 꽂혀 있어도 마찬가지입니다. 예시에서는 `lock:item:1`이 주차권이고, Redis 서버가 관리인입니다.
- **실제로는**:
  - 만료 시각은 명령 실행을 시작할 때 읽어 둔 서버 시각에 지정한 밀리초를 더해 정합니다.
  - 그 서버 시각은 벽시계입니다. 만료 판정도 이 시각이 만료 시각을 넘었는지로 합니다. 공식 문서도 "Redis is not using monotonic clock for TTL expiration mechanism"이라고 밝힙니다(distributed-locks, Disclaimer about consistency).
  - 만료 시각이 지난 키가 곧바로 메모리에서 지워지지는 않습니다. 주 서버는 그 키에 접근할 때 지우거나, 주기적으로 만료된 키를 골라 지웁니다. 그래도 결과는 같습니다. 쓰기 명령이 키를 찾을 때 만료된 키를 먼저 지우므로, 아직 메모리에 남은 락 키도 다음 `SET … NX`에게는 없는 키입니다.
  - 복제본은 만료된 키를 스스로 지우지 않고 주 서버가 보내는 삭제를 기다립니다. 읽기 명령에는 만료된 키를 없는 것으로 답합니다. 복제본이 주 서버로 승격되면 그때부터 자기 시계로 만료를 처리합니다(공식 문서 replication "How Redis replication deals with expires on keys").
  - `SET … PX 30000`은 복제본과 AOF에 `SET … PXAT <밀리초 절대 시각>`으로 바뀌어 전달됩니다. 그래서 복제본에도 같은 절대 시각이 붙습니다.
  - **비유와 다른 점**: 관리인의 손목시계는 앞뒤로 튈 수 있습니다. 서버의 시각이 바뀌면 같은 주차권이 더 일찍, 또는 더 늦게 무효가 됩니다. 그리고 관리인이 바뀌면(장애 조치) 새 관리인은 자기 손목시계로 판정합니다.
- **이 주제에서는**: **락의 수명은 Redis 서버의 벽시계가 정합니다.** 락을 건 서버 1의 시계와는 관계가 없습니다. 서버 1은 "30초가 지났는지"를 Redis에 묻지 않는 한 알 수 없습니다.

## 락을 걸기 전에: 정말 락이 필요한가

락이 없으면 예시는 다음처럼 틀어집니다.

| 순서 | 요청 A (서버 1) | 요청 B (서버 2) | DB `stock` |
| --- | --- | --- | --- |
| 1 | 재고 읽기 → 1 | | 1 |
| 2 | | 재고 읽기 → 1 | 1 |
| 3 | 0을 쓰고 주문 저장, 커밋 | | 0 |
| 4 | | 0을 쓰고 주문 저장, 커밋 | 0 |

재고는 0이지만 주문은 2건입니다. 확인 후 행동형 경쟁 상태입니다.

하지만 이 장면만이라면 락보다 단순한 해결책이 있습니다. 판단을 **자원이 직접** 하게 하는 것입니다.

- **DB의 조건부 UPDATE**: "재고가 1 이상일 때만 1 줄이기"를 한 문장으로 보내고, 바뀐 행 수로 성공을 판단합니다. 두 요청이 겹쳐도 한쪽은 실패합니다. 실패가 "바뀐 행 0"으로 나타나는지 오류로 나타나는지는 DB와 격리 수준에 따라 다릅니다.
- **버전 비교(JPA `@Version`)**: 읽을 때의 버전과 같을 때만 갱신합니다. 늦은 쪽은 충돌로 실패하고 다시 시도합니다.
- **고유 제약**: "1인당 1개"라면 (사용자, 상품) 고유 제약이 중복 주문을 DB에서 거절합니다.
- **DB 행 잠금(`SELECT … FOR UPDATE`)**: 판단이 여러 문장이나 테이블에 걸쳐도, 읽은 행을 이 방식으로 잠그면 다른 트랜잭션은 그 행을 잠그거나 고치려 할 때 내 트랜잭션이 끝날 때까지 기다립니다(PostgreSQL 17 Explicit Locking). 대가는 잠금 대기입니다. 트랜잭션이 길어지면 기다리는 요청마다 DB 커넥션을 붙잡고, 두 트랜잭션이 여러 행을 서로 다른 순서로 잠그면, 각자 상대가 쥔 잠금을 기다리며 둘 다 진행하지 못하는 교착이 생길 수 있습니다.

이 방법들은 Redis 왕복이 없고, 락의 만료나 Redis 장애를 따로 다룰 필요가 없습니다. 락은 다음 경우에 검토합니다.

- **판단과 변경이 DB 트랜잭션 하나에 담기지 않을 때**: 중간에 외부 API 호출이 끼거나, 지킬 상태가 여러 저장소에 나뉘어 DB의 잠금이나 조건이 닿지 않습니다.
- **같은 비싼 일을 여러 서버가 동시에 하지 않게 할 때**: 집계나 캐시 재계산처럼, 겹쳐도 결과는 맞지만 두 번 하면 낭비인 일입니다. 정산처럼 결과를 데이터에 반영하는 배치는 두 번 돌면 결과가 틀어지므로 여기에 들지 않습니다. 이런 배치는 아래의 정확성용 락입니다.
- **경합을 DB 앞에서 줄 세우고 싶을 때**: 버전 비교만 쓰면 한 행에 요청이 몰릴 때 실패와 재시도가 폭증합니다. 락으로 먼저 줄을 세우면 DB가 받는 시도가 줄어듭니다.

그리고 락을 쓰기로 했다면 먼저 물을 것이 있습니다. **"이 락이 깨져 두 요청이 겹치면 무슨 일이 생기는가?"** 같은 일을 두 번 하는 정도라면 효율용 락이고, 데이터가 틀어진다면 정확성용 락입니다. 이 문서의 뒤쪽은 Redis 락이 어떤 경우에 깨지는지를 다루는데, 그 결과를 얼마나 막아야 하는지는 이 구분이 정합니다. 구분의 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "효율을 위한 락과 정확성을 위한 락"에서 다룹니다. 예시의 초과 판매는 정확성용입니다.

## 락을 거는 명령: SET NX PX 하나로 '없으면 만들고 기한을 붙입니다'

요청 A는 다음 명령을 보냅니다. `<토큰 a>`는 이번 획득만을 위한 고유한 값입니다.

`SET lock:item:1 <토큰 a> NX PX 30000`

- **`NX`**: 키가 없을 때만 저장합니다. 키가 이미 있으면 아무것도 바꾸지 않고 nil을 돌려줍니다. 저장하면 `OK`를 돌려줍니다.
- **`PX 30000`**: 30,000밀리초 뒤의 절대 시각을 만료 시각으로 붙입니다. 키가 생기는 순간 이미 기한이 있습니다.
- 키 확인과 생성이 명령 하나 안에서 일어나므로, 두 서버가 동시에 보내도 메인 스레드가 하나씩 실행해 하나만 `OK`를 받습니다.

| 순서 | 요청 A (서버 1) | 요청 B (서버 2) | `lock:item:1` | DB `stock` |
| --- | --- | --- | --- | --- |
| 1 | `SET … NX PX 30000` → `OK` | | 토큰 a, 30초 뒤 만료 | 1 |
| 2 | | `SET … NX PX 30000` → nil | 토큰 a | 1 |
| 3 | 재고 읽기 1 → 0 쓰기, 주문 저장, 커밋 | (기다리거나 포기) | 토큰 a | 0 |
| 4 | 락 해제 | | 없음 | 0 |
| 5 | | `SET … NX PX 30000` → `OK` | 토큰 b | 0 |
| 6 | | 재고 읽기 0 → 품절 | 토큰 b | 0 |

락 하나에 드는 왕복은 거는 데 1번, 푸는 데 1번입니다.

### SETNX와 EXPIRE를 따로 보내면 영원한 락이 생길 수 있습니다

`SETNX`로 키를 만들고 `EXPIRE`로 기한을 따로 걸면, 두 명령 사이에 서버 1이 죽을 때 기한 없는 락 키가 남습니다. 아무도 그 키를 지우지 않으면 상품 1은 영원히 잠깁니다. 리스가 해결하려던 바로 그 문제입니다.

`SETNX`는 폐기 예정(deprecated)으로 표시돼 있습니다.

### 값에는 이번 획득만의 토큰을 넣습니다

값은 다음 절의 해제에서 "이 락이 아직 내 것인가"를 확인하는 데 씁니다. 그래서 모든 클라이언트와 모든 락 요청에 걸쳐 고유해야 합니다(공식 문서 distributed-locks: "This value must be unique across all clients and all lock requests"). JVM에서는 예를 들어 무작위 UUID 문자열을 씁니다. 서버 이름처럼 매번 같은 값을 쓰면, 같은 서버의 다른 요청이 건 락을 내 락으로 착각하게 됩니다.

## 락을 푸는 명령: '값이 내 토큰일 때만 지우기'를 한 덩어리로

### DEL만 보내면 남의 락을 지웁니다

요청 A가 일하는 도중 기한이 끝나는 장면입니다. 남의 락이 지워지는 결과를 보이려면 요청이 하나 더 필요하므로, 같은 상품을 주문하는 세 번째 요청 C를 더합니다. 시각과 정지 시간은 가상 예시입니다.

| 시각 | 요청 A | 요청 B | 요청 C | `lock:item:1` |
| --- | --- | --- | --- | --- |
| 0초 | `SET … NX PX 30000` → `OK` | | | 토큰 a, 30초에 만료 |
| 1~36초 | 재고를 읽은 뒤 멈춤 | | | 토큰 a |
| 30초 | (멈춤) | | | 만료 → 없음 |
| 31초 | (멈춤) | `SET … NX` → `OK`, 작업 시작 | | 토큰 b, 61초에 만료 |
| 36초 | 깨어나 작업을 마치고 `DEL` | 작업 중 | | **없음(b의 락이 지워짐)** |
| 37초 | | 작업 중 | `SET … NX` → `OK`, 작업 시작 | 토큰 c |

B가 일하는 동안 C도 들어왔습니다. A의 `DEL`이 B의 락을 지웠기 때문입니다. A와 B도 31~36초에 겹쳤는데, 이것은 해제 방식과 상관없는 문제이므로 "락이 지켜 주지 못하는 경우 1: 보유자가 기한보다 오래 멈출 때"에서 다룹니다.

`GET`으로 값을 확인한 뒤 `DEL`을 보내도 고쳐지지 않습니다. 확인과 삭제가 두 명령이라 그 사이에 기한이 끝나고 B가 락을 얻을 수 있습니다. 틈이 짧아졌을 뿐 같은 확인 후 행동입니다.

### 확인과 삭제를 Lua 스크립트 하나로 묶습니다

공식 문서가 제시하는 해제 스크립트는 다음 세 단계입니다(distributed-locks, Correct Implementation with a Single Instance).

1. `KEYS[1]`(여기서는 `lock:item:1`)의 값을 읽습니다.
2. 그 값이 `ARGV[1]`(내 토큰)과 같으면 키를 지우고, 지운 키 수(1)를 돌려줍니다.
3. 다르거나 키가 없으면 0을 돌려줍니다.

스크립트 하나가 실행되는 동안 다른 명령이 끼어들지 않으므로, 확인한 값이 지우는 순간에도 그대로입니다. 위 표의 36초에 A가 이 스크립트를 보내면 값이 토큰 b이므로 0을 받고, B의 락은 남습니다. 결과를 1과 0의 정수로 정해 두는 이유는 Lua 값이 Redis 응답으로 바뀌는 규칙 때문이며, [Redis 원자성](./atomicity.md)의 "Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다"에서 다룹니다.

**0이라는 결과는 그 자체로 경고입니다.** 대개 "내가 일하는 도중 락이 이미 내 것이 아니게 됐다"는 뜻이기 때문입니다. 그 사이 다른 요청이 같은 자원에 들어왔을 수 있습니다. 예외가 하나 있습니다. 해제가 실행돼 1을 돌려준 뒤 응답이 유실되면 Lettuce가 다시 연결해 같은 해제를 한 번 더 보낼 수 있고, 그때는 키가 이미 없어 0이 옵니다([Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)). 그래서 0은 겹침을 확정하는 값이 아니라 겹침이 있었을 수 있다는 신호로 다룹니다. 이 결과를 무시하지 않고 기록해야 하는 이유는 "해제 결과 0이 남는 유일한 흔적일 수 있습니다"에서 이어 봅니다.

이 스크립트가 막는 것은 **남의 락을 지우는 일**뿐입니다. A가 기한이 끝난 뒤에도 일한 것, 즉 31~36초의 A와 B의 겹침은 막지 못합니다.

## 기한은 짧으면 겹치고, 길면 기다리게 합니다

### 기한을 정하는 기준

- **보호 구간이 느릴 때 걸리는 시간보다 길어야 합니다.** 예시의 2단계가 평소 200밀리초에 끝나더라도, DB 잠금 대기, 재시도, GC 정지가 겹치면 수 초가 될 수 있습니다(가상 수치). 평소 시간이 아니라 꼬리 쪽 시간을 기준으로 잡습니다.
- **보유자가 죽으면 그만큼 기다립니다.** 기한이 30초일 때 서버 1이 락을 쥔 채 죽으면, 최대 30초 동안 상품 1의 주문은 아무도 처리하지 못합니다.
- **갱신이 없는 락이라면, 코드가 해제를 빠뜨려도 기한이 안전망이 됩니다.** 예외 경로에서 해제를 빠뜨리면 기한이 끝날 때까지 그 자원이 잠깁니다. 해제는 `finally`에서 하고, 기한은 그것마저 실패했을 때의 마지막 수단으로 봅니다. 갱신을 켠 락에서는 이 안전망이 없습니다. 이유는 "갱신은 '살아 있음'만 보여 줄 뿐, '일하고 있음'을 보여 주지 않습니다"에서 다룹니다.

기한을 늘려도 겹침이 사라지지는 않고 확률만 줄어든다는 점은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "기한의 길이는 두 위험을 맞바꿉니다"에서 다룹니다.

### 갱신: 일하는 동안 기한을 늘립니다

기한은 짧게 두고, 일하는 동안 주기적으로 늘리는 방법입니다. 늘릴 때도 "값이 내 토큰일 때만" 늘려야 합니다. 이미 남에게 넘어간 락의 기한을 늘리면 안 되기 때문입니다. 해제와 같은 모양의 스크립트로 만듭니다.

1. `lock:item:1`의 값이 내 토큰과 같으면 `PEXPIRE`로 기한을 다시 30초로 맞추고 1을 돌려줍니다.
2. 아니면 0을 돌려줍니다. 0을 받으면 락을 잃은 것이므로 하던 일을 멈춥니다.

주기는 기한보다 충분히 짧게 잡습니다. Redisson과 Spring Integration은 둘 다 기한의 3분의 1마다 늘립니다(아래 "Spring에서 확인할 것"). 한 번 늘리기에 실패해도 기한이 끝나기 전에 한 번 더 기회가 있습니다.

### 갱신은 '살아 있음'만 보여 줄 뿐, '일하고 있음'을 보여 주지 않습니다

갱신에는 두 방향의 한계가 있습니다.

- **멈추거나 끊기면 갱신도 멈춥니다.** GC의 stop-the-world 정지는 같은 JVM의 갱신 스레드도 멈추고, 네트워크가 끊기면 갱신 명령이 Redis에 닿지 않습니다. 그동안 기한이 끝날 수 있습니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "갱신해도 막지 못합니다"에서 다룹니다.
- **살아만 있으면 갱신은 계속됩니다.** 갱신은 보통 별도의 타이머 스레드가 합니다. 보호 구간의 요청 스레드가 응답 없는 외부 호출에 무한정 묶여 있어도, JVM이 살아 있는 한 타이머는 기한을 계속 늘립니다. 그러면 락이 사실상 풀리지 않습니다. Redisson의 갱신 스크립트는 Redis의 락 해시에 보유자 필드가 있는지만 보고 기한을 늘립니다. 같은 이유로, 해제를 호출하지 않은 락은 그 JVM의 Redisson 클라이언트가 살아 있는 동안 계속 갱신되는 것으로 소스에서 읽힙니다. 재현해 확인하지는 않았습니다.

그래서 갱신을 켤수록 **보호 구간 안의 모든 외부 호출에 타임아웃**을 두고, 해제를 `finally`에서 반드시 호출해야 합니다.

## 락을 못 얻었을 때: 바로 포기하거나, 기다리거나

`SET … NX`가 nil을 돌려주면 세 가지 중 하나를 고릅니다.

| 방식 | 동작 | 맞는 곳 | 대가 |
| --- | --- | --- | --- |
| 바로 포기 | "처리 중" 응답이나 건너뛰기 | 중복 클릭 방지, 같은 배치의 중복 실행 방지 | 사용자가 다시 시도해야 합니다 |
| 다시 시도(스핀) | 잠깐 쉬고 다시 `SET … NX` | 보유 시간이 짧고 대기자가 적을 때 | 대기자 수 × 초당 시도 횟수만큼 Redis 명령이 늘어납니다. 순서가 없어 오래 기다린 요청이 계속 질 수 있습니다 |
| 알림을 기다림 | 해제 알림을 받으면 다시 시도 | 대기자가 많거나 보유 시간이 길 때 | Pub/Sub 구독 연결이 필요합니다. 알림이 와도 다시 경쟁합니다 |

- **스핀의 비용**: 대기 요청 100개가 각각 초당 10번 시도하면, 락 하나를 위해 Redis가 초당 1,000개의 실패할 명령을 처리합니다(가상 계산). 공식 문서는 Redlock 절차에서, 락을 얻지 못한 클라이언트가 무작위로 지연한 뒤 다시 시도하라고 권합니다. 여러 클라이언트가 동시에 시도해 아무도 과반을 얻지 못하는 일을 피하기 위해서입니다(distributed-locks, Retry on Failure). 이 방식을 단일 인스턴스의 스핀에도 적용해 같은 순간에 몰리는 재시도를 흩어 놓는 것은 이 문서의 확장입니다.
- **Redisson의 알림 방식**: 기다리는 동안 락 이름별 Pub/Sub 채널을 구독하고, 해제 스크립트가 그 채널에 메시지를 발행합니다. 메시지가 오지 않아도 남은 기한(`PTTL` 결과)만큼 기다린 뒤 다시 시도합니다. 해제 메시지 하나에 구독 중인 Redisson 클라이언트마다 대기 중인 쪽 하나가 깨어나 다시 시도합니다. 서버마다 Redisson 클라이언트가 하나라면, 서버 10대에서 해제 한 번에 최대 10개 요청이 다시 경쟁합니다.
- **기다리는 쪽의 비용**: 기다리는 동안 요청 스레드가 묶입니다. 한 상품에 요청이 몰리면 Tomcat 요청 스레드가 락 대기로 바닥나, 다른 상품의 요청까지 처리하지 못할 수 있습니다. 대기 상한(예: Redisson `tryLock`의 `waitTime`)을 두고, 상한을 넘으면 실패로 응답합니다.

## 락이 지켜 주지 못하는 경우 1: 보유자가 기한보다 오래 멈출 때

요청 A가 재고를 읽은 직후 GC로 오래 멈춥니다. 해제는 앞의 스크립트를 씁니다. 시각과 정지 시간은 가상 예시입니다.

| 시각 | 요청 A (서버 1) | 요청 B (서버 2) | `lock:item:1` | DB `stock` |
| --- | --- | --- | --- | --- |
| 0초 | `SET … NX PX 30000` → `OK` | | 토큰 a | 1 |
| 1초 | 트랜잭션 시작, 재고 읽기 → 1 | | 토큰 a | 1 |
| 1~41초 | GC로 정지 | | 토큰 a | 1 |
| 30초 | (정지 중) | | 만료 → 없음 | 1 |
| 31초 | (정지 중) | `SET … NX` → `OK` | 토큰 b | 1 |
| 32초 | (정지 중) | 재고 읽기 1 → 0 쓰기, 주문 저장, 커밋 | 토큰 b | 0 |
| 33초 | (정지 중) | 해제 스크립트 → 1 | 없음 | 0 |
| 41초 | 깨어나 읽어 둔 1 기준으로 0 쓰기, 주문 저장, 커밋 | | 없음 | 0 |
| 42초 | 해제 스크립트 → **0** | | 없음 | 0 |

재고는 0이지만 **주문은 2건**입니다. Redis는 규칙대로 동작했습니다. Redis의 기록으로는 어느 순간에도 보유자가 하나였습니다. 하지만 A가 믿은 보유 기간과 Redis가 정한 보유 기간이 어긋났고, DB는 그 어긋남을 알 방법이 없습니다. 갱신을 켜 두었어도 GC는 갱신 스레드까지 멈추므로 결과는 같습니다. 41초에 쓰기 직전 "아직 내 락인가"를 확인해도, 확인과 쓰기 사이에 다시 멈출 수 있으므로 막지 못합니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "리스의 빈틈: 보유자는 자기 리스가 끝난 것을 모릅니다"에서 다룹니다.

### 해제 결과 0이 남는 유일한 흔적일 수 있습니다

42초의 해제 결과 0은 "A가 락을 잃은 뒤에도 일했다"는 뜻입니다. 이 시점에는 이미 커밋이 끝났으므로 되돌릴 수는 없지만, 겹침이 있었을 수 있다는 신호로 기록하고 지표로 셉니다. 라이브러리들도 이 상황을 예외로 알립니다.

- Spring Integration의 `RedisLockRegistry`는 기한이 지나 Redis에서 락이 사라진 뒤 해제하면 `ConcurrentModificationException`을 던지고, 메시지로 보호하던 데이터의 무결성이 깨졌을 수 있다고 알립니다("The integrity of data protected by this lock may have been compromised").
- Redisson의 `unlock()`은 현재 스레드가 보유자가 아니면 `IllegalMonitorStateException`을 던집니다. 기한이 지나 락을 잃은 경우와, 락을 건 스레드가 아닌 다른 스레드에서 해제한 경우를 같은 예외로 알리므로, 둘을 구별해 기록해야 합니다.

### 펜싱 토큰으로 DB가 늦은 쓰기를 거절하게 합니다

보유자 쪽에서는 이 겹침을 막을 수 없으므로, 마지막 확인을 DB로 옮깁니다.

1. **토큰 발급**: 락을 거는 스크립트 안에서 `SET … NX PX`가 성공하면, 같은 스크립트에서 카운터 키 `fence:item:1`을 `INCR`해 그 값을 돌려줍니다. 실패하면 0을 돌려줍니다. 락 획득과 번호 발급이 한 덩어리이므로 "락을 얻은 순서 = 번호 순서"가 됩니다. 아래 절차에서 데이터를 지키는 것은 DB의 등록과 조건부 쓰기이고, 이 순서는 카운터가 되돌아가지 않는 동안 락을 쥔 쪽이 이기게 해 줍니다. 락을 얻은 뒤 따로 번호를 받으면, 그 사이에 멈춘 요청이 나중에 더 큰 번호를 받아 락을 쥔 요청의 쓰기를 밀어낼 수 있습니다. 확인 방식별 조건의 차이는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "펜싱 토큰: 마지막 확인을 자원에게 맡깁니다"에서 다룹니다.
2. **DB에 토큰 등록**: 상품 행에 마지막으로 받은 토큰을 담는 컬럼을 둡니다. 재고를 **읽기 전에** "저장된 토큰이 내 토큰보다 작을 때만 내 토큰으로 바꾸기"를 실행하고 반영(커밋)해 둡니다. 등록은 한 번의 보유에 한 번만 하므로 같은 토큰을 허용하지 않습니다. 이렇게 엄격하게 비교해야 같은 번호를 받은 두 요청 중 하나만 등록됩니다("Redis 카운터로 토큰을 만들 때의 조건").
3. **조건부 쓰기**: 그다음 새 트랜잭션을 열어 재고를 읽고, 쓰기는 "상품 1이고 저장된 토큰이 내 토큰 이하일 때만 재고를 바꾸기"라는 조건부 UPDATE로 합니다. 등록이나 쓰기가 실패하면 롤백하고 실패로 응답합니다. 실패는 두 모양으로 나타나고, 뜻이 다릅니다.
   - **바뀐 행이 0**이면 비교에서 진 것입니다. 등록이면 저장된 토큰이 내 토큰 이상이고, 쓰기면 저장된 토큰이 내 토큰보다 큽니다. 더 새로운 보유자가 있거나, 같은 번호를 받은 다른 요청이 먼저 등록했거나, 카운터가 되돌아간 경우입니다. 등록이 엄격 비교이므로, 첫 등록이 커밋된 뒤 응답만 끊겨 같은 토큰으로 다시 등록해도 0행으로 실패합니다. 안전한 쪽의 실패입니다. MySQL은 바꾸려는 값이 지금 값과 같으면 바뀐 행을 0으로 세지만(MySQL 8.4 UPDATE 문서), 이 절차의 등록과 쓰기는 항상 값을 바꾸므로 여기에는 해당하지 않습니다.
   - **직렬화 오류**는 격리 수준에 따라 나타납니다. PostgreSQL 17의 REPEATABLE READ에서는 내 트랜잭션이 시작된 뒤 다른 트랜잭션이 그 행을 실제로 고치고 커밋했다면, 그 행을 UPDATE할 때 "could not serialize access due to concurrent update"로 실패합니다(PostgreSQL 17 Transaction Isolation). 이 오류는 그 행이 바뀌었다는 뜻일 뿐, 저장된 토큰이 내 것보다 크다는 뜻은 아닙니다. 다른 보유자의 쓰기와 겹쳐도 납니다. 이렇게 실패한 등록은 커밋되지 않았으므로 새 트랜잭션에서 다시 시도해도 됩니다.

같은 장면에 펜싱을 넣으면 다음과 같습니다. 토큰의 시작값 32는 이전 주문들이 남긴 값이라고 가정한 가상 예시입니다.

| 시각 | 요청 A (서버 1) | 요청 B (서버 2) | `fence:item:1` | DB `stock` | DB의 토큰 |
| --- | --- | --- | --- | --- | --- |
| 0초 | 락 획득, 토큰 33 | | 33 | 1 | 32 |
| 1초 | 토큰 33 등록 → 1행. 재고 읽기 → 1. 이후 GC로 정지 | | 33 | 1 | 33 |
| 31초 | (정지 중) | 락 획득, 토큰 34 | 34 | 1 | 33 |
| 32초 | (정지 중) | 토큰 34 등록 → 1행. 재고 읽기 → 1 | 34 | 1 | 34 |
| 33초 | (정지 중) | 토큰 34로 조건부 UPDATE → 1행, 주문 저장, 커밋 | 34 | 0 | 34 |
| 41초 | 토큰 33으로 조건부 UPDATE → **0행**, 롤백, 실패 응답 | | 34 | 0 | 34 |

주문은 1건입니다. Redis와 DB가 서로 통신하지 않아도, 토큰이 두 곳의 순서를 잇습니다.

**읽기 전에 등록하는 이유**: B가 32초에 읽은 뒤 늦어져 33초가 아니라 50초에 쓰게 되어도 결과는 같습니다. 41초의 A의 쓰기가 B가 32초에 등록한 34 때문에 거절되기 때문입니다. 등록 없이 쓸 때만 토큰을 확인했다면, 이 순서에서는 A(33)가 먼저 쓰고 B(34)도 뒤이어 써서 둘 다 성공합니다. 원리와 그 순서의 표는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "쓸 때만 확인하면 순서가 바뀐 경우를 막지 못합니다"에서 다룹니다. 이 절차는 이 문서가 그 원리에서 끌어낸 설계이며, 재현해 확인하지는 않았습니다. 등록 뒤의 읽기가 그때까지 커밋된 값을 본다는 전제가 필요합니다. 등록을 커밋한 뒤 새 트랜잭션에서 주 DB를 읽으면 성립하고, 읽기를 비동기 복제본으로 보내면 깨집니다. 등록보다 먼저 스냅숏을 잡은 트랜잭션 안에서 읽어도 깨질 수 있는데(여기서 스냅숏은 트랜잭션이 읽을 때 기준으로 삼는 DB의 한 시점 모습입니다. 그 시점 뒤에 커밋된 변경은 보이지 않습니다), 특히 판단에 쓰는 데이터가 토큰 행 밖에 있을 때입니다. 토큰과 재고가 같은 행인 이 예시에서는, 그 행이 스냅숏 뒤에 바뀌었다면 PostgreSQL REPEATABLE READ의 등록이 직렬화 오류로 실패하고, MySQL은 트랜잭션이 스스로 고친 행의 최신 값을 봅니다(MySQL 8.4 Consistent Nonlocking Reads). 격리 수준별 근거는 같은 CS 문서의 같은 절에서 다룹니다.

**그 밖에 필요한 전제**: 이 절차가 데이터를 지킨다는 결론은 다음도 깔고 있습니다.

- **토큰은 조건부 UPDATE가 잠그는 바로 그 행에 둡니다.** 판단에 쓰는 데이터의 쓰기는 모두 그 UPDATE와 같은 트랜잭션에서 커밋되거나 함께 롤백돼야 합니다. 토큰을 별도 테이블에 두고 다른 문장으로 확인하면, 격리 수준에 따라 낡은 쪽의 확인이 등록 전의 값을 보고 통과해 두 쓰기가 모두 반영되는 순서가 있습니다. 판단에 쓰는 데이터가 여러 테이블에 걸칠 때 특히 지켜야 하는 조건입니다.
- **등록 뒤의 작업은 한 트랜잭션에 담습니다.** 트랜잭션은 두 개입니다. 등록을 먼저 커밋하는 트랜잭션, 그리고 그 뒤에 새로 열어 재고 읽기, 조건부 쓰기, 주문 저장을 함께 커밋하는 트랜잭션입니다. 뒤의 작업이 여러 트랜잭션으로 나뉘면 중간에 거절될 때 일부만 반영됩니다.
- **쓰기 커밋의 응답이 끊겼을 때 같은 쓰기를 그대로 다시 보내지 않습니다.** 쓰기 조건은 같은 토큰을 허용하므로 다시 통과해, 카운터가 되돌아가지 않아도 주문이 2건이 될 수 있습니다. 락과 토큰을 새로 받아 처음부터 다시 하거나, 주문 ID 같은 멱등성 키로 쓰기 자체를 멱등하게 만듭니다. 멱등성의 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)의 "원자성이 보장하지 않는 것"에서 다룹니다.
- **DB에 저장된 토큰은 등록 말고는 줄어들지 않아야 합니다.** DB를 백업에서 되살리거나 값을 손으로 초기화하면 이 전제가 깨집니다.

**더 단순한 대안**: 쓰기를 "읽은 재고 그대로일 때만"이나 버전 비교로 걸면, 쓰는 순서와 상관없이 늦게 쓰는 쪽이 실패합니다. 이 예시라면 토큰 없이도 풀립니다. "락을 걸기 전에: 정말 락이 필요한가"에서 본 방법입니다.

클러스터라면 락 키와 카운터 키를 한 스크립트에서 다루므로 둘을 같은 슬롯에 두어야 합니다. `lock:{item:1}`, `fence:{item:1}`처럼 해시 태그를 맞춥니다. 규칙과 대가는 [Redis 원자성](./atomicity.md)의 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다"에서 다룹니다.

Redisson에는 이 방식을 구현한 `RFencedLock`이 있습니다. 락을 거는 스크립트 안에서 토큰 키를 `INCR`해 함께 돌려주고, 인터페이스 설명은 보호받는 서비스가 토큰을 확인해 이전 값보다 작으면 거절해야 한다고 적고 있습니다. 확인은 여전히 DB 쪽 코드의 몫입니다.

### Redis 카운터로 토큰을 만들 때의 조건

Redis 카운터는 장애 조치, 재시작, 축출로 되돌아갈 수 있습니다. 되돌아가면 이미 나간 번호나 그보다 작은 번호가 다시 나옵니다. 2단계에서 등록을 엄격하게 비교하는 것은 이때를 위해서입니다. DB에 저장된 가장 큰 토큰을 S, 되돌아가기 전에 나간 가장 큰 번호를 N이라고 하면 다음과 같습니다.

- **S 이하의 번호**는 등록에서 거절됩니다.
- **S보다 크고 N 이하인 번호**는, 되돌아가기 전에 나갔지만 아직 등록되지 않은 번호와 같을 수 있습니다. 같은 번호를 받은 두 요청 중 먼저 등록한 쪽만 통과하고, 늦은 쪽은 등록에서 거절됩니다.
- **낡은 보유자보다 작은 번호**를 받은 현재 보유자는, 낡은 보유자가 먼저 등록하면 쓰기에서 거절됩니다. 그렇지 않으면 낡은 보유자보다 먼저 끝내고, 낡은 보유자는 그 뒤에 등록하고 읽으므로 바뀐 재고를 봅니다.

이 문서가 실행 순서를 따라가 본 바로는, 어느 경우든 두 요청의 쓰기가 모두 반영되지는 않습니다. 남는 대가는 주문 실패입니다. 카운터가 S를 넘을 때까지는 등록이 모두 거절되고, 그 뒤 N까지는 겹치는 번호를 받은 요청이 거절될 수 있습니다. 락을 얻을 때마다 `INCR`하므로 등록에 실패한 요청도 카운터를 올립니다. 이 결론은 재현하지 않은 이 문서의 추론이고, 등록 뒤의 읽기가 최신 커밋을 본다는, "펜싱 토큰으로 DB가 늦은 쓰기를 거절하게 합니다"에서 밝힌 전제를 깔고 있습니다.

등록이 등호를 허용하면(저장된 토큰이 내 토큰 이하일 때 등록) 결과가 달라집니다. 재시작 전에 토큰 34를 등록하고 재고 1을 읽은 보유자 P가 GC로 멈춰 있다고 합시다. 재시작 뒤 카운터가 1부터 다시 세면 1~33을 받은 요청은 등록에서 거절되지만 카운터는 계속 오릅니다. 34번째로 락을 얻은 요청 Q가 34를 받아 "34 ≤ 34"로 등록하고 재고 1을 읽으면, P와 Q의 쓰기가 모두 통과해 주문이 2건이 될 수 있습니다. Kleppmann이 노드 하나의 카운터로는 그 노드가 장애를 겪을 수 있어 부족하다고 지적한 것도, 쓰기 때 더 작은 토큰만 거절하는 방식을 다룬 글에서입니다.

경우마다 되돌아가는 폭과, 락까지 함께 잃는지가 다릅니다.

- **장애 조치**: 주 서버가 응답한 `INCR`이 복제본에 닿기 전에 장애 조치가 일어나면, 새 주 서버의 카운터는 그보다 작습니다. 되돌아가는 폭은 복제 지연에 달려 있습니다. 이것은 복제가 비동기라는 공식 문서의 설명에서 끌어낸 이 문서의 추론입니다. 락을 거는 스크립트의 쓰기는 한 덩어리로 복제본에 전달되므로([Redis 원자성](./atomicity.md)의 "스크립트의 쓰기는 복제본에도 한 덩어리로 전달됩니다"), 카운터 증가가 빠지면 그 락 키도 함께 빠진다고 볼 수 있습니다(추론). 그래서 이전 보유자가 멈추지 않고 일하는 중에도 새 요청이 락을 얻습니다("장애 조치: 복제되기 전의 락은 새 주 서버에 없습니다").
- **재시작**: 영속성을 끈 Redis는 카운터와 락이 모두 사라지고, 카운터는 1부터 다시 셉니다. `INCR`은 키가 없으면 0에서 시작하기 때문입니다. RDB로 되살리면 마지막 스냅숏 이후의 증가를 모두 잃습니다. 잃는 폭은 저장 주기 설정에 달려 있습니다(Redis 영속성). 이때 카운터 키는 남아 있으므로 "키가 사라졌는가"로는 알아챌 수 없습니다. AOF `everysec`에서 정전이 나면 1초 안팎을 잃을 수 있습니다. 락도 같은 범위로 잃습니다. RDB로 되살리면 마지막 스냅숏 뒤에 건 락을 잃으므로, 기한이 30초인 락이라면 그 순간 쥐고 있던 락의 대부분을 잃습니다. AOF `everysec`이면 마지막 1초 안팎에 건 락을 잃습니다.
- **축출**: 카운터 키에는 만료 시간이 없으므로 `allkeys-` 정책이면 메모리 한도에서 지워질 수 있습니다. 결과는 영속성을 끈 재시작의 카운터와 같습니다. 다만 락 키는 남아 있을 수 있으므로, 이때 겹치려면 이전 보유자의 일시 정지가 함께 있어야 합니다. 정책별 동작은 [Redis 원자성](./atomicity.md)의 "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다"에서 다룹니다.
- **라이브러리 조작**: Redisson의 `RFencedLock`은 `deleteAsync`와 `expireAsync`를 토큰 키에도 함께 적용합니다. 그래서 락 객체를 지우거나 만료를 걸면 카운터도 사라지거나 만료되고, 결과는 축출과 같습니다.

정리하면, 등록을 엄격하게 비교하는 한 Redis 카운터로 만든 토큰은 카운터가 되돌아가도 DB의 데이터를 지킵니다. 지키지 못하는 것은 두 가지입니다. 되돌아간 동안의 주문 실패, 그리고 같은 장애로 락 자체가 사라져 생기는 DB 밖의 겹침(외부 API 호출 등)입니다. 대응은 다음 중에서 고릅니다.

- **실패 구간을 줄입니다.** 락 스크립트가 `SET … NX`를 실행하기 전에 카운터가 있는지 확인해, 없으면 락도 번호도 내주지 않고 거부하게 합니다. 그러지 않으면 `INCR`이 0에서 시작해 1을 내주고, 확인 순서를 바꾸면 거부해도 락 키가 남습니다. 그다음 카운터를 DB에 저장된 가장 큰 토큰 이상으로 맞춥니다. 여러 서버가 동시에 맞춰도 값이 줄지 않도록, "지금 값보다 클 때만 바꾸는" 원자적 스크립트로 합니다. 되돌아가기 전에 나갔지만 등록되지 않은 번호까지는 알 수 없으므로 여유분을 더하지만, 그 크기를 정확히 정할 수는 없습니다. RDB 복구나 장애 조치처럼 카운터 키가 남아 있는 경우에는, 등록 거절이 이어지는 것을 지표로 보고 알아채야 합니다. 이 대응은 이 문서의 설계입니다.
- **Redis 장애로 락과 번호를 잃는 일을 없애려면** 락과 번호를 함께 내주는 합의 기반 락 서비스로 옮깁니다. Kleppmann이 드는 ZooKeeper 같은 시스템입니다. 운영할 시스템이 하나 늘어납니다. 다만 이 방법이 없애는 것은 장애로 락과 번호를 잃는 경우뿐입니다. Kleppmann은 락 서비스가 완벽해도 보유자가 멈추는 문제는 남는다고 지적합니다. 그래서 DB 밖의 일(외부 API 호출 등)에는 여전히 멱등성 키 같은 장치가 필요합니다.
- **토큰 대신 DB의 버전 비교나 조건부 UPDATE로 정확성을 지킵니다.** 이 예시라면 가장 단순합니다.

## 락이 지켜 주지 못하는 경우 2: Redis가 락을 잃을 때

### 장애 조치: 복제되기 전의 락은 새 주 서버에 없습니다

Redis 복제는 기본적으로 비동기입니다. 주 서버는 복제본이 받았는지 기다리지 않고 응답합니다(공식 문서 replication). 공식 문서는 이 때문에 생기는 경쟁을 다음 순서로 설명합니다(distributed-locks, Why Failover-based Implementations Are Not Enough).

| 순서 | 요청 A | 요청 B | 주 서버 M | 복제본 R |
| --- | --- | --- | --- | --- |
| 1 | `SET … NX` → `OK` | | 토큰 a | (아직 받지 못함) |
| 2 | 작업 중 | | 장애로 중단 | 없음 |
| 3 | 작업 중 | | | 주 서버로 승격 |
| 4 | 작업 중 | `SET … NX` → `OK` | | 토큰 b |

A와 B가 동시에 락을 쥡니다. A는 아무 신호도 받지 못합니다. 공식 문서는 장애 같은 특수한 상황에서 여러 클라이언트가 동시에 락을 쥐어도 괜찮다면 복제 기반 구성을 써도 된다고 하고, 그렇지 않다면 Redlock을 제안합니다.

### WAIT은 잃을 확률을 줄일 뿐입니다

`SET … NX`가 성공한 뒤 같은 연결로 `WAIT 1 100`을 보내면, 복제본 1대가 그 쓰기를 받았다고 확인할 때까지 최대 100밀리초 기다리고 확인한 복제본 수를 돌려줍니다. 0이면 락을 풀고 실패로 처리할 수 있습니다. 하지만 공식 문서는 `WAIT`이 Redis를 강한 일관성 저장소로 만들지 않는다고 밝힙니다. 장애 조치 때 Sentinel과 Cluster는 가장 나은 복제본을 승격하려고 최선을 다할 뿐이어서, 여러 복제본에 전달된 쓰기도 잃을 수 있습니다(공식 문서 wait, Consistency and WAIT). 대가는 락을 거는 지연에 복제본의 확인을 기다리는 시간이 더해진다는 점입니다.

Redisson은 단일 서버 구성이 아니고 서버가 `WAIT`을 지원하면, 락 명령을 `WAIT`과 함께 보냅니다. 연결된 복제본 수만큼 최대 `slavesSyncTimeout`(기본 1,000밀리초) 동안 기다리고, 복제본이 있는데 하나도 확인하지 않았으면 락을 풀고 `NoSyncedSlavesException`을 던집니다. 이 검사는 `checkLockSyncedSlaves`(기본 `true`)로 켜고 끕니다. 확률을 줄이는 장치이지, 위 표의 경우를 없애는 장치는 아닙니다.

### 재시작: 영속성 설정만큼 락을 잃습니다

- **영속성을 끈 Redis가 재시작하면** 모든 락이 사라집니다. A가 일하는 도중 Redis가 재시작하면 B가 바로 락을 얻습니다.
- **AOF를 `everysec`로 켜 두어도** 정전이 나면 마지막 1초 안팎의 쓰기를 잃을 수 있고, 그 안에 건 락이 사라질 수 있습니다. 공식 문서도 같은 이유로, 모든 재시작에서 안전하려면 `fsync=always`가 필요하다고 설명합니다(distributed-locks, Performance, Crash Recovery and fsync).
- **영속성을 켠 상태에서 정상 종료 후 재시작**하면 락이 남습니다. 여기서 영속성은 AOF, 또는 종료할 때 RDB를 저장하는 설정을 말합니다. 만료 시각을 절대 시각으로 저장하므로, 내려가 있던 시간도 기한에서 빠집니다. 공식 문서도 AOF를 켠 경우의 정상 종료와 재시작을 안전한 경우로 듭니다. 기본 종료 동작은 RDB 저장 시점(save point)이 설정돼 있을 때만 RDB를 저장합니다(`shutdown-on-sigterm` 기본값). 그래서 저장 시점도 AOF도 없다면 정상 종료라도 락이 사라집니다.

설정별로 무엇을 얼마나 잃는지는 Redis 영속성에서 다룹니다.

### 시계: 서버의 벽시계가 뛰면 락이 일찍 풀립니다

"Redis의 만료: 키에 절대 시각을 붙이고, 서버의 벽시계로 판정합니다"에서 본 것처럼 만료 판정은 서버의 벽시계로 합니다.

- **서버 시각이 앞으로 뛰면** 그만큼 락이 일찍 풀립니다. 관리자가 시각을 바꾸거나, 시각 동기화가 시계를 한 번에 옮길 때 생깁니다. 공식 문서는 벽시계 이동으로 여러 프로세스가 락을 얻을 수 있다고 경고하고, 관리자가 서버 시각을 직접 바꾸지 못하게 하고 NTP를 제대로 설정하면 줄일 수 있지만 여전히 생길 수 있다고 적습니다(distributed-locks, Disclaimer about consistency).
- **장애 조치 뒤에는 새 주 서버의 시계가 판정합니다.** 락 키에는 옛 주 서버 시계 기준의 절대 시각이 복제돼 있습니다. 새 주 서버의 시계가 옛 주 서버보다 앞서 있으면 그 차이만큼 락이 일찍 풀린다고 추론할 수 있습니다(앞에서 본 `PXAT` 전파와 만료 판정에서 끌어낸 추론이며, 재현하지 않았습니다).

## Redlock: 서로 독립된 주 서버 여러 대의 과반에 락을 겁니다

### 알고리즘

Redlock은 복제로 이어지지 않은, 서로 독립된 Redis 주 서버 N대(문서의 예는 5대)를 씁니다. 공식 문서의 절차는 다음과 같습니다(distributed-locks, The Redlock Algorithm).

1. 현재 시각을 밀리초로 읽습니다.
2. N대 모두에 같은 키와 같은 토큰으로 `SET … NX PX`를 보냅니다. 가능하면 동시에 보냅니다. 노드마다 응답을 기다리는 시간은 기한보다 훨씬 짧게 잡습니다. 응답 없는 노드에 오래 묶이지 않기 위해서입니다.
3. 걸린 시간을 계산합니다. **과반(5대 중 3대 이상)에서 성공했고 걸린 시간이 기한보다 짧을 때만** 락을 얻은 것으로 봅니다.
4. 락의 유효 시간은 처음 기한에서 걸린 시간을 뺀 값입니다.
5. 실패하면 성공하지 못했다고 생각한 노드까지 포함해 모든 노드에서 락을 풉니다.

해제도 모든 노드에 "값이 내 토큰일 때만 지우기"를 보냅니다. 실패하면 무작위로 지연한 뒤 다시 시도합니다. 장애로 재시작한 노드는 최대 기한보다 조금 더 오래 참여하지 않게 하면(지연 재시작), 영속성 없이도 재시작으로 락이 겹치는 일을 피할 수 있다고 설명합니다. 대신 과반이 함께 재시작하면 그 시간 동안 어떤 락도 얻을 수 없습니다.

공식 문서는 이 알고리즘의 상호 배제가 **보유자가 유효 시간에서 시계 차이 보정분을 뺀 시간 안에 일을 끝낼 때만** 보장된다고 명시합니다(distributed-locks, Is the Algorithm Asynchronous?).

### 무엇을 메우는가

복제를 쓰지 않으므로 "장애 조치: 복제되기 전의 락은 새 주 서버에 없습니다"의 경우가 없습니다. A가 5대 중 3대에서 락을 얻은 뒤 그중 1대가 죽어도, 살아 있는 4대 가운데 A의 락이 없는 노드는 2대뿐이어서 다른 클라이언트는 과반(3대)을 얻지 못합니다. 이 결론은 죽은 노드가 락을 잃은 채 기한 전에 돌아오지 않는다는 전제에서만 성립합니다. 그래서 앞에서 본 지연 재시작이나 `fsync=always`가 필요합니다(distributed-locks, Performance, Crash Recovery and fsync). 노드 일부가 죽어도 과반이 살아 있으면 락을 계속 걸고 풀 수 있습니다.

### 무엇을 남기는가: 두 글의 쟁점

Redlock의 안전성에는 공개된 반론과 재반론이 있습니다. 이 문서는 어느 쪽이 옳은지 검증하지 않았고, 쟁점만 정리합니다.

| 쟁점 | Kleppmann(2016-02-08) | antirez(2016년 2월의 반론) |
| --- | --- | --- |
| 보유자의 일시 정지 | 락을 얻은 뒤 기한보다 오래 멈추면 Redlock도 겹침을 막지 못합니다. 펜싱 토큰이 필요한데 Redlock은 단조 증가하는 번호를 만들지 않습니다 | 획득 도중의 지연은 3단계의 경과 시간 확인이 잡아냅니다. 획득 뒤의 정지는 자동으로 풀리는 모든 락의 공통 문제입니다. 무작위 토큰도 자원 쪽의 비교 후 교체에 쓸 수 있습니다 |
| 시계 | 노드 하나의 시계가 앞으로 뛰면, 클라이언트 1이 A·B·C에, 클라이언트 2가 C·D·E에 동시에 과반 락을 쥘 수 있습니다 | 필요한 것은 시각의 일치가 아니라 비슷한 속도입니다. 시각을 직접 바꾸지 않고 NTP가 시계를 한 번에 옮기지 않게 하면 피할 수 있습니다. Redis가 만료에 단조 시계를 쓰도록 바꾸는 데 동의합니다 |
| 권고 | 효율용이면 Redis 한 대로 충분하고, 정확성용이면 ZooKeeper 같은 합의 기반 시스템이나 트랜잭션을 보장하는 DB와 펜싱 토큰을 씁니다 | Redlock을 쓰지 말아야 한다는 결론에는 동의하지 않습니다 |

확인할 수 있는 사실도 있습니다. 만료 판정은 여전히 벽시계를 쓰고, 공식 문서도 이를 밝히며 일관성이 중요하다면 펜싱 토큰을 구현하라고 권합니다(distributed-locks, Disclaimer about consistency). 공식 문서 안에서도 권고의 결이 다릅니다. `SET` 명령 페이지는 `SET … NX`로 만드는 단순한 락 패턴보다 Redlock을 권하고(set, Patterns), distributed-locks 페이지는 가끔의 경쟁 상태를 받아들일 수 있는 곳이라면 단일 인스턴스 방식도 쓸 만하다고 적습니다(distributed-locks, Correct Implementation with a Single Instance). 그리고 Redisson은 Redlock 구현인 `RedissonRedLock` 클래스를 `@Deprecated`로 표시하고 있습니다. 소스에는 그 이유가 적혀 있지 않습니다.

### 이 문서의 판단

- Redlock은 **Redis 장애 조치로 락을 잃는 경우**를 메우지만, **보유자의 일시 정지로 겹치는 경우**는 메우지 못합니다. 이것은 공식 문서의 "유효 시간 안에 끝낼 때만"이라는 조건에서도 확인됩니다.
- 정확성용 락이라면 어느 쪽이든 자원 쪽 확인(펜싱 토큰, 조건부 UPDATE, 버전 비교)이 필요합니다. 자원 쪽 확인이 있다면 락은 효율용이 되고, 효율용이라면 Redis 한 대(와 복제본)로 충분합니다.
- 그래서 Redlock이 값어치를 하는 곳은 좁습니다. "장애 조치 때 두 보유자가 생기는 일은 줄이고 싶지만, 드물게 겹치는 것은 견딜 수 있는" 경우입니다. 대가는 독립된 주 서버 5대의 운영, 과반 중 가장 느린 노드에 묶이는 획득 지연, 다섯 배의 명령입니다.
- 선택하지 않은 대안: ZooKeeper 같은 합의 기반 락 서비스는 되돌아가지 않는 번호를 줄 수 있어 펜싱에 맞지만, 운영할 시스템이 하나 늘어납니다. 이미 그런 시스템이 있거나, DB만으로 자원 쪽 확인을 할 수 없을 때 검토합니다.

## 요청과 데이터가 늘면 무엇이 달라지는가

- **락 하나의 처리량은 보유 시간이 정합니다.** 한 락 키는 한 번에 한 요청만 쥐므로, 그 키로 처리할 수 있는 요청은 초당 최대 (1 ÷ 평균 보유 시간)건입니다. 보유 시간이 50밀리초면 초당 20건입니다(가상 계산이며, 락을 걸고 푸는 왕복은 뺐습니다). 선착순 상품 하나에 초당 1,000건이 오면 대부분은 기다리거나 실패합니다. 보호 구간에서 외부 호출처럼 오래 걸리는 일을 빼서 보유 시간을 줄이거나, Redis 원자 연산처럼 락이 필요 없는 방식으로 바꿔야 합니다.
- **락을 잘게 나눌수록 교착 위험이 생깁니다.** 전역 락 하나 대신 상품별 락을 쓰면 다른 상품끼리는 겹치지 않습니다. 하지만 주문 하나가 상품 여러 개를 담으면 락을 여러 개 잡아야 하고, 두 요청이 서로 다른 순서로 잡으면 서로를 기다립니다. 키 이름 순서처럼 정해진 순서로 잡습니다. 갱신 없이 기한을 정한 락이라면 교착은 기한이 지나면 풀리지만, 그동안 두 요청 모두 멈추고, 풀린 뒤에는 겹침이 생길 수 있습니다. 갱신을 켠 락은 두 JVM이 살아 있는 한 기한이 계속 늘어나므로 교착이 풀리지 않습니다. 그래서 갱신을 켠 락에는 대기 상한(예: `tryLock`의 `waitTime`)이 꼭 필요합니다.
- **대기 방식이 Redis 부하를 정합니다.** 스핀은 대기자 수 × 시도 빈도만큼 명령을 늘리고, 알림 방식은 해제 때마다 Redisson 클라이언트 수만큼 재시도를 일으킵니다. 한 락 키는 클러스터에서도 한 노드가 맡으므로, 인기 상품의 락 명령은 노드 하나에 몰립니다.
- **락 키 자체의 메모리는 작습니다.** 키 하나에 짧은 문자열 하나이고, 기한이 지나면 사라집니다. 문제는 기한 없는 락 키가 생기는 버그입니다. 메모리 문제가 아니라 그 자원이 영원히 잠기는 문제입니다.
- **메모리 한도 정책이 락을 지울 수 있습니다.** 락 키에는 만료 시간이 있으므로 `volatile-` 정책에서도, `allkeys-` 정책에서도 축출 대상입니다. 축출되면 기한 전에 락이 사라져 다음 요청이 들어옵니다. `noeviction`이면 지워지지는 않지만, 한도를 넘은 상태에서 `SET`은 OOM 에러로 거부됩니다. 락 키는 캐시와 같은 인스턴스에 축출 정책을 켜고 두지 않습니다.
- **Redis가 느려지거나 멈추면 결정이 필요합니다.** 락을 걸 수 없을 때 요청을 거절할지(닫힌 쪽으로 실패), 락 없이 진행할지(열린 쪽으로 실패) 정해 둡니다. 정확성용 락이면 거절하고, 효율용 락이면 진행할 수 있습니다. 정하지 않으면 타임아웃이 쌓여 요청 스레드가 바닥납니다.

| 복제본이 있으니 락은 안전하다 | 복제는 비동기여서 장애 조치 때 락을 잃습니다. `WAIT`도 확률만 줄입니다 | 경우 2 |
| 만료 시간이 있는 키는 축출되지 않는다 | 만료 시간이 있는 키는 `volatile-` 정책의 축출 대상입니다 | 요청과 데이터가 늘면 |
| Redlock을 쓰면 정확성이 보장된다 | 장애 조치 문제는 메우지만 보유자의 일시 정지는 메우지 못합니다. 공식 문서도 유효 시간 안에 끝낼 때만 보장한다고 적습니다 | Redlock |
| 쓸 때 토큰을 확인하면 늦은 쓰기는 항상 거절된다 | 새 보유자의 쓰기가 먼저 도착했을 때만 거절됩니다. 읽기 전에 토큰을 등록하거나, 읽은 상태 그대로일 때만 써야 합니다 | 펜싱 토큰 |
| 펜싱 토큰을 쓰면 Redis 장애와 무관하게 안전하다 | Redis 카운터는 장애 조치·재시작·축출로 되돌아갈 수 있습니다. 등록을 엄격 비교로 해야 DB 데이터가 지켜지고, 그래도 되돌아간 동안 주문이 실패하며 같은 장애로 락이 사라져 DB 밖의 일은 겹칠 수 있습니다 | Redis 카운터로 토큰을 만들 때의 조건 |
| `@Transactional` 안에서 락을 걸고 풀면 된다 | 해제가 커밋보다 먼저 일어나 다음 요청이 커밋 전 데이터를 읽습니다 | Spring에서 확인할 것 |

## 실무 포인트

### 어떤 방식을 고를까

1. **자원이 직접 판단할 수 있으면 Redis 락을 쓰지 않습니다.** DB의 조건부 UPDATE, 버전 비교, 고유 제약, 행 잠금, 또는 데이터가 Redis에 있다면 Redis의 원자 연산이 먼저입니다.
2. **효율용 락**(다시 돌아도 결과가 같은 배치의 중복 실행, 중복 계산, 중복 클릭 방지)이면 Redis 한 대에 `SET … NX PX`로 걸고, 값이 내 토큰일 때만 푸는 스크립트로 풉니다. 직접 짜거나 Redisson, Spring Integration을 씁니다.
3. **정확성용 락**(초과 판매, 이중 결제 방지)이면 위에 더해 **자원 쪽 확인**을 반드시 둡니다. 같은 상태를 두고 겹치는 초과 판매에는 DB의 버전 비교 조건부 UPDATE, 또는 읽기 전에 등록하는 펜싱 토큰을 씁니다. 같은 작업이 두 번 실행되는 이중 결제(같은 주문의 결제)에는 외부 API가 지원하는 멱등성 키를 씁니다. 멱등성 키는 서로 다른 주문끼리의 초과 판매를 막지 못합니다. 락은 경합과 헛수고를 줄이는 역할로 둡니다.
4. **Redlock**은 장애 조치로 생기는 이중 보유를 줄이는 대가로 독립된 주 서버 여러 대를 운영할 가치가 있을 때만 검토합니다. 정확성용이라면 Redlock을 써도 3번이 필요합니다.

### 중요도별 점검 항목

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | 획득과 기한 설정이 명령 하나(`SET … NX PX`)나 스크립트 하나인가 | 따로 보내면 기한 없는 락이 남을 수 있습니다 |
| 필수 | 해제가 "값이 내 토큰일 때만"인가 | `DEL`은 기한이 지난 뒤 남의 락을 지웁니다 |
| 필수 | 정확성용 락에 자원 쪽 확인이 있는가 | 보유자의 일시 정지와 Redis 장애 조치로 락이 겹칠 수 있습니다 |
| 필수 | 락 범위가 DB 커밋을 감싸는가 | 해제가 커밋보다 먼저면 락이 있어도 초과 판매가 생깁니다 |
| 필수 | 락이 있는 인스턴스의 `maxmemory-policy` | 축출 정책이 켜져 있으면 락 키가 기한 전에 지워질 수 있습니다 |
| 알면 유리 | 기한을 꼬리 지연과 GC 정지 기준으로 잡았는가 | 평소 시간 기준이면 느린 순간에 겹칩니다 |
| 알면 유리 | 보호 구간 안의 외부 호출에 타임아웃이 있는가 | 갱신과 만나면 락이 풀리지 않습니다 |
| 알면 유리 | 대기 방식과 대기 상한 | 스핀은 Redis 부하를, 무한 대기는 요청 스레드 고갈을 부릅니다 |
| 알면 유리 | Redis 장애 시 닫힌 쪽으로 실패할지 열린 쪽으로 실패할지 | 정하지 않으면 타임아웃이 쌓입니다 |
| 참고 | Redlock과 합의 기반 락 서비스 | 장애 조치까지 견뎌야 할 때의 선택지입니다 |

### 관찰할 것

- **해제 결과가 0인 횟수**: 기한 안에 일을 끝내지 못한 횟수이자, 겹침이 있었을 수 있는 횟수입니다. Spring Integration의 `ConcurrentModificationException`도 같은 신호입니다. Redisson의 `IllegalMonitorStateException`은 락을 잃은 경우와 다른 스레드에서 해제한 경우에 모두 나므로, 해제한 스레드가 락을 건 스레드와 같은지 함께 기록해 구별합니다.
- **락 보유 시간의 분포**: 최댓값과 꼬리 백분위가 기한에 얼마나 가까운지 봅니다.
- **락 대기 시간과 획득 실패 수**: 경합이 얼마나 심한지 보여 줍니다.
- **JVM GC 정지 시간**: 가장 긴 정지가 기한에 가까우면 겹침이 운영 중에 생길 수 있습니다.
- **Redis 쪽**: `INFO`의 `evicted_keys`(축출이 일어나는가), `maxmemory_policy`, `errorstats`의 OOM 에러, 복제 지연(`INFO replication`), 장애 조치 이력. Redisson이라면 `NoSyncedSlavesException` 발생 수.
- **자원 쪽**: 펜싱이나 버전 비교로 거절된 쓰기 수. 이 값이 0이 아니면 락이 겹쳐 자원 쪽 확인이 막아 냈을 수 있습니다. 다만 겹침 없이도 거절이 생깁니다. 카운터가 되돌아간 동안의 등록 거절과, 응답이 끊긴 뒤 같은 토큰으로 다시 등록한 0행 실패입니다. 거절 시각을 Redis 장애 조치·재시작 이력과, 거절된 토큰을 같은 요청의 앞선 등록과 맞춰 보며 구별합니다. 불변식(남은 재고 + 성공 주문 수 = 처음 재고)도 점검합니다.

### 증상과 대응

| --- | --- | --- | --- |

| Redis 명령 수가 급증 | 스핀 재시도 | `INFO commandstats`의 `set` 호출 수 | 재시도 간격을 늘리고 무작위로 흩거나 알림 방식으로 바꿉니다 |

| 기한 전에 락이 사라짐 | 축출 정책, 서버 시각 변경, 장애 조치, 재시작 | `evicted_keys`, 서버 시각 동기화 로그, 장애 조치·재시작 이력 | 락을 축출 없는 인스턴스로 옮기고, 시각 변경을 막습니다. 장애 조치는 자원 쪽 확인으로만 막을 수 있습니다 |

### Spring에서 확인할 것

**락 범위는 트랜잭션 커밋을 감싸야 합니다.** 가장 흔한 실수입니다. `@Transactional` 메서드 안에서 락을 걸고 풀면, 해제가 커밋보다 먼저 일어납니다. 트랜잭션 프록시는 메서드 본문을 실행한 뒤에 커밋하기 때문입니다.

| 순서 | 요청 A | 요청 B | `lock:item:1` | DB에 커밋된 `stock` |
| --- | --- | --- | --- | --- |
| 1 | 프록시가 트랜잭션 시작 | | 없음 | 1 |
| 2 | 메서드 안에서 락 획득 | | 토큰 a | 1 |
| 3 | 재고 읽기 1 → 0 쓰기, 주문 저장(아직 커밋 전) | | 토큰 a | 1 |
| 4 | 메서드 끝에서 락 해제 | | 없음 | 1 |
| 5 | | 락 획득, 재고 읽기 → 1(A가 커밋 전이므로) | 토큰 b | 1 |
| 6 | 메서드 반환 → 프록시가 커밋 | | 토큰 b | 0 |
| 7 | | 0 쓰기, 주문 저장, 커밋 | 토큰 b | 0 |

5번에서 B가 1을 읽는 것은, 커밋되지 않은 변경을 다른 트랜잭션이 보지 않는 일반적인 격리 수준을 가정한 것입니다. 주문은 2건입니다. 대응은 락을 트랜잭션 바깥에서 거는 것입니다. 트랜잭션이 없는 바깥 메서드가 락을 걸고, 다른 빈의 `@Transactional` 메서드를 호출해 커밋까지 마친 뒤 락을 풉니다. 같은 클래스 안에서 `@Transactional` 메서드를 호출하면 프록시를 거치지 않아 트랜잭션이 적용되지 않으므로(참조 문서 annotations, 프록시 모드), 호출은 다른 빈을 거치게 하거나 `TransactionTemplate`으로 트랜잭션을 락 안에서 직접 엽니다.

**`@Scheduled` 작업은 인스턴스마다 따로 뜹니다.** 서버 3대에 같은 cron 작업이 있으면 같은 시각에 세 번 시작됩니다. 작업마다 락 키를 두고, 락을 얻지 못한 인스턴스는 기다리지 않고 건너뜁니다. 함정은 일찍 푸는 것입니다. 서버 1이 0.2초 만에 끝내고 락을 푼 뒤, 서버 2의 스케줄러가 시계 차이나 GC 정지로 0.5초 늦게 뜨면 락이 비어 있어 같은 회차를 한 번 더 실행합니다(가상 수치). 락은 "동시에 두 번"만 막고 "같은 회차를 두 번"은 막지 못하기 때문입니다. 그래서 키에 회차(예약된 실행 시각)를 넣고 작업이 끝나도 지우지 않은 채 기한으로 사라지게 하거나, 회차의 완료를 따로 기록합니다([멱등성 키](./idempotency-key.md)). 회차 키의 기한은 인스턴스 사이의 시작 시각 차이보다 길어야 합니다. 이 방법은 이 문서의 설계이며 재현하지 않았습니다. 정산처럼 결과를 데이터에 반영하는 작업이라면 이것으로도 부족하고, 정확성용 락처럼 자원 쪽 확인이 필요합니다.

**Redisson**

- **`leaseTime`을 주는지에 따라 갱신 여부가 다릅니다.** 보유 시간(`leaseTime`)을 주지 않으면 기한을 `lockWatchdogTimeout`(기본 30초)으로 잡고, 그 3분의 1(10초)마다 늘립니다. `lock()`뿐 아니라 `tryLock(waitTime, unit)`처럼 `leaseTime`을 받지 않는 메서드도 그렇습니다. 보유 시간을 주면 늘리지 않고 그 시간이 지나면 풀립니다. 갱신을 켤지 말지는 "갱신은 '살아 있음'만 보여 줄 뿐, '일하고 있음'을 보여 주지 않습니다"의 대가를 보고 정합니다.
- **락은 스레드에 묶입니다.** 보유자를 `클라이언트ID:스레드ID` 해시 필드로 구별하므로, 다른 스레드에서 `unlock()`하면 보유자가 아니라는 `IllegalMonitorStateException`이 납니다. 같은 스레드가 다시 걸면 필드 값이 늘어나는 재진입 락입니다. Kotlin 코루틴처럼 일시 중단 뒤 다른 스레드에서 이어 실행될 수 있는 코드에서는 이 구별이 깨질 수 있습니다. 보유자 ID를 직접 넘기는 `lockAsync(threadId)`, `unlockAsync(threadId)` 같은 API가 있습니다.
- **`finally`의 `unlock()`이 원래 예외를 덮을 수 있습니다.** 기한이 지나 보유자가 아니게 된 뒤 `finally`에서 `unlock()`하면 `IllegalMonitorStateException`이 나고, JVM에서는 `finally`에서 던진 예외가 본문의 예외를 대신합니다(JLS 21 §14.20.2: 본문의 예외는 "discarded and forgotten"). 이 예외는 잡아서 기록합니다. 락을 건 스레드에서 해제했는데도 났다면 락을 잃었다는 신호입니다.
- **복제 구성에서는 획득이 복제본 확인을 기다립니다.** "WAIT은 잃을 확률을 줄일 뿐입니다"의 동작 때문에 락 획득 지연에 복제본 확인 시간이 더해지고, 복제본이 확인하지 못하면 예외가 납니다.
- **펜싱 토큰이 필요하면 `RFencedLock`**을 씁니다. 토큰 확인은 DB 쪽 코드가 해야 합니다.

**Spring Integration `RedisLockRegistry`**

- 락 키는 `registryKey:lockKey`, 값은 레지스트리 인스턴스마다 만든 UUID입니다. 같은 JVM의 스레드끼리는 먼저 JVM 안의 `ReentrantLock`으로 줄을 서고, 그다음 Redis 락을 겁니다.
- 기본 기한은 60초입니다. 갱신은 `renewalTaskScheduler`를 설정했을 때만, 기한의 3분의 1마다 합니다.
- 기한이 지나 Redis에서 락이 사라진 뒤 해제하면 `ConcurrentModificationException`이 납니다. 락을 걸지 않은 스레드가 해제하면 이와 다른 `IllegalStateException`이 나므로, 이쪽은 두 경우가 예외 종류로 갈립니다.
- 대기 방식은 기본이 주기적 재시도(`SPIN_LOCK`)이고, Pub/Sub 알림(`PUB_SUB_LOCK`)을 고를 수 있습니다. 소스 설명은 주/복제본 연결이 아닐 때 Pub/Sub 방식을 권합니다.

**`RedisTemplate`으로 직접 구현할 때**

- `opsForValue().setIfAbsent(key, token, Duration)`은 `NX`와 만료를 담은 `SET` 명령 하나를 보냅니다. `setIfAbsent(key, token)` 뒤에 `expire`를 따로 부르면 "SETNX와 EXPIRE를 따로 보내면 영원한 락이 생길 수 있습니다"의 문제가 그대로 생깁니다.
- 해제·갱신 스크립트는 `execute(RedisScript, keys, args…)`로 보냅니다. 스크립트가 토큰을 바이트 단위로 비교하므로, 락을 걸 때와 풀 때 같은 직렬화기를 써야 합니다. 문자열 직렬화기를 쓰는 `StringRedisTemplate`이 단순합니다. 직렬화와 스크립트 결과 타입의 세부는 [Redis 원자성](./atomicity.md)의 "Spring에서 확인할 것"에서 다룹니다.
- 락용 템플릿에는 트랜잭션 지원을 켜지 않습니다. 트랜잭션 지원을 켠 템플릿은 `@Transactional` 안에서 쓰기 명령을 대기열에 쌓았다가 커밋 때 적용하므로(참조 문서 transactions), 락을 얻었는지를 그 자리에서 알 수 없습니다.

## 말로 설명하기

### 30초 버전

Redis 분산 락은 `SET 키 토큰 NX PX 기한` 한 명령으로 "없으면 만들고 기한을 붙여" 걸고, "값이 내 토큰일 때만 지우는" 스크립트로 풉니다. 기한은 보유자가 죽어도 락이 풀리게 하지만, 그 때문에 보유자가 GC 정지 등으로 기한보다 오래 멈추면 다른 요청이 들어와 겹칩니다. Redis 장애 조치나 재시작, 서버 시각 변경으로도 락이 사라질 수 있습니다. 그래서 겹쳐도 되는 효율용이면 Redis 한 대로 충분하고, 초과 판매처럼 겹치면 안 되는 곳에서는 DB가 펜싱 토큰이나 조건부 UPDATE로 늦은 쓰기를 거절하게 해야 합니다.

### 2분 버전

서버가 여러 대면 JVM의 `synchronized`는 닿지 않으므로, 두 서버가 함께 보는 Redis에 락 키를 둡니다. 먼저 락이 정말 필요한지 봅니다. 판단이 DB 한 문장에 담기면 조건부 UPDATE나 버전 비교로, 한 트랜잭션에 담기면 DB 행 잠금으로 충분합니다.

락은 `SET lock:item:1 토큰 NX PX 30000` 한 명령으로 겁니다. 키 확인과 생성, 기한 설정이 한 명령이라 두 서버 중 하나만 성공하고, `SETNX`와 `EXPIRE`를 나눠 보낼 때처럼 기한 없는 락이 남지 않습니다. 풀 때는 `DEL` 대신 "값이 내 토큰일 때만 지우는" Lua 스크립트를 씁니다. 기한이 지난 뒤의 `DEL`이 다른 요청의 락을 지우기 때문입니다.

문제는 기한입니다. 기한이 있어서 보유자가 죽어도 풀리지만, 보유자가 GC 정지로 기한보다 오래 멈추면 그사이 다른 요청이 락을 얻고, 깨어난 보유자는 그 사실을 모른 채 DB에 씁니다. 갱신을 켜도 GC는 갱신 스레드까지 멈추고, 반대로 멈춘 작업이라도 JVM이 살아 있으면 갱신이 계속됩니다. Redis 쪽에서도 비동기 복제 때문에 장애 조치 때 락을 잃을 수 있고, 영속성 설정만큼 재시작 때 잃고, 만료가 벽시계 기준이라 서버 시각이 뛰면 일찍 풀립니다. Redlock은 독립된 주 서버 여러 대의 과반에 락을 걸어 장애 조치 문제를 줄이지만, 보유자가 멈추는 문제는 남습니다.

그래서 기준은 "락이 깨지면 무슨 일이 생기는가"입니다. 같은 일을 두 번 하는 정도면 Redis 한 대로 충분합니다. 데이터가 틀어진다면, 락을 걸 때 펜싱 토큰을 받아 재고를 읽기 전에 DB에 등록하고 DB가 더 작은 토큰의 쓰기를 거절하게 하거나, 버전 비교 같은 DB 쪽 확인을 둡니다. Spring에서는 락 범위가 트랜잭션 커밋을 감싸게 하는 것이 먼저입니다.

### 예상 질문과 꼬리 질문

**Q. Redis로 락을 어떻게 거나요?**
`SET lock:item:1 <토큰> NX PX 30000`을 보냅니다. `NX`는 키가 없을 때만 저장하고, 있으면 nil을 돌려줍니다. 확인과 생성이 명령 하나 안에서 일어나므로 동시에 보내도 하나만 성공합니다. `PX`로 기한을 같은 명령 안에서 붙여, 보유자가 죽어도 락이 풀리게 합니다. (본문: "락을 거는 명령: SET NX PX 하나로 '없으면 만들고 기한을 붙입니다'")

- **꼬리: `SETNX` 뒤에 `EXPIRE`를 보내면 안 되나요?**
  두 명령 사이에 서버가 죽으면 기한 없는 락이 남아 그 자원이 영원히 잠깁니다. `SETNX`는 폐기 예정으로 표시돼 있습니다.
- **꼬리: 값에는 무엇을 넣나요?**
  이번 획득만의 고유한 값입니다. 해제와 갱신 때 "아직 내 락인가"를 확인하는 데 씁니다. 서버 이름처럼 반복되는 값을 쓰면 같은 서버의 다른 요청이 건 락을 내 것으로 착각합니다.

**Q. 락을 풀 때 `DEL`만 쓰면 왜 문제인가요?**
내 기한이 이미 끝나 다른 요청이 락을 얻은 뒤라면 `DEL`이 그 요청의 락을 지웁니다. 그러면 세 번째 요청까지 들어와 겹칩니다. 값이 내 토큰일 때만 지우는 스크립트로 확인과 삭제를 한 덩어리로 묶습니다. (본문: "DEL만 보내면 남의 락을 지웁니다")

- **꼬리: `GET`으로 확인하고 `DEL`하면요?**
  두 명령 사이에 기한이 끝나고 다른 요청이 락을 얻을 수 있습니다. 틈이 짧을 뿐 같은 확인 후 행동입니다.
- **꼬리: 소유자를 확인해 풀면 겹침이 없어지나요?**
  남의 락을 지우는 일만 막습니다. 기한이 지난 뒤에도 내가 일한 구간은 이미 다른 요청과 겹쳤을 수 있습니다. 해제 스크립트가 0을 돌려주면 그런 일이 있었다는 신호입니다.

**Q. 기한은 어떻게 정하나요?**
보호 구간이 느릴 때 걸리는 시간, 즉 DB 잠금 대기와 GC 정지까지 넣은 꼬리 시간보다 길게 잡습니다. 대신 보유자가 죽으면 그 기한만큼 아무도 처리하지 못합니다. 길게 잡아도 겹칠 확률이 줄 뿐 없어지지는 않습니다. (본문: "기한을 정하는 기준")

- **꼬리: 그럼 짧게 잡고 갱신하면 되지 않나요?**
  갱신은 느리지만 움직이는 경우를 구합니다. GC 정지는 갱신 스레드도 멈추고, 네트워크가 끊기면 갱신이 닿지 않아 기한이 끝납니다. 반대로 작업 스레드가 응답 없는 외부 호출에 묶여 있어도 JVM이 살아 있으면 갱신이 계속돼 락이 풀리지 않습니다. 그래서 보호 구간의 외부 호출에 타임아웃을 둡니다.
- **꼬리: Redisson의 watchdog은 언제 동작하나요?**
  `leaseTime` 없이 걸면 기한을 30초로 잡고 10초마다 늘립니다. `leaseTime`을 주면 늘리지 않습니다.

**Q. Redis 락을 썼는데 왜 주문이 두 건 생길 수 있나요?**
보유자가 기한보다 오래 멈추면, 그사이 기한이 끝나 다른 요청이 락을 얻습니다. 깨어난 보유자는 락을 잃은 것을 모른 채 읽어 둔 재고로 씁니다. Redis 기록으로는 보유자가 늘 하나였지만, 실제 작업은 겹쳤습니다. 장애 조치로 복제되기 전의 락이 사라지거나, 서버 시각이 뛰어 일찍 풀리는 경우도 같은 결과를 냅니다. (본문: "락이 지켜 주지 못하는 경우 1: 보유자가 기한보다 오래 멈출 때", "락이 지켜 주지 못하는 경우 2: Redis가 락을 잃을 때")

- **꼬리: 쓰기 직전에 락이 아직 내 것인지 확인하면요?**
  확인과 쓰기 사이에 또 멈출 수 있습니다. 보유자 쪽 확인으로는 막을 수 없습니다.
- **꼬리: 그럼 어떻게 막나요?**
  확인을 쓰기를 받는 DB로 옮깁니다. 락을 거는 스크립트에서 카운터를 `INCR`해 펜싱 토큰을 받고, 재고를 읽기 전에 그 토큰을 "저장된 토큰이 내 토큰보다 작을 때만 바꾸기"라는 엄격 비교로 DB에 등록합니다. 쓰기는 "저장된 토큰이 내 토큰 이하일 때만" 바꾸는 조건부 UPDATE로 합니다. 쓸 때만 확인하면, 새 보유자가 읽은 뒤 낡은 보유자가 먼저 쓰는 순서를 막지 못하기 때문입니다. 판단에 쓴 데이터가 모두 JPA의 버전 검사 대상이라면, 버전 비교가 쓰는 순서와 상관없이 늦은 쓰기를 거절하므로 토큰 없이도 됩니다. 고치는 엔티티는 자동으로 검사되지만, 읽기만 한 엔티티는 `lock(entity, LockModeType.OPTIMISTIC)`을 걸어야 검사 대상이 됩니다(Jakarta Persistence 3.1 §3.4.4.1). (본문: "펜싱 토큰으로 DB가 늦은 쓰기를 거절하게 합니다")

**Q. 펜싱 토큰을 Redis 카운터로 만들면 충분한가요?**
DB의 데이터에 대해서는 전제를 지키면 충분하다고 이 문서는 봅니다. 전제는 세 가지입니다. 읽기 전에 엄격 비교로 등록할 것, 등록을 커밋한 뒤 주 DB를 새 트랜잭션에서 읽을 것, 토큰과 판단 데이터를 같은 행·같은 트랜잭션에서 다룰 것입니다. 그러면 카운터가 장애 조치·재시작·축출로 되돌아가도 두 쓰기가 모두 반영되지 않습니다. 같은 번호라면 먼저 등록한 쪽만 통과하므로, 새 요청이 먼저 등록하면 낡은 보유자가 거절됩니다. 더 작은 번호라면 등록이나 쓰기에서 거절되거나, 상대보다 먼저 끝납니다. 대가는 되돌아간 동안 늘어나는 주문 실패입니다. 이것은 재현하지 않은 이 문서의 추론입니다. 다만 같은 장애로 락 자체도 사라질 수 있으므로 DB 밖의 일은 겹칠 수 있고, 여기에는 멱등성 키 같은 장치가 필요합니다. 등록이 등호를 허용하면, 카운터가 이미 나간 번호에 다시 닿을 때 같은 번호를 받은 두 보유자가 모두 통과해 주문이 2건이 될 수 있습니다. Redis 장애로 락과 번호를 잃는 일 자체를 없애려면 합의 기반 락 서비스로 옮기고, 가장 단순한 길은 DB의 버전 비교입니다. (본문: "Redis 카운터로 토큰을 만들 때의 조건")

- **꼬리: 토큰을 락과 따로 받으면요?**
  확인 방식에 따라 다릅니다. 재고를 읽은 뒤에 번호를 받고 쓸 때만 확인하면 주문이 2건이 될 수 있습니다. 읽기 전에 엄격 비교로 등록하는 방식이라면 데이터는 지켜집니다. 하지만 락을 얻고 번호를 받기 전에 멈춘 요청이 나중에 더 큰 번호를 받아, 락을 쥔 요청의 쓰기를 밀어낼 수 있습니다. 그래서 락 획득과 번호 발급은 한 스크립트에서 하는 편이 좋습니다.

**Q. 복제본이 있으면 락이 안전하지 않나요?**
복제는 비동기라서 주 서버가 `OK`를 준 락이 복제본에 닿기 전에 장애 조치가 일어나면, 새 주 서버에는 락이 없고 다른 요청이 바로 얻습니다. `WAIT`으로 복제본 확인을 기다리면 확률은 줄지만, 공식 문서는 확인된 쓰기도 장애 조치 때 잃을 수 있다고 밝힙니다. (본문: "장애 조치: 복제되기 전의 락은 새 주 서버에 없습니다", "WAIT은 잃을 확률을 줄일 뿐입니다")

- **꼬리: Redisson은 이를 어떻게 다루나요?**
  단일 서버 구성이 아니면 락 명령과 함께 `WAIT`을 보내고, 복제본이 하나도 확인하지 않으면 락을 풀고 예외를 던집니다. 확률을 줄이는 장치이고, 대가로 획득 지연이 늘어납니다.
- **꼬리: Redis가 재시작하면요?**
  영속성을 껐다면 모든 락이 사라집니다. AOF `everysec`도 정전 때 마지막 1초 안팎을 잃을 수 있습니다. 영속성(AOF, 또는 종료 때 RDB 저장)을 켠 상태의 정상 종료라면, 만료 시각이 절대 시각으로 저장되므로 락이 남습니다. 저장 시점도 AOF도 없다면 정상 종료라도 락이 사라집니다.

**Q. 락의 기한은 누구의 시계로 흐르나요?**
Redis 서버의 벽시계입니다. Redis는 명령을 시작할 때 읽은 서버 시각에 기한을 더해 절대 만료 시각을 정하고, 같은 시계로 판정합니다. 서버 시각이 앞으로 뛰면 락이 일찍 풀립니다. 장애 조치 뒤에는 새 주 서버의 시계로 판정하므로, 두 서버의 시계 차이만큼 기한이 달라진다고 추론할 수 있습니다. (본문: "Redis의 만료: 키에 절대 시각을 붙이고, 서버의 벽시계로 판정합니다", "시계: 서버의 벽시계가 뛰면 락이 일찍 풀립니다")

- **꼬리: 락을 건 앱 서버의 시계가 틀리면요?**
  기한 판정에는 영향이 없습니다. 다만 앱이 "남은 시간"을 직접 계산한다면 벽시계가 아니라 단조 시계(`nanoTime`)로 재야 합니다.

**Q. Redlock은 무엇이고, 쓰면 안전한가요?**
복제로 이어지지 않은 독립된 주 서버 여러 대(예: 5대)에 같은 락을 걸고, 기한 안에 과반을 얻었을 때만 락을 얻은 것으로 보는 알고리즘입니다. 복제를 쓰지 않으므로 장애 조치로 락을 잃는 문제를 메웁니다. 하지만 공식 문서도 보유자가 유효 시간 안에 일을 끝낼 때만 상호 배제를 보장한다고 적으므로, 보유자의 일시 정지 문제는 남습니다. (본문: "Redlock: 서로 독립된 주 서버 여러 대의 과반에 락을 겁니다")

- **꼬리: Kleppmann과 antirez는 무엇을 두고 다퉜나요?**
  Kleppmann은 Redlock이 펜싱 토큰을 만들지 못하고, 노드의 시계가 뛰면 두 클라이언트가 동시에 과반을 얻을 수 있다고 지적했습니다. antirez는 획득 중 지연은 경과 시간 확인이 잡아내고, 획득 뒤 정지는 모든 자동 해제 락의 공통 문제이며, 시계 점프는 운영으로 피할 수 있다고 반박하면서 만료에 단조 시계를 쓰는 데는 동의했습니다. Redis의 만료는 여전히 벽시계를 씁니다. 이 문서는 어느 쪽이 옳은지 검증하지 않았습니다.
- **꼬리: 그럼 언제 Redlock을 쓰나요?**
  장애 조치 때의 이중 보유를 줄이고 싶지만 드문 겹침은 견딜 수 있고, 독립된 주 서버 여러 대를 운영할 수 있을 때입니다. 정확성이 필요하다면 Redlock을 써도 자원 쪽 확인이 필요하고, 자원 쪽 확인이 있다면 Redis 한 대로 충분한 경우가 많습니다.

**Q. 락을 못 얻은 요청은 어떻게 하나요?**
바로 포기하거나, 잠깐 쉬고 다시 시도하거나, 해제 알림을 기다립니다. 다시 시도는 대기자 수와 시도 빈도에 비례해 Redis 명령을 늘리고 순서를 보장하지 않습니다. 알림 방식은 Redisson처럼 Pub/Sub로 깨우지만, 깨어난 요청끼리 다시 경쟁합니다. 어느 쪽이든 대기 상한을 두지 않으면 요청 스레드가 바닥납니다. (본문: "락을 못 얻었을 때: 바로 포기하거나, 기다리거나")

**Q. 인기 상품 하나에 요청이 몰리면 락이 버티나요?**
락 하나는 한 번에 한 요청만 처리하므로 처리량이 초당 (1 ÷ 보유 시간)건을 넘지 못합니다. 대기하는 요청은 Redis 부하와 스레드 고갈을 만듭니다. 이런 곳은 락보다 Redis 원자 연산이나 DB의 조건부 UPDATE처럼 판단을 한 연산에 담는 방식이 맞고, 앞단의 [입장 대기](./waiting-queue.md)로 요청 수를 줄이는 방법도 있습니다. (본문: "요청과 데이터가 늘면 무엇이 달라지는가")

**Q. 락 키에 만료 시간이 있는데 메모리 정책과 무슨 상관인가요?**
만료 시간이 있는 키는 `volatile-` 정책에서도 축출 대상이고, `allkeys-` 정책에서는 모든 키가 대상입니다. 메모리 한도에서 락 키가 축출되면 기한 전에 락이 사라집니다. `noeviction`이면 지워지지는 않지만 한도를 넘으면 `SET`이 OOM 에러로 거부되어 락을 걸 수 없습니다. 락 키는 축출 정책을 켠 캐시 인스턴스와 분리합니다. (본문: "요청과 데이터가 늘면 무엇이 달라지는가")

**Q. Spring에서 `@Transactional` 메서드 안에서 락을 걸고 풀면 왜 문제인가요?**
트랜잭션 프록시는 메서드 본문이 끝난 뒤에 커밋하므로, 락 해제가 커밋보다 먼저 일어납니다. 그 틈에 다른 요청이 락을 얻으면 커밋 전의 재고를 읽어 주문이 두 건이 됩니다. 락은 트랜잭션 바깥에서 걸고, 커밋이 끝난 뒤 풉니다. 같은 클래스 안의 호출은 프록시를 거치지 않아 트랜잭션이 적용되지 않으니 다른 빈을 거치게 합니다. (본문: "Spring에서 확인할 것")

- **꼬리: 여러 인스턴스의 `@Scheduled` 배치를 한 번만 돌리려면요?**
  작업별 락을 걸고 못 얻으면 건너뜁니다. 다만 먼저 끝낸 인스턴스가 락을 풀면 늦게 뜬 인스턴스가 같은 회차를 다시 돌 수 있으므로, 키에 회차를 넣고 끝나도 지우지 않거나 회차 완료를 기록합니다. 결과를 데이터에 반영하는 배치라면 자원 쪽 확인도 둡니다.
- **꼬리: Redisson 락을 코루틴에서 쓰면요?**
  Redisson은 보유자를 스레드 ID로 구별하므로, 일시 중단 뒤 다른 스레드에서 `unlock()`하면 보유자가 아니라는 예외가 납니다. 보유자 ID를 직접 넘기는 비동기 API를 쓰는 방법이 있습니다.
- **꼬리: `RedisTemplate`으로 직접 만들면 무엇을 조심하나요?**
  `setIfAbsent(key, token, Duration)`처럼 기한을 함께 주는 메서드를 써서 명령 하나로 겁니다. 해제 스크립트의 토큰 비교는 바이트 단위이므로 걸 때와 같은 직렬화기를 씁니다. 트랜잭션 지원을 켠 템플릿은 쓰기를 커밋 때 적용하므로 락용으로 쓰지 않습니다.

# Redis 멱등 키: 다시 온 요청을 한 번만 실행하려면 무엇을 기록해야 하는가

> **핵심 질문**: 클라이언트가 타임아웃 뒤 같은 요청을 다시 보내거나, 같은 요청이 두 서버에 동시에 도착할 때, 그 요청이 실제로 한 번만 실행되게 하려면 무엇을 어디에 기록해야 하는가? Redis의 `SET NX`와 TTL은 그중 어디까지를 맡을 수 있고, 어디서부터 DB의 고유 제약이 필요한가?
>
> **범위**: HTTP API의 멱등 키(`Idempotency-Key`)를 Redis로 처리하는 설계를 다룹니다. 단일 Redis 주 서버를 기준으로 합니다. Redis 안의 값 하나를 바꾸는 쓰기(예: 재고 `DECR`)를 멱등하게 만드는 방법은 [Redis 원자성](./atomicity.md)의 "원자성이 보장하지 않는 것"에서, 메시지 소비자의 멱등 처리는 [메시지 큐 기초](../cs/message-queue.md)에서 다룹니다.

## 배경 지식

### 이 문서의 예시: 주문 생성 요청 하나, 다시 보낸 요청 하나

문서 끝까지 다음 장면 하나를 씁니다.

- 모바일 앱이 주문 생성 API(`POST /orders`)를 부릅니다. 주문 API 서버는 S1, S2 두 대이고, 주문은 주문 DB에 저장하며, 결제는 외부 결제사 API를 부릅니다.
- 앱은 사용자 u42가 "주문하기"를 누를 때 무작위 UUID 하나(이하 `K1`)를 만들어 `Idempotency-Key` 헤더에 담습니다. 초안의 문법에서 이 값은 큰따옴표로 감싼 문자열이므로 실제 헤더는 `Idempotency-Key: "8e03978e-…"` 모양입니다. 이 문서에서는 이 값을 짧게 `K1`이라 부릅니다. 같은 주문을 다시 보낼 때는 같은 `K1`을 씁니다.
- 첫 요청 A가 S1에 도착합니다. S1이 결제와 주문 저장을 하는 동안 앱의 HTTP 타임아웃(가상 수치 3초)이 지나, 앱이 같은 `K1`으로 요청 B를 다시 보냅니다. B는 S2에 도착합니다.
- **바라는 결과**: 결제는 한 번, 주문은 한 건이며, 앱은 A와 B 어느 쪽 응답으로든 같은 주문 번호를 받습니다.

```text
 Mobile app ──A (Idempotency-Key: K1)──> S1 ─┐            ┌─> Payment API
            ──B (same K1, retry)──────> S2 ─┼─> Redis    ├─> Order DB
                                            └─(idem:u42:K1)┘
```

그림의 화살표는 요청이 이동하는 방향입니다. S1과 S2는 Redis의 같은 키(`idem:u42:K1`)를 보고 "이 요청을 이미 받았는가"를 판단합니다. 연결 풀, Redis 복제본, 영속화는 그림에서 뺐습니다. Redis가 기록을 잃는 경우는 "TTL과 장애는 보장의 범위를 정합니다"에서 다룹니다.

### 멱등성

같은 요청을 여러 번 실행해도 한 번 실행한 것과 효과가 같은 성질입니다. "주문 생성"은 그 자체로 멱등이 아니므로, 요청마다 고유 ID를 붙이고 "이 ID는 이미 처리했다"는 기록을 남겨야 합니다. 그 기록과 실제 처리 사이에 틈이 있으면 같은 문제가 다시 생깁니다. 이 주제에서는 `K1`이 그 고유 ID이고, 문서 전체가 "기록과 처리 사이의 틈을 어디까지 줄일 수 있는가"를 다룹니다. 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)의 "원자성이 보장하지 않는 것"에서 다룹니다.

### 타임아웃은 일을 취소하지 않습니다

타임아웃은 기다리는 쪽이 기다리기를 그만두는 것일 뿐이고, 상대에게 취소를 알리거나 이미 한 변경을 되돌리지 않습니다. 그래서 응답을 받지 못한 쪽은 요청이 아직 안 갔는지, 실행 중인지, 실행됐는데 응답만 사라졌는지 구분하지 못합니다. 이 주제에서는 앱이 3초 만에 포기해도 S1은 A를 계속 처리하고 있을 수 있다는 뜻입니다. 그래서 B가 도착한 순간 A는 "끝남"이 아니라 "처리 중"일 수 있습니다. 원리는 [타임아웃](../cs/timeout.md)에서 다룹니다.

### 다시 보내는 주체는 여럿입니다

같은 요청이 다시 오는 길은 사용자의 재시도만이 아닙니다. 앱의 HTTP 클라이언트 재시도, 사용자가 버튼을 두 번 누르는 경우, 게이트웨이의 재시도가 있습니다. 서버 안에서도 Lettuce는 연결이 끊겼다 다시 붙으면 응답을 받지 못한 Redis 명령을 앱 코드 몰래 다시 보냅니다. 이 주제에서는 S1이 보낸 Redis 명령 자체도 두 번 실행될 수 있다는 점이 "기록에는 주인 토큰을 넣습니다"의 이유가 됩니다. 세부는 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)의 "연결이 끊기면 Lettuce가 응답 못 받은 명령을 다시 보냅니다"에 있습니다.

### 리스

TTL은 키에 붙이는 만료 시각이고, 그 시각이 지나면 Redis는 키를 없는 것으로 취급합니다. `PX 60000`은 60,000밀리초, 곧 60초 뒤에 만료하라는 뜻입니다. 언제 실제로 지워지고 어떤 경우 일찍 사라지는지는 [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.

리스는 정해진 기간 동안만 유효한 락입니다. 보유자가 죽어도 기한이 지나면 풀리지만, 보유자가 기한보다 오래 멈추면 보유자 자신은 리스가 끝난 것을 모른 채 일을 계속합니다. 이 주제에서는 "처리 중" 기록이 TTL을 가진 키이므로 리스입니다. 그래서 S1이 기한보다 오래 멈추면 B가 A와 겹쳐 실행될 수 있습니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)에서 다룹니다.

### 멱등 키

- **한 줄**: 멱등 키는 클라이언트가 "이 요청들은 같은 하나의 의도"라고 표시하려고 요청에 붙이는 고유 값이고, 서버는 이 값으로 처음 온 요청과 다시 온 요청을 구분합니다.
- **비유**: 은행 창구의 번호표 대신 "송금 신청서 일련번호"입니다. 손님이 같은 신청서를 두 번 내밀어도, 직원은 일련번호 장부를 보고 "이미 처리한 신청서"면 처리 결과 영수증 사본을 돌려줍니다. 예시에서 일련번호는 `K1`, 장부는 Redis, 직원은 S1·S2입니다.
- **실제로는**:
  - IETF의 인터넷 초안 "The Idempotency-Key HTTP Header Field"(draft-ietf-httpapi-idempotency-key-header-08)가 헤더 이름과 기대 동작을 정리하고 있습니다. 아직 표준(RFC)이 아니라 초안입니다. 초안은 키가 고유해야 하고 다른 요청 본문에 다시 쓰면 안 되며, UUID 같은 무작위 값을 권합니다(2.2절).
  - 초안이 나누는 경우는 셋입니다(2.6절, 2.7절). 처음 온 요청은 평소처럼 처리합니다. 원래 요청이 **끝난 뒤** 다시 오면 원래 처리와 일관된 응답을 돌려줍니다. 원래 요청이 **아직 처리 중일 때** 다시 오면 409 Conflict로 응답합니다. 같은 키를 **다른 본문**에 다시 쓰면 422 Unprocessable Content로 응답합니다.
  - 본문이 같은지 판단하는 값을 초안은 지문(fingerprint)이라고 부르며, 본문 전체나 일부의 체크섬 등을 예로 듭니다(2.4절).
  - 키를 얼마나 오래 기억할지(만료 정책)는 서버가 정하고 문서로 공개해야 한다고 적습니다(2.3절, 2.5.2절).
  - **비유와 다른 점**: 은행 직원은 장부를 한 권만 보지만, 예시에서는 S1과 S2가 같은 장부를 **동시에** 봅니다. 그리고 장부(Redis)와 실제 돈이 움직이는 곳(결제사, 주문 DB)이 서로 다른 시스템이라, 장부에 적는 일과 처리하는 일이 한 번에 일어나지 않습니다.
- **이 주제에서는**: Redis는 `K1`에 대해 "처음인가, 처리 중인가, 끝났는가"와 끝났다면 무슨 응답을 했는지를 기억합니다. 문서의 나머지는 이 기록을 언제, 어떤 명령으로 쓰고, 그 기억이 어떤 경우에 틀리는지를 다룹니다.

## 확인하고 처리하면 왜 두 번 실행되는가

가장 단순한 구현은 "기록이 있는가 확인 → 없으면 처리 → 끝나면 기록"입니다. 예시는 이렇게 틀어집니다.

| 순서 | S1 (요청 A) | S2 (요청 B) | Redis `idem:u42:K1` |
| --- | --- | --- | --- |
| 1 | `GET` → 없음 | | 없음 |
| 2 | 결제 시작(오래 걸림) | | 없음 |
| 3 | | `GET` → 없음 | 없음 |
| 4 | | 결제 시작 | 없음 |
| 5 | 주문 저장, 응답 기록 | 주문 저장, 응답 기록 | 나중에 쓴 것 |

결제 두 번, 주문 두 건입니다. 두 가지가 겹쳤습니다.

- **확인과 기록 사이에 틈이 있습니다.** 1단계의 확인과 5단계의 기록 사이에 다른 서버가 끼어들 수 있습니다. 확인 후 행동형 경쟁 상태입니다.
- **"끝났다"만 기록합니다.** A가 처리하는 몇 초 동안 Redis에는 아무 흔적이 없습니다. 그런데 B가 오는 때가 바로 그 몇 초입니다. 앱이 타임아웃으로 다시 보낸 요청은 대개 원래 요청이 **아직 처리 중일 때** 도착하기 때문입니다.

그래서 기록은 처리를 **시작할 때** 남겨야 하고, 확인과 기록이 명령 하나여야 합니다.

## SET NX로 처리 시작을 먼저 기록합니다

### 명령 하나로 "없으면 만들고 기한을 붙입니다"

S1은 처리를 시작하기 전에 다음 명령 하나를 보냅니다.

`SET idem:u42:K1 <처리 중 기록> NX GET PX 60000`

- **`NX`**: 키가 없을 때만 저장합니다. 두 서버가 동시에 보내도 메인 스레드가 하나씩 실행하므로 하나만 저장에 성공합니다. 분산 락을 거는 명령과 같은 구조이고, 그 원리는 [Redis 분산 락](./distributed-lock.md)의 "락을 거는 명령: SET NX PX 하나로 '없으면 만들고 기한을 붙입니다'"에서 다룹니다.
- **`GET`**: 저장 전의 값을 돌려줍니다. `NX`와 함께 쓰면, 키가 없어 저장했을 때는 nil을, 키가 이미 있어 저장하지 않았을 때는 **이미 있던 값**을 돌려줍니다. 그래서 명령 하나로 "내가 처음인가"와 "처음이 아니라면 지금 상태가 무엇인가"를 함께 알 수 있습니다. 이미 있던 값이 String이 아니면 에러가 납니다.
- **`PX 60000`**: 처리 중 기록의 기한입니다. 값을 정하는 기준은 "처리 중 기록의 기한은 리스입니다"에서 다룹니다.

`GET` 없이 `SET … NX PX`만 보내면 저장 여부(`OK` 또는 nil)만 알 수 있으므로, 실패했을 때 `GET`을 한 번 더 보내 상태를 읽어야 합니다. 그 사이에 키가 만료되거나 바뀔 수 있으므로, 읽은 결과가 nil이면 처음부터 다시 시도합니다.

### 기록에 담는 것

처리 중 기록과 완료 기록은 같은 키에 쓰고, 값(예: JSON 문자열)에 다음을 담습니다.

| 필드 | 처리 중 | 완료 | 쓰임 |
| --- | --- | --- | --- |
| 상태 | `IN_PROGRESS` | `COMPLETED` | 다시 온 요청에 409를 줄지, 저장한 응답을 줄지 |
| 요청 지문 | 본문의 해시 | 같음 | 같은 키로 다른 본문이 오면 422 |
| 주인 토큰 | 이번 처리 시도의 무작위 값 | (지워도 됨) | 완료 기록을 쓸 자격 확인, 자기 명령의 재전송 구분 |
| 응답 | 없음 | 상태 코드, 본문(주문 번호 등) | 다시 온 요청에 같은 응답 돌려주기 |

키 이름에는 사용자(또는 API 클라이언트) 식별자를 넣습니다. 멱등 키는 클라이언트가 만드는 값이므로, 서로 다른 사용자가 우연히 또는 고의로 같은 값을 보내도 남의 기록을 보지 못하게 하기 위해서입니다.

### 예시를 넣으면

| 순서 | S1 (요청 A) | S2 (요청 B) | Redis `idem:u42:K1` |
| --- | --- | --- | --- |
| 1 | `SET … NX GET PX 60000` → nil (내가 처음) | | `IN_PROGRESS`, 토큰 t1 |
| 2 | 결제, 주문 저장 진행 중 | | `IN_PROGRESS` |
| 3 | | `SET … NX GET PX 60000` → `IN_PROGRESS` 기록 | `IN_PROGRESS` |
| 4 | | 지문 비교: 같음 → **409** 응답 | `IN_PROGRESS` |
| 5 | 완료 기록 쓰기(다음 절), 201 응답 | | `COMPLETED`, 주문 번호 |
| 6 | | (앱이 조금 뒤 같은 `K1`로 C를 다시 보냄) → `COMPLETED` 기록 | `COMPLETED` |
| 7 | | 지문 같음 → 저장된 201 응답과 주문 번호 반환 | `COMPLETED` |

결제와 주문은 한 번입니다. 앱은 409를 받으면 잠시 뒤 같은 키로 다시 보내고, 결국 원래 응답을 받습니다. 409에 대해 초안은 클라이언트가 요청을 고칠 필요가 없다고 적습니다(2.7절).

### 기록에는 주인 토큰을 넣습니다

S1이 보낸 `SET … NX GET`이 서버에서 실행된 직후 연결이 끊기면, Lettuce는 응답을 받지 못한 그 명령을 다시 연결된 뒤 한 번 더 보낼 수 있습니다. 두 번째 실행은 첫 번째가 만든 키를 보고 이미 있던 값을 돌려줍니다. 기록에 주인이 없다면 S1은 **자기가 만든 기록**을 보고 "다른 요청이 처리 중"이라며 409를 응답하고, 정작 아무도 처리하지 않습니다. 기록에 이번 시도의 토큰을 넣어 두면, 돌려받은 값의 토큰이 자기 것인지 보고 "내 기록"임을 알 수 있습니다(이 문서의 설계).

## 처리 중에서 완료로: 응답을 기록합니다

### 완료 기록은 "아직 내 기록일 때만" 씁니다

처리가 끝나면 S1은 상태를 `COMPLETED`로 바꾸고 응답을 담습니다. 이때 그냥 `SET`으로 덮어쓰면 안 됩니다. S1이 오래 멈춘 사이 처리 중 기록이 만료되어 다른 서버가 새 처리 중 기록을 만들었을 수 있기 때문입니다(다음 절). 그래서 "기록의 토큰이 t1이면 완료 기록으로 바꾸고 기한을 새로 붙인다"를 Lua 스크립트 하나로 합니다. 이 스크립트는 앱이 아니라 Redis 서버 안에서 실행되고, 스크립트 하나가 끝날 때까지 다른 연결의 명령이 끼어들지 않습니다. 앱 코드의 함수 하나에 명령 두 개를 묶는 것과 다릅니다. 확인과 쓰기 사이에 다른 명령이 끼어들지 않게 하는 이유는 분산 락의 해제 스크립트와 같습니다([Redis 분산 락](./distributed-lock.md)의 "확인과 삭제를 Lua 스크립트 하나로 묶습니다").

스크립트가 "내 기록이 아님"을 돌려주면, S1의 처리와 다른 서버의 처리가 겹쳤을 수 있다는 신호입니다. 이 경우는 Redis만으로 되돌릴 수 없고, "Redis만으로는 부족한 곳: DB 고유 제약"의 장치가 막아야 합니다. 로그와 지표로 남깁니다.

### 어떤 응답을 저장하는가

- **성공 응답과, 다시 해도 같은 결과일 실패(예: 본문 검증 실패)** 는 저장해 같은 응답을 돌려줍니다. 초안도 원래 처리와 일관된 응답을 권합니다.
- **아무것도 바꾸지 않았다고 확신하는 일시적 실패**(예: 결제를 부르기 전에 DB 연결을 못 얻음)는 기록을 지워, 다음 재시도가 처음부터 처리하게 합니다. 이때도 토큰을 확인하고 지웁니다. 실패를 저장해 버리면, 클라이언트가 고쳐지지 않는 실패를 계속 받습니다.
- **결과를 모르는 실패**(예: 결제사 호출이 타임아웃)는 지우면 안 됩니다. 결제사에서는 이미 결제됐을 수 있으므로, 지우면 다음 재시도가 두 번째 결제를 합니다. 처리 중으로 두거나 "확인 필요" 상태로 바꾸고, 결제사에 조회하거나 결제사의 멱등 키 기능으로 정리합니다. 결제사가 멱등 키를 받는다면 `K1`에서 만든 값을 그대로 넘겨, 바깥 시스템도 같은 요청을 한 번만 처리하게 합니다.
  다만 처리 중으로만 두면 그 기록은 리스라서 기한이 지나면 사라지고, 그 뒤 재시도는 "내가 처음"으로 결제를 다시 부릅니다. 결과를 확인하기 전의 재실행을 끝까지 막는 것은 Redis 기한이 아니라 결제사의 멱등 키(결제사가 그 키를 기억하는 기간 안에서는 같은 키로 다시 불러도 한 번만 결제)나 DB의 결제 시도 행입니다("그럼 Redis는 왜 두는가"). 결제 시도 행은 남기기만 해서는 막지 못합니다. 결제를 부르기 전에 그 행을 커밋하고, 같은 키에 결과가 확정되지 않은 시도 행이 있으면 재시도는 결제를 부르지 않고 결과 조회로 넘어가게 해야 합니다. "확인 필요" 상태를 Redis에 둔다면 처리 중 리스의 짧은 기한을 그대로 두지 말고, 확인이 끝날 때까지 남을 만큼의 기한을 따로 붙입니다.
- 응답 본문이 크면 키 하나가 커집니다. 다시 온 요청에 필요한 최소한(상태 코드, 주문 번호 같은 식별자)만 저장하고 나머지는 DB에서 읽게 하는 방법이 있습니다. 개인정보나 결제 정보가 담긴 응답을 Redis에 그대로 두는 것이 허용되는지도 확인합니다.

## TTL과 장애는 보장의 범위를 정합니다

Redis 기록에는 두 기한이 있고, 둘은 서로 다른 것을 정합니다.

### 처리 중 기록의 기한은 리스입니다

처리 중 기록에 기한이 없다면, S1이 처리 도중 죽었을 때 `K1`은 영원히 "처리 중"으로 남아 모든 재시도가 409를 받습니다. 그래서 기한을 붙입니다. 그런데 기한은 "S1이 죽었다"가 아니라 "그 시간이 지났다"를 뜻할 뿐입니다.

| 순서 | S1 (요청 A) | S2 (요청 B') | `idem:u42:K1` |
| --- | --- | --- | --- |
| 1 | 처리 중 기록(토큰 t1, 60초) | | `IN_PROGRESS` t1 |
| 2 | 결제사 응답이 70초 걸림 | | `IN_PROGRESS` t1 |
| 3 | | (60초 뒤) `SET … NX GET` → nil, 내가 처음 | `IN_PROGRESS` t2 |
| 4 | 결제 완료 | 결제 시작 → **두 번째 결제** | |
| 5 | 완료 기록 스크립트 → "내 기록 아님" | | |

리스의 빈틈 그대로입니다. 기한을 길게 잡으면 겹칠 가능성은 줄지만, S1이 정말 죽었을 때 사용자는 그만큼 오래 409를 받습니다. 기한은 **처리 하나가 걸리는 최대 시간**, 특히 그 안의 외부 호출 타임아웃의 합보다 길게 잡습니다. 그래도 GC 정지나 네트워크 지연처럼 예상 밖의 멈춤은 막지 못하므로, 겹침을 최종적으로 막는 장치는 따로 둡니다.

### 완료 기록의 기한은 "얼마 동안의 재시도까지 지키는가"입니다

완료 기록이 만료되면 그 뒤에 온 같은 `K1` 요청은 처음 온 요청으로 처리됩니다. 그래서 Redis만으로 판단한다면 완료 기록의 기한이 곧 **멱등성을 보장하는 기간**입니다. 뒤의 "Redis만으로는 부족한 곳: DB 고유 제약"처럼 DB에도 키를 남기면, 최종 보장 기간은 DB의 키 행을 보존하는 기간이 정하고 Redis 기한은 "저장한 응답을 빠르게 돌려주는 기간"이 됩니다.

- 기한은 클라이언트가 같은 키로 다시 보낼 수 있는 가장 긴 시간보다 길어야 합니다. 앱의 재시도 정책, 오프라인이던 앱이 나중에 다시 보내는 경우, 게이트웨이나 큐의 재전송을 모두 더해 봅니다. 앱이 하루 뒤에도 다시 보낼 수 있다면 기한은 하루보다 길어야 합니다.
- 길게 잡으면 기록이 그만큼 쌓입니다. 같은 키의 재시도는 새 기록을 만들지 않으므로, 새 키가 들어오는 속도가 일정하다면 기록 수는 "초당 새 멱등 키 수 × 기한(초)"입니다. 키 하나의 크기는 `MEMORY USAGE`로 재서 곱해 봅니다. 응답을 크게 저장할수록 이 곱이 커집니다.
- 초안은 이 기한을 API 문서로 공개하라고 권합니다. 클라이언트가 "언제까지 같은 키로 재시도해도 안전한가"를 알 수 있게 하기 위해서입니다.

### 기한 전에도 기록은 사라질 수 있습니다

TTL은 "적어도 그때까지 남는다"는 약속이 아닙니다. 다음 경우 기한 전에 기록이 사라지고, 그 뒤의 재시도는 다시 실행됩니다.

- **메모리 축출**: `allkeys-*` 정책이면 모든 키가 후보입니다. `volatile-*` 정책이면 TTL 있는 키만 후보인데, 멱등 기록은 모두 TTL이 있으므로 **우선 후보**가 됩니다. TTL 없는 캐시가 함께 있는 Redis라면 멱등 기록이 먼저 지워질 수 있습니다. `noeviction`이면 지워지지는 않지만 메모리가 가득 찰 때 `SET`이 OOM 에러를 받아 처리를 시작할 수 없습니다. 정책별 동작은 [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.
- **장애 조치**: 주 서버는 쓰기를 복제본에 복사하지만 복사가 끝나기를 기다리지 않고 응답합니다(비동기 복제). 주 서버가 죽으면 복제본 하나를 새 주 서버로 올리는데(장애 조치), 이때 새 주 서버가 가진 데이터가 새 기준이 됩니다. 그래서 주 서버가 응답한 처리 중·완료 기록이 복제본에 닿기 전에 장애 조치가 일어나면 그 기록을 잃습니다. 새 주 서버에는 `K1`이 없으므로 재시도가 다시 처리됩니다. 복제본이 쓰기를 받았다고 확인할 때까지 기다리는 `WAIT` 명령은 잃는 구간을 줄일 뿐 없애지 못합니다. Redis 복제에서 다룹니다.
- **재시작**: 영속성을 끈 Redis가 다시 시작하면 모든 기록을 잃습니다. 영속성을 켜도 마지막 저장 이후의 기록은 잃을 수 있습니다. [Redis 영속성](./persistence.md)에서 다룹니다.
- **시계**: 만료는 Redis 서버의 벽시계로 판정하므로, 서버 시각이 앞으로 뛰면 기록이 일찍 만료됩니다.

그래서 Redis 기록만으로 지킬 수 있는 것은 "Redis가 정상이고, 처리 시간이 기한 안이며, 재시도가 보장 기간 안에 온 경우"의 한 번 실행입니다. 이것으로 대부분의 재시도를 싸게 걸러 낼 수 있지만, 결제처럼 두 번 일어나면 안 되는 일의 정확성을 이것에만 맡기면 안 됩니다.

## Redis만으로는 부족한 곳: DB 고유 제약

### 기록과 처리가 다른 저장소에 있습니다

예시에서 처리의 결과(주문 행)는 주문 DB에, "처리했다"는 기록은 Redis에 있습니다. 두 저장소의 쓰기는 한 번에 일어나지 않습니다. S1이 주문을 커밋한 직후, 완료 기록을 쓰기 전에 죽으면 Redis에는 처리 중 기록만 남습니다. 그 기록이 만료된 뒤 온 재시도는 Redis만 보고 처음 온 요청으로 처리해 **주문 두 건**을 만듭니다. 이 틈은 Redis 쪽 장치를 아무리 다듬어도 없어지지 않습니다. 서로 다른 저장소의 쓰기를 묶을 수 없다는 일반 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)의 "원자성이 보장하지 않는 것"에서 다룹니다.

### 처리 결과와 같은 트랜잭션에 키를 남깁니다

해법은 "처리했다"는 사실을 **처리 결과와 같은 저장소, 같은 트랜잭션**에 남기는 것입니다.

- 주문 테이블에 (사용자, 멱등 키) 고유 제약을 둡니다. 또는 멱등 키 테이블을 따로 두고, 주문 저장과 같은 DB 트랜잭션에서 그 테이블에 키를 넣습니다.
- 두 처리가 겹쳐도 두 번째 트랜잭션은 키 행을 넣는 순간 고유 제약 위반으로 실패하고(상대 트랜잭션이 아직 커밋 전이면 그 결과를 기다린 뒤) 롤백되므로 주문은 한 건입니다. 검사 시점은 DB와 제약 설정에 따라 다르므로 쓰는 DB의 문서로 확인합니다.
- 실패한 쪽은 기존 주문을 읽어 그 결과로 응답합니다. 다만 Redis 기록을 잃은 뒤라면 같은 키에 **다른 본문**이 왔는지 Redis로는 알 수 없으므로, DB의 키 행에도 요청 지문을 저장해 두고 다르면 422로 거절합니다.
- 이 장치는 Redis 기록이 축출·장애 조치·재시작으로 사라져도, 처리 중 리스가 겹쳐도 그대로 작동합니다. 대신 DB 쓰기마다 고유 인덱스 확인 비용이 들고, 멱등 키 행을 언제 지울지 정해야 합니다.

### 그럼 Redis는 왜 두는가

DB 고유 제약이 최종 판정을 맡으면, Redis 기록의 역할은 정확성이 아니라 **효율**이 됩니다.

- **겹침을 앞에서 줄입니다.** 고유 제약은 키 행을 넣는 쓰기에서만 두 번째를 거절하므로, 앱이 그 쓰기보다 먼저 한 일(외부 결제 호출 등)은 이미 두 번 일어났을 수 있습니다. Redis의 처리 중 기록은 대부분의 동시 재시도를 처리 시작 전에 409로 돌려보내, 비싼 작업이 겹치는 일을 크게 줄입니다.
- **다시 온 요청에 DB를 거치지 않고 응답합니다.** 완료 기록에 담은 응답을 바로 돌려줍니다.

외부 결제처럼 DB 트랜잭션에 묶을 수 없는 부수 효과는 고유 제약으로도 막지 못합니다. 결제사가 멱등 키를 받는다면 그 기능이 마지막 장치이고, 받지 않는다면 결제 전에 "결제 시도" 행을 DB에 먼저 남기고 결과를 조회해 맞추는 정합성 점검(대사)이 필요합니다. 대사는 두 번째 결제를 미리 막지 못하고, 생긴 뒤에 찾아 취소·환불하는 사후 복구입니다. 이 효율용·정확성용의 구분은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "효율을 위한 락과 정확성을 위한 락"과 같은 판단입니다.

| 장치 | 막는 것 | 막지 못하는 것 |
| --- | --- | --- |
| Redis 처리 중 기록(`SET NX`) | 처리 중에 온 동시 재시도 대부분 | 기한보다 오래 걸린 처리, 기록을 잃은 경우 |
| Redis 완료 기록 | 보장 기간 안에 온 재시도. 응답을 빠르게 재사용 | 기한 뒤의 재시도, 축출·장애 조치로 잃은 기록, DB 커밋 뒤 기록 전에 죽은 경우 |
| DB 고유 제약(같은 트랜잭션) | 같은 키로 주문이 두 건 생기는 모든 경우 | 트랜잭션 밖의 부수 효과(외부 결제 호출) |
| 바깥 시스템의 멱등 키 | 그 시스템 안의 중복 처리 | 그 기능이 없는 시스템 |

## 요청과 데이터가 늘면 무엇이 달라지는가

- **기록 수는 "초당 새 멱등 키 수 × 완료 기록 기한(초)"입니다.** 재시도는 새 기록을 만들지 않습니다. 새 요청이 열 배가 되거나 보장 기간을 열 배로 늘리면 기록도 열 배입니다. 응답 본문을 저장하면 키 하나가 커져 곱이 함께 커집니다.
- **요청마다 Redis 왕복이 시작에 1번, 끝에 1번 붙습니다.** `SET … NX GET`을 쓰면 다시 온 요청은 시작의 1번으로 끝납니다. `setIfAbsent`처럼 저장 여부만 받는 방식이면 상태를 읽는 `GET` 1번이 더 붙습니다.
- **무작위로 만든 멱등 키는 클러스터의 슬롯에 고르게 퍼질 것을 기대할 수 있습니다.** 클러스터는 키 이름의 해시값으로 키마다 슬롯을 정하고 슬롯을 노드에 배정합니다. 키 이름의 중괄호 부분(해시 태그)이 있으면 그 부분만으로 슬롯을 정합니다. 처리 중 기록과 완료 기록을 같은 키에 쓰면 스크립트도 키 하나만 다루므로 슬롯 문제가 없습니다. 기록과 다른 키(예: 사용자별 집계)를 한 스크립트에서 함께 바꾸면 해시 태그로 같은 슬롯에 묶어야 합니다.
- **처리 시간이 길어지면 처리 중 기한을 다시 봐야 합니다.** 외부 API가 느려져 처리 시간이 기한에 가까워지면 리스가 겹치는 일이 늘어납니다. "완료 기록 스크립트가 내 기록이 아니라고 답한 횟수"가 그 가능성을 보여 주는 신호입니다(다른 서버가 끼어들지 않고 기록만 만료된 경우에도 늘 수 있습니다).

## 흔한 오해 모아 보기

| 오해 | 실제 | 처음 다룬 곳 |
| --- | --- | --- |
| 처리가 끝난 뒤에 기록하면 된다 | 다시 온 요청은 대개 원래 요청이 처리 중일 때 오므로, 시작할 때 기록해야 합니다 | 확인하고 처리하면 왜 두 번 실행되는가 |
| `GET`으로 확인하고 `SET`으로 기록하면 된다 | 사이에 다른 서버가 끼어듭니다. `SET NX` 하나로 해야 합니다 | 확인하고 처리하면 왜 두 번 실행되는가 |
| 기록이 있으면 무조건 저장된 응답을 돌려준다 | 처리 중이면 409, 본문이 다르면 422, 자기 명령의 재전송이면 자기 기록입니다 | 예시를 넣으면, 주인 토큰 |
| 실패하면 기록을 지우면 된다 | 결과를 모르는 실패(결제 타임아웃)에서 지우면 두 번 결제됩니다 | 어떤 응답을 저장하는가 |
| TTL 동안은 기록이 남는다 | 축출, 장애 조치, 재시작, 시계 이동으로 기한 전에 사라질 수 있습니다 | 기한 전에도 기록은 사라질 수 있습니다 |
| `volatile-*` 정책이면 TTL 있는 기록은 안전하다 | TTL 있는 키만 후보이므로 멱등 기록이 오히려 우선 후보입니다 | 기한 전에도 기록은 사라질 수 있습니다 |
| Redis 멱등 기록이면 한 번 실행이 보장된다 | Redis와 DB는 함께 커밋되지 않습니다. 최종 판정은 DB 고유 제약이 맡아야 합니다 | Redis만으로는 부족한 곳 |

## 실무 포인트

### 어떤 방식을 고를까

| 상황 | 선택 | 이유 |
| --- | --- | --- |
| 부수 효과가 Redis 안의 값 하나뿐(재고 차감 등) | 기록과 변경을 한 Lua 스크립트로 | 같은 저장소라 한 번에 묶입니다([Redis 원자성](./atomicity.md)) |
| 결과가 DB에 남는 생성 API | DB 고유 제약을 최종 장치로, Redis 기록을 앞단 걸러내기로 | Redis와 DB는 함께 커밋되지 않습니다 |
| 결과가 DB에만 남고 동시 재시도가 드묾 | DB 고유 제약만 | Redis를 빼면 장애 지점과 왕복이 줄어듭니다. 겹친 처리의 비용이 작을 때 맞습니다 |
| 외부 결제·발송이 끼어 있음 | 위에 더해 바깥 시스템의 멱등 키, 없으면 결제 시도 기록과 대사 | 트랜잭션 밖의 부수 효과는 고유 제약으로 막을 수 없습니다 |

### 중요도별 점검 항목

- **필수**(Redis 기록을 쓴다면): 처리 시작 전에 `SET … NX`로 처리 중 기록을 남기는가. 확인과 기록이 명령 하나인가.
- **필수**: 최종 정확성을 DB 고유 제약(또는 처리 결과와 같은 트랜잭션의 키 기록)이 맡는가. Redis 기록이 사라져도 두 번 생기지 않는가.
- **필수**: 최종 보장 기간(DB에 키를 남기면 그 행의 보존 기간, Redis만 쓰면 완료 기록의 기한)이 클라이언트가 재시도할 수 있는 가장 긴 시간보다 긴가. 그 기한을 API 문서로 공개했는가.
- **필수**: 결과를 모르는 실패에서 기록을 지우지 않는가.
- **알면 유리**: 처리 중 기한이 외부 호출 타임아웃의 합보다 긴가. 기록에 주인 토큰을 넣고, 완료 기록을 토큰 확인 후 스크립트로 쓰는가.
- **알면 유리**: 같은 키에 다른 본문이 오면 422로 거절하도록 지문을 저장하는가. 키 이름에 사용자 식별자를 넣었는가.
- **참고**: 멱등 기록을 TTL 없는 캐시와 같은 Redis에 `volatile-*` 정책으로 두지 않는가. 둔다면 기록이 우선 축출된다는 점을 받아들였는가.

### 관찰할 것

- 409 응답 수(처리 중 재시도), 저장된 응답으로 답한 수(완료 뒤 재시도), 422 수(키 재사용).
- 완료 기록 스크립트가 "내 기록 아님"을 돌려준 수. 처리 중 리스가 겹쳤을 가능성을 보여 줍니다. 실제 겹침인지는 같은 키로 두 번 처리된 흔적(결제·주문 로그)으로 확인합니다.
- DB 고유 제약 위반 수. Redis가 걸러 내지 못한 중복이 최종 장치에 닿은 횟수입니다. 장애 조치나 축출 직후 늘면 Redis 기록을 잃었을 가능성을 먼저 의심하고, `evicted_keys`와 장애 조치 시각을 대조합니다.
- 멱등 기록 키 수와 `MEMORY USAGE`로 잰 키 하나의 크기, `evicted_keys`.

### 증상과 대응

| 증상 | 먼저 확인할 것 | 대응과 부작용 |
| --- | --- | --- |
| 같은 주문이 두 건 생김 | DB 고유 제약이 있는가, 그 시각에 장애 조치·축출이 있었는가 | 고유 제약을 추가합니다. 기존 중복 데이터 정리가 먼저 필요합니다 |
| 특정 요청이 계속 409를 받음 | 처리 중 기록의 토큰과 남은 기한, 처리한 서버가 죽었는가 | 기한이 지나면 풀립니다. 기한을 줄이면 리스가 겹칠 위험이 커집니다 |
| 재시도했는데 실패 응답만 계속 돌아옴 | 일시적 실패를 완료 기록으로 저장했는가 | 일시적 실패는 기록을 지우도록 바꿉니다. 결과를 모르는 실패는 지우지 않습니다 |
| 결제는 두 번, 주문은 한 건 | 결제 호출이 처리 중 리스보다 오래 걸렸는가, 결제사 멱등 키를 넘기는가 | 결제사 멱등 키를 넘기고, 처리 중 기한을 결제 타임아웃보다 길게 잡습니다 |
| Redis 메모리가 계속 증가 | 완료 기록의 기한과 저장한 응답 크기 | 응답을 식별자 위주로 줄이고, 보장 기간을 문서와 맞춥니다 |

### Spring에서 확인할 것

- `opsForValue().setIfAbsent(key, value, timeout, unit)`는 `SET … NX` 명령 하나를 보내므로 처리 중 기록에 쓸 수 있습니다. 다만 즉시 실행할 때 저장 여부만 돌려주므로(파이프라인이나 Redis 트랜잭션 안에서는 null), `false`면 `get`으로 상태를 한 번 더 읽고, 그 결과가 null이면(그사이 만료) 다시 시도합니다. 한 번에 읽으려면 `SET … NX GET`을 스크립트나 저수준 명령으로 보냅니다.
- 완료 기록은 `opsForValue().set(...)`로 덮어쓰지 말고 토큰을 확인하는 스크립트로 씁니다. 옵션 없는 `set`은 기한도 지웁니다([TTL과 축출](./ttl-and-eviction.md)).
- 기록 값을 직렬화하는 방식이 서버마다 같아야 다른 서버가 쓴 기록을 읽을 수 있습니다. 배포 중 두 버전이 함께 돌 때 특히 확인합니다. 직렬화의 선택은 [Redis 직렬화](./serializer.md)에서 다룹니다.
- 주문 저장과 멱등 키 행 삽입을 같은 `@Transactional` 안에서 하고, 고유 제약 위반 예외를 "이미 처리됨"으로 바꿔 기존 결과를 돌려줍니다. 이 예외는 그 트랜잭션이 끝난 바깥에서 받고, 기존 주문은 새 트랜잭션에서 읽습니다. 호출하는 쪽 메서드도 같은 트랜잭션에 참여하고 있다면(기본 전파) 그곳도 아직 실패한 트랜잭션 안입니다. 위반이 난 트랜잭션은 롤백되고, DB에 따라(예: PostgreSQL) 같은 트랜잭션의 이후 쿼리도 실패하기 때문입니다. JPA는 저장을 flush나 커밋 때 DB에 보내므로, 위반 예외가 메서드가 끝난 뒤에야 나올 수도 있습니다. 또 멱등 키 제약의 위반일 때만 "이미 처리됨"으로 바꿉니다. 다른 고유 제약의 위반까지 바꾸면 진짜 오류를 숨깁니다.
- Redis 완료 기록은 DB 트랜잭션에 묶이지 않으므로 커밋이 끝난 뒤에 씁니다. 기본 `RedisTemplate`은 명령을 즉시 보내므로, 트랜잭션 안에서 먼저 쓰면 그 뒤 커밋이 실패해 주문이 롤백돼도 Redis에는 성공 응답이 남습니다. `RedisTemplate`의 트랜잭션 지원을 켜면 Redis 쓰기를 모아 DB 트랜잭션이 끝날 때 함께 보내거나 버리지만, 이것도 두 저장소를 원자적으로 커밋하지는 않습니다.

## 말로 설명하기

### 30초 버전

멱등 키는 클라이언트가 같은 의도의 요청에 붙이는 고유 값이고, 서버는 처리를 시작할 때 `SET NX`로 "처리 중" 기록을 남겨 동시에 온 재시도에 409를, 끝난 뒤의 재시도에 저장한 응답을 돌려줍니다. 처리 중 기록의 기한은 리스라 처리보다 길어야 하고, Redis만으로 판단하면 완료 기록의 기한이 곧 보장 기간입니다. Redis 기록은 축출·장애 조치로 사라질 수 있고 DB와 함께 커밋되지 않으므로, 최종 판정은 DB 고유 제약이 맡고 Redis는 비싼 작업이 겹치지 않게 하는 효율 장치로 씁니다.

### 2분 버전

타임아웃은 일을 취소하지 않으므로, 앱이 다시 보낸 요청은 대개 원래 요청이 아직 처리 중일 때 도착합니다. 그래서 "끝난 뒤 기록"으로는 막지 못하고, 처리를 시작할 때 기록해야 합니다. 확인과 기록을 `GET`과 `SET`으로 나누면 두 서버가 둘 다 "없음"을 볼 수 있으므로, `SET 키 값 NX GET PX` 명령 하나로 "없으면 처리 중 기록을 만들고, 있으면 그 기록을 돌려받습니다".

돌려받은 기록이 처리 중이면 409, 완료면 저장된 응답, 본문 지문이 다르면 422를 줍니다. 기록에는 주인 토큰을 넣어 Lettuce가 자기 명령을 다시 보낸 경우를 구분하고, 완료 기록은 토큰이 아직 내 것일 때만 스크립트로 씁니다. 실패는 나눠 다룹니다. 아무것도 바꾸지 않은 일시적 실패는 기록을 지우고, 다시 해도 같은 결과일 검증 실패는 저장하고, 결과를 모르는 실패는 지우지 않습니다.

기한은 두 가지입니다. 처리 중 기한은 리스라서, 처리가 그보다 오래 걸리면 재시도가 함께 실행됩니다. 완료 기한은 그 기간 안의 재시도까지만 지킵니다. 그리고 TTL 전에도 축출, 비동기 복제의 장애 조치, 재시작으로 기록이 사라질 수 있습니다. 무엇보다 처리 결과는 DB에, 기록은 Redis에 있어 함께 커밋되지 않습니다. 그래서 같은 트랜잭션에 멱등 키를 남기는 DB 고유 제약이 최종 판정을 맡고, Redis는 대부분의 재시도를 비싼 작업 전에 걸러 내는 역할입니다. 외부 결제처럼 트랜잭션 밖의 부수 효과는 결제사의 멱등 키로 막고, 그 기능이 없으면 대사로 사후에 찾아 복구합니다.

### 예상 질문과 꼬리 질문

**기본 개념과 선택 이유**

- **왜 처리가 끝난 뒤가 아니라 시작할 때 기록하나요?**
  앱이 타임아웃 뒤 다시 보낸 요청은 원래 요청이 아직 처리 중일 때 오는 경우가 많습니다. 끝난 뒤에만 기록하면 그 몇 초 동안 Redis에 흔적이 없어 재시도가 처음 온 요청처럼 처리됩니다(확인하고 처리하면 왜 두 번 실행되는가).
  - **꼬리: 시작할 때 기록하면 서버가 죽었을 때 그 키가 영원히 막히지 않나요?**
    그래서 처리 중 기록에 기한을 붙입니다. 대신 그 기한이 리스가 되어, 처리가 기한보다 오래 걸리면 재시도가 함께 실행될 수 있습니다(처리 중 기록의 기한은 리스입니다).

- **`setIfAbsent`가 true/false만 주는데 `SET NX GET`이 꼭 필요한가요?**
  꼭 필요하지는 않습니다. false면 `GET`을 한 번 더 보내면 됩니다. 다만 두 명령 사이에 기록이 만료될 수 있으므로 `GET`이 null이면 처음부터 다시 시도해야 하고, 왕복이 하나 늡니다(명령 하나로 "없으면 만들고 기한을 붙입니다").

- **처리 중인 기록을 보면 왜 기다리지 않고 409를 주나요?**
  서버가 기다리면 요청 스레드가 묶이고, 원래 처리가 얼마나 걸릴지 모릅니다. 초안도 처리 중 재시도에 409를 권하고, 클라이언트는 요청을 고치지 않고 잠시 뒤 다시 보내면 됩니다(예시를 넣으면).
  - **꼬리: 사용자 입장에서는 409가 실패처럼 보이지 않나요?**
    그래서 클라이언트가 409를 "처리 중"으로 해석해 같은 키로 재시도하도록 API 문서에 정해 둬야 합니다. 서버가 짧게 기다렸다 완료 기록을 확인하는 설계도 가능하지만 스레드를 묶는 대가가 있습니다.

**잘못된 전제와 장애**

- **기록에 왜 주인 토큰이 필요한가요?**
  Lettuce는 연결이 끊겼다 붙으면 응답을 받지 못한 명령을 다시 보냅니다. 첫 `SET … NX GET`이 실행된 뒤 재전송되면 두 번째 실행은 자기 기록을 돌려받으므로, 토큰이 없으면 자기 요청에 409를 주고 아무도 처리하지 않습니다. 완료 기록을 쓸 때도 기한이 지나 남의 기록이 된 것을 덮어쓰지 않게 해 줍니다(기록에는 주인 토큰을 넣습니다).

- **TTL을 24시간으로 잡으면 24시간 동안은 안전한가요?**
  아닙니다. `allkeys-*`나 `volatile-*` 축출, 비동기 복제의 장애 조치, 영속성 설정에 따른 재시작 유실, 서버 시각 이동으로 기한 전에 사라질 수 있습니다. 특히 `volatile-*`에서는 TTL이 있는 멱등 기록이 우선 후보입니다(기한 전에도 기록은 사라질 수 있습니다).
  - **꼬리: 그럼 `noeviction`과 `WAIT`을 쓰면 Redis만으로 충분하지 않나요?**
    축출과 일부 복제 유실은 줄어도, Redis와 DB가 함께 커밋되지 않는 문제는 남습니다. 주문을 커밋한 직후 완료 기록 전에 서버가 죽으면 처리 중 기록이 만료된 뒤 재시도가 두 번째 주문을 만듭니다(기록과 처리가 다른 저장소에 있습니다).

- **결제 타임아웃이 나면 기록을 지우고 다시 하게 해야 하지 않나요?**
  결제사에서는 이미 결제됐을 수 있으므로 지우면 두 번째 결제가 됩니다. 결과를 모르는 실패는 처리 중이나 "확인 필요"로 남기고, 결제사 조회나 결제사의 멱등 키로 정리합니다(어떤 응답을 저장하는가).
  - **꼬리: 처리 중으로 남겨 두면 확인 전까지 안전한가요?**
    아닙니다. 처리 중 기록은 리스라 기한이 지나면 사라지고, 그 뒤 재시도는 결제를 다시 부릅니다. 확인 전 재실행을 끝까지 막는 것은 결제사의 멱등 키나, 결제 전에 커밋해 두고 미확정이면 재시도가 결제 대신 조회로 가게 하는 DB의 결제 시도 행입니다(어떤 응답을 저장하는가).

**대안 비교**

- **DB 고유 제약이 있으면 Redis는 필요 없지 않나요?**
  정확성만 보면 그렇습니다. 하지만 고유 제약은 키 행을 넣는 쓰기에서만 두 번째를 거절하므로, 앱이 그보다 먼저 한 외부 결제 호출 같은 비싼 일은 이미 겹쳤을 수 있습니다. Redis 처리 중 기록은 대부분의 동시 재시도를 처리 전에 돌려보내고, 완료 기록은 DB를 거치지 않고 응답합니다. 동시 재시도가 드물고 겹친 처리가 싸면 Redis를 빼는 것도 합리적입니다(그럼 Redis는 왜 두는가).
  - **꼬리: 고유 제약 위반이 나면 사용자에게 에러를 주나요?**
    아닙니다. "이미 처리됨"으로 해석해 기존 주문을 읽어 원래와 같은 응답을 돌려줍니다. 단, DB에 저장한 요청 지문이 이번 본문과 다르면 같은 키의 재사용이므로 422로 거절합니다.

- **재고 차감처럼 Redis 안에서 끝나는 일도 이렇게 복잡하게 해야 하나요?**
  아닙니다. 기록과 변경이 같은 Redis에 있으므로 Lua 스크립트 하나에서 "이미 처리한 주문인가 확인, 아니면 차감과 기록"을 함께 하면 됩니다. 이 문서의 복잡함은 기록과 처리 결과가 다른 저장소에 있어서 생깁니다(어떤 방식을 고를까).

**데이터 증가와 운영**

- **보장 기간을 7일로 늘리면 무엇을 계산해야 하나요?**
  새 키가 일정하게 들어온다면 기록 수가 "초당 새 멱등 키 수 × 7일(초)"이 됩니다. 키 하나의 크기를 `MEMORY USAGE`로 재서 곱하고, 응답 본문을 식별자 위주로 줄일 수 있는지 봅니다. 길게 보관해야 하는 기록은 DB의 멱등 키 행이 더 맞을 수 있습니다(완료 기록의 기한은 "얼마 동안의 재시도까지 지키는가"입니다).

- **중복이 생겼는지 어떻게 아나요?**
  DB 고유 제약 위반 수와 완료 기록 스크립트의 "내 기록 아님" 수를 봅니다. 앞의 것은 Redis가 놓친 중복이 최종 장치에 닿은 것이고, 뒤의 것은 처리 중 리스가 겹친 신호입니다. 장애 조치나 축출 직후 늘면 Redis 기록을 잃었을 가능성이 높으므로 그 시각과 대조합니다(관찰할 것).

- **Spring에서 주문 저장과 멱등 키를 어떻게 묶나요?**
  같은 `@Transactional` 안에서 주문 행과 멱등 키 행을 쓰고, 멱등 키 제약의 위반 예외를 트랜잭션 바깥에서 받아 "이미 처리됨"으로 바꾼 뒤 기존 주문을 새 트랜잭션에서 읽습니다. 위반이 난 트랜잭션은 롤백되므로 그 안에서 다시 읽을 수 없습니다. Redis 기록은 트랜잭션 밖이므로 커밋 뒤에 완료 기록을 씁니다. 커밋 전에 쓰면 롤백된 주문의 응답이 저장됩니다(Spring에서 확인할 것).

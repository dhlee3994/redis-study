# 기능 레시피: 이미 배운 원리를 엮어 "이 기능을 Redis로 어떻게 만들겠는가"에 답하기

> **핵심 질문**: 인증번호, 접속 상태, 좌석 선점, 알림 중복 방지, 검색어 자동완성처럼 자주 만드는 기능을 Redis로 설계하라고 하면, 키·자료형·만료를 어떻게 정하고 어떤 순서로 명령을 보내며, 어디서 틀어지는가?
>
> **범위**: 다섯 기능의 설계만 다룹니다. 각 레시피는 원리를 다시 설명하지 않고, 원리를 맡은 문서의 결론을 조합합니다. 원리는 한 줄로만 적고 링크합니다. 실행 코드는 넣지 않고 명령 이름 수준으로 순서를 적습니다.
>
> **읽는 법**: 레시피는 서로 독립이므로, 이 문서는 문서 전체에 예시 하나를 쓰지 않고 **레시피마다 작은 예시 하나**를 둡니다. 각 레시피는 같은 순서로 씁니다. 요구사항 → 키 이름·자료형·만료 → 처리 순서 → 빠뜨리기 쉬운 함정 → 판단 이유가 있는 문서.
>
> **출처와 설계의 구분**: 명령의 동작과 복잡도는 "근거"의 소스와 공식 문서로 확인했습니다. 키 이름, 기한, 횟수 같은 값과 처리 순서는 이 문서의 설계이며, 예시의 수치는 모두 가상입니다. 재현해 보지는 않았습니다.

## 배경 지식

다섯 레시피는 같은 원리 몇 개를 서로 다르게 조합합니다. 여기서 한 번만 정의하고, 레시피에서는 이름으로 부릅니다.

- **명령 하나와 스크립트 하나는 끼어들기 없이 실행됩니다.** Redis 노드 하나는 명령을 메인 스레드 하나에서 하나씩 끝까지 실행하므로, 명령 하나나 Lua 스크립트 하나가 도는 동안 다른 연결의 명령이 끼어들지 않습니다. 명령 두 개 사이에는 끼어들 수 있습니다. 그래서 "확인하고 바꾸기"는 명령 하나의 반환값으로 판단하거나 스크립트 하나에 넣습니다. 스크립트는 중간에 에러가 나도 앞의 쓰기를 되돌리지 않으므로 인자 검사를 첫 쓰기 전에 끝냅니다. [Redis 원자성](./atomicity.md)에서 다룹니다.
- **TTL은 키에 붙은 절대 시각이고, 옵션 없는 `SET`은 TTL을 지웁니다.** `SET … EX 180`은 지금부터 180초 뒤의 시각을 키에 붙입니다. 값을 고치는 명령(`INCR`, `HINCRBY`, `HSET`)은 TTL을 그대로 두고, 옵션 없는 `SET`으로 덮어쓰면 TTL이 사라집니다. 만료된 키는 그 시각에 없는 것으로 취급되지만 메모리에서는 나중에 지워질 수 있습니다. [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.
- **`SET … NX EX`는 "없을 때만 만들고 기한을 붙이기"를 명령 하나로 합니다.** 여러 서버가 동시에 보내도 하나만 `OK`를 받고 나머지는 nil을 받습니다. `GET` 옵션을 더하면 만들지 못했을 때 이미 있던 값을 돌려받습니다. [Redis 분산 락](./distributed-lock.md)과 [Redis 멱등 키](./idempotency-key.md)에서 다룹니다.
- **기한이 있는 기록은 리스입니다.** 정해진 시간 동안만 유효한 권리이고, 보유자가 죽어도 기한이 지나면 풀립니다. 대신 보유자가 기한보다 오래 멈추면 자기 권리가 끝난 줄 모르고 일을 계속합니다. 그래서 겹치면 안 되는 일의 마지막 판정은 리스가 아니라 원천(DB 고유 제약, 외부 시스템의 멱등 키)이 맡습니다. [리스와 펜싱 토큰](../cs/lease-and-fencing.md)에서 다룹니다.
- **Redis 기록은 기한 전에도 사라질 수 있습니다.** 메모리 한도의 축출, 장애 조치(복제가 비동기라 응답한 쓰기를 잃을 수 있음), 재시작이 그 길입니다. 그래서 레시피마다 "이 키를 잃으면 무슨 일이 생기는가"를 먼저 정합니다. 경로는 [Redis 멱등 키](./idempotency-key.md)의 "기한 전에도 기록은 사라질 수 있습니다"에 모여 있습니다.
- **클러스터에서는 한 번의 실행이 다루는 키가 같은 슬롯이어야 합니다.** 클러스터는 키를 16,384개의 슬롯 중 하나에 배정하고, 슬롯마다 맡는 노드를 정해 데이터를 여러 노드에 나눕니다. 키 이름의 `{…}` 부분(해시 태그)만으로 슬롯을 정하게 해 맞춥니다. 대신 태그가 같은 키는 모두 한 노드에 몰립니다. [Redis Cluster](./cluster.md)에서 다룹니다.

복잡도 표기 O(…)는 데이터가 커질 때 작업량이 늘어나는 모양입니다. O(1)은 데이터 양과 무관하게 일정하고, O(log N)은 N이 두 배가 될 때 한 단계쯤 늘며, O(N)은 N에 비례합니다. N이 무엇을 세는지는 명령마다 밝힙니다. 실제 시간이 아니며, 앱이 느끼는 지연에는 네트워크 왕복이 더해집니다.

## 인증번호: 키 하나에 번호와 시도 횟수를 담고, 확인과 삭제를 스크립트 하나로

**요구사항**

- 회원 u42가 휴대폰 인증을 요청하면 6자리 번호를 보내고, 3분 안에 입력해야 합니다.
- 틀린 입력은 번호 하나당 5번까지 받습니다.
- 맞게 입력한 번호는 한 번만 쓸 수 있습니다. 같은 번호로 두 요청이 동시에 와도 하나만 성공해야 합니다.
- 재발송은 60초에 한 번, 하루 10번까지입니다.

**예시**: 10:00:00에 u42에게 `483920`을 보냅니다. 10:00:40에 `111111`(틀림), 10:01:10에 `483920`을 입력합니다. 같은 순간 화면의 중복 제출로 `483920`이 한 번 더 옵니다.

**키 이름·자료형·만료**(이 문서의 설계)

| 키 | 자료형 | 값 | 만료 |
| --- | --- | --- | --- |
| `otp:u42` | Hash | `code` = 483920, `phone` = 번호를 보낸 전화번호, `tries` = 0 | 180초 |
| `otp:cool:u42` | String | 아무 값 | 60초 |
| `otp:day:u42:20261111` | String(정수) | 그날 발급 수 | 그날 끝 + 여유 |

번호와 시도 횟수를 키 하나(Hash)에 둔 이유는 확인 스크립트가 키 하나만 다루게 하기 위해서입니다. 그러면 클러스터에서 해시 태그를 고민할 필요가 없습니다. `HINCRBY`는 TTL을 그대로 두므로 시도 횟수를 올려도 만료 시각이 밀리지 않습니다.

**처리 순서**

1. 발급 요청: `SET otp:cool:u42 1 NX EX 60`을 보냅니다. nil이면 "60초 뒤에 다시"로 응답합니다.
2. `INCR otp:day:u42:20261111`의 반환값이 10을 넘으면 거절합니다. 이 카운터의 만료는 [Redis 처리율 제한](./rate-limiting.md)의 "고정 윈도: 창마다 INCR 한 번"과 같은 방식으로 붙입니다.
3. `MULTI`, `HSET otp:u42 code 483920 phone <전화번호> tries 0`, `EXPIRE otp:u42 180`, `EXEC`로 번호를 저장한 뒤 문자를 보냅니다. 앞 결과로 분기할 일이 없으므로 `MULTI`/`EXEC`로 충분합니다. 다만 Spring의 Lettuce 클러스터 연결은 `MULTI`를 서버에 보내기 전에 예외를 던지므로, 클러스터에서는 이 두 명령도 스크립트 하나로 보냅니다([원자성](./atomicity.md)의 "검사 시점이 다르면 실패했을 때 남는 상태가 다릅니다"). 새 번호는 이전 번호와 시도 횟수를 덮어씁니다.
4. 확인 요청: 스크립트 하나가 다음을 합니다. 키가 없으면 "만료"를, `tries`가 5 이상이면 "시도 초과"를 돌려줍니다. 입력이 `code`와 같고 확인 요청의 전화번호가 `phone`과 같으면 `DEL otp:u42` 후 "성공"을, 하나라도 다르면 `HINCRBY otp:u42 tries 1` 후 남은 횟수를 돌려줍니다.

예시에 대면, 10:00:40의 확인은 `tries`를 1로 올립니다. 10:01:10의 두 확인 중 먼저 실행된 스크립트가 "성공"과 함께 키를 지우므로, 다음 스크립트는 키가 없어 "만료"를 받습니다. 한 번만 쓰기가 지켜집니다.

**빠뜨리기 쉬운 함정**

- **읽어서 비교한 뒤 `DEL`하면 같은 번호가 두 번 통과합니다.** 두 요청이 모두 `HGET otp:u42 code`를 끝낸 뒤 `DEL`을 보내면 둘 다 맞다고 판단합니다. 번호를 Hash 대신 String 키 하나에 담는 설계라면 `GETDEL`(String 값을 돌려주고 같은 명령 안에서 키를 지움, String이 아닌 키에는 에러)로 이 틈을 없앨 수 있습니다. 하지만 틀린 입력에도 번호가 지워져 시도 횟수 제한이 의미를 잃습니다. 비교 결과에 따라 지울지 말지를 정해야 하므로 스크립트가 맞습니다.
- **번호는 보낸 대상과 묶어 확인합니다.** 키가 회원 단위라 번호만 비교하면, 확인 요청이 인증할 전화번호를 따로 받는 구현에서 내 휴대폰으로 받은 번호로 남의 전화번호를 인증할 수 있습니다. 그래서 보낸 전화번호를 `phone`에 함께 저장하고 확인 스크립트가 같이 비교합니다. 가입·비밀번호 재설정처럼 용도가 여럿이면 용도를 키 이름에 넣어(`otp:reset:u42`) 한 용도로 받은 번호가 다른 용도에 통하지 않게 합니다.
- **재발송이 시도 횟수를 초기화합니다.** 번호를 새로 받으면 `tries`가 0이 되므로, 발급 횟수에 상한이 없으면 공격자는 번호를 받고 5번 맞혀 보기를 무한히 반복합니다. 발급 상한이 전체 추측 수를 정합니다. 예시의 하루 10번 × 5번이면 하루 최대 50번입니다. 번호를 000000~999999에서 고르게 무작위로 뽑는다면 번호 하나를 5번 안에 맞힐 확률은 많아야 5/1,000,000이고, 하루 동안 한 번이라도 맞힐 확률은 많아야 50/1,000,000, 곧 0.005%입니다. 한 계정이 아니라 여러 계정·여러 전화번호를 노리는 공격은 계정별 상한으로 막지 못하므로 IP·전화번호별 상한을 따로 둡니다. 문자 발송 비용을 노리는 공격도 같은 상한이 막습니다.
- **`volatile-*` 정책에서는 인증번호 키가 먼저 축출 후보가 됩니다.** 모두 TTL이 있기 때문입니다. 잃어도 사용자가 다시 받으면 되므로 원천 DB는 필요 없지만, 축출이 잦으면 "입력했는데 만료"가 늘어납니다. 장애 조치로 `tries` 증가를 잃으면 몇 번 더 맞혀 볼 수 있다는 점도 받아들이는 위험입니다.
- **번호 문자열의 직렬화를 맞춥니다.** 앞자리가 0인 번호(`012345`)를 숫자로 바꾸면 비교가 틀어집니다. 스크립트에 넘기는 값과 Hash에 저장한 값을 같은 문자열 직렬화로 다룹니다. [직렬화기 고르기](./serializer.md)에서 다룹니다.

**판단 이유가 있는 문서**: 스크립트를 고른 이유는 [Redis 원자성](./atomicity.md)의 "Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다", 발급 횟수 카운터의 틈은 [Redis 처리율 제한](./rate-limiting.md)의 "INCR과 EXPIRE 사이의 틈: 기한 없는 카운터가 남습니다", TTL 유지 규칙은 [TTL과 축출](./ttl-and-eviction.md)의 "TTL은 언제 유지되고, 언제 사라지는가"에 있습니다.

## 접속 상태: 하트비트가 기한을 계속 미루고, 기한이 지나면 접속 종료로 봅니다

**요구사항**

- 친구 목록 화면에서 친구마다 "접속 중"을 표시합니다.
- 앱이 강제 종료되거나 네트워크가 끊겨 "나간다"는 신호를 보내지 못해도 언젠가는 접속 종료로 바뀌어야 합니다.

**예시**: u42의 친구는 u1, u2, u3입니다. 앱은 20초마다 하트비트를 보냅니다. u1은 10:00:00에 마지막 하트비트를 보내고 10:00:05에 지하철에서 연결이 끊깁니다.

**키 이름·자료형·만료**(이 문서의 설계)

| 키 | 자료형 | 값 | 만료 |
| --- | --- | --- | --- |
| `online:u1` | String | 접속한 앱 서버나 기기 식별자 | 60초, 하트비트마다 다시 |

이 표는 사용자당 연결 하나를 가정합니다. 여러 기기의 동시 접속을 허용하면 로그아웃 처리가 달라지며, 아래 함정에서 다룹니다.

**처리 순서**

1. 접속할 때와 하트비트마다 `SET online:u1 <기기> EX 60`을 보냅니다. `EX`를 함께 주므로 덮어써도 TTL이 사라지지 않고 60초 뒤로 다시 잡힙니다.
2. 정상 로그아웃이나 앱 종료 신호가 오면 `DEL online:u1`을 보냅니다.
3. 친구 목록은 `MGET online:u1 online:u2 online:u3` 한 번으로 읽고, 값이 있으면 접속 중, nil이면 접속 종료로 표시합니다. `MGET`은 키 수만큼 일하는 O(N)이고, 없는 키에 nil을 돌려줍니다.

예시에서 u1의 키는 10:01:00에 만료됩니다. 실제로는 10:00:05에 떠났지만 친구들은 55초 동안 "접속 중"을 봅니다.

**빠뜨리기 쉬운 함정**

- **접속 종료는 마지막 하트비트부터 최대 TTL만큼 늦게 보입니다.** 이 상한은 그 뒤로 하트비트가 도착하지 않고(다음 항목의 예외), 화면이 상태를 다시 읽는다는 조건에서 성립합니다. 이것이 이 방식의 본질적인 한계입니다. TTL을 하트비트 간격에 가깝게 줄이면 늦게 보이는 시간은 줄지만, 하트비트 하나가 늦거나 빠지기만 해도 접속 중인 사용자가 잠깐 사라졌다 나타납니다. 예시처럼 TTL을 간격의 세 배로 두면 하트비트 두 번을 놓쳐도 버팁니다. 하트비트 간격을 줄이면 쓰기가 늘어납니다. 동시 접속 100,000명이 20초마다 보내면 초당 `SET` 5,000번입니다(가상 수치).
- **로그아웃 뒤에 늦게 도착한 하트비트가 키를 되살립니다.** `DEL` 직후 이미 출발한 하트비트가 도착하면 최대 60초 동안 다시 접속 중으로 보입니다. 하트비트를 `SET … XX EX 60`(키가 있을 때만 쓰기)으로 보내면 되살리지 않지만, 대신 네트워크가 잠깐 끊겨 키가 만료된 사용자는 하트비트로 돌아오지 못하므로, `XX`가 nil을 돌려주면 앱 서버가 연결이 살아 있는지 확인한 뒤 1번의 `SET`을 다시 보내야 합니다.
- **여러 기기로 접속하면 한 기기의 로그아웃이 다른 기기의 접속까지 지웁니다.** 키가 사용자 단위라, PC를 켜 둔 채 휴대폰에서 로그아웃하면 `DEL online:u1`로 친구들에게는 접속 종료로 보입니다. 여러 기기를 허용하면 로그아웃 때 `DEL`하지 않고 만료에 맡기거나(대가: 나간 사용자가 최대 TTL만큼 접속 중으로 보임), 값이 내 기기일 때만 지우는 스크립트를 씁니다. 다만 키에는 마지막으로 하트비트를 보낸 기기 하나만 남으므로, PC가 접속 중이어도 휴대폰이 마지막으로 썼다면 이 스크립트도 키를 지웁니다. 그러면 PC의 다음 하트비트가 키를 다시 만들 때까지, 하트비트가 제때 도착한다면 최대 하트비트 간격만큼 접속 종료로 보입니다. 앞 항목의 `XX` 하트비트를 함께 쓰면 하트비트로는 키가 다시 생기지 않으므로, 앞 항목처럼 앱 서버가 1번의 `SET`을 다시 보내야 합니다.
- **"친구가 방금 접속을 끊었다" 알림을 만료 알림에 맡기지 않습니다.** 키스페이스 알림의 `expired` 이벤트는 TTL이 지난 순간이 아니라 Redis가 실제로 키를 지울 때 나가고, 구독하지 않던 동안의 알림은 사라지며, 클러스터에서는 그 키가 있는 노드에서만 나갑니다. [Redis 세션 저장소](./session-store.md)의 "색인이 기대는 만료 알림과 그 약점"에서 다룹니다. 화면은 다시 읽을 때 상태를 확인하는 방식으로 둡니다.
- **모든 접속 키를 한 슬롯에 모으지 않습니다.** 클러스터에서 `MGET`의 키가 여러 슬롯에 흩어지면 Lettuce가 슬롯별로 나눠 보내 에러 없이 처리합니다. 명령 하나가 키가 흩어진 슬롯 수만큼의 명령으로 늘지만, 해시 태그로 모든 사용자의 접속 키를 한 노드에 모으면 하트비트 쓰기 전체가 그 노드 하나에 몰립니다.
- **접속자 수는 키를 세서 구하지 않습니다.** `SCAN`으로 `online:*`를 훑으면 키 공간 전체를 읽어야 하고, `DBSIZE`는 다른 키까지 셉니다. "지금 접속자 수"는 "최근 1분 동안 하트비트를 보낸 고유 사용자 수"로 바꿔, 하트비트마다 1분 구간의 고유 수 키에 함께 기록합니다. 정확한 Set, 고정 메모리의 HyperLogLog 중 고르는 기준은 [실시간 집계](./realtime-aggregation.md)의 "고유 수: 정확한 Set, 고정 메모리의 HyperLogLog, 번호가 촘촘하면 Bitmap"에 있습니다.
- **마지막 접속 시각은 다른 기록입니다.** "3시간 전 접속"을 보여 주려면 키가 사라진 뒤에도 남는 값이 필요합니다. 만료되는 접속 키에서는 얻을 수 없으므로 DB나 TTL 없는 별도 키에 둡니다.

다른 구성으로 Sorted Set 하나에 사용자를 원소로, 마지막 하트비트 시각을 점수로 두는 방법이 있습니다. 접속자 수를 점수 구간으로 바로 셀 수 있지만, 키 하나가 접속자 수만큼 커지는 빅키이자 모든 하트비트가 몰리는 핫키가 되고, 오래된 원소를 지우는 주기 작업이 필요합니다. 구조는 [Redis 처리율 제한](./rate-limiting.md)의 "슬라이딩 로그: 요청 시각을 모두 적어 둡니다"와 같습니다.

**판단 이유가 있는 문서**: 다중 키 읽기와 클러스터의 나눠 보내기는 [Redis 파이프라이닝과 다중 키 명령](./pipelining.md)의 "다중 키 명령: 명령 하나로 여러 키를 다룹니다"와 "클러스터에서는 슬롯별로 갈립니다", 만료가 실제로 지워지는 시점은 [TTL과 축출](./ttl-and-eviction.md), 한 노드에 몰리는 부하는 [Hot Key와 Big Key](./hot-key-big-key.md)에 있습니다.

## 좌석 선점: 좌석마다 키 하나로 선점하고, 판매 확정은 DB 고유 제약이 정합니다

**요구사항**

- 공연 좌석을 고르면 10분 동안 그 사용자만 결제할 수 있습니다. 10분 안에 결제하지 않으면 좌석이 다시 풀립니다.
- 여러 좌석을 함께 고르면 모두 잡히거나 하나도 잡히지 않아야 합니다.
- 같은 좌석이 두 번 팔리면 안 됩니다.

**예시**: 공연 7의 A12, A13. u1이 10:00:00에 둘을 함께 고르고, u2가 10:00:03에 A13을 고릅니다. u1은 10:09:50에 결제를 누르고, 결제사 승인 결과가 10:10:20에 도착합니다.

**키 이름·자료형·만료**(이 문서의 설계)

| 키 | 자료형 | 값 | 만료 |
| --- | --- | --- | --- |
| `seat:{show:7}:A12` | String | 선점 ID(u1의 이번 선점마다 새로 만든 무작위 값) | 600초 |
| `seat:{show:7}:A13` | String | 같은 선점 ID | 600초 |
| DB `seat_sales(show_id, seat_id)` | 고유 제약 | 판매된 좌석 한 행 | 없음 |

한 공연의 좌석 키는 해시 태그 `{show:7}`로 같은 슬롯에 둡니다. 여러 좌석을 스크립트 하나로 잡으려면 같은 슬롯이어야 하기 때문입니다. 대가로 공연 하나의 선점이 모두 한 노드에 몰립니다. 공연이 여럿이면 공연별로 흩어집니다.

**처리 순서**

1. 선점: 스크립트 하나가 고른 좌석 키를 모두 확인해, 하나라도 있으면 그 좌석을 돌려주고 아무것도 쓰지 않습니다. 모두 비어 있으면 각 키에 `SET <선점 ID> PX 600000`을 합니다. 인자 검사는 첫 쓰기 전에 끝냅니다.
2. 결제 요청 직전: 스크립트로 "값이 내 선점 ID면 기한을 결제 제한 시간만큼 늘린다"를 실행합니다. 내 선점이 아니면 결제로 보내지 않습니다.
3. 결제 승인 뒤: DB 트랜잭션에서 `seat_sales`에 좌석 행을 넣고 주문을 확정합니다. 고유 제약 위반이면 이미 팔린 좌석이므로 결제를 취소(환불)합니다.
4. 커밋에 성공하면 `SET seat:{show:7}:A12 SOLD`를 옵션 없이 보내 TTL 없는 "판매됨" 표시로 바꿉니다. 여기서는 옵션 없는 `SET`이 TTL을 지우는 성질을 일부러 씁니다. 선점 ID를 확인하지 않는 이유는 DB가 이미 이 좌석의 주인을 정했기 때문입니다.
5. 사용자가 선택을 취소하면 "값이 내 선점 ID일 때만 지우기"를 스크립트로 보냅니다. 그냥 `DEL`하면 기한이 지나 남이 새로 잡은 선점을 지울 수 있습니다.
6. 좌석 배치도는 DB의 판매 좌석에 `MGET`으로 읽은 선점 상태를 겹쳐 그립니다.

예시에 대면, 10:00:03에 u2의 선점은 A13이 있으므로 실패합니다. u1의 키는 10:10:00에 만료됩니다. 10:09:50의 2단계가 기한을 늘렸다면 결제 승인이 10:10:20에 와도 좌석은 u1의 것입니다.

**빠뜨리기 쉬운 함정**

- **기한이 지난 뒤에 결제가 끝날 수 있습니다.** 2단계를 하지 않았거나, 늘린 기한보다 결제가 더 늦으면 다음처럼 됩니다.

  | 시각 | u1 | u3 | `seat:{show:7}:A13` | DB |
  | --- | --- | --- | --- | --- |
  | 10:09:50 | 결제 요청 | | u1의 선점 | |
  | 10:10:00 | (결제 대기) | | 만료 | |
  | 10:10:05 | | 선점 성공, 결제 요청 | u3의 선점 | |
  | 10:10:20 | 승인 → `seat_sales` 넣기 성공 | | `SOLD` | A13 판매(u1) |
  | 10:10:40 | | 승인 → 고유 제약 위반 → 결제 취소 | `SOLD` | |

  두 번 팔리지는 않습니다. 고유 제약이 먼저 커밋한 쪽만 남기기 때문입니다. 대신 u3은 결제했다가 환불을 받습니다. Redis 선점은 리스이므로 이 겹침을 줄일 수는 있어도 없앨 수 없습니다. 기한의 길이가 겹침과 묶인 좌석을 맞바꾸는 구조는 [Redis 재고 예약과 DB 주문 확정](./stock-reservation.md)의 "예약 기한은 두 위험을 맞바꿉니다"와 같습니다. "10분 안에 결제하지 않으면 무효"를 업무 규칙으로 지켜야 하면, DB 트랜잭션이 커밋할 때 그 기한을 함께 확인합니다.
- **수량 조건으로는 좌석을 지키지 못합니다.** 재고 예약처럼 "남은 수량 > 0"만 확인하면 같은 좌석의 두 행을 막지 못합니다. 좌석은 주인이 정해지는 재고라 좌석 단위의 고유 제약이 최종 방어선입니다.
- **Redis가 선점이나 판매 표시를 잃어도 두 번 팔리지는 않지만, 헛걸음이 생깁니다.** 장애 조치로 `SOLD` 표시를 잃으면 이미 팔린 좌석에 새 선점이 성공하고, 그 사용자는 결제 뒤 3단계에서 환불을 받습니다. 결제사의 승인 전에 DB의 판매 여부를 한 번 확인하면 환불 건수는 줄어듭니다. 이 확인도 승인 사이의 틈은 막지 못합니다.
- **인기 공연에서는 실패할 선점과 배치도 반복 조회가 요청의 대부분이 됩니다.** 수만 명이 같은 좌석을 동시에 누르면 한 좌석에 성공하는 요청은 하나뿐이고, 나머지는 실패한 뒤 배치도를 다시 읽고 다시 누릅니다(이 문서의 추론이며 재지 않았습니다). 입장 인원을 제한하는 대기열을 앞에 둡니다. [Redis 입장 대기열](./waiting-queue.md)에서 다룹니다.

Redis 없이 DB 좌석 행에 `hold_until` 열을 두고 조건부 `UPDATE`로 선점하는 방법도 정확합니다. Redis를 쓰는 이유는 자동 만료와 배치도 조회 부하를 DB에서 떼어 내기 위해서이고, 그 대가가 위의 두 저장소 사이의 틈입니다.

**판단 이유가 있는 문서**: 원천을 DB에 두는 판단은 [Redis 재고 예약과 DB 주문 확정](./stock-reservation.md)의 "원천은 DB에 둡니다: Redis가 틀려도 초과 판매가 되지 않게", 확인 후 삭제는 [Redis 분산 락](./distributed-lock.md)의 "확인과 삭제를 Lua 스크립트 하나로 묶습니다", 여러 키 스크립트의 슬롯 조건은 [Redis 원자성](./atomicity.md)의 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다"에 있습니다.

## 알림 중복 발송: 발송 기록 키로 대부분 막고, 남는 중복은 외부 API의 멱등 키에 맡깁니다

**요구사항**

- 주문 상태가 바뀌면 메시지를 Redis Stream에 넣고, 알림 작업자가 받아 외부 푸시·문자 API를 부릅니다.
- 작업자가 죽거나 느려 같은 메시지가 다시 와도 사용자에게는 한 번만 보내고 싶습니다.

**예시**: 알림 `n9001`("주문 101 배송 시작", 회원 u7)이 스트림에 들어갑니다. 작업자 N1이 받아 외부 API를 부릅니다. 외부 API의 호출 제한 시간은 10초, 처리 중 기록의 기한은 30초, 회수 기준 시간(`XAUTOCLAIM`의 min-idle-time)은 60초입니다.

**키 이름·자료형·만료**(이 문서의 설계)

| 키 | 자료형 | 값 | 만료 |
| --- | --- | --- | --- |
| `notif:n9001` | String | 상태(`SENDING`·`SENT`)와 주인 토큰 | 처리 중 30초, 보낸 뒤 1일 |

키 이름의 기준은 스트림 엔트리 ID가 아니라 **업무 ID**인 알림 ID입니다. 생산자가 같은 알림을 다시 `XADD`하면 새 엔트리 ID가 붙기 때문입니다.

**처리 순서**

1. `XREADGROUP`으로 엔트리를 받습니다. 받은 엔트리는 소비자 그룹의 처리 대기 목록(PEL)에 기록되고, 작업자가 `XACK`(처리를 끝냈다는 신호)를 보내야 목록에서 빠집니다. 목록에 오래 남은 엔트리는 `XAUTOCLAIM`으로 다른 작업자가 가져가 다시 처리하므로, ACK하지 않으면 다시 처리될 기회가 남습니다.
2. `SET notif:n9001 <SENDING, 토큰> NX GET PX 30000`을 보냅니다.
   - nil(내가 처음)이면 3번으로 갑니다.
   - `SENT`가 돌아오면 이미 보낸 알림이므로 `XACK`만 하고 끝냅니다.
   - 남의 토큰이 담긴 `SENDING`이면 다른 작업자가 보내는 중이므로 ACK하지 않고 둡니다. 엔트리는 PEL에 남아 나중에 다시 옵니다.
3. 외부 API를 부릅니다. API가 멱등 키를 받으면 `n9001`을 넘깁니다.
4. 성공하면 스크립트로 "값의 토큰이 내 것이거나 키가 없으면 `SENT`로 바꾸고 기한을 1일로"를 실행한 뒤 `XACK`합니다. 이 알림은 이미 나갔으므로 다시 처리할 이유가 없기 때문입니다. 스크립트가 남의 토큰을 보고 쓰지 못했다면 처리 중 기록이 만료된 사이 다른 작업자가 같은 알림을 보내는 중이라는 뜻입니다. 중복 발송이 이미 일어나고 있다는 신호이므로 로그와 지표로 남기고, 내 엔트리는 그대로 `XACK`합니다. 다른 작업자는 자기 처리를 끝내고 `SENT`를 씁니다.
5. 보내지 않은 것이 확실한 실패(요청이 거절됨)면 토큰을 확인하고 기록을 지운 뒤 ACK하지 않습니다. 다음 회수 때 처음부터 다시 보냅니다.
6. 결과를 모르는 실패(호출 제한 시간 초과)면 기록을 지우지 않습니다. 이미 발송됐을 수 있기 때문입니다.

**빠뜨리기 쉬운 함정**

- **외부 발송은 되돌릴 수 없으므로, Redis만으로는 중복을 0으로 만들 수 없습니다.** N1이 3번에서 발송을 끝낸 직후, 4번을 보내기 전에 죽었다고 합시다. 처리 중 기록은 30초 뒤 만료되고, 60초 뒤 회수된 엔트리를 받은 N2는 2번에서 nil을 받아 다시 보냅니다. 사용자는 같은 알림을 두 번 받습니다. 반대로 3번 전에 `SENT`를 먼저 쓰면, 발송 전에 죽었을 때 알림이 영영 나가지 않습니다. 이 경우까지 막는 것은 외부 API의 멱등 키뿐이며, 그것도 API가 문서로 약속하는 범위(같은 키를 기억하는 기간, 같은 키로 동시에 부를 때의 동작) 안에서만 막습니다. 멱등 키가 없다면 알림마다 "두 번 가는 것"과 "안 가는 것" 중 덜 나쁜 쪽을 고릅니다. 배송 알림은 두 번이 낫고, 광고 푸시는 안 가는 쪽이 나을 수 있습니다. 이 고르기의 원리는 [메시지 큐 기초](../cs/message-queue.md)의 "ACK를 언제 보내는가가 유실과 중복을 가릅니다"에 있습니다.
- **처리 중 기록의 기한은 외부 API 호출 제한 시간보다 길어야 합니다.** 기한이 더 짧으면 느린 호출 하나 동안 기록이 만료되어, 회수된 엔트리가 같은 알림을 동시에 보냅니다. 회수 기준 시간도 기한보다 길게 둡니다. 예시의 10초 < 30초 < 60초가 그 순서입니다.
- **보낸 기록의 기한은 같은 알림이 다시 올 수 있는 가장 긴 시간보다 길어야 합니다.** 회수와 재전달은 분 단위지만, 생산자의 재전송, 실패 메시지를 사람이 며칠 뒤 다시 넣는 경우까지 더해야 합니다. 대신 기록 수는 "초당 알림 수 × 기한(초)"입니다. 초당 50건 × 1일이면 4,320,000개입니다(가상 수치). 키 하나의 크기를 `MEMORY USAGE`로 재서 곱해 보고, 너무 크면 기한을 줄이거나 발송 기록을 DB에 둡니다.
- **발송 중복과 내용 중복은 다른 요구사항입니다.** 이 레시피는 "같은 알림 ID를 두 번 보내지 않기"입니다. "같은 사용자에게 같은 종류의 광고를 하루 한 번만"은 알림 ID가 다른 메시지끼리의 규칙이라, `notif:once:u7:promo:20261111` 같은 키에 `SET … NX EX`를 따로 둡니다.

**판단 이유가 있는 문서**: 처리 중·완료 기록과 주인 토큰은 [Redis 멱등 키](./idempotency-key.md)의 "SET NX로 처리 시작을 먼저 기록합니다"와 "어떤 응답을 저장하는가", 재전달과 회수는 [Redis Streams](./streams.md)의 "ACK 시점이 유실과 중복을 가르는 것은 Streams에서도 같습니다"와 "죽은 소비자의 메시지는 Redis가 다시 주지 않습니다: 직접 회수합니다"에 있습니다.

## 검색어 자동완성: 사전순 범위 조회는 싸지만 인기순이 아니고, 인기순은 접두사마다 목록을 미리 만듭니다

**요구사항**

- 검색창에 한 글자 칠 때마다 그 글자로 시작하는 검색어를 최대 10개 보여 줍니다.
- 많이 검색된 검색어가 위에 와야 합니다.

**예시**: 검색어는 우산(120회), 우비(40회), 우유(300회), 장화(80회) 넷입니다. 사용자가 "우"를 입력합니다. 바라는 결과는 우유, 우산, 우비 순서입니다.

### 사전순 범위 조회: Sorted Set 하나, 모든 점수를 0으로

모든 원소의 점수가 같은 Sorted Set은 원소 문자열의 바이트 순서로 줄을 섭니다([Redis 랭킹](./ranking.md)의 "아무것도 정하지 않으면 회원 ID의 바이트 순서가 정합니다"). `ZRANGE … BYLEX`는 이 순서에서 두 문자열 사이의 원소를 꺼내는 명령입니다.

- 키: `ac:all`(Sorted Set). 검색어마다 `ZADD ac:all 0 우산`처럼 점수 0으로 넣습니다.
- 조회: `ZRANGE ac:all "[우" "[우\xff" BYLEX LIMIT 0 10`. `[`는 그 값을 포함한다는 표시이고, `\xff`는 바이트 값 255입니다. "우"로 시작하는 모든 문자열은 "우"보다 크거나 같고 "우" 뒤에 255 바이트를 붙인 것보다 작으므로, 이 범위가 곧 "우"로 시작하는 원소입니다. UTF-8로 인코딩한 문자열에는 255 바이트가 나오지 않으므로 상한으로 안전합니다.
- 비용: O(log N + M)입니다. N은 Sorted Set의 원소 수, M은 돌려받는 원소 수입니다. 범위의 시작을 찾는 데 log N, 꺼내는 데 M만큼 일합니다.

예시의 결과는 우비, 우산, 우유입니다. 비(U+BE44) < 산(U+C0B0) < 유(U+C720)라 UTF-8 바이트 순서도 이 순서이기 때문입니다. **가장 인기 있는 우유가 마지막입니다.** `LIMIT 0 10`은 인기 상위 10개가 아니라 바이트 순서로 앞선 10개입니다. "우"로 시작하는 검색어가 1,000개면 인기순으로 고르려면 1,000개를 모두 꺼내 앱에서 정렬해야 하고, 그러면 M이 1,000이 됩니다.

공식 문서는 점수가 서로 다른 원소가 섞인 Sorted Set에서 `BYLEX`의 결과가 정해지지 않는다고 적습니다. 그래서 인기 점수를 같은 키의 점수로 쓸 수 없습니다.

### 인기순 목록: 접두사마다 Sorted Set을 미리 만듭니다

- 키: `ac:v3:p:우`(Sorted Set). 원소는 검색어, 점수는 검색 횟수입니다. `v3`은 만든 판의 번호입니다(이 문서의 설계).
- 만들기: 주기 작업이 검색어별 횟수를 받아, 검색어의 접두사마다 `ZADD`합니다. "우산"은 `ac:v3:p:우`와 `ac:v3:p:우산`에 들어갑니다. 다 넣으면 접두사 키마다 `ZREMRANGEBYRANK`로 상위 N개만 남기고, `SET ac:ver 3`으로 새 판을 가리킵니다. 옛 판이 저절로 사라지도록 키를 만들 때 TTL을 붙입니다. 이 TTL은 지금 쓰는 판에도 붙어 있고 키를 만들 때부터 흐르므로, 이 판을 만들기 시작한 때부터 다음 판이 `ac:ver`로 공개될 때까지의 시간(교체 주기와 다음 판을 만드는 시간)에 앱이 판 번호를 들고 있는 시간을 더한 것보다 넉넉히 길게 잡습니다. 새 판 만들기가 TTL 안에 끝나지 못하면 `ac:ver`가 가리키는 판이 만료되어 자동완성이 비므로, 판 만들기의 실패를 지표로 지켜봅니다.
- 조회: 앱이 `ac:ver`를 몇 초 동안 메모리에 들고 있다가, `ZRANGE ac:v3:p:우 0 9 REV WITHSCORES`로 상위 10개를 읽습니다. O(log N + M)이고, 여기서 N은 그 접두사 목록의 원소 수입니다.

예시를 넣으면 다음과 같습니다.

```text
ac:v3:p:우     우유 300, 우산 120, 우비 40   -> 우유, 우산, 우비
ac:v3:p:우산   우산 120
ac:v3:p:우비   우비 40
ac:v3:p:우유   우유 300
ac:v3:p:장     장화 80
ac:v3:p:장화   장화 80
```

검색어 4개(원소 4개)가 키 6개, 원소 8개가 됐습니다. **원소 수는 검색어마다 그 길이만큼 곱해집니다.** 검색어 1,000,000개의 평균 길이가 6글자면 자르기 전 원소가 약 6,000,000개입니다(가상 수치). 그래서 접두사 길이에 상한을 두고(예: 10글자), 목록마다 상위 N개만 남깁니다. 읽기는 키 하나에서 끝나는 대신, 쓰기와 메모리를 미리 냅니다.

검색어별 횟수는 [실시간 집계](./realtime-aggregation.md)의 "인기 검색어: 구간마다 Sorted Set, 창 단위로 한 번 합칩니다"의 결과나 DB의 검색 로그에서 가져옵니다. 검색마다 모든 접두사 키를 바로 갱신하면 검색 한 번이 쓰기 여러 번이 되고, 짧은 접두사 키에 쓰기가 몰립니다. 그래서 주기적으로 새 판을 만듭니다.

**빠뜨리기 쉬운 함정**

- **한글은 입력 도중의 글자가 접두사가 아닙니다.** "우산"을 치는 동안 입력창의 문자열은 "우", "웃", "우사", "우산"으로 바뀝니다. "웃"(U+C6C3)은 "우산"의 접두사가 아니므로 그 순간 추천이 사라집니다. 두 방식 모두 바이트를 비교하기 때문입니다. 자모로 풀어 쓴 정규화 문자열을 조회 기준으로 두고 화면에는 원래 검색어를 보여 주는 방법이 있지만, 접두사 수가 자모 수만큼 늘어 인기순 목록의 메모리가 더 커집니다. 대소문자와 띄어쓰기도 넣기 전에 정규화합니다.
- **Spring에서 `\xff` 상한을 문자열로 만들면 한글이 빠집니다.** `opsForZSet().rangeByLex`는 범위의 경계를 템플릿의 문자열 직렬화기(UTF-8)로 바이트로 바꿉니다. 자바 문자열의 U+00FF는 UTF-8에서 바이트 2개(0xC3 0xBF)가 되므로 255 한 바이트가 아닙니다. 한글의 첫 바이트(0xEA~0xED)는 0xC3보다 크므로, "우" 뒤에 한글이 붙은 우산·우비·우유가 모두 상한을 넘어 결과에서 빠집니다. 상한을 "마지막 글자의 코드 포인트를 하나 올린 문자열"로 두고 그 값 자체는 포함하지 않는 경계(`(`)로 쓰면 피할 수 있습니다. "우"(U+C6B0)라면 "(욱"(U+C6B1)입니다. UTF-8에서 "우"는 0xEC 0x9A 0xB0, "욱"은 0xEC 0x9A 0xB1이라, "우"로 시작하는 문자열은 세 번째 바이트에서 "욱"보다 작아지므로 모두 범위 안에 들고, "욱"으로 시작하는 문자열은 빠집니다. 이 우회는 바이트 비교 규칙에서 끌어낸 이 문서의 추론이며 재현하지 않았습니다.
- **원소와 경계의 직렬화가 다르면 아무것도 나오지 않습니다.** 같은 메서드에서 원소는 값 직렬화기로, 경계는 문자열 직렬화기로 바뀝니다. 값 직렬화기가 JSON이면 저장된 원소는 따옴표로 시작해 경계와 맞지 않습니다. 자동완성 키는 `StringRedisTemplate`처럼 원소도 문자열로 저장하는 템플릿으로 다룹니다. 직렬화기의 차이는 [직렬화기 고르기](./serializer.md)에서 다룹니다.
- **한 글자 접두사 키는 핫키가 됩니다.** 모든 사용자의 첫 입력이 몇 안 되는 키로 갑니다. 이 목록은 판이 바뀔 때만 바뀌므로, 짧은 접두사의 결과는 앱 메모리에 판 번호와 함께 캐시합니다. [Hot Key와 Big Key](./hot-key-big-key.md)의 "핫키는 Redis 앞에서 막거나, 복사본에 나눕니다"에서 다룹니다.
- **인기순은 조작과 부적절한 검색어에 열려 있습니다.** 한 사람이 같은 검색을 반복하면 순위를 올릴 수 있으므로, 무엇을 한 번으로 셀지와 노출 전 걸러 낼 검색어를 정해 둡니다.

**판단 이유가 있는 문서**: Sorted Set의 동점 순서는 [Redis 랭킹](./ranking.md), 검색 횟수를 구간마다 세고 합치는 비용과 정규화는 [실시간 집계](./realtime-aggregation.md)의 "무엇을 한 번으로 셀지는 서비스가 정합니다"에 있습니다. 오타 교정, 형태소 분석, 초성 검색처럼 접두사 일치를 넘는 요구는 검색 엔진의 일입니다. 이 문서는 다루지 않습니다.

## 말로 설명하기

### 30초 버전

다섯 기능은 같은 원리의 다른 조합입니다. 인증번호는 번호와 시도 횟수를 TTL 있는 Hash 하나에 두고, 비교·삭제·횟수 증가를 스크립트 하나로 해서 한 번만 쓰기를 지킵니다. 접속 상태는 하트비트가 TTL을 미루는 키라서 접속 종료가 마지막 하트비트부터 최대 TTL만큼 늦게 보이는 것을 받아들입니다. 좌석은 좌석마다 `SET NX PX` 선점을 두되, 리스라서 겹칠 수 있으므로 판매 확정은 DB 고유 제약이 합니다. 알림은 멱등 키 패턴으로 대부분의 중복을 막지만, 외부 발송은 되돌릴 수 없어 남는 중복은 외부 API의 멱등 키에 맡깁니다. 자동완성은 사전순 조회가 싸지만 인기순이 아니어서, 인기순이 필요하면 접두사마다 목록을 미리 만들고 메모리를 냅니다.

### 2분 버전

공통 질문은 세 가지입니다. 첫째, 판단과 변경이 한 실행 안에 있는가. 인증번호의 "맞으면 지우고 틀리면 횟수를 올린다"는 결과에 따라 갈리므로, 번호를 String에 담고 `GETDEL` 명령 하나로 읽고 지우는 방식으로는 안 되고 스크립트가 필요합니다. 여러 좌석을 한꺼번에 잡는 것도 스크립트이며, 그래서 공연 하나의 좌석 키를 해시 태그로 같은 슬롯에 둡니다.

둘째, 기한이 무엇을 뜻하는가. 접속 키의 TTL은 "마지막 신호 이후 이만큼 조용하면 나간 것"이라는 판정이고, 늦은 하트비트가 키를 되살리지 않고 화면이 다시 읽는다면 그 값이 늦게 보이는 시간의 상한입니다. 좌석 선점과 알림의 처리 중 기록은 리스라서 보유자가 기한보다 오래 걸리면 다른 쪽과 겹칩니다. 그래서 기한은 정상 처리 시간의 상한(결제 제한 시간, 외부 호출 제한 시간)보다 길게 잡습니다.

셋째, 이 키를 잃거나 겹치면 누가 최종 판정을 하는가. 인증번호는 잃어도 다시 받으면 되므로 Redis만으로 충분합니다. 좌석은 두 번 팔리면 안 되므로 DB의 좌석 고유 제약이 마지막에 정하고, 기한 뒤에 끝난 결제는 환불로 정리합니다. 알림은 외부 발송이 되돌릴 수 없어 Redis 기록으로는 중복을 0으로 만들 수 없고, 외부 API의 멱등 키가 없으면 알림마다 중복과 유실 중 덜 나쁜 쪽을 고릅니다.

자동완성은 읽기 비용과 쓰기 비용을 어디에 둘지의 문제입니다. 같은 점수의 Sorted Set에 `ZRANGE … BYLEX`를 쓰면 O(log N + M)으로 접두사 범위를 바로 꺼내지만 바이트 순서라서 인기순이 아닙니다. 접두사마다 인기순 목록을 미리 만들면 읽기는 키 하나에서 끝나는 대신 원소가 검색어 길이만큼 곱해지므로, 접두사 길이 상한과 목록당 상한을 둡니다.

### 예상 질문과 꼬리 질문

**인증번호**

- **번호를 String에 담고 확인에 `GETDEL`을 쓰면 원자적이니 충분하지 않나요?**
  두 요청이 같은 번호로 동시에 와도 하나만 값을 받으므로 "한 번만 쓰기"는 지켜집니다. 하지만 틀린 입력에도 번호를 지워 버려 "5번까지"라는 요구를 지키지 못합니다. 비교 결과에 따라 지울지 횟수를 올릴지 갈리므로 스크립트가 필요합니다(본문: "인증번호: 키 하나에 번호와 시도 횟수를 담고, 확인과 삭제를 스크립트 하나로").
  - **꼬리: 시도 횟수를 번호 키 안에 두면 재발송으로 초기화되는데, 그게 구멍 아닌가요?**
    맞습니다. 그래서 발급 횟수에 상한을 둡니다. 전체 추측 수는 발급 상한 × 번호당 시도 수로 묶이고, 예시에서는 하루 50번입니다. 여러 계정을 노리는 공격은 계정별 상한으로 막지 못하므로 IP·전화번호별 상한을 함께 둡니다.
- **인증번호를 Redis에만 두어도 되나요? 장애 조치로 잃으면요?**
  잃으면 사용자가 "만료"를 보고 다시 받으면 됩니다. 원천이 따로 필요 없는 짧은 수명의 기록입니다. 다만 시도 횟수 증가를 잃으면 몇 번 더 맞혀 볼 수 있다는 위험을 받아들이는 것이고, 축출로 사라지는 일이 잦으면 사용자 경험이 나빠지므로 이 키가 있는 서버는 `noeviction`이나 캐시와 분리된 서버로 둡니다.

**접속 상태**

- **접속 종료를 바로 알 수는 없나요?**
  사용자당 연결이 하나라면 앱이 "나간다"는 신호를 보낼 때 `DEL`로 바로 반영합니다. 신호 없이 사라진 경우는 하트비트가 끊긴 것으로만 알 수 있으므로 마지막 하트비트부터 최대 TTL만큼 늦습니다. TTL을 줄이면 하트비트 한 번의 지연에도 접속 중인 사용자가 깜빡이므로, TTL은 하트비트 간격의 몇 배로 둡니다.
  - **꼬리: 그럼 만료 알림을 구독해 "나갔다" 이벤트를 보내면 되지 않나요?**
    만료 알림은 Redis가 실제로 키를 지울 때 나가므로 TTL 시각보다 늦을 수 있고, 구독이 끊긴 동안의 알림은 사라지며, 클러스터에서는 그 키가 있는 노드에서만 나옵니다. 이벤트의 신뢰할 수 있는 근거가 되지 못하므로 화면은 다시 읽어 확인합니다.
- **친구 500명의 상태를 `MGET` 한 번에 읽으면 클러스터에서 괜찮나요?**
  Lettuce가 슬롯별로 나눠 보내므로 에러는 나지 않고, 키가 흩어진 슬롯 수만큼 명령이 갈립니다. 해시 태그로 모으면 요청은 하나가 되지만 모든 사용자의 하트비트 쓰기가 그 노드에 몰리므로, 원자성이 필요 없는 이 읽기에서는 나뉘는 비용을 받아들입니다.

**좌석 선점**

- **Redis 선점에 성공했으면 그 좌석은 그 사용자 것 아닌가요?**
  아닙니다. 선점은 리스입니다. 결제가 기한보다 오래 걸리면 키가 만료되어 다른 사용자가 같은 좌석을 잡을 수 있고, 장애 조치로 선점 기록을 잃을 수도 있습니다. 두 번 팔리지 않게 하는 것은 DB의 좌석 고유 제약입니다.
  - **꼬리: 결제 직전에 "아직 내 선점인가"를 확인하고 기한을 늘리면 겹침이 없어지지 않나요?**
    줄어들 뿐입니다. 확인한 뒤에도 결제사 응답이 늘린 기한보다 늦게 올 수 있습니다. 확인 직후의 멈춤을 막을 수 없다는 것이 리스의 빈틈이고, 그래서 마지막 판정을 원천에 맡깁니다. 겹치면 늦은 쪽은 결제 취소로 정리합니다.
- **재고 예약 문서처럼 수량 카운터로 하면 안 되나요?**
  수량 조건은 "몇 개 남았는가"만 지키므로 같은 좌석이 두 사람에게 가는 것을 막지 못합니다. 좌석은 단위마다 주인이 정해지는 재고라 좌석 단위의 키와 고유 제약이 필요합니다.

**알림 중복 발송**

- **발송 기록 키를 `SET NX`로 먼저 쓰면 중복이 완전히 막히지 않나요?**
  `SENT`를 발송 전에 쓰면 발송 전에 죽은 경우 알림이 영영 나가지 않고, 발송 뒤에 쓰면 그 사이에 죽은 경우 다시 보냅니다. 외부 발송은 되돌릴 수 없어서 Redis 기록만으로는 둘 중 하나가 남습니다. 남는 중복을 막는 것은 외부 API가 받는 멱등 키이고, 그 효과는 API가 키를 기억하는 기간과 약속한 동작의 범위 안으로 한정됩니다.
  - **꼬리: 처리 중 기록의 기한은 무엇을 기준으로 정하나요?**
    외부 API 호출 제한 시간보다 길게, 회수 기준 시간보다 짧게 둡니다. 호출보다 짧으면 느린 호출 중에 기록이 만료되어 회수된 메시지가 같은 알림을 동시에 보냅니다.
- **스트림 엔트리 ID로 중복을 판단하면 안 되나요?**
  생산자가 같은 알림을 다시 넣으면 새 엔트리 ID가 붙으므로 같은 알림을 다른 것으로 봅니다. 기준은 메시지 안의 업무 ID인 알림 ID입니다.
- **발송 기록을 오래 두면 무엇이 문제인가요?**
  기록 수가 초당 알림 수 × 기한만큼 쌓입니다. 초당 50건을 하루 두면 약 432만 개입니다. 같은 알림이 다시 올 수 있는 가장 긴 시간과 이 메모리를 맞바꾸고, 너무 길어야 하면 DB에 기록합니다.

**검색어 자동완성**

- **같은 점수의 Sorted Set에서 `ZRANGE … BYLEX LIMIT 0 10`이면 상위 10개 아닌가요?**
  바이트 순서로 앞선 10개입니다. 인기와 무관합니다. 인기 점수를 같은 키의 점수로 넣으면 공식 문서가 결과가 정해지지 않는다고 하는 경우가 되므로, 인기순이 필요하면 접두사마다 인기순 목록을 따로 만듭니다.
  - **꼬리: 접두사마다 목록을 만들면 메모리가 얼마나 늘어나나요?**
    검색어 하나가 그 길이만큼의 접두사 목록에 들어가므로 원소 수가 평균 길이만큼 곱해집니다. 접두사 길이 상한과 목록당 상위 N개 자르기로 묶습니다. 대신 판을 새로 만드는 동안만큼 결과가 늦게 바뀝니다.
- **검색할 때마다 접두사 목록을 바로 갱신하면 더 최신이지 않나요?**
  검색 한 번이 접두사 수만큼의 쓰기가 되고, 한 글자 접두사 키에 모든 검색의 쓰기가 몰립니다. 자동완성이 몇 분 늦게 바뀌어도 되는지 먼저 정합니다. 늦어도 된다면 주기적으로 새 판을 만드는 쪽은 검색 수와 무관하게 판마다 한 번만 쓰므로, 검색이 많을수록 쓰기 수가 적습니다.
- **한글 자동완성에서 따로 챙길 것은?**
  입력 도중의 글자("웃")가 완성될 검색어("우산")의 접두사가 아니어서 추천이 깜빡입니다. 자모로 정규화한 문자열을 기준으로 두면 해결되지만 접두사 수가 늘어납니다. Spring에서 255 바이트 상한을 자바 문자열로 만들면 UTF-8에서 두 바이트가 되어 한글 결과가 빠지는 점도 확인합니다.

# HTTP 캐싱: 요청이 우리 서버에 닿기 전에 누가 답하고, 서버는 그것을 어떻게 통제하는가

> **핵심 질문**: 사용자의 요청이 우리 서버나 Redis에 닿기 전에, 그 요청에 대신 답할 수 있는 캐시는 어디에 있는가? 서버는 그 캐시들이 무엇을, 얼마 동안, 누구에게 다시 쓰게 할지 어떻게 지시하는가? 지시가 틀리면 어떤 사고가 나고, 왜 Redis 캐시처럼 지울 수 없는가?
>
> **범위**: 서버가 만든 API 응답을 브라우저와 CDN·리버스 프록시가 저장하고 다시 쓰는 규칙(HTTP 캐싱 표준)과, Spring MVC에서 그 규칙을 지시하는 방법을 다룹니다. 브라우저의 뒤로 가기 기록, 서비스 워커, CDN 제품별 설정 화면은 다루지 않습니다. 요청 쪽에서 보내는 캐시 지시는 응답 지시를 이해하는 데 필요한 만큼만 씁니다.

## 배경 지식

### 이 문서의 예시: 상품 상세 `GET /products/42`

문서 끝까지 다음 장면 하나를 씁니다.

- 상품 상세 API `GET /products/42`는 상품 42의 이름, 가격, 설명을 JSON으로 돌려줍니다. 응답 본문은 약 **20KB**입니다.
- 이 API에는 전 세계에서 **초당 500번** 요청이 옵니다. 요청은 CDN을 거쳐 앱 서버로 갑니다. CDN은 지역마다 **엣지 20곳**을 두고, 사용자는 가까운 엣지로 연결됩니다.
- 앱 서버(Spring MVC) **4대**는 Redis의 `product:42`를 먼저 읽고, 없으면 DB에서 읽어 채웁니다.
- DB의 상품 행에는 수정할 때마다 1씩 늘어나는 **버전 번호** 열이 있습니다. 지금 상품 42의 버전은 **7**입니다.
- 로그인한 사용자에게는 같은 응답에 **"내 쿠폰 적용가"** 필드가 함께 들어갑니다. 로그인 여부는 요청의 쿠키로 압니다. 이 필드가 뒤에서 사고의 원인이 됩니다.

```text
브라우저 ──▶ CDN 엣지(20곳 중 하나) ──▶ 앱 서버(4대 중 하나) ──▶ Redis product:42 ──(미스)──▶ DB
[브라우저 캐시]   [CDN 캐시]                  [Redis 캐시]
  사용자 한 명 것  여러 사용자가 함께 씀          우리가 키를 정하고 지우는 캐시
```

화살표는 요청이 가는 방향이고, 응답은 같은 길을 거꾸로 돌아옵니다. 대괄호는 그 자리에 있는 캐시입니다. 로드 밸런서, 앱 서버 안의 로컬 캐시, Redis 복제본은 그림에서 뺐습니다. 로드 밸런서는 응답을 저장하지 않는다고 가정하고, 나머지는 이 문서의 질문인 "요청이 앱 서버에 닿기 전에 누가 답하는가"와 관계가 없기 때문입니다. 회사 네트워크의 프록시처럼 사용자와 CDN 사이에 끼는 캐시도 있을 수 있지만, 동작 규칙이 CDN과 같은 "공유 캐시"이므로 따로 그리지 않았습니다.

이 문서의 요청 수, 엣지 수, 응답 크기, 초 단위 시간은 계산을 보여 주기 위한 **가상의 숫자**이며 이 문서에서 잰 값이 아닙니다.

### HTTP 요청과 응답, 헤더

- **한 줄**: HTTP 요청은 "무엇을 하라(메서드) + 어느 자원에(주소, URI)"이고, 응답은 "결과 코드(상태 코드) + 내용(본문)"입니다. 양쪽 모두 본문 앞에 `이름: 값` 꼴의 부가 정보인 **헤더**를 붙입니다.
- **비유**: 택배 상자의 송장과 내용물입니다. 송장(헤더)에는 받는 사람과 "취급 주의" 같은 지시가 적히고, 상자 안(본문)에는 물건이 있습니다. 중간 물류 센터는 상자를 열지 않고 송장만 보고 처리를 정합니다.
- **실제로는**: Spring 컨트롤러가 돌려주는 JSON은 응답 본문이 되고, 상태 코드 200과 `Content-Type: application/json` 같은 헤더가 함께 갑니다. 이 문서에서 다루는 캐시 지시(`Cache-Control`, `ETag`, `Vary` 등)도 모두 헤더입니다. 메서드는 **읽기만 하는 것(안전한 메서드, `GET`·`HEAD`)**과 **서버의 상태를 바꿀 수 있는 것(`POST`·`PUT`·`DELETE` 등)**으로 나뉩니다. 캐시가 다시 쓰는 대상은 주로 `GET`의 응답입니다. 상태를 바꾸는 요청에 저장해 둔 응답으로 대신 답하면 실제 변경이 일어나지 않기 때문입니다.
- **이 주제에서는**: 중간의 캐시는 본문의 의미를 모릅니다. 응답에 "내 쿠폰 적용가"가 들어 있는지는 본문을 읽어야 알 수 있지만, 캐시는 헤더만 보고 저장할지 정합니다. **그래서 "이 응답을 누구에게 다시 줘도 되는가"는 서버가 헤더로 말해 주지 않으면 캐시가 알 방법이 없습니다.** 이 문서의 모든 사고는 이 사실에서 나옵니다.

### 캐시가 끼어드는 두 자리: 개인 캐시와 공유 캐시

- **한 줄**: HTTP 캐시는 받은 응답을 저장해 두었다가 같은 요청이 오면 원래 서버(오리진 서버, 이 문서에서는 앱 서버)에 가지 않고 대신 답하는 저장소입니다. 사용자 한 명만 쓰는 것을 **개인 캐시(private cache)**, 여러 사용자가 함께 쓰는 것을 **공유 캐시(shared cache)**라고 부릅니다.
- **비유**: 개인 캐시는 내 책상 서랍에 넣어 둔 복사본이고, 공유 캐시는 동네 도서관 복사본입니다. 서랍 복사본은 나만 보므로 내 개인 정보가 적혀 있어도 괜찮습니다. 도서관 복사본은 누구나 빌려 가므로, 거기에 내 개인 정보가 적힌 복사본이 꽂히면 다음 사람이 그것을 봅니다.
- **실제로는**: 예시에서 브라우저의 캐시가 개인 캐시이고, CDN 엣지와 리버스 프록시(앱 서버 앞에서 요청을 받아 전달하는 서버, 예: Nginx)가 공유 캐시입니다. 비유와 다른 점은 두 가지입니다. 첫째, 캐시마다 서로 독립적입니다. 엣지 20곳은 각자 자기 복사본을 따로 가지며, 한 엣지에 저장됐다고 다른 엣지에도 저장되는 것은 아닙니다. 둘째, 복사본을 언제까지 쓰고 언제 버릴지를 캐시가 스스로 판단합니다. 서버는 규칙을 헤더로 알려 줄 뿐, 저장된 복사본을 직접 꺼내거나 지울 수 없습니다.
- **이 주제에서는**: 브라우저 캐시가 답하면 요청은 네트워크로 나가지도 않고, CDN이 답하면 요청은 앱 서버에 오지 않습니다. 둘 다 앱 서버의 로그·지표에는 보이지 않습니다. 반면 Redis 캐시는 요청이 이미 앱 서버에 들어온 뒤에 쓰입니다. **HTTP 캐시는 Redis보다 앞단에서 요청 수 자체를 줄이고, 그 대가로 서버의 통제에서 벗어난 곳에 사본을 둡니다.**

### 캐시 키: 무엇이 같으면 같은 요청인가

- **한 줄**: 캐시 키는 캐시가 저장된 응답을 찾을 때 쓰는 이름표이고, 기본은 **메서드와 URI**입니다.
- **비유**: 도서관의 청구 기호입니다. 같은 청구 기호로 찾으면 같은 책이 나옵니다.
- **실제로는**: 표준은 캐시 키를 "최소한 메서드와 URI"로 정합니다. 표준은 또 많은 캐시가 `GET` 응답만 저장하므로 사실상 URI만 키로 쓴다고 설명합니다. 여기에 응답의 `Vary` 헤더가 지목한 요청 헤더(예: 언어)를 더해 키를 넓힐 수 있고, 캐시가 스스로 다른 정보를 더하기도 합니다. 요청의 쿠키나 `Authorization`은 표준이 요구하는 키에 들어 있지 않습니다. `Vary`로 지목하지 않았는데도 키에 넣는지는 캐시 제품과 그 설정에 달려 있습니다.
- **이 주제에서는**: 예시의 CDN이 쿠키를 키에 넣지 않는다고 가정합시다. 그러면 앨리스와 밥이 같은 엣지로 `GET /products/42`를 보낼 때, 쿠키가 달라도 캐시 키는 같습니다. 이 사실이 뒤의 "개인화 응답이 공유 캐시로 새는 경로"의 출발점이고, 키를 넓히는 대가는 "Vary는 캐시 키를 넓히고, 그만큼 히트를 나눕니다"에서 다룹니다.

### 신선함, 나이, 검증

- **한 줄**: 저장된 응답이 아직 서버에 묻지 않고 써도 되는 상태를 **신선함(fresh)**, 그 기한이 지난 상태를 **낡음(stale)**이라고 합니다. 기한을 재는 기준은 응답이 오리진 서버에서 만들어지거나 오리진에 마지막으로 검증받은 뒤 흐른 시간인 **나이(age)**입니다. 낡은 응답을 버리지 않고 "이것 아직 맞나요?"라고 서버에 물어 다시 쓰는 것을 **검증(validation)**이라고 합니다.
- **비유**: 우유의 유통기한입니다. 기한 안이면 그냥 마십니다(신선함). 기한이 지났다고 바로 버리지 않고, 가게에 전화해 "이 제조번호 아직 괜찮나요?"라고 묻습니다(검증). 가게가 "그대로 괜찮다"고 하면 새 우유를 받지 않고 기한만 연장합니다.
- **실제로는**: 유통기한은 내가 우유를 산 날이 아니라 **공장에서 만든 날**부터 셉니다. HTTP도 같습니다. CDN에 50초 머문 응답을 브라우저가 받으면, 브라우저는 그 응답의 나이를 0초가 아니라 약 50초로 시작합니다. 중간 캐시를 거쳤다고 나이가 0으로 돌아가지는 않고, 오리진에 검증받아 "그대로"라는 답을 받았을 때 다시 0부터 셉니다. 비유와 다른 점은 "가게에 묻는" 검증이 네트워크 왕복 한 번이고, 그 왕복에서 서버가 얼마나 일하는지는 서버 구현에 달려 있다는 것입니다. 이 차이는 "낡으면 버리지 않고 묻습니다: ETag와 304"에서 다룹니다.
- **이 주제에서는**: 서버가 정하는 것은 두 가지입니다. **신선한 기간**(그동안 아무에게도 묻지 않고 답함)과 **검증 수단**(기간이 지난 뒤 싸게 확인하는 방법)입니다. 신선한 기간은 서버 부하를 줄이는 대신 낡은 값을 보여 줄 수 있는 시간이고, 검증은 낡은 값을 막는 대신 왕복 한 번을 치릅니다.

## 서버는 저장하지 않고, 지시만 합니다

Redis 캐시와 HTTP 캐시는 둘 다 "비싼 결과의 사본을 가까이 둔다"는 점에서 같지만, **사본을 누가 쥐고 있는가**가 다릅니다.

| | Redis 캐시 `product:42` | HTTP 캐시(브라우저, CDN) |
| --- | --- | --- |
| 사본을 저장하는 곳 | 우리가 운영하는 Redis | 사용자의 브라우저, CDN 업체의 엣지 |
| 저장 여부와 키를 정하는 쪽 | 앱 코드 | 캐시. 서버는 헤더로 규칙만 알림 |
| 수명 | 앱이 키마다 TTL을 붙임 | 서버가 헤더로 신선한 기간을 알리고, 캐시가 그에 따라 판단 |
| 지우기 | 앱이 원하는 때 키를 지움 | 서버가 원하는 때 모든 사용자의 브라우저 사본을 지울 방법은 없음. CDN은 업체가 제공하는 별도 기능으로 지움 |
| 줄여 주는 것 | DB 조회 | 앱 서버에 오는 요청 자체와 네트워크 전송량 |

이 표가 문서 전체의 요약입니다. Redis에서는 "잘못 넣으면 지우면 된다"가 통하지만, HTTP 캐시에서는 **응답을 보내는 순간의 헤더가 사실상 마지막 지시**입니다. 그래서 HTTP 캐싱의 설계는 "무엇을 얼마나 오래 둘까"보다 "**누구의 캐시에, 지울 수 없어도 괜찮을 만큼만** 두는가"를 먼저 정합니다.

서버가 지시에 쓰는 헤더는 주로 `Cache-Control`입니다. 쉼표로 구분한 여러 **지시어(directive)**를 담습니다. 예를 들어 `Cache-Control: max-age=60, s-maxage=300`은 "모든 캐시에 60초, 공유 캐시에는 300초"라는 뜻입니다. 지시어는 응답이 지나는 모든 캐시가 함께 읽습니다. 표준은 특정 캐시 하나만 겨냥해 지시하는 방법이 없다고 밝힙니다. 그래서 개인 캐시와 공유 캐시를 구분하는 지시어(`s-maxage`, `private`)가 따로 있습니다.

## 얼마 동안 묻지 않고 쓰는가: 신선한 기간과 Age

### max-age와 s-maxage

응답이 신선한지는 **신선한 기간 > 현재 나이**로 판정합니다. 신선한 기간은 캐시가 다음 순서로 처음 맞는 것을 씁니다.

1. 공유 캐시이고 `s-maxage`가 있으면 그 값
2. `max-age`가 있으면 그 값
3. `Expires` 헤더(만료 시각)가 있으면 그 시각에서 응답의 `Date`(생성 시각)를 뺀 값. `max-age`가 있으면 `Expires`는 무시합니다
4. 셋 다 없으면 캐시가 추정한 값(아래 "아무 지시도 없으면 캐시가 추정합니다")

예시의 상품 상세에 `Cache-Control: max-age=10, s-maxage=60`을 붙였다고 합시다. 단위는 초입니다. 브라우저(개인 캐시)는 `max-age`만 보므로 10초, CDN(공유 캐시)은 `s-maxage`를 먼저 보므로 60초 동안 서버에 묻지 않고 답합니다.

`s-maxage`에는 잘못 읽기 쉬운 성질이 두 가지 더 있습니다. 첫째, `s-maxage`가 붙은 응답은 공유 캐시에서 낡으면 **반드시 검증한 뒤에** 다시 써야 합니다. 서버에 연결할 수 없을 때 낡은 사본으로 버티는 것을 막는 지시이기도 합니다. 둘째, 요청에 `Authorization` 헤더가 있어도 공유 캐시가 저장하도록 허용합니다. 둘째 성질은 "개인화 응답이 공유 캐시로 새는 경로"에서 다시 다룹니다.

### 나이는 받은 때가 아니라 오리진에서부터 셉니다

캐시가 저장해 둔 응답을 검증 없이 내줄 때는 `Age` 헤더에 그 응답의 나이(초)를 적어야 합니다. 받는 쪽은 이 값에서 나이를 이어 셉니다. 예시로 따라가 봅시다(전송 시간은 0으로 단순화합니다).

| 시각 | 일어나는 일 | CDN 사본의 나이 | 브라우저 판단 |
| --- | --- | --- | --- |
| 0초 | 엣지 A가 앱 서버에서 응답을 받아 저장 | 0 | |
| 5초 | 사용자 1이 엣지 A에서 받음, `Age: 5` | 5 | 나이 5 < `max-age` 10. 앞으로 5초 더 신선 |
| 50초 | 사용자 2가 엣지 A에서 받음, `Age: 50` | 50 | 나이 50 > 10. 이번 요청에 대한 답으로 막 받은 응답이므로 이번 화면에는 그대로 씀. 다만 저장해 두고 다음 요청에 다시 쓸 때는 이미 낡았으므로 검증해야 함 |
| 60초 | 엣지 A의 사본이 낡음 | 60 | |

두 가지를 바로잡아 둡니다.

- **`max-age=10`은 "브라우저가 받은 뒤 10초"가 아닙니다.** 오리진 서버가 만들거나 마지막으로 검증한 뒤 10초입니다. 그래서 CDN에 오래 머문 응답을 받은 브라우저는 그 응답을 거의 다시 쓰지 못합니다. 브라우저 쪽 재사용을 기대한다면 `max-age`가 CDN 체류 시간보다 너무 짧지 않은지 함께 봐야 합니다.
- **사용자가 보는 값이 얼마나 낡을 수 있는지는 가장 긴 신선한 기간이 정합니다.** 예시에서 사용자 2는 50초 전에 만들어진 응답을 봅니다. 상품 가격을 바꾼 직후에도 최대 약 60초(`s-maxage`)까지 옛 가격이 보일 수 있습니다. 뒤에서 `stale-while-revalidate`를 더하면 이 시간이 더 늘어납니다.

### 앱 서버까지 오는 요청 수

`s-maxage=60`일 때 엣지 한 곳은 60초마다 한 번 앱 서버에 응답을 받으러 갑니다(만료 순간 동시에 들어온 요청을 엣지가 하나로 합쳐 보내는 경우). 엣지가 20곳이면 앱 서버에 오는 상품 42 요청은 60초에 약 20번, 초당 약 0.33번입니다. 초당 500번이던 요청이 그만큼으로 줄어듭니다.

이 계산에는 가정이 셋 있습니다.

- **엣지마다 따로 셉니다.** 엣지가 늘면 오리진에 오는 요청도 비례해 늘어납니다. 일부 CDN은 엣지들 앞에 중간 계층 캐시를 하나 더 두어 이 수를 줄이지만, 제품 기능이라 이 문서에서는 다루지 않습니다.
- **만료 순간의 동시 미스를 하나로 합친다고 가정했습니다.** 표준은 캐시가 미스 때 여러 요청을 하나의 전달 요청으로 합쳐도 된다고(collapse) 허용할 뿐, 반드시 그렇게 하라고 하지는 않습니다. 합치지 않는 캐시라면 만료 순간 그 엣지에 들어온 요청이 모두 앱 서버로 갑니다. Redis 캐시에서 인기 키가 만료될 때 미스가 몰리는 것과 같은 모양이 HTTP 캐시 앞단에서도 생길 수 있다는 뜻입니다.
- **캐시가 사본을 끝까지 들고 있다고 가정했습니다.** 저장 공간이 부족하면 캐시는 신선한 기간이 남은 사본도 먼저 버릴 수 있습니다. `s-maxage`는 "그 시간까지 써도 된다"는 상한이지 "그 시간까지 남아 있다"는 보장이 아닙니다.

### 아무 지시도 없으면 캐시가 추정합니다

`Cache-Control`도 `Expires`도 없는 응답은 캐시하지 않을 것이라고 생각하기 쉽지만, 표준은 그렇게 정하지 않습니다. 상태 코드 200, 404 같은 일부 응답은 **추정으로 캐시할 수 있는(heuristically cacheable)** 응답으로 정의돼 있어서, 명시적 기한이 없으면 캐시가 스스로 기한을 추정해 붙일 수 있습니다. 표준은 구체적인 계산법을 정하지 않고, `Last-Modified`(마지막 수정 시각)가 있으면 "그 뒤로 흐른 시간의 일부, 예컨대 10%" 이하를 쓰라고 권할 뿐입니다.

그래서 "헤더를 안 붙였으니 캐시되지 않는다"는 판단은 근거가 없습니다. 어떤 캐시가 얼마나 추정할지는 구현마다 다르므로, **캐시되면 안 되는 응답에는 그 의도를 헤더로 밝혀야 합니다.** Spring Security를 쓰는 앱이라면 이 일이 이미 일어나고 있을 수 있습니다. 아래 "Spring에서 지시를 붙이는 곳"에서 다룹니다.

## 낡으면 버리지 않고 묻습니다: ETag와 304

### 검증의 흐름

신선한 기간이 지나도 상품 42가 그대로라면, 20KB를 다시 받는 것은 낭비입니다. 검증은 이 낭비를 줄입니다.

- **ETag**: 서버가 응답에 붙이는 "이 내용의 버전 이름"입니다. 예시에서는 DB 버전 번호를 써서 `ETag: "v7"`을 붙입니다. 값의 형식은 서버가 정하고, 받는 쪽은 그 뜻을 해석하지 않고 같은지만 비교합니다.
- **If-None-Match**: 낡은 사본을 가진 캐시가 검증할 때 요청에 붙이는 헤더입니다. `If-None-Match: "v7"`은 "지금 버전이 v7이 아니면 새 내용을 주세요"라는 뜻입니다.
- **304 Not Modified**: 서버가 보기에 현재 버전이 요청의 ETag와 같으면 본문 없이 이 상태 코드로 답합니다. 캐시는 가진 사본을 다시 쓰고, 304에 실려 온 헤더(새 `Cache-Control` 등)로 사본의 헤더를 갱신해 신선한 기간을 다시 시작합니다. 다르면 서버는 평소처럼 200과 새 본문을 보냅니다.

```text
(CDN 사본이 낡음)
엣지 A ── GET /products/42, If-None-Match: "v7" ──▶ 앱 서버
엣지 A ◀── 304 Not Modified, ETag: "v7", Cache-Control: ... ── (본문 없음)
엣지 A: 가진 20KB 사본을 다시 60초 동안 신선한 것으로 씀
```

화살표는 요청과 응답이 오가는 방향입니다. 엣지 대신 브라우저가 같은 일을 할 수도 있습니다. 이 경우 브라우저의 검증 요청은 엣지에 먼저 닿고, 엣지가 신선한 사본을 갖고 있으면 엣지가 그 사본과 비교해 답합니다.

`Last-Modified`와 `If-Modified-Since`라는 시각 기반 검증도 있습니다. 표준은 둘 다 왔을 때 `If-None-Match`를 우선한다고 정하고, 시각은 초 단위라 1초 안의 변경을 구분하지 못하므로, 버전을 정확히 알 수 있다면 ETag가 더 확실합니다.

**강한 ETag와 약한 ETag.** `"v7"`처럼 따옴표만 있는 것은 강한 ETag로, 내용이 한 바이트라도 바뀌면 값도 바뀐다는 약속입니다. 앞에 `W/`를 붙인 `W/"v7"`은 약한 ETag로, 의미가 같으면 바이트가 조금 달라도 같은 값을 쓸 수 있다는 뜻입니다. 강한 약속을 지킬 수 없는 생성 방식이라면 반드시 `W/`를 붙여야 합니다. `If-None-Match` 비교에는 약한 비교(`W/` 유무를 무시하고 따옴표 안만 비교)를 씁니다. 그래서 GET 검증만 놓고 보면 둘의 결과가 같고, 차이는 범위 요청이나 쓰기 조건처럼 강한 비교를 요구하는 곳에서 납니다.

### 304가 아끼는 것과 아끼지 않는 것

304는 **본문 전송**을 아낍니다. 예시에서 20KB 대신 헤더만 오갑니다. 하지만 304가 왕복 자체를 없애지는 않고, **서버가 304를 결정하기까지 한 일**은 ETag를 어떻게 계산하느냐에 달려 있습니다. 이 차이가 이 절의 핵심입니다.

| ETag를 만드는 방식 | 304를 결정하기 전에 서버가 하는 일 | 아끼는 것 |
| --- | --- | --- |
| 응답 본문 전체의 해시(본문 바이트를 모두 읽어 짧은 고정 길이 값으로 요약한 것. 바이트가 바뀌면 값도 바뀜) | 핸들러 전체 실행(Redis·DB 조회 포함) + JSON 직렬화 + 해시 계산 | 네트워크 전송량뿐 |
| 응답 객체를 다 만든 뒤 버전으로 비교 | 핸들러 전체 실행(Redis·DB 조회 포함). 직렬화는 생략 | 전송량 + 직렬화 |
| 핸들러 맨 앞에서 버전만 읽어 비교 | 버전 번호 하나 읽기 | 전송량 + 직렬화 + 나머지 조회와 조립 |

표의 첫 줄을 **얕은(shallow) ETag**라고 부릅니다. 내용을 모르는 바깥 계층이 결과 바이트만 보고 만들기 때문입니다. 얕은 ETag로도 304는 정확히 나갑니다. 그러나 앱 서버는 200을 보낼 때와 거의 같은 일을 다 한 뒤 마지막에 본문만 버립니다. **"304가 많이 나가니 서버 부하가 줄었다"는 추론은 얕은 ETag에서는 틀립니다.** 서버 부하를 줄이려면 셋째 줄처럼, 본문을 만들기 전에 싸게 알 수 있는 버전(예시의 버전 번호, 수정 시각)으로 먼저 비교해야 합니다. 그 대가로 버전 번호가 응답 내용의 모든 변화를 반영하도록 관리할 책임이 생깁니다. 예를 들어 "내 쿠폰 적용가"처럼 상품 행 밖의 데이터가 응답에 섞이면, 상품 버전만으로 만든 ETag는 그 변화를 놓칩니다.

### Spring에서 304를 만드는 세 가지 방법

위 표의 세 줄은 Spring MVC에서 각각 다음에 해당합니다.

- **`ShallowEtagHeaderFilter`**: 서블릿 필터로 등록하면, `GET` 요청의 2xx 응답 본문 전체를 메모리에 모아 두었다가 MD5 해시로 ETag를 만들고 `If-None-Match`와 비교합니다. 응답 상태가 200이고 둘이 같으면 본문을 버리고 304를 보냅니다. 200이 아닌 2xx 응답에는 ETag만 붙고 304로 바뀌지는 않습니다. Spring 문서 주석도 이 필터가 뷰를 그대로 렌더링하므로 **대역폭만 아낄 뿐 서버 성능은 아끼지 않는다**고 밝힙니다. 추가로, 응답 본문을 다 모은 뒤에야 보내므로 응답이 클수록 요청마다 그만큼 메모리를 더 쓰고, 첫 바이트가 나가는 시각도 늦어집니다. 응답의 `Cache-Control`에 `no-store`가 있으면 ETag를 만들지 않습니다.
- **`ResponseEntity`에 `eTag(...)`를 붙여 반환**: 컨트롤러가 응답 객체를 다 만들어 반환한 뒤, Spring이 상태가 200이고 `GET`·`HEAD` 요청이면 `If-None-Match`와 비교해 같을 때 본문을 쓰지 않고 304로 끝냅니다. JSON 직렬화는 건너뛰지만, 컨트롤러 안의 Redis·DB 조회는 이미 끝난 뒤입니다.
- **컨트롤러 맨 앞에서 `WebRequest.checkNotModified(etag)` 호출**: 버전 번호만 읽어 ETag를 만든 뒤 이 메서드를 부르면, 조건이 맞을 때 Spring이 304 상태와 ETag 헤더를 설정하고 `true`를 돌려줍니다. 그때 컨트롤러가 바로 반환하면 나머지 조회와 조립을 하지 않습니다. 셋 중 서버 일을 가장 많이 줄이는 대신, 버전을 싸게 얻을 수 있어야 하고 버전 관리가 정확해야 합니다.

예시에 적용하면, 버전 번호 7은 DB 행에 있으므로 이것만 읽는 데도 DB 조회 한 번이 듭니다. Redis의 `product:42`에 버전도 함께 넣어 두었다면 Redis 읽기 한 번으로 비교할 수 있습니다. 어느 쪽이든 본문 조립과 직렬화, 20KB 전송은 아낍니다.

## 저장과 재사용을 막는 지시: no-cache, no-store, private

이름 때문에 가장 많이 헷갈리는 세 지시어입니다. **무엇을 막는가**로 나눠 봐야 합니다.

| 지시어 | 저장 | 다시 쓸 때 | 막는 대상 |
| --- | --- | --- | --- |
| `no-cache` | 해도 됨 | 쓸 때마다 서버에 검증하고 성공해야 씀 | 서버에 묻지 않고 다시 쓰는 것 |
| `no-store` | 하면 안 됨 | 해당 없음 | 저장 자체(모든 캐시) |
| `private` | 개인 캐시만 해도 됨 | 개인 캐시는 다른 지시에 따름 | 공유 캐시의 저장 |

- **`no-cache`는 "캐시하지 마라"가 아닙니다.** 저장은 허용하되 매번 검증하라는 뜻입니다. ETag와 함께 쓰면 내용이 그대로일 때 304로 본문 전송을 아끼면서도, 서버가 바뀐 내용을 놓치지 않습니다. 서버가 접속되지 않을 때 낡은 사본을 내주는 설정이 된 캐시도 `no-cache` 응답은 검증 없이 쓰지 못합니다.
- **`no-store`는 저장을 막지만, 비밀 보장 장치는 아닙니다.** 표준도 이 지시어를 따르지 않는 잘못된 캐시나 도청을 막지 못한다고 밝힙니다. 민감한 응답에 붙이는 최소한의 조치이고, 전송 암호화(HTTPS)와 인가는 별도로 필요합니다.
- **`private`는 공유 캐시만 막습니다.** 브라우저는 저장할 수 있습니다. 또 표준이 밝히듯 `private`는 "어디에 저장되는가"만 정할 뿐, 내용을 비밀로 지켜 주지 않습니다.

예시에 적용하면 다음과 같습니다.

- 모두에게 같은 상품 정보: `max-age=10, s-maxage=60`과 ETag.
- 로그인한 사용자의 쿠폰가: 공유 캐시에 저장되면 안 되므로 최소한 `private`. 브라우저에서도 쿠폰가가 바뀌면 바로 보여야 한다면 `private, no-cache`와 ETag.

같은 주소 `GET /products/42`에서 비로그인 응답에는 공유 캐시를 허용하고 로그인 응답에만 `private`를 붙이는 방식은 이것만으로는 동작하지 않습니다. 엣지에 비로그인 사본이 신선하게 저장돼 있으면, 로그인한 사용자의 요청도 같은 캐시 키로 그 사본을 받습니다. 앱 서버는 요청을 받지 못하므로 `private` 응답을 만들 기회도 없고, 로그인 사용자에게 쿠폰가가 빠진 화면이 나갑니다. 그래서 두 응답은 아래 "막는 방법"처럼 주소를 나누는 쪽이 확실합니다.
- 결제 정보처럼 사용자 기기에도 남기지 않을 응답: `no-store`.

## 개인화 응답이 공유 캐시로 새는 경로

### 사고는 이렇게 일어납니다

상품 상세를 빠르게 하려고 응답 전체에 `Cache-Control: max-age=10, s-maxage=60`을 붙였다고 합시다. 로그인 사용자의 응답에 쿠폰가가 섞인다는 사실은 잊었습니다.

1. 0초: 로그인한 앨리스가 엣지 A로 `GET /products/42`를 보냅니다. 요청에는 앨리스의 세션 쿠키가 있습니다. 엣지 A에 사본이 없으므로 앱 서버로 갑니다.
2. 앱 서버는 앨리스의 쿠폰가 8,000원이 든 응답에 위 헤더를 붙여 돌려줍니다. 엣지 A는 `s-maxage=60`을 보고 저장합니다. 캐시 키는 `GET /products/42`입니다.
3. 10초: 밥이 같은 엣지 A로 같은 요청을 보냅니다. 쿠키는 다르지만 캐시 키는 같고, 사본은 신선합니다. **엣지 A는 앨리스의 쿠폰가가 든 응답을 밥에게 줍니다.** 앱 서버는 이 요청을 받지도 않았으므로 앱 로그에는 아무 흔적이 없습니다.

가격이 아니라 이름, 주소, 장바구니였다면 개인 정보 유출 사고입니다.

### 왜 캐시가 막아 주지 않는가

표준에는 이를 막는 장치가 하나 있지만, 예시의 경우에는 작동하지 않습니다.

- **`Authorization` 헤더**: 요청에 이 헤더가 있으면 공유 캐시는 그 응답을 다른 요청에 다시 쓰면 안 됩니다. 단, 응답에 `public`, `s-maxage`, `must-revalidate` 중 하나가 있으면 허용됩니다. 즉 **`Authorization`으로 인증하는 API에 `s-maxage`를 붙이면 그 보호를 서버가 스스로 푸는 것**입니다.
- **쿠키**: 쿠키에는 이런 보호가 없습니다. 표준은 응답의 `Set-Cookie` 헤더조차 캐시를 막지 않으며, 그런 응답도 다시 쓰일 수 있다고 명시합니다. 예시의 앨리스처럼 쿠키로 로그인 상태를 전하는 웹 서비스는 응답 헤더 말고는 공유 캐시를 막을 수단이 없습니다.

CDN 제품은 쿠키가 있는 요청을 캐시하지 않는 기본 설정을 두기도 합니다. 그러나 그것은 제품 설정이지 표준의 약속이 아니고, 운영 중에 누군가 바꿀 수 있습니다. 서버가 확인하고 통제할 수 있는 것은 자기 응답 헤더뿐입니다.

### 막는 방법

- **개인화가 섞인 응답에는 `private`(필요하면 `no-store`)를 붙입니다.** 공유 캐시가 저장하지 않으므로 사고는 막히지만, 공유 캐시가 답할 수 없으니 로그인 사용자의 요청 중 브라우저 사본으로 끝나지 않는 것은 모두 앱 서버로 옵니다.
- **공용 부분과 개인 부분을 다른 주소로 나눕니다.** 상품 정보는 `GET /products/42`(공유 캐시 허용), 쿠폰가는 `GET /me/coupon-price?product=42`(`private`)처럼 나누면 공용 부분은 계속 CDN이 답합니다. 대가는 화면 하나에 요청이 둘로 늘고, 클라이언트가 둘을 합쳐야 한다는 것입니다.
- **`Vary: Cookie`로 키를 사용자별로 나누는 방법도 있지만, 사용자 사이의 공유가 사라집니다.** 같은 사용자가 같은 쿠키로 반복 요청할 때만 히트하므로, 여러 사용자의 요청을 하나의 사본으로 막는 공유 캐시의 이득은 거의 남지 않습니다. 다음 절에서 다룹니다.

## Vary는 캐시 키를 넓히고, 그만큼 히트를 나눕니다

### Vary가 하는 일

같은 URI라도 요청 헤더에 따라 다른 내용을 주는 경우가 있습니다. 예시의 상품 상세가 `Accept-Language`가 `ko`면 한국어, `en`이면 영어 설명을 준다고 합시다. 캐시 키가 URI뿐이라면 한국어 사본이 영어 사용자에게 갑니다.

`Vary: Accept-Language`를 응답에 붙이면, 캐시는 저장된 사본을 쓰기 전에 **새 요청의 `Accept-Language`가 사본을 만든 원래 요청의 값과 같은지** 확인합니다. 다르면 그 사본은 쓰지 않고, 같은 URI로 저장된 다른 사본 중 값이 맞는 것을 찾습니다. 맞는 사본이 하나도 없으면 요청을 서버로 보냅니다(가진 사본의 ETag를 실어 검증 요청으로 보낼 수도 있습니다). 결과적으로 캐시 키가 "URI + 지목한 헤더 값"으로 넓어집니다. 서버가 304로 답할 때도 200에 붙였을 `Vary`를 같이 보내야 합니다.

### 키가 넓어질수록 사본이 늘고 히트가 나뉩니다

Vary로 지목한 헤더에 실제로 들어오는 값의 종류만큼, URI 하나의 사본이 늘어날 수 있습니다. 실제로 저장되는 사본 수는 그 값들이 얼마나 자주 반복되는지와 캐시 공간에 달려 있습니다. 엣지 하나 기준으로 대략을 봅시다.

| 지목한 헤더 | 가질 수 있는 값 | 상품 42의 사본 수 | 엣지 하나에 들어오는 초당 25번의 요청이 나뉘는 정도 |
| --- | --- | --- | --- |
| 없음 | 1 | 1 | 모두 한 사본을 씀 |
| `Accept-Language`를 CDN 설정이 캐시 키를 만들기 전에 ko·en 둘로 정규화한다면 | 2 | 2 | 사본마다 일부씩. 사본마다 60초에 한 번은 미스 |
| `Accept-Language` 원본 값 | 브라우저마다 `ko-KR,ko;q=0.9,en;q=0.8`처럼 달라 수십~수백 | 수십~수백 | 대부분 처음 보는 값이라 미스가 늘어남 |
| `User-Agent` | 브라우저·버전·기기마다 다름 | 매우 많음 | 히트가 드묾 |
| `Cookie` | 사용자마다, 세션마다 다름 | 사용자 수만큼 | 같은 사용자의 반복 요청만 히트. 공유 캐시를 쓰는 의미가 거의 없음 |

(엣지 하나에 초당 25번은 500 ÷ 20으로 나눈 가상의 평균이고, 값의 개수도 설명을 위한 대략입니다. 정규화는 앱 서버 안에서 언어를 고르는 일과 다릅니다. 앱이 ko·en 중 하나로 답하더라도 CDN은 요청에 실려 온 원래 `Accept-Language` 값으로 사본을 비교하므로, 키를 두 종류로 줄이려면 CDN이나 그 앞단에서 값을 바꿔야 합니다. 히트율은 실제 요청에서 같은 값이 얼마나 자주 반복되는지에 달려 있어, 표의 "미스가 늘어남", "히트가 드묾"은 값이 고르게 흩어져 같은 값이 신선한 기간(여기서는 60초) 안에 다시 오는 일이 드문 경우를 가정한 것입니다. 값이 여러 개여도 각 값이 그 기간 안에 자주 반복되면 히트율은 높을 수 있습니다.)

결과는 세 가지입니다. 히트율이 떨어져 **앱 서버로 오는 요청이 늘고**, 같은 URI의 사본이 여럿 저장돼 **캐시 공간을 더 쓰며**, 그 공간 때문에 다른 URI의 사본이 먼저 밀려나 **다른 응답의 히트율도 떨어질 수 있습니다.** 표준이 정한 비교 규칙은 공백 차이나 순서처럼 의미가 같은 차이만 정규화할 수 있게 허용하므로, `ko-KR,ko;q=0.9`와 `ko`를 같다고 볼지는 캐시나 그 앞의 설정이 따로 정해야 합니다. CDN이 `Vary`를 어떻게 다루는지(어떤 헤더를 지원하는지, 값을 정규화하는지)는 제품마다 다르므로 그 제품의 문서를 확인해야 합니다.

`Vary: *`는 "요청 헤더 말고도 응답을 바꾸는 요인이 있다"는 뜻이어서, 표준은 이런 사본이 **어떤 요청과도 맞지 않는다**고 정합니다. 사실상 매번 서버에 가야 합니다.

판단 기준은 하나입니다. **`Vary`에는 응답 내용을 실제로 바꾸고, 값의 종류가 적은 헤더만 넣습니다.** 종류가 많은 값(쿠키, 기기 정보)이 응답을 바꾼다면, Vary로 키를 쪼개기보다 그 응답을 공유 캐시에서 빼거나(`private`) 주소를 나눕니다.

## 만료 순간을 넘기는 지시: stale-while-revalidate

`s-maxage=60`이 끝나는 순간, 엣지는 낡은 사본을 검증하거나 새로 받아야 합니다. 그동안 그 엣지로 들어온 요청은 앱 서버의 응답을 기다립니다. 앱 서버가 느리다면 60초마다 한 번씩 그 엣지의 사용자들이 느린 응답을 겪습니다.

`stale-while-revalidate`는 이 순간을 넘기는 확장 지시어입니다(HTTP 캐싱 표준 본문이 아니라 별도 확장 문서에 정의돼 있습니다). `Cache-Control: max-age=10, s-maxage=60, stale-while-revalidate=30`이면, 신선한 기간이 끝난 뒤 30초 동안 캐시는 **낡은 사본을 바로 내주면서 뒤에서 검증을 시작**해도 됩니다. 사용자는 기다리지 않고, 검증이 끝나면 사본이 새것으로 바뀝니다. 아래 그림과 계산은 CDN이 `s-maxage`와 이 지시어를 함께 받았을 때 이 지시어를 따른다고 가정한 것입니다. 그 가정이 맞는지는 이 절 끝의 주의 사항대로 따로 확인해야 합니다.

```text
나이 0초 ─────── 60초 ──────────── 90초 ──────▶
      [  신선함  ][ 낡았지만 바로 내주고 뒤에서 검증 ][ 낡음: 요청이 검증을 기다림 ]
```

그림의 칸 길이는 시간 비율과 맞지 않습니다. 이 창 안에서 요청이 하나도 오지 않으면 뒤에서의 검증도 시작되지 않으므로, 요청이 드문 URI는 창이 끝난 뒤 첫 요청이 결국 기다립니다.

대가와 주의할 점은 다음과 같습니다.

- **낡은 값이 보이는 최대 시간이 늘어납니다.** 예시에서 가격을 바꾼 뒤 옛 가격이 보일 수 있는 시간은 약 60초에서 약 90초로 늘어납니다. 확장 문서도 서버는 `max-age`와 `stale-while-revalidate`의 합을 "견딜 수 있는 가장 긴 신선한 기간"으로 잡으라고 권합니다.
- **`s-maxage`와 함께 쓸 때는 CDN 문서를 확인합니다.** 앞에서 본 대로 HTTP 캐싱 표준은 `s-maxage`가 붙은 응답을 공유 캐시가 낡은 채로 쓰지 못하게 하고, 확장 지시어가 기본 규칙을 바꿀 수 있다고도 정합니다. 두 문서만으로는 공유 캐시가 둘을 함께 받았을 때 무엇을 따를지 판단이 갈립니다. 실제 동작은 사용하는 CDN의 문서와 응답의 `Age` 관찰로 확인합니다.
- 서버가 응답하지 못할 때 낡은 사본으로 버티게 하는 `stale-if-error`도 같은 확장 문서에 있습니다. 같은 주의가 적용됩니다.

같은 확장 문서에 있는 이 동작은, 앱 안의 캐시로 치면 "만료가 지나도 낡은 값을 주면서 한 요청이 뒤에서 갱신하는" 논리 만료와 같은 생각입니다. 다른 점은 갱신을 앱이 아니라 캐시가 하고, 엣지마다 따로 한다는 것입니다.

## 지우고 싶을 때: HTTP 캐시 무효화의 한계

상품 42의 가격을 바꿨습니다. Redis 캐시라면 앱이 `product:42`를 지우면 다음 요청부터 모든 앱 서버가 새 값을 읽습니다. HTTP 캐시에는 이에 해당하는 표준 장치가 없습니다.

| 지우고 싶은 사본 | 방법 | 한계 |
| --- | --- | --- |
| 쓰기 요청이 지나간 캐시의 사본 | 표준: 캐시는 상태를 바꾸는 요청(`PUT`·`POST`·`DELETE` 등)에 오류가 아닌 응답(2xx·3xx)을 받으면 그 요청 주소의 사본을 무효화해야 함 | **그 요청이 지나간 캐시만** 무효화됨. 관리자가 엣지 B를 거쳐 가격을 바꿨다면 엣지 A와 사용자들의 브라우저 사본은 그대로임. 또 수정 API 주소(`PUT /admin/products/42`)가 조회 주소와 다르면, 반드시 무효화되는 것은 수정 주소뿐임. 같은 오리진의 다른 주소(응답의 `Location` 등)도 캐시가 무효화할 수는 있지만 보장되지 않음 |
| CDN 엣지의 사본 | CDN 업체가 제공하는 퍼지(purge) 기능. HTTP 표준 밖의 기능 | 모든 엣지에 퍼지가 퍼지는 데 걸리는 시간과 호출 한도는 제품마다 다름. 그 사이 일부 엣지는 옛 사본을 줌 |
| 사용자 브라우저의 사본 | **서버가 원하는 때 모든 사용자의 사본을 지울 방법이 없음**(그 사용자 자신의 쓰기 요청이 그 브라우저 캐시를 지나간 경우만 위 첫 줄이 적용됨) | 대부분의 사용자에게는 신선한 기간이 끝나기를 기다리는 수밖에 없음. 기간이 끝나도 브라우저가 스스로 검증하지는 않고, 그 뒤 같은 주소를 다시 요청할 때 검증함 |

여기서 무효화는 사본을 실제로 지우는 것과, 사본을 남겨 두되 "다음에 쓰기 전에 반드시 검증"으로 표시하는 것 둘 다를 뜻합니다. 어느 쪽이든 그 뒤로는 서버에 묻지 않고 쓰이지 않습니다. 마찬가지로 신선한 기간이 끝나는 것도 삭제가 아닙니다. 낡은 사본은 검증용으로 남을 수 있고, 반대로 공간이 부족하면 기한 전에 버려질 수도 있습니다.

여기서 설계 원칙이 나옵니다.

- **브라우저 쪽 `max-age`는 "지울 수 없어도 괜찮은 시간"으로 정합니다.** 예시의 10초는 "가격을 바꾼 뒤 10초 동안 브라우저가 서버에 묻지 않고 옛 가격을 다시 보여 줘도 된다"는 결정입니다. 사본이 그 뒤 사라진다는 뜻이 아니라, 그 뒤로는 검증을 거쳐야 다시 쓰인다는 뜻입니다. 그보다 오래 남으면 안 된다면 더 짧게 두거나 `no-cache`와 ETag로 매번 검증합니다.
- **공유 캐시에는 더 긴 `s-maxage`를 주고, 지워야 할 때 퍼지를 씁니다.** CDN은 우리가 계약한 업체라 퍼지 수단이 있지만, 브라우저에는 없기 때문입니다.
- **내용이 바뀌면 주소를 바꿀 수 있는 자원은 주소에 버전을 넣습니다.** 캐시 키는 URI이므로 `GET /products/42?v=8`은 v7의 사본과 다른 키입니다. 옛 사본을 지울 필요 없이 새 주소가 새 사본을 받습니다. 대신 클라이언트가 새 주소를 알아야 하므로, 정적 파일처럼 다른 문서(HTML 등)가 주소를 알려 주는 자원에 맞고, 사용자가 주소를 직접 쓰는 API에는 맞지 않습니다.

Redis 캐시와 HTTP 캐시를 함께 쓸 때, Redis 키를 지운 것은 앱 서버 뒤쪽만 정리한 것입니다. CDN이 `s-maxage` 동안 계속 답하고 있다면 그 요청은 애초에 앱 서버에 오지 않으므로, Redis를 아무리 빨리 갱신해도 사용자는 옛 값을 봅니다. **사용자가 낡은 값을 볼 수 있는 최대 시간은 앞단 HTTP 캐시들의 기한과 Redis TTL이 겹친 결과**로 따져야 합니다.

## Spring에서 지시를 붙이는 곳

- **`CacheControl`**: `CacheControl.maxAge(...)`, `noCache()`, `noStore()`로 시작해 `cachePrivate()`, `sMaxAge(...)`, `staleWhileRevalidate(...)`, `mustRevalidate()` 등을 이어 붙여 `Cache-Control` 값을 만드는 빌더입니다. `ResponseEntity.ok().cacheControl(...)`로 응답에 붙입니다. 지시어 이름과 값은 그대로 헤더에 쓰이므로, 위 절들의 뜻이 그대로 적용됩니다.
- **ETag**: `ResponseEntity`의 `eTag(...)` 또는 `WebRequest.checkNotModified(...)`. 서버 일이 어디까지 생략되는지는 위 "Spring에서 304를 만드는 세 가지 방법"에 있습니다.
- **Spring Security의 기본 헤더**: Spring Security를 쓰면 기본 설정에서 응답에 `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`, `Pragma: no-cache`, `Expires: 0`이 붙습니다. 응답에 이미 `Cache-Control`, `Expires`, `Pragma` 중 하나가 있거나 상태가 304이면 붙이지 않습니다. 따라서 Spring Security를 쓰는 앱은 아무것도 안 하면 기본적으로 저장되지 않는 쪽이고, 컨트롤러에서 `CacheControl`을 직접 붙인 응답만 그 지시를 따릅니다. 이 구조는 안전한 기본값이지만, **캐시를 허용하는 순간 그 응답이 개인화되지 않았는지 확인할 책임은 그 컨트롤러로 넘어옵니다.**

## 요청과 데이터가 늘면 무엇이 달라지는가

| 늘어나는 것 | 달라지는 것 | 확인할 것 |
| --- | --- | --- |
| 요청 수 | 공유 캐시가 히트를 유지하면 앱 서버로 오는 요청은 거의 늘지 않음. 대신 만료 순간마다 엣지당 미스가 생김 | 오리진 요청 수, 엣지의 요청 합치기 여부 |
| 엣지 수(지역 확대) | 엣지마다 따로 미스가 나므로 오리진 요청이 엣지 수에 비례해 늘어남 | 중간 계층 캐시 사용 여부 |
| URI 수(상품 수) | URI마다 사본이 필요하고, 인기 없는 URI는 사본이 밀려나 히트가 낮음 | URI별 히트율 분포 |
| `Vary`로 지목한 헤더 값의 종류 | 실제로 들어오는 값의 조합만큼 사본이 늘 수 있고, 같은 값이 드물게 반복될수록 히트가 나뉨 | 지목한 헤더의 값 종류 |
| 응답 크기 | 304가 아끼는 전송량이 커짐. 얕은 ETag는 응답마다 본문 전체를 메모리에 모으고 해시함 | 응답 크기 분포, 필터의 메모리 사용 |
| 내용이 바뀌는 빈도 | 신선한 기간 동안 낡은 값이 보이는 일이 잦아지고, 검증 결과가 200인 비율이 늘어 304의 이득이 줄어듦 | 변경 빈도와 허용 가능한 낡음 시간 |

## 흔한 오해 모아 보기

| 오해 | 실제 | 바로잡은 곳 |
| --- | --- | --- |
| `no-cache`는 캐시하지 말라는 뜻이다 | 저장은 허용하고, 쓸 때마다 검증하라는 뜻입니다. 저장을 막는 것은 `no-store`입니다 | 저장과 재사용을 막는 지시: no-cache, no-store, private |
| `Cache-Control`을 안 붙이면 캐시되지 않는다 | 200 같은 응답은 캐시가 기한을 추정해 저장할 수 있습니다 | 아무 지시도 없으면 캐시가 추정합니다 |
| `max-age`는 브라우저가 받은 때부터 센다 | 오리진 서버가 만들거나 마지막으로 검증한 때부터 셉니다. CDN에 머문 시간도 나이에 들어갑니다 | 나이는 받은 때가 아니라 오리진에서부터 셉니다 |
| 304가 많이 나가면 서버 부하가 줄었다 | 얕은 ETag에서는 핸들러와 Redis·DB 조회를 다 한 뒤 본문만 버립니다 | 304가 아끼는 것과 아끼지 않는 것 |
| 로그인 쿠키가 있는 요청은 CDN이 알아서 캐시하지 않는다 | 표준의 보호는 `Authorization`에만 있고, 쿠키와 `Set-Cookie`는 캐시를 막지 않습니다 | 왜 캐시가 막아 주지 않는가 |
| `s-maxage`는 CDN 수명만 바꾼다 | 낡으면 검증을 강제하고, `Authorization` 요청의 공유 캐시 저장을 허용하는 성질도 있습니다 | max-age와 s-maxage |
| `private`를 붙이면 내용이 안전하다 | 공유 캐시 저장만 막습니다. 내용의 비밀은 전송 암호화와 인가가 맡습니다 | 저장과 재사용을 막는 지시: no-cache, no-store, private |
| Redis 캐시를 지우면 사용자는 새 값을 본다 | 앞단 HTTP 캐시가 답하는 요청은 앱 서버에 오지 않습니다. 모든 사용자의 브라우저 사본을 서버가 원하는 때 지울 수도 없습니다 | 지우고 싶을 때: HTTP 캐시 무효화의 한계 |
| `s-maxage`가 60이면 엣지는 60초 동안 반드시 사본을 들고 있다 | 상한일 뿐이고, 공간이 부족하면 먼저 버릴 수 있습니다 | 앱 서버까지 오는 요청 수 |

## 근거

HTTP 표준은 번호로 고정된 RFC를 기준으로 합니다. RFC는 발행 후 내용이 바뀌지 않습니다. Spring은 이 저장소의 다른 문서가 쓰는 Spring Boot 3.5.16이 의존하는 버전(Spring Framework 6.2.19, Spring Security 6.5.11)의 태그 소스를 확인했습니다.

- [RFC 9111 HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html)
  - 1 Introduction: 공유 캐시는 여러 사용자가, 개인 캐시는 한 사용자가 쓰는 캐시. 신선한 응답은 검증 없이 재사용
  - 2 Overview of Cache Operation: 캐시 키는 최소한 메서드와 URI이며 많은 캐시가 GET만 저장해 URI만 키로 씀. Vary로 요청 헤더를 키에 더함
  - 3 Storing Responses in Caches: `no-store`가 있으면 저장 금지, 공유 캐시는 `private`이면 저장 금지, `Authorization` 요청은 허용 지시어가 없으면 공유 캐시 저장 금지, 추정 캐시 가능한 상태 코드면 저장 가능
  - 3.5 Storing Responses to Authenticated Requests: `must-revalidate`, `public`, `s-maxage`가 `Authorization` 요청 응답의 공유 캐시 재사용을 허용
  - 4 Constructing Responses from Caches: 재사용 조건(URI·메서드·Vary 일치, `no-cache`면 검증 필요, 신선·낡음 허용·검증 중 하나), 검증 없이 내줄 때 `Age` 생성, 안전하지 않은 메서드는 오리진까지 전달, 미스 때 요청을 합쳐도 됨(collapse)
  - 4.1 Calculating Cache Keys with the Vary Header Field: Vary가 지목한 요청 헤더가 원래 요청과 일치해야 재사용, 의미가 같은 차이만 정규화, `Vary: *`는 항상 불일치
  - 4.2 Freshness, 4.2.1 Calculating Freshness Lifetime: 신선함 = 신선한 기간 > 현재 나이, 기간은 `s-maxage`(공유 캐시) → `max-age` → `Expires − Date` 순
  - 4.2.2 Calculating Heuristic Freshness: 명시적 기한이 없을 때 추정 기한 허용, 구체 알고리즘은 정하지 않고 `Last-Modified` 이후 시간의 일부(예: 10%)를 권함
  - 4.2.3 Calculating Age: 나이는 오리진이 생성·검증한 뒤 경로상 캐시에 머문 시간과 전송 시간의 합
  - 4.2.4 Serving Stale Responses: `no-cache`, `must-revalidate`, `s-maxage` 등이 금지하면 낡은 응답을 내주지 못함. 확장(RFC 5861)으로 허용될 수 있음
  - 4.3.1·4.3.2 Validation: 저장된 ETag로 `If-None-Match` 검증, `If-None-Match`가 `If-Modified-Since`보다 우선
  - 4.3.4 Freshening Stored Responses upon Validation: 304를 받으면 저장된 사본의 헤더를 304의 헤더로 갱신
  - 4.4 Invalidating Stored Responses: 안전하지 않은 메서드의 성공 응답에 대상 URI를 무효화해야 하며, 그 요청이 지나간 캐시만 무효화됨
  - 5.2 Cache-Control: 지시어는 경로상 모든 수신자에게 적용되며 특정 캐시를 겨냥할 수 없음
  - 5.2.2.1 max-age, 5.2.2.4 no-cache, 5.2.2.5 no-store, 5.2.2.7 private, 5.2.2.10 s-maxage: 각 지시어의 정의. `no-store`·`private`가 비밀을 보장하지 않는다는 문장, `s-maxage`가 `proxy-revalidate` 의미를 포함한다는 문장 포함
  - 5.2.3 Extension Directives: 확장 지시어가 기본 요구사항을 바꿀 수 있음
  - 5.3 Expires: `max-age`가 있으면 `Expires` 무시
  - 7.3 Caching of Sensitive Information: `Set-Cookie`는 캐시를 막지 않으며 그런 응답도 재사용될 수 있음
- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)
  - 8.8.1 Weak versus Strong, 8.8.3 ETag: 강한·약한 ETag의 정의, 강한 조건을 만족하지 못하면 `W/`를 붙여야 함, 강한·약한 비교 표
  - 12.5.5 Vary: Vary는 캐시 키를 넓힘, `*`는 요청 밖의 요인을 뜻함
  - 13.1.2 If-None-Match: 약한 비교를 쓰며, 조건이 거짓이면 GET·HEAD에 304
  - 15.1 Overview of Status Codes 및 각 상태 코드 절: 200, 404 등이 추정 캐시 가능(heuristically cacheable)
  - 15.4.5 304 Not Modified: 200이었다면 보냈을 `ETag`, `Vary`, `Cache-Control` 등을 304에도 보내야 하며 본문이 없음
- [RFC 5861 HTTP Cache-Control Extensions for Stale Content](https://www.rfc-editor.org/rfc/rfc5861.html)
  - 3 The stale-while-revalidate Cache-Control Extension, 3.1 Example: 지정한 초만큼 낡은 응답을 내주며 막지 않고 검증, 창 안에 요청이 없으면 검증도 없음, `max-age`와 합을 견딜 수 있는 최대 기간으로 잡으라는 권고
  - 4 The stale-if-error Cache-Control Extension: 오류 시 낡은 응답 사용 허용
- Spring Framework 태그 [`v6.2.19`](https://github.com/spring-projects/spring-framework/tree/v6.2.19)
  - [`ShallowEtagHeaderFilter`](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-web/src/main/java/org/springframework/web/filter/ShallowEtagHeaderFilter.java): 클래스 주석 "this filter only saves bandwidth, not server performance". `isEligibleForEtag`가 GET·2xx·`no-store` 없음을 조건으로 함, `generateETagHeaderValue`가 본문 MD5로 ETag 생성, 응답 래퍼가 본문을 모아 둔 뒤 `copyBodyToResponse`로 보냄
  - [`HttpEntityMethodProcessor`](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-webmvc/src/main/java/org/springframework/web/servlet/mvc/method/annotation/HttpEntityMethodProcessor.java) `handleReturnValue`: 반환된 `ResponseEntity`가 200이고 GET·HEAD이면 `isResourceNotModified`로 비교해, 수정되지 않았으면 메시지 변환(`writeWithMessageConverters`) 전에 끝냄
  - [`WebRequest`](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-web/src/main/java/org/springframework/web/context/request/WebRequest.java) `checkNotModified(String)`: 주석의 사용 예가 `true`면 바로 반환해 이후 처리를 생략함
  - [`ServletWebRequest`](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-web/src/main/java/org/springframework/web/context/request/ServletWebRequest.java) `checkNotModified(String, long)`: RFC 9110 우선순위대로 조건 평가, `If-None-Match`는 약한 비교, GET·HEAD에서 수정되지 않았으면 304 설정과 ETag 헤더 추가
  - [`CacheControl`](https://github.com/spring-projects/spring-framework/blob/v6.2.19/spring-web/src/main/java/org/springframework/http/CacheControl.java): `maxAge`, `noCache`, `noStore`, `cachePrivate`, `sMaxAge`, `staleWhileRevalidate`, `mustRevalidate` 등과 `getHeaderValue`가 만드는 지시어 문자열
- Spring Security 태그 [`6.5.11`](https://github.com/spring-projects/spring-security/tree/6.5.11)
  - [`CacheControlHeadersWriter`](https://github.com/spring-projects/spring-security/blob/6.5.11/web/src/main/java/org/springframework/security/web/header/writers/CacheControlHeadersWriter.java): `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`, `Pragma: no-cache`, `Expires: 0`을 쓰되, 응답에 셋 중 하나가 이미 있거나 상태가 304이면 쓰지 않음
  - [`HeadersConfigurer`](https://github.com/spring-projects/spring-security/blob/6.5.11/config/src/main/java/org/springframework/security/config/annotation/web/configurers/HeadersConfigurer.java) `CacheControlConfig`: 생성자에서 `enable()`을 불러 기본으로 켜짐
  - [`HeaderWriterFilter`](https://github.com/spring-projects/spring-security/blob/6.5.11/web/src/main/java/org/springframework/security/web/header/HeaderWriterFilter.java): 기본값(`shouldWriteHeadersEagerly = false`)에서는 응답이 커밋될 때 헤더를 씀. 그래서 컨트롤러가 먼저 붙인 `Cache-Control`이 있으면 위 조건에 따라 덮어쓰지 않음
- 미확인: CDN 제품별 동작(요청 합치기, 중간 계층 캐시, `Vary` 처리와 정규화, 쿠키가 있는 요청의 기본 처리, 퍼지 전파 시간, `s-maxage`와 `stale-while-revalidate`를 함께 받았을 때의 동작)은 이 문서에서 확인하지 않았습니다. 본문에서는 "제품마다 다르다"로만 썼습니다.

## 실무 포인트

### 응답 종류별 선택

| 응답의 성격 | 예시에서 | 고를 지시 | 대가 |
| --- | --- | --- | --- |
| 모두에게 같고, 잠깐 낡아도 됨 | 상품 정보(개인화 필드를 다른 주소로 뺀 것) | `max-age`(짧게) + `s-maxage`(길게) + ETag | 최대 `s-maxage`까지 낡은 값이 보임. CDN이 `stale-while-revalidate`를 함께 따른다면 그만큼 더 늘어남 |
| 모두에게 같지만 바뀌면 바로 보여야 함 | 재고 수량 | `no-cache` + 싼 ETag | 매 요청 왕복 한 번. 서버는 버전 비교만큼 일함 |
| 사용자마다 다름 | 쿠폰가, 장바구니 | 공용 응답과 다른 주소 + `private`(+ 필요하면 `no-cache`) | 공유 캐시 이득 없음. 브라우저 사본으로 끝나지 않는 요청은 모두 앱 서버로 옴 |
| 기기에도 남기면 안 됨 | 결제 정보 | `no-store` | 캐시 이득 없음 |
| 내용이 바뀌면 주소도 바뀜 | 버전이 들어간 정적 파일 주소 | 긴 `max-age` | 주소를 알려 주는 쪽이 새 버전을 알아야 함 |

### 중요도별 점검 항목

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | 공유 캐시를 허용하는 응답(`s-maxage`, `public`, 또는 `private` 없이 `max-age`)에 사용자별 데이터가 섞이지 않았는지 확인 | 쿠키 로그인에는 표준의 보호가 없어, 한 사용자의 응답이 다른 사용자에게 갑니다. 앱 로그에도 남지 않아 발견이 늦습니다 |
| 필수 | `Authorization`으로 인증하는 API에 `s-maxage`·`public`·`must-revalidate`를 붙일 때 그 응답이 정말 공용인지 확인 | 이 지시어가 공유 캐시의 기본 보호를 풉니다 |
| 필수 | 브라우저 `max-age`를 "서버가 지울 수 없어도 되는 시간"으로 정함 | 브라우저 사본은 퍼지할 수 없습니다 |
| 필수 | 캐시되면 안 되는 응답에 의도를 헤더로 밝힘 | 지시가 없으면 캐시가 기한을 추정할 수 있습니다. Spring Security를 쓰면 기본값이 대신하지만, 그 기본을 끈 앱이나 Security 밖의 경로는 확인합니다 |
| 알면 유리 | 304로 서버 부하를 줄이려면 본문 전에 비교할 수 있는 버전을 둠 | 얕은 ETag는 전송량만 줄입니다 |
| 알면 유리 | `Vary`에는 값의 종류가 적은 헤더만 넣음 | 종류가 많으면 사본이 늘고 히트가 나뉩니다 |
| 알면 유리 | 낡은 값이 보일 최대 시간을 HTTP 캐시 기한과 Redis TTL을 합쳐 계산 | Redis를 지워도 앞단 캐시가 답하는 동안은 반영되지 않습니다 |
| 참고 | `stale-while-revalidate`·`stale-if-error`의 실제 동작 | CDN마다 다르므로 제품 문서와 `Age` 관찰로 확인합니다 |

### 관찰할 것

- **응답의 `Age` 헤더**: 0보다 크면 중간 캐시가 저장된 사본으로 답했다는 신호입니다. CDN이 붙이는 히트·미스 표시 헤더는 제품마다 이름이 다릅니다.
- **오리진(앱 서버)에 오는 요청 수와 CDN 전체 요청 수의 비율**: 공유 캐시가 실제로 얼마나 막고 있는지 보여 줍니다.
- **앱 서버 응답 중 304 비율과 그때의 처리 시간**: 304의 처리 시간이 200과 비슷하다면 얕은 ETag처럼 본문을 다 만든 뒤 비교하고 있을 가능성이 있습니다. 버전 조회나 공통 처리 자체가 비싼 경우도 같은 모습이므로, 304 요청에서 컨트롤러의 조회와 직렬화가 실제로 실행됐는지 추적이나 로그로 확인합니다.
- **배포 전 응답 헤더 점검**: 로그인 상태와 비로그인 상태로 같은 주소를 요청해 `Cache-Control`, `Vary`, `Set-Cookie`를 비교합니다.

### 증상과 확인 순서

**증상: "다른 사람의 정보가 보인다"는 문의가 들어왔다.**

1. 그 응답이 앱 서버에서 나왔는지 봅니다. 응답에 `Age`가 0보다 크면 중간 캐시가 저장된 사본으로 답했다는 신호입니다. 문의한 사용자의 요청이 앱 로그에 없다는 것도 단서이지만, 로그 누락이나 다른 경로일 수도 있으므로 응답 헤더와 요청 경로(CDN 로그)를 함께 확인합니다.
2. 해당 주소의 응답 헤더를 봅니다. `private`나 `no-store` 없이 `max-age`·`s-maxage`·`public`이 있으면 공유 캐시가 저장할 수 있었습니다.
3. 즉시 대응은 CDN에서 해당 주소를 퍼지하고 응답 헤더를 `private`나 `no-store`로 고쳐 배포하는 것입니다. 퍼지 전에 헤더를 먼저 고쳐야 퍼지 직후 다시 저장되지 않습니다. 이미 사용자 브라우저에 저장된 사본은 지울 수 없으므로, 그 브라우저가 서버에 묻지 않고 그 사본을 다시 보여 줄 수 있는 기간은 `max-age`로 판단합니다. 이미 화면에 표시된 정보는 헤더로 되돌릴 수 없으므로 노출 범위는 그 기간과 별도로 따집니다.

**증상: "가격을 바꿨는데 일부 사용자에게 옛 가격이 보인다."**

1. 그 사용자의 응답 `Age`와 `Cache-Control`을 봅니다. 신선한 기간 안이라면 설계대로 동작한 것입니다.
2. 기한보다 오래 보인다면 퍼지가 일부 엣지에 아직 퍼지지 않았는지, `stale-while-revalidate`·`stale-if-error`로 낡은 사본이 나가고 있는지 확인합니다.
3. 마지막으로 앱 서버 뒤쪽(Redis 캐시)의 값이 갱신됐는지 확인합니다. 앞단과 뒤쪽 중 어디가 낡았는지 나눠야 대응이 정해집니다.

## 말로 설명하기

### 30초 버전

요청은 우리 서버에 닿기 전에 브라우저 캐시와 CDN 같은 공유 캐시를 지나고, 이들은 저장된 응답으로 대신 답할 수 있습니다. 서버는 사본을 직접 쥐지 못하고 `Cache-Control`과 `ETag` 헤더로 "얼마나, 누구의 캐시에, 어떻게 확인하며" 쓸지만 지시합니다. 그래서 Redis 캐시처럼 잘못 넣은 것을 바로 지울 수 없습니다. 사용자별 응답을 공유 캐시에 허용하면 다른 사용자에게 가고, 브라우저 사본은 서버가 지울 수 없어 기한이 끝날 때까지 검증 없이 다시 쓰일 수 있습니다. 공용 응답만 공유 캐시에 두고, 기한은 지울 수 없어도 되는 만큼만 줍니다.

### 2분 버전

상품 상세 `GET /products/42`에 초당 500번 요청이 온다고 합시다. 응답에 `max-age=10, s-maxage=60`을 붙이면 브라우저는 10초, CDN 엣지는 60초 동안 서버에 묻지 않고 답합니다. 엣지가 20곳이면 앱 서버에 오는 요청은 60초에 약 20번으로 줄어듭니다. 이 기한은 사본이 오리진에서 만들어지거나 마지막으로 검증된 때부터 세므로, CDN에 오래 머문 응답은 브라우저가 거의 다시 쓰지 못합니다.

기한이 지나면 캐시는 사본을 버리지 않고 `If-None-Match`에 ETag를 실어 묻고, 그대로면 서버는 본문 없이 304로 답합니다. 304는 전송을 아끼지만 서버 일까지 아끼는지는 ETag를 만드는 방식에 달려 있습니다. Spring의 `ShallowEtagHeaderFilter`처럼 본문 해시로 만들면 핸들러와 Redis·DB 조회를 다 한 뒤 본문만 버립니다. 버전 번호처럼 본문 전에 알 수 있는 값으로 `checkNotModified`를 먼저 부르면 나머지 일을 건너뜁니다.

가장 큰 위험은 개인화입니다. 캐시 키는 기본적으로 URI라서, 쿠키를 키에 넣지 않는 캐시라면 로그인 쿠키에 따라 쿠폰가가 섞인 응답에 공유 캐시를 허용하면 다른 사용자가 그 응답을 받습니다. 표준의 보호는 `Authorization` 헤더에만 있고 쿠키에는 없으며, `s-maxage`는 그 보호마저 풉니다. 이런 응답은 주소를 나눠 개인 부분만 `private`로 공유 캐시에서 뺍니다. `Vary: Cookie`로 키를 쪼개면 사본이 사용자 수만큼 늘 수 있고, 같은 사용자의 반복 요청만 히트해 사용자 사이의 공유가 사라집니다.

마지막으로 지우는 문제입니다. 상태를 바꾸는 요청은 그 요청이 지나간 캐시만 무효화하고, CDN은 표준 밖의 퍼지 기능으로 지우며, 모든 사용자의 브라우저 사본을 서버가 원하는 때 지울 방법은 없습니다. 그래서 브라우저 `max-age`는 짧게, CDN `s-maxage`는 길게 두고 퍼지를 쓰며, 사용자가 낡은 값을 볼 수 있는 시간은 HTTP 캐시 기한과 Redis TTL을 함께 따져 정합니다.

### 예상 질문과 꼬리 질문

**Q. 이미 Redis 캐시가 있는데 HTTP 캐시까지 왜 신경 써야 하나요?**
막는 위치가 다릅니다. Redis는 요청이 앱 서버에 들어온 뒤 DB 조회를 줄이고, HTTP 캐시는 요청이 앱 서버에 오는 것 자체를 줄입니다. 예시에서 CDN이 초당 500번을 60초에 약 20번으로 줄이면 앱 서버의 스레드, 네트워크, Redis 호출이 모두 줄어듭니다. 또 신경 쓰지 않아도 HTTP 캐시는 존재합니다. 헤더가 없으면 캐시가 기한을 추정할 수 있으므로, 쓰지 않을 때도 그 의도를 밝혀야 합니다. (본문: "서버는 저장하지 않고, 지시만 합니다", "아무 지시도 없으면 캐시가 추정합니다")

- **꼬리: 그럼 HTTP 캐시만 두고 Redis를 빼도 되나요?**
  공유 캐시는 공용 응답에만 쓸 수 있고, 엣지마다 따로 미스가 나며, URI 수가 많으면 인기 없는 URI는 히트가 낮습니다. 로그인 사용자 응답처럼 `private`인 것은 브라우저 사본으로 끝나지 않는 한 모두 앱 서버로 옵니다. 그 요청들의 DB 부하는 여전히 Redis가 막아야 합니다. 둘은 대체가 아니라 층이 다른 캐시입니다.
- **꼬리: 둘을 함께 쓰면 낡은 값이 보이는 시간은요?**
  앞단 HTTP 캐시가 답하는 동안 요청은 앱 서버에 오지 않으므로, Redis를 갱신해도 반영되지 않습니다. 최악의 경우는 Redis에 낡은 값이 남은 시점에 CDN이 그 값을 받아 가는 경우로, 두 기한이 겹칩니다. 그래서 허용 가능한 낡음 시간은 두 층을 합쳐 계산합니다. (본문: "지우고 싶을 때: HTTP 캐시 무효화의 한계")

**Q. `no-cache`와 `no-store`의 차이는 무엇인가요?**
`no-cache`는 저장을 허용하되 쓸 때마다 서버에 검증하라는 뜻이고, `no-store`는 저장 자체를 막습니다. `no-cache`에 ETag를 붙이면 내용이 그대로일 때 304로 본문 전송을 아끼면서도 바뀐 내용은 놓치지 않습니다. (본문: "저장과 재사용을 막는 지시: no-cache, no-store, private")

- **꼬리: 민감한 정보에는 `no-store`면 충분한가요?**
  아닙니다. 표준도 `no-store`가 비밀을 보장하지 않는다고 밝힙니다. 지시를 따르지 않는 캐시나 도청은 막지 못하므로 HTTPS와 인가가 별도로 필요합니다. `no-store`는 정상적인 캐시에 사본이 남지 않게 하는 최소 조치입니다.
- **꼬리: `private`와 `no-cache`는 무엇이 다른가요?**
  막는 대상이 다릅니다. `private`는 공유 캐시의 저장을 막고 브라우저 저장은 허용합니다. `no-cache`는 어느 캐시든 저장은 허용하고 검증 없는 재사용을 막습니다. 사용자별 응답을 브라우저에서도 항상 최신으로 보여야 하면 둘을 함께 씁니다.

**Q. 개인화 응답이 CDN으로 새는 일은 왜 생기나요?**
캐시 키가 기본적으로 메서드와 URI라서, 쿠키를 키에 넣지 않는 캐시에서는 쿠키가 달라도 같은 주소의 요청은 같은 사본을 받습니다. 캐시는 본문에 개인 정보가 있는지 모르고 헤더만 보고 저장합니다. 표준은 `Authorization` 요청의 응답만 공유 캐시 재사용을 기본으로 막고, 쿠키에는 그런 보호가 없으며 `Set-Cookie`도 캐시를 막지 않습니다. (본문: "개인화 응답이 공유 캐시로 새는 경로")

- **꼬리: 우리는 `Authorization` 헤더로 인증하니 안전한가요?**
  응답에 `s-maxage`, `public`, `must-revalidate`를 붙이지 않았다면 표준상 공유 캐시가 다시 쓰지 않습니다. 하지만 성능을 위해 `s-maxage`를 붙이는 순간 그 보호는 풀립니다. 또 같은 서비스에 쿠키로 인증하는 경로가 섞여 있지 않은지도 확인해야 합니다.
- **꼬리: CDN이 쿠키 있는 요청을 캐시하지 않게 설정돼 있다면요?**
  그것은 제품 설정이고 표준의 약속이 아닙니다. 설정이 바뀌거나 CDN을 바꾸면 사라집니다. 서버가 확인하고 통제할 수 있는 것은 자기 응답 헤더이므로, 개인화 응답에는 `private`를 붙이는 것을 기본으로 둡니다.
- **꼬리: 사고를 알게 되면 무엇부터 하나요?**
  응답 헤더를 `private`나 `no-store`로 고쳐 배포한 뒤 CDN에서 해당 주소를 퍼지합니다. 순서를 바꾸면 퍼지 직후 다시 저장될 수 있습니다. 이미 브라우저에 남은 사본은 지울 수 없으므로, 그 사본이 검증 없이 다시 쓰일 수 있는 기간은 `max-age`로 판단합니다. 이미 화면에 표시된 정보는 별도로 따집니다. (본문: "증상과 확인 순서")

**Q. ETag로 304를 돌려주면 서버 부하가 줄어드나요?**
ETag를 어떻게 만드느냐에 달려 있습니다. 304는 본문 전송만 확실히 아낍니다. 본문 해시로 만드는 얕은 ETag는 핸들러, Redis·DB 조회, 직렬화를 다 한 뒤 비교하므로 서버 일은 거의 그대로입니다. 버전 번호처럼 본문 전에 싸게 얻는 값으로 핸들러 맨 앞에서 비교해야 서버 일까지 줄어듭니다. (본문: "304가 아끼는 것과 아끼지 않는 것")

- **꼬리: 그럼 `ShallowEtagHeaderFilter`는 왜 쓰나요?**
  컨트롤러를 고치지 않고 GET의 2xx 응답에 ETag를 붙이고, 그중 200 응답은 304로 바꿀 수 있습니다(`no-store`가 붙은 응답은 제외). 모바일처럼 전송량이 비싼 환경에서 큰 응답을 반복해 받는 경우에 이득이 있습니다. 대가로 응답 본문 전체를 메모리에 모았다가 보내므로 큰 응답에서는 메모리와 첫 바이트 시각이 나빠집니다.
- **꼬리: 버전 번호 ETag의 위험은요?**
  응답에 들어가는 모든 데이터의 변화가 그 번호에 반영돼야 합니다. 예시에서 상품 행의 버전만으로 ETag를 만들면, 상품 행 밖의 데이터(쿠폰가)가 바뀌어도 ETag가 같아 304가 나가고 옛 값이 계속 보입니다. 응답을 이루는 데이터의 출처가 여럿이면 각각의 버전을 함께 넣어야 합니다.
- **꼬리: 약한 ETag를 쓰면 무엇이 다른가요?**
  `If-None-Match` 비교는 표준상 약한 비교를 쓰므로 GET 검증 결과는 같습니다. 차이는 범위 요청이나 쓰기 조건처럼 강한 비교를 요구하는 곳에서 납니다. 다만 강한 ETag는 내용이 한 바이트라도 바뀌면 값이 바뀌어야 하므로, 그 약속을 지킬 수 없는 생성 방식이면 `W/`를 붙여야 합니다.

**Q. `Vary`는 언제 쓰고, 무엇이 위험한가요?**
같은 URI가 요청 헤더에 따라 다른 내용을 줄 때, 그 헤더를 캐시 키에 넣으라고 알리는 데 씁니다. 위험은 실제로 들어오는 값의 종류만큼 사본이 늘 수 있고 히트가 나뉜다는 것입니다. `Accept-Language` 원본 값이나 `User-Agent`, `Cookie`처럼 종류가 많고 같은 값이 드물게 반복되는 헤더는 히트율을 크게 떨어뜨리고 캐시 공간도 차지합니다. (본문: "Vary는 캐시 키를 넓히고, 그만큼 히트를 나눕니다")

- **꼬리: 언어별 응답이 꼭 필요하면요?**
  서버가 지원하는 언어 몇 개로 값을 정규화해 키를 만들거나, 언어를 주소에 넣는 방법이 있습니다. 표준의 비교 규칙은 의미가 같은 차이만 정규화하므로, `ko-KR,ko;q=0.9`를 `ko`로 묶는 일은 CDN 설정이나 주소 설계가 맡아야 합니다.
- **꼬리: `Vary`를 빠뜨리면요?**
  캐시가 첫 요청의 언어로 만든 사본을 다른 언어 사용자에게 줍니다. 개인화 사고와 같은 구조이며, 다만 섞이는 것이 개인 정보가 아니라 표현일 뿐입니다.

**Q. `stale-while-revalidate`는 왜 쓰고, 대가는 무엇인가요?**
신선한 기간이 끝난 순간 들어온 요청이 서버 응답을 기다리지 않게, 정해진 시간 동안 낡은 사본을 바로 내주며 뒤에서 검증하게 합니다. 대가는 낡은 값이 보일 수 있는 최대 시간이 그만큼 늘어난다는 것입니다. 창 안에 요청이 없으면 검증도 시작되지 않으므로 요청이 드문 URI에는 효과가 작습니다. (본문: "만료 순간을 넘기는 지시: stale-while-revalidate")

- **꼬리: `s-maxage`와 같이 쓰면 CDN이 따르나요?**
  표준 문서만으로는 판단이 갈립니다. HTTP 캐싱 표준은 `s-maxage` 응답을 공유 캐시가 낡은 채 쓰지 못하게 하고, 확장 지시어가 기본 규칙을 바꿀 수 있다고도 정합니다. 사용하는 CDN의 문서와 `Age` 관찰로 확인해야 합니다.

**Q. 가격을 바꿨을 때 캐시된 옛 응답을 어떻게 지우나요?**
층마다 다릅니다. 상태를 바꾸는 요청은 그 요청이 지나간 캐시에서 그 요청 주소를 반드시 무효화할 뿐이므로, 다른 엣지와 다른 사용자의 브라우저에는 효과가 없고 조회 주소가 다르면 그 무효화도 보장되지 않습니다. CDN 사본은 업체의 퍼지 기능으로 지우지만 전파 시간은 제품마다 다릅니다. 모든 사용자의 브라우저 사본을 서버가 지울 방법은 없어, 신선한 기간이 끝나길 기다려야 합니다. 그 뒤 같은 주소를 다시 요청할 때 브라우저가 검증합니다. (본문: "지우고 싶을 때: HTTP 캐시 무효화의 한계")

- **꼬리: 그럼 기한을 어떻게 정하나요?**
  브라우저 `max-age`는 "가격을 바꾼 뒤 이 시간 동안 옛 값이 보여도 된다"는 결정으로 짧게 둡니다. CDN `s-maxage`는 퍼지할 수 있으니 더 길게 두어 오리진 부하를 줄입니다. 바뀌면 곧바로 보여야 하는 응답은 `no-cache`와 싼 ETag로 매번 검증합니다.
- **꼬리: 주소에 버전을 넣는 방식은 API에도 쓰나요?**
  주소를 다른 문서가 알려 주는 정적 파일에는 잘 맞습니다. 캐시 키가 URI이므로 새 주소는 옛 사본과 무관하게 새로 받습니다. 사용자가 주소를 직접 쓰는 API에는 클라이언트가 새 버전을 알 방법이 없어 맞지 않습니다.

**Q. Spring Boot 앱에서 아무 설정도 안 하면 API 응답은 어떻게 캐시되나요?**
Spring Security를 쓰면 기본 설정에서 `Cache-Control: no-cache, no-store, max-age=0, must-revalidate`가 붙어 저장되지 않는 쪽입니다. 컨트롤러가 `CacheControl`로 직접 붙인 응답에는 이 기본 헤더를 쓰지 않습니다. Spring Security를 쓰지 않는다면 이 기본값이 없으므로, 캐시가 기한을 추정할 여지가 있습니다. (본문: "Spring에서 지시를 붙이는 곳", "아무 지시도 없으면 캐시가 추정합니다")

- **꼬리: 그럼 Security를 쓰면 개인화 사고는 걱정 없나요?**
  기본 상태에서는 그렇습니다. 하지만 성능을 위해 특정 응답에 `CacheControl`을 붙이는 순간 Security의 기본 헤더는 물러나고, 그 응답이 공용인지 확인할 책임은 그 컨트롤러로 넘어옵니다.

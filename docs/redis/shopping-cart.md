# 장바구니와 최근 본 상품: 사용자마다 작은 모음을 Redis에 둘 때 무엇을 잃어도 되는가

> **핵심 질문**: 장바구니와 최근 본 상품을 Redis에 둘까, DB에 둘까? Redis에 둔다면 어떤 자료형과 TTL로 두고, 잃어도 되는 것과 잃으면 안 되는 것을 어떻게 나누는가? 비회원으로 담은 장바구니는 로그인할 때 어떻게 합치는가?
>
> **범위**: 사용자 한 명에게 딸린 작은 모음(상품 수십 개 이하)을 사용자마다 키 하나로 두는 경우를 다룹니다. 주문, 결제, 재고 차감은 다루지 않으며 장바구니에서 주문으로 넘어가는 경계까지만 봅니다. Hash의 내부 표현은 [객체 하나를 String에 담을까, Hash에 담을까](./string-vs-hash.md)에, Sorted Set의 기본 성질은 [Redis 랭킹](./ranking.md)에 있으며, 이 문서는 필요한 만큼만 다시 씁니다.
>
> **출처와 설계의 구분**: 명령의 동작과 복잡도, 설정 기본값, Spring Data Redis의 동작은 "근거"에 적은 소스와 공식 문서로 확인했습니다. 키 이름, TTL 길이, 합치기 규칙, 상한 같은 선택은 공식 문서에 있는 패턴이 아니라 이 문서의 설계이며, 그런 문장에는 그 자리에 "이 문서의 설계"라고 적었습니다. 재현해 보지는 않았습니다.

## 배경 지식

### 이 문서의 예시: 회원 42의 하루

문서 끝까지 다음 장면 하나를 씁니다.

- 쇼핑몰에 상품 `p1001`, `p1002`, `p1003`, `p1004`가 있습니다.
- 회원 42는 지난주 노트북에서 로그인한 채 `p1002` 1개와 `p1003` 1개를 장바구니에 담아 두었습니다.
- 오늘 휴대폰에서는 로그인하지 않은 채 둘러보다가 `p1001` 1개와 `p1002` 2개를 담았습니다. 이때는 회원 번호를 모르므로, 서버는 브라우저 쿠키에 무작위 비회원 ID `g7f3`을 발급해 그 ID로 장바구니를 둡니다.
- 결제하려고 휴대폰에서 로그인합니다. 이 순간 비회원 장바구니와 회원 장바구니를 합쳐야 합니다.
- 같은 날 회원 42는 상품 상세 화면을 `p1001` → `p1002` → `p1001` → `p1003` → `p1004` 순서로 봅니다. "최근 본 상품"에는 중복 없이 최근 것부터 **3개**만 보여 줍니다. 실제 서비스라면 20개 정도겠지만, 손으로 따라가려고 3개로 줄였습니다.

키는 다음 셋입니다(이 문서의 설계).

| 키 | 담는 것 | 자료형 |
| --- | --- | --- |
| `cart:user:42` | 회원 42의 장바구니. 상품 ID → 수량 | Hash |
| `cart:guest:g7f3` | 비회원 `g7f3`의 장바구니. 상품 ID → 수량 | Hash |
| `recent:user:42` | 회원 42가 최근 본 상품 ID | Sorted Set(List와 비교는 본문에서) |

```text
 laptop (logged in)          phone (guest → login)
        |                           |
        | HINCRBY                   | HINCRBY
        v                           v
 +---------------------+    +----------------------+
 | cart:user:42        |    | cart:guest:g7f3      |
 |  p1002 -> 1         |<===|  p1001 -> 1          |   <=== merge at login
 |  p1003 -> 1         |    |  p1002 -> 2          |
 +---------------------+    +----------------------+

 checkout:  cart:user:42 (product IDs, qty)  +  DB/product service (price, stock)  -->  order
```

가는 화살표는 명령이 어느 키로 가는지, 굵은 화살표(`<===`)는 로그인 때 비회원 장바구니의 내용이 회원 장바구니로 옮겨 가는 방향입니다. 그림에는 `recent:user:42`와 Redis 서버 구성(어느 인스턴스에 두는지)을 뺐습니다. 최근 본 상품은 "최근 본 상품: 중복을 없애고 개수를 자르는 두 방법"에서, 인스턴스 구성은 "축출 정책이 장바구니를 조용히 지울 수 있습니다"에서 다룹니다. 장바구니에 가격과 재고가 없는 것은 일부러 뺀 것이 아니라 설계입니다. 이유는 "장바구니에는 상품 ID와 수량만 둡니다"에서 다룹니다.

메모리를 다루는 곳에서만 장면을 키웁니다. **키운 장면**에서는 장바구니가 있는 회원이 300만 명, 비회원 장바구니가 하루 50만 개 생깁니다. 이 숫자는 모두 가상 예시입니다.

### 이 문서가 기대는 원리들

- **경쟁 상태와 원자성**: 여러 요청이 같은 데이터를 "읽고 → 판단하고 → 쓰는" 사이에 끼어들면 결과가 틀어집니다. 원자성은 그 중간에 끼어들 수 없게 만드는 성질입니다. 이 주제에서는 노트북과 휴대폰이 같은 장바구니를 동시에 고치는 경우와, 로그인 때 두 장바구니를 합치는 경우에 쓰입니다. 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에 있습니다.
- **Redis의 명령, `MULTI`/`EXEC`, Lua 스크립트**: Redis는 명령 하나를 다른 연결의 명령과 섞지 않고 끝까지 실행합니다. `MULTI`/`EXEC`는 명령 여러 개를 대기열에 모았다가 한 번에 이어 실행하지만, 앞 명령의 결과를 보고 뒤 명령을 바꿀 수는 없습니다. Lua 스크립트는 읽고 판단하고 쓰는 일을 서버 안에서 한 번에 실행합니다. 이 주제에서는 "수량을 줄이고 0이면 지우기", "쓰고 TTL 다시 걸기", "합치기"를 어떻게 묶을지 고를 때 쓰입니다. 동작과 대가는 [Redis 원자성](./atomicity.md)에 있습니다.
- **멱등성**: 같은 요청을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질입니다. 응답을 못 받은 클라이언트는 다시 보내므로, 다시 보내도 수량이 두 배가 되지 않는지가 이 주제의 판단 기준 하나입니다. 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에, 요청 단위로 막는 방법은 [Redis 멱등 키](./idempotency-key.md)에 있습니다.
- **TTL과 축출**: TTL은 키에 붙인 만료 시각이고, 축출은 메모리 한도(`maxmemory`)에 닿았을 때 Redis가 정책(`maxmemory-policy`)에 따라 키를 골라 지우는 일입니다. 만료는 개발자가 "언제"를 정하고, 축출은 Redis가 "무엇을"을 정합니다. 이 주제에서는 오래 안 쓴 장바구니를 치우는 일(만료)과, 메모리가 찼을 때 장바구니가 사라지는 사고(축출)를 구분해야 합니다. 동작은 [TTL과 축출](./ttl-and-eviction.md)에 있습니다.
- **영속성과 복제**: Redis는 메모리에 데이터를 두므로, 재시작했을 때 무엇이 남는지는 디스크에 무엇을 적어 두었는지(RDB 스냅샷, AOF 로그)가 정합니다. 복제는 주 서버의 쓰기를 복제본에 비동기로 보내므로, 장애 조치 때 주 서버가 응답한 쓰기를 잃을 수 있습니다. 이 주제에서는 "장바구니를 Redis에만 두어도 되는가"의 판단 재료입니다. 동작은 [Redis 영속성](./persistence.md)과 [Redis 복제](./replication.md)에 있습니다.
- **직렬화**: 메모리 안의 객체를 저장할 수 있는 바이트열로 바꾸는 일입니다. Redis는 값의 바이트가 무엇을 뜻하는지 모르므로, 애플리케이션의 직렬화 설정이 "필드 이름이 상품 ID 그대로 저장되는가", "수량이 숫자로 저장되는가"를 정합니다. 직렬화기의 종류는 [직렬화기 고르기](./serializer.md)에 있습니다.
- **메모리 할당: 한 덩어리와 원소마다 따로**: 데이터를 메모리 조각 하나에 이어 담으면 조각 비용이 한 번만 들고, 원소마다 조각을 따로 받으면 원소 수만큼 포인터와 할당 비용이 붙습니다. 이 주제에서는 작은 Hash와 작은 Sorted Set이 한 덩어리(listpack)로 담기는지가 사용자 수백만 명분의 메모리를 바꿉니다. 원리는 [메모리 할당](../cs/memory-allocation.md)에 있습니다.

### Hash: 키 하나 안에 필드와 값의 쌍을 여럿 담는 자료형

- **한 줄**: 키 하나 아래에 "필드 → 값" 쌍을 여럿 담고, 필드 하나만 골라 읽고 쓸 수 있는 Redis 자료형입니다.
- **비유**: 회원마다 한 장씩 있는 주문서 용지입니다. 용지 한 장(키)에 "상품 ID / 수량" 줄이 여러 개 있고, 한 줄만 고쳐 쓸 수 있습니다. 예시의 `cart:user:42`가 이 용지이고, `p1002 → 1`, `p1003 → 1`이 두 줄입니다.
- **실제로는**:
  - 필드와 값은 모두 바이트열입니다. Redis는 "수량"이라는 개념을 모르고, 값이 정수처럼 생긴 문자열이면 정수 명령을 받아 줄 뿐입니다.
  - `HSET cart:user:42 p1001 3`은 그 필드의 값을 3으로 덮어쓰고, `HINCRBY cart:user:42 p1001 1`은 지금 값에 1을 더한 새 값을 돌려줍니다. 필드나 키가 없으면 0에서 더한 것처럼 새로 만듭니다. `HDEL`은 필드를 지우고, 마지막 필드를 지우면 키 자체가 사라집니다. `HGETALL`은 모든 필드와 값을, `HLEN`은 필드 수를 돌려줍니다.
  - Kotlin의 `MutableMap<String, String>` 하나를 원격에 둔 것과 비슷합니다. 맵을 통째로 직렬화해 저장하면 한 항목을 바꿀 때도 전체를 읽고 다시 써야 하지만, Hash는 명령 하나가 서버에 있는 필드 하나만 바꾸므로, 서로 다른 필드를 바꾸는 두 요청이 서로의 변경을 덮어쓰지 않습니다.
  - **비유와 다른 점**: 주문서 용지의 줄에는 순서가 있지만, Hash의 필드에는 의미 있는 순서가 없습니다. "담은 순서대로 보여 주기"가 필요하면 순서를 따로 담아야 합니다.
- **이 주제에서는**: 장바구니가 요구하는 "상품 하나 담기·빼기·수량 바꾸기"가 필드 하나짜리 명령이 됩니다.

필드가 적고 값이 짧은 Hash는 필드와 값을 한 덩어리의 메모리(listpack)에 이어 적고, 기준 버전의 기본 설정에서 필드가 512개를 넘거나 64바이트를 넘는 필드 이름이나 값이 하나라도 들어오면 필드마다 따로 담는 해시 테이블(hashtable)로 바뀝니다. 한 번 바뀌면 필드가 줄어도 돌아오지 않습니다. 예시의 장바구니는 필드가 몇 개이고 상품 ID와 수량이 짧으므로 listpack입니다. 두 표현의 메모리 차이와 바뀌는 조건은 [객체 하나를 String에 담을까, Hash에 담을까](./string-vs-hash.md)에서 다룹니다.

### Sorted Set과 List: 순서가 있는 두 모음

- **Sorted Set**: 원소마다 숫자 점수가 붙고, 원소가 중복 없이 점수 순으로 늘어선 자료형입니다. 이미 있는 원소를 `ZADD`로 다시 넣으면 원소가 하나 더 생기지 않고 점수만 바뀝니다. 최근 본 상품에서는 "본 시각"을 점수로 두면, 같은 상품을 다시 봤을 때 시각만 새것으로 바뀌어 중복이 저절로 없어집니다. 기본 설정에서 원소가 128개를 넘거나 64바이트를 넘는 원소가 들어오기 전까지는 한 덩어리(listpack)로 담기고, 한 번 바뀌면 원소를 지워 줄여도 돌아오지 않습니다. 자세한 성질은 [Redis 랭킹](./ranking.md)의 배경 지식에 있습니다.
- **List**: 원소를 넣은 순서대로 늘어선 자료형이며, 같은 값이 여러 번 들어갈 수 있습니다. `LPUSH`는 맨 앞(머리)에 넣고, `LRANGE key 0 2`는 앞에서 세 개를 읽습니다. Kotlin의 `ArrayDeque`처럼 양 끝에 넣고 빼기가 싸지만, 중간의 특정 값을 찾으려면 앞에서부터 훑어야 합니다. List도 작을 때는 한 덩어리(listpack)로 담깁니다. 최근 본 상품처럼 개수에 상한이 있고 상품 ID가 짧으면 그 덩어리를 벗어나지 않습니다.

둘 중 무엇을 고르는지는 "최근 본 상품: 중복을 없애고 개수를 자르는 두 방법"에서 다룹니다.

### 복잡도 표기

공식 문서는 명령마다 데이터가 커질 때 작업량이 어떻게 늘어나는지를 O(…)로 적습니다. O(1)은 크기와 상관없이 일정하다는 뜻이고, O(N)은 N에 비례한다는 뜻이며, O(log N)은 N이 두 배가 될 때 단계가 하나 정도 늘어난다는 뜻입니다. N이 무엇을 세는지는 명령마다 다릅니다. `HINCRBY`는 O(1), `HGETALL`은 Hash의 필드 수 N에 대해 O(N), `LREM`은 List 길이 N과 지운 수 M에 대해 O(N+M), `ZADD`는 Sorted Set의 원소 수 N에 대해 O(log N)입니다. 이 표기는 작업량이 늘어나는 모양이지 실제 시간이 아니며, 작은 모음에서는 명령의 실행 시간보다 네트워크 왕복이 지연의 큰 몫을 차지할 수 있습니다(측정하지 않은 추론이며, 실제 비중은 환경마다 재야 합니다). 왕복의 비용은 [왕복과 배치](../cs/round-trip-and-batching.md)에 있습니다.

## 먼저 정할 것: 이 데이터를 잃으면 무슨 일이 생기는가

자료형보다 먼저 정할 것은 "Redis가 이 데이터의 원본인가, 사본인가"입니다. **원본**은 둘이 다를 때 맞다고 보는 쪽이고, **사본**은 원본에서 다시 만들 수 있는 복사본입니다. 사본은 잃어도 다시 만들면 되지만, 원본을 잃으면 되돌릴 곳이 없습니다. 원본을 어떻게 정하는지의 일반 원리는 [두 저장소에 나눠 쓰기](../cs/dual-write.md)에 있습니다.

예시의 세 데이터는 잃었을 때의 결과가 다릅니다.

| 데이터 | 잃으면 | 다시 만들 수 있는가 | 이 문서의 판단 |
| --- | --- | --- | --- |
| 최근 본 상품 `recent:user:42` | 화면의 한 칸이 비어 보임 | 없음. 다만 없어도 서비스가 돌아감 | 잃어도 됨. 캐시와 같은 곳에 둬도 됨 |
| 비회원 장바구니 `cart:guest:g7f3` | 손님이 다시 담아야 함 | 없음 | 잃는 것을 받아들임. 짧은 TTL |
| 회원 장바구니 `cart:user:42` | 회원이 며칠 동안 담아 둔 것이 사라짐. 구매 포기로 이어질 수 있음 | 원본이 Redis뿐이면 없음 | 잃으면 안 되는 쪽. 아래 세 가지 중 하나를 고름 |

회원 장바구니를 두는 방법은 셋입니다.

| 방법 | 잃는 경우 | 비용 | 맞는 요구사항 |
| --- | --- | --- | --- |
| ① DB가 원본, Redis 없음 | DB 장애 수준 | 담기·빼기마다 DB 쓰기. 장바구니 화면마다 DB 읽기 | 장바구니를 오래(수개월) 보관, 장바구니 이탈 알림·분석에 씀, 다른 시스템이 장바구니를 읽음 |
| ② DB가 원본, Redis는 사본 | DB 장애 수준. Redis를 잃으면 DB에서 다시 채움 | 두 곳에 쓰는 순서와 어긋남을 맞추는 일 | 장바구니 읽기가 아주 많아 DB가 부담일 때 |
| ③ Redis가 원본 | 메모리가 차서 축출될 때, 재시작 때 영속성 설정에 따라, 장애 조치 때 복제가 따라오지 못한 쓰기 | 잃는 경우를 설정으로 막아야 함(아래 절들) | 장바구니가 짧게 살고, 잃었을 때의 결과(다시 담기)를 받아들일 수 있을 때 |

이 문서의 예시는 ③을 고릅니다(이 문서의 설계). ③이 덜어 주는 것은 ①의 비용 칸에 있는 것, 곧 담기·빼기마다의 DB 쓰기와 장바구니 화면마다의 DB 읽기입니다. 장바구니는 주문이 아니라 "사려고 모아 둔 목록"이라 몇 초치 변경을 잃어도 돈이 틀어지지 않고 회원이 다시 담으면 되는데, 이것은 ③을 고를 수 있게 해 주는 조건이지 ③을 골라야 하는 이유는 아닙니다. DB가 장바구니의 쓰기와 읽기를 무리 없이 감당한다면 저장소 하나만 지키면 되는 ①이 운영할 것이 적습니다. 대신 ③을 고르면 "축출 정책이 장바구니를 조용히 지울 수 있습니다"와 "재시작과 장애 조치 때 잃는 것"의 조건을 지켜야 하고, 지킬 수 없으면 ①로 갑니다. ②는 두 곳에 쓰는 비용을 내면서도 읽기 말고는 얻는 것이 적어, 장바구니 읽기가 DB를 실제로 압박한다는 지표가 있을 때만 고릅니다. DB와 캐시를 함께 쓸 때의 어긋남은 [캐시 갱신과 일관성](./cache-aside-consistency.md)에서 다룹니다.

**잘못 읽기 쉬운 점**: "장바구니를 잃으면 안 된다"는 말을 "주문과 같은 수준으로 지켜야 한다"로 읽으면 안 됩니다. 주문·결제는 응답한 쓰기를 하나도 잃으면 안 되지만, 장바구니는 대개 "드물게 마지막 짧은 구간의 변경을 잃는 것"까지는 받아들일 수 있고, "어느 날 조용히 수만 명분이 사라지는 것"은 받아들일 수 없습니다. 이 둘을 나눠 막는 것이 이 문서의 나머지입니다.

## 장바구니는 회원마다 Hash 하나에, 상품 ID를 필드로 둡니다

### 왜 String 하나에 JSON으로 두지 않는가

장바구니 전체를 JSON 문자열 하나로 `SET`할 수도 있습니다. 하지만 노트북에서 `p1003`을 담는 요청과 휴대폰에서 `p1002`를 빼는 요청이 거의 동시에 오면, 둘 다 같은 옛 JSON을 읽고 각자 고쳐 덮어쓰므로 먼저 쓴 쪽의 변경이 사라집니다. Hash에 상품 ID를 필드로 두면 두 요청이 서로 다른 필드를 명령 하나씩으로 바꾸므로 둘 다 남습니다. 이 차이는 [객체 하나를 String에 담을까, Hash에 담을까](./string-vs-hash.md)의 "두 요청이 서로 다른 필드를 바꾸면, String은 한쪽을 잃습니다"에서 다룹니다.

필드를 상품 ID로 두는 대신 "옵션까지 붙인 상품" 단위가 필요하면 필드 이름을 `p1002:red-M`처럼 상품 ID와 옵션 ID를 이어 만듭니다(이 문서의 설계). 필드 이름이 64바이트를 넘으면 그 장바구니는 hashtable로 바뀌므로, 옵션 이름 문자열이 아니라 짧은 ID를 씁니다.

### 담기·빼기·수량 바꾸기를 어떤 명령으로 하는가

화면의 버튼마다 뜻이 다르므로 명령도 다릅니다.

| 화면의 동작 | 명령 | 다시 보내면 | 예시 |
| --- | --- | --- | --- |
| "담기"(상세 화면) 또는 "+" 버튼 | `HINCRBY cart:user:42 p1001 1` | 두 번 더해짐 | `p1001`이 1 → 2 |
| 수량 입력 칸에 3을 적음 | `HSET cart:user:42 p1001 3` | 같은 결과(멱등) | `p1001`이 3 |
| "삭제" | `HDEL cart:user:42 p1001` | 같은 결과(멱등) | `p1001` 필드가 사라짐 |
| "−" 버튼 | 아래 스크립트 | 두 번 빠짐 | `p1002`가 1 → 0이면 필드 삭제 |
| 장바구니 화면 | `HGETALL cart:user:42` | 읽기 | 모든 상품 ID와 수량 |
| 장바구니 아이콘의 개수 | `HLEN cart:user:42` | 읽기 | 상품 종류 수 |

세 가지를 주의합니다.

**첫째, `HINCRBY`로 줄이면 0이나 음수가 남습니다.** `HINCRBY cart:user:42 p1002 -1`을 수량 1인 필드에 보내면 필드가 지워지지 않고 값 0이 남고, 한 번 더 보내면 −1이 됩니다. Redis가 `HINCRBY`를 거부하는 것은 기존 값이 정수가 아니거나 결과가 64비트 정수 범위를 넘을 때뿐이고, "수량은 1 이상"이라는 업무 규칙은 모르기 때문입니다. "줄이고, 0 이하가 되면 필드를 지우는" 일은 결과를 보고 판단해야 하므로 명령 하나로도, `MULTI`/`EXEC`로도 되지 않습니다. 스크립트 하나에서 `HINCRBY`의 결과를 보고 0 이하이면 `HDEL`하도록 묶거나, 앱이 지금 수량을 알고 있다면 "−"도 `HSET`(새 수량)이나 `HDEL`로 보냅니다. 다만 이 방법은 화면이 본 수량을 기준으로 덮어쓰므로, 그사이 다른 기기에서 담은 수량을 잃을 수 있습니다. 아래 둘째에서 말하는 `HSET`의 대가와 같습니다. 수량의 상한(예: 상품당 99개)도 같은 이유로 스크립트나 앱에서 검사합니다.

**둘째, 다시 보내도 되는 명령과 안 되는 명령이 섞여 있습니다.** 응답 시간 초과로 클라이언트가 "담기"를 다시 보내면 `HINCRBY`는 두 번 실행되어 수량이 2가 될 수 있습니다. 장바구니에서 이 결과는 회원이 화면에서 보고 고칠 수 있는 정도라, 이 문서는 "담기"를 `HINCRBY`로 두고 재시도 횟수를 제한하는 것으로 받아들입니다(이 문서의 설계). 받아들일 수 없으면 화면이 보고 있던 수량을 바탕으로 새 수량을 계산해 `HSET`으로 보내 멱등하게 만듭니다. 대가는 아래 "여러 기기가 같은 장바구니를 동시에 고칠 때"에서 보듯, 두 기기가 동시에 담으면 한쪽이 덮인다는 점입니다.

**셋째, 장바구니 줄 수에도 상한을 둡니다.** 상품 종류 수에 상한이 없으면 봇이나 버그가 키 하나에 필드 수천 개를 쌓을 수 있고, 512개를 넘으면 hashtable이 되어 그 키의 메모리와 `HGETALL` 응답이 커집니다. 담기 전에 `HLEN`으로 상한(예: 100종)을 검사합니다(이 문서의 설계). 검사와 담기 사이에 다른 요청이 끼어들면 상한을 조금 넘을 수 있으므로, 정확히 지켜야 하면 같은 스크립트에서 검사하고 담습니다.

### 쓸 때마다 TTL을 다시 겁니다

회원 장바구니에 TTL을 30일로 두고, 담기·빼기·수량 바꾸기가 있을 때마다 다시 30일로 겁니다(이 문서의 설계). 마지막으로 고친 날부터 30일 동안 아무 변경이 없으면 사라지는 셈입니다. 이렇게 쓸 때마다 만료를 미루는 방식을 **미끄러지는 만료(sliding expiration)**라고 합니다.

여기서 잘못 읽기 쉬운 점이 있습니다. `HINCRBY`, `HSET`, `HDEL`은 값을 "고치는" 명령이라 이미 걸린 TTL을 그대로 둡니다. 그러니 "처음 만들 때 한 번 TTL을 걸면 된다"고 생각하기 쉽지만, 두 경우에 TTL 없는 장바구니가 생깁니다.

1. **마지막 상품을 빼면 키가 사라집니다.** `HDEL`로 마지막 필드를 지우면 키도 지워지고 TTL도 함께 사라집니다. 다음 "담기"의 `HINCRBY`는 키를 새로 만들며, 이 키에는 TTL이 없습니다.
2. **두 명령 사이에서 끊깁니다.** `HINCRBY`와 `EXPIRE`를 따로 보내다가 그 사이에 앱이 죽거나 연결이 끊기면, 키는 만들어졌는데 TTL은 걸리지 않습니다.

TTL 없는 장바구니는 축출되지 않는 한 영원히 남아 메모리를 차지합니다. 그래서 쓰기 명령과 `EXPIRE`를 **항상 함께, 끊기지 않게** 보냅니다. 판단할 것이 없으므로 `MULTI`/`EXEC`로 묶어도 되고, 위의 "−" 스크립트처럼 이미 스크립트를 쓴다면 스크립트 끝에서 `EXPIRE`를 겁니다. 순서와 TTL 규칙은 [TTL과 축출](./ttl-and-eviction.md)의 "TTL은 언제 유지되고, 언제 사라지는가"에 있습니다.

읽을 때도 TTL을 미룰지 정해야 합니다. 장바구니 화면을 볼 때마다 `EXPIRE`를 보내면, 읽기 요청이 쓰기 명령 하나를 더 만들고 그 쓰기는 복제본과 AOF로도 전해집니다. 이 문서는 "고칠 때만 미룬다"를 고릅니다(이 문서의 설계). 보기만 하는 회원의 장바구니가 30일 뒤 사라지는 것을 받아들이는 대신이며, 받아들일 수 없으면 읽을 때는 남은 시간(`TTL`)이 일정 이하일 때만 `EXPIRE`를 보내 쓰기를 줄입니다.

필드마다 따로 만료를 거는 `HEXPIRE`도 있습니다. "담은 지 30일이 지난 상품만 빼기"처럼 상품별 기한이 필요할 때 쓸 수 있지만, 이 문서의 요구사항(오래 안 쓴 장바구니 전체를 치우기)에는 키 TTL이면 충분하므로 쓰지 않습니다.

## 장바구니에는 상품 ID와 수량만 둡니다

장바구니에 가격이나 재고 수량을 함께 적어 두면 화면을 그릴 때 상품 정보를 다시 읽지 않아도 되니 편해 보입니다. 하지만 그 값은 담은 순간의 사본이고, 장바구니는 30일을 삽니다. 그사이 가격이 바뀌거나 품절되면 장바구니의 값은 틀린 값이 됩니다. 그 값으로 주문 금액을 계산하면 옛 가격으로 팔게 되고, 클라이언트가 보낸 장바구니 값을 믿으면 조작된 가격으로 주문이 들어올 수 있습니다.

그래서 이 문서는 장바구니를 "무엇을 몇 개"까지만 담는 곳으로 둡니다(이 문서의 설계).

- **장바구니 화면**: `HGETALL`로 상품 ID와 수량을 읽은 뒤, 가격·이름·품절 여부는 상품 서비스나 상품 캐시에서 한 번에 읽어 붙입니다. 상품 캐시가 조금 늦은 값을 보여 주는 것은 화면에서는 받아들일 수 있습니다.
- **주문 화면과 주문 확정**: 가격과 재고는 반드시 원본(DB, 재고 서비스)에서 다시 읽습니다. 장바구니에 담긴 상품이 그사이 판매 중지되었으면 그 줄을 빼고 회원에게 알립니다.
- **주문이 끝나면**: 주문한 상품의 필드만 `HDEL`로 지웁니다. 일부만 골라 주문하는 화면이라면 장바구니 전체를 지우면 안 됩니다. 주문 확정과 장바구니 정리는 서로 다른 저장소의 쓰기라 한 번에 확정되지 않으므로, 장바구니 정리가 실패해도 주문은 유효하게 두고 정리는 다시 시도합니다. 다시 시도가 늦어지는 사이 회원이 같은 상품을 또 담았을 수 있으므로, 상품 ID만 보고 지우지 않고 지금 수량이 주문한 수량과 같은 필드만 지우는 스크립트로 정리합니다(이 문서의 설계). 수량이 다르면 주문 뒤에 바뀐 것으로 보고 남깁니다. 대가는 둘입니다. 주문 직후 수량만 고친 줄은 지워지지 않고 남고, 정리된 뒤나 정리 전에 같은 상품을 같은 수량으로 다시 담은 줄은 구별하지 못해 함께 지워집니다. 장바구니에 상품 ID와 수량만 두므로 같은 수량이면 같은 줄로 보이기 때문입니다. 다시 담은 줄까지 지켜야 한다면 줄마다 담은 시각 같은 식별 정보를 함께 두어야 합니다. 같은 주문이 두 번 만들어지지 않게 하는 일은 [Redis 멱등 키](./idempotency-key.md)에서 다룹니다.

## 로그인할 때 비회원 장바구니를 합칩니다

### 비회원 장바구니는 무작위 ID로 따로 둡니다

로그인 전에는 회원 번호가 없으므로, 처음 "담기"를 누를 때 추측할 수 없는 무작위 비회원 ID를 만들어 쿠키에 넣고 `cart:guest:<비회원 ID>`에 담습니다(이 문서의 설계). 순번처럼 추측할 수 있는 ID를 쓰면 다른 사람의 장바구니를 읽을 수 있습니다. 쿠키를 받은 시점이 아니라 **처음 담을 때** 키를 만드는 것도 중요합니다. Hash는 필드가 하나도 없으면 존재하지 않으므로, 방문할 때 장바구니 키를 미리 만들려면 자리표시 필드 같은 값을 넣게 되고, 그러면 봇과 검색 엔진 크롤러의 방문 수만큼 키가 생깁니다.

비회원 장바구니의 TTL은 쿠키 수명에 맞춰 7일로 둡니다(이 문서의 설계). 쿠키가 사라지면 그 장바구니는 아무도 찾지 못하는 키이므로, 쿠키보다 오래 살 이유가 없습니다.

### 합치는 규칙: 상품마다 더할까, 큰 값을 고를까

회원 42가 로그인하면 두 장바구니가 있습니다.

```text
cart:guest:g7f3 = { p1001: 1, p1002: 2 }
cart:user:42    = { p1002: 1, p1003: 1 }
```

`p1002`가 양쪽에 있는 것이 쟁점입니다. 규칙에 따라 결과가 다릅니다.

| 규칙 | 결과 `cart:user:42` | 장점 | 문제 |
| --- | --- | --- | --- |
| 더하기 | `p1001:1, p1002:3, p1003:1` | 담은 것을 하나도 버리지 않음 | 같은 상품을 기기마다 담은 것이 "더 사려는 뜻"이 아닐 때가 많음. 다시 실행하면 또 더해짐 |
| 큰 값 고르기 | `p1001:1, p1002:2, p1003:1` | 다시 실행해도 결과가 같음(멱등) | 정말 두 기기에서 따로 더 사려 했다면 덜 담김 |
| 비회원 쪽으로 덮기 | `p1001:1, p1002:2, p1003:1` | 방금 고른 것을 우선함 | 회원 쪽에만 있던 상품을 지우는 변형이면 지난주에 담은 것이 사라짐 |

이 예시에서는 큰 값 고르기와 덮기의 결과가 우연히 같습니다. 비회원 쪽 수량이 더 작았다면(예: `p1002:1`과 `p1002:3`) 큰 값 고르기는 3, 덮기는 1이 됩니다.

이 문서는 **상품마다 큰 값을 고르고, 회원 쪽에만 있는 상품은 그대로 둡니다**(이 문서의 설계). 결정적인 이유는 다시 실행해도 결과가 같다는 점입니다. 합치기는 로그인 요청 안에서 일어나므로 시간 초과로 재시도되거나, 휴대폰과 다른 탭에서 거의 동시에 로그인해 두 번 실행될 수 있습니다. 더하기 규칙은 두 번 실행되면 `p1002`가 3을 지나 5가 되지만, 큰 값 고르기는 몇 번을 실행해도 2입니다. 합친 뒤 줄 수가 상한을 넘으면, 회원 쪽 장바구니를 먼저 지키고 넘는 비회원 상품은 합치지 않은 채 회원에게 알립니다(이 문서의 설계).

### 합치는 순서: 회원 쪽을 먼저 쓰고, 비회원 쪽은 나중에 지웁니다

합치기는 두 키를 다룹니다. 두 키를 한 스크립트로 다루면 한 번에 끝나지만, 클러스터는 데이터를 여러 Redis 서버(노드)에 나눠 담는 구성이고, 키 이름으로 계산한 해시 슬롯 번호가 그 키가 놓일 노드를 정합니다. 스크립트 하나는 노드 하나에서 실행되므로, 한 스크립트의 키는 모두 같은 슬롯에 있어야 합니다. `cart:guest:g7f3`과 `cart:user:42`는 이름이 달라 대개 다른 슬롯, 곧 다른 노드일 수 있습니다. 해시 태그(키 이름의 `{` `}` 안만 슬롯 계산에 쓰게 하는 표기)로 슬롯을 맞추려면 두 키에 같은 태그가 있어야 하는데, 비회원 ID는 로그인 전에 회원 번호를 모른 채 만들어지므로 사용자마다 다른 태그를 미리 맞춰 둘 수 없습니다. 모든 장바구니에 같은 태그를 붙이면 슬롯은 맞지만 장바구니 전체가 노드 하나에 몰려 사용자별로 흩어지는 이점을 잃습니다. 규칙은 [Redis 원자성](./atomicity.md)의 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다"에 있습니다.

그래서 이 문서는 클러스터가 아니어도 같은 순서로 합칩니다(이 문서의 설계).

1. 앱이 `HGETALL cart:guest:g7f3`로 비회원 장바구니를 읽습니다. 비어 있으면 끝입니다.
2. 앱이 읽은 상품과 수량을 인자로 넘겨, `cart:user:42` **하나만** 다루는 스크립트를 실행합니다. 스크립트는 상품마다 지금 수량을 읽어 넘겨받은 수량이 더 크면 바꾸고, 없는 상품은 줄 수 상한 안에서 새로 넣고, 끝에서 TTL을 다시 겁니다. 반영한 상품과 줄 수 상한 때문에 넣지 않은 상품은 나눠 돌려주고, 앱은 넣지 않은 상품을 회원에게 알립니다. 스크립트 안에서는 다른 요청이 끼어들지 못하므로, 노트북에서 그 순간 들어온 "담기"와 섞여 수량이 틀어지지 않습니다.
3. 스크립트가 성공하면 `cart:guest:g7f3` 하나만 다루는 두 번째 스크립트로, 1에서 읽은 상품 중 **값이 그때와 같은 필드만** 지웁니다. 상한 때문에 넣지 않은 상품도 여기서 함께 지웁니다. 남겨 두면 다음 로그인 때마다 같은 상품이 다시 거절되고, 비회원 키도 TTL이 끝날 때까지 남기 때문입니다. 대가는 알림을 본 회원이 그 상품을 직접 다시 담아야 한다는 점입니다. 남은 필드가 없으면 키도 사라지므로 쿠키도 지웁니다. 1과 3 사이에 다른 탭에서 비회원으로 `p1004`를 담았거나 수량을 바꿨다면 그 필드는 남고, 다음 합치기에서 옮겨 갑니다. `DEL`로 통째로 지우면 1에서 읽지 않은 이 변경까지 사라집니다.

끊긴 자리에서 남는 상태를 대부분 다시 실행으로 고칠 수 있게 고른 순서입니다. 예외 하나는 아래 "다만"에서 다룹니다.

- 1과 2 사이, 또는 2 도중에 끊기면: 스크립트는 한 번에 실행되거나 실행되지 않습니다(중간에 에러가 나는 경우는 아래). 비회원 장바구니는 남아 있으므로 다음 로그인이나 다음 요청에서 다시 합치면 됩니다.
- 2와 3 사이에 끊기면: 회원 장바구니에는 이미 합쳐졌고 비회원 장바구니도 남아 있습니다. 다시 합쳐도 큰 값 고르기라 결과가 같습니다. 순서를 반대로(비회원 쪽을 먼저 지우고 회원 쪽에 쓰기) 하면 이 자리에서 끊겼을 때 비회원 장바구니를 잃습니다.

다만 큰 값 고르기의 멱등성에도 틈이 하나 있습니다. 2와 3 사이에서 끊긴 뒤 회원이 `p1002`를 1로 줄였는데, 그다음 합치기가 다시 실행되면 비회원 쪽의 2가 더 크므로 2로 되돌아갑니다. 3을 2 바로 뒤에 실행하고, 합치기를 로그인 직후 한 번만 시도하면 이 틈은 드물어집니다. 완전히 막아야 하면 스크립트가 "이 비회원 ID는 합쳤음"이라는 표시를 회원 키 쪽에 남기고 같은 비회원 ID를 다시 합치지 않게 합니다. 이 표시는 회원 장바구니 Hash 안의 특별한 필드로 둘 수 있지만, 그러면 장바구니를 읽는 모든 코드가 그 필드를 상품이 아니라고 알아야 하므로, 별도 키보다 실수하기 쉽습니다.

스크립트가 중간에 에러를 내면, 그때까지 실행한 쓰기는 되돌려지지 않습니다. 이 스크립트는 상품마다 "큰 값이면 쓰기"를 반복하므로, 일부 상품만 반영된 상태도 다시 실행하면 같은 결과로 수렴합니다. 이것도 큰 값 고르기를 고른 이유입니다. 스크립트 에러의 동작은 [Redis 원자성](./atomicity.md)의 "대가 2: 중간에 에러가 나도 이미 한 쓰기는 되돌리지 않습니다"에 있습니다.

## 여러 기기가 같은 장바구니를 동시에 고칠 때

회원 42의 노트북과 휴대폰이 거의 동시에 `cart:user:42`를 고치는 경우를 명령 단위로 봅니다. Redis는 두 명령을 섞지 않고 하나씩 끝까지 실행하므로, 결과는 Redis가 어느 명령을 먼저 실행했는가로 정해집니다. 연결 하나 안에서는 보낸 순서대로 실행되지만, 서로 다른 연결(두 기기의 요청이 지나간 서로 다른 앱 서버 연결)끼리는 어느 쪽이 먼저 실행될지 정해져 있지 않습니다(공식 문서 clients, "What Order are Client Requests Served In?"). 사용자가 먼저 누른 쪽이 먼저 실행된다는 보장도 없습니다.

| 노트북 | 휴대폰 | 결과 | 받아들일 수 있는가 |
| --- | --- | --- | --- |
| `p1003` 담기(`HINCRBY +1`) | `p1002` 삭제(`HDEL`) | 둘 다 반영 | 예. 서로 다른 필드 |
| `p1002` 담기(`HINCRBY +1`) | `p1002` 담기(`HINCRBY +1`) | `p1002`가 2 늘어남 | 예. 두 번 담은 뜻 그대로 |
| `p1002` 수량 3(`HSET`) | `p1002` 수량 5(`HSET`) | 나중에 실행된 쪽 | 예. 나중 쓰기가 이김 |
| `p1002` 수량 3(`HSET`) | `p1002` 삭제(`HDEL`) | 실행 순서에 따라 3이거나 없음 | 대개 예. 회원이 화면에서 다시 확인함 |

어느 경우에도 장바구니가 깨진 값(예: 다른 상품의 수량이 사라짐)이 되지는 않습니다. 필드 하나를 명령 하나로 바꾸기 때문입니다. 대신 한 기기의 화면은 다른 기기의 변경을 모르므로, 장바구니 화면을 열 때와 주문 화면으로 넘어갈 때 `HGETALL`로 다시 읽어 보여 줍니다. "읽은 수량을 보고 계산해 다시 쓰는" 코드(예: 앱이 `HGET`으로 2를 읽고 3을 `HSET`)는 이 표에 없는 경쟁 상태를 만듭니다. 두 기기가 같은 2를 읽고 각자 3을 쓰면 한 번의 담기가 사라집니다. 더하기는 `HINCRBY`로, 판단이 필요한 변경은 스크립트로 보내 앱이 읽은 값에 기대지 않습니다.

## 최근 본 상품: 중복을 없애고 개수를 자르는 두 방법

최근 본 상품의 요구사항은 세 가지입니다. 최근 것부터 보여 줄 것, 같은 상품은 한 번만 보여 줄 것, 개수에 상한(예시는 3개)을 둘 것. 회원 42가 `p1001` → `p1002` → `p1001` → `p1003` → `p1004` 순서로 봅니다.

### List: 지우고, 앞에 넣고, 자릅니다

상품을 볼 때마다 세 명령을 보냅니다.

1. `LREM recent:user:42 0 p1001`: 이미 있는 같은 상품을 모두 지웁니다(개수 인자 0은 "모두"). 
2. `LPUSH recent:user:42 p1001`: 맨 앞에 넣습니다.
3. `LTRIM recent:user:42 0 2`: 앞에서 3개만 남기고 나머지를 지웁니다.

```text
view p1001  ->  [p1001]
view p1002  ->  [p1002, p1001]
view p1001  ->  LREM removes old p1001  ->  [p1001, p1002]
view p1003  ->  [p1003, p1001, p1002]
view p1004  ->  [p1004, p1003, p1001, p1002]  --LTRIM 0 2-->  [p1004, p1003, p1001]
```

1번을 빼면 세 번째 조회 뒤 목록이 `[p1001, p1002, p1001]`이 되어, 화면 3칸 중 2칸이 같은 상품입니다. 공식 문서가 소개하는 "`LPUSH` 뒤 `LTRIM`으로 길이를 제한하는 목록" 패턴에는 중복 제거가 없으므로, 최근 본 상품에 쓰려면 `LREM`을 더해야 합니다.

비용은 `LREM`이 List를 앞에서부터 훑으므로 O(N+M)이고, `LTRIM`은 지우는 원소 수에 비례하며, `LPUSH`는 O(1)입니다. N이 상한(3이나 20)으로 묶여 있으므로 셋 다 작습니다.

세 명령 사이에 다른 요청이 끼어들 수 있다는 점은 주의합니다. 두 탭이 거의 동시에 같은 `p1001`을 열면, A의 `LREM` → B의 `LREM` → A의 `LPUSH` → B의 `LPUSH` 순서로 실행되어 `p1001`이 두 번 들어갈 수 있습니다. 판단할 것이 없으므로 세 명령과 `EXPIRE`를 `MULTI`/`EXEC`로 묶으면 됩니다.

### Sorted Set: 본 시각을 점수로 넣고, 오래된 것부터 자릅니다

상품을 볼 때마다 두 명령을 보냅니다. 점수는 본 시각(유닉스 시각 밀리초)이고, 아래 그림에서는 손으로 따라가려고 1, 2, 3…으로 줄였습니다.

1. `ZADD recent:user:42 <본 시각> p1001`: 없으면 넣고, 있으면 점수만 새 시각으로 바꿉니다. 중복이 저절로 없어집니다.
2. `ZREMRANGEBYRANK recent:user:42 0 -4`: 점수가 낮은(오래된) 쪽부터 센 순위 0부터 "뒤에서 네 번째"까지, 곧 최근 3개를 뺀 나머지를 지웁니다. 음수 순위는 점수가 높은 쪽 끝에서 셉니다.

```text
view p1001 @1  ->  {p1001:1}
view p1002 @2  ->  {p1001:1, p1002:2}
view p1001 @3  ->  {p1002:2, p1001:3}            (score of p1001 updated, no duplicate)
view p1003 @4  ->  {p1002:2, p1001:3, p1003:4}
view p1004 @5  ->  {p1002:2, p1001:3, p1003:4, p1004:5}  --ZREMRANGEBYRANK 0 -4-->  {p1001:3, p1003:4, p1004:5}
```

그림은 점수가 낮은 쪽부터 적었습니다. 화면에는 `ZRANGE recent:user:42 0 -1 REV`로 높은 쪽(최근)부터 읽어 `p1004, p1003, p1001`을 보여 줍니다. List의 결과와 같습니다.

비용은 `ZADD`가 O(log N), `ZREMRANGEBYRANK`가 O(log N + M)(M은 지운 수)입니다. 상한이 127 이하라면 쓸 때마다 잘라도 원소가 128개를 넘는 일이 없으므로, 상품 ID가 64바이트 이하인 한 처음부터 끝까지 한 덩어리(listpack)로 담깁니다.

### 무엇을 고르는가

| 기준 | List | Sorted Set |
| --- | --- | --- |
| 중복 제거 | `LREM`을 따로 보내야 함 | 자료형이 보장 |
| 조회당 명령 | 3개(+`EXPIRE`) | 2개(+`EXPIRE`) |
| 두 탭의 동시 조회 | 묶지 않으면 중복이 생길 수 있음 | 묶지 않아도 중복은 생기지 않음 |
| "7일 안에 본 것만" | 넣은 시각이 없어 할 수 없음 | `ZREMRANGEBYSCORE`로 시각 기준 삭제 가능 |
| 순서의 기준 | Redis가 실행한 순서 | 점수에 적은 시각. 앱 서버 시계가 다르면 순서가 조금 어긋날 수 있음 |
| 메모리(상한 20, 짧은 ID) | listpack 하나 | listpack 하나. 원소마다 점수를 더 담음 |

이 문서는 Sorted Set을 고릅니다(이 문서의 설계). 중복 제거를 자료형이 보장하므로 묶지 않아도 같은 상품이 두 번 보이지는 않고, 시각 기준 정리라는 선택지가 남기 때문입니다. 대가는 원소마다 점수를 더 담는 메모리와, 앱 서버 시계에 기대는 순서입니다. 최근 본 상품의 순서가 몇 밀리초 어긋나는 것은 화면에서 드러나지 않으므로 받아들입니다. 시각을 점수로 쓸 때 정수가 정확히 담기는 범위(2^53)는 [Redis 랭킹](./ranking.md)의 "점수는 64비트 부동소수점 수입니다"에 있으며, 밀리초 유닉스 시각은 그 범위 안입니다.

상한은 쓸 때마다 자르는 것이 핵심입니다. 자르지 않으면 많이 둘러보는 회원의 키가 계속 커져, 원소가 128개를 넘는 순간 스킵 리스트와 해시 테이블로 바뀌어 원소마다 메모리를 따로 씁니다. TTL은 30일로 두고 조회할 때마다 다시 겁니다(이 문서의 설계). 최근 본 상품은 조회 자체가 쓰기이므로 장바구니와 달리 "읽을 때 미루는" 고민이 없습니다. 다만 `EXPIRE`를 따로 보내다 끊기면 TTL 없는 키가 남는 틈은 장바구니와 같으므로, `ZADD`, `ZREMRANGEBYRANK`, `EXPIRE`는 `MULTI`/`EXEC`로 묶어 보냅니다.

최근 본 상품에서 판매 중지된 상품을 지울 필요는 없습니다. 읽을 때 상품 정보를 붙이면서 없는 상품을 걸러 보여 주면 됩니다. 걸러진 상품 때문에 화면에 3개보다 적게 보일 수 있으므로, 상한을 화면 칸 수보다 조금 크게 두는 것도 방법입니다.

## 축출 정책이 장바구니를 조용히 지울 수 있습니다

"Redis가 원본"을 고른 회원 장바구니에 가장 위험한 것은 장애가 아니라 정상 동작인 축출입니다. 메모리가 `maxmemory`에 닿으면 Redis는 `maxmemory-policy`에 따라 키를 골라 지우는데, 정책은 키가 장바구니인지 캐시인지 모릅니다.

| 장바구니가 있는 서버의 정책 | 메모리가 차면 |
| --- | --- |
| `allkeys-lru`, `allkeys-lfu` 등 | 오래 안 쓴(또는 덜 쓴) 키가 후보. 며칠 동안 안 들어온 회원의 장바구니가 상품 캐시와 똑같이 지워짐. 에러도 로그도 없이, 회원이 다음에 들어와서야 빈 장바구니를 봄 |
| `volatile-lru`, `volatile-ttl` 등 | TTL 있는 키만 후보. 장바구니는 30일 TTL이 있으므로 후보가 됨 |
| `noeviction`(기본값) | 아무 키도 지우지 않음. 대신 메모리를 늘리는 명령(`HINCRBY`, `HSET`, `ZADD` 등)이 OOM 에러를 받아 "담기"가 실패함. 읽기와 `HDEL`은 됨 |

"TTL을 붙였으니 `volatile-*` 정책에서 안전하다"는 기대는 반대입니다. `volatile-*`는 TTL 있는 키**만** 지우는 정책이라, 오래된 장바구니를 치우려고 붙인 TTL이 장바구니를 축출 후보로 만듭니다.

그래서 이 문서는 다음처럼 나눕니다(이 문서의 설계).

- **회원 장바구니와 비회원 장바구니**: 캐시와 다른 Redis 인스턴스에 두고 `noeviction`으로 둡니다. 메모리가 차면 "담기"가 실패하므로 알아챌 수 있고, 장바구니는 남습니다. 대신 메모리를 감시해 한도에 닿기 전에 늘리고, OOM 에러가 오면 앱이 "잠시 후 다시 시도" 같은 응답을 주도록 처리합니다.
- **최근 본 상품**: 잃어도 되므로 상품 캐시와 같은 캐시용 인스턴스(`allkeys-lru` 등)에 둬도 됩니다.

인스턴스를 나누지 못하고 한 서버에 섞어야 한다면, 어떤 정책으로도 "캐시는 지우고 장바구니는 지키기"를 정확히 할 수 없습니다. 정책별로 무엇이 지워지는지는 [TTL과 축출](./ttl-and-eviction.md)의 "예시에 정책을 대 보면"에 있습니다.

## 재시작과 장애 조치 때 잃는 것

`noeviction`으로 축출을 막아도, 장바구니를 Redis에만 두면 두 경우에 잃을 수 있습니다.

- **재시작**: 영속성을 끈 Redis는, 예전에 남겨 둔 RDB 파일도 없다면 다시 시작했을 때 비어 있습니다. 모든 회원의 장바구니가 사라집니다(남은 RDB 파일이 있으면 그 시점으로 돌아갑니다). 회원 장바구니를 원본으로 두려면 AOF(실행한 쓰기를 파일에 덧붙이는 방식)를 켭니다. 기본 `appendfsync everysec`이면 운영체제나 전원 장애 때 대개 마지막 1초 안팎의 변경을 잃을 수 있고, 디스크가 느리면 더 늘어납니다. RDB 스냅샷만 쓰면 마지막 저장 이후의 변경을 모두 잃을 수 있고, 그 간격은 저장 조건에 따라 분 단위가 될 수 있습니다. 조건은 [Redis 영속성](./persistence.md)에 있습니다.
- **장애 조치**: 복제는 비동기라, 주 서버가 응답한 "담기"가 복제본에 닿기 전에 주 서버가 사라지고 복제본이 새 주 서버가 되면 그 담기는 없던 일이 됩니다. 이것은 영속성 설정과 별개입니다. 조건은 [Redis 복제](./replication.md)의 "장애 조치 때 무엇을 잃는가"에 있습니다.

AOF를 켜고 디스크와 복제가 정상일 때 두 경우에 잃는 것은 대개 "마지막 짧은 구간에 고친 장바구니의 변경"이고, 회원이 다시 담으면 됩니다. 다만 Redis가 이 구간의 길이에 상한을 보장하지는 않습니다. 디스크가 느리면 AOF 쪽이, 복제본이 크게 뒤처져 있으면 장애 조치 쪽이 잃는 범위가 늘어납니다. 이 정도를 받아들일 수 없다면, 곧 "응답한 담기는 절대 잃으면 안 된다"가 요구사항이면, 그것은 Redis 설정이 아니라 "먼저 정할 것: 이 데이터를 잃으면 무슨 일이 생기는가"의 ①(DB가 원본)로 돌아가라는 신호입니다.

## 사용자와 요청이 늘면 무엇이 달라지는가

### 키 수는 "TTL 안에 담은 사람 수"를 따라갑니다

장바구니 키 수는 전체 회원 수가 아니라 **TTL 기간 안에 무언가를 담은 회원 수 + 비회원 장바구니 수**입니다. 회원 장바구니는 마지막 변경 뒤 30일, 비회원 장바구니는 7일 뒤 사라지므로, 키 수는 대략 "30일 동안 담은 회원 수 + 7일 동안 담은 비회원 수"에서 멈춥니다. 키운 장면이라면 회원 300만 개 + 비회원 하루 50만 개 × 7일 = 350만 개, 합해서 약 650만 개입니다(가상 예시). TTL을 늘리면 멈추는 지점이 그만큼 높아지고, TTL 없이 저장되는 키가 생기면 그 키들은 멈추지 않고 계속 쌓입니다.

키 수를 크게 늘리는 것은 대개 비회원 쪽입니다. 방문만으로 자리표시 값을 넣어 키를 만들거나, 로그인 뒤 비회원 장바구니를 지우지 않거나, 봇이 담기 API를 부르면 비회원 키가 회원 키보다 많아질 수 있습니다. `SCAN`으로 키 이름 접두사별 개수를 세어 보면 어느 쪽이 늘었는지 알 수 있습니다.

### 메모리는 표본을 재서 곱합니다

키 하나의 메모리는 자료형, 내부 표현, 필드 수, 직렬화 형식, 할당기에 따라 다르므로 이 문서는 숫자를 적지 않습니다. 대신 이렇게 추정합니다.

1. 운영과 같은 직렬화 설정으로, 실제 분포에 맞는 장바구니를 몇 가지(상품 1개, 5개, 20개) 만듭니다.
2. 키마다 `MEMORY USAGE`로 바이트 수를 잽니다. 이 값은 키 이름과 값, 관리 비용을 합친 추정치입니다. `OBJECT ENCODING`으로 listpack인지도 함께 봅니다.
3. 상품 수 분포로 가중 평균을 내어 예상 키 수를 곱합니다.
4. 이렇게 낸 값은 데이터의 몫일 뿐입니다. 연결 버퍼, 복제 버퍼, 할당기의 남는 칸은 따로 있으므로 `INFO memory`의 `used_memory`와 비교해 여유를 둡니다.

키 하나가 몇십 바이트 차이여도 650만 개를 곱하면 수백 MB 차이가 됩니다. 그래서 listpack을 유지하는지가 키 수가 많은 이 주제에서는 판단을 바꿉니다. 지표의 뜻은 [Redis 메모리 지표](./memory-metrics.md)의 "`MEMORY` 명령과 `redis-cli` 스캔으로 알 수 있는 것과 없는 것"에 있습니다.

### 명령은 작지만, 화면 하나가 부르는 수가 늘어납니다

장바구니 명령은 키 하나의 작은 모음을 다루므로 Redis 쪽 실행 시간은 작습니다. 그래서 상품 수에 따라 지연이 늘어난다면 먼저 의심할 곳은 앱이 보내는 왕복 수입니다(측정하지 않은 추론). 장바구니 화면에서 상품마다 `HGET`을 따로 보내거나 상품 정보를 하나씩 읽으면, 상품 수만큼 왕복이 늘어 상품이 많은 회원만 느려집니다. 장바구니는 `HGETALL` 한 번, 상품 정보는 한 번에 여러 개를 읽는 방식으로 왕복 수를 상품 수와 떼어 냅니다. 원리는 [왕복과 배치](../cs/round-trip-and-batching.md)에 있습니다.

사용자별 키는 이름이 서로 달라 클러스터의 여러 슬롯으로 흩어지므로, 데이터가 한 노드를 넘으면 클러스터로 나누기 좋은 데이터입니다. 다만 로그인 합치기처럼 두 키를 함께 다루는 곳은 앞에서처럼 키 하나씩 다루도록 짜 두어야 합니다.

## Spring에서 장바구니 키를 다룰 때

- **명령과 메서드**: Spring Data Redis의 `HashOperations`에서 `HINCRBY`는 `increment`, `HSET`은 `put`, `HDEL`은 `delete`, `HGETALL`은 `entries`입니다. `ListOperations`에서 `LREM`은 `remove`, `LTRIM`은 `trim`이고, `ZSetOperations`에서 `ZREMRANGEBYRANK`는 `removeRange`입니다.
- **필드 이름과 값의 직렬화기**: `RedisTemplate`은 Hash의 필드 이름과 값에 키·값과 별도의 직렬화기 칸을 두며, 정하지 않으면 Java 직렬화를 씁니다. 장바구니에서 이 기본값은 세 가지 문제를 만듭니다.
  - 필드 이름(상품 ID)에 Java 직렬화의 머리 바이트가 붙습니다. `redis-cli`나 다른 서비스가 평문 `p1001`로 `HDEL`이나 `HGET`을 보내면 같은 필드로 찾지 못합니다.
  - 수량을 `put`으로 Java 직렬화해 넣은 필드에 `increment`(`HINCRBY`)를 보내면, Redis가 그 바이트를 정수로 읽지 못해 "hash value is not an integer" 에러를 냅니다. 반대로 `increment`로 만든 필드의 값은 평문 숫자 문자열이라, 값 직렬화기가 Java 직렬화이면 `entries`로 읽을 때 역직렬화에 실패합니다.
  - 수량을 `put`으로 넣으면 `Integer`나 `Long`의 Java 직렬화 결과가 대개 64바이트를 넘어, 그 장바구니 키가 hashtable로 바뀝니다. `increment`만으로 만든 값은 평문 숫자라 이 문제가 없습니다. 이 전환과 위의 정수 변환 에러는 서로 다른 문제입니다.
  
  상품 ID와 수량은 문자열과 숫자 문자열이므로, 필드 이름과 값을 모두 `StringRedisSerializer`로 쓰는 `StringRedisTemplate`이 맞습니다. 수량은 `String`으로 받아 `toInt()`로 바꿉니다. 직렬화기의 차이는 [직렬화기 고르기](./serializer.md)에 있습니다.
- **쓰기와 TTL을 함께 보내기**: `HINCRBY`와 `EXPIRE`를 끊기지 않게 보내려면 `MULTI`/`EXEC`를 쓰거나 스크립트를 씁니다. `RedisTemplate`에서 `MULTI`/`EXEC`는 같은 연결에서 실행되어야 하므로 `SessionCallback` 안에서 보내야 하며, 그냥 이어 부르면 명령마다 다른 연결로 갈 수 있습니다. 다만 Lettuce 클러스터 연결에서는 Spring Data Redis가 `MULTI`를 서버로 보내지 않고 예외를 던지므로, 클러스터에서는 스크립트를 씁니다([Redis 원자성](./atomicity.md)). "−" 버튼이나 합치기처럼 이미 스크립트가 필요한 곳은 스크립트 끝에서 `EXPIRE`를 거는 편이 단순합니다.
- **장바구니를 객체 하나로 저장하지 않기**: 장바구니를 Kotlin 데이터 클래스로 만들어 `opsForValue().set()`으로 JSON 하나에 저장하면 "왜 String 하나에 JSON으로 두지 않는가"의 갱신 손실이 생기고, 옵션 없는 `SET`이라 걸려 있던 TTL도 사라집니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 본문 |
| --- | --- | --- |
| TTL을 처음에 한 번 걸면 계속 유지된다 | 고치는 명령은 TTL을 유지하지만, 마지막 상품을 빼면 키가 지워져 TTL도 사라지고, 다음 담기는 TTL 없는 키를 만듭니다 | 쓸 때마다 TTL을 다시 겁니다 |
| `HINCRBY -1`로 수량을 줄이면 0일 때 상품이 빠진다 | 필드에 0이나 음수가 남습니다. 결과를 보고 지우려면 스크립트가 필요합니다 | 담기·빼기·수량 바꾸기를 어떤 명령으로 하는가 |
| TTL을 붙이면 `volatile-*` 정책에서 장바구니가 안전하다 | 반대로 TTL 있는 키만 축출 후보가 됩니다 | 축출 정책이 장바구니를 조용히 지울 수 있습니다 |
| 장바구니에 가격을 담아 두면 주문이 빨라진다 | 담은 순간의 사본이라 30일 사이 틀린 값이 됩니다. 주문 때는 원본에서 다시 읽습니다 | 장바구니에는 상품 ID와 수량만 둡니다 |
| `LPUSH` + `LTRIM`이면 최근 본 상품이 된다 | 중복이 남습니다. `LREM`을 더하거나 Sorted Set을 씁니다 | List: 지우고, 앞에 넣고, 자릅니다 |
| 합치기는 더하기가 자연스럽다 | 재시도되면 또 더해집니다. 큰 값 고르기는 다시 실행해도 같습니다 | 합치는 규칙: 상품마다 더할까, 큰 값을 고를까 |
| 장바구니 키 수는 회원 수다 | TTL 기간 안에 담은 회원과 비회원 수이며, 비회원 쪽이 더 빨리 늘 수 있습니다 | 키 수는 "TTL 안에 담은 사람 수"를 따라갑니다 |

## 말로 설명하기

### 30초 버전

장바구니와 최근 본 상품은 사용자마다 작은 모음이라 키 하나씩 두기 좋습니다. 장바구니는 회원마다 Hash 하나에 상품 ID를 필드, 수량을 값으로 두어 여러 기기의 변경이 서로 덮이지 않게 하고, 최근 본 상품은 본 시각을 점수로 둔 Sorted Set으로 중복을 없애고 쓸 때마다 상한으로 자릅니다. 먼저 정할 것은 잃어도 되는가입니다. 최근 본 상품은 잃어도 되지만 회원 장바구니를 Redis에만 둔다면, 캐시와 다른 인스턴스에 `noeviction`, AOF, 쓰기마다 TTL 다시 걸기로 조용한 손실을 막아야 하고, 가격과 재고는 주문 때 원본에서 읽습니다.

### 2분 버전

장바구니를 DB에 둘지 Redis에 둘지는 먼저 잃었을 때의 결과로 Redis에 둘 수 있는지를 거르고, 그다음 담기·조회마다의 DB 접근을 덜어 낼 필요가 있는지로 정합니다. 장바구니는 주문이 아니라 사려고 모아 둔 목록이라, 드물게 마지막 짧은 구간의 변경을 잃는 것은 받아들일 수 있어도 메모리가 찼다고 수만 명분이 에러 없이 사라지는 것은 안 됩니다. 그래서 Redis를 원본으로 쓰려면 캐시와 다른 인스턴스에 `noeviction`으로 두고 AOF를 켭니다. 그래도 장애 조치 때 복제가 따라오지 못한 쓰기는 잃을 수 있으므로, 그것조차 안 되면 DB가 원본입니다.

자료형은 Hash입니다. JSON 하나로 두면 두 기기의 동시 변경이 서로를 덮지만, 필드 단위 명령은 다른 상품끼리 섞이지 않습니다. 대신 `HINCRBY -1`은 0에서 필드를 지우지 않으므로 결과를 보고 지우는 스크립트가 필요하고, 마지막 상품을 빼면 키와 TTL이 함께 사라져 다음 담기가 TTL 없는 키를 만들므로 쓰기마다 `EXPIRE`를 묶어 보냅니다. 장바구니에는 상품 ID와 수량만 두고 가격과 재고는 주문 때 원본에서 다시 읽습니다.

로그인 때는 비회원 장바구니를 상품마다 큰 값으로 회원 장바구니에 합칩니다. 더하기는 재시도되면 또 더해지지만 큰 값 고르기는 몇 번 실행해도 같습니다. 두 키가 클러스터에서 다른 슬롯일 수 있으므로, 비회원 쪽을 읽고 회원 키 하나만 다루는 스크립트로 쓴 뒤, 읽은 값 그대로인 비회원 필드만 지웁니다. 끊기면 대개 다시 실행하면 되지만, 그사이 회원이 줄인 수량이 되돌아갈 수 있는 틈은 남습니다. 최근 본 상품은 Sorted Set에 `ZADD`와 `ZREMRANGEBYRANK`로 넣고 자르며, List로 하려면 `LREM`으로 중복을 지우고 명령을 묶어야 합니다. 키 수는 TTL 안에 담은 사람 수를 따라가므로 TTL과 비회원 키 생성 시점이 메모리를 정하고, 메모리는 `MEMORY USAGE` 표본에 키 수를 곱해 추정합니다.

### 예상 질문과 꼬리 질문

**Q. 장바구니를 왜 DB가 아니라 Redis에 두나요?**
반드시 Redis여야 하는 것은 아닙니다. Redis를 원본으로 두는 이득은 담기·빼기와 장바구니 화면마다의 DB 접근을 덜어 내는 것이고, 잃어도 되는가는 그것을 고를 수 있는 조건일 뿐입니다. DB가 그 부하를 감당한다면 저장소 하나만 지키는 쪽이 운영할 것이 적습니다. 장바구니를 오래 보관하거나, 이탈 알림·분석에 쓰거나, 다른 시스템이 읽는다면 DB가 원본이어야 합니다. 이 문서는 장바구니가 짧게 살고 잃었을 때 회원이 다시 담으면 되는 경우에만 Redis를 원본으로 고르며, 그 조건으로 축출 차단, 영속성, 쓰기마다 TTL을 요구합니다. (본문: "먼저 정할 것: 이 데이터를 잃으면 무슨 일이 생기는가")

- **꼬리: DB를 원본으로 두고 Redis를 캐시로 앞에 두면 둘의 장점을 다 얻지 않나요?**
  읽기 부담은 줄지만, 담기마다 두 곳에 써야 하고 그 사이에 어긋남이 생깁니다. 장바구니는 대개 쓰기와 읽기가 같은 사람에게서 비슷하게 오므로 캐시가 아끼는 것이 적습니다. 장바구니 읽기가 DB를 실제로 압박한다는 지표가 있을 때 고릅니다.
- **꼬리: AOF를 `always`로 켜면 DB만큼 안전한가요?**
  재시작 때의 손실은 줄지만, 비동기 복제의 장애 조치 손실은 영속성 설정과 별개라 막지 못합니다. "응답한 담기는 절대 잃으면 안 된다"가 요구사항이면 Redis 설정으로 풀 문제가 아니라 DB가 원본이어야 한다는 뜻입니다. (본문: "재시작과 장애 조치 때 잃는 것")

**Q. 장바구니에 TTL을 붙이면 무엇이 위험한가요?**
두 가지입니다. 첫째, 캐시와 같은 인스턴스에 `volatile-*` 정책이면 TTL이 장바구니를 축출 후보로 만듭니다. 둘째, TTL을 처음 한 번만 걸면 마지막 상품을 뺄 때 키와 함께 TTL이 사라지고, 다음 담기가 TTL 없는 키를 만들어 영원히 남습니다. 그래서 장바구니는 `noeviction` 인스턴스에 두고, 쓰기마다 `EXPIRE`를 묶어 보냅니다. (본문: "쓸 때마다 TTL을 다시 겁니다", "축출 정책이 장바구니를 조용히 지울 수 있습니다")

- **꼬리: `noeviction`이면 메모리가 찼을 때 어떻게 되나요?**
  키는 지워지지 않고 `HINCRBY`, `HSET` 같은 쓰기가 OOM 에러를 받습니다. 읽기와 `HDEL`은 됩니다. 담기가 실패하는 것은 장애지만 알아챌 수 있고 데이터는 남습니다. 그래서 메모리를 감시해 한도 전에 늘리는 일이 함께 따라옵니다.
- **꼬리: 읽을 때도 TTL을 미뤄야 하나요?**
  이 문서는 고칠 때만 미룹니다. 읽을 때마다 `EXPIRE`를 보내면 읽기마다 쓰기가 하나 생겨 복제와 AOF에도 전해지기 때문입니다. 보기만 하는 회원의 장바구니가 사라지면 안 되면, 남은 시간이 일정 이하일 때만 미룹니다.

**Q. 수량 변경은 `HINCRBY`와 `HSET` 중 무엇으로 하나요?**
화면의 뜻에 따릅니다. "+"나 "담기"는 더하기라 `HINCRBY`가 맞고, 두 기기에서 동시에 담으면 둘 다 반영됩니다. 다만 재시도되면 두 번 더해집니다. 수량 입력 칸은 `HSET`이며 다시 보내도 결과가 같지만, 두 기기가 동시에 쓰면 나중 쓰기가 이깁니다. "−"는 0에서 필드를 지워야 하므로 스크립트입니다. (본문: "담기·빼기·수량 바꾸기를 어떤 명령으로 하는가")

- **꼬리: 앱이 `HGET`으로 지금 수량을 읽고 하나 더해 `HSET`하면 안 되나요?**
  두 기기가 같은 값을 읽고 각자 쓰면 한 번의 담기가 사라집니다. 더하기는 서버에서 계산하는 `HINCRBY`로, 판단이 필요한 변경은 스크립트로 보내 앱이 읽은 값에 기대지 않게 합니다. (본문: "여러 기기가 같은 장바구니를 동시에 고칠 때")

**Q. 비회원 장바구니를 로그인 때 어떻게 합치나요?**
상품마다 큰 값을 고르고, 회원 쪽에만 있는 상품은 둡니다. 합치기는 로그인 재시도나 동시 로그인으로 두 번 실행될 수 있는데, 큰 값 고르기는 몇 번 실행해도 결과가 같기 때문입니다. 순서는 비회원 쪽을 읽고, 회원 키 하나만 다루는 스크립트로 쓰고, 성공하면 읽은 값 그대로인 비회원 필드만 지웁니다. 그사이 비회원으로 새로 담은 상품을 지우지 않기 위해서입니다. (본문: "로그인할 때 비회원 장바구니를 합칩니다")

- **꼬리: 두 키를 한 스크립트로 처리하면 더 간단하지 않나요?**
  클러스터에서는 한 스크립트의 키가 같은 슬롯이어야 하는데, 비회원 ID는 회원 번호를 모른 채 만들어지므로 사용자마다 같은 해시 태그를 미리 맞출 수 없고, 모든 장바구니에 공통 태그를 붙이면 노드 하나에 몰립니다. 클러스터가 아니라도 회원 키 하나만 다루는 순서로 짜 두면 나중에 옮길 때 바꿀 것이 없습니다.
- **꼬리: 회원 쪽에 쓰고 비회원 쪽을 지우기 전에 죽으면요?**
  둘 다 남아 있으므로 다시 합치면 됩니다. 큰 값 고르기라 결과가 같습니다. 반대 순서로 하면 그 자리에서 비회원 장바구니를 잃습니다. 다만 그사이 회원이 수량을 줄였다면 다시 합칠 때 비회원 쪽의 큰 값으로 되돌아갈 수 있어, 지우기를 쓰기 바로 뒤에 하고, 완전히 막으려면 합친 비회원 ID를 표시해 둡니다.
- **꼬리: 더하기 규칙을 원하는 서비스라면요?**
  다시 실행하면 또 더해지므로 합치기 자체를 멱등하게 만들어야 합니다. 비회원 ID별로 "합쳤음"을 회원 쪽 스크립트에서 함께 기록하고, 기록이 있으면 건너뜁니다.

**Q. 장바구니에 가격을 담아 두면 안 되나요?**
담은 순간의 사본이라 장바구니가 사는 동안 가격과 재고가 바뀌면 틀린 값이 됩니다. 그 값으로 주문 금액을 계산하면 옛 가격으로 팔거나, 클라이언트가 보낸 값을 믿으면 조작된 가격으로 주문이 들어옵니다. 장바구니는 상품 ID와 수량만 두고, 화면에서는 상품 정보를 붙이고, 주문 때는 원본에서 다시 읽습니다. (본문: "장바구니에는 상품 ID와 수량만 둡니다")

**Q. 최근 본 상품은 List와 Sorted Set 중 무엇인가요?**
Sorted Set을 고릅니다. 본 시각을 점수로 넣으면 같은 상품은 점수만 바뀌어 중복이 저절로 없어지고, `ZREMRANGEBYRANK`로 오래된 것부터 자릅니다. List는 `LPUSH`와 `LTRIM`에 `LREM`을 더해야 중복이 없고, 세 명령이 섞이지 않게 묶어야 합니다. Sorted Set의 대가는 원소마다 점수를 더 담는 메모리와 앱 서버 시계에 기대는 순서입니다. (본문: "최근 본 상품: 중복을 없애고 개수를 자르는 두 방법")

- **꼬리: 상한을 두지 않으면 무엇이 문제인가요?**
  많이 둘러보는 회원의 키가 계속 커지고, 원소가 128개를 넘으면 한 덩어리가 아니라 원소마다 따로 담는 구조로 바뀌어 메모리가 늘어납니다. 사용자마다 키가 있으므로 이 차이가 사용자 수만큼 곱해집니다.

**Q. 장바구니 Redis의 메모리는 어떻게 추정하나요?**
키 수와 키 하나의 크기를 곱합니다. 키 수는 전체 회원 수가 아니라 TTL 안에 담은 회원과 비회원 수이고, 비회원 쪽이 더 빨리 늘 수 있습니다. 키 하나의 크기는 운영과 같은 직렬화로 만든 표본에 `MEMORY USAGE`를 재서 정하며, 이 값은 데이터 몫이라 버퍼와 할당기 여유를 따로 둡니다. (본문: "사용자와 요청이 늘면 무엇이 달라지는가")

- **꼬리: 그 추정이 크게 틀리는 경우는요?**
  직렬화기 하나로 장바구니 키가 listpack에서 hashtable로 바뀌는 경우입니다. 필드 값이 64바이트를 넘으면 처음부터 hashtable이 되고, 키 수백만 개에 곱해지므로 표본을 운영과 같은 설정으로 만들어야 합니다. 또 TTL 없는 키가 섞여 있으면 키 수가 멈추지 않아 추정의 전제가 깨집니다.

**Q. Spring에서 주의할 점은요?**
`RedisTemplate`의 기본 직렬화기는 Hash의 필드 이름과 값에도 Java 직렬화를 씁니다. 그러면 상품 ID 앞에 머리 바이트가 붙어 다른 서비스가 같은 필드를 찾지 못하고, `put`으로 넣은 수량은 Java 직렬화 바이트라 `increment`를 보내면 Redis가 정수로 읽지 못해 에러를 내고, 값이 64바이트를 넘어 hashtable이 되기 쉽습니다. `StringRedisTemplate`을 쓰고, 쓰기와 `EXPIRE`는 `SessionCallback` 안의 `MULTI`/`EXEC`나 스크립트로 묶습니다. Lettuce 클러스터 연결에서는 `MULTI`가 예외를 던지므로 스크립트를 씁니다. (본문: "Spring에서 장바구니 키를 다룰 때")

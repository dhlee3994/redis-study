# Redis 처리율 제한: 여러 서버가 한 Redis로 요청 수를 셀 때 무엇이 틀어지는가

> **핵심 질문**: 앱 서버 여러 대가 Redis 하나를 함께 보면서 "사용자마다 일정 시간에 몇 번까지"를 셀 때, 어떻게 해야 정확하고 싸게 셀 수 있는가? 고정 윈도, 슬라이딩 로그, 슬라이딩 윈도 카운터, 토큰 버킷은 각각 무엇을 지키고 무엇을 놓치며, Redis가 느려지거나 멈추면 요청을 어떻게 처리해야 하는가?
>
> **범위**: 단일 Redis 주 서버를 기준으로 하고, 클러스터는 키 배치만 다룹니다. 게이트웨이 제품별 설정, 분산 환경의 정밀한 전역 제한(여러 지역에 걸친 합산 등)은 다루지 않습니다. 같은 요청이 두 번 실행되지 않게 하는 멱등 처리는 [Redis 멱등 키](./idempotency-key.md)에서 다룹니다.

## 배경 지식

### 이 문서의 예시: 서버 3대, 사용자 u42, 60초에 5번

문서 끝까지 다음 장면 하나를 씁니다.

- 주문 조회 API를 앱 서버 S1, S2, S3 세 대가 나눠 받습니다. 로드 밸런서가 요청을 세 서버에 나눠 보내므로, 같은 사용자의 요청도 매번 다른 서버로 갈 수 있습니다.
- 규칙은 **"사용자 한 명당 60초에 5번까지"** 입니다. 넘치면 거절합니다.
- 사용자 u42가 12:00:58.0부터 12:01:00.9 사이에 요청 10개를 보냅니다(0.3초쯤 간격, 가상 시나리오). 앞의 5개는 12:00:58.0~12:00:59.9, 뒤의 5개는 12:01:00.1~12:01:00.9에 도착합니다.
- **바라는 결과**: 규칙을 말 그대로 읽으면, 3초도 안 되는 사이에 온 10개 중 5개만 통과해야 합니다.

```text
 u42 ──requests──> Load balancer ──> S1 ─┐
                                    ──> S2 ─┼──INCR/EVAL──> Redis (one counter per user)
                                    ──> S3 ─┘
```

그림의 화살표는 요청이 이동하는 방향입니다. 세 서버가 같은 Redis에 명령을 보내 u42의 횟수를 함께 셉니다. 연결 풀, 복제본, 영속화는 그림에서 뺐습니다. Redis가 멈췄을 때의 처리는 "Redis가 느리거나 멈추면: 열어 둘 것인가, 닫을 것인가"에서, 복제본과 장애 조치는 같은 절과 "흔한 오해 모아 보기"에서 다룹니다.

이 장면을 네 가지 방식에 차례로 넣어, 각 방식이 몇 개를 통과시키는지 손으로 따라갑니다.

### 처리율 제한

- **한 줄**: 처리율 제한(rate limiting)은 "누가, 어떤 시간 동안, 몇 번까지"라는 규칙을 정해 두고, 넘는 요청을 거절하거나 늦추는 장치입니다.
- **비유**: 놀이공원 놀이기구의 탑승 횟수 제한입니다. 직원이 손님별 탑승 횟수를 장부에 적어 두고, 정해진 시간 안에 횟수를 다 쓴 손님은 돌려보냅니다. 예시에서 장부는 Redis, 손님은 u42, 직원은 S1~S3입니다.
- **실제로는**:
  - 무엇을 지키는지가 두 가지로 나뉩니다. 하나는 **보호**입니다. 한 사용자나 공격자가 서버·DB·유료 외부 API를 혼자 다 써 버리지 않게 막습니다. 다른 하나는 **공정한 배분**입니다. 사용자마다 쓸 수 있는 몫을 정합니다.
  - "60초에 5번"이라는 말은 생각보다 모호합니다. 매 정각 분마다 5번인지, 아무 60초 구간을 잘라 봐도 5번 이하인지, 평균 12초에 1번이면 되고 잠깐 몰리는 것은 허용하는지에 따라 구현이 달라집니다. 이 문서의 네 방식은 이 모호함을 서로 다르게 해석한 것입니다.
  - 거절한 요청은 보통 HTTP 429(Too Many Requests)로 응답하고, 언제 다시 보내면 되는지 `Retry-After` 헤더로 알려 줄 수 있습니다(RFC 6585, 4절). 이 RFC는 사용자를 어떻게 구분하고 요청을 어떻게 셀지는 정하지 않습니다.
  - **비유와 다른 점**: 놀이공원 직원은 한 명이 장부 하나를 보지만, 예시에서는 직원 셋(S1~S3)이 동시에 장부 하나에 적습니다. 그래서 "장부를 읽고 → 판단하고 → 적는" 사이에 다른 직원이 끼어들 수 있습니다.
- **이 주제에서는**: 처리율 제한은 대개 **효율과 보호를 위한 장치**입니다. 몇 개가 더 통과하거나 덜 통과해도 데이터가 틀어지지는 않습니다. 그래서 이 문서는 정확도를 무한히 올리기보다, 어느 정도의 오차를 어떤 비용으로 받아들일지를 판단 기준으로 삼습니다. 같은 요청이 두 번 반영되면 안 되는 문제는 처리율 제한이 아니라 멱등 처리의 일입니다.

### 경쟁 상태와 원자성

경쟁 상태는 실행 순서에 따라 결과가 틀어지는 문제이고, 원자성은 여러 단계를 다른 실행 흐름에게 "시작 전" 또는 "끝난 후"로만 보이게 하는 성질입니다. 이 주제에서는 S1과 S2가 u42의 횟수를 동시에 "읽고 → 5 미만인지 보고 → 1 더해 쓰면" 둘 다 4를 읽고 둘 다 통과시킬 수 있습니다. 그래서 "세고 판단하기"를 Redis 안에서 끼어들기 없는 한 단위로 만들어야 합니다. 원자적 연산 두 개를 이어 붙여도 원자적이지 않다는 점이 특히 중요합니다. 자세한 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.

### 명령 하나와 Lua 스크립트 하나는 끼어들기 없이 실행됩니다

Redis에서 키를 읽고 바꾸는 명령은 메인 스레드 하나가 하나씩 끝까지 실행합니다. 그래서 `INCR` 같은 명령 하나나 `EVAL`로 보낸 Lua 스크립트 하나가 실행되는 동안에는 다른 연결의 명령이 끼어들지 않습니다. 명령 두 개 사이에는 끼어들 수 있습니다. 스크립트는 판단과 변경을 서버 안에서 한 번에 하지만, 도는 동안 다른 모든 명령을 기다리게 합니다. 이 주제에서는 처리율 제한 판단 하나를 명령 하나나 짧은 스크립트 하나로 만들어야 한다는 뜻입니다. 스크립트의 동작과 대가(다른 명령의 대기, 에러 때 되돌리지 않음, 스크립트 캐시)는 [Redis 원자성](./atomicity.md)에서 다룹니다.

### TTL: 키에 붙은 절대 시각

`EXPIRE key 60`처럼 TTL을 주면 Redis는 "지금 + 60초"를 절대 시각으로 바꿔 키에 붙이고, 서버 시계가 그 시각을 지나면 키를 없는 것으로 취급합니다. `INCR`처럼 값을 고치는 명령은 TTL을 유지하고, 옵션 없는 `SET`처럼 값을 통째로 바꾸는 명령은 TTL을 지웁니다. 이 주제에서는 창(window)이 끝난 카운터를 지우는 일을 TTL에 맡깁니다. TTL이 언제 유지되고 사라지는지, 만료된 키가 언제 메모리에서 빠지는지, 메모리가 설정한 한도에 닿을 때 Redis가 TTL과 상관없이 키를 골라 지우는 축출이 어떤 키를 고르는지는 [TTL과 축출](./ttl-and-eviction.md)에서 다룹니다.

### 벽시계

벽시계는 "지금이 몇 시인가"를 알려 주는 시계이고, 관리자가 시각을 바꾸거나 시각 동기화가 시계를 옮기면 앞뒤로 뜁니다. 컴퓨터마다 벽시계가 조금씩 어긋나 있습니다. 이 주제에서는 "지금이 어느 창인가", "마지막 요청 뒤 몇 초 흘렀는가"를 계산할 때 S1~S3의 시계를 쓸지 Redis 서버의 시계를 쓸지가 결과를 바꿉니다. 벽시계와 단조 시계의 차이는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "시계는 두 종류입니다: 벽시계와 단조 시계"에서 다룹니다.

### 복잡도 표기

O(1)은 데이터가 커져도 작업량이 일정하다는 뜻이고, O(log N + M)은 원소 수 N의 로그에 비례하는 탐색 비용에(로그 비용은 원소가 두 배가 될 때마다 탐색 단계가 하나 정도씩만 늘어나는 정도로 느리게 커집니다), 실제로 지우거나 돌려준 원소 수 M에 비례하는 비용이 더해진다는 뜻입니다. 이 표기는 서버가 그 명령을 실행하는 작업량을 말할 뿐입니다. 클라이언트가 느끼는 지연에는 네트워크 왕복과 앞 명령을 기다린 시간이 더해집니다.

### Sorted Set과 그 내부 표현

- **Sorted Set**은 멤버마다 숫자 점수를 붙여 점수 순으로 유지하는 중복 없는 집합입니다. 같은 멤버를 다시 넣으면 새 원소가 생기지 않고 점수만 바뀝니다. 점수 범위로 지우기(`ZREMRANGEBYSCORE`)와 개수 세기(`ZCARD`)를 할 수 있습니다. 대기열에 쓰는 예는 [Redis 입장 대기열](./waiting-queue.md)에 있습니다.
- Redis는 작은 Sorted Set을 `listpack`이라는 **연속된 메모리 한 덩어리**에 이어 적고, 원소가 128개를 넘거나 멤버 하나가 64바이트를 넘으면 원소마다 따로 메모리를 할당하는 구조로 바꿉니다(기본 설정 `zset-max-listpack-entries 128`, `zset-max-listpack-value 64`). 한 덩어리와 원소마다 따로의 차이가 메모리와 지우는 비용을 어떻게 바꾸는지는 [객체 하나를 String에 담을까, Hash에 담을까](./string-vs-hash.md)의 Hash 사례와 같습니다.
- 이 주제에서는 슬라이딩 로그가 요청 시각을 Sorted Set에 적으므로, 제한 횟수가 이 경계를 넘는지가 키 하나의 메모리를 크게 바꿉니다.

## 서버마다 세면 왜 안 되는가: 세는 곳이 하나여야 합니다

가장 먼저 떠오르는 방법은 각 앱 서버가 자기 메모리에 사용자별 횟수를 두는 것입니다. JVM 안의 `ConcurrentHashMap`과 `AtomicInteger`로 충분해 보입니다.

예시에서는 이렇게 틀어집니다. 로드 밸런서가 u42의 요청 10개를 S1, S2, S3에 번갈아 보내면 각 서버는 3~4개씩만 봅니다. 어느 서버도 5를 넘지 않으므로 **10개가 모두 통과합니다.** 서버가 N대면 한 사용자가 최대 N × 5번까지 통과할 수 있습니다. 서버 수가 자동 확장으로 바뀌면 제한도 함께 흔들립니다.

그래서 세는 곳을 모든 서버가 함께 보는 한 곳(Redis)으로 옮깁니다. 그러면 두 문제가 새로 생깁니다.

- **세는 일이 네트워크 요청이 됩니다.** 요청마다 Redis 왕복이 한 번 이상 붙습니다. 그래서 판단 하나를 명령 하나나 스크립트 하나로 끝내 왕복을 1번으로 유지하는 것이 목표가 됩니다.
- **세 서버가 동시에 셉니다.** "읽고 판단하고 쓰기"를 명령 여러 개로 나누면, 그 틈에 다른 서버의 명령이 끼어듭니다.

이 두 조건 위에서 네 방식을 봅니다.

## 고정 윈도: 창마다 INCR 한 번

### 동작: 창 번호를 키 이름에 넣고, 더한 결과로 판단합니다

시간을 60초짜리 칸(창)으로 자릅니다. 창 번호는 "유닉스 시각(초) ÷ 60의 몫"입니다. 손으로 따라가기 쉽게, 12:00:00~12:00:59.999의 창 번호를 1000, 12:01:00부터를 1001이라 하겠습니다.

요청이 오면 서버는 다음을 합니다.

1. 지금 시각으로 창 번호를 구해 키 이름을 만듭니다. 12:00:58이면 `rl:u42:1000`입니다.
2. `INCR rl:u42:1000`을 보냅니다. 키가 없으면 0에서 시작해 1이 되고, 더한 뒤의 값을 돌려줍니다.
3. 돌려받은 값이 5 이하면 통과, 6 이상이면 거절합니다.
4. 창이 끝나면 키가 사라지도록 TTL을 붙입니다(다음 절의 문제가 여기서 생깁니다).

**판단에 쓰는 값이 `INCR`의 반환값**이라는 점이 핵심입니다. "읽기 → 비교 → 쓰기"를 명령 셋으로 나누지 않고, 더하기와 읽기를 명령 하나로 합쳤습니다. 세 서버가 동시에 보내도 메인 스레드가 하나씩 실행하므로, 여섯 번째 `INCR`을 받은 서버만 6을 받습니다. 거절된 요청도 횟수를 하나씩 올리지만, 판단은 "5 이하인가"뿐이므로 결과가 틀어지지 않습니다. 오히려 거절된 요청까지 센 값이 남아 공격 규모를 보여 줍니다. 이 방식이 [Redis 원자성](./atomicity.md)의 "DECR의 반환값으로 판단하기"와 같은 구조입니다.

비용은 정상 경로에서 요청마다 O(1) 명령 하나, 왕복 1번입니다(기한을 따로 붙이는 첫 요청에는 왕복이 하나 더 붙습니다). 사용자당 키는 창마다 정수 값 하나입니다.

### INCR과 EXPIRE 사이의 틈: 기한 없는 카운터가 남습니다

TTL을 붙이는 가장 단순한 방법은 `INCR`의 반환값이 1이면(이 창의 첫 요청이면) `EXPIRE rl:u42:1000 60`을 이어서 보내는 것입니다. 두 명령 사이에 틈이 있습니다. `INCR`을 실행한 직후 앱 서버가 죽거나, 연결이 끊겨 `EXPIRE`가 서버에서 실행되지 못하면 **기한 없는 카운터**가 남습니다. `EXPIRE`가 타임아웃 났다면 실행됐는지 알 수 없으므로, 기한 없는 카운터가 남았을 **가능성**이 생깁니다. 이 창의 다음 요청들은 반환값이 2, 3, …이므로 아무도 `EXPIRE`를 다시 보내지 않습니다. 공식 문서의 `INCR` 페이지도 이 순서를 "race condition"이라고 부르며 같은 결과를 지적합니다(incr, "Pattern: rate limiter 2").

틈이 남기는 피해는 키 이름에 창 번호가 들어 있는지에 따라 다릅니다.

| 키 구성 | 기한 없는 카운터가 남으면 |
| --- | --- |
| 창 번호를 넣음(`rl:u42:1000`) | 다음 창은 새 키 `rl:u42:1001`을 쓰므로 판단은 정상입니다. 옛 키가 영원히 남아 **메모리만 샙니다.** 이런 일이 쌓이면 사용자 수 × 창 수만큼 늘어납니다 |
| 사용자당 키 하나(`rl:u42`)에 "첫 요청부터 60초"를 TTL로 맡김 | 카운터가 0으로 돌아가지 않습니다. u42는 5번을 쓴 뒤로 **영원히 거절됩니다**(이 문서의 추론. 공식 문서는 키가 남는다는 점까지만 적습니다) |

두 번째 줄은 처리율 제한이 장애가 되는 경우입니다. 그래서 창 번호를 키 이름에 넣는 쪽이 이 틈에 더 강합니다. 틈을 없애거나 메우는 방법은 셋입니다.

| 방법 | 동작 | 대가 |
| --- | --- | --- |
| Lua 스크립트 하나 | 스크립트 안에서 `INCR`하고, 결과가 1이면 `EXPIRE`합니다. 결과를 돌려줍니다 | 스크립트 관리. Redis는 받은 스크립트를 캐시해 두고 해시값만으로 다시 실행하게 하는데, 재시작 등으로 캐시가 비면 `NOSCRIPT` 에러가 나서 본문을 다시 보내야 합니다. 실행은 명령 두 개 분량이라 짧습니다 |
| `MULTI`/`EXEC`로 매번 `INCR`과 `EXPIRE`를 함께 | 요청마다 두 명령을 트랜잭션으로 보냅니다. 판단은 `EXEC`가 돌려준 `INCR` 결과로 합니다 | 요청마다 TTL을 다시 60초로 늘립니다. 창 번호를 넣은 키에서는 무해하지만, 사용자당 키 하나에 쓰면 요청이 계속 오는 동안 키가 영원히 살아 위의 "영원히 거절"과 같아집니다 |
| `INCR` 뒤에 `EXPIRE … NX`를 매번 파이프라이닝(응답을 기다리지 않고 이어 보내기. 실행 사이에 다른 명령이 끼어드는 것은 막지 않습니다) | `EXPIRE`의 `NX` 옵션은 키에 기한이 **없을 때만** 기한을 붙입니다. 매 요청이 이 명령을 함께 보내므로, 앞 요청이 기한을 못 붙였어도 다음 요청이 붙입니다 | 두 명령이 원자적이지 않아 틈은 그대로 있습니다. 다만 다음 요청이 메워 주는 "스스로 낫는" 구조입니다. 그 사용자가 다시 오지 않으면 키가 남습니다 |

`MULTI`/`EXEC`가 여기서 통하는 이유는, 고정 윈도의 판단이 Redis 안에서 이뤄질 필요가 없기 때문입니다. 횟수는 무조건 올리고, 판단은 앱이 결과를 받아서 합니다. `MULTI`/`EXEC`는 중간 결과로 분기할 수 없다는 한계가 있는데([Redis 원자성](./atomicity.md)), 이 경우에는 분기할 일이 없습니다. 공식 문서의 첫 번째 패턴도 창마다 키를 두고 `MULTI` 안에서 `INCR`과 `EXPIRE`를 함께 보냅니다(incr, "Pattern: rate limiter 1").

이 문서는 **Lua 스크립트 하나**를 기본으로 권합니다. 정상 경로에서 왕복 1번에 틈이 없고, 뒤의 다른 방식들도 어차피 스크립트가 필요하므로 관리 방법을 하나로 맞출 수 있습니다. 스크립트를 쓰지 않는 팀이라면 창 번호를 넣은 키에 `MULTI`/`EXEC`가 차선입니다.

### 창 경계에서 두 배가 통과합니다

예시를 넣어 봅니다.

| 시각 | 키 | `INCR` 결과 | 판단 |
| --- | --- | --- | --- |
| 12:00:58.0 ~ 12:00:59.9 (5개) | `rl:u42:1000` | 1, 2, 3, 4, 5 | 모두 통과 |
| 12:01:00.1 ~ 12:01:00.9 (5개) | `rl:u42:1001` | 1, 2, 3, 4, 5 | 모두 통과 |

**10개가 모두 통과합니다.** 앞 5개는 1000번 창의 끝에, 뒤 5개는 1001번 창의 시작에 들어갔고, 각 창 안에서는 5번을 넘지 않았기 때문입니다. 3초가 안 되는 사이에 규칙의 두 배가 지나갔습니다.

이것은 버그가 아니라 고정 윈도의 정의입니다. 고정 윈도가 지키는 것은 "**정각 분마다** 5번"이고, "**아무 60초 구간**에서나 5번"이 아닙니다. 아무 60초 구간을 잘라 보면 그 구간은 창 두 개에 걸치므로, 최대 2 × 5 = 10번까지 통과할 수 있습니다.

이 정도 오차를 받아들일 수 있는지는 무엇을 보호하느냐가 정합니다. 사용자별 공정한 배분이 목적이고 뒤쪽 서버에 여유가 있다면 대개 문제가 되지 않습니다. 반면 "외부 문자 발송 API는 분당 5건을 넘으면 계약 위반"처럼 짧은 순간의 몰림 자체가 문제라면, 다음 방식들을 봅니다.

## 슬라이딩 로그: 요청 시각을 모두 적어 둡니다

### 동작

사용자마다 Sorted Set 하나(`rl:log:u42`)를 두고, 통과시킨 요청의 시각을 점수로 적습니다. 요청이 오면 스크립트 하나가 다음을 합니다.

1. 지금 시각(밀리초)을 구합니다. 어느 시계를 쓸지는 "누구의 시계로 세는가"에서 다룹니다.
2. `ZREMRANGEBYSCORE rl:log:u42 -inf <지금 − 60000>`으로 점수가 "지금 − 60초" 이하인 기록, 곧 60초 이상 지난 기록을 지웁니다. 이 명령의 숫자 경계는 그 값을 포함하므로, 남는 기록은 "지금 − 60초"보다 뒤이고 지금 이하인 것입니다.
3. `ZCARD`로 남은 기록 수를 셉니다.
4. 5 미만이면 `ZADD`로 지금 시각을 점수로 하는 기록을 넣고, 키에 60초 TTL을 다시 붙인 뒤 1(통과)을 돌려줍니다. 5 이상이면 0(거절)을 돌려줍니다.

판단(3단계)의 결과로 쓰기(4단계)를 할지 정해야 하므로, 고정 윈도와 달리 `MULTI`/`EXEC`만으로는 만들 수 없습니다. `WATCH`로 키를 감시하며 앱에서 판단하고 바뀌었으면 다시 시도하는 방법도 가능하지만, 왕복이 늘고 한 사용자의 요청이 몰리면 재시도가 늘어납니다. 그래서 이 문서는 스크립트를 씁니다.

예시를 넣으면, 12:00:58.0~12:00:59.9의 5개가 기록되고, 12:01:00.1의 요청은 "지난 60초에 5개"를 보고 거절됩니다. 뒤의 5개가 모두 거절되어 **정확히 5개만 통과합니다.** 다음 요청이 통과할 수 있는 때는 가장 오래된 기록(12:00:58.0)이 60초 밖으로 빠지는 12:01:58.0입니다. 이 시각을 `Retry-After`로 알려 줄 수 있습니다.

### 거절한 요청은 기록하지 않습니다

4단계에서 거절한 요청까지 기록하면, 계속 두드리는 사용자는 자기 거절 기록 때문에 영원히 통과하지 못합니다. 이것을 처벌로 의도한 것이 아니라면 통과한 요청만 적습니다. 고정 윈도에서 거절된 요청까지 세도 괜찮았던 것은 창이 바뀌면 카운터가 새로 시작하기 때문입니다.

### 같은 밀리초의 요청 두 개는 멤버가 겹칩니다

Sorted Set은 멤버가 중복되지 않으므로, 멤버를 시각 문자열로만 쓰면 같은 밀리초에 온 요청 두 개가 같은 멤버가 되어 **하나로 합쳐집니다.** 기록이 하나 덜 쌓이므로 제한보다 많이 통과합니다. 멤버는 "시각 + 요청마다 고유한 값"(예: 시각과 요청 ID를 이은 문자열)으로 만들고, 점수에만 시각을 씁니다.

### 비용: 정확한 대신 요청 하나마다 기록 하나

- **메모리**: 사용자당 최대 "제한 횟수"만큼 원소를 들고 있습니다. 예시처럼 5개면 작지만, "1시간에 1,000번"이면 사용자당 원소 1,000개입니다. 128개를 넘으므로 원소마다 따로 할당하는 구조가 되어, 같은 원소 수라도 한 덩어리일 때보다 메모리를 더 씁니다. 원소를 지워 128개 아래로 내려가도 키가 남아 있는 동안 한 덩어리로 돌아가지 않고, 키가 비거나 만료되어 지워져야 사라집니다.
- **실행 시간**: `ZREMRANGEBYSCORE`는 O(log N + M), `ZADD`는 O(log N), `ZCARD`는 O(1)입니다. N은 그 사용자의 기록 수, M은 이번에 지운 기록 수입니다. 요청마다 지난 기록을 조금씩 지우므로 보통 M은 작습니다. 다만 오래 쉬던 사용자가 다시 오면 쌓인 기록을 한 번에 지울 수 있고, 스크립트가 도는 동안 다른 모든 명령이 기다립니다.

정확도가 꼭 필요하고 제한 횟수가 작을 때 맞는 방식입니다.

## 슬라이딩 윈도 카운터: 두 창의 수를 섞어 추정합니다

### 동작

고정 윈도의 카운터를 그대로 두되, **지난 창의 카운터도 함께 읽어** 경계의 몰림을 누그러뜨립니다. 지금이 1001번 창이 시작된 지 t초 지났다면, 최근 60초 동안의 요청 수를 다음처럼 추정합니다.

> 추정치 = 지난 창의 수 × (60 − t) ÷ 60 + 이번 창의 수

지난 창의 요청이 그 창 안에 고르게 퍼져 있었다고 가정하고, 최근 60초 구간에 걸친 비율만큼만 지난 창의 수를 셉니다. 추정치가 5 미만이면 통과시키고 이번 창의 카운터를 1 올립니다. "추정치를 보고 올릴지 정하는" 분기가 있으므로 스크립트로 만듭니다. 지난 창의 카운터는 이번 창이 끝날 때까지 읽어야 하므로, 고정 윈도처럼 60초 TTL을 붙이면 이번 창 도중에 사라질 수 있습니다. TTL은 창 두 개 길이(120초) 이상으로 둡니다. 키는 두 개(`rl:{u42}:1000`, `rl:{u42}:1001`)인데, 클러스터는 키 이름의 해시값으로 키를 슬롯에 나누고 슬롯마다 담당 노드를 정하며, 한 스크립트가 다루는 키는 같은 슬롯에 있어야 합니다. 키 이름에 중괄호 부분(해시 태그)이 있으면 그 부분만으로 슬롯을 정하므로 중괄호로 사용자 ID를 해시 태그로 묶습니다([Redis 원자성](./atomicity.md)의 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다").

### 예시: 균등 분포 가정이 깨지면 오차가 납니다

| 시각 | 지난 창 수 | 가중치 (60 − t) ÷ 60 | 이번 창 수 | 추정치 | 판단 |
| --- | --- | --- | --- | --- | --- |
| 12:01:00.1 | 5 | 0.998 | 0 | 4.99 | **통과** (이번 창 1로) |
| 12:01:00.4 | 5 | 0.993 | 1 | 5.97 | 거절 |
| 12:01:00.7 ~ 12:01:00.9 | 5 | 약 0.99 | 1 | 약 5.95 | 거절 |

뒤의 5개 중 **1개가 더 통과해 모두 6개**입니다. 실제로는 지난 창의 5개가 모두 끝 2초에 몰려 있었는데, 추정은 60초에 고르게 퍼져 있었다고 봤기 때문입니다. 반대로 지난 창의 요청이 모두 창의 앞부분에 몰려 있었다면, 실제로는 이미 60초 밖으로 빠진 요청을 세어 덜 통과시킵니다.

최악의 경우는 고정 윈도와 같습니다. 추정치에는 이번 창의 수가 그대로 들어가므로 정각 창마다 통과는 L번 이하이고, 그래서 아무 60초 구간에 최대 2L까지 통과할 수 있습니다. 예를 들어 12:00:59.5에 5개를 보내고 12:01:59.0에 5개를 더 보내면, 뒤의 5개는 지난 창의 가중치가 1/60뿐이라 모두 통과해 59.5초 동안 10개가 됩니다. 그래도 위 예시처럼 경계 바로 앞뒤에 몰린 요청은 대부분 막아, 사용자당 정수 두 개만 들고 O(1)로 판단합니다. 메모리와 정확도 사이의 절충이며, 실제 오차가 얼마나 되는지는 그 서비스의 요청 분포로 재 봐야 합니다.

## 토큰 버킷: 쌓인 만큼 한꺼번에, 그 뒤로는 일정한 속도로

### 동작

창으로 자르지 않고, 사용자마다 **토큰이 담긴 통**을 둡니다.

- 통의 크기(용량) B만큼 토큰이 들어갈 수 있습니다. 예시에서는 B = 5입니다.
- 토큰은 일정한 속도 r로 다시 찹니다. "60초에 5번"이면 r = 5 ÷ 60, 곧 12초에 1개입니다. 통이 가득 차면 더 쌓이지 않습니다.
- 요청 하나가 토큰 하나를 씁니다. 토큰이 1개 미만이면 거절합니다.

토큰을 실제로 1초마다 채우는 작업을 따로 돌리지 않습니다. 사용자마다 Hash 하나(`rl:tb:u42`)에 "남은 토큰 수"와 "마지막으로 계산한 시각" 두 필드만 두고, 요청이 올 때 스크립트가 흐른 시간만큼 한 번에 채웁니다.

1. 지금 시각을 구하고, 두 필드를 읽습니다. 키가 없으면 통이 가득 찬 상태(토큰 5개)로 봅니다.
2. 흐른 시간 = 지금 − 마지막 시각. **음수면 0으로 봅니다**(이유는 "누구의 시계로 세는가").
3. 토큰 = min(B, 남은 토큰 + 흐른 시간 × r).
4. 토큰이 1 이상이면 1을 빼고 통과, 아니면 거절합니다.
5. 두 필드를 새 값으로 쓰고, 통이 빈 상태에서 가득 찰 때까지 걸리는 시간(B ÷ r = 60초)보다 조금 길게 TTL을 붙입니다. 그 시간 동안 요청이 없었다면 키가 사라져도 "가득 찬 통"과 같기 때문입니다.

### 예시

| 시각 | 계산 전 토큰 | 판단 | 계산 후 토큰 |
| --- | --- | --- | --- |
| 12:00:58.0 | 5 (키 없음 = 가득) | 통과 | 4 |
| 12:00:58.3 ~ 12:00:59.9 (4개) | 각각 조금씩 차오름 | 모두 통과 | 약 0.16 |
| 12:01:00.1 | 약 0.18 | 거절 | 약 0.18 |
| 12:01:00.4 ~ 12:01:00.9 | 약 0.2 ~ 0.24 | 모두 거절 | |

**5개가 통과합니다.** 다섯 번째 요청 뒤로 통은 거의 비었고, 남은 토큰은 첫 요청(12:00:58.0) 뒤 흐른 시간 ÷ 12초만큼입니다. 토큰 하나가 차는 데 12초가 걸리므로, 다음 요청은 첫 요청 12초 뒤인 12:01:10.0에 통과합니다. 그 뒤로는 12초마다 하나씩 통과합니다.

### 토큰 버킷이 지키는 것: 순간 몰림의 상한과 긴 시간의 평균

토큰 버킷도 "아무 60초 구간에 5번 이하"를 지키지는 않습니다. 통이 가득 찬 상태에서 시작하면, 길이 T인 구간에 최대 **B + r × T**개가 통과합니다. 60초 구간이면 5 + 5 = 10개입니다. 처음 5개를 한꺼번에 쓰고, 이어서 12초마다 하나씩 쓰면 60초 동안 10개가 됩니다.

차이는 **몰림의 모양**입니다.

- 고정 윈도는 창 경계 바로 앞뒤의 짧은 순간에 10개를 통과시킬 수 있습니다.
- 토큰 버킷은 어떤 짧은 순간에도 B(= 5)개 남짓을 넘지 못하고, 그 뒤로는 r의 속도로만 통과시킵니다. 3초 구간이면 최대 5 + 3 × (5 ÷ 60) = 5.25, 곧 5개입니다.

그래서 토큰 버킷은 "평소에는 평균 속도를 지키되, 잠깐 몰리는 것은 B만큼 허용한다"를 표현하는 방식입니다. B와 r을 따로 정할 수 있다는 점이 다른 방식에 없는 손잡이입니다. 예를 들어 B = 1로 두면 몰림이 전혀 없이 12초에 하나씩만 통과합니다.

비용은 사용자당 작은 Hash 하나(필드 두 개)와 요청마다 짧은 스크립트 하나입니다. 짧은 필드 이름과 숫자 값을 담은 필드 두 개짜리 Hash는 기본 설정에서 한 덩어리(`listpack`)로 저장됩니다.

## 네 방식을 한 표로 비교합니다

| 방식 | 예시에서 통과 | 지키는 것 | 사용자당 상태 | 요청당 Redis 작업 | 스크립트 필요 |
| --- | --- | --- | --- | --- | --- |
| 고정 윈도 | 10 | 정각 창마다 L번. 아무 구간으로는 최대 2L | 정수 하나(창마다 키) | `INCR` O(1) + 기한 | 아니오(`MULTI`/`EXEC` 가능), 권장은 스크립트 |
| 슬라이딩 로그 | 5 | 아무 창 길이 구간에 L번 이하. 정확 | 통과한 요청 수만큼의 원소(최대 L) | O(log N + M) | 예(`WATCH`로도 가능하나 재시도 비용) |
| 슬라이딩 윈도 카운터 | 6 | 근사. 최악은 고정 윈도와 같은 2L | 정수 둘 | O(1) | 예 |
| 토큰 버킷 | 5 | 순간 몰림 B 이하, 긴 시간 평균 r | 숫자 둘(Hash 하나) | O(1) | 예 |

L은 창마다 허용 횟수(예시는 5), N은 사용자 한 명의 기록 수, M은 지운 기록 수입니다. "예시에서 통과"는 이 문서의 시나리오 하나를 넣은 결과이며, 다른 요청 분포에서는 달라집니다.

## 누구의 시계로 세는가

네 방식 모두 "지금"이 필요합니다. 고정 윈도는 창 번호를 정하는 데, 나머지는 기록을 지우거나 토큰을 채우는 데 씁니다. 그 "지금"을 어디서 읽느냐가 두 가지입니다.

### 앱 서버의 시계를 쓰면 서버마다 기준이 다릅니다

S1~S3이 각자 자기 시각을 계산해 Redis에 넘긴다고 합시다. S2의 시계가 실제보다 2초 빠르다면(가상 수치) 다음이 생깁니다.

- **고정 윈도**: 실제 시각 12:00:58.5에 S2로 간 요청은 S2가 보기에 12:01:00.5이므로 1001번 창으로 셉니다. 같은 순간에 S1로 간 요청은 1000번 창으로 셉니다. 경계 근처 2초 동안은 두 창이 동시에 열려 있어, 경계에서 두 배가 되는 일이 더 쉽게 생깁니다.
- **슬라이딩 로그**: S2가 넣은 기록은 실제보다 2초 미래의 점수를 갖습니다. 다른 서버가 "60초 이상 지난 기록"을 지울 때 이 기록은 2초 늦게 빠집니다. 순서도 실제 도착 순서와 달라질 수 있습니다.
- **토큰 버킷**: S2가 "마지막 시각"을 12:01:00.5로 써 둔 뒤, 실제 같은 순간에 S1이 12:00:58.6으로 계산하면 흐른 시간이 −1.9초가 됩니다. 음수를 그대로 쓰면 **토큰이 줄어듭니다.** 그래서 2단계에서 음수를 0으로 바꿉니다.

시계 차이가 창 길이에 비해 작고 근사로 충분하다면, 앱 서버의 시계로도 운영할 수 있습니다. 대가는 시계 차이만큼의 오차이며, 그 크기는 각 서버의 시각 동기화 상태에 달려 있어 관찰해야 합니다.

### Redis의 시계를 쓰면 하나로 맞춰집니다

스크립트 안에서 `TIME` 명령을 부르면 Redis 서버의 시각(초와 마이크로초)을 얻습니다. 모든 서버의 판단이 Redis 서버 하나의 시계를 기준으로 하므로 서버 간 차이가 사라집니다. 다만 고정 윈도는 창 번호가 키 이름에 들어가는데, 스크립트가 다루는 키 이름은 실행 전에 키 인자(`EVAL`에 넘기는 키 목록, 스크립트 안에서는 `KEYS` 배열)로 넘겨야 하므로 창 번호를 스크립트 안의 `TIME`으로 정할 수 없습니다. 고정 윈도에서 Redis 시계를 쓰려면 사용자당 키 하나에 창 번호와 횟수를 함께 담고, 스크립트가 창이 바뀌었으면 횟수를 새로 시작하게 하는 식으로 구조를 바꿔야 합니다. 슬라이딩 로그와 토큰 버킷은 키 이름에 시각이 없으므로 그대로 `TIME`을 쓸 수 있습니다.

- 복제본은 주 서버의 데이터를 따라 받는 다른 Redis 서버이고, AOF는 재시작 때 복구하려고 쓰기 명령을 적어 두는 파일입니다. 스크립트는 본문이 아니라 실행한 쓰기 명령을 이 둘에 전달합니다. 그래서 `TIME`처럼 실행할 때마다 값이 달라지는 명령을 써도, 복제본에는 계산이 끝난 값이 담긴 쓰기가 갑니다(공식 문서 eval-intro, "Script replication").
- 대가는 Redis 서버 시계의 문제를 그대로 받는다는 점입니다. 서버 시각이 앞으로 뛰면 창이 일찍 끝나고 토큰이 많이 찹니다. 뒤로 가면 토큰 버킷의 흐른 시간이 음수가 되어, 0으로 바꾸지 않으면 토큰이 줄어듭니다. 0으로 바꾸고 마지막 시각을 새 값으로 저장하면 그 요청에서만 충전이 없고 다음 요청부터 다시 찹니다. 장애 조치 뒤에는 새 주 서버의 시계로 계산합니다. 원리는 [Redis 분산 락](./distributed-lock.md)의 "시계: 서버의 벽시계가 뛰면 락이 일찍 풀립니다"에서 다룹니다.

이 문서의 권장은 **스크립트 안에서 Redis의 `TIME`을 쓰는 것**입니다. 앱 서버 N대의 시계 N개를 맞추는 것보다 Redis 하나의 시계를 믿는 편이 오차의 원인이 적습니다. 넘어도 뒤쪽 서버가 조금 바빠지는 정도의 제한이라면, 드문 시각 이동이 남기는 결과(잠시 더 통과하거나 잠시 덜 통과함)는 받아들일 만합니다. 넘으면 돈이나 계약이 망가지는 제한이라면 이 결과도 "판단: 실패하면 통과시킬까, 거절할까"와 같은 기준으로 따져야 합니다.

## 키 하나가 차지하는 메모리

처리율 제한의 상태는 사용자 수에 비례해 늘어납니다. 무엇이 늘어나는지를 방식별로 보면 다음과 같습니다.

| 방식 | 사용자 한 명이 차지하는 것 | 동시에 살아 있는 키 수 |
| --- | --- | --- |
| 고정 윈도 | 정수 값을 담은 String 키 하나 | 최근 "TTL 길이" 동안 키를 만든 사용자 수. TTL이 창 하나 길이면 창 두 개분의 키가 겹칠 수 있고, TTL을 더 길게 잡으면 그만큼 더 겹칩니다 |
| 슬라이딩 로그 | Sorted Set 하나에 최근 통과한 요청 수만큼의 원소 | 최근 창 길이 안에 요청한 사용자 수 |
| 슬라이딩 윈도 카운터 | String 키 둘 | 최근 "TTL 길이" 안에 요청한 사용자 수. 판단에 읽는 키는 둘이지만, TTL을 창 두 개 길이(120초)로 두면 창 중간에 생긴 키가 다음다음 창까지 남아 사용자당 최대 셋이 함께 살아 있을 수 있습니다 |
| 토큰 버킷 | 필드 둘인 작은 Hash 하나 | 최근 "TTL 길이" 안에 요청한 사용자 수. TTL은 가득 찰 때까지의 시간보다 길게 잡습니다 |

- **값이 한 덩어리인가, 원소마다 따로인가가 가장 크게 가릅니다.** 정수 하나, 짧은 필드 둘인 Hash, 원소가 128개 이하이고 멤버가 64바이트 이하인 Sorted Set은 기본 설정에서 한 덩어리입니다. 이 경계를 한 번이라도 넘은 Sorted Set은 원소마다 따로 할당되어 원소당 비용이 커지고, 원소가 줄어도 키가 남아 있는 한 돌아오지 않습니다. 그래서 실제로 담긴 원소 수 N이 128을 넘을 만큼 제한 횟수가 크고 요청이 많은 슬라이딩 로그가 메모리에서 가장 비쌉니다.
- 키마다 키 이름, 값, TTL을 담는 고정 비용이 붙습니다. 그래서 사용자 ID가 길거나 키 접두어가 길면 사용자 수만큼 곱해집니다.
- 정확한 바이트 수는 빌드, 메모리 할당기, 키 이름 길이에 따라 다르므로 이 문서는 숫자를 적지 않습니다. 실제 크기는 운영과 같은 키 이름으로 키를 몇 개 만든 뒤 `MEMORY USAGE`로 재고, 동시에 살아 있을 키 수를 곱해 봅니다.
- **TTL을 빼먹은 키가 가장 큰 비용입니다.** 앞의 "INCR과 EXPIRE 사이의 틈: 기한 없는 카운터가 남습니다"처럼 기한이 없는 카운터는 사용자 수 × 창 수만큼 쌓입니다. `INFO keyspace`에서 키 수(`keys`)와 기한 있는 키 수(`expires`)의 차이가 계속 늘면 의심합니다.

## Redis가 느리거나 멈추면: 열어 둘 것인가, 닫을 것인가

처리율 제한을 Redis에 맡기면, 모든 요청이 Redis 호출 하나를 거칩니다. 그래서 Redis의 장애가 곧 모든 API의 장애가 될 수 있습니다. 이때 정할 것은 두 가지입니다.

### 기다림: 제한기 호출에 짧은 상한을 둡니다

- Redis가 응답하지 않으면, 동기 호출(Spring Data Redis의 일반 `RedisTemplate` 호출)에서는 요청 스레드가 명령 타임아웃만큼 기다립니다. 리액티브 호출에서는 스레드를 붙잡지는 않지만 요청의 완료가 그만큼 늦어집니다. Spring Boot의 Lettuce 기본 명령 타임아웃은 60초이고, 연결이 끊긴 동안 Lettuce는 명령을 거절하지 않고 쌓아 둡니다. 그래서 Redis가 멈추면 모든 API 요청이 처리율 제한 단계에서 오래 묶일 수 있습니다. 세부는 [Spring 앱의 Redis 연결과 명령 타임아웃](./client-connection-timeout.md)에서 다룹니다.
- 처리율 제한은 본 작업의 앞에 붙는 검사이므로, 기다림의 상한을 본 작업보다 짧게 잡습니다. 정상 응답 시간의 꼬리 바로 위가 기준입니다. 값을 정하는 원리는 [타임아웃](../cs/timeout.md)에 있습니다.
- 실패가 이어지면 한동안 Redis 호출 자체를 건너뛰는 장치(서킷 브레이커)를 둡니다. 실패를 기다리는 시간까지 없애야 장애 동안의 지연이 줄어듭니다.

### 판단: 실패하면 통과시킬까, 거절할까

제한기가 답을 얻지 못했을 때의 선택은 둘입니다.

| 선택 | 동작 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| **열어 두기(fail-open)** | Redis 오류·타임아웃이면 통과시킵니다 | Redis 장애가 API 장애로 번지지 않습니다 | 장애 동안 제한이 없습니다. 공격이나 폭주가 그때 오면 뒤쪽이 그대로 받습니다 |
| **닫기(fail-closed)** | Redis 오류·타임아웃이면 거절합니다 | 판단하지 못한 요청이 추가로 통과하지 않습니다. 다만 고정 윈도의 경계, 카운터 유실, 시계 이동으로 생기는 초과는 그대로입니다 | Redis 장애가 그대로 API 전체의 장애가 됩니다 |

고르는 기준은 "제한을 넘으면 무엇이 망가지는가"입니다.

- **넘어도 뒤쪽 서버가 조금 바빠지는 정도**라면 열어 둡니다. 대부분의 사용자별 API 제한이 여기에 해당합니다. Spring Cloud Gateway의 `RedisRateLimiter`(4.3.5)도 Redis 호출이 실패하면 요청을 통과시키고 에러 로그를 남깁니다. 소스 주석은 Redis에 강하게 의존하지 않으려는 선택이라며, 이런 일이 잦으면 알림을 걸라고 적습니다.
- **넘으면 돈이나 계약, 외부 시스템이 망가진다면** 닫습니다. 건당 과금되는 문자 발송, 호출 한도를 넘으면 차단되는 외부 결제 API가 그렇습니다.
- **중간 길**: Redis가 실패한 동안만 각 앱 서버가 자기 메모리로 셉니다. 서버 N대가 각자 "L ÷ N"으로 세면 합계가 대략 L 근처에 머뭅니다. 대가는 부정확함입니다. 로드 밸런서가 한 사용자의 요청을 고르게 나누지 않거나, 자동 확장으로 N이 바뀌면 오차가 커집니다. 처음에 본 "서버마다 세면 왜 안 되는가: 세는 곳이 하나여야 합니다"의 문제를 장애 동안만 받아들이는 것입니다.

어느 쪽이든 **"제한기가 판단하지 못한 요청 수"를 지표로 남깁니다.** 열어 둔 상태가 조용히 계속되면 제한이 없는 서비스를 운영하는 셈이기 때문입니다.

닫기로 했다면, 판단하지 못해 거절한 요청에는 한도 초과의 429와 구분되는 응답을 씁니다. 예를 들어 503(Service Unavailable)은 서버가 일시적으로 요청을 처리할 수 없다는 뜻이고, 이때도 `Retry-After`를 붙일 수 있습니다(RFC 9110, 15.6.4). 둘을 같은 429로 돌려주면 클라이언트는 자기가 한도를 넘었다고 오해하고, 거절 비율 지표에 Redis 장애가 섞여 원인을 가리기 어려워집니다. 지표도 두 원인을 나눠 셉니다.

### 메모리 한도와 장애 조치도 같은 질문으로 이어집니다

- **`noeviction`에서 메모리가 가득 차면** `INCR`, `ZADD`, `HSET` 같은 쓰기는 OOM 에러를 받습니다. 스크립트 안의 쓰기는 스크립트 시작 시점에 한도를 넘었고 **스크립트가 아직 아무것도 쓰지 않았을 때만** 거절됩니다. 슬라이딩 로그처럼 지우기(`ZREMRANGEBYSCORE`)를 먼저 하면 지운 것이 없어도 쓰기로 치므로, 뒤의 `ZADD`는 거절되지 않을 수 있습니다. 이 에러도 제한기에게는 "판단 실패"이므로 위의 선택을 따릅니다.
- **축출 정책이 `allkeys-*`이거나 `volatile-*`이면** 카운터가 지워질 수 있습니다. 처리율 제한의 키는 대개 TTL이 있으므로 `volatile-*`의 후보이기도 합니다. 지워진 사용자는 새 몫을 받아 잠시 더 통과합니다.
- **장애 조치나 재시작으로** 아직 복제되거나 저장되지 않은 카운터를 잃으면, 마찬가지로 몇몇 사용자가 잠시 더 통과합니다.

축출과 유실의 결과는 "잠시 덜 막음"이고, OOM 에러의 결과는 위의 선택에 따라 "덜 막음"(열어 두기)이나 "더 거절함"(닫기)입니다. 처리율 제한이 효율용이라면 받아들일 수 있습니다. 정확성이 필요한 숫자(남은 재고, 결제 횟수)를 처리율 제한 키처럼 다루면 안 되는 이유이기도 합니다.

## 요청과 데이터가 늘면 무엇이 달라지는가

- **요청이 늘면 Redis 왕복이 요청 수만큼 늡니다.** 처리율 제한은 거절할 요청에도 Redis 호출을 합니다. 공격 트래픽이 몰리면 Redis가 받는 명령도 그만큼 늘어나므로, Redis 용량을 정상 트래픽이 아니라 거절할 트래픽까지 포함해 잡습니다. IP 단위의 거친 차단은 Redis 앞(로드 밸런서, 게이트웨이)에서 먼저 하면 Redis가 받는 양이 줄어듭니다.
- **사용자가 늘면 키 수가 늡니다.** 사용자당 상태가 작은 방식(고정 윈도, 토큰 버킷)은 키 수에 거의 정비례합니다. 슬라이딩 로그는 키 수 × 제한 횟수로 늘어납니다.
- **전역 제한 하나는 핫키가 됩니다.** "외부 API 전체 호출을 초당 100번"처럼 모든 사용자가 공유하는 제한은 키 하나에 모든 서버의 요청이 몰립니다. 클러스터에서도 키 하나는 노드 하나에 있으므로 노드를 늘려도 나뉘지 않습니다. 몫을 서버별로 나눠 각자 세는 방법이 있지만 위의 "중간 길"과 같은 부정확함이 따릅니다. 원리는 Hot Key와 Big Key에서 다룹니다.
- **사용자별 키는 클러스터에서 고르게 퍼집니다.** 다만 한 스크립트가 여러 키를 다루면(슬라이딩 윈도 카운터의 두 창) 해시 태그로 같은 슬롯에 묶어야 합니다. Spring Cloud Gateway의 `RedisRateLimiter`도 사용자별 키 두 개를 해시 태그로 묶습니다.
- **스크립트는 짧게 유지합니다.** 처리율 제한 스크립트는 모든 요청이 거치므로, 원소 수에 비례해 도는 부분(슬라이딩 로그의 기록 지우기)이 길어지면 다른 모든 명령의 지연이 됩니다.

## 실무 포인트

### 어떤 방식을 고를까

| 요구사항 | 고를 방식 | 이유 |
| --- | --- | --- |
| 사용자별 공정한 배분, 경계의 두 배는 괜찮음 | 고정 윈도(스크립트로 `INCR` + 기한) | 가장 싸고 단순합니다. 오차가 창 경계에 국한됩니다 |
| 평균 속도를 지키되 잠깐 몰리는 것은 허용 | 토큰 버킷 | 몰림의 상한(B)과 평균(r)을 따로 정할 수 있고 상태가 작습니다 |
| 짧은 몰림도 막아야 하지만 상태는 작게 | 슬라이딩 윈도 카운터 또는 B를 작게 둔 토큰 버킷 | 둘 다 O(1)입니다. 카운터는 근사이고, B = 1인 토큰 버킷은 몰림이 아예 없습니다 |
| 아무 구간에서나 L번 이하가 계약 조건이고 L이 작음 | 슬라이딩 로그 | 유일하게 정확합니다. L이 크면 메모리가 커지므로 다른 방식을 먼저 검토합니다 |

대안을 하나 더 적으면, 게이트웨이나 로드 밸런서의 처리율 제한 기능이 이미 있다면 그것을 먼저 씁니다. 앱 코드와 Redis에 제한 로직을 두는 것은 사용자 ID처럼 앱만 아는 기준으로 세야 할 때의 선택입니다.

### 중요도별 점검 항목

- **필수**: 카운터와 기한을 한 단위로 만들었는가(스크립트, 또는 창 번호를 넣은 키에 `MULTI`/`EXEC`). 틈이 있으면 기한 없는 키가 남고, 사용자당 키 하나를 쓰는 구성이면 사용자가 영원히 거절되는 장애가 됩니다.
- **필수**: Redis 실패 때 열어 둘지 닫을지를 정하고, 제한기 호출에 본 작업보다 짧은 기다림 상한을 두었는가. 정하지 않으면 클라이언트 기본값(Lettuce 60초)과 예외 처리 방식이 대신 정합니다.
- **필수**: 제한 기준(사용자 ID, API 키, IP)을 정했는가. IP 기준은 회사 네트워크처럼 여러 사용자가 한 IP를 쓰면 함께 막히고, 프록시 뒤에서는 클라이언트 IP를 어느 헤더에서 읽는지에 따라 위조될 수 있습니다. 합산 범위도 키 이름이 정합니다. 키에 사용자 ID만 넣으면 그 사용자의 모든 API가 한 몫을 나눠 쓰고, API 경로까지 넣으면 API마다 따로 셉니다. 사용자별 제한과 전역 제한처럼 여러 제한을 따로 판단하면, 앞 제한에서 몫을 깎은 뒤 뒤 제한에서 거절되어도 앞 제한의 몫은 이미 줄어 있습니다.
- **알면 유리**: 시각을 Redis의 `TIME`으로 읽는가. 앱 시계를 쓴다면 서버 간 시계 차이를 관찰하고 있는가.
- **알면 유리**: 슬라이딩 로그의 멤버가 요청마다 고유한가, 거절한 요청을 기록하지 않는가.
- **참고**: 429 응답에 `Retry-After`를 넣어 클라이언트가 바로 다시 두드리지 않게 하는가. 고정 윈도는 창이 끝나는 시각, 슬라이딩 로그는 가장 오래된 기록이 빠지는 시각, 토큰 버킷은 토큰이 1개가 되는 시각을 계산할 수 있습니다.

### 관찰할 것

- 거절 비율(전체, 사용자별 상위). 갑자기 늘면 공격, 클라이언트의 재시도 폭주, 정상 수요 증가, 제한 설정·키 기준의 실수를 후보로 놓고 확인하며, 특정 사용자가 계속 거절되면 기한 없는 카운터를 의심합니다.
- 제한기가 판단하지 못한 요청 수(Redis 오류, 타임아웃, 서킷 브레이커 열림).
- 제한기 호출의 응답 시간 분포. 모든 요청의 지연에 더해지는 값입니다.
- `INFO keyspace`의 `keys`와 `expires`의 차이, 처리율 제한 키 접두어의 키 수 추이.
- `MEMORY USAGE`로 잰 키 하나의 크기 × 동시에 살아 있는 키 수.

### 증상과 대응

| 증상 | 먼저 확인할 것 | 대응과 부작용 |
| --- | --- | --- |
| 특정 사용자가 몇 시간째 계속 거절됨 | 그 사용자의 카운터 키에 TTL이 있는가(`TTL`이 -1이면 기한 없음) | 키를 지우고, `INCR`과 기한을 한 단위로 묶도록 고칩니다. 키 삭제는 그 사용자에게 새 몫을 줍니다 |
| 제한을 걸었는데 순간적으로 두 배가 들어옴 | 고정 윈도인가, 창 경계에서 생겼는가 | 정상 동작입니다. 막아야 하면 토큰 버킷이나 슬라이딩 방식으로 바꿉니다 |
| 서버별로 제한이 다르게 걸리는 듯함 | 앱 서버 시계로 창 번호나 시각을 계산하는가 | Redis `TIME`으로 옮깁니다 |
| Redis 장애 때 API 전체가 느려지거나 멈춤 | 제한기 호출의 기다림 상한, 닫기로 설정했는가 | 상한을 줄이고 서킷 브레이커를 둡니다. 열어 두면 장애 동안 제한이 없어집니다 |
| Redis 장애 뒤 뒤쪽 서버가 과부하 | 열어 두기로 설정했는가 | 장애 동안만 서버별 메모리 제한(L ÷ N)으로 바꿉니다. 정확도는 떨어집니다 |
| Redis 메모리가 계속 늘어남 | 처리율 제한 키 중 기한 없는 키, 슬라이딩 로그의 원소 수 | 기한을 붙이고, 제한 횟수가 큰 슬라이딩 로그는 다른 방식으로 바꿉니다 |

### Spring에서 확인할 것

- `opsForValue().increment(key)`는 `INCR` 하나만 보냅니다. 이어서 `expire(key, …)`를 부르면 명령 두 개이므로 "INCR과 EXPIRE 사이의 틈: 기한 없는 카운터가 남습니다"가 그대로 생깁니다. 스크립트(`RedisScript`)로 묶어 `execute`로 보냅니다. 스크립트 캐시와 `NOSCRIPT` 처리는 [Redis 원자성](./atomicity.md)에 있습니다.
- Spring Cloud Gateway의 `RedisRateLimiter`는 토큰 버킷이고, Redis 호출이 실패하면 통과시킵니다. 닫아야 하는 서비스라면 이 동작을 그대로 쓰면 안 됩니다. 시각을 넘기지 않으면 `TIME`의 초 단위 값만 쓰므로, 토큰은 1초 단위로 차오릅니다.
- 처리율 제한 호출이 일반 Redis 호출과 같은 연결과 명령 타임아웃을 공유하면, Redis가 느려질 때 둘이 함께 느려집니다. 짧은 상한이 필요하면 제한기 호출에 따로 기한을 두는 방법을 검토합니다.

## 말로 설명하기

### 30초 버전

처리율 제한은 서버가 여러 대면 세는 곳이 하나여야 해서 Redis에 둡니다. 가장 단순한 고정 윈도는 창 번호를 키에 넣고 `INCR`의 반환값으로 판단하는데, `INCR`과 기한을 따로 보내면 기한 없는 카운터가 남을 수 있어 스크립트로 묶습니다. 사용자당 키 하나를 쓰는 구성이라면 그 사용자가 영원히 막힙니다. 고정 윈도는 창 경계에서 두 배가 통과하므로, 몰림을 막아야 하면 토큰 버킷이나 슬라이딩 방식을 씁니다. 처리율 제한은 효율용이라, Redis 장애 때는 대개 열어 두고 그 사실을 지표로 봅니다.

### 2분 버전

서버마다 자기 메모리로 세면 서버 N대에서 N배가 통과하므로, 모든 서버가 Redis 하나에서 셉니다. 그러면 세는 일이 네트워크 요청이 되고 여러 서버가 동시에 세므로, 판단 하나를 명령 하나나 스크립트 하나로 만들어 왕복 1번에 끼어들기가 없게 합니다.

고정 윈도는 `INCR`의 반환값으로 판단하므로 횟수 자체는 정확하게 셉니다. 문제는 기한입니다. 첫 요청에서 `EXPIRE`를 따로 보내다 실패하면 기한 없는 키가 남고, 사용자당 키 하나를 쓰는 구성이면 그 사용자는 영원히 거절됩니다. 그래서 스크립트로 묶거나, 창 번호를 넣은 키에 `MULTI`/`EXEC`를 씁니다. 그리고 고정 윈도는 정각 창마다 L번을 지킬 뿐이라 경계 앞뒤로 2L이 통과합니다.

슬라이딩 로그는 요청 시각을 Sorted Set에 적어 아무 구간에서나 정확하지만 사용자당 L개를 들고 있어야 합니다. 슬라이딩 윈도 카운터는 지난 창의 수를 비율로 섞어 정수 두 개로 근사합니다. 토큰 버킷은 몰림의 상한 B와 평균 속도 r을 따로 정하는 방식입니다. 토큰 버킷도 60초 구간에 B + 60r까지 통과시키므로, "아무 구간에 L번 이하"를 지키는 것은 아닙니다.

시각은 스크립트 안의 `TIME`으로 Redis 서버 하나의 시계를 씁니다. 앱 서버 시계를 쓰면 서버마다 창이 어긋나고 토큰 버킷의 흐른 시간이 음수가 될 수 있습니다. 마지막으로 Redis가 멈추면 제한기 때문에 API 전체가 멈추지 않도록 기다림을 짧게 하고, 넘었을 때의 피해를 기준으로 열어 둘지 닫을지 정합니다.

### 예상 질문과 꼬리 질문

**기본 개념과 선택 이유**

- **왜 앱 서버 메모리가 아니라 Redis에서 세나요?**
  로드 밸런서가 한 사용자의 요청을 여러 서버에 나눠 보내므로, 서버마다 세면 각 서버가 일부만 봅니다. 서버 N대에서 최대 N배가 통과하고, 자동 확장으로 N이 바뀌면 제한도 바뀝니다(서버마다 세면 왜 안 되는가: 세는 곳이 하나여야 합니다).
  - **꼬리: 그럼 스티키 세션으로 한 사용자를 한 서버에 묶으면요?**
    그 서버가 내려가거나 확장으로 재배치되면 몫이 새로 시작되고, 세션 고정이 깨지는 순간 같은 문제가 다시 생깁니다. 서버 장애와 배포가 곧 제한의 오차가 되므로, 세는 곳을 서버 밖에 두는 편이 단순합니다. 다만 Redis 장애 동안 임시로 서버별 제한을 쓰는 것은 받아들일 만한 절충입니다(Redis가 느리거나 멈추면).

- **고정 윈도에서 `INCR` 하나로 왜 경쟁 상태가 없나요?**
  판단을 "읽은 값"이 아니라 "더한 뒤 돌려받은 값"으로 하기 때문입니다. 더하기와 읽기가 명령 하나라 메인 스레드가 끼어들기 없이 실행하고, 여섯 번째 요청을 보낸 서버만 6을 받습니다(동작: 창 번호를 키 이름에 넣고, 더한 결과로 판단합니다).
  - **꼬리: `GET`으로 먼저 보고 5 미만일 때만 `INCR`하면 거절된 요청을 안 세서 더 깔끔하지 않나요?**
    `GET`과 `INCR` 사이에 다른 서버가 끼어들어, 둘 다 4를 보고 둘 다 `INCR`하면 6번째가 통과합니다. 거절된 요청까지 세는 것은 창이 바뀌면 초기화되므로 판단을 틀리게 하지 않습니다.

- **`INCR`과 `EXPIRE`를 따로 보내면 정확히 무엇이 문제인가요?**
  `INCR` 직후 앱이 죽거나 `EXPIRE`가 실패하면 기한 없는 카운터가 남고, 이후 요청은 결과가 1이 아니라 아무도 기한을 다시 붙이지 않습니다. 창 번호를 넣은 키라면 메모리만 새지만, 사용자당 키 하나라면 그 사용자는 영원히 거절됩니다(INCR과 EXPIRE 사이의 틈: 기한 없는 카운터가 남습니다).
  - **꼬리: 그 확률이 얼마나 된다고 굳이 스크립트를 쓰나요?**
    확률은 낮아도 결과가 "특정 사용자의 영구 차단"이라 원인을 찾기 어렵고, 고치는 비용이 거의 없습니다. 스크립트 하나나 `MULTI`/`EXEC` 하나로 왕복 수를 늘리지 않고 틈을 없앨 수 있습니다.
  - **꼬리: `EXPIRE … NX`를 매번 붙여 보내면 스크립트가 필요 없지 않나요?**
    틈은 남지만 다음 요청이 기한을 붙여 주므로 스스로 낫습니다. 그 사용자가 다시 오지 않으면 키가 남는다는 한계가 있고, 원자적이지 않다는 사실은 그대로입니다. 스크립트를 쓸 수 없는 환경의 차선으로 봅니다.

**대안 비교**

- **고정 윈도의 경계 문제는 실제로 얼마나 심각한가요?**
  아무 60초 구간을 보면 최대 2L이 통과합니다. 예시에서는 3초가 안 되는 사이 10개가 지나갔습니다(창 경계에서 두 배가 통과합니다). 공정한 배분이 목적이고 뒤쪽에 여유가 있으면 대개 괜찮고, 짧은 몰림 자체가 계약 위반이나 비용이 되면 문제입니다.
  - **꼬리: 그럼 토큰 버킷으로 바꾸면 "60초에 5번"이 정확히 지켜지나요?**
    아닙니다. 토큰 버킷도 가득 찬 상태에서 60초 동안 B + 60r = 10개까지 통과시킵니다. 토큰 버킷이 지키는 것은 "짧은 순간의 몰림은 B 이하, 긴 시간 평균은 r"입니다. 아무 구간에 L번 이하를 정확히 지키는 것은 슬라이딩 로그뿐입니다(토큰 버킷이 지키는 것: 순간 몰림의 상한과 긴 시간의 평균).

- **슬라이딩 로그가 정확한데 왜 기본으로 안 쓰나요?**
  사용자당 최대 L개의 원소를 들고 있어야 합니다. L이 128을 넘으면 원소마다 따로 할당하는 구조가 되어 메모리가 커지고, 오래 쉰 사용자의 기록을 지울 때 스크립트가 길어집니다(비용: 정확한 대신 요청 하나마다 기록 하나).
  - **꼬리: L이 작으면 슬라이딩 로그가 항상 낫나요?**
    정확도가 필요하다면 그렇습니다. 다만 같은 밀리초 요청이 합쳐지지 않게 멤버를 고유하게 만들고, 거절한 요청은 기록하지 않는 등 지켜야 할 세부가 늘어납니다. 근사로 충분하면 상태가 정수 두 개뿐인 슬라이딩 윈도 카운터가 더 단순합니다.

- **슬라이딩 윈도 카운터의 오차는 어떻게 생기나요?**
  지난 창의 요청이 창 안에 고르게 퍼져 있다고 가정하고 비율만큼 세기 때문입니다. 예시처럼 지난 창의 요청이 끝에 몰려 있으면 덜 세어 더 통과시키고, 앞에 몰려 있으면 더 세어 덜 통과시킵니다(예시: 균등 분포 가정이 깨지면 오차가 납니다).
  - **꼬리: 오차가 최대 얼마라고 말할 수 있나요?**
    최악은 고정 윈도와 같은 2L입니다. 정각 창마다 L번 이하라는 성질은 그대로이기 때문입니다. 예시처럼 경계에 몰린 경우에는 5개 제한에 6개처럼 작게 넘지만, 실제로 얼마나 넘는지는 그 서비스의 요청 분포로 재 봐야 합니다(예시: 균등 분포 가정이 깨지면 오차가 납니다).

**시계**

- **시각은 앱 서버에서 넘기면 안 되나요?**
  넘길 수는 있지만 서버마다 시계가 다르므로, 고정 윈도는 경계 근처에서 두 창이 동시에 열리고, 슬라이딩 로그는 미래 점수의 기록이 늦게 빠지고, 토큰 버킷은 흐른 시간이 음수가 될 수 있습니다(앱 서버의 시계를 쓰면 서버마다 기준이 다릅니다).
  - **꼬리: Redis `TIME`을 쓰면 시계 문제가 없어지나요?**
    서버 간 차이는 없어지지만 Redis 서버 시계의 문제는 그대로입니다. 시각이 앞으로 뛰면 창이 일찍 끝나 더 통과하고, 뒤로 가면 흐른 시간이 음수가 되므로 0으로 잘라야 합니다. 장애 조치 뒤에는 새 주 서버의 시계를 씁니다(Redis의 시계를 쓰면 하나로 맞춰집니다).
  - **꼬리: 스크립트 안에서 `TIME`처럼 매번 다른 값을 쓰면 복제본과 결과가 달라지지 않나요?**
    스크립트는 본문이 아니라 실행한 쓰기 명령을 복제하므로, 복제본에는 계산이 끝난 값이 그대로 갑니다(공식 문서 eval-intro, "Script replication").

- **토큰 버킷 스크립트에서 흐른 시간을 왜 0 이상으로 자르나요?**
  시계가 뒤로 가거나 다른 시계로 기록된 "마지막 시각"이 지금보다 미래면 흐른 시간이 음수가 됩니다. 그대로 계산하면 토큰이 줄어들어 아무 요청 없이도 거절이 늘어납니다. Spring Cloud Gateway의 스크립트도 같은 처리를 합니다(동작, 근거).

**장애와 운영**

- **Redis가 멈추면 요청을 통과시켜야 하나요, 막아야 하나요?**
  제한을 넘었을 때의 피해로 정합니다. 뒤쪽 서버가 조금 바빠지는 정도라면 열어 두고, 건당 과금이나 외부 계약 한도처럼 넘으면 돈이나 외부 관계가 망가지면 닫습니다(판단: 실패하면 통과시킬까, 거절할까).
  - **꼬리: 열어 두면 공격자가 Redis를 먼저 공격해 제한을 끌 수 있지 않나요?**
    그런 구성이라면 그렇습니다. 그래서 열어 두더라도 장애 동안 서버별 메모리 제한으로 바꾸는 중간 길을 두고, "판단하지 못한 요청 수"를 지표로 보고 알림을 겁니다. 처리율 제한 하나에 보호를 전부 맡기지 않고 게이트웨이의 거친 제한을 앞에 둡니다.
  - **꼬리: 닫기로 했으면 끝인가요?**
    닫으면 Redis 장애가 API 장애가 되므로, 기다림의 상한을 짧게 하고 서킷 브레이커로 실패를 빨리 내야 합니다. 그렇지 않으면 장애 동안 모든 요청이 명령 타임아웃만큼 늦게 거절됩니다(기다림: 제한기 호출에 짧은 상한을 둡니다).

- **Redis 장애 조치로 카운터를 잃으면 어떻게 되나요?**
  복제되지 않은 증가분을 잃어 몇몇 사용자가 잠시 더 통과합니다. 넘어도 뒤쪽 서버가 조금 바빠지는 정도의 제한이라면 받아들일 수 있는 결과입니다. 같은 이유로 재고나 결제 횟수처럼 정확해야 하는 숫자는 처리율 제한 키처럼 다루면 안 됩니다(메모리 한도와 장애 조치도 같은 질문으로 이어집니다).

- **메모리 정책이 처리율 제한에 영향을 주나요?**
  `noeviction`에서 메모리가 차면 카운터 쓰기가 OOM으로 실패하므로 열어 둘지 닫을지의 분기를 탑니다. `allkeys-*`나 `volatile-*`면 카운터가 축출되어 그 사용자가 새 몫을 받습니다. 처리율 제한 키는 대개 TTL이 있으므로 `volatile-*`에서도 후보입니다.

**데이터 증가와 Spring**

- **사용자가 열 배로 늘면 무엇을 다시 계산해야 하나요?**
  동시에 살아 있는 키 수와 키 하나의 크기입니다. 고정 윈도와 토큰 버킷은 사용자 수에 비례하고, 슬라이딩 로그는 사용자 수 × 제한 횟수에 비례합니다. 키 하나의 크기는 `MEMORY USAGE`로 재서 곱합니다(키 하나가 차지하는 메모리).
  - **꼬리: 공격으로 거절 요청이 폭증하면요?**
    거절할 요청도 Redis 호출을 하므로 Redis 부하가 함께 늡니다. IP 단위의 거친 차단을 게이트웨이에서 먼저 하면 Redis까지 오는 양이 줄어듭니다(요청과 데이터가 늘면 무엇이 달라지는가).

- **전역 제한 "외부 API 초당 100번"을 Redis 키 하나로 걸면 무엇이 문제인가요?**
  모든 서버의 모든 요청이 키 하나로 몰려 핫키가 됩니다. 클러스터에서도 그 키는 노드 하나에 있으므로 나뉘지 않습니다. 서버별로 몫을 나눠 세면 부하는 나뉘지만 서버 수 변화와 불균등한 분배만큼 부정확해집니다.

- **Spring에서 `increment` 뒤에 `expire`를 부르는 코드는 왜 위험한가요?**
  `increment`는 `INCR` 하나, `expire`는 별도 명령이라 둘 사이의 틈이 그대로 있습니다. 스크립트로 묶어 한 번에 보냅니다(Spring에서 확인할 것).
  - **꼬리: Spring Cloud Gateway의 `RedisRateLimiter`를 쓰면 이런 고민이 없나요?**
    원자성과 서버 간 시계 차이, 음수 경과 시간은 스크립트 안에서 처리되어 있습니다. Redis 서버 시계 자체의 이동은 그대로 받습니다. 하지만 Redis가 실패하면 통과시키는 열어 두기 방식이고, 토큰이 초 단위로 차오릅니다. 서비스가 닫기를 요구하거나 초보다 세밀한 제한이 필요하면 맞지 않습니다.

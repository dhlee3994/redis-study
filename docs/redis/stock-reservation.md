# Redis 재고 예약과 DB 주문 확정: 두 저장소 사이에서 재고는 어디서 새고 어디서 넘치는가

> **핵심 질문**: 한정 재고를 Redis에서 먼저 차감(예약)하고 DB에서 주문을 확정할 때, 두 저장소 사이 어디서 실패하면 재고가 새거나 초과 판매되는가? 그 상태를 어떻게 발견하고 보정하며, Spring의 `@Transactional`은 그중 무엇을 해 주고 무엇을 해 주지 않는가?
>
> **범위**: 타임딜 상품 하나의 재고 예약과 주문 확정을 다룹니다. Redis 안에서 재고 확인과 차감을 한 덩어리로 만드는 방법 자체는 [Redis 원자성](./atomicity.md)에서, 요청 재시도의 멱등 키 설계는 [Redis 멱등 키](./idempotency-key.md)에서 다룹니다. 결제 연동과 입장 대기열은 다루지 않습니다. 공연 좌석처럼 단위마다 주인이 정해지는 재고도 다루지 않습니다. 이 문서의 최종 방어선인 수량 조건은 "몇 개 남았는가"만 지키므로, 그런 재고에서는 좌석 단위의 고유 제약이 그 자리를 맡아야 합니다.

## 배경 지식

### 이 문서의 예시: 재고 3개, 구매자 5명

문서 끝까지 다음 장면 하나를 씁니다.

- 타임딜 상품 `item:1`의 한정 재고는 3개이고, 구매자 u1~u5 다섯 명이 동시에 주문합니다.
- 주문 하나마다 주문 ID가 붙습니다(o1, o2, …). 같은 주문을 다시 보낼 때는 같은 주문 ID를 씁니다. 새로 주문하면 새 ID입니다.
- **Redis**에는 키 세 개가 있습니다. Redis 클러스터는 키를 정해진 수의 슬롯으로 나누고 슬롯마다 맡는 서버를 정해 데이터를 여러 서버에 나눠 담는 구성입니다. 키 이름의 중괄호 부분(`{item:1}`)이 같으면 같은 슬롯, 곧 같은 서버에 놓입니다. 스크립트 하나가 여러 키를 다루려면 그 키들이 같은 슬롯에 있어야 하므로 세 키에 같은 표시를 붙였습니다(뒤의 "요청과 데이터가 늘면 무엇이 달라지는가").
  - `stock:{item:1}`: 남은 예약 가능 수량. String, 처음 값 `"3"`.
  - `resv:{item:1}`: 진행 중인 예약. Sorted Set이고, 원소는 주문 ID, 점수는 예약 기한(밀리초 단위 시각)입니다.
  - `done:{item:1}`: 예약을 끝낸(확정했거나 되돌린) 주문 ID. Set.
- **DB**에는 테이블 두 개가 있습니다.
  - `item_stock(item_id, qty)`: 상품 재고. 처음 `qty = 3`.
  - `orders(order_id PK, item_id, user_id, status)`: 주문. `order_id`가 기본 키라 같은 주문 ID로 두 행을 만들 수 없습니다.
- **바라는 결과**: 정확히 3명의 주문이 확정되고, 나머지 2명은 품절 응답을 받으며, 판매가 끝났을 때 Redis와 DB의 남은 재고가 모두 0입니다.

```text
 Order API (JVM)                Redis                          DB
+---------------+   ① reserve  +---------------------+       +----------------------+
| request u1..u5|------------->| stock:{item:1} = 3  |       | item_stock.qty = 3   |
|               |   ③ confirm  | resv:{item:1}  = {} |       | orders = (empty)     |
|               |------------->| done:{item:1}  = {} |       |                      |
|               |              +---------------------+       |                      |
|               |------------------ ② order tx ------------->|                      |
+---------------+                                            +----------------------+
         ^
         | ④ sweep expired reservations (separate worker)
```

화살표는 주문 API가 보내는 요청의 방향이고, 번호는 한 주문의 실행 순서입니다. ④는 주문 요청과 별도로 도는 청소 작업입니다. Redis 복제본, Sentinel, DB 커넥션 풀은 그림에서 뺐습니다. Redis 복제본은 "Redis 장애 조치는 예약·확정·되돌리기를 잃습니다"에서 다룹니다.

### 두 저장소는 서로의 커밋을 모릅니다

- **한 줄**: Redis의 쓰기와 DB의 커밋은 각자 따로 확정되고, 둘을 하나로 묶는 커밋은 없습니다. 그래서 두 쓰기 사이에 실패하면 한쪽만 반영된 상태가 남습니다.
- **이 주제에서는**: ①(Redis 예약)과 ②(DB 주문 커밋) 사이, ②와 ③(Redis 확정) 사이가 모두 틈입니다. 두 단계 커밋(2PC)은 조정자가 먼저 모든 저장소에 변경을 커밋도 취소도 하지 않은 채 붙잡아 두게 하고(준비), 모두 준비되면 커밋을 알리는 방식입니다. 순서·보상·기한·대사·원천·아웃박스 같은 일반 원리와 2PC를 보통 쓰지 않는 이유는 [두 저장소에 나눠 쓰기](../cs/dual-write.md)에서 다룹니다. 이 문서는 그 원리를 Redis 명령과 장애, Spring 설정에 대입합니다.

### Redis의 원자성은 Redis 안에서만 통합니다

- **한 줄**: Redis는 명령 하나, 그리고 Lua 스크립트 하나를 다른 연결의 명령이 끼어들지 않게 끝까지 실행합니다. 실행 중 에러가 나도 이미 한 쓰기를 되돌리지는 않습니다.
- **이 주제에서는**: "재고 확인 → 차감 → 예약 기록"을 스크립트 하나로 묶어 Redis 안의 경쟁은 없앱니다. 하지만 이 덩어리는 DB 커밋과는 묶이지 않습니다. 원리와 대가는 [Redis 원자성](./atomicity.md)에서 다룹니다.

### Redis 복제는 기다리지 않고 응답합니다

- **한 줄**: 쓰기를 받는 Redis 서버를 주 서버, 그 변경을 받아 사본을 유지하는 서버를 복제본이라고 합니다. 주 서버는 쓰기를 실행하면 복제본이 그 쓰기를 받았는지 확인하지 않고 응답합니다(비동기 복제). 주 서버가 죽으면 Sentinel 같은 감시 장치가 복제본 하나를 새 주 서버로 올리는데(장애 조치), 이때 복제본에 닿지 않았던 쓰기는 새 주 서버에 없습니다.
- **이 주제에서는**: 앱이 "예약 성공", "확정 완료"를 받았어도 장애 조치 뒤의 새 주 서버에는 그 쓰기가 없을 수 있습니다. 원리는 [Redis 복제](./replication.md)에서 다룹니다.

### 예약은 기한이 있는 리스입니다

- **한 줄**: 리스는 정해진 기간 동안만 유효한 권리이고, 보유자가 죽어도 기한이 지나면 풀립니다. 대신 보유자가 기한보다 오래 멈추면 자기 리스가 끝난 줄 모른 채 일을 계속합니다.
- **이 주제에서는**: `resv:{item:1}`의 점수(기한)가 지난 예약은 청소 작업이 되돌립니다. 그런데 느렸을 뿐인 주문 API가 그 뒤에 DB에 커밋하려 할 수 있습니다. 이 겹침을 무엇이 막는지가 "앱이 죽으면: 기한과 청소 작업이 뒤처리를 맡습니다"의 주제입니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)에서 다룹니다.

### Sorted Set: 점수 순으로 늘어선, 중복 없는 집합

- **한 줄**: 원소마다 숫자 점수를 붙여 점수 순으로 정렬해 두는 Redis 자료형이고, 같은 원소는 한 번만 들어갑니다.
- **비유**: 마감 시각 순으로 꽂아 둔 접수증 꽂이입니다. 앞에서부터 보면 마감이 가장 이른 접수증이 나옵니다.
- **실제로는**: `ZADD`로 원소와 점수를 넣고, `ZSCORE`로 한 원소의 점수를 보고, `ZREM`으로 지우며, `ZRANGEBYSCORE`로 점수 구간의 원소를 꺼냅니다. 공식 복잡도는 `ZSCORE`가 O(1), `ZADD`가 원소 하나당 O(log N), `ZRANGEBYSCORE`가 O(log N + M)입니다. 여기서 N은 Sorted Set의 원소 수, M은 돌려받는 원소 수입니다. O(1)은 원소 수와 무관하게 작업량이 일정하다는 뜻이고, O(log N)은 원소 수가 두 배가 될 때 작업량이 일정량씩만 늘어난다는 뜻입니다. 비유와 다른 점은, 꽂이는 사람이 직접 순서를 맞추지만 Sorted Set은 넣을 때 Redis가 자리를 찾아 줍니다.
- **이 주제에서는**: 점수를 예약 기한으로 두면, 청소 작업이 "기한이 지금보다 이른 예약"을 앞에서부터 꺼낼 수 있습니다. 같은 주문 ID가 두 번 들어가지 않으므로 "이 주문은 이미 예약했는가"도 바로 확인됩니다.

## 왜 Redis에서 먼저 빼는가: 정확성이 아니라 경합을 덜기 위해서입니다

Redis 없이도 DB 하나로 초과 판매는 막힙니다. 주문 트랜잭션에서 `UPDATE item_stock SET qty = qty - 1 WHERE item_id = 1 AND qty > 0`처럼 조건부로 빼고, 바뀐 행이 0개면 품절로 처리하면 됩니다. 문제는 비용입니다. 다섯 명의 요청이 모두 같은 행 하나를 바꾸려 하므로, 관계형 DB는 보통 이 행의 잠금으로 한 번에 하나씩만 통과시킵니다(잠금 방식은 DB와 격리 수준에 따라 다르므로 쓰는 DB의 문서로 확인합니다). 기다리는 동안 각 요청은 DB 커넥션을 붙잡고 있습니다. 실제 타임딜에서 다섯이 수만이 되면, 커넥션 풀 크기와 트랜잭션 시간에 따라 풀이 바닥나 같은 풀을 쓰는 다른 API까지 느려질 수 있습니다.

Redis 예약을 앞에 두면, 진행 중인 예약은 재고 수를 넘지 못하므로 **동시에 DB 트랜잭션에 들어가 있는 주문도 재고 수 이하**로 묶입니다. 이 상한은 Redis가 실제보다 많이 갖지 않고, 기한이 지나 회수된 주문이 뒤늦게 DB에 오지 않는 동안의 성질입니다. 두 경우는 뒤의 "Redis 장애 조치는 예약·확정·되돌리기를 잃습니다"와 "앱이 죽으면: 기한과 청소 작업이 뒤처리를 맡습니다"에서 보며, 그때도 초과 판매는 DB가 막습니다. 예시에서 u4와 u5는 Redis에서 품절을 받고 DB에 닿지 않습니다. 다만 DB 실패로 예약이 되돌려지면 그 재고로 새 주문이 다시 DB에 오므로, 판매 전체에서 DB가 받는 시도의 누적 수는 확정 수에 실패·재시도·청소 작업의 쓰기를 더한 만큼입니다. 품절 뒤의 요청은 Redis가 DB 커넥션 없이 돌려보냅니다. 이 효과가 실제로 커넥션 대기를 얼마나 줄이는지는 풀 크기와 요청량에 달려 있어 측정해 봐야 합니다.

대가는 **재고라는 같은 사실을 두 저장소가 따로 갖게 된다**는 것입니다. 둘은 언젠가 달라집니다. Redis가 실제보다 많이 가지면 초과로 들여보내고, 적게 가지면 팔 수 있는 재고를 못 팝니다(재고가 샘). 그래서 첫 결정은 둘이 다를 때 누가 맞는지입니다.

## 원천은 DB에 둡니다: Redis가 틀려도 초과 판매가 되지 않게

원천(source of truth)은 두 저장소가 다를 때 맞다고 보는 쪽입니다. 두 가지 구성을 비교합니다.

| | DB가 원천(이 문서의 구성) | Redis가 원천 |
| --- | --- | --- |
| DB가 하는 일 | `item_stock`을 조건부로 빼고 주문을 넣음(같은 트랜잭션) | 주문만 넣음. 재고 수량은 DB에 없음 |
| Redis가 실제보다 많이 가질 때 | 초과로 들여보낸 요청을 DB가 거절. 헛걸음으로 끝남 | **초과 판매** |
| Redis가 실제보다 적게 가질 때 | 재고가 샘. DB 기준으로 다시 채움 | 재고가 샘. 무엇이 맞는지 계산해야 함 |
| Redis 장애 조치로 쓰기를 잃을 때 | 위 두 경우 중 하나. 정확성은 지켜짐 | 초과 판매 가능 |
| 대가 | 확정된 주문마다 DB에서 재고 행 하나를 갱신. 동시에 오는 주문이 대체로 재고 수 이하라 경합은 작음 | DB 쓰기가 가벼움 |

Redis 복제는 응답한 쓰기를 잃을 수 있으므로, Redis를 원천으로 두면 장애 조치 한 번에 초과 판매가 생길 수 있습니다. 그래서 이 문서는 **DB를 원천으로 두고, Redis 예약은 DB로 가는 요청을 걸러 내는 효율용 문**으로 봅니다. 이렇게 하면 Redis 쪽 실패의 결과가 "초과 판매"에서 "헛걸음이나 못 판 재고"로 바뀝니다. 효율용 장치와 정확성용 장치의 구분은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "효율을 위한 락과 정확성을 위한 락"과 같은 판단입니다.

Redis를 원천으로 둘 수밖에 없는 구성이라면(예: DB 재고 행의 경합조차 감당하지 못하는 경우), 장애 조치 뒤에 초과 판매가 있었는지를 대사로 찾아 취소하는 업무 절차까지 함께 설계해야 합니다.

## 예약 하나의 흐름: 예약, 확정, 되돌리기를 각각 스크립트 하나로

### 세 스크립트

각 스크립트는 `KEYS`로 위의 Redis 키를, `ARGV`로 주문 ID(와 기한)를 받습니다. Lua 스크립트 하나는 다른 명령이 끼어들지 않게 실행되므로, 단계 사이에 다른 주문이 끼어들 틈이 없습니다.

**예약**(①)

1. 주문 ID가 `resv`에 있으면 "이미 예약됨"을, `done`에 있으면 "이미 끝남"을 돌려주고 아무것도 바꾸지 않습니다.
2. `stock` 키가 없으면 "초기화 안 됨" 에러를 돌려줍니다. `DECR`은 키가 없으면 0에서 시작해 -1을 만들기 때문에, 키 없음을 품절과 구분하려고 먼저 확인합니다.
3. `stock`이 0 이하면 "품절"을 돌려줍니다.
4. `DECR stock`, `ZADD resv <기한> <주문 ID>`를 하고 "예약 성공"을 돌려줍니다.

1번 덕분에 같은 주문 ID로 예약을 다시 보내도 재고는 한 번만 줄어듭니다. 예약 응답을 받지 못해 다시 보내는 경우가 여기에 해당합니다.

스크립트는 실행 중 에러가 나도 앞의 쓰기를 되돌리지 않습니다. 예를 들어 기한 인자가 숫자가 아니면 `DECR`은 이미 끝났는데 `ZADD`가 실패해, 재고만 빠지고 예약 기록이 없는 상태가 남습니다. 그래서 인자 검사는 1번보다 먼저, 첫 쓰기 전에 끝냅니다.

"이미 예약됨"과 "이미 끝남"을 받은 쪽이 할 일도 정해 둡니다.

- **"이미 예약됨"**: 이 요청이 방금 보낸 예약의 응답을 못 받아 다시 보낸 것이면, 자기 예약이므로 DB 단계로 계속 갑니다. 같은 주문 ID로 들어온 **다른 요청**(클라이언트가 재시도해 다른 서버에 도착한 요청 등)이면 원래 요청이 아직 처리 중일 수 있으므로 DB 단계로 가지 않고 "처리 중"으로 응답합니다. [Redis 멱등 키](./idempotency-key.md)에서 처리 중인 요청에 409로 응답하는 것과 같은 판단입니다.
- **"이미 끝남"**: Redis와 DB를 바꾸지 않고, `orders`에서 그 주문의 상태를 읽어 응답합니다. `done`은 확정과 되돌림을 함께 담으므로 이것만으로는 주문이 성공했는지 알 수 없습니다.

**확정**(③): `ZREM resv <주문 ID>`, `SADD done <주문 ID>`. 재고는 바꾸지 않습니다. Redis 재고는 예약 때 이미 뺐고, 확정은 그 예약을 끝난 목록으로 옮길 뿐이기 때문입니다.

**되돌리기**(보상): `ZREM resv <주문 ID>`의 결과가 1(실제로 지웠음)일 때만 `INCR stock`과 `SADD done <주문 ID>`를 합니다. 결과가 0이면 아무것도 하지 않습니다.

되돌리기를 "예약이 남아 있을 때만"으로 묶은 이유는 두 가지입니다. 같은 주문을 두 번 되돌려도 재고는 한 번만 늘어납니다(멱등). 그리고 이미 확정된 주문을 실수로 되돌리려 해도 `resv`에 없으므로 아무 일도 일어나지 않습니다.

### 손으로 따라가기: 정상과 흔한 실패가 섞인 경우

예약 기한은 30초로 둡니다(가상 수치). 시각은 판매 시작부터 센 초입니다.

| 시각 | 일어난 일 | `stock` | `resv` | `done` | DB `qty` | 확정 주문 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.0 | u1~u3 예약 성공(o1, o2, o3) | 0 | o1, o2, o3 | | 3 | |
| 0.0 | u4(o4), u5(o5) 예약 → 품절 | 0 | o1, o2, o3 | | 3 | |
| 0.2 | o1 DB 커밋 → 확정 | 0 | o2, o3 | o1 | 2 | o1 |
| 0.3 | o2 DB 트랜잭션이 예외로 롤백 → 되돌리기 | 1 | o3 | o1, o2 | 2 | o1 |
| 0.3 | o3를 처리하던 주문 API 서버가 죽음 | 1 | o3 | o1, o2 | 2 | o1 |
| 1.0 | u4가 다시 주문(o6) → 예약 → DB 커밋 → 확정 | 0 | o3 | o1, o2, o6 | 1 | o1, o6 |
| 30.0 | 청소 작업: o3 기한 지남 → DB에 o3 취소 행 → 되돌리기 | 1 | | o1, o2, o3, o6 | 1 | o1, o6 |
| 31.0 | u5가 다시 주문(o7) → 예약 → DB 커밋 → 확정 | 0 | | …, o7 | 0 | o1, o6, o7 |

결과는 바라던 대로 확정 3건, Redis와 DB의 남은 재고 0입니다. 다만 o3의 재고는 0.3초부터 30초까지 아무도 쓰지 못하고 묶여 있었습니다. 이것이 예약 기한의 대가입니다. 아래 절들은 이 표의 각 줄에서 다른 일이 일어나면 무엇이 남는지 봅니다.

## 실패 지점마다 남는 상태가 다릅니다

| 실패 지점 | 남는 상태 | 결과 | 맡는 장치 |
| --- | --- | --- | --- |
| ① 예약의 응답을 못 받음 | 예약됐을 수도, 안 됐을 수도 있음 | 모름 | 같은 주문 ID로 다시 예약(멱등) |
| ② DB 트랜잭션이 확실히 롤백됨 | Redis만 빠짐 | 재고가 샘 | 되돌리기 |
| ② DB가 재고 0으로 거절 | Redis가 실제보다 많이 가졌음 | 헛걸음 | 되돌리지 않고 예약만 지움 + 대사 |
| ② 커밋의 응답을 못 받음, 기본 키 충돌 | DB에 주문이 있을 수도 없을 수도 | 모름 | 되돌리지 않고 취소 행으로 판정 |
| ①~③ 사이에 앱이 죽음 | 예약만 남음 | 재고가 묶임 | 기한과 청소 작업 |
| Redis 장애 조치 | 예약·확정·되돌리기 중 최근 것을 잃음 | Redis가 많이 가지거나 재고가 묶임 | 대사, 청소 작업 |

### 예약의 응답을 못 받으면: 같은 주문 ID로 다시 보냅니다

예약 스크립트를 보냈는데 명령 타임아웃이 났다면, 스크립트가 실행됐는지 앱은 모릅니다. 같은 주문 ID로 다시 보내면 됩니다. 실행됐었다면 1번 단계가 "이미 예약됨"을 돌려주고, 아니었다면 이번에 예약됩니다. 이 멱등성은 주문 ID를 클라이언트가 정하고 재시도 때 같은 값을 쓸 때만 성립합니다. 서버가 요청마다 새 ID를 만들면 재시도가 새 예약이 되어 재고를 두 번 뺍니다. 주문 ID를 요청에 싣는 방법은 [Redis 멱등 키](./idempotency-key.md)와 같은 판단입니다.

다시 보내지 않고 사용자에게 실패를 돌려준다면, 실행됐던 예약은 주인 없이 남습니다. 이 예약은 기한이 지나면 청소 작업이 되돌립니다.

### DB가 확실히 실패하면: 되돌리기를 보냅니다

0.3초의 o2처럼 트랜잭션이 커밋 전에 실패해 롤백됐다면, DB에는 주문도 재고 차감도 없습니다. 예외가 났다는 것과 롤백됐다는 것은 다를 수 있습니다. Spring의 기본 규칙에서는 어떤 예외가 롤백으로 이어지는지가 정해져 있으므로 "Spring의 `@Transactional`은 Redis 쓰기를 DB 커밋에 묶지 않습니다"에서 확인합니다. Redis만 1개 빠져 있으므로 되돌리기를 보냅니다. 되돌리기도 응답이 사라질 수 있지만 멱등하므로 몇 번이든 다시 보내도 됩니다. 끝내 보내지 못하고 앱이 죽어도 예약이 `resv`에 남아 있으므로 청소 작업이 기한 뒤에 되돌립니다.

단, **`orders`의 기본 키 충돌로 롤백된 경우는 확실한 실패가 아닙니다.** 같은 주문 ID의 다른 실행(또는 청소 작업)이 이미 행을 넣었다는 뜻이고, 그 실행이 주문을 확정했을 수 있습니다. 여기서 되돌리면 성공한 주문의 예약을 되돌려 Redis가 실제보다 많아집니다. 이 경우는 되돌리지 않고 "DB 커밋의 응답을 못 받으면: 되돌리지 말고 판정합니다"의 판정으로 넘깁니다.

### DB가 '재고 없음'으로 거절하면: 되돌리지 않습니다

조건부 `UPDATE`가 0행을 바꿨다는 것은, Redis는 들여보냈는데 DB의 재고가 이미 0이라는 뜻입니다. Redis가 실제보다 많이 가지고 있었던 것입니다. 이때 되돌리기(`INCR`)를 보내면 Redis의 과대 계산을 더 키워 다음 요청도 헛걸음하게 합니다. 그래서 이 경우는 `INCR` 없이 예약만 지우고 `done`에 넣는 별도의 스크립트로 처리하고, 이 일이 일어났다는 사실을 지표로 남겨 대사를 앞당깁니다. 정확성은 DB가 지켰으므로 초과 판매는 없습니다. 어떻게 Redis가 많이 가지게 되는지는 "Redis 장애 조치는 예약·확정·되돌리기를 잃습니다"에서 다룹니다.

### DB 커밋의 응답을 못 받으면: 되돌리지 말고 판정합니다

커밋 요청을 보낸 뒤 DB 연결이 끊기면, 커밋이 됐는지 앱은 모릅니다. 이때 "실패했겠지" 하고 되돌리면 위험합니다.

| 순서 | 주문 API (o1) | Redis `stock` | DB |
| --- | --- | --- | --- |
| 1 | 예약 성공 | 2 | qty 3 |
| 2 | 커밋 요청 → DB는 커밋했지만 응답이 사라짐 | 2 | qty 2, o1 확정 |
| 3 | 실패로 보고 되돌리기 | **3** | qty 2, o1 확정 |

Redis가 실제보다 1개 많아졌습니다. DB가 원천이므로 초과 판매는 DB가 막지만, 그 1개만큼 마지막에 누군가 헛걸음합니다. Redis가 원천인 구성이었다면 초과 판매입니다.

그렇다고 `orders`에서 o1을 조회해 "없으면 되돌리기"로 정할 수도 없습니다. 조회는 그 시점까지 커밋된 행만 보므로, 아직 끝나지 않은 원래 트랜잭션이 조회 뒤에 커밋하면 같은 불일치가 생깁니다. 조회로 확정할 수 있는 것은 "있음"뿐입니다.

그래서 결과를 모를 때는 청소 작업과 같은 **판정**을 합니다. o1의 취소 행을 먼저 넣어 늦은 커밋을 막은 뒤, 넣기에 성공하면 되돌리고, 기본 키 충돌이면 기존 행의 상태가 확정이면 확정 스크립트를, 취소면 되돌리기를 보냅니다(절차는 다음 절). 원래 트랜잭션이 아직 진행 중이면, DB는 보통 취소 행 넣기를 그 트랜잭션이 끝날 때까지 기다리게 한 뒤 결과에 따라 충돌 또는 성공으로 처리합니다(검사 방식은 DB 문서로 확인합니다). DB에 닿지 못해 판정조차 못 하면 아무것도 하지 않고 사용자에게 "처리 중"으로 응답합니다. 예약은 `resv`에 남아 있으므로 청소 작업이 기한 뒤에 같은 판정을 대신 합니다. Spring이 이 "모름"을 어떻게 드러내는지는 "Spring의 `@Transactional`은 Redis 쓰기를 DB 커밋에 묶지 않습니다"에서 다룹니다.

### 앱이 죽으면: 기한과 청소 작업이 뒤처리를 맡습니다

0.3초의 o3처럼 예약 뒤에 주문 API 서버가 죽으면, 되돌리기를 보낼 주체가 없습니다. 청소 작업이 주기적으로 다음을 합니다.

1. `ZRANGEBYSCORE resv:{item:1} -inf <지금> LIMIT 0 <한 번에 처리할 수>`로 기한이 지난 예약을 꺼냅니다.
2. 예약마다 DB에 `INSERT INTO orders(order_id, …, status) VALUES (o3, …, 'CANCELLED')`를 커밋합니다.
3. 넣기에 성공하면 o3는 DB에 없던 주문이므로 되돌리기를 보냅니다.
4. 기본 키 충돌로 실패하면 o3 행이 이미 있습니다. 상태가 확정이면 확정 스크립트를, 취소면(이전 청소가 2번까지 하고 죽은 경우) 되돌리기를 보냅니다.

2번이 "조회해서 없으면 되돌리기"가 아니라 **취소 행을 먼저 넣는 것**인 이유가 리스의 빈틈입니다. o3의 서버가 죽은 것이 아니라 GC 정지로 40초 멈췄다가 깨어나 DB 커밋을 시도한다고 합시다.

| 시각 | 청소 작업 | o3의 주문 API(멈췄다 깨어남) | DB |
| --- | --- | --- | --- |
| 30.0 | o3 취소 행 커밋 → 되돌리기(`stock` +1) | (멈춤) | qty 1, o3 취소 |
| 31.0 | | | o7이 그 1개를 가져감: qty 0 |
| 40.0 | | 트랜잭션: 재고 빼기 → o3 넣기 | `qty > 0` 조건으로 0행 → 품절, 또는 o3 기본 키 충돌 → 롤백 |

청소 작업이 "조회해서 없으니 되돌림"만 했다면, 40초에 DB 재고가 남아 있는 경우 o3의 커밋이 성공해 1개를 가져갑니다. 그런데 Redis는 그 1개를 이미 되돌려 다른 사람에게 내준 상태이므로, Redis가 실제보다 1개 많아집니다. DB가 원천이면 마지막에 1명이 헛걸음하고, Redis가 원천이면 초과 판매입니다. 취소 행이 먼저 있으면 o3의 늦은 커밋은 기본 키 충돌로 반드시 실패합니다. 마지막 확인을 원천에 맡기는 방식으로, [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 펜싱 토큰과 같은 생각입니다.

깨어난 o3의 주문 API는 커밋 실패를 받으면 되돌리기를 보내지 않습니다. 청소 작업이 이미 했고, 보내더라도 `resv`에 o3가 없어 아무 일도 일어나지 않습니다.

### 예약 기한은 두 위험을 맞바꿉니다

- **짧으면**: 느린 주문이 청소와 겹치는 일이 잦아집니다. 겹쳐도 정확성은 위의 취소 행이 지키지만, 사용자는 주문 처리 도중 실패를 받습니다.
- **길면**: 서버가 정말 죽었을 때 그 재고가 기한만큼 묶여, 품절 직후에는 "남은 재고가 있는데 품절" 상태가 이어집니다.

기한은 청소 작업이 회수를 시작해도 되는 시각일 뿐, 그 뒤의 확정을 막지 않습니다. 청소가 취소 행을 넣기 전에 느린 주문이 커밋하면 그 주문은 확정되고, 청소는 확정 행을 보고 확정으로 맞춥니다. "몇 분 안에 끝내지 않으면 무효" 같은 업무 마감이 필요하면, DB 주문 트랜잭션이 커밋할 때 그 기한을 함께 확인해야 합니다.

기한은 주문 하나의 정상 처리 시간 상한(DB 트랜잭션 제한 시간과 그 앞뒤의 호출 제한 시간의 합)보다 길게 잡습니다. 기한은 주문 API 서버의 시계로 정하고 청소 작업은 자기 시계로 비교하므로, 두 서버의 시각 차이만큼 일찍 청소될 수 있습니다. 이 경우도 취소 행이 정확성을 지킵니다.

## Redis 장애 조치는 예약·확정·되돌리기를 잃습니다

Redis 주 서버가 죽고 복제본이 새 주 서버가 되면, 복제본에 닿지 않았던 최근 쓰기는 사라집니다. 스크립트 하나가 실제로 한 쓰기들은 복제 흐름에 한 덩어리(`MULTI`/`EXEC`)로 들어가므로, 끝까지 실행된 예약의 `DECR`과 `ZADD`는 함께 남거나 함께 사라집니다. 메모리 한도, 읽기 전용 복제본, 디스크 쓰기 오류, 복제본 수 부족으로 쓰기를 거부하는 일은 스크립트가 아직 아무것도 쓰지 않았을 때만 일어나므로, 이 네 가지 때문에 스크립트가 중간에서 끊기지는 않습니다. 인자 오류처럼 첫 쓰기 뒤에 날 수 있는 명령 에러는 "세 스크립트"에서 본 대로 첫 쓰기 전 검사로 막습니다. 무엇을 잃었느냐에 따라 결과가 다릅니다. 아래 표는 이 문서의 추론이며, 장애 조치를 재현해 확인하지 않았습니다.

| 잃은 쓰기 | 새 주 서버의 상태 | 결과 |
| --- | --- | --- |
| o1의 예약(DB 커밋은 됨) | `stock`이 1 많고 `resv`에 o1 없음 | o1의 확정 스크립트는 `ZREM`이 0이라 무해. Redis가 1개 많아 마지막에 1명이 헛걸음(DB가 재고 0으로 거절) |
| o1의 확정 | `resv`에 o1이 되살아남 | 기한 뒤 청소 작업이 o1 확정 행을 보고 확정 처리. 무해 |
| o2의 되돌리기(DB는 롤백됨) | `stock`이 1 적고 `resv`에 o2가 되살아남 | 기한 뒤 청소 작업이 DB에 o2 취소 행을 넣고 되돌리기. 그때까지 재고 1개가 묶임 |
| 되돌리기의 `INCR`만 남고 예약이 남아 있는 상태 | 끝까지 실행된 스크립트라면 생기지 않음 | 한 스크립트의 쓰기는 함께 남거나 함께 사라지므로 |

예약을 잃은 첫 줄을 예시로 따라가면, 장애 조치 뒤 Redis `stock`은 3, DB `qty`는 2입니다. Redis가 3명을 더 들여보내고, DB는 2명만 받고 세 번째를 "재고 없음"으로 거절합니다. 그 사람은 "DB가 '재고 없음'으로 거절하면: 되돌리지 않습니다"의 경로로 품절 응답을 받습니다. 초과 판매는 없고, 대가는 한 명의 헛걸음입니다. Redis가 원천이었다면 4명에게 팔립니다.

잃는 구간을 줄이는 장치로 예약 뒤에 **같은 연결로** `WAIT 1 <제한 시간>`을 보내 복제본 하나가 받았는지 확인하는 방법이 있습니다. `WAIT`은 그 연결이 앞서 보낸 쓰기만 보며, 돌려받은 복제본 수가 1보다 작으면(제한 시간이 지나면 그렇게 끝납니다) 확인되지 않은 것이므로 앱이 반환값을 보고 대응을 정해야 합니다. 공식 문서는 `WAIT`이 Redis를 강한 일관성 저장소로 만들지 않는다고 밝히므로, 이것은 잃는 경우를 줄일 뿐입니다. 대가는 복제본의 확인을 기다리는 만큼 늘어나는 예약 지연입니다. DB가 원천인 구성에서는 잃어도 정확성이 지켜지므로, 보통은 `WAIT` 대신 장애 조치 뒤 대사를 택합니다(이 문서의 판단). `WAIT`과 `min-replicas-to-write`의 세부는 [Redis 복제](./replication.md)의 "WAIT은 기다려서, min-replicas는 거부해서 잃는 구간을 줄입니다"에서 다룹니다.

## 대사: DB를 기준으로 Redis의 재고를 다시 맞춥니다

### 불변식

DB가 원천이면, 정상일 때 다음 식이 성립합니다.

> Redis `stock` = DB `qty` − (`resv`에 있는 예약 중 DB에 확정 주문 행이 없는 수)

빼는 것은 `resv`의 예약 전부가 아니라 **DB에 확정 주문 행이 없는 예약**입니다. DB 커밋은 끝났지만 확정 스크립트가 아직 안 간 예약은 DB `qty`에 이미 반영됐으므로 빼면 두 번 세게 됩니다. 반대로 청소 작업이 취소 행을 넣었지만 아직 되돌리지 않은 예약은 빼야 합니다. 취소 행은 `orders`에만 들어가고 DB `qty`를 바꾸지 않으므로, 그 예약의 몫은 Redis에서만 빠져 있습니다.

예시 표의 1.0초 직후라면 DB `qty` 1, `resv`에 o3 하나(DB에 없음), 그래서 Redis `stock`은 1 − 1 = 0이어야 하고 실제로 0입니다. 장애 조치로 o1의 예약을 잃었다면 Redis `stock`은 기대보다 1 많습니다. 반면 o2의 되돌리기를 잃은 경우는 `stock`이 1 적은 대신 o2 예약도 되살아나 식은 그대로 성립합니다. 이런 "묶인 재고"는 식이 아니라 기한이 지난 예약으로 드러나고, 청소 작업이 맡습니다. 식이 "Redis가 적다"를 가리키는 것은 예약 없이 재고만 빠진 경우, 예를 들어 DB가 실패한 주문에 확정 스크립트를 보낸 코드 오류입니다.

### 두 저장소를 같은 순간에 읽을 수 없습니다

대사 작업이 Redis를 읽고 DB를 읽는 사이에도 주문은 진행됩니다. 예를 들어 Redis를 읽은 직후 o6가 DB에 커밋되면, 대사 작업은 정상인데도 "Redis가 1 많다"고 계산합니다. 그래서 **찾기와 고치기를 나눕니다.**

- **판매 중의 차이는 탐지 신호로만 씁니다.** 예약 기한보다 긴 간격을 두고 같은 방향의 차이가 이어지면 불일치가 있다고 보고 알립니다. 같은 숫자가 반복돼도 같은 원인이라는 보장은 없으므로, 그 숫자를 그대로 보정값으로 쓰지 않습니다.
- **고치는 것은 멈춘 상태에서 합니다.** 그 상품의 예약 스크립트가 새 예약을 받지 않게 막고(예: 판매 중지 표시 키를 스크립트가 먼저 확인), 진행 중인 예약이 확정되거나 청소로 정리되어 `resv`가 빌 때까지 기다립니다. 다만 `resv`가 비었다고 진행 중인 주문이 없는 것은 아닙니다. 장애 조치로 예약 기록만 잃은 주문은 `resv`에 없는 채로 DB 커밋을 계속할 수 있습니다. 그래서 문을 닫은 뒤 주문 하나의 정상 처리 시간 상한만큼도 지난 다음에 식을 계산합니다. 그러면 정상 시간 안에 끝나는 주문은 모두 DB에 반영됐으므로 식이 성립해야 하고, 차이는 그대로 고칠 대상입니다. 다만 이 기다림은 늦은 커밋을 막는 장치가 아닙니다. 이 상한은 호출마다 건 제한 시간의 합일 뿐이어서, 예약 직후 DB 트랜잭션을 시작하기 전에 오래 멈췄던 주문(긴 GC 정지 등)은 그 뒤에 커밋할 수 있습니다. 그러면 그 주문 수만큼 Redis가 다시 많아지지만, 초과 판매는 DB의 조건부 차감이 막고 피해는 많아야 그만큼의 헛걸음입니다. 이 차이는 다음 대사의 차이나 "DB 재고 없음"으로 지운 횟수 중 하나 이상으로 드러납니다. 판매 시작 전 초기화와 판매 종료 뒤 정산도 같은 상태입니다.
- **고치는 주체는 상품당 하나입니다.** 대사 작업 두 개가 같은 부족분을 각자 계산해 `INCRBY`하면 두 번 더해집니다. `INCRBY`는 받은 수를 현재 값에 더할 뿐 언제 계산한 값인지 확인하지 않기 때문입니다. 보정의 응답을 못 받았을 때도 같은 값을 다시 보내지 않고, 다시 읽어 계산부터 합니다.
- **값은 멈춘 상태에서 계산한 기대값으로 씁니다.** 멈춘 동안에는 다른 `DECR`이 없으므로 `SET`으로 덮어써도 지워지는 차감이 없습니다. 멈추지 않고 고치면 덮어쓰기는 그 사이의 `DECR`을 지웁니다. `INCRBY <차이>`도 답이 아닙니다. 고치는 주체가 하나여도, 판매 중에 계산한 차이는 앞의 "판매 중의 차이는 탐지 신호로만 씁니다"처럼 진행 중인 주문 때문에 틀릴 수 있고, 그 틀린 차이를 그대로 더하기 때문입니다. 판매를 멈추지 않고 고쳐야 한다면 수가 아니라 주문 ID 단위로 맞추는 방식이 필요합니다(Redis 재고를 DB 기준으로 다시 맞추기).

### 언제 돌리는가

- **장애 조치 직후**: 응답한 쓰기를 잃는 대표적인 시점이므로 가장 중요합니다. 영속성을 끈 주 서버가 장애 조치 전에 빈 상태로 다시 시작하는 경우처럼 장애 조치 없이 잃는 경로도 있으므로([Redis 영속성](./persistence.md)), Redis 재시작도 같은 신호로 봅니다. Sentinel의 주 서버 교체 알림(`+switch-master`)을 듣거나, 주문 API가 연결 재수립을 감지했을 때 대사를 시작합니다.
- **"DB가 재고 없음으로 거절"이 생겼을 때**: Redis가 많이 가졌다는 직접 증거입니다.
- **주기적으로**: 위 두 신호를 놓친 경우와 예상하지 못한 버그를 잡기 위해 둡니다.
- **판매 종료 뒤**: DB `qty`가 0보다 큰데 Redis가 품절이었다면 재고가 샌 것입니다. 원인을 찾을 수 있게 차이와 시각을 기록합니다.

대사는 불일치를 **생긴 뒤에** 찾습니다. DB가 원천인 구성에서는 그사이 생긴 피해가 "헛걸음"이나 "잠시 못 판 재고"에 그치므로 이것으로 충분합니다. Redis가 원천이라면 그사이 생긴 초과 판매는 대사가 되돌리지 못합니다.

## Spring의 `@Transactional`은 Redis 쓰기를 DB 커밋에 묶지 않습니다

`@Transactional` 메서드 안에서 예약 스크립트와 DB 주문 저장을 함께 부르면 "둘이 한 트랜잭션"처럼 보이지만, 그렇지 않습니다. Spring Data Redis는 자체 트랜잭션 매니저(`PlatformTransactionManager` 구현)를 제공하지 않고, `@Transactional`은 DB의 트랜잭션 매니저가 관리하는 DB 트랜잭션 하나를 시작하고 끝냅니다. Redis가 이 트랜잭션에 어떻게 참여하는지는 `RedisTemplate`의 `enableTransactionSupport` 설정이 정합니다.

### 기본(꺼짐): Redis 명령은 바로 실행되고, 롤백되지 않습니다

`RedisTemplate`의 `enableTransactionSupport` 기본값은 `false`입니다. 이때 `@Transactional` 안의 Redis 명령은 보낸 즉시 실행되고 결과도 바로 돌려받습니다. DB 트랜잭션이 롤백돼도 Redis 쪽은 그대로입니다. 즉 "예약 → DB" 순서의 두 쓰기이고, DB가 롤백되면 되돌리기를 앱이 직접 보내야 합니다. 이 문서의 흐름은 이 기본 동작을 전제로 합니다.

### 켜면: 쓰기는 DB 커밋 뒤로 미뤄지고, 결과를 받을 수 없습니다

`setEnableTransactionSupport(true)`로 켜고 읽기 전용이 아닌 트랜잭션 안에서 템플릿을 쓰면, Spring Data Redis는 다음처럼 동작합니다.

1. 트랜잭션 안에서 처음 Redis를 쓸 때 연결 하나를 현재 스레드에 묶고 그 연결에 `MULTI`를 보냅니다. 클러스터 연결은 `MULTI`를 지원하지 않아 이 단계에서 `InvalidDataAccessApiUsageException`이 납니다. 아래 2~4번은 주 서버 하나에 연결하는 구성(단일 서버, Sentinel) 이야기입니다.
2. 쓰기 명령(스크립트 실행 포함)은 그 연결로 가서 Redis의 대기열에 쌓이고, 앱에는 **`null`**이 돌아옵니다. `decrement`의 API 문서도 트랜잭션 안에서는 `null`을 돌려준다고 적습니다.
3. 읽기 명령은 묶이지 않은 다른 연결로 바로 실행되므로, 대기열에 쌓인 자기 쓰기를 보지 못합니다.
4. DB 트랜잭션이 끝난 **뒤**에 결과에 따라 `EXEC`(커밋) 또는 `DISCARD`(롤백, 결과 모름)를 보냅니다.

이 설정이 재고 예약에 맞지 않는 이유는 세 가지입니다.

- **예약 결과로 판단할 수 없습니다.** 예약 스크립트의 결과가 `null`이므로 "예약 성공인가 품절인가"를 알 수 없습니다. Redis로 DB 앞의 문을 만든다는 목적 자체가 성립하지 않습니다.
- **순서가 "DB 먼저, Redis 나중"으로 바뀝니다.** `EXEC`는 DB 커밋이 끝난 뒤에 나갑니다. Redis가 문이 아니라 DB를 뒤따르는 사본이 됩니다.
- **`EXEC`가 실패해도 호출한 쪽은 모릅니다.** Spring은 커밋 뒤의 완료 콜백에서 난 예외를 로그(`TransactionSynchronization.afterCompletion threw exception`)로만 남기고 호출한 쪽에 던지지 않습니다. DB는 커밋됐고 메서드는 성공으로 끝나는데, Redis 쪽은 `EXEC`가 닿지 않아 반영되지 않았을 수도, 실행됐는데 응답만 사라졌을 수도, 대기열의 일부 명령만 에러가 나고 나머지는 반영됐을 수도 있습니다(`EXEC`는 에러가 난 명령이 있어도 나머지를 실행하고 되돌리지 않습니다). 어느 쪽이든 앱은 결과를 모른 채 성공으로 응답합니다.

또 커밋 도중 DB 연결이 끊기는 등 커밋 단계에서 트랜잭션 예외가 나면, 기본 설정(`rollbackOnCommitFailure = false`)의 Spring은 완료 상태를 "알 수 없음"(`STATUS_UNKNOWN`)으로 콜백에 알리고, Spring Data Redis는 이때 `DISCARD`를 보냅니다. DB가 실제로는 커밋했다면 Redis 쓰기만 버려집니다. 다만 커밋 단계의 예외가 모두 "알 수 없음"은 아닙니다. 롤백 표시가 붙어 커밋 대신 롤백된 경우(`UnexpectedRollbackException`)는 "롤백"으로 알립니다.

### 이 문서의 흐름을 Spring에 놓는 법

- 예약과 확정·되돌리기는 **트랜잭션 지원을 끈 템플릿으로, `@Transactional` 메서드 바깥에서** 부릅니다. 바깥 서비스 메서드가 예약 → (트랜잭션 메서드 호출) → 확정을 차례로 부르는 모양입니다.
- **예외가 났다고 롤백된 것은 아닙니다.** `@Transactional`의 기본 규칙은 `RuntimeException`과 `Error`에만 롤백하고, 그 밖의 예외(`Exception`을 직접 상속한 예외)는 예외를 던지면서도 **커밋**합니다. Kotlin은 checked 예외를 강제하지 않아 이런 예외를 무심코 던지기 쉽습니다. Spring 6.2의 `@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)`로 모든 예외에 롤백하게 바꿀 수 있고, `EnableTransactionManagement`의 API 문서도 Kotlin 앱에는 이 전환을 권합니다. 그렇지 않으면 메서드마다 `rollbackFor`를 지정합니다.
- 트랜잭션 메서드가 롤백으로 이어지는 예외를 커밋 전에 던졌다면 DB는 롤백됐으므로 되돌리기를 보냅니다. 단, 조건부 `UPDATE`가 0행이라 던진 품절 예외라면 "DB가 '재고 없음'으로 거절하면: 되돌리지 않습니다"의 경로로, `orders`의 기본 키 충돌이라면 판정으로 갑니다.
- 커밋 단계의 트랜잭션 예외는 결과를 모르는 경우로 보고, 되돌리지 말고 "DB 커밋의 응답을 못 받으면: 되돌리지 말고 판정합니다"의 판정을 합니다.
- 확정을 `TransactionSynchronization`의 커밋 뒤 콜백에 등록하는 방법도 있지만, 이 콜백은 서버가 그 직전에 죽으면 실행되지 않습니다. 어느 방식이든 확정이 빠질 수 있다는 전제는 같고, 그 경우는 청소 작업이 확정 행을 보고 맞춥니다.

## 순서를 바꾸면: DB 먼저, Redis는 아웃박스로 따라가는 사본

Redis를 문으로 쓰지 않고 "남은 재고 표시"처럼 DB를 뒤따르는 용도로만 쓴다면 순서는 DB 먼저가 맞습니다. 이때 커밋 직후 서버가 죽으면 Redis 반영이 빠지므로, 주문 트랜잭션 안에서 "item:1의 표시 재고를 갱신할 것"이라는 행을 아웃박스 테이블에 함께 넣고, 별도 과정이 그 행을 읽어 Redis에 반영합니다.

- 반영이 두 번 갈 수 있으므로, `DECR` 대신 **DB에서 읽은 `qty`를 그대로 `SET`**하는 쪽이 멱등합니다. 다만 늦게 도착한 반영이 새 값을 옛 값으로 덮지 않게, 값과 함께 버전(예: 재고 행의 갱신 번호)을 두고 더 큰 버전만 쓰게 합니다. 같은 문제가 캐시 무효화에서는 [Cache-aside 정합성](./cache-aside-consistency.md)의 "버전을 붙여 더 새로운 값만 쓰게 합니다"로 다뤄집니다.
- 이 사본은 늦게 반영되므로 문으로 쓰면 안 됩니다. 표시가 "1개 남음"인데 이미 품절일 수 있고, 주문은 DB가 판정합니다.
- 이 순서는 DB로 가는 경합을 줄여 주지 않습니다. 그것이 필요하면 이 문서의 "Redis 먼저 예약" 흐름으로 돌아옵니다.

아웃박스의 일반 원리와 대가는 [두 저장소에 나눠 쓰기](../cs/dual-write.md)의 "아웃박스: 원천에 먼저 쓰고, 나머지는 '할 일'로 남겨 옮깁니다"에서 다룹니다.

## 요청과 데이터가 늘면 무엇이 달라지는가

- **`resv`의 크기는 진행 중인 예약 수입니다.** 재고보다 커질 수 없으므로 작게 유지됩니다. 청소 작업의 `ZRANGEBYSCORE`는 O(log N + M)이고, `LIMIT`으로 한 번에 꺼내는 수 M을 묶을 수 있습니다.
- **`done`은 판매가 끝날 때까지 주문 ID 수만큼 자랍니다.** 확정과 되돌림을 합친 수이므로, 되돌림이 많으면 재고보다 커질 수 있습니다. 판매가 끝나고 재시도가 올 수 있는 기간이 지나면 키째 지우거나 만료를 둡니다. 판매 중에 만료되면 재시도가 새 예약이 될 수 있으므로 판매 기간보다 길게 둡니다.
- **요청이 몰려도 Redis 쪽 비용은 요청당 스크립트 하나입니다.** 품절 뒤의 요청은 1~3번 단계에서 끝나 쓰기가 없습니다. 반면 상품 하나의 키 세 개가 한 노드에 있으므로, 요청이 그 노드 하나에 몰리는 것은 피할 수 없습니다([Redis 원자성](./atomicity.md)의 "해시 태그로 슬롯을 맞추면 그 키들은 한 노드에 몰립니다").
- **클러스터에서는 세 키가 같은 슬롯이어야 스크립트가 실행됩니다.** 키 이름의 `{item:1}`이 그 역할을 합니다.
- **DB 쪽 비용은 동시에는 대체로 재고 수 이하, 누적으로는 확정 + DB 실패 + 헛걸음 + 청소 작업의 쓰기만큼입니다.** DB 실패로 되돌린 재고는 다시 예약되어 DB로 오기 때문입니다. 헛걸음이 늘었다는 것은 Redis가 실제보다 많이 가졌다는 신호이므로, 비용 지표이자 정합성 지표입니다.
- **상품이 많아지면 대사도 상품 수만큼 돕니다.** 판매 중인 상품만 대상으로 하고, 판매가 끝난 상품은 한 번 정산한 뒤 키를 지웁니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 처음 다룬 곳 |
| --- | --- | --- |
| Redis 예약이 초과 판매를 막는다 | DB만으로도 조건부 `UPDATE`로 막힙니다. Redis 예약은 DB로 가는 경합을 줄이고, 원천은 DB입니다 | 왜 Redis에서 먼저 빼는가 |
| Lua로 원자적이니 DB와도 원자적이다 | Redis 안에서만 원자적이고, DB 커밋과는 묶이지 않습니다 | 배경 지식 |
| DB 커밋이 실패하면 무조건 되돌린다 | 결과를 모르거나 기본 키 충돌이면 취소 행으로 판정하고, "재고 없음" 거절이면 되돌리지 않습니다. 예외가 났어도 롤백 규칙에 따라 커밋됐을 수 있습니다 | 실패 지점마다 남는 상태가 다릅니다 |
| 예약에 기한을 두면 늦은 커밋도 해결된다 | 청소가 DB에 취소 행을 먼저 넣어야 늦은 커밋이 거절됩니다 | 앱이 죽으면 |
| 앱이 "예약 성공"을 받았으면 Redis에 남아 있다 | 장애 조치로 응답한 쓰기도 잃을 수 있습니다 | Redis 장애 조치 |
| 대사에서 본 차이를 바로 고치면 된다 | 판매 중에는 진행 중인 주문 때문에 차이가 보이고, 덮어쓰기는 그 사이의 `DECR`을 지우며, 차이만큼 더하기도 두 작업이 겹치면 두 번 반영됩니다. 고치기는 판매를 멈춘 상태에서 한 작업만 합니다 | 대사 |
| `@Transactional`이 Redis와 DB를 함께 커밋·롤백한다 | 기본은 Redis가 바로 실행되고 롤백되지 않습니다. 켜면 DB 커밋 뒤에 `EXEC`가 나가고, 그 실패는 호출한 쪽에 전달되지 않습니다 | Spring의 `@Transactional` |

## 실무 포인트

### 어떤 구성을 고를까

1. **DB 하나로 버틸 수 있으면 Redis 예약을 두지 않습니다.** 조건부 `UPDATE`만으로 정확하고, 두 저장소의 틈이 아예 없습니다. DB 커넥션 대기와 행 잠금 대기가 실제로 문제가 될 때 Redis 예약을 더합니다.
2. **Redis 예약을 두면 DB를 원천으로 둡니다.** DB가 조건부 차감과 주문을 같은 트랜잭션에서 하고, Redis는 문 역할만 합니다.
3. **Redis를 표시·집계용 사본으로만 쓰면 DB 먼저 + 아웃박스**입니다.
4. **Redis를 원천으로 두는 것은 마지막 선택지**입니다. 장애 조치 한 번에 초과 판매가 날 수 있음을 업무가 받아들이고, 찾아서 취소하는 절차가 있을 때만 고릅니다.

### 중요도별 점검 항목

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | DB 트랜잭션에서 재고를 조건부로 빼고 주문과 함께 커밋 | Redis가 어떻게 틀려도 초과 판매가 나지 않게 하는 최종 방어선입니다 |
| 필수 | 예약·확정·되돌리기를 주문 ID 기준으로 멱등하게 | 응답 유실 재시도와 중복 보상이 재고를 두 번 바꿉니다 |
| 필수 | 결과를 모르는 실패와 확실한 실패를 코드에서 구분 | 모를 때 되돌리면 Redis가 실제보다 많아집니다 |
| 필수 | 청소 작업이 DB에 취소 행을 먼저 넣은 뒤 되돌리기 | 느린 주문의 늦은 커밋을 원천이 거절하게 합니다 |
| 필수 | 재고 예약 템플릿의 `enableTransactionSupport`를 끄고, 예약을 `@Transactional` 바깥에서 실행 | 켜면 결과가 `null`이고 Redis 쓰기가 DB 커밋 뒤로 밀립니다 |
| 필수 | 재고 키가 메모리 축출 대상이 되지 않게 | 재고 키가 지워지면 "초기화 안 됨"으로 판매가 멈춥니다([Redis 원자성](./atomicity.md)의 "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다") |
| 알면 유리 | 장애 조치·Redis 재시작 직후와 판매 종료 뒤의 대사 | 잃은 쓰기로 생긴 수량 차이를 찾는 수단입니다 |
| 알면 유리 | 예약 기한을 정상 처리 시간 상한보다 길게, 너무 길지 않게 | 짧으면 실패가 늘고, 길면 재고가 묶입니다 |
| 참고 | 예약 뒤 `WAIT` | 장애 조치 손실을 줄이지만 지연이 늘고 보장하지는 않습니다 |

### 관찰할 것

- **예약 결과별 횟수**: 예약 성공, 품절, 이미 예약됨, 이미 끝남, 초기화 안 됨. "초기화 안 됨"은 재고 키가 없다는 뜻입니다. 판매 시작 전 초기화가 빠졌는지, 축출(`INFO`의 `evicted_keys`)이나 만료로 사라졌는지 나눠 확인합니다.
- **예약의 끝 상태별 횟수**: 확정, 되돌림, 청소로 되돌림, 청소로 확정, "DB 재고 없음"으로 지움. 마지막 것은 Redis가 실제보다 많았다는 직접 신호입니다.
- **가장 많이 기한을 넘긴 예약**: `resv`에서 점수가 가장 작은 원소의 기한이 지금보다 얼마나 지났는지입니다(예약을 만든 뒤 지난 시간이 아닙니다). 크게 넘긴 예약이 남아 있으면 청소 작업이 멈췄거나, 돌고 있지만 DB 장애·잠금 대기로 판정이 실패하고 있거나, 처리량보다 많이 밀린 것입니다. 청소 작업의 실행 횟수와 판정 실패 횟수를 함께 봐서 나눕니다.
- **대사 차이**: 상품별 "기대 `stock` − 실제 `stock`"을 기록합니다. 양수가 지속되면 Redis가 적게 가진 것, 음수면 많이 가진 것입니다. 기한이 지나 묶인 예약은 이 차이에 나타나지 않으므로 위 항목으로 봅니다.
- **판매 종료 때 DB `qty`**: 0보다 큰데 Redis가 품절이었다면 재고가 샌 것입니다.
- **Redis 장애 조치 이벤트**: Sentinel의 `+switch-master`, `INFO replication`의 역할 변화. 이 시각과 대사 차이를 함께 봅니다.
- **Spring 로그**: `TransactionSynchronization.afterCompletion threw exception`. 모든 완료 콜백이 쓰는 공통 로그이므로, 예외의 스택에서 Redis 트랜잭션 콜백(`RedisConnectionUtils`)인지 먼저 확인합니다. Redis 콜백이라면 그 커밋의 Redis 쓰기는 결과를 모르는 상태이므로 대사 대상입니다.

## 말로 설명하기

### 30초 버전

타임딜 재고를 Redis에서 먼저 예약하는 이유는 정확성이 아니라, 동시에 DB 재고 행을 두고 다투는 주문을 재고 수 이하로 줄이기 위해서입니다. Redis와 DB는 서로의 커밋을 모르므로 두 쓰기 사이의 실패는 항상 남고, 그래서 DB가 조건부 차감으로 원천을 맡게 해 Redis가 틀려도 초과 판매가 아니라 헛걸음이나 못 판 재고로 끝나게 합니다. 남은 불일치는 멱등한 되돌리기, 기한과 청소 작업, DB 기준 대사로 고칩니다.

### 2분 버전

한정 재고 3개에 수만 명이 몰리면 DB 재고 행 하나에 잠금 대기가 쌓이고, 풀 크기와 트랜잭션 시간에 따라 커넥션 풀이 바닥날 수 있습니다. 그래서 Redis에서 Lua 스크립트 하나로 재고를 확인하고 빼면서 주문 ID와 기한을 예약으로 기록하고, 통과한 요청만 DB로 보냅니다. DB는 같은 트랜잭션에서 재고를 조건부로 빼고 주문을 넣습니다. 이것이 원천입니다. 이제 틈별로 봅니다. DB가 확실히 롤백되면 예약을 되돌리는데, 되돌리기는 예약이 남아 있을 때만 재고를 늘리므로 여러 번 보내도 안전합니다. DB 커밋의 응답을 못 받으면 결과를 모르므로 바로 되돌리지 않습니다. 모를 때 되돌리면 Redis가 실제보다 많아지기 때문입니다. 조회로 "없음"을 봐도 원래 트랜잭션이 뒤늦게 커밋할 수 있으므로, 취소 행을 먼저 넣어 판정합니다. 서버가 죽으면 청소 작업이 기한 지난 예약을 꺼내 DB에 취소 행을 먼저 넣고 되돌립니다. 취소 행 덕분에 느렸던 서버의 늦은 커밋은 기본 키 충돌로 거절됩니다. Redis 장애 조치는 응답한 예약이나 되돌리기를 잃을 수 있어, 장애 조치 직후 DB 기준으로 "Redis 재고 = DB 재고 − DB에 확정 주문이 없는 예약"을 대사하고, 고칠 때는 그 상품의 판매를 잠깐 멈춥니다. Spring의 `@Transactional`은 이 둘을 묶어 주지 않습니다. 기본은 Redis 명령이 바로 실행되고 롤백되지 않으며, 트랜잭션 지원을 켜면 결과가 `null`이 되고 `EXEC`가 DB 커밋 뒤에 나가며 그 실패는 호출한 쪽에 전달되지 않습니다. 또 예외가 났다고 DB가 롤백된 것은 아니어서, 기본 규칙에서는 checked 예외면 커밋됩니다.

### 예상 질문과 꼬리 질문

**Q. DB만으로도 초과 판매를 막을 수 있는데 왜 Redis를 앞에 두나요?**
정확성 때문이 아니라 경합 때문입니다. 모든 요청이 재고 행 하나의 잠금을 기다리며 DB 커넥션을 붙잡으면 다른 API까지 느려집니다. Redis 예약을 앞에 두면 동시에 DB에 들어가는 주문이 대체로 재고 수 이하로 묶이고, 품절 뒤의 요청은 DB 커넥션 없이 돌아갑니다(왜 Redis에서 먼저 빼는가).

- **꼬리: 그럼 DB가 받는 요청은 재고 수만큼인가요?** 동시에는 대체로 그렇지만(Redis가 실제보다 많이 가졌거나 회수된 주문이 뒤늦게 오면 넘을 수 있습니다) 누적으로는 아닙니다. DB가 실패해 되돌린 재고는 다시 예약되어 DB로 오고, 헛걸음과 청소 작업의 쓰기도 더해집니다. 실제로 커넥션 대기가 얼마나 줄었는지는 측정해야 합니다.

- **꼬리: 그럼 Redis 예약을 넣었다고 초과 판매 테스트로 효과를 확인하면 되나요?** 아닙니다. DB 조건부 차감이 이미 초과 판매를 막으므로 그 지표는 Redis가 있든 없든 같습니다. 비교할 것은 DB 커넥션 대기, 잠금 대기 시간, 응답 지연입니다.

**Q. Redis를 원천으로 두면 DB 쓰기가 가벼워지는데 왜 안 하나요?**
Redis 복제는 비동기라 장애 조치 때 응답한 쓰기를 잃을 수 있습니다. 예약을 잃으면 재고가 되살아나 같은 물건을 또 팔게 되는데, DB에 재고가 없으면 아무도 막지 못합니다. DB가 원천이면 같은 상황이 헛걸음으로 끝납니다(원천은 DB에 둡니다).

- **꼬리: `WAIT`을 쓰면 Redis를 원천으로 둬도 되지 않나요?** `WAIT`은 잃는 경우를 줄일 뿐 강한 일관성을 주지 않는다고 공식 문서가 밝힙니다. 같은 연결로 보내고 반환값을 확인해야 하며, 복제본의 확인을 기다리는 만큼 예약이 느려지는 대가도 있습니다(Redis 장애 조치).

**Q. DB 저장이 실패하면 Redis 재고를 그냥 되돌리면 되지 않나요?**
실패의 종류를 나눠야 합니다. 커밋 전에 롤백된 것이 확실하면 되돌립니다. 커밋의 응답을 못 받았거나 `orders`의 기본 키 충돌이면 그 주문이 실제로 확정됐을 수 있어, 되돌리면 Redis가 실제보다 많아집니다. 이때는 취소 행을 먼저 넣어 판정합니다. DB가 재고 없음으로 거절했다면 Redis가 이미 많이 가진 것이라 되돌리면 안 됩니다(실패 지점마다 남는 상태가 다릅니다).

- **꼬리: 주문 ID로 조회해서 없으면 되돌리면 되지 않나요?** 조회는 그때까지 커밋된 행만 봅니다. 원래 트랜잭션이 아직 진행 중이면 조회 뒤에 커밋할 수 있어, "없음"으로는 판정할 수 없습니다. 취소 행을 넣으면 그 늦은 커밋이 기본 키 충돌로 거절되므로 판정이 확정됩니다.
- **꼬리: 예외가 났으면 롤백된 것 아닌가요?** Spring의 기본 규칙은 `RuntimeException`과 `Error`에만 롤백합니다. Kotlin에서 `Exception`을 직접 상속한 예외를 던지면 예외와 함께 커밋되므로, 모든 예외에 롤백하도록 설정하거나 `rollbackFor`를 지정합니다(Spring의 `@Transactional`).

- **꼬리: 되돌리기를 재시도하다 두 번 실행되면요?** 되돌리기는 예약을 지웠을 때만 재고를 늘리므로 두 번째 실행은 아무것도 하지 않습니다.
- **꼬리: DB에 닿지 못해 판정도 못 하면요?** 아무것도 하지 않고 "처리 중"으로 응답합니다. 예약이 남아 있으므로 청소 작업이 기한 뒤에 같은 판정을 대신 합니다.

**Q. 서버가 예약 뒤에 죽으면 재고는 어떻게 돌아오나요?**
예약에 기한을 두고, 청소 작업이 기한 지난 예약을 꺼내 처리합니다. DB에 그 주문의 취소 행을 먼저 넣고, 넣기에 성공하면 되돌리고, 충돌하면 기존 행의 상태에 따라 확정하거나 되돌립니다(앱이 죽으면).

- **꼬리: 왜 조회하지 않고 취소 행을 넣나요?** 서버가 죽은 것이 아니라 느렸을 뿐이면, 청소가 되돌린 뒤에 그 서버가 커밋할 수 있습니다. 취소 행이 먼저 있으면 그 늦은 커밋이 기본 키 충돌로 반드시 거절됩니다. 조회만 하면 그 사이를 막지 못합니다.
- **꼬리: 기한을 넉넉히 잡으면 그 문제가 없지 않나요?** GC 정지나 네트워크 지연은 기한 길이로 배제할 수 없어 확률만 줄어듭니다. 그리고 기한이 길수록 죽은 서버의 재고가 오래 묶입니다(예약 기한은 두 위험을 맞바꿉니다).

**Q. Redis 장애 조치가 나면 무엇이 틀어지나요?**
복제되기 전의 최근 쓰기를 잃습니다. 예약을 잃으면 Redis 재고가 실제보다 많아 누군가 헛걸음하고, 되돌리기를 잃으면 재고가 기한까지 묶이거나 새며, 확정을 잃으면 예약이 되살아나 청소가 다시 확정합니다. 끝까지 실행된 스크립트의 쓰기는 함께 남거나 함께 사라지므로, 장애 조치 때문에 차감만 남고 예약 기록이 없는 반쪽 상태가 생기지는 않습니다. 스크립트가 중간에 에러로 멈추면 앞의 쓰기가 남으므로 첫 쓰기 전에 인자를 검사합니다. 이 표는 소스에서 끌어낸 추론이며 재현하지 않았습니다(Redis 장애 조치).

- **꼬리: 그럼 어떻게 복구하나요?** 장애 조치 직후 DB 기준으로 대사합니다. "Redis 재고 = DB 재고 − DB에 확정 주문이 없는 예약"이 성립하는지 봅니다. 차이가 이어지면 그 상품의 새 예약을 막고, 진행 중 예약이 정리되고 정상 처리 시간 상한만큼 지난 뒤 한 작업이 다시 맞춥니다. 예약 기록을 잃은 주문은 `resv`에 없어도 뒤늦게 커밋할 수 있기 때문입니다. 되돌리기를 잃어 묶인 재고는 식에 나타나지 않고 청소 작업이 맡습니다.
- **꼬리: 왜 진행 중 예약을 전부 빼지 않나요?** DB 커밋은 끝났지만 확정 스크립트가 아직 안 간 예약은 DB 재고에 이미 반영됐으므로, 전부 빼면 그 주문을 두 번 셉니다.

**Q. 대사에서 차이가 보이면 Redis에 DB 값을 그대로 쓰면 되지 않나요?**
판매 중에는 Redis와 DB를 같은 순간에 읽을 수 없어 진행 중인 주문 때문에 차이가 보입니다. 그리고 `SET`으로 덮어쓰면 그 사이 다른 요청이 한 `DECR`을 지웁니다. 판매 중의 차이는 탐지 신호로 쓰고, 고치기는 그 상품의 새 예약을 막고, 진행 중 예약이 정리되고 정상 처리 시간 상한만큼 지난 뒤에 합니다(대사).

- **꼬리: 차이만큼 `INCRBY`하면 덮어쓰기 문제가 없지 않나요?** 다른 차감은 지우지 않지만, 대사 작업 두 개가 같은 부족분을 각자 더하거나 응답을 못 받은 보정을 다시 보내면 두 번 반영됩니다. 그래서 고치는 주체를 상품당 하나로 두고, 보정 결과를 모르면 다시 계산부터 합니다. 주체가 하나여도 판매 중에 계산한 차이는 진행 중인 주문 때문에 틀릴 수 있으므로, 차이는 멈춘 상태에서 계산합니다.

**Q. `@Transactional` 안에서 Redis와 DB를 함께 쓰면 함께 롤백되지 않나요?**
되지 않습니다. Spring Data Redis는 트랜잭션 매니저가 없고, `@Transactional`은 DB 트랜잭션만 관리합니다. 기본 설정에서 Redis 명령은 바로 실행되고 DB가 롤백돼도 남습니다(Spring의 `@Transactional`).

- **꼬리: `enableTransactionSupport`를 켜면요?** Redis 쓰기가 `MULTI` 대기열에 쌓였다가 DB 커밋 뒤 `EXEC`로 나갑니다. 함께 커밋되는 것이 아니라 순서가 "DB 먼저"로 바뀌는 것입니다. 쓰기의 결과가 `null`이라 예약 성공 여부도 알 수 없고, `EXEC`가 실패하면 Spring이 로그만 남겨 호출한 쪽은 성공으로 압니다. 클러스터 연결이면 `MULTI`를 지원하지 않아 처음 쓰기에서 예외가 납니다.
- **꼬리: 커밋 중에 DB 연결이 끊기면 그 설정에서는 어떻게 되나요?** Spring이 완료 상태를 "알 수 없음"으로 알리고 Spring Data Redis는 `DISCARD`를 보냅니다. DB가 실제로 커밋했다면 Redis 쓰기만 버려집니다.

**Q. 남은 재고 표시처럼 Redis를 DB의 사본으로만 쓸 때는요?**
DB를 먼저 커밋하고, 같은 트랜잭션에 아웃박스 행을 남겨 별도 과정이 Redis에 반영합니다. 반영이 두 번 갈 수 있으므로 `DECR`보다 DB 값을 버전과 함께 `SET`하는 편이 멱등합니다. 늦게 반영되므로 문으로 쓰면 안 됩니다(순서를 바꾸면).

**Q. 2PC로 두 저장소를 한 번에 커밋하면 되지 않나요?**
Redis에는 2PC에 참여할 준비 상태가 없습니다. `MULTI` 대기열은 연결에 붙은 임시 상태라 연결이 끊기면 버려지고, 장애 뒤에도 남아 결정을 기다리는 상태가 아닙니다. 지원하는 저장소끼리라도 준비부터 결정까지 데이터를 붙잡아 경합이 큰 재고 행에서 처리량을 깎고, 조정자가 결정을 알리기 전에 죽으면 결정을 모르는 참여자는 기다리게 됩니다. 타임딜처럼 경합을 줄이려고 Redis를 둔 곳과는 목적이 반대입니다([두 저장소에 나눠 쓰기](../cs/dual-write.md)).

**Q. 무엇을 보면 불일치를 알 수 있나요?**
"DB 재고 없음으로 지움" 횟수(Redis가 많음), 대사 차이(부호로 방향), 기한을 넘긴 예약(청소가 멈췄거나 밀림), 판매 종료 때 DB에 남은 재고(재고가 샘), 장애 조치와 Redis 재시작 시각을 함께 봅니다. 지표 하나가 원인 하나를 가리키지는 않으므로, 함께 나타난 지표로 원인을 좁힙니다(실무 포인트의 "관찰할 것").

# Redis를 백엔드 관점에서 이해하기

백엔드 개발자를 위한 Redis 학습 저장소다. 설명은 한국어로 작성하며, CS 배경지식을 알고 있다는 전제로 시작하지 않는다.

목표는 Redis 명령어나 소스 코드를 많이 외우는 것이 아니다.

> 필요한 배경지식부터 시작해 “왜 이렇게 동작하는가, 어떤 대가가 있는가, 내 서비스에서는 무엇을 판단해야 하는가”를 설명할 수 있게 된다.

CS를 전부 공부한 뒤 Redis를 시작하는 방식이 아니다. **Redis에서 생긴 질문을 해결하는 데 필요한 CS를 배우고, 다른 주제에서도 다시 활용하는 방식**이다.

문서 구조, 설명 깊이, 근거, 코드 예제 같은 문서 작성 규칙은 [AGENTS.md](./AGENTS.md)에만 둔다.

## 기준 버전

학습의 기준 계열은 **Redis 8.2**다. 각 문서가 실제로 확인한 정확한 태그·커밋과 Spring Data Redis 같은 라이브러리 버전은 그 문서의 `근거` 절에 있다. 문서마다 확인한 시점이 달라 패치 버전이 다를 수 있으므로, 여기에는 계열만 적는다.

## 문서를 읽고 질문하는 방법

질문은 구현 이름보다 현상이나 판단에서 출발해도 좋다. 예를 들어 “데이터가 늘었는데 특정 쓰기가 갑자기 느려진 이유는?”, “메모리 지표가 서로 다른 값을 가리키는데 무엇부터 확인해야 하나?”, “이 서비스 요구사항에서 어떤 자료형과 키 구성을 선택해야 하나?”처럼 묻는다.

설명이 어려우면 이해가 끊긴 문장을 지정해 질문한다.

실행 예제가 필요할 때는 명시적으로 요청한다.

## 필요할 때 확장할 주제

아래는 필수 선행 순서나 완료 목록이 아니라 질문이 생겼을 때 문서를 확장할 방향의 예시다. 다음에 볼 주제는 이 표에 없더라도 에이전트가 제안한다.

| 영역 | 중심 질문의 예 |
| --- | --- |
| 키와 수명 설계 | 데이터를 어떤 단위로 나누며, TTL과 eviction을 어떻게 판단할 것인가? |
| 자료형과 Encoding | 논리 자료형과 내부 저장 방식은 어떻게 다르며, 구조 선택의 대가는 무엇인가? |
| 메모리 | 데이터 자체의 크기와 메모리 지표를 어떻게 구분해서 이해할 것인가? |
| 성능과 명령 처리 | 명령 실행 비용, 요청 대기, 클라이언트가 본 지연을 어떻게 나누어 볼 것인가? |
| Big Key와 Hot Key | 어떤 증상을 관찰하고, 어떤 대응의 부작용을 검토해야 하는가? |
| 원자성·재시도·배치 | 여러 동작의 정확성과 처리 효율을 어떻게 함께 설계할 것인가? |
| 영속성·복제·장애 | 어떤 실패를 가정하고, 데이터 손실과 복구를 어떻게 판단할 것인가? |
| Spring 연동 | 직렬화·접근 방식·연결 설정이 Redis 사용 방식과 어떻게 연결되는가? |

## 학습의 완료 기준

한 주제를 공부한 뒤 이름과 정의만 기억하는 것으로 끝내지 않는다. 다음을 자신의 말로 설명할 수 있는지가 기준이다.

**왜 필요한가 → 어떻게 동작하는가 → 대안과 비교해 무엇을 얻고 잃는가 → 조건이 달라지면 무엇이 문제인가 → 서비스에서는 무엇을 선택하고 확인할 것인가.**

이 판단에 필요한 지식은 필수로 다룬다. 구조체 배치나 정확한 함수 구현처럼 더 깊은 내용은 관심과 질문에 따라 확장하되, 어려운 내용이라는 이유로 답을 회피하지 않는다.

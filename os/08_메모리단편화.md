# 메모리 단편화

> 필요한 주제: **3 Object / Encoding, 4 ZSET (지금)**.

## 1. 한 줄 요약

빈 공간을 합치면 충분한데, **조각조각 흩어져 있어서** OS에 돌려주지도 못하고 큰 덩어리로 쓰지도 못하는 상태입니다.

## 2. 그림

할당자는 OS에서 **페이지(4KB) 단위**로 받아 옵니다. OS에 돌려줄 때도 페이지 단위입니다.

```
처음: 페이지 하나에 같은 크기 객체가 꽉 참
 [A][B][C][D][E][F][G][H]            ← 4KB, RSS에 포함

키를 하나 건너 하나씩 지움
 [A][ ][C][ ][E][ ][G][ ]            ← 절반이 비었지만
                                       살아 있는 객체가 하나라도 있으면
                                       이 페이지는 통째로 OS에 못 돌려줌

→ used_memory는 절반으로 줄고, RSS는 그대로
```

Java에서는 이런 일이 덜합니다. GC가 살아 있는 객체를 한쪽으로 **옮겨서 모으기(compaction)** 때문입니다. C에서는 여기저기서 포인터가 주소를 직접 들고 있어서, 할당자가 객체를 마음대로 옮길 수 없습니다.

## 3. Redis에서 언제 생기나

- 크기가 제각각인 값을 대량으로 쓰고 지우기를 반복할 때 (TTL로 키가 대량 만료되는 경우 포함)
- 큰 키를 지운 뒤
- 값이 커졌다 작아졌다 할 때 (`APPEND`, 리스트가 늘었다 줄었다)
- 인코딩 전환: listpack(한 덩어리) → skiplist/dict(작은 조각 수백 개, [06](06_메모리할당자_jemalloc.md) 3절)

## 4. Redis의 대응: activedefrag

Redis가 **직접 객체를 새 자리로 복사하고 포인터를 고쳐 주는** 기능입니다. jemalloc에 "이 할당이 듬성듬성한 페이지에 있나?"를 물어보고, 그렇다면 옮깁니다. GC의 compaction을 Redis가 대신 하는 셈입니다.

- 설정 `activedefrag` (기본 off), `active-defrag-cycle-min` / `max` (CPU를 몇 %까지 쓸지) 등
- **CPU를 쓰므로 latency와 맞바꾸는 것**입니다. 메인 스레드에서 조금씩 돌기 때문입니다.
- 소스: `defrag.c:2147` `activeDefragCycle`, `config.c:3478`

## 5. 직접 확인 (단편화 만들기)

100만 키를 넣은 뒤 **하나 건너 하나씩** 지웁니다. `DEBUG POPULATE`는 `key:0`, `key:1`, ... 이름으로 만듭니다.

```bash
docker exec redis-os redis-cli DEBUG POPULATE 1000000
```

```bash
docker exec redis-os redis-cli EVAL "for i=0,999999,2 do redis.call('DEL','key:'..i) end" 0
```

각 단계마다 확인합니다.

```bash
docker exec redis-os redis-cli INFO memory | grep -E "^(used_memory|used_memory_rss|mem_fragmentation_ratio|allocator_frag_ratio):"
```

실제 결과:

| 상태 | used_memory | used_memory_rss | mem_frag_ratio | allocator_frag_ratio |
|---|---|---|---|---|
| 100만 키 | 81.5 MB | 100.5 MB | 1.23 | 1.07 |
| **절반 삭제 후** | **45.6 MB** | **100.4 MB** | **2.21** | **1.92** |
| FLUSHALL 후 | 1.2 MB | 20.8 MB | 17.36 | 5.56 |

- 절반을 지웠더니 `used_memory`는 거의 반으로 줄었는데 **RSS는 그대로**입니다. 2절 그림 그대로입니다.
- `FLUSHALL`로 전부 지우면 페이지가 통째로 비므로 RSS가 돌아옵니다(빈 상태의 비율은 의미 없음, [07](07_RSS와_used_memory.md) 4절).
- 덤: 위 `EVAL`은 50만 번 DEL하는 동안 메인 스레드를 혼자 씁니다. 주제 5(Lua)에서 다시 나올 "긴 스크립트는 p99를 올린다"의 예이기도 합니다.

## 6. 주제 3·4 실험과 연결

ZSET 인코딩 전환이나 DEL/UNLINK 실험을 반복하면 단편화가 쌓여서 **뒤에 한 실험일수록 RSS 숫자가 부풀 수 있습니다.** 실험 조건을 맞추려면 매 실험 전에 컨테이너를 새로 띄우거나 `FLUSHALL`을 하고 시작하세요.

## 7. 여기서 멈춤

- **설명할 수 있으면 충분:** 단편화가 왜 생기는지, 왜 RSS가 안 줄어드는지, GC 언어와 무엇이 다른지, activedefrag는 CPU와 맞바꾸는 것이라는 것.
- **몰라도 됨:** jemalloc의 extent/slab 재사용 정책, defrag가 어떤 순서로 객체를 옮기는지.

# 시스템 콜과 유저/커널 모드

> 필요한 주제: 1 Event Loop. 03~05 문서의 바탕입니다.

## 1. 한 줄 요약

프로그램은 디스크나 네트워크 카드를 직접 만질 수 없고, **커널에 부탁**해야 합니다. 이 부탁이 시스템 콜입니다. `read`, `write`, `accept`, `epoll_wait`, `fork`, `fsync`가 모두 시스템 콜입니다.

## 2. 그림

```
 유저 공간 (Redis 코드)                    커널 공간
 ─────────────────────                    ─────────────────────────
 connSocketRead()
   read(24, buf, 16KB)  ──── 모드 전환 ───▶ 소켓 24의 수신 버퍼 확인
                                            있으면 buf로 복사
   ret = 27             ◀─── 모드 전환 ──── 복사한 바이트 수 반환
 processInputBuffer()
   (명령 파싱, dict에 SET)                  ← 여기는 시스템 콜 없음.
                                              유저 공간 메모리 안에서 끝남
   write(24, "+OK\r\n") ──── 모드 전환 ───▶ 소켓 24의 송신 버퍼에 복사
```

## 3. 왜 비싼가, 그래서 Redis는 어떻게 하나

시스템 콜 한 번에 드는 일은 이렇습니다: CPU 모드 전환, 커널 쪽 검사, 유저 버퍼 ↔ 커널 버퍼 복사. 일반 함수 호출보다 훨씬 비쌉니다. 그래서 Redis는 **시스템 콜 횟수를 줄이는 방향**으로 짜여 있습니다.

| 설계 | 효과 | 어디 |
|---|---|---|
| 응답을 바로 `write`하지 않고 클라이언트 버퍼에 모았다가 `beforeSleep`에서 한 번에 | 명령마다 write하지 않음 | `server.c:2117` `handleClientsWithPendingWrites` ([04_server_흐름지도.md](../04_server_흐름지도.md)) |
| `writev`로 여러 버퍼를 한 번에 | 응답 조각 N개를 시스템 콜 1번에 | `socket.c:151` |
| 16KB씩 크게 `read` | 파이프라인 명령 여러 개를 read 1번에 | `server.h:207` `PROTO_IOBUF_LEN` |

"Redis가 싱글 스레드인데 빠른 이유" 중 하나가 여기 있습니다. 명령 처리 자체는 메모리 안에서 끝나고(시스템 콜 0번), 커널에 가는 건 네트워크 I/O뿐이며, 그것도 모아서 갑니다.

**블로킹**도 시스템 콜에서 생깁니다. `read`, `fsync` 같은 시스템 콜이 "기다리는" 동안 그 스레드는 아무것도 못 합니다([04](04_blocking_nonblocking.md), [13](13_write와_fsync.md)).

## 4. Redis 소스에서 어디에 나오나

Redis가 커널을 부르는 실제 지점은 몇 군데 안 됩니다.

| 위치 | 시스템 콜 |
|---|---|
| `socket.c:166` `connSocketRead` | `read` 한 줄을 감싼 함수 |
| `socket.c:136` `connSocketWrite` | `write` |
| `socket.c:151` `connSocketWritev` | `writev` |
| `ae_epoll.c:93` `aeApiPoll` | `epoll_wait` |
| `anet.c:615` | `accept4` |

## 5. 직접 확인

[README.md](README.md)의 strace 명령을 띄우고 다른 터미널에서 `SET k v`를 보냈을 때의 실제 결과입니다.

```
epoll_pwait(7, [{events=EPOLLIN, data=0x12}], 10128, 100, NULL, 8) = 1   ← 새 연결 왔음
accept4(18, {... 127.0.0.1 ...}, ..., SOCK_CLOEXEC|SOCK_NONBLOCK) = 24
accept4(18, ...) = -1 EAGAIN (Resource temporarily unavailable)
epoll_pwait(7, [{events=EPOLLIN, data=0x18}], 10128, 61, NULL, 8) = 1    ← 24번에 데이터 왔음
read(24, "*3\r\n$3\r\nSET\r\n$1\r\nk\r\n$1\r\nv\r\n", 20474) = 27
write(24, "+OK\r\n", 5)                 = 5
epoll_pwait(7, [{events=EPOLLIN, data=0x18}], 10128, 61, NULL, 8) = 1
read(24, "", 20474)                     = 0                              ← 클라이언트가 연결 끊음
```

`read`와 `write` 사이에 시스템 콜이 하나도 없습니다. SET 명령의 실제 처리(dict에 넣기)는 전부 유저 공간에서 끝났다는 뜻입니다.

각 줄의 의미는 03(`accept4`), 04(`EAGAIN`), 05(`epoll_pwait`), 14(`read = 0`) 문서에서 하나씩 설명합니다.

## 6. 여기서 멈춤

- **설명할 수 있으면 충분:** 시스템 콜이 무엇이고 왜 비싼지, Redis가 응답을 왜 모아서 보내는지.
- **몰라도 됨:** 인터럽트, `syscall` 명령어, 커널 스택, vDSO, 링(ring) 레벨.

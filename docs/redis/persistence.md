# Redis 영속성: 장애가 나면 무엇이 남는가

> **핵심 질문**: Redis는 데이터를 메모리에 두는데, 프로세스가 죽거나 서버 전원이 꺼지면 무엇이 남는가? RDB와 AOF는 각각 어떤 장애에서 얼마만큼을 잃게 하며, 무엇을 대가로 치르는가? 디스크 쓰기가 실패하거나, 파일이 깨지거나, 설정을 잘못 바꾸면 Redis는 어떻게 행동하는가? 사람이 실수로 지운 데이터는 되살릴 수 있는가?
>
> **범위**: 단일 Redis 서버의 RDB와 AOF를 다룹니다. 운영체제 동작은 Linux를 기준으로 합니다. 복제와 장애 조치는 영속성 설정과 맞물려 데이터가 사라지는 경우까지만 다루고, Sentinel·Cluster의 장애 조치 절차와 백업 자동화는 다루지 않습니다. "AOF가 응답 전에 `write`한다"는 설명은 `io-threads` 기본값(1)을 기준으로 합니다. "`everysec`에서 디스크가 느리면" 절과 I/O 스레드를 켰을 때의 프로세스 장애 손실은 소스를 읽은 해석이며, 장애를 재현해 확인하지는 않았습니다.

## 배경 지식

### 이 문서의 예시: 재고 10개, 주문 3건, 그리고 장애

[Redis 원자성](./atomicity.md)의 재고 키를 이어서 씁니다. 문서 끝까지 다음 장면 하나를 씁니다.

| 시각(가상) | 일어난 일 | Redis 메모리의 `stock:item:1` |
| --- | --- | --- |
| 10:00:00.0 | RDB 스냅숏 저장이 끝남. `dump.rdb`에는 `10` | 10 |
| 10:00:01.2 | 주문 A: `DECR` → 9, 주문 API가 응답을 받고 사용자에게 "주문 완료" | 9 |
| 10:00:01.7 | 주문 B: `DECR` → 8, "주문 완료" | 8 |
| 10:00:02.4 | 주문 C: `DECR` → 7, "주문 완료" | 7 |
| 10:00:02.6 | **장애** | ? |

- 주문 A, B, C는 모두 Redis의 응답을 받았고, 주문 DB에도 기록됐다고 합시다.
- **Redis를 다시 시작하면 `stock:item:1`은 얼마인가?** 답은 영속성 설정과 장애의 종류에 따라 "키 없음", 10, 8, 7로 갈립니다. 
- AOF를 켠 경우의 계산에는 시각 하나를 더 정합니다. AOF의 마지막 `fsync`가 10:00:02.0에 끝났고, 그 `fsync`가 주문 A와 B의 기록까지 저장 장치에 내렸다고 합시다. 주문 C의 기록은 장애 순간까지 운영체제 메모리에만 있었고 저장 장치에는 내려가지 않았다고 합니다. 운영체제의 자체 내려 쓰기(writeback)는 Redis의 `fsync` 호출 없이도 일어나며, Redis가 관리하는 다음 `fsync` 실행 간격을 다시 시작시키지 않습니다. 이 때문에 실제로는 C가 남아 있을 수도 있지만, 예시에서는 아직 내려가지 않았다고 가정합니다. 이 두 가정은 `appendfsync everysec`의 정상 경로를 계산할 때 씁니다. 응답 전에 `fsync`하는 `always`나, `write`가 미뤄지거나 실패해 C가 Redis 프로세스 메모리에만 있는 경우는 해당 절에서 따로 다룹니다.

```text
 Redis process                      OS                   Storage
+--------------------------+       +------------+       +----------------------+
| Memory: stock:item:1 = 7 |       | Page cache |       | dump.rdb (10)        |
| AOF buffer: C's DECR     | ----> | C's DECR   | ----> | appendonlydir/       |
| (before write)           |  (1)  |            |  (2)  |   ...incr.aof (A, B) |
+--------------------------+       +------------+       +----------------------+
(1) write    (2) fsync (or OS writeback)
```

화살표는 데이터가 복사되어 이동하는 방향입니다. 상자 크기는 실제 크기와 무관합니다.  
`dump.rdb`와 `appendonlydir`는 각각 `dbfilename`, `appenddirname` 설정의 기본값이며, 이 문서는 기본 이름으로 부릅니다.  
이 그림은 AOF를 켠 경우이며, AOF를 끄면 가운데 경로가 없고 `dump.rdb`만 남습니다.  
복제본은 그림에서 뺐습니다. "복제와 영속성이 맞물리면 데이터가 통째로 사라질 수 있습니다"에서 다룹니다.

### 디스크에 '썼다'와 '남았다'는 다릅니다

- **한 줄**: 파일에 `write`하면 데이터는 운영체제 메모리(페이지 캐시)에 들어가고, `fsync`를 해야 저장 장치에 기록됐다고 확신할 수 있습니다. 그래서 프로세스만 죽으면 `write`한 데이터는 남지만, 운영체제가 멈추거나 정전이 나면 `fsync`가 끝난 데이터만 확실히 남습니다. 저장 장치나 서버를 잃으면 다른 곳의 사본만 남습니다. 원리는 [파일 쓰기와 내구성](../cs/file-write-durability.md)에서 다룹니다.
- **이 주제에서는**: 그림의 (1)은 `write`, (2)는 운영체제 메모리에서 저장 장치로 내려 쓰는 과정입니다. AOF의 `appendfsync` 설정은 Redis가 `fsync`로 (2)의 완료를 언제 요청하고 기다릴지를 고르는 것이고, 이 선택이 "운영체제·전원 장애 때 무엇을 잃는가"를 정합니다. 이 문서는 장애를 다음 네 가지로 나눠 따라갑니다.
  - **정상 종료**: `SHUTDOWN` 명령이나 종료 신호(`SIGTERM`)로 Redis가 스스로 정리하고 끝나는 경우
  - **프로세스 장애**: `kill -9`, Redis 버그로 인한 비정상 종료, 운영체제가 메모리 부족으로 Redis를 강제 종료(OOM killer)
  - **운영체제·전원 장애**: 커널 패닉, 정전, 가상 머신 강제 종료
  - **저장 장치·서버 소실**: 디스크 고장, 로컬 디스크와 함께 인스턴스가 사라짐

### fork와 copy-on-write

- **한 줄**: 운영체제는 메모리를 페이지라는 고정 크기 단위로 나눠 관리하고, 프로세스마다 "내 주소의 어느 페이지가 실제 메모리의 어디에 있는지"를 적은 표(페이지 테이블)를 둡니다. `fork`는 프로세스를 복제해 자식 프로세스를 만들고, 자식은 `fork` 순간의 메모리를 봅니다. Linux는 데이터를 바로 복사하지 않고 페이지 테이블을 복사해 부모와 자식이 같은 페이지를 함께 가리키게 한 뒤, 부모나 자식이 어떤 페이지에 처음 쓸 때 그 페이지만 복사합니다(copy-on-write). 복사 단위가 키가 아니라 페이지이므로, 작은 키 하나를 바꿔도 그 키가 든 페이지 전체가 복사되고, 바꾸는 키가 여러 페이지에 흩어져 있을수록 복사량이 커집니다. 대가는 메모리가 클수록 길어지는 `fork` 시간, 자식이 사는 동안 바뀐 페이지만큼 늘어나는 메모리, 그리고 커널의 메모리 약속 정책(overcommit)에 따른 `fork` 실패나 강제 종료입니다. 원리는 [fork와 copy-on-write](../cs/fork-and-copy-on-write.md)에서 다룹니다.
- **이 주제에서는**: Redis는 RDB 스냅숏과 AOF 다시 쓰기를 자식 프로세스에 맡깁니다. 메인 스레드는 `fork`가 끝나자마자 명령 처리로 돌아가고, 자식은 `fork` 순간의 데이터를 파일로 씁니다. 그래서 RDB 파일에 담기는 것은 저장이 **끝난** 시점이 아니라 `fork`한 시점의 데이터입니다. Redis 프로세스에는 다른 스레드도 있는데 이 사본이 왜 명령의 중간 상태가 아니고, 자식이 왜 잠금에 걸려 멈추지 않는지는 [Redis의 fork와 스레드](./fork-and-threads.md)에서 다룹니다.

### 이 문서에 나오는 실행 단위

영속성에는 Redis의 여러 실행 단위가 등장하므로 구분해 둡니다. 프로세스와 스레드의 일반 원리는 [프로세스와 스레드](../cs/process-and-thread.md)에서 다룹니다.

| 실행 단위 | 영속성에서 하는 일 |
| --- | --- |
| 메인 스레드 | 명령을 실행하고, 실행한 쓰기 명령을 AOF 버퍼에 덧붙이고, AOF 버퍼를 파일에 `write`합니다. `io-threads` 기본값(1)에서는 응답도 메인 스레드가 `write` 뒤에 보냅니다. `appendfsync always`면 `fsync`도 여기서 합니다. `fork`도 메인 스레드가 부릅니다 |
| I/O 스레드 | `io-threads`를 2 이상으로 켰을 때만 있습니다. 소켓 읽기·쓰기를 맡고 명령은 실행하지 않습니다. 응답을 보내는 시점이 AOF `write`보다 앞설 수 있어, "명령 하나가 디스크에 닿기까지"에서 다시 다룹니다 |
| 백그라운드 스레드 | `appendfsync everysec`일 때 `fsync`를 대신 부릅니다 |
| 자식 프로세스 | RDB 파일과 AOF의 새 기준 파일을 씁니다. 메인 스레드와 주소 공간이 따로이고, 물리 메모리는 copy-on-write로 어느 쪽이든 쓰기 전까지만 공유합니다 |

메인 스레드는 "요청이 도착한 연결을 골라 명령을 실행하고, 응답을 보내기 전에 정리 작업을 하고, 응답을 보내고, 다시 기다리는" 일을 되풀이합니다. 이 반복을 **이벤트 루프**라고 합니다. `io-threads` 기본값에서는 AOF의 `write`가 응답 직전의 정리 작업, 즉 응답보다 앞에서 일어난다는 점이 뒤에서 중요해집니다.

## 영속성을 끄면 다시 시작한 Redis는 비어 있습니다

Redis의 데이터는 메모리에만 있습니다. 영속성은 그 데이터를 디스크에 남겨, 프로세스가 다시 시작될 때 읽어 들이게 하는 기능입니다. 방식은 두 가지입니다(공식 문서 persistence).

- **RDB**: 정해 둔 조건이 되면 그 시점의 데이터 전체를 파일 하나로 떠 둡니다.
- **AOF**: 실행한 쓰기 명령을 파일 끝에 계속 덧붙여 두었다가, 다시 시작할 때 차례로 다시 실행합니다.

기본값은 **RDB 켬, AOF 끔**입니다. `save` 설정을 따로 두지 않으면 "3600초 동안 1번 이상 변경, 300초 동안 100번 이상 변경, 60초 동안 10,000번 이상 변경" 중 하나를 만족할 때 RDB를 저장합니다. 배포되는 `redis.conf`에도 `save` 줄은 주석으로만 있어 이 기본값이 적용됩니다. `save ""`로 RDB 자동 저장을 끄고 AOF도 끄면 새 변경은 디스크에 남지 않습니다. 다만 `save ""`는 저장만 멈출 뿐 읽기는 막지 않습니다. AOF가 꺼져 있으면 Redis는 저장 조건과 상관없이 시작할 때 `dump.rdb`를 읽으므로, 예전에 남은 파일이 있으면 그 시점의 데이터로 돌아갑니다.

처음부터 영속성 없이 운영해 읽을 `dump.rdb`도 없다면 예시의 답은 "키 없음"입니다(예시 표의 10:00:00 RDB 저장은 없던 일로 봅니다). 이후 "영속성 끔"은 이 경우를 가리킵니다. 다시 시작한 Redis는 비어 있습니다. 이때 주문 API가 `DECR`을 보내면, `DECR`은 키가 없을 때 0에서 시작하므로 -1이 되고 "품절"로 판단됩니다. Redis 원자성 문서의 "DECR의 반환값으로 판단하기"에서 본 함정이 그대로 나타납니다.

Redis를 순수한 캐시로만 쓴다면(원본은 DB에 있고, 비면 다시 채움) 이것으로 충분할 수 있습니다. 다만 재시작 직후 모든 요청이 캐시를 놓쳐 DB로 몰립니다. 반면 재고, 세션, 작업 큐, 분산 락처럼 **Redis에만 있는 상태**라면 재시작 한 번에 그 상태가 사라집니다. 영속성 설정을 고르기 전에, 그 데이터의 원본이 어디인지부터 정해야 합니다.

## RDB는 정해 둔 조건마다 메모리 전체를 한 시점으로 떠 둡니다

### 언제 저장하는가

메인 스레드는 주기적으로 도는 작업에서 저장 조건을 확인합니다. 조건은 "마지막 저장 뒤 바뀐 횟수가 M 이상이고, 마지막 저장에서 N초가 지났는가"입니다. 이 밖에 다음 경우에도 저장합니다.

- `BGSAVE` 명령: 자식 프로세스에 저장을 맡깁니다. RDB를 쓰는 자식이 이미 있으면 오류를 돌려줍니다. 다른 종류의 자식(예: AOF 다시 쓰기)이 일하고 있으면 거부하고, `BGSAVE SCHEDULE`이면 예약합니다.
- `SAVE` 명령: 메인 스레드가 직접 저장합니다. 저장이 끝날 때까지 다른 모든 명령이 기다립니다.
- 정상 종료: "종료 방식에 따라 남는 것이 다릅니다"에서 다룹니다.
- 복제본이 전체 동기화를 요청할 때: 데이터 전체를 보내기 위해 필요하면 `fork`합니다. 이미 진행 중인 복제용 저장이 있으면 거기에 붙거나 다음 저장을 기다리고, 디스크를 거치지 않고 소켓으로 보내는 방식이면 다른 복제본을 함께 모으려고 잠시 늦추기도 합니다.

**기본 저장 조건에서 쓰기가 드물면 한 시간 분량을 잃을 수 있습니다.** 예시처럼 10:00:00 이후 바뀐 횟수가 3번뿐이면, 300초 조건(100번)과 60초 조건(10,000번)은 만족하지 않고 3600초 조건(1번)만 남습니다. 다음 저장은 11:00:00이 지나서입니다. 그 전에 장애가 나면 한 시간 동안의 변경을 모두 잃습니다. 쓰기가 많을 때보다 적을 때 잃는 시간이 길어진다는 점이 직관과 반대입니다.

### 어떻게 저장하는가: fork한 자식이 임시 파일에 쓰고 이름을 바꿉니다

1. 메인 스레드가 `fork`합니다. `fork`가 끝나면 메인 스레드는 바로 명령 처리로 돌아갑니다.
2. 자식은 `fork` 순간의 데이터를 `temp-<자식 pid>.rdb`라는 임시 파일에 씁니다.
3. 다 쓰면 `fsync`로 저장 장치에 내립니다.
4. `rename`으로 임시 파일을 `dump.rdb`로 바꿔 기존 파일을 원자적으로 교체하고, 디렉터리도 `fsync`합니다. 파일 시스템은 파일 내용과 "이 디렉터리에 이 이름의 파일이 있다"는 항목을 따로 기록하므로, 이름 교체가 저장 장치에 남으려면 디렉터리도 `fsync`해야 합니다.
5. 자식이 끝나면 메인 스레드가 결과를 받아 "마지막 저장 시각"과 성공 여부를 기록합니다.

이 순서는 [파일 쓰기와 내구성](../cs/file-write-durability.md)의 "통째로 교체할 때는 임시 파일에 쓰고 이름을 바꿉니다"와 같습니다. 이 순서가 노리는 것은 **저장 도중에 장애가 나도 `dump.rdb`가 반쯤 쓰인 파일이 되지 않는 것**입니다. 다만 두 가지 원자성을 구분해야 합니다. `rename`이 보장하는 것은 실행 중에 다른 프로세스가 보는 순간의 원자성입니다. 전원 장애가 `rename` 도중에 났을 때도 이름이 옛 파일이나 새 파일 중 하나를 가리키는지는 장애 후 복구의 성질이고, 파일 시스템이 보장해야 성립합니다. 이 문서에서는 이 성질을 검증하지 않았습니다. 그 전제 아래에서, `rename` 전에 멈추면 직전에 성공한 스냅숏 그대로이고 임시 파일 찌꺼기가 남습니다. 프로세스만 죽었다면 `rename`이 끝난 뒤에는 새 스냅숏입니다. 전원 장애라면 이름 교체가 저장 장치에 남았다고 확신할 수 있는 것은 디렉터리 `fsync`까지 끝난 뒤이고, `rename`과 디렉터리 `fsync` 사이에 멈췄다면 옛 스냅숏이나 새 스냅숏 중 하나입니다. 공식 문서가 Redis가 돌고 있는 중에도 `dump.rdb`를 복사해 백업해도 안전하다고 설명하는 것은 앞의 성질, 즉 실행 중에는 완성된 파일만 보인다는 점 덕분입니다(persistence "Backing up Redis data").

### 무엇을 잃는가

RDB만 쓰면 **마지막으로 성공한 스냅숏의 `fork` 시점 이후의 모든 변경**을 잃습니다. 예시에서는 프로세스 장애든 정전이든 `dump.rdb`의 `10`으로 돌아갑니다. `dump.rdb`는 저장할 때 `fsync`한 파일이므로 정전에도 남습니다(저장 장치가 `fsync` 완료를 지킨다는 전제. "디스크에 '썼다'와 '남았다'는 다릅니다" 참고). 주문 3건이 되살아난 재고가 됩니다.

### 대가: fork, 복사되는 메모리, 매번 전체 쓰기

- **`fork` 동안 모든 명령이 멈춥니다.** `fork`는 메인 스레드가 부르고, 페이지 테이블을 복사하므로 Redis가 쓰는 메모리가 클수록 대체로 길어집니다. 실제 값은 커널과 가상화 환경에 따라 다르므로 운영 환경에서 잽니다. 마지막 `fork`에 걸린 시간은 `INFO stats`의 `latest_fork_usec`(마이크로초)로 봅니다.
- **자식이 사는 동안 메모리가 늘어납니다.** 그동안 메인 스레드가 처리한 쓰기가 페이지를 복사시킵니다. 마지막 저장에서 복사된 양은 `rdb_last_cow_size`(바이트)로 봅니다. 쓰기가 많고 흩어져 있으면 최악의 경우 복사된 페이지가 데이터 전체에 가까워져 메모리가 두 배 가까이 될 수 있습니다. 페이지 테이블 같은 그 밖의 메모리는 환경에 따라 더해집니다.
- **바뀐 양과 상관없이 매번 전체를 씁니다.** 키 하나만 바뀌어도 데이터 전체를 새로 씁니다. 저장할 때마다 데이터 전체를 다시 직렬화해 RDB 파일 크기만큼 쓰고, 그동안 디스크와 CPU를 씁니다. 파일 크기는 메모리 사용량과 같지 않고 값의 인코딩과 압축(`rdbcompression` 기본값 `yes`)에 따라 달라집니다.

### 파일이 없으면 빈 상태로, 깨져 있으면 시작하지 않습니다

다시 시작할 때 `dump.rdb`가 없으면 Redis는 빈 상태로 시작합니다. 반대로 파일이 있는데 읽다가 손상을 발견하면 시작하지 않고 끝납니다. RDB 파일 끝에는 검증용 체크섬(CRC64)이 있고, 읽은 내용과 맞지 않으면 "Wrong RDB checksum" 오류를 냅니다(`rdbchecksum` 기본값 `yes`). 깨진 데이터로 조용히 시작하는 것보다, 멈춰서 사람이 보게 하는 쪽을 택한 것입니다.

## AOF는 실행한 쓰기를 로그로 덧붙이고, fsync 정책이 잃는 범위를 정합니다

### 명령 하나가 디스크에 닿기까지

주문 C의 `DECR`을 따라갑니다.

1. 메인 스레드가 `DECR`을 실행해 메모리의 값을 7로 바꿉니다.
2. 실행한 쓰기 명령을 Redis 프로토콜 형식 그대로 AOF 버퍼에 덧붙입니다. AOF 버퍼는 Redis 프로세스의 메모리입니다.
3. 이벤트 루프 한 바퀴의 처리가 끝나고 응답을 보내기 직전의 정리 작업에서 AOF 버퍼를 파일에 `write`합니다. AOF는 응답을 보내기 전에 써야 하므로, 쓰기를 메모리에 모아 두었다가 이 자리에서 한꺼번에 씁니다.
4. 그다음 응답을 보냅니다. 주문 API는 이때 7을 받습니다.
5. `fsync`는 `appendfsync` 설정에 따라 다른 때에 일어납니다.

3번과 4번의 순서 덕분에, `io-threads` 기본값(1)에서는 **응답을 받은 쓰기가 보통 이미 `write`가 끝나 페이지 캐시에 있습니다.** 그래서 Redis 프로세스만 죽는 장애에서는 응답한 쓰기를 잃지 않습니다. `redis.conf`도 AOF를 쓰면 "Redis 프로세스에 문제가 생기고 운영체제는 정상인 경우 쓰기 하나 정도"만 잃는다고 설명합니다. 예외는 셋입니다. 하나는 "`everysec`에서 디스크가 느리면" 절에서 다룹니다. 또 하나는 바로 아래의 I/O 스레드입니다. 마지막은 `write`가 실패한 경우로, "디스크 쓰기가 실패하면 Redis는 쓰기 명령을 거부합니다"의 "AOF 쓰기 실패"에서 다룹니다.

**I/O 스레드를 켜면 응답이 `write`보다 먼저 나갈 수 있습니다.** `io-threads`를 2 이상으로 두면, I/O 스레드가 읽어 온 클라이언트의 명령을 메인 스레드가 실행한 뒤, 그 클라이언트를 곧바로 I/O 스레드에 돌려보내 응답을 쓰게 합니다. 이 일은 응답 직전의 정리 작업에서 하는 AOF `write`를 기다리지 않습니다. `appendfsync always`이면 아직 AOF 버퍼를 파일에 쓰고 동기화하지 않았으므로 돌려보내기를 그 뒤로 미룹니다. 따라서 `everysec`이나 `no`에서 I/O 스레드를 켜면, 응답은 나갔지만 쓰기는 아직 AOF 버퍼(프로세스 메모리)에만 있는 순간이 생길 수 있습니다. 그 순간 프로세스가 죽으면 응답한 쓰기를 잃습니다. 이것은 소스를 읽은 해석이며 재현하지 않았습니다.

AOF 파일은 `appendonlydir` 디렉터리에 있고, 쓰기 명령은 그 안의 증분 파일(`appendfilename`이 기본값 `appendonly.aof`이면 `appendonly.aof.<번호>.incr.aof`)에 덧붙습니다. 파일 구성은 "AOF는 계속 커지므로, 자식 프로세스가 새 기준 파일을 만듭니다"에서 다룹니다.

### appendfsync 세 가지: 무엇을 기다리고, 무엇을 잃는가

| 설정 | `fsync`를 누가 언제 하나 | 프로세스 장애 | 운영체제·전원 장애 | 대가 |
| --- | --- | --- | --- | --- |
| `always` | 메인 스레드가 응답 전에 매번 | 7 | 7 | 이벤트 루프 한 바퀴마다 저장 장치 왕복을 기다림 |
| `everysec`(기본값) | 백그라운드 스레드가 1초마다 | 7(예외 있음: 디스크가 느릴 때, `write`가 실패했을 때, I/O 스레드를 켰을 때) | 8 | 1초마다 `fsync` 한 번 |
| `no` | Redis는 호출하지 않음. 운영체제가 자체 내려 쓰기 | 7(예외 있음: `write`가 실패했을 때, I/O 스레드를 켰을 때) | 장담할 수 없음 | 가장 적음 |

표의 숫자는 예시에서 다시 시작한 뒤의 `stock:item:1`이고, `io-threads` 기본값(1)을 기준으로 합니다. 근거는 공식 문서 persistence "How durable is the append only file?"입니다.

- **`always`**: 메인 스레드가 `write` 직후 `fsync`를 부르고, 끝나야 응답합니다. 이벤트 루프 한 바퀴에서 여러 클라이언트의 쓰기를 실행했다면 `write`와 `fsync`를 한 번씩만 하고 함께 응답합니다. 공식 문서가 말하는 그룹 커밋입니다. 다른 클라이언트가 같은 바퀴에서 그 값을 읽었더라도 그 응답도 `fsync` 뒤에 나갑니다. 즉 `always`는 응답했거나 다른 클라이언트가 관찰한 쓰기는 디스크에 동기화되어 있다고 약속합니다. 단, `io-threads`를 2 이상으로 켠 상태에서도 이 약속이 모든 경로에서 지켜지는지는 **미확인**입니다. 소스상 응답 직전의 정리 작업이 AOF `write`·`fsync` 뒤에 I/O 스레드에서 넘어온 클라이언트의 명령을 더 실행하고 곧바로 I/O 스레드로 넘기는 경로가 보이지만, 그 응답이 실제로 `fsync`보다 먼저 나가는지는 재현하지 않았습니다. 대가는 저장 장치가 느려지면 그 시간이 **모든 클라이언트의 지연**이 된다는 점입니다. 메인 스레드가 기다리는 동안 다른 명령도 실행되지 않기 때문입니다.
- **`everysec`**: Redis가 관리하는 약 1초 간격에 맞춰, 이전 `fsync` 작업이 끝났고 동기화할 변경이 있으면 새 `fsync`를 백그라운드 스레드에 맡깁니다. 운영체제의 자체 내려 쓰기는 이 간격의 기준을 바꾸지 않습니다. 매초 정각에 호출·완료된다는 보장은 없고, 새 변경이 없으면 생략할 수 있습니다. 메인 스레드는 기다리지 않습니다. 정전이 나면 마지막으로 끝난 `fsync` 이후의 쓰기를 잃을 수 있습니다. 운영체제가 그사이 스스로 내려 쓴 부분은 남을 수 있으므로, 실제로 잃는 것은 그 범위의 일부일 수도 있습니다. 다만 저장 장치가 자체 캐시에 받아 두고 완료를 알린 쓰기는 정전에 사라질 수 있어, 남는다고 장담할 수 있는 것은 `fsync`가 끝난 부분뿐입니다. 예시에서는 10:00:02.0의 `fsync`가 A와 B를 내렸고 C는 내려가지 않았다고 했으므로 C를 잃고 8이 됩니다. 공식 문서는 "1초 분량을 잃을 수 있다"고 하지만, 이는 저장 장치가 제때 응답할 때의 값입니다. 바로 아래 절처럼 디스크가 느리면 늘어납니다.
- **`no`**: Redis는 `fsync`를 부르지 않습니다. 운영체제가 내려 쓰기 전에 정전이 나면 그만큼 잃습니다. Linux 기본 설정에서는 수십 초 분량이 될 수 있고, 공식 문서도 "보통 30초마다"라고 설명합니다. 예시라면 10:00:02.6에서 수십 초 전 상태로 돌아갈 수 있습니다.

세 설정 모두 저장 장치·서버 소실은 막지 못합니다. 그 장애에는 복제나 다른 곳에 둔 백업이 필요합니다.

### everysec에서 디스크가 느리면: 쓰기를 미루고, 그 사이 응답은 나갑니다

`everysec`의 백그라운드 `fsync`가 아직 끝나지 않았는데 메인 스레드가 같은 파일에 `write`하면, Linux에서는 그 `write`가 `fsync`가 끝날 때까지 막힐 수 있습니다(공식 문서 latency "Latency due to AOF and disk I/O"). 메인 스레드가 막히면 모든 명령이 멈추므로, Redis는 이 경우 `write`를 최대 2초까지 미룹니다. 2초가 지나도 `fsync`가 끝나지 않으면 기다리지 않고 `write`하고, `aof_delayed_fsync` 카운터를 올리며 "Asynchronous AOF fsync is taking too long (disk is busy?)"를 로그에 남깁니다.

이 동작에서 두 가지가 따라 나옵니다.

- **정전 때 잃을 수 있는 범위가 1초보다 커집니다.** `fsync`가 늦게 끝날수록 "마지막으로 끝난 `fsync`" 이후의 쓰기가 많아지기 때문입니다.
- **프로세스 장애에서도 응답한 쓰기를 잃을 수 있습니다.** 이것은 소스를 읽은 해석입니다. `write`를 미루는 동안에도 Redis는 미룸 여부와 상관없이 응답을 보냅니다. 그동안 응답한 쓰기는 Redis 프로세스의 AOF 버퍼에만 있습니다. 예시에서 10:00:02.0에 시작한 `fsync`가 디스크가 바빠 10:00:02.4까지 끝나지 않았다면, C의 `DECR`은 응답은 나갔지만 `write`되지 않은 상태입니다. 이때 `kill -9`를 당하면 C를 잃고 8이 됩니다.

이 상황은 디스크가 바쁠 때 생기므로, AOF와 같은 디스크를 쓰는 다른 작업(자식 프로세스의 RDB 저장, 다른 서비스의 대량 쓰기)이 원인이 될 수 있습니다.

### 자식이 일하는 동안 fsync를 끄는 설정

`no-appendfsync-on-rewrite`를 `yes`로 하면, RDB 저장이나 AOF 다시 쓰기 같은 자식 프로세스(모듈이 만든 자식도 포함)가 있는 동안 `fsync`를 아예 하지 않습니다. `always`여도 마찬가지입니다. 자식의 대량 쓰기 때문에 `fsync`가 오래 막히는 문제를 피하려는 설정입니다. 대가로 그동안의 내구성은 `no`와 같아지고, `redis.conf`는 Linux 기본 설정에서 최악의 경우 30초 분량을 잃을 수 있다고 설명합니다. 기본값은 `no`입니다.

### 트랜잭션과 스크립트는 AOF에서도 한 덩어리입니다

`MULTI`/`EXEC`와 Lua 스크립트가 실행한 쓰기가 둘 이상이면, AOF에 `MULTI`와 `EXEC`로 감싸 기록됩니다. 쓰기가 하나뿐이면 감싸지 않고 그 명령만 기록합니다(Redis 원자성 문서의 "스크립트의 쓰기는 복제본에도 한 덩어리로 전달됩니다"). 파일 끝에 `MULTI`만 있고 `EXEC`가 없는, 반쯤 기록된 트랜잭션이 남으면 어떻게 될까요? AOF를 읽을 때 Redis는 `MULTI` 뒤의 명령을 바로 실행하지 않고 모아 두었다가, `EXEC`를 만나야 한꺼번에 실행합니다. 그래서 `EXEC` 없이 파일이 끝나면 모아 둔 명령은 메모리에 하나도 반영되지 않습니다. 이미 실행한 것을 되돌리는 것이 아니라, 처음부터 실행하지 않은 것입니다. `aof-load-truncated`가 `yes`(기본값)이면 파일을 잘라 낸 뒤 시작합니다. 파일이 명령 경계에서 끝났다면 `MULTI` 앞까지 자릅니다. 명령 중간에서 끝났다면 마지막으로 온전히 읽은 명령 뒤까지만 잘라, `EXEC` 없는 트랜잭션의 앞부분이 파일에 남을 수 있습니다(소스를 읽은 해석이며 재현하지 않았습니다). `no`이면 끝이 잘린 파일과 같이 시작을 거부합니다. 어느 쪽이든 장애 뒤에 트랜잭션의 일부만 반영된 상태로 되살아나지는 않습니다.

## AOF는 계속 커지므로, 자식 프로세스가 새 기준 파일을 만듭니다

### 왜 다시 써야 하는가

재고를 1,000번 `DECR`하면 AOF에는 명령 1,000줄이 쌓이지만, 지금 상태를 만드는 데는 "값을 이것으로 하라" 한 번이면 됩니다. 그대로 두면 파일이 끝없이 커지고, 다시 시작할 때 1,000줄을 모두 다시 실행해야 합니다. 그래서 Redis는 주기적으로 **현재 데이터를 만드는 최소한의 내용**으로 새 기준 파일을 만듭니다. 이것이 AOF 다시 쓰기(rewrite)입니다.

### AOF는 여러 파일과 목록 파일로 이루어집니다

`appendonlydir` 안에는 세 종류의 파일이 있습니다(`redis.conf`의 `appendfilename` 설명, 공식 문서 persistence "Append-only file").

- **기준(base) 파일**: 다시 쓰기를 한 시점의 데이터 전체입니다. 기본으로 RDB 형식으로 씁니다(`aof-use-rdb-preamble` 기본값 `yes`). 명령을 한 줄씩 다시 실행하는 것보다 읽기가 빠릅니다.
- **증분(incr) 파일**: 기준 파일 이후의 쓰기 명령입니다. 메인 스레드는 이 파일에 덧붙입니다.
- **목록(manifest) 파일**: 어느 기준 파일과 어느 증분 파일을 어떤 순서로 읽어야 하는지 적은 파일입니다.

### 다시 쓰는 동안에도 기존 파일들은 그대로 완전합니다

1. 메인 스레드가 AOF 버퍼를 비우고 **새 증분 파일**을 엽니다. 이제부터 쓰기는 새 증분 파일에 덧붙습니다.
2. `fork`합니다. 자식은 `fork` 순간의 데이터로 임시 기준 파일을 씁니다.
3. 자식이 끝나면 메인 스레드가 "새 기준 파일 + 새 증분 파일"을 적은 임시 목록 파일을 만들어 `fsync`하고, 원자적으로 교체합니다. 그 뒤 옛 기준 파일과 옛 증분 파일을 지웁니다(공식 문서 persistence "How it works").

다시 쓰기가 어느 단계에서 실패해도 "옛 기준 + 옛 증분 + 새 증분"이 전체 데이터를 담고 있으므로 데이터를 잃지 않습니다. 단, 이것은 이미 AOF를 쓰고 있던 서버의 다시 쓰기에 해당합니다. `CONFIG SET appendonly yes` 직후의 첫 다시 쓰기에는 옛 기준·증분 파일이 없고, 그동안의 쓰기는 목록에 오르지 않은 임시 증분 파일에 모입니다. 첫 다시 쓰기가 성공하기 전까지는 디스크의 AOF로 데이터를 되살릴 수 없습니다. 자식 프로세스가 실행된 뒤 실패하거나 완료 처리에서 실패한 경우가 몇 번 이어지면, 자동·예약 다시 쓰기의 다음 시도를 점점 늘어나는 간격(상한 있음)으로 미룹니다. `fork` 실패, 디렉터리 생성 실패, 새 증분 파일 열기 실패처럼 자식을 띄우기 전의 실패는 이 연속 실패 수에 들어가지 않아 간격 제한이 걸리지 않습니다. 다시 쓰기를 시작할 때마다 새 증분 파일을 열므로(`fork` 실패는 새 증분 파일을 연 뒤에 일어납니다), 계속 실패하면 증분 파일이 쌓이고 다시 시작할 때 읽을 양도 늘어납니다.

### 언제 다시 쓰는가, 무엇이 드는가

자동 다시 쓰기는 AOF 전체 크기가 64MB를 넘고, 마지막 다시 쓰기 직후 크기의 두 배(100% 증가) 이상이 되면 시작합니다(`auto-aof-rewrite-min-size` 64mb, `auto-aof-rewrite-percentage` 100). 다만 이 비교 기준 크기는 파일에 남기지 않으므로, 재시작 뒤에는 기준 파일의 크기를 비교 기준으로 삼습니다. 그래서 재시작 뒤 첫 자동 다시 쓰기가 예상보다 일찍 시작될 수 있습니다. `BGREWRITEAOF` 명령으로 직접 시작할 수도 있습니다.

대가는 RDB 저장과 같습니다. `fork` 동안 모든 명령이 멈추고, 자식이 사는 동안 복사되는 메모리(`aof_last_cow_size`)가 늘고, 디스크를 크게 씁니다. Redis는 RDB 저장과 AOF 다시 쓰기를 동시에 하지 않고, RDB·AOF·모듈용 자식 프로세스를 한 번에 하나만 둡니다. 다른 자식이 일하는 동안 자동 저장 조건 확인은 건너뜁니다. 명령으로 요청했는데 **다른 종류의** 자식이 일하고 있으면 예약될 수 있습니다. RDB 저장 중의 `BGREWRITEAOF`는 예약했다가 앞의 일이 끝나면 시작하고, AOF 다시 쓰기 중의 `BGSAVE`는 `SCHEDULE`을 붙여야 예약됩니다. 같은 종류의 자식이 이미 돌고 있으면(AOF 다시 쓰기 중의 `BGREWRITEAOF`, RDB 저장 중의 `BGSAVE SCHEDULE`) 예약하지 않고 오류를 돌려줍니다(공식 문서 persistence "Interactions between AOF and RDB persistence").

## 다시 시작하면 무엇을 읽는가: AOF가 켜져 있으면 RDB는 보지 않습니다

### 읽는 순서

시작할 때 AOF가 켜져 있으면 AOF만 읽고, 꺼져 있으면 `dump.rdb`만 읽습니다. 둘 다 켜 두면 AOF를 씁니다. AOF가 더 최근까지의 변경을 담고 있기 때문입니다(공식 문서 persistence). 읽는 동안 들어온 명령은 대부분 `-LOADING Redis is loading the dataset in memory` 오류를 받습니다. 데이터가 클수록 이 시간이 길어지므로, 재시작은 곧 "데이터가 클수록 길어지는 시간 동안 쓸 수 없음"입니다. 실제 시간은 파일 형식, CPU, 저장 장치에 따라 다르므로 운영 환경에서 잽니다.

### 설정 파일에서 AOF만 켜고 재시작하면 데이터가 사라집니다

RDB만 쓰던 서버에서 `redis.conf`의 `appendonly`를 `yes`로 바꾸고 재시작하면 어떻게 될까요?

1. AOF가 켜져 있으므로 Redis는 AOF만 읽으려 합니다. 그런데 AOF 파일이 아직 없습니다.
2. Redis는 AOF가 없다고 판단하고, `dump.rdb`를 읽지 않은 채 넘어갑니다. **Redis는 빈 상태로 시작합니다.**
3. 이어서 빈 데이터로 새 기준 파일을 만듭니다.
4. `dump.rdb`는 아직 디스크에 있지만, RDB 저장 조건이 켜져 있으면 다음 저장 때 지금의(빈 상태에서 다시 쌓인) 데이터로 덮어씁니다.

예시라면 재시작 직후 `stock:item:1`이 없습니다. `redis.conf`의 `appendonly` 주석과 공식 문서 모두 이 절차가 데이터 손실로 이어질 수 있다고 경고합니다. 올바른 순서는 다음과 같습니다(공식 문서 persistence "How I can switch to AOF").

1. 최신 `dump.rdb`를 안전한 곳에 백업합니다.
2. 실행 중인 서버에 `CONFIG SET appendonly yes`를 보냅니다. Redis는 지금 메모리의 데이터로 첫 기준 파일을 만드는 다시 쓰기를 시작합니다.
3. `INFO persistence`에서 `aof_rewrite_in_progress`와 `aof_rewrite_scheduled`가 0이고 `aof_last_bgrewrite_status`가 `ok`인지 확인합니다.
4. `CONFIG REWRITE` 등으로 설정 파일에도 반영합니다. 빠뜨리면 다음 재시작 때 옛 설정으로 돌아갑니다.
5. 재시작 뒤 키 개수가 전과 같은지 확인합니다.

2번의 첫 다시 쓰기를 자식 프로세스가 하고 있는 동안에는 Redis가 정상 종료를 거부합니다("Writing initial AOF, can't exit"). 아직 AOF에 데이터가 없는 상태로 끝나면 위와 같은 손실이 나기 때문입니다. 다만 다른 자식 프로세스가 일하고 있어 첫 다시 쓰기가 예약만 된 상태라면 이 보호가 걸리지 않습니다. 그래서 3번의 확인이 끝나기 전에는 종료하지 않는 것을 운영 규칙으로 둡니다. `SHUTDOWN FORCE`면 이 경우에도 "Writing initial AOF. Exit anyway."를 남기고 끝내므로, 이때는 쓰지 않습니다.

## 디스크 쓰기가 실패하면 Redis는 쓰기 명령을 거부합니다

디스크가 가득 차거나, 권한이 바뀌거나, 저장 장치에 오류가 나면 영속화가 실패합니다. Redis는 이때 "조용히 계속 쓰기를 받고 디스크에는 남기지 못하는" 상태를 피하려고 쓰기를 거부합니다. 거부의 대상과 조건은 다음과 같습니다.

### RDB 저장 실패: stop-writes-on-bgsave-error

- **원인**: 디스크 공간 부족, 쓰기 권한 없음, 입출력 오류, 그리고 `fork` 실패입니다. `fork`는 메모리가 모자라거나 커널의 overcommit 정책이 거절하면 실패합니다. `fork`가 성공하더라도 copy-on-write로 메모리가 바닥나면 커널이 프로세스를 강제 종료할 수 있습니다. 자세한 조건은 [fork와 copy-on-write](../cs/fork-and-copy-on-write.md)의 "대가 3"에서 다룹니다.
- **동작**: 마지막 백그라운드 저장이 실패했고, `stop-writes-on-bgsave-error`가 `yes`(기본값)이고, 저장 조건이 하나 이상 있으면, 쓰기 명령과 `PING`에 `-MISCONF Redis is configured to save RDB snapshots, but it's currently unable to persist to disk...` 오류를 돌려줍니다. 읽기 명령은 계속 처리합니다. 이 거부는 일반 클라이언트에 대한 것이며, 복제본이 주 서버에서 받은 명령을 적용하는 경로는 따로 처리합니다.
- **회복**: 저장 조건을 만족하고 마지막 시도에서 5초가 넘게 지나면, 주기 작업이 다음에 확인할 때 다시 저장을 시도합니다. 저장이 성공하면 쓰기를 다시 받습니다.

예시라면 디스크가 가득 찬 뒤 주문 D의 `DECR`이 `MISCONF`로 실패합니다. 재고 조회(`GET`)는 됩니다. `PING`도 실패한다는 점이 함정입니다. `PING`으로 상태를 확인하는 도구는 Redis가 죽었다고 판단할 수 있습니다.

`stop-writes-on-bgsave-error`를 `no`로 바꾸면 쓰기는 계속 되지만, 새 변경이 RDB에 남지 않는 상태를 `rdb_last_bgsave_status`를 지켜보지 않는 한 알 수 없습니다. 이 설정은 RDB 저장 실패에만 적용됩니다. 아래의 AOF 쓰기 실패로 인한 거부는 이 설정과 상관없이 일어납니다. `redis.conf`도 영속화 모니터링을 제대로 갖춘 경우에만 끄라고 설명합니다. 가용성과, 문제를 늦게 알아차릴 위험을 맞바꾸는 선택입니다.

### AOF 쓰기 실패

- **`everysec`, `no`일 때**: `write`가 실패하면 데이터를 AOF 버퍼에 그대로 두고 `aof_last_write_status`를 오류로 표시합니다. 이 상태에서는 쓰기 명령과 `PING`에 `-MISCONF Errors writing to the AOF file: <원인>`을 돌려줍니다. 메인 스레드는 이벤트 루프의 응답 직전 정리 작업과 1초 주기 작업에서 다시 `write`를 시도하고, 성공하면 "AOF write error looks solved, Redis can write again."을 남기고 쓰기를 다시 받습니다. 주의할 점은 거부가 **그다음 명령부터**라는 것입니다. `write`가 실패한 그 이벤트 루프 한 바퀴에서 이미 실행한 쓰기는, AOF 쓰기 처리가 오류만 기록하고 돌아온 뒤 그대로 성공 응답이 나갑니다. 이 쓰기는 AOF 버퍼(프로세스 메모리)에만 있으므로, 재시도가 성공하기 전에 프로세스가 죽으면 응답을 받은 쓰기를 잃습니다. 예시라면 주문 C의 `DECR`을 `write`하다 디스크가 가득 찼을 때, 주문 API는 7을 받지만 C는 버퍼에만 있습니다. 이때 `kill -9`를 당하면 8이 됩니다. 백그라운드 `fsync`가 실패한 경우도 같은 방식으로 쓰기를 거부합니다. 이 상태는 `write` 실패와 따로 기록되어, `write`가 성공해도 풀리지 않고 그 뒤의 백그라운드 `fsync`가 성공해야 풀립니다. 그런데 Redis는 `fsync`를 맡긴 시점에 "여기까지 맡겼다"고 기록하고, 그 `fsync`가 실패해도 이 기록을 되돌리지 않습니다. 그래서 쓰기가 거부되어 새로 쓸 내용이 없으면 `fsync`를 다시 맡기지 않는 경로가 있습니다. 그래서 디스크를 고쳐도 이 거부가 저절로 풀린다고 장담할 수 없습니다. 이것은 소스를 읽은 해석이며 재현하지 않았습니다.
- **일부만 쓴 경우**: 요청한 바이트 중 일부만 썼다면 그 부분을 잘라 냅니다. 잘라 내기도 실패하면 "Redis may refuse to load the AOF the next time it starts"를 로그에 남기고, `everysec`·`no`에서는 나머지를 다음 `write`에서 이어 씁니다(`always`는 아래처럼 프로세스를 끝냅니다). 이어 쓰기가 성공하기 전에 프로세스가 끝났는데 남은 부분이 명령 중간에서 끊겨 있으면, 다음 시작 때 끝이 잘린 파일로 처리됩니다.
- **`always`일 때**: `write`나 `fsync`가 실패하면 **Redis가 프로세스를 끝냅니다**. 메모리의 값은 이미 바뀌었고 되돌릴 수 없는데, `always`는 응답했거나 관찰된 쓰기는 디스크에 있다고 약속했으므로 계속 돌면 그 약속을 어기게 되기 때문입니다. 이 경우 응답은 아직 보내지 않았으므로, 응답을 받은 쓰기를 잃지는 않습니다. 대신 서비스는 Redis가 다시 시작될 때까지 멈춥니다.

## 파일이 잘리거나 깨지면: 끝은 잘라 내고 시작하고, 가운데가 깨지면 멈춥니다

[파일 쓰기와 내구성](../cs/file-write-durability.md)의 "쓰다가 멈추면 끝이 잘린 기록이 남을 수 있습니다"에서 본 구분이 Redis에서는 이렇게 나타납니다.

- **마지막 파일의 끝이 잘림**: 정전으로 마지막 명령이 반쯤만 기록됐거나 디스크가 가득 찬 경우입니다. `aof-load-truncated`가 `yes`(기본값)면 마지막으로 온전히 읽은 명령 위치까지 파일을 자르고, "AOF loaded anyway because aof-load-truncated is enabled"를 남기고 시작합니다. `no`면 시작하지 않고 `redis-check-aof --fix`를 안내합니다. 이렇게 잘라 내는 것은 Redis 프로토콜 형식으로 기록된 부분이 도중에 끝난 경우이고, Redis는 그 파일이 목록의 마지막인지 확인하기 **전에** 먼저 잘라 냅니다. 시작을 이어 가는 것은 그 파일이 마지막일 때뿐입니다(바로 아래 "마지막이 아닌 파일이 잘림"). 기준 파일의 RDB 형식 부분을 읽다 실패하면 잘라 내지 않고 "AOF loading aborted"를 남기고 시작하지 않습니다. 운영체제가 멈춰 생긴 전형적인 잘림이라면 버려지는 것은 `fsync`가 끝나지 않은 꼬리이므로, `always`였다면 응답한 적이 없는 쓰기입니다(`no-appendfsync-on-rewrite`가 기본값 `no`이고 I/O 스레드를 켜지 않았을 때). 다만 Redis는 파일 모양만 보고 자를 뿐, 그 부분이 `fsync`됐는지나 응답했는지는 알지 못합니다. 그런데 저장 장치는 섹터라는 고정 크기 단위로 쓰므로, 새로 덧붙인 명령과 이미 `fsync`한 앞 명령이 한 섹터에 함께 들어갈 수 있습니다. 새 명령을 덧붙이다 그 섹터가 손상되면, 응답한 쓰기가 잘림으로 판정돼 함께 버려지거나 시작이 거부될 수 있습니다. 이 경우는 [AOF 손상 판정](./aof-corruption.md)에서 다룹니다. `redis.conf`는 이런 잘림이 운영체제가 멈출 때 생기며, Redis 프로세스만 죽을 때는 생기지 않는다고 설명합니다.
- **마지막이 아닌 파일이 잘림**: 기준 파일이나 앞쪽 증분 파일이 잘려 있으면 그 뒤의 파일을 이어 붙일 수 없으므로 시작하지 않습니다("Fatal error: the truncated file is not the last file"). 이때 `aof-load-truncated`가 `yes`였다면 그 파일은 이미 잘린 뒤입니다. 파일을 먼저 자른 다음에 마지막 파일인지 확인하기 때문입니다. 시작을 거부한 서버의 AOF를 살펴볼 때는 원본이 이미 바뀌었을 수 있다는 점을 염두에 둡니다.
- **가운데가 깨짐**: 명령 형식이 맞지 않는 바이트가 중간에 있으면 "Bad file format reading the append only file"을 남기고 시작하지 않습니다. 공식 문서는 먼저 `--fix` 없이 `redis-check-aof`로 위치를 확인하고, 가능하면 손으로 고치라고 권합니다. `--fix`에 맡기면 **깨진 지점부터 파일 끝까지를 버릴 수 있어**, 손상이 앞쪽에 있으면 대량의 데이터를 잃습니다(공식 문서 persistence "What should I do if my AOF gets corrupted?"). `--fix`가 잘라 낼 수 있는 것도 목록의 마지막 파일뿐이고, 기준 파일의 RDB 형식 부분이 깨졌으면 검사를 중단합니다. 고치기 전에 반드시 파일을 백업합니다.
- **목록 파일에 있는 AOF 파일이 디스크에 없음**: 치명적 오류로 보고 시작하지 않습니다.
- **RDB 파일 손상**: 앞의 "파일이 없으면 빈 상태로, 깨져 있으면 시작하지 않습니다"처럼 시작하지 않습니다. `redis-check-rdb`로 확인합니다.

공통된 태도는 "끝의 잘림은 장애의 흔적이니 자동으로 정리하고, 그 밖의 손상은 사람이 보게 한다"입니다. 그 대가로 손상이 있으면 Redis가 뜨지 않아 서비스가 멈춥니다.

## 종료 방식에 따라 남는 것이 다릅니다

### 정상 종료: 저장하고 끝내며, RDB 저장에 실패하면 끝내지 않습니다

`SHUTDOWN` 명령이나 `SIGTERM`·`SIGINT`를 받으면 Redis는 다음 순서로 정리합니다(`redis.conf`의 SHUTDOWN 절).

1. 복제본이 있으면, 뒤처진 복제본이 따라올 때까지 최대 `shutdown-timeout`(기본 10초) 기다립니다.
2. 일하던 자식 프로세스가 있으면 끝냅니다. RDB를 쓰던 자식이면 임시 파일도 지웁니다. AOF 다시 쓰기 자식도 끝내지만, 첫 다시 쓰기라면 "설정 파일에서 AOF만 켜고 재시작하면 데이터가 사라집니다"에서 본 것처럼 종료를 거부합니다.
3. AOF가 켜져 있으면 AOF 버퍼를 `write`하고 `fsync`합니다. `everysec`·`no`에서는 이 `write`나 `fsync`가 실패해도 경고 로그만 남기고 다음 단계로 넘어갑니다. `always`에서 `write`가 실패하면 그 자리에서 프로세스가 끝납니다.
4. 저장 조건이 하나 이상 있으면(기본값) **메인 스레드가 직접 RDB를 저장합니다.** 데이터가 클수록 오래 걸립니다.
5. RDB 저장이 실패하면 "Error trying to save the DB, can't exit"를 남기고 **끝내지 않습니다.** `SHUTDOWN FORCE`면 실패해도 끝냅니다.

예시라면 정상 종료 뒤에는 RDB만 쓰든 AOF를 쓰든 7이 남습니다. `SHUTDOWN NOSAVE`는 4번의 RDB 저장을 건너뜁니다. 3번의 AOF `fsync`는 그대로 합니다. 종료를 멈추는 것은 5번의 RDB 저장 실패와, 2번에서 본 첫 AOF 다시 쓰기 진행 중(`SHUTDOWN FORCE`가 아닐 때)뿐이고, AOF의 `write`·`fsync` 실패는 종료를 멈추지 않는다는 점도 기억해 둡니다. RDB 저장 조건 없이 AOF만 쓰는 구성에서 디스크가 가득 찬 채 정상 종료하면, 3번이 실패해도 그대로 끝나므로 버퍼에 남은 쓰기를 잃을 수 있습니다.

### 강제 종료는 프로세스 장애와 같습니다

`kill -9`나 OOM killer는 Redis에 정리할 기회를 주지 않습니다. 결과는 "프로세스 장애" 줄과 같습니다. 컨테이너 오케스트레이터는 보통 먼저 `SIGTERM`을 보내고 유예 시간이 지나면 강제로 끝냅니다. 이 순서와 유예 시간은 쓰는 도구의 문서에서 확인해야 하며, 이 문서는 특정 도구의 문서로 확인하지 않았습니다. 4번의 RDB 저장이 유예 시간보다 오래 걸리면 저장 도중 강제 종료되고, `dump.rdb`는 직전에 성공한 스냅숏으로 남습니다. 큰 Redis를 RDB만으로 운영한다면, 정상 종료라고 생각한 재시작이 실제로는 마지막 스냅숏 이후를 잃는 재시작이 될 수 있습니다.

### 장애 종류별 결과를 한 표로

| 설정 | 정상 종료 | 프로세스 장애 | 운영체제·전원 장애 | 저장 장치·서버 소실 |
| --- | --- | --- | --- | --- |
| 영속성 끔(남은 `dump.rdb` 없음) | 키 없음 | 키 없음 | 키 없음 | 키 없음 |
| RDB만(기본 저장 조건) | 7 | 10 | 10 | 키 없음 |
| AOF `always` | 7 | 7 | 7 | 키 없음 |
| AOF `everysec` | 7 | 7(디스크가 느리거나, `write`가 실패했거나, I/O 스레드를 켰으면 8일 수 있음) | 8(디스크가 느리면 더 이전) | 키 없음 |
| AOF `no` | 7 | 7(`write`가 실패했거나 I/O 스레드를 켰으면 8일 수 있음) | 수십 초 전 상태일 수 있음 | 키 없음 |

"키 없음"인 칸은 다른 곳에 사본(복제본, 외부 백업)이 없을 때의 결과입니다. 백업에서 복구하면 그 백업 시점으로 돌아갑니다. "프로세스 장애" 열은 `io-threads` 기본값(1) 기준이고, I/O 스레드를 켰을 때의 예외는 소스 해석입니다. `always`에서 I/O 스레드를 켠 경우는 미확인입니다.

## 사람의 실수와 백업: 지운 데이터를 되살릴 수 있는가

지금까지는 장비나 프로세스가 멈추는 장애를 봤습니다. 데이터를 잃는 또 하나의 흔한 원인은 사람의 실수입니다. 예시를 이어, 10:05:00에 운영자가 다른 서버인 줄 알고 이 Redis에 `FLUSHALL`을 보냈다고 합시다. Redis는 명령을 정상적으로 실행했으므로 이것은 장애가 아니고, 영속성은 이 실수까지 충실히 남깁니다. 되살릴 수 있는지는 **실수 이전의 데이터를 아직 무엇이 갖고 있는가**에 달려 있습니다.

### FLUSHALL은 복제본과 AOF로 전파되고, RDB 파일까지 덮어씁니다

- **복제본**: `FLUSHALL`과 `FLUSHDB`는 데이터가 이미 비어 있어도 복제본과 AOF에 반드시 전파됩니다. 복제본은 장비 장애에는 사본이지만, 실수에는 같은 실수를 따라 하는 사본입니다.
- **`dump.rdb`**: 저장 조건이 하나라도 있으면(기본값) `FLUSHALL`은 데이터를 비운 직후 메인 스레드가 직접 RDB를 저장합니다. 이 저장이 성공하면 `dump.rdb`가 빈 데이터로 곧바로 덮어써지고, "마지막 스냅숏은 남아 있겠지"라는 기대가 틀립니다. 저장 결과는 확인하지 않으므로 디스크가 가득 차 저장이 실패하면 이전 `dump.rdb`가 남지만, 이것은 우연일 뿐 기댈 수 있는 동작이 아닙니다. `FLUSHDB`는 이 저장을 하지 않지만, 다음 저장 조건이 되면 지워진 상태가 저장됩니다.
- **AOF**: `FLUSHALL`도 쓰기 명령 하나로 증분 파일 끝에 덧붙습니다. 실수 이전의 명령들은 그 앞에 그대로 남아 있습니다.

### AOF는 다시 쓰기 전이라면 실수 직전으로 돌릴 수 있습니다

공식 문서는 `FLUSHALL`을 실수로 실행했더라도 그사이 AOF 다시 쓰기가 없었다면, 서버를 멈추고 마지막 명령을 지운 뒤 재시작해 데이터를 되살릴 수 있다고 설명합니다(persistence "AOF advantages"). 기준·증분·목록 파일 구성에 맞춰 풀면 다음 순서가 됩니다. 이 순서는 공식 문서의 설명과 소스의 동작을 이어 붙인 것이며, 실제로 수행해 확인하지는 않았습니다.

1. **다시 쓰기를 막습니다.** 실수 뒤에 시작한 다시 쓰기는 지금 메모리(빈 상태)로 새 기준 파일을 만들고, 끝나면 옛 기준·증분 파일을 지웁니다. 그 순간 되돌릴 근거가 사라집니다. 자동 다시 쓰기는 실수와 상관없이 AOF 크기 조건만 보고 시작하므로, `CONFIG SET auto-aof-rewrite-percentage 0`으로 끄고 `BGREWRITEAOF`도 보내지 않습니다. 이 설정은 새로 시작할 다시 쓰기만 막고, 이미 진행 중이거나 예약된 다시 쓰기는 멈추지 않습니다. 그래서 `INFO persistence`의 `aof_rewrite_in_progress`와 `aof_rewrite_scheduled`를 확인하고, 어느 쪽이든 1이면 끝나기를 기다리지 말고 바로 2번으로 서버를 멈춥니다. 정상 종료는 진행 중인 다시 쓰기 자식을 끝내고 그 결과를 버리며, 예약은 메모리에만 있으므로 함께 사라집니다. 단, 복제본이 있으면 정상 종료는 자식을 끝내기 전에 뒤처진 복제본을 최대 `shutdown-timeout`(기본 10초)까지 기다리고, 그동안에도 주기 작업이 돌아 진행 중인 다시 쓰기가 끝나거나 예약된 다시 쓰기가 시작될 수 있습니다. 그래서 복제본이 있으면 이 기다림을 건너뛰는 `SHUTDOWN NOW`로 멈춥니다. 일반 백업이라면 다시 쓰기가 끝나기를 기다려도 되지만, 여기서는 기다리는 동안 되돌릴 근거가 사라질 수 있습니다.

   되살릴 수 있는지의 기준은 다시 쓰기가 끝난 시각이 아니라, **`FLUSHALL`이 목록 파일에 오른 증분 파일에 아직 남아 있는가**입니다. 다시 쓰기는 `fork`한 순간의 데이터로 기준 파일을 만들고, 그 뒤의 명령은 다시 쓰기를 시작할 때 연 새 증분 파일에 덧붙입니다. 그래서 실수 **전에** `fork`한 다시 쓰기는 실수 뒤에 끝났더라도 실수 전 데이터로 기준 파일을 만들고, `FLUSHALL`은 새 증분 파일에 남으므로 3번으로 되살릴 수 있습니다. 실수 **뒤에** `fork`한 다시 쓰기가 성공했다면 기준 파일은 빈 상태이고 `FLUSHALL`이 담긴 증분 파일은 지워졌으므로 이 방법은 쓸 수 없습니다.
2. **서버를 멈추고 `appendonlydir`를 통째로 복사해 둡니다.** 편집을 잘못해도 돌아갈 곳이 있어야 합니다.
3. **목록 파일에 적힌 순서대로 증분 파일을 살펴 `FLUSHALL`을 찾고, 그 명령과 그 뒤의 명령을 모두 지웁니다.** 보통은 마지막 증분 파일에 있습니다. 하지만 실수 뒤에 시작한 다시 쓰기가 실패했거나 서버를 멈춰 끝나지 못했다면, 다시 쓰기는 `fork` 전에 새 증분 파일을 열므로 `FLUSHALL`은 그 앞 증분 파일에 있습니다. 이때는 그 파일에서 `FLUSHALL`부터 끝까지 지우고, 뒤따르는 증분 파일의 명령도 모두 지웁니다. 비어 있는 증분 파일은 읽을 때 문제가 되지 않습니다. 증분 파일은 Redis 프로토콜 형식이라 값이 문자열이면 편집기로 읽을 수 있습니다. 기준 파일은 기본값(`aof-use-rdb-preamble yes`)에서 RDB 형식의 바이너리이므로 편집 대상이 아닙니다. 다만 값에는 임의의 바이트가 들어갈 수 있고 인자마다 바이트 길이가 앞에 적혀 있으므로, 편집기가 바이트를 바꾸거나 길이가 어긋나면 파일이 깨집니다. 명령을 통째로 지우고, 고친 뒤 `redis-check-aof`로 확인합니다. `FLUSHALL`만 지우면 그 뒤에 들어온 쓰기는 옛 데이터 위에 그대로 다시 실행됩니다. 무엇을 남길지는 서비스가 판단해야 합니다.
4. **재시작한 뒤 키 개수와 대표 키를 확인합니다.** 예시라면 `stock:item:1`이 7인지 봅니다.

**시각을 지정해 자를 수도 있습니다.** `aof-timestamp-enabled`(기본값 `no`)를 켜 두면, AOF에 초 단위 시각이 이전 표시보다 커질 때마다 `#TS:<유닉스 시각>` 표시가 들어갑니다(시계가 뒤로 가면 새 표시가 생기지 않습니다). 그러면 `redis-check-aof --truncate-to-timestamp <시각> <목록 파일>`로 그 시각 이후를 잘라 낼 수 있습니다. 예시라면 10:04:59에 해당하는 시각을 주어 10:05:00부터를 버립니다. 제약은 셋입니다.

- 표시가 초 단위이므로, 같은 초 안에서 `FLUSHALL`보다 먼저 들어온 쓰기도 함께 버려집니다.
- 자를 수 있는 곳은 마지막 파일 안뿐입니다. 지정한 시각이 그보다 앞 파일에 있으면 도구가 거부합니다. 기준 파일 이전으로는 돌아갈 수 없으므로, 되돌릴 수 있는 범위는 "마지막 다시 쓰기 이후"입니다.
- `redis.conf`는 이 옵션이 AOF 형식을 바꿔 기존 AOF 파서와 맞지 않을 수 있다고 경고합니다. 켜기 전에 AOF를 읽는 다른 도구가 있는지 확인합니다.

**RDB만 쓰면 서버 안에는 되돌릴 근거가 없습니다.** `dump.rdb`가 이미 빈 데이터로 덮어써졌기 때문입니다. 서버 밖으로 옮겨 둔 백업만 남습니다. 예시라면 마지막 백업 시점의 재고로 돌아가고, 그 뒤의 주문은 주문 DB의 기록으로 다시 계산해야 합니다.

### 백업: RDB는 실행 중에 복사해도 되지만, AOF는 다시 쓰기를 멈추고 복사합니다

- **RDB**: 임시 파일에 쓰고 `rename`으로 교체하므로, 실행 중에 `dump.rdb`를 복사해도 완성된 스냅숏 하나를 얻습니다. 공식 문서는 시간별·일별 사본을 날짜를 붙여 보관하고, 하루 한 번 이상 서버 밖(적어도 다른 물리 장비)으로 옮기라고 권합니다. 옮긴 뒤에는 파일 크기와 SHA1을 비교해 제대로 옮겨졌는지 확인하라고 합니다(persistence "Backing up Redis data", "Disaster recovery").
- **AOF**: `appendonlydir` 안의 파일들을 함께 복사해야 합니다. 다시 쓰기 도중에 복사하면 깨진 백업이 될 수 있습니다. 공식 문서의 절차는 다음과 같습니다(persistence "Backing up AOF persistence").
  1. `CONFIG SET auto-aof-rewrite-percentage 0`으로 자동 다시 쓰기를 끕니다. 백업 도중 Redis가 재시작될 수 있다면 `CONFIG REWRITE`로 설정 파일에도 반영해, 재시작 뒤 다시 쓰기가 자동으로 시작되지 않게 합니다. 이때는 4번에서도 `CONFIG REWRITE`로 되돌린 값을 반영합니다.
  2. `INFO persistence`에서 `aof_rewrite_in_progress`와 `aof_rewrite_scheduled`가 모두 0인지 확인합니다. 공식 문서 절차는 앞의 것만 확인하지만, 예약된 다시 쓰기는 1번 설정과 상관없이 다른 자식 프로세스가 끝나면 시작합니다.
  3. 디렉터리의 파일을 복사합니다.
  4. 원래 값으로 되돌립니다.

  다시 쓰기를 끄는 시간을 줄이려면, 3번에서 파일들에 하드 링크를 만든 뒤 바로 4번을 하고 링크를 천천히 복사합니다. 하드 링크는 같은 파일 내용에 이름을 하나 더 붙이는 것입니다. 이 시점에 사본이 생기지는 않지만, Redis가 다시 쓰기 뒤 원래 이름의 파일을 지워도 링크한 이름으로 그 내용을 계속 읽을 수 있습니다. Redis가 이 디렉터리의 파일을 덧붙이기만 하거나 통째로 교체하므로 가능하다고 공식 문서가 설명합니다.

### 복구: AOF를 켠 서버에 dump.rdb만 넣으면 무시됩니다

백업에서 되살릴 때도 "다시 시작하면 무엇을 읽는가"의 규칙이 그대로 적용됩니다. 두 가지 함정이 있습니다.

- **실행 중인 Redis 옆에 백업 파일을 넣고 재시작하면 안 됩니다.** 정상 종료는 저장 조건이 있으면 지금 메모리로 `dump.rdb`를 다시 씁니다("종료 방식에 따라 남는 것이 다릅니다"). 넣어 둔 백업이 덮어써집니다. 먼저 Redis를 멈춘 뒤 파일을 넣습니다.
- **AOF를 켠 설정으로 시작하면 넣어 둔 `dump.rdb`는 읽히지 않습니다.** 시작할 때 AOF가 켜져 있으면 AOF만 읽기 때문입니다.

그래서 RDB 백업으로 되살리면서 AOF도 쓰려면 다음 순서를 따릅니다. 앞의 시작 규칙과 "설정 파일에서 AOF만 켜고 재시작하면 데이터가 사라집니다"의 전환 절차를 이어 붙인 것이며, 실제로 수행해 확인하지는 않았습니다.

1. Redis를 멈춥니다.
2. 기존 `appendonlydir`를 다른 곳으로 옮겨 두고, 백업한 `dump.rdb`를 데이터 디렉터리(`dir`)에 둡니다.
3. `appendonly no`로 시작해 RDB를 읽게 합니다.
4. 키 개수와 대표 키를 확인합니다.
5. 실행 중에 `CONFIG SET appendonly yes`로 AOF를 켜고, 첫 다시 쓰기가 끝난 것을 확인한 뒤 설정 파일에 반영합니다.

AOF 백업으로 되살릴 때는 Redis를 멈추고 `appendonlydir`를 백업본으로 바꾼 뒤 `appendonly yes`로 시작합니다.

### 다시 시작하면 만료 시각이 지난 키는 돌아오지 않습니다

- RDB와 AOF는 만료 시간을 "몇 초 남음"이 아니라 **절대 시각**으로 저장합니다. RDB에는 만료 시각을 밀리초 단위 유닉스 시각으로 적습니다. AOF에는 `EXPIRE key 60` 같은 상대 시간 명령이 `PEXPIREAT key <밀리초 시각>`으로 바뀌어 기록됩니다.
- 그래서 Redis가 내려가 있는 동안 만료 시각이 지난 키는 다시 시작한 뒤 보이지 않습니다. 주 서버가 RDB 파일을 읽을 때는 그런 키를 아예 올리지 않고, 건너뛴 수를 `INFO persistence`의 `rdb_last_load_keys_expired`로 셉니다. AOF로 시작하면 만료 시각이 지난 키도 일단 올라왔다가, 조회하거나 주기적 만료 처리가 돌 때 만료된 것으로 처리되어 보이지 않습니다.
- 예시의 재고 키에는 만료 시간이 없으므로 영향이 없습니다. 하지만 같은 서비스가 TTL로 관리하는 세션이나 락 키라면, 재시작 뒤에는 "남은 시간이 지난 만큼 줄어든" 상태로 돌아옵니다. 내려가 있던 시간이 TTL보다 길면 사라집니다.
- 만료 판정은 서버의 현재 시각과 비교합니다. 그래서 백업 파일을 시계가 다른 서버에서 읽으면 그 차이만큼 키가 일찍 또는 늦게 만료된다고 추론할 수 있습니다. 재현해 확인하지는 않았습니다.

## 복제와 영속성이 맞물리면 데이터가 통째로 사라질 수 있습니다

### 영속성을 끈 주 서버가 자동으로 다시 시작하면

복제는 쓰기를 받는 주 서버가 데이터 변경을 복제본에 보내, 복제본이 같은 데이터를 갖게 하는 기능입니다. 복제본이 있으니 주 서버의 영속성은 꺼도 된다고 생각하기 쉽습니다. 공식 문서는 이 구성에서 다음 일이 생길 수 있다고 경고합니다(replication "Safety of replication when master has persistence turned off").

1. 영속성을 끈 주 서버 A와 복제본 B, C가 있습니다.
2. A가 죽고, 자동 재시작 도구가 A를 바로 다시 띄웁니다. 영속성이 없고 읽을 `dump.rdb`도 없으므로 A는 빈 상태입니다.
3. B와 C는 A에 다시 연결해 A의 데이터를 받아 옵니다. A가 비어 있으므로 **B와 C의 데이터도 지워집니다.**

Sentinel로 장애 조치를 하더라도, A가 Sentinel이 알아채기 전에 빨리 재시작되면 같은 일이 생길 수 있습니다. 공식 문서의 권고는 주 서버와 복제본 모두 영속성을 켜거나, 그럴 수 없다면 자동 재시작을 끄는 것입니다.

### 장애 조치로 응답한 쓰기를 잃는 것은 영속성 설정과 별개입니다

Redis 복제는 기본으로 비동기입니다. 주 서버는 복제본이 받았는지 기다리지 않고 응답합니다. 그래서 주 서버가 응답한 쓰기가 복제본에 닿기 전에 장애 조치가 일어나면 그 쓰기를 잃습니다(공식 문서 replication). 예시에서 주 서버가 C의 `DECR`에 응답한 직후 서버째 사라지고 복제본이 새 주 서버가 되면, `appendfsync always`였어도 새 주 서버의 재고는 8일 수 있습니다. 주 서버의 디스크에 남긴 것은 새 주 서버에 아무 영향이 없기 때문입니다.

이 위험을 줄이는 명령이 둘 있습니다. 둘 다 그 연결이 지금까지 보낸 쓰기를 기준으로 기다리며, 시간 제한이 다 되면 그때까지 확인된 수를 돌려줍니다.

- `WAIT`: 지정한 수의 복제본이 쓰기를 받았다고 확인할 때까지 기다립니다.
- `WAITAOF`: 이 서버의 AOF와 지정한 수의 복제본 AOF에 `fsync`됐다고 확인할 때까지 기다립니다. AOF가 꺼진 서버에서 이 서버 쪽 확인을 요구하면 오류이고, 복제본에서는 쓸 수 없습니다(공식 문서 waitaof).

`WAIT`은 확인한 복제본 수 하나를, `WAITAOF`는 [이 서버의 확인 수(0 또는 1), 확인한 복제본 수] 두 값을 돌려줄 뿐 실패를 오류로 알리지 않으므로, 앱이 각 값을 요구한 수와 비교해야 합니다. 쓰기를 보낸 그 연결에서 호출해야 하고, `MULTI`나 스크립트 안처럼 기다릴 수 없는 곳에서는 기다리지 않고 지금까지 확인된 수를 바로 돌려줍니다. 또 스크립트(`redis.set_repl`)나 모듈이 쓰기를 AOF와 복제에 다르게 보내면 `WAITAOF`의 결과가 실제와 다를 수 있습니다(공식 문서 waitaof).

예를 들어 결제 확정처럼 잃으면 안 되는 쓰기만 `WAITAOF`로 확인하고, 나머지는 `everysec`에 맡기는 식으로 비용을 쓰기별로 나눌 수 있습니다. 대가는 그 쓰기의 응답 지연입니다. 그리고 공식 문서는 `WAIT`도 Redis를 강한 일관성 시스템으로 만들지는 않으며, 장애 조치 때 확인된 쓰기를 잃을 가능성을 크게 줄일 뿐이라고 밝힙니다. 복제와 장애 조치의 세부는 이 문서의 범위 밖입니다.

## 데이터와 쓰기가 늘면 비용이 어떻게 커지는가

| 늘어나는 것 | 커지는 비용 | 누가 언제 내는가 | 다른 요청에 영향 |
| --- | --- | --- | --- |
| 메모리 사용량 | `fork` 시간(페이지 테이블 복사) | 메인 스레드, RDB 저장·AOF 다시 쓰기·전체 동기화 시작 때 | 있음. 그동안 모든 명령이 멈춤 |
| 메모리 사용량 | 자식이 파일을 쓰는 시간 → 그동안 복사되는 페이지 | 커널, 자식이 사는 동안 메인 스레드가 쓸 때 | 메모리가 모자라면 `fork` 실패·강제 종료 |
| 쓰기 양과 흩어짐 | copy-on-write로 복사되는 페이지 수. 최악이면 메모리 두 배 | 위와 같음 | 위와 같음 |
| 데이터 크기 | RDB 한 번에 쓰는 양. 바뀐 양과 무관하게 전체 | 자식 프로세스 | 디스크를 함께 쓰는 AOF `fsync`가 느려질 수 있음 |
| 쓰기 양 | AOF 크기와 다시 쓰기 빈도 | 메인 스레드(`write`), 자식(다시 쓰기) | 다시 쓰기마다 `fork` |
| 데이터 크기 + AOF 증분 크기 | 재시작 때 읽는 시간 | 메인 스레드, 시작 때 | 그동안 `LOADING` 오류 |
| 저장 장치 지연 | `always`면 명령 지연, `everysec`면 쓰기 미룸과 손실 범위 | 메인 스레드 또는 백그라운드 스레드 | `always`면 모든 클라이언트의 지연 |

명령의 실행 시간과 클라이언트가 본 지연은 다릅니다. `GET` 하나의 실행 시간은 그대로여도, 그 순간 메인 스레드가 `fork`나 `always`의 `fsync`로 멈춰 있었다면 클라이언트는 그만큼 더 기다립니다. 영속성 때문에 생기는 지연은 대부분 이런 **기다림**으로 나타납니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 처음 다룬 곳 |
| --- | --- | --- |
| Redis는 기본으로 영속성이 없다 | 기본값은 RDB 켬(기본 저장 조건), AOF 끔입니다 | 영속성을 끄면 |
| RDB는 몇 분마다 저장한다 | 기본 조건에서 쓰기가 100번 미만이면 3600초가 지나야 저장합니다. 쓰기가 적을수록 잃는 시간이 길 수 있습니다 | RDB: 언제 저장하는가 |
| RDB 파일에는 저장이 끝난 시점의 데이터가 있다 | `fork`한 시점의 데이터입니다 | 배경 지식, RDB |
| RDB 저장 도중 장애가 나면 파일이 깨진다 | 임시 파일에 쓰고 `rename`하므로, 파일 시스템이 장애 후에도 `rename`의 원자성을 지킨다는 전제(미검증)에서 `dump.rdb`가 반쯤 쓰인 파일이 되지 않습니다. `rename` 전이면 직전 스냅숏이고, 프로세스 장애라면 `rename` 뒤에는 새 스냅숏입니다. 전원 장애라면 디렉터리 `fsync`가 끝나기 전까지는 둘 중 하나입니다 | RDB: 어떻게 저장하는가 |
| `everysec`이면 어떤 장애에도 최대 1초만 잃는다 | 1초는 정전 기준의 보통 값입니다. 디스크가 느리면 늘고, 프로세스만 죽으면 보통 잃지 않으며, 서버 소실에는 전부 잃습니다 | appendfsync 세 가지 |
| AOF를 켜면 프로세스가 죽어도 아무것도 잃지 않는다 | `io-threads` 기본값에서는 보통 그렇습니다. 하지만 `everysec`에서 `write`를 미루는 동안, `everysec`·`no`에서 `write`가 실패한 바퀴, 그리고 I/O 스레드를 켠 `everysec`·`no`에서는 응답한 쓰기가 프로세스 메모리에만 있을 수 있습니다(소스 해석) | 명령 하나가 디스크에 닿기까지, everysec에서 디스크가 느리면, 디스크 쓰기가 실패하면 |
| `always`면 장애 조치에도 안전하다 | 주 서버 디스크에 있을 뿐, 비동기 복제로 새 주 서버에는 없을 수 있습니다 | 복제와 영속성 |
| 설정 파일에서 `appendonly yes`로 바꾸고 재시작하면 AOF로 전환된다 | AOF가 없으니 빈 상태로 시작합니다. 실행 중에 `CONFIG SET`으로 켜야 합니다 | 다시 시작하면 무엇을 읽는가 |
| 디스크가 차도 Redis는 메모리에서 계속 동작한다 | 기본 설정에서는 쓰기와 `PING`을 `MISCONF`로 거부합니다. `always`면 프로세스가 끝납니다 | 디스크 쓰기가 실패하면 |
| 깨진 AOF는 `redis-check-aof --fix`로 고치면 된다 | 깨진 지점부터 끝까지 버릴 수 있습니다. 먼저 백업하고 위치를 확인합니다 | 파일이 잘리거나 깨지면 |
| `FLUSHALL`을 실수로 보내도 `dump.rdb`는 남아 있다 | 저장 조건이 있으면 `FLUSHALL` 직후 빈 데이터로 덮어씁니다 | 사람의 실수와 백업 |
| 실수로 지우면 복제본에서 되살리면 된다 | `FLUSHALL`·`FLUSHDB`는 복제본에도 반드시 전파되어 복제본도 지워집니다 | 사람의 실수와 백업 |
| 백업한 `dump.rdb`를 넣고 재시작하면 복구된다 | AOF가 켜져 있으면 무시되고, 실행 중에 넣고 정상 종료하면 덮어써집니다 | 사람의 실수와 백업 |
| 재시작하면 TTL이 저장 시점의 남은 시간부터 다시 흐른다 | 만료 시각은 절대 시각으로 저장되므로, 내려가 있던 시간만큼 줄어 있거나 이미 사라졌습니다 | 사람의 실수와 백업 |
| 복제본이 있으니 주 서버 영속성은 꺼도 된다 | 자동 재시작된 빈 주 서버가 복제본까지 지울 수 있습니다 | 복제와 영속성 |

## 실무 포인트

### 어떤 설정을 고를까

먼저 **Redis에 있는 데이터의 원본이 어디인가**를 정합니다. 그다음 잃어도 되는 범위를 장애 종류별로 정합니다.

| 데이터 성격 | 고를 설정 | 남는 위험과 대가 |
| --- | --- | --- |
| 원본이 DB에 있는 캐시 | 영속성 끔 또는 RDB | 재시작 직후 캐시 미스가 DB로 몰립니다. 복제 구성이면 영속성을 끈 주 서버의 자동 재시작을 막아야 합니다 |
| 몇 분~한 시간 잃어도 되는 상태 | RDB(저장 조건을 쓰기량에 맞게 조정) | 기본 조건이면 쓰기가 적을 때 한 시간 넘게 잃을 수 있습니다. 3600초는 마지막 저장이 끝난 뒤 다음 저장을 시작하는 조건일 뿐 손실의 상한이 아닙니다. 스냅숏에는 저장이 끝난 시점이 아니라 `fork`한 시점의 데이터가 담기고, 다음 저장도 끝나기까지 시간이 걸리며, 저장이 실패하면 간격이 더 벌어집니다. 저장마다 `fork`와 전체 쓰기 |
| 1초 안팎 잃어도 되는 상태(재고, 세션, 작업 큐) | AOF `everysec` + RDB | 공식 문서가 권하는 조합입니다. 디스크가 느리면 손실 범위가 늘어납니다. `dump.rdb`는 서버 밖 백업용입니다. AOF를 켜면 시작할 때 `dump.rdb`는 읽지 않으며, 재시작이 빠른 것은 AOF 기준 파일이 RDB 형식이기 때문입니다 |
| 응답한 쓰기를 정전에도 잃으면 안 됨 | AOF `always`, 또는 중요한 쓰기에만 `WAITAOF` | `always`는 저장 장치 지연이 모든 명령의 지연이 됩니다. `no-appendfsync-on-rewrite yes`면 `always`도 자식이 일하는 동안 `fsync`를 건너뛰고, `WAITAOF`는 반환값을 확인해야 의미가 있습니다. 둘 다 저장 장치가 `fsync` 완료를 지킨다는 전제 위에 있습니다. 그래도 서버 소실과 장애 조치는 따로 대비해야 합니다. 이 수준이 필요하면 Redis를 유일한 원본으로 둘지부터 다시 검토합니다 |

어떤 설정이든 저장 장치·서버 소실은 막지 못합니다. 복제본, 그리고 서버 밖으로 옮긴 RDB 백업이 필요합니다. 사람의 실수(`FLUSHALL` 등)는 복제본도 따라 하므로, 실수 대비는 다시 쓰기 전의 AOF와 서버 밖 백업이 맡습니다.

### 중요도별 점검 항목

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | 데이터의 원본과 허용 손실을 장애 종류별로 적기 | "Redis가 죽으면 1초 잃는다"는 어떤 장애인지 빠지면 판단에 쓸 수 없습니다 |
| 필수 | 메모리 한도를 데이터 크기 + copy-on-write 여유로 잡기 | 저장 중 메모리가 두 배 가까이 될 수 있고, 모자라면 `fork` 실패(쓰기 거부)나 강제 종료로 이어집니다 |
| 필수 | AOF를 켤 때 실행 중에 `CONFIG SET`으로 켜고 다시 쓰기 완료를 확인 | 설정 파일만 바꾸고 재시작하면 빈 상태로 시작합니다 |
| 필수 | `MISCONF`를 받았을 때의 동작 정하기 | 영속화가 실패하는 동안(디스크 문제, `fork` 실패 등) 모든 쓰기가 실패합니다. 재시도로는 풀리지 않습니다 |
| 필수 | 영속성을 끈 주 서버의 자동 재시작 금지 | 빈 주 서버가 복제본을 지웁니다 |
| 필수 | 앱·일상 운영 계정에서 `FLUSHALL`·`FLUSHDB`를 명령 단위로 빼기(ACL의 `-flushall -flushdb`), 복구용 관리자 계정은 따로 두기 | 두 명령 모두 복제본에 전파되고, `FLUSHALL`은 저장 조건이 있으면 `dump.rdb`까지 곧바로 빈 데이터로 덮어씁니다. 서버가 명령을 거부하게 하는 것이 가장 싼 대비입니다. 두 명령이 속한 `@dangerous` 분류째 빼면 `INFO`, `KEYS`, 그리고 관리 명령인 `CONFIG SET`·`SHUTDOWN`·`BGREWRITEAOF`도 함께 막힙니다. 그러면 Spring의 캐시 비우기·헬스 체크와 이 문서의 백업·복구 절차가 실패합니다 |
| 필수 | 서버 밖 백업과 복구 절차를 미리 정하기 | AOF를 켠 서버에 `dump.rdb`만 넣으면 무시되고, 실행 중에 넣으면 종료 저장이 덮어씁니다. 사고 중에 처음 해 보면 틀리기 쉽습니다. 미리 해 보며 백업 가져오기·로딩·확인에 걸리는 시간을 재고, 허용 중단 시간보다 길면 복제본 같은 다른 대비를 함께 둡니다 |
| 필수 | 데이터 디렉터리(`dir`)가 컨테이너·인스턴스를 교체해도 남는 저장소인지 확인 | 교체 때 함께 사라지는 저장소에 있으면 RDB·AOF 설정과 상관없이 재시작 뒤 빈 상태로 시작합니다 |
| 알면 유리 | `aof-timestamp-enabled` | 시각을 지정해 AOF를 되돌릴 수 있습니다. AOF 형식이 바뀌므로 AOF를 읽는 다른 도구와의 호환을 먼저 확인합니다 |
| 알면 유리 | 정상 종료의 RDB 저장 시간과 오케스트레이터 유예 시간 비교 | 유예 시간이 짧으면 정상 종료가 강제 종료가 됩니다 |
| 알면 유리 | `vm.overcommit_memory`와 THP 설정 | overcommit은 `fork` 실패 방식을 좌우합니다. THP(Transparent Huge Pages)는 커널이 기본 페이지 여러 개를 큰 페이지 하나로 묶어 쓰게 하는 기능이라, 커널 버전에 따라 copy-on-write의 복사 단위가 커져 복사량에 영향을 줄 수 있습니다. 공식 문서는 overcommit 1, THP 끄기를 권합니다. Redis는 커널의 THP 설정이 `always`이면 자기 프로세스의 THP를 스스로 끕니다(Linux에서 끄기에 성공할 때, `disable-thp` 기본값 `yes`) |
| 알면 유리 | 깨진 AOF를 고치기 전에 백업 | `--fix`가 대량의 데이터를 버릴 수 있습니다 |
| 참고 | `no-appendfsync-on-rewrite` | 지연을 줄이는 대신 자식이 일하는 동안 내구성이 `no`가 됩니다 |
| 참고 | `WAITAOF` | 쓰기마다 내구성 수준을 다르게 줄 수 있습니다 |

### 관찰할 것

- **`INFO persistence`**: `aof_last_write_status`가 `err`이면 쓰기 거부 상태입니다. `rdb_last_bgsave_status`가 `err`이면, 저장 조건이 있고 `stop-writes-on-bgsave-error`가 `yes`일 때 쓰기 거부 상태입니다. `rdb_changes_since_last_save`와 `rdb_last_save_time`(마지막으로 성공한 저장이 끝난 시각)은 지금 장애가 나면 RDB로는 얼마나 잃는지 가늠하게 해 줍니다. 어떤 키를 잃는지까지는 알려 주지 않습니다. `aof_last_bgrewrite_status`와 `aof_rewrites_consecutive_failures`는 다시 쓰기가 계속 실패하는지(`fork` 실패처럼 자식을 띄우기 전의 실패는 뒤의 값에 세지 않으므로 앞의 값과 로그를 함께 봅니다), `aof_delayed_fsync`가 늘거나 `aof_pending_bio_fsync`가 계속 1이면 디스크가 `fsync`를 따라가지 못한다는 뜻입니다. `aof_pending_bio_fsync`가 잠깐 1인 것은 정상입니다. `rdb_last_cow_size`, `aof_last_cow_size`, `current_cow_size`는 저장 중 복사된 메모리입니다. `rdb_last_load_keys_expired`는 마지막으로 RDB 파일을 읽을 때 만료되어 건너뛴 키 수입니다. 로딩을 시작할 때마다 0으로 돌아가고 AOF를 읽을 때는 만료 키를 건너뛰지 않으므로, AOF로 시작한 서버에서는 늘 0입니다.
- **`INFO stats`의 `latest_fork_usec`**: 마지막 `fork`에 걸린 시간입니다. 데이터가 늘면서 함께 늘어나는지 봅니다.
- **로그**: "Asynchronous AOF fsync is taking too long", "Background saving error", "Can't save in background: fork", "Error writing to the AOF file", "short read while loading the AOF file"(재시작 때 끝이 잘렸거나 끝나지 않은 `MULTI`를 발견해 잘라 내기를 시도한다는 뜻. 잘라 내기에 성공했는지는 이어지는 "AOF … loaded anyway because aof-load-truncated is enabled"로 확인합니다. 실제 줄은 "!!! Warning: short read while loading the AOF file …"처럼 시작합니다).
- **`LATENCY` 이벤트**: `fork`, `aof-write-pending-fsync`, `aof-fsync-always` 같은 이벤트로 영속성이 만든 지연을 따로 볼 수 있습니다. 단, `latency-monitor-threshold` 기본값이 0(끔)이라 먼저 밀리초 임계값을 설정해야 기록됩니다.
- **디스크 여유 공간**: RDB 임시 파일과 AOF 다시 쓰기는 기존 파일 옆에 새 파일을 만들므로, 그 크기만큼 여유가 더 필요합니다.

### 증상과 대응

| 증상 | 의심할 원인 | 확인 | 대응과 부작용 |
| --- | --- | --- | --- |
| 쓰기와 `PING`이 `MISCONF`로 실패, 읽기는 됨 | RDB 저장 실패(디스크 부족, 권한, `fork` 실패) 또는 AOF 쓰기 실패 | `INFO persistence`의 두 status, 로그, 디스크 여유 | 원인을 고치면 보통 자동으로 풀립니다. 다만 AOF의 백그라운드 `fsync` 실패는 새로 쓸 내용이 없으면 다시 시도하지 않아 거부가 남을 수 있습니다(소스 해석). `stop-writes-on-bgsave-error no`는 RDB 저장 실패에만 듣고, AOF 쓰기 실패의 거부는 풀지 못합니다. RDB 쪽을 이 설정으로 급히 풀면 쓰기는 되지만 새 변경이 RDB에 남지 않는 상태를 놓칠 수 있습니다 |
| Redis가 갑자기 끝나고 로그에 AOF 쓰기·`fsync` 오류 | `appendfsync always`에서 디스크 오류 | 로그, 디스크 상태 | 디스크를 고친 뒤 재시작합니다. 응답한 쓰기는 잃지 않았지만 재시작까지 서비스가 멈춥니다 |
| 재시작 뒤 데이터가 통째로 비어 있음 | 설정 파일에서만 AOF를 켬, 영속성 끔, 빈 주 서버에 복제본이 동기화, 데이터 디렉터리가 컨테이너·인스턴스 교체 때 함께 사라지는 저장소에 있음 | 시작 로그("Creating AOF base file"), 설정, 복제 구성, `CONFIG GET dir`의 경로가 어떤 저장소인지 | `dump.rdb`가 덮어써지기 전이면 백업해 복구합니다. 절차를 고칩니다 |
| 재시작 뒤 재고가 늘어나 있음 | 마지막 저장 이후 변경 유실(RDB 간격, `fsync` 범위, 장애 조치) | 장애 종류, 설정, `rdb_last_save_time` | DB의 주문 기록으로 재고를 다시 계산합니다. 원본이 Redis뿐이면 복구할 근거가 없습니다 |
| Redis가 시작하지 않고 AOF·RDB 형식 오류 로그 | 파일 가운데 손상, 잘린 파일이 마지막이 아님, 목록에 있는 파일 없음 | `redis-check-aof`(먼저 `--fix` 없이), `redis-check-rdb` | 파일을 백업한 뒤 고칩니다. `--fix`는 손상 지점 뒤를 버릴 수 있습니다 |
| 주기적으로 모든 명령의 지연이 튐 | `fork`(RDB 저장·AOF 다시 쓰기), `always`의 `fsync`, 디스크 경합 | `latest_fork_usec`, `LATENCY`, 저장 시각과 지연 시각 비교, THP 상태 | 저장 빈도 조정, AOF용 디스크 분리, THP가 켜져 있으면 끄기(공식 문서 권고). 저장을 줄이면 잃는 범위가 늘어납니다 |
| 저장 중 메모리가 급증하거나 Redis가 강제 종료됨 | copy-on-write 복사량, overcommit 설정 | `current_cow_size`, `rdb_last_cow_size`, 커널 로그의 OOM 기록, THP 상태 | 메모리 여유 확보, 저장 시간대의 쓰기 분산. THP가 복사량을 키우는지는 커널 버전에 따라 다르므로 운영 커널에서 확인합니다 |
| 재시작 직후 한동안 `LOADING` 오류 | 데이터 읽는 중 | `INFO persistence`의 `loading` | 앱에서 재시도·대기합니다. 데이터가 클수록 길어집니다. AOF 기준 파일을 RDB 형식으로 두면 빨라집니다 |
| 실수로 `FLUSHALL`이나 대량 삭제를 보냄 | 잘못된 대상 서버, 테스트 코드, 운영 스크립트 | 접속 대상, AOF 증분 파일들(목록 순서) | AOF면 자동 다시 쓰기를 끄고, 서버를 멈추고, AOF를 복사해 둔 뒤 해당 명령부터 지웁니다. 그 뒤의 쓰기도 함께 버릴지 정해야 합니다. RDB만이면 서버 밖 백업으로 돌아가고 그 뒤의 변경은 원본으로 다시 만듭니다 |
| 백업에서 복구했는데 데이터가 백업과 다름 | AOF를 켠 채 시작해 `dump.rdb`를 무시함, 실행 중에 넣은 파일을 종료 저장이 덮어씀 | 시작 로그("DB loaded from append only file" 또는 "DB loaded from disk"), 설정 | Redis를 멈춘 뒤 파일을 넣고, `appendonly no`로 시작한 다음 실행 중에 AOF를 켭니다 |
| 재시작 뒤 세션·락 키가 사라짐 | 내려가 있던 동안 만료 시각이 지남 | 내려가 있던 시간. RDB로 시작했다면 `rdb_last_load_keys_expired`, AOF로 시작했다면 이 값은 늘 0이므로 재시작 뒤 `INFO stats`의 `expired_keys` 증가(재시작 뒤 0부터 세고 평소의 만료와 섞임) | 정상 동작입니다. TTL 키에 기대는 로직은 재시작 뒤 키가 없을 수 있다고 전제합니다 |

### Spring에서 확인할 것

- **`MISCONF`와 `LOADING`은 예외로 옵니다.** Spring Data Redis의 Lettuce 연동은 서버가 돌려준 명령 오류를 `RedisSystemException`으로 바꿉니다. 같은 예외 종류이고 바깥 예외의 메시지도 둘 다 "Error in execution"이므로, 원인 예외의 메시지가 `MISCONF`로 시작하는지 `LOADING`으로 시작하는지 봐야 구분됩니다. `LOADING`은 기다리면 풀리지만, `MISCONF`는 영속화 실패의 원인(디스크 부족·오류, 메모리 부족에 따른 `fork` 실패 등)이 풀릴 때까지 재시도해도 실패합니다. 둘을 같은 재시도 정책에 넣지 않습니다.
- **재시도는 멱등해야 합니다.** 재시작이나 장애 조치 전후로 응답을 받지 못한 쓰기를 다시 보낼 때, Redis 원자성 문서의 "원자성이 보장하지 않는 것"과 같은 이유로 이중 반영이 생길 수 있습니다.
- **재시작 뒤의 정합성 점검을 앱에 둡니다.** Redis가 이전 상태로 돌아갈 수 있다는 전제에서, 재고처럼 원본(주문 DB)으로 다시 계산할 수 있는 값은 재시작 뒤나 주기적으로 맞춰 봅니다. "남은 재고 + 성공 주문 수 = 처음 재고" 같은 불변식이 그 기준입니다.
- **테스트 코드의 `flushAll()`을 조심합니다.** Spring Data Redis의 `RedisServerCommands.flushAll()`은 `FLUSHALL`을 보냅니다. 테스트를 정리하려고 부른 코드가 설정 실수로 공유·운영 Redis를 가리키면 그대로 사고가 됩니다. 앱·테스트 계정의 ACL에서 `-flushall -flushdb`로 두 명령을 빼 두면 서버가 거부합니다. `@dangerous` 분류째 빼면 안 됩니다. Spring Data Redis의 기본 캐시 비우기는 `KEYS`를 쓰고, Spring Boot의 Redis 헬스 체크는 `INFO`를 부르는데, 두 명령 모두 이 분류에 들어 있어 함께 실패합니다.
- **영속성은 서버 설정입니다.** Spring Data Redis의 연결 설정이 서버의 RDB·AOF 설정을 바꾸지는 않습니다. `RedisServerCommands.setConfig`로 `CONFIG SET`을 보낼 수는 있지만, 권한(ACL, 관리형 서비스의 명령 제한)이 허용해야 하고, 앱이 서버 설정을 바꾸면 다른 앱의 내구성까지 바뀝니다. 쓰는 Redis(직접 운영, 관리형 서비스)의 설정을 확인해, 앱이 기대하는 내구성과 맞는지 맞춰 봐야 합니다.

## 말로 설명하기

### 30초 버전

Redis는 메모리에 데이터를 두고, RDB와 AOF로 디스크에 남깁니다. RDB는 조건이 되면 `fork`한 자식이 그 순간의 전체 데이터를 파일로 떠 두는 방식이라, 마지막 스냅숏 이후를 통째로 잃습니다. AOF를 켜면 정상 경로에서는 쓰기 명령을 응답 전에 파일에 `write`하고 `fsync` 정책에 따라 디스크에 내리므로, 기본값 `everysec`이면 프로세스만 죽을 때는 보통 잃지 않고 정전 때는 1초 안팎을 잃을 수 있습니다. 단, I/O 스레드를 켜거나, 디스크가 느리거나, `write`가 실패하면 응답한 쓰기가 아직 프로세스 메모리에만 있을 수 있습니다. 어떤 설정도 서버 소실과 비동기 복제의 장애 조치 유실은 막지 못하므로 복제와 백업을 함께 봐야 합니다.

### 2분 버전

기본값은 RDB 켬, AOF 끔입니다. RDB는 "N초 동안 M번 이상 변경" 조건이 되면 메인 스레드가 `fork`하고, 자식이 `fork` 시점의 데이터를 임시 파일에 써서 `fsync`한 뒤 `rename`으로 교체합니다. 그래서 저장 중 장애가 나도 반쯤 쓰인 파일은 남지 않지만(`rename` 전이면 이전 파일, 뒤면 새 파일. 전원 장애라면 디렉터리 `fsync`가 끝나기 전까지는 어느 쪽이 남을지 파일 시스템에 달려 있습니다), 장애 때 마지막 스냅숏 이후를 잃습니다. 기본 조건에서 쓰기가 적으면 한 시간 분량일 수도 있습니다. 대가는 메모리에 비례하는 `fork` 시간과, 저장 중 copy-on-write로 늘어나는 메모리입니다.

AOF는 실행한 쓰기 명령을 버퍼에 모았다가 이벤트 루프마다 응답을 보내기 전에 파일에 `write`합니다. 그래서 `io-threads` 기본값에서는 프로세스만 죽어도 응답한 쓰기가 페이지 캐시에 남아 보존됩니다. I/O 스레드를 켜면 응답이 `write`보다 먼저 나갈 수 있어 이 보장이 약해집니다(`everysec`·`no`는 소스로 확인한 해석, `always`와의 조합은 미확인). 정전에 대비하는 정도는 `appendfsync`가 정합니다. `always`는 응답 전에 매번 `fsync`해서 응답한 쓰기를 잃지 않지만 디스크 지연이 모든 명령의 지연이 되고, `everysec`은 백그라운드 스레드가 1초마다 `fsync`해 보통 1초 안팎을 잃을 수 있고, `no`는 운영체제에 맡겨 수십 초를 잃을 수 있습니다. `everysec`에서 디스크가 느리면 `write`를 최대 2초 미루는데, 그 사이 응답한 쓰기는 프로세스 메모리에만 있어 손실 범위가 늘어납니다. AOF는 커지므로 자식이 새 기준 파일을 만들고, 파일이 기준·증분·목록 파일로 나뉘어 있어, 이미 AOF를 쓰던 서버라면 다시 쓰기가 실패해도 안전합니다.

비정상 상황에서의 태도도 알아야 합니다. 디스크 쓰기가 실패하면 기본 설정에서 그다음 쓰기 명령과 `PING`을 `MISCONF`로 거부하고(AOF `write`가 실패한 바퀴의 쓰기는 이미 응답이 나가 버퍼에만 있습니다), `always`면 프로세스를 끝냅니다. AOF 끝이 잘렸으면 잘라 내고 시작하지만, 가운데가 깨졌으면 시작하지 않습니다. 설정 파일에서만 AOF를 켜고 재시작하면 AOF만 읽으려다 빈 상태로 시작합니다. 영속성을 끈 주 서버가 자동 재시작되면 빈 데이터가 복제본까지 지울 수 있고, 비동기 복제라 장애 조치 때는 디스크 설정과 상관없이 응답한 쓰기를 잃을 수 있습니다. 마지막으로 사람의 실수는 따로 봐야 합니다. `FLUSHALL`은 복제본에 전파되고 저장 조건이 있으면 `dump.rdb`까지 빈 데이터로 덮어쓰므로, 되살릴 근거는 다시 쓰기 전의 AOF와 서버 밖 백업뿐입니다.

### 예상 질문과 꼬리 질문

**Q. RDB와 AOF의 차이는 무엇인가요?**
RDB는 조건이 될 때 그 시점의 전체 데이터를 파일 하나로 떠 두고, AOF는 실행한 쓰기 명령을 계속 덧붙입니다. 같은 데이터라면 RDB 파일이 보통 더 작고 데이터가 클 때 재시작도 보통 더 빠르며 백업에 좋지만, 마지막 스냅숏 이후를 잃습니다. AOF는 `fsync` 정책에 따라 잃는 범위를 1초 안팎까지 줄일 수 있지만, 파일이 보통 더 크고 다시 쓰기가 필요합니다. 공식 문서는 데이터가 중요하면 둘을 함께 쓰라고 권합니다. (본문: "RDB는 정해 둔 조건마다", "AOF는 실행한 쓰기를 로그로 덧붙이고")

- **꼬리: 둘 다 켜면 재시작 때 무엇을 읽나요?**
  AOF만 읽습니다. 더 최근까지의 변경을 담고 있기 때문입니다. RDB 파일은 백업과 복구용으로 남습니다.
- **꼬리: RDB에는 언제의 데이터가 들어 있나요?**
  저장이 끝난 시점이 아니라 `fork`한 시점의 데이터입니다. 자식은 copy-on-write로 `fork` 순간의 메모리를 계속 봅니다.

**Q. RDB 저장은 어떻게 서비스를 멈추지 않고 전체 데이터를 떠 두나요?**
메인 스레드가 `fork`하면 Linux는 데이터를 복사하지 않고 페이지 테이블을 복사해 페이지를 공유합니다. 자식은 그 페이지들을 읽어 파일을 쓰고, 메인 스레드는 바로 명령을 처리합니다. 메인 스레드가 어떤 페이지에 쓰면 그 페이지만 복사되므로 자식은 `fork` 순간의 값을 계속 봅니다. (본문: "어떻게 저장하는가")

- **꼬리: 그럼 공짜인가요?**
  아닙니다. `fork` 자체가 메모리가 클수록 길어지는 시간 동안 메인 스레드를 멈추고, 저장 중 쓰인 페이지만큼 메모리가 늘어납니다. 쓰기가 많고 흩어져 있으면 두 배 가까이 될 수 있습니다.
- **꼬리: 메모리가 모자라면요?**
  `fork`가 실패하면 저장 실패로 기록되고, 기본 설정에서는 쓰기 명령을 `MISCONF`로 거부합니다. overcommit을 1로 두면 메모리 약속 검사로는 `fork`가 거절되지 않지만, 실제 메모리가 바닥나면 커널이 Redis를 강제 종료할 수 있습니다.

**Q. `appendfsync everysec`이면 장애 때 정확히 무엇을 잃나요?**
장애 종류에 따라 다릅니다. Redis 프로세스만 죽으면, `io-threads` 기본값에서는 응답한 쓰기가 응답 전에 `write`되어 페이지 캐시에 있으므로 보통 잃지 않습니다. I/O 스레드를 켰다면 응답이 `write`보다 먼저 나갈 수 있어 이 경우에도 잃을 수 있습니다. `write`가 실패한 바퀴의 쓰기도 응답은 나가지만 버퍼에만 있어 같은 위험이 있습니다. 정전이나 운영체제 장애면 마지막으로 끝난 `fsync` 이후를 잃을 수 있는데, 그 범위는 보통 1초 안팎입니다. 운영체제가 그사이 스스로 내려 쓴 부분은 남을 수도 있지만, 장담할 수 있는 것은 `fsync`가 끝난 부분뿐입니다. 서버나 디스크를 잃으면 그 서버의 데이터는 전부 잃습니다. (본문: "appendfsync 세 가지")

- **꼬리: 1초보다 많이 잃을 수도 있나요?**
  네. 디스크가 바빠 백그라운드 `fsync`가 늦으면 마지막 `fsync` 이후가 길어집니다. 또 `fsync`가 진행 중이면 `write`를 최대 2초 미루는데, 소스를 보면 그 사이에도 응답은 나가므로 그동안 프로세스가 죽으면 응답한 쓰기를 잃을 수 있습니다. `aof_delayed_fsync`와 "Asynchronous AOF fsync is taking too long" 로그로 이 상황을 확인합니다.
- **꼬리: `always`는 왜 느린가요?**
  메인 스레드가 응답 전에 `fsync`를 기다리기 때문입니다. 한 바퀴의 쓰기를 모아 한 번에 `fsync`하는 그룹 커밋으로 줄이지만, 저장 장치가 느려지면 그 시간이 모든 클라이언트의 지연이 됩니다.

**Q. 디스크가 가득 차면 Redis는 어떻게 되나요?**
기본 설정에서는 쓰기 명령과 `PING`을 `MISCONF` 오류로 거부하고, 읽기는 계속 처리합니다. RDB 저장이 실패한 경우와 AOF 쓰기가 실패한 경우 모두 그렇습니다. 다만 AOF `write`가 처음 실패한 바퀴에서 이미 실행한 쓰기는 성공 응답이 나가고, 거부는 그다음 명령부터입니다. 그 쓰기는 AOF 버퍼에만 있어 재시도가 성공하기 전에 프로세스가 죽으면 잃습니다. 원인이 풀리면 보통 자동으로 쓰기를 다시 받습니다. AOF `write` 실패는 `write` 재시도가 성공하는 순간 풀립니다. AOF의 백그라운드 `fsync` 실패는 따로 기록되어 그 뒤의 백그라운드 `fsync`가 성공해야 풀리는데, 새로 쓸 내용이 없으면 다시 시도하지 않는 경로가 있습니다(소스 해석). RDB는 저장 조건을 만족하고 마지막 시도에서 5초가 넘게 지나 다시 시도한 저장이 성공해야 풀립니다. `appendfsync always`라면 쓰기나 `fsync` 실패 때 프로세스를 끝냅니다. (본문: "디스크 쓰기가 실패하면 Redis는 쓰기 명령을 거부합니다")

- **꼬리: 왜 쓰기를 거부하나요? 메모리에는 쓸 수 있잖아요.**
  쓰기를 계속 받으면서 디스크에는 남기지 못하면, 다음 장애 때 그 쓰기를 모두 잃는데 아무도 모릅니다. Redis는 이를 쓰기 실패로 드러내는 쪽을 기본으로 택했습니다. RDB 저장 실패에 대해서는 `stop-writes-on-bgsave-error no`로 바꿀 수 있지만, 그러면 영속화 실패를 지표로 따로 지켜봐야 합니다. AOF 쓰기 실패의 거부는 이 설정으로 풀리지 않습니다.
- **꼬리: `always`에서 끝나 버리면 응답한 쓰기를 잃나요?**
  아닙니다. `io-threads` 기본값에서 `always`는 `write`와 `fsync`가 끝나야 응답하므로, 실패한 쓰기에는 아직 응답하지 않았습니다. 대신 재시작까지 서비스가 멈춥니다.

**Q. AOF 파일이 깨지면 어떻게 하나요?**
마지막 파일의 끝만 잘렸다면 기본 설정(`aof-load-truncated yes`)에서 마지막 온전한 명령까지 잘라 내고 시작합니다. 가운데가 깨졌거나 잘린 파일이 마지막이 아니면 시작하지 않습니다. 그때는 파일을 백업하고 `redis-check-aof`를 먼저 `--fix` 없이 돌려 위치를 확인합니다. `--fix`는 깨진 지점부터 끝까지 버릴 수 있어 손상이 앞쪽이면 대량으로 잃습니다. (본문: "파일이 잘리거나 깨지면")

- **꼬리: 끝이 잘리는 일은 언제 생기나요?**
  `redis.conf`는 운영체제가 멈출 때 생기고, Redis 프로세스만 죽을 때는 생기지 않는다고 설명합니다. 디스크가 가득 차 일부만 쓴 경우에도 생길 수 있는데, Redis는 일부 쓰기를 발견하면 잘라 내려고 시도합니다.

**Q. RDB만 쓰던 서버에 AOF를 켜려면 어떻게 하나요?**
실행 중인 서버에 `CONFIG SET appendonly yes`를 보내 지금 메모리의 데이터로 첫 기준 파일을 만들게 하고, 다시 쓰기가 끝난 것을 확인한 뒤 설정 파일에 반영합니다. 설정 파일만 바꾸고 재시작하면, AOF가 켜져 있으니 AOF만 읽으려는데 파일이 없어서 빈 상태로 시작합니다. 이어서 RDB 저장이 일어나면 `dump.rdb`까지 덮어써집니다. (본문: "설정 파일에서 AOF만 켜고 재시작하면 데이터가 사라집니다")

**Q. 정상 종료하면 데이터를 잃지 않나요?**
정상 종료에서는 AOF를 `fsync`하고, 저장 조건이 있으면 RDB를 동기로 저장한 뒤 끝냅니다. RDB 저장에 실패하거나 첫 AOF 다시 쓰기가 진행 중이면 끝내지 않습니다. 하지만 AOF의 `write`나 `fsync`가 실패하면(`always`가 아닐 때) 경고만 남기고 끝내므로, RDB 저장 조건 없이 AOF만 쓰는 구성에서 디스크가 가득 찬 채 종료하면 버퍼에 남은 쓰기를 잃을 수 있습니다. 저장이 모두 성공하면 정상 종료 자체로는 잃지 않습니다. 다만 RDB 저장은 데이터가 클수록 오래 걸려, 오케스트레이터의 유예 시간을 넘기면 강제 종료되어 마지막 스냅숏 이후를 잃습니다. (본문: "종료 방식에 따라 남는 것이 다릅니다")

- **꼬리: `SHUTDOWN NOSAVE`는요?**
  RDB 저장만 건너뜁니다. AOF가 켜져 있으면 AOF는 `write`하고 `fsync`하므로, 그것이 성공하면 AOF 기준으로는 잃지 않습니다. AOF가 꺼져 있으면 마지막 스냅숏 이후를 잃습니다.

**Q. 실수로 `FLUSHALL`을 실행했습니다. 되살릴 수 있나요?**
AOF를 켜 두었고 실수 뒤에 시작한 다시 쓰기가 성공하지 않았다면 됩니다. 기준은 `FLUSHALL`이 목록에 오른 증분 파일에 아직 남아 있는가입니다. 실수 전에 시작해 실수 뒤에 끝난 다시 쓰기는 실수 전 데이터로 기준 파일을 만들므로 괜찮습니다. 자동 다시 쓰기를 끄고, 진행 중이거나 예약된 다시 쓰기가 있으면 끝나기를 기다리지 말고 바로 서버를 멈춘 뒤(복제본이 있으면 복제본을 기다리는 동안 다시 쓰기가 끝날 수 있으므로 `SHUTDOWN NOW`), AOF 디렉터리를 복사해 둡니다. 그리고 목록 파일 순서대로 증분 파일에서 `FLUSHALL`을 찾아 그 뒤의 명령까지 모두 지우고 재시작합니다. 실패한 다시 쓰기가 있었다면 `FLUSHALL`은 마지막 증분 파일이 아닐 수 있습니다. RDB만 썼다면 저장 조건이 있는 한 `FLUSHALL` 직후 `dump.rdb`가 빈 데이터로 덮어써지므로, 서버 밖 백업만 남습니다. (본문: "사람의 실수와 백업: 지운 데이터를 되살릴 수 있는가")

- **꼬리: 복제본에서 가져오면 되지 않나요?**
  안 됩니다. `FLUSHALL`은 데이터가 이미 비어 있어도 복제본과 AOF에 반드시 전파되므로 복제본도 지워집니다. 복제는 장비 장애에 대비한 사본이지, 실수에 대비한 사본이 아닙니다.
- **꼬리: 특정 시각으로 되돌릴 수 있나요?**
  `aof-timestamp-enabled`를 켜 두었다면 `redis-check-aof --truncate-to-timestamp`로 그 시각 이후를 잘라 낼 수 있습니다. 시각 표시가 초 단위이고, 마지막 파일 안에서만 자를 수 있어 마지막 다시 쓰기 이전으로는 돌아가지 못합니다.
- **꼬리: 애초에 막으려면요?**
  앱과 일상 운영 계정의 ACL에서 `-flushall -flushdb`처럼 두 명령을 뺍니다. 그러면 서버가 명령을 거부합니다. 두 명령이 속한 `@dangerous` 분류째 빼면 `INFO`, `KEYS`, `CONFIG SET`, `SHUTDOWN`까지 막혀 헬스 체크, 캐시 비우기, 백업·복구 절차가 실패하므로, 복구는 따로 둔 관리자 계정으로 합니다. 다만 ACL 규칙은 적힌 순서대로 적용되므로 뒤에 `+@all` 같은 규칙이 있으면 다시 허용됩니다. `ACL DRYRUN`으로 실제로 거부되는지 확인합니다.

**Q. 백업한 `dump.rdb`로 복구하려면 어떻게 하나요?**
먼저 Redis를 멈추고 파일을 넣습니다. 실행 중에 넣고 정상 종료하면 종료 때의 RDB 저장이 넣은 파일을 덮어씁니다. 그리고 AOF가 켜진 설정으로 시작하면 AOF만 읽어 넣은 파일이 무시됩니다. 그래서 `appendonly no`로 시작해 RDB를 읽고 확인한 뒤, 실행 중에 `CONFIG SET appendonly yes`로 AOF를 켭니다. 이 순서는 소스의 시작 규칙과 공식 문서의 전환 절차를 이어 붙인 것이며, 직접 수행해 확인하지는 않았습니다. (본문: "복구: AOF를 켠 서버에 dump.rdb만 넣으면 무시됩니다")

- **꼬리: AOF는 어떻게 백업하나요?**
  자동 다시 쓰기를 끄고 진행 중이거나 예약된 다시 쓰기가 없는지 확인한 뒤, `appendonlydir`의 파일을 함께 복사하고 설정을 되돌립니다. 다시 쓰기 중에 복사하면 깨진 백업이 될 수 있습니다.

**Q. Redis를 재시작하면 TTL은 어떻게 되나요?**
만료 시각은 절대 시각으로 저장되므로, 남은 시간은 내려가 있던 시간만큼 줄어 있습니다. 그동안 만료 시각이 지난 키는 재시작 뒤 보이지 않습니다. 주 서버가 RDB를 읽을 때는 그런 키를 아예 올리지 않고 `rdb_last_load_keys_expired`로 셉니다. AOF로 되살린 키는 일단 올라간 뒤 만료 처리로 사라집니다. (본문: "다시 시작하면 만료 시각이 지난 키는 돌아오지 않습니다")

**Q. 복제본이 있으면 주 서버 영속성은 꺼도 되나요?**
위험합니다. 영속성을 끈 주 서버가 죽었다가 자동으로 재시작되면 (남은 `dump.rdb`가 없으면) 빈 상태로 뜨고, 복제본들이 그 빈 데이터를 받아 자기 데이터까지 지웁니다. 공식 문서는 영속성을 켜거나, 끈다면 자동 재시작을 막으라고 권합니다. (본문: "영속성을 끈 주 서버가 자동으로 다시 시작하면")

- **꼬리: 영속성을 켜면 장애 조치 때도 안전한가요?**
  아닙니다. 복제가 비동기라 주 서버가 응답한 쓰기가 복제본에 닿기 전에 장애 조치가 일어나면 잃습니다. 주 서버 디스크에 `fsync`한 것은 새 주 서버와 무관합니다. `WAIT`이나 `WAITAOF`로 중요한 쓰기의 복제·`fsync`를 확인하면 가능성을 크게 줄일 수 있지만, 공식 문서도 강한 일관성을 보장하지는 않는다고 밝힙니다.

**Q. 재고를 Redis에 두고 있는데 재시작 뒤 재고가 늘어났습니다. 원인과 대응은요?**
마지막 저장 이후의 차감이 사라진 것입니다. RDB만 쓰면 마지막 스냅숏 이후, AOF `everysec`이면 정전 때 보통 1초 안팎(디스크가 느렸다면 더 많이), 장애 조치였다면 복제되지 않은 쓰기가 원인입니다. 주문 DB가 원본이라면 주문 기록으로 재고를 다시 계산해 맞추고, 원인에 맞게 영속성 설정이나 중요한 쓰기의 `WAITAOF`를 검토합니다. Redis가 유일한 원본이면 되돌릴 근거가 없으므로, 그 구조부터 다시 검토해야 합니다. (본문: "실무 포인트")

- **꼬리: Spring 앱은 이 상황을 어떻게 알아차리나요?**
  Redis가 예외를 주지 않으므로 앱이 스스로 알 수 없습니다. 재시작 뒤나 주기적으로 "남은 재고 + 성공 주문 수 = 처음 재고" 같은 불변식을 점검해야 드러납니다.

**Q. 영속성 때문에 지연이 튀는 경우는 언제인가요?**
`fork`할 때, `appendfsync always`에서 `fsync`를 기다릴 때, `everysec`에서 `fsync`가 밀려 `write`가 막힐 때입니다. 모두 메인 스레드가 기다리는 동안 다른 명령도 멈추므로, 명령 자체의 실행 시간은 그대로여도 클라이언트가 본 지연이 늘어납니다. `latest_fork_usec`, `LATENCY` 이벤트, `aof_delayed_fsync`로 구분합니다. (본문: "데이터와 쓰기가 늘면 비용이 어떻게 커지는가")

- **꼬리: THP는 왜 끄라고 하나요?**
  공식 문서는 THP가 켜져 있으면 `fork` 뒤 큰 페이지 단위로 복사가 일어나 지연과 메모리 사용이 크게 늘 수 있다고 설명합니다. 다만 큰 페이지를 언제 어떤 단위로 복사하는지는 커널 버전마다 달라서, 실제 영향은 운영 커널에서 재 봐야 압니다. Redis는 커널 설정이 `always`이면 자기 프로세스의 THP를 스스로 끕니다(`disable-thp` 기본값 `yes`, Linux에서 끄기에 성공할 때).

**Q. Spring에서 `MISCONF` 오류는 어떻게 다루나요?**
Spring Data Redis는 이 오류를 `RedisSystemException`으로 줍니다. `LOADING`도 같은 예외로 오고 바깥 예외의 메시지는 둘 다 "Error in execution"이므로, 원인 예외(`getMostSpecificCause()`)의 메시지가 `MISCONF`로 시작하는지 `LOADING`으로 시작하는지로 구분합니다. `LOADING`은 잠시 기다리면 풀리지만, `MISCONF`는 영속화 실패의 원인(디스크, `fork` 실패 등)이 해결될 때까지 재시도해도 실패하므로, 쓰기를 빠르게 실패 처리하고 알림을 보내는 쪽이 맞습니다. (본문: "Spring에서 확인할 것")

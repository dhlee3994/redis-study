# Redis 원자성: 단일 명령, MULTI/EXEC, WATCH, Lua

> **핵심 질문**: 재고 1개에 동시 요청 2개가 오면 왜 둘 다 성공할 수 있는가? 단일 명령, MULTI/EXEC, WATCH, Lua 스크립트는 이 문제를 각각 어떻게 막거나 막지 못하며, 무엇을 대가로 치르는가?
>
> **범위**: 단일 Redis 서버를 기준으로 하고, 클러스터는 키 배치 제약만 다룹니다. 분산 락 알고리즘, 복제·장애 조치 때의 유실 세부, Redis와 DB 사이의 정합성 패턴은 다루지 않습니다.

## 배경 지식

### 이 문서의 예시: 재고 1개, 동시 요청 2개

문서 끝까지 다음 장면 하나를 씁니다.

- Redis에 키 `stock:item:1`이 있고 값은 `"1"`입니다. 자료형은 String입니다.
- 주문 API 서버에 사용자 요청 A와 B가 동시에 들어옵니다. 각 요청 스레드는 Redis와의 연결을 통해 명령을 보냅니다.
- **바라는 결과**: 한 명은 성공, 한 명은 품절, 재고는 0입니다.

```text
 Order API server (JVM)                 Redis server
+--------------------------+         +------------------------+
| request thread A --------|-conn 1->| main thread            |
| request thread B --------|-conn 2->|   runs commands        |
|                          |<-reply--|   one at a time        |
+--------------------------+         |                        |
                                     |   stock:item:1 = "1"   |
                                     +------------------------+
```

그림의 왼쪽은 주문 API 서버(JVM 프로세스), 오른쪽은 Redis 서버(프로세스)입니다. `conn 1`, `conn 2`는 요청 A, B가 쓰는 연결 1, 2이고, `reply`는 응답입니다.

화살표는 네트워크로 명령과 응답이 이동하는 방향입니다. 연결 풀, Redis의 I/O 스레드, 복제본, 디스크 영속화는 그림에서 뺐습니다. I/O 스레드는 바로 아래 "Redis는 명령을 메인 스레드 하나에서 하나씩 끝까지 실행합니다"에서, 복제는 "원자성이 보장하지 않는 것"에서 다룹니다.

### 프로세스·스레드, 경쟁 상태와 원자성

- **프로세스와 스레드**: 주문 API와 Redis는 메모리를 공유하지 않는 별도 프로세스입니다. 그래서 주문 API는 재고 값을 직접 바꾸지 못하고, 명령을 보내 Redis가 바꾸게 합니다. 명령마다 네트워크 왕복이 생기고, 그사이 다른 연결의 명령이 먼저 실행될 수 있습니다. 자세한 원리는 [프로세스와 스레드](../cs/process-and-thread.md)에서 다룹니다.
- **경쟁 상태와 원자성**: 경쟁 상태는 실행 순서에 따라 결과가 틀어지는 문제입니다. 원자성은 여러 단계를 다른 실행 흐름에게 "시작 전" 또는 "끝난 후"로만 보이게 하는 성질입니다. 이 문서는 "재고 확인"과 "차감"을 Redis 안에서 하나의 단위로 묶는 방법을 찾습니다. 원자적 연산 두 개를 이어 붙이면 원자적이지 않다는 점, 원자성에 두 가지 뜻이 있다는 점이 특히 중요합니다. 자세한 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.

### Redis에서 '클라이언트'는 연결 하나입니다

Redis 문서와 소스에서 클라이언트는 애플리케이션 하나가 아니라 **연결 하나**를 뜻합니다. 서버는 연결마다 상태를 따로 둡니다. 예를 들어 MULTI 뒤에 쌓인 명령 대기열과 WATCH 중인 키 목록이 연결별로 있습니다. 이 문서의 MULTI/EXEC와 WATCH는 같은 연결로 보내야만 의미가 있습니다. 예시에서 요청 A는 연결 1, 요청 B는 연결 2를 쓴다고 봅니다.

### Redis는 명령을 메인 스레드 하나에서 하나씩 끝까지 실행합니다

- **한 줄**: Redis 서버 프로세스에서 키와 값을 읽고 바꾸는 명령은 메인 스레드 하나가 실행하고, 명령 하나를 끝낸 뒤에 다음 명령을 시작합니다.
- **비유**: 창구 직원이 한 명인 은행입니다. 직원은 여러 손님(연결)이 맡긴 일을 한 건씩 처리하고, 한 건을 처리하는 동안에는 다른 건을 받지 않습니다. 예시에서 메인 스레드가 A의 명령을 처리하는 동안 B의 명령은 기다립니다.
- **실제로는**:
  - 메인 스레드는 명령이 도착한 연결을 골라 명령을 해석하고 실행합니다. 명령 하나가 끝나야 다음 명령으로 넘어갑니다.
  - I/O 스레드(`io-threads`)를 켜면 소켓 읽기·쓰기와 요청 해석을 다른 스레드가 맡을 수 있습니다. 기본값은 꺼짐입니다. 켜더라도 I/O 스레드는 요청을 다 읽은 연결을 메인 스레드에 넘기고, 명령 실행은 메인 스레드가 합니다.
  - 이 밖에 큰 값 해제나 느린 파일 작업을 맡는 보조 스레드도 있습니다. 보조 스레드는 클라이언트 명령을 실행하지 않습니다.
  - **비유와 다른 점**: 손님 한 명이 여러 건(명령 여러 개)을 맡기면, 건과 건 사이에 다른 손님의 건이 처리될 수 있습니다. 직원은 "건" 단위로만 끼어들기를 막아 줍니다.
- **이 주제에서는**: **명령 하나는 다른 명령과 섞이지 않습니다. 하지만 명령 두 개 사이에는 다른 연결의 명령이 들어올 수 있습니다.** 이 문서의 네 가지 방법은 모두 "재고 확인과 차감을 메인 스레드가 끊지 않고 처리하는 한 덩어리"로 만드는 서로 다른 방법입니다.

Redis 문서가 "원자적(atomic)"이라고 할 때는 주로 **실행 도중 다른 클라이언트의 명령이 끼어들지 않는다**는 뜻입니다. 실패했을 때 되돌린다(롤백)는 뜻이 아닙니다. 이 차이는 MULTI/EXEC와 Lua의 에러 처리에서 다시 확인합니다.

### 왕복과 파이프라이닝

- **왕복(round trip)**: 명령 하나를 보내고 응답을 받기까지의 과정입니다. 명령을 하나씩 응답을 기다려 보내면 명령 수만큼 왕복이 생깁니다. 왕복 동안 다른 연결의 명령이 실행될 수 있습니다.
- **파이프라이닝**: 응답을 기다리지 않고 여러 명령을 연달아 보내 왕복 수를 줄이는 방식입니다. **원자성을 주지 않습니다.** 보낸 순서대로 실행되지만, 그 사이에 다른 클라이언트의 명령이 끼어들 수 있습니다(공식 문서 eval-intro: "The commands in a pipelined request run in the order they are sent, but other clients' commands may be interleaved"). 파이프라이닝은 왕복을 줄이는 도구이고, 끼어들기를 막는 도구가 아닙니다.

## 왜 둘 다 성공하는가: 명령과 명령 사이의 틈

가장 흔한 첫 구현은 "`GET`으로 읽고, 앱에서 1 이상인지 확인하고, `DECR`로 줄이기"입니다.

| 순서 | 요청 A (연결 1) | 요청 B (연결 2) | `stock:item:1` |
| --- | --- | --- | --- |
| 1 | `GET` → `"1"` | | 1 |
| 2 | | `GET` → `"1"` | 1 |
| 3 | 앱에서 판단: 1 이상 → `DECR` → 0 | | 0 |
| 4 | | 앱에서 판단: 1 이상이었음 → `DECR` → -1 | -1 |
| 5 | 주문 성공 | 주문 성공 | -1 |

Redis는 명령 네 개를 각각 끼어들기 없이 정확히 실행했습니다. 틀린 것은 B의 판단입니다. B가 2번에서 읽은 `"1"`은 4번에서 `DECR`을 보낼 때 이미 낡은 값입니다. 판단이 앱에서 이루어지므로, 확인(`GET`)과 행동(`DECR`) 사이에 왕복과 다른 연결의 명령이 끼어들 틈이 있습니다. 이것이 확인 후 행동(check-then-act)형 경쟁 상태입니다. `DECR`은 그 순간의 값에서 빼므로 JVM 필드에서 생기는 갱신 손실은 없지만, 재고가 -1이 되고 주문은 2건입니다.

해결의 방향은 하나입니다. **확인과 차감을 메인 스레드가 끊지 않고 실행하는 한 덩어리 안에 넣는 것**입니다. 그 덩어리를 무엇으로 만드는지에 따라 방법이 나뉩니다.

## 판단을 명령 하나에 담을 수 있으면 그것이 가장 단순합니다

### DECR의 반환값으로 판단하기

`DECR`은 값을 1 줄이고 **줄인 뒤의 값**을 돌려줍니다. 먼저 줄이고, 돌려받은 값으로 판단하면 확인과 차감이 명령 하나가 됩니다. 결과가 0 이상이면 성공입니다. 0보다 작으면 품절이므로, 줄인 1을 `INCR`로 되돌립니다.

| 순서 | 요청 A | 요청 B | `stock:item:1` |
| --- | --- | --- | --- |
| 1 | `DECR` → 0, 0 이상이므로 성공 | | 0 |
| 2 | | `DECR` → -1, 0 미만이므로 품절 | -1 |
| 3 | | 되돌리기: `INCR` → 0 | 0 |

요청이 몇 개가 와도 `DECR`이 한 번에 하나씩 실행되므로, 0 이상을 돌려받는 요청은 처음 재고 수만큼뿐입니다. 왕복은 성공 시 1번, 품절 시 2번입니다. `DECR`의 공식 복잡도는 O(1)입니다. 데이터가 커져도 작업량이 일정하다는 뜻입니다.

대가와 조건은 다음과 같습니다.

- **되돌리기 전까지 음수가 보입니다.** 2번과 3번 사이에 다른 요청이 재고를 조회하면 -1을 봅니다. 화면에 재고를 보여 준다면 음수를 0으로 바꿔 보여 줘야 합니다.
- **되돌리기가 빠지면 음수가 남습니다.** 2번 뒤에 앱이 죽거나 연결이 끊겨 `INCR`을 보내지 못하면 -1이 남습니다. 초과 판매는 생기지 않습니다(다음 `DECR`도 음수를 받으므로). 하지만 나중에 재고를 채울 때 그만큼 덜 채워집니다.
- **키가 없으면 0에서 시작합니다.** `DECR`은 키가 없으면 0을 초깃값으로 써서 -1을 만들고 키를 새로 만듭니다. 재고 키가 만료되거나, 메모리 한도 때문에 지워지거나, 아직 초기화되지 않았으면 "품절"과 구분되지 않습니다. 새로 생긴 키에는 만료 시간도 없습니다. 메모리 한도의 경우는 "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다"에서 다룹니다.
- **값이 정수 문자열이 아니면 에러입니다.** 클라이언트가 값을 다른 형태로 직렬화해 저장했다면 `DECR`이 실패합니다. Spring 직렬화와의 관계는 "실무 포인트"에서 다룹니다.

### 재고를 '꺼낼 토큰'으로 바꾸기

예시를 조금 바꿉니다. 숫자 대신 꺼낼 물건으로 재고를 표현하면 "꺼내기" 자체가 판단이 되기 때문입니다. 재고가 1개면 List 키 `stock:item:1:tokens`에 원소 하나(`"t1"`)를 넣어 둡니다.

| 순서 | 요청 A | 요청 B | `stock:item:1:tokens` |
| --- | --- | --- | --- |
| 1 | `LPOP` → `"t1"`, 성공 | | (비어서 키 삭제) |
| 2 | | `LPOP` → nil, 품절 | (없음) |

`LPOP`은 키가 없으면 nil을 돌려줍니다. 원소를 꺼내 List가 비면 키가 삭제됩니다. 음수가 생기지 않고 되돌리기도 필요 없습니다.

대가는 데이터 모양입니다. 재고 수만큼 원소가 필요하므로 메모리가 재고 수에 비례해 늘어납니다. 재고 수를 바꾸려면 원소를 넣고 빼야 합니다. 남은 수는 `LLEN`으로 셉니다. 주문이 뒤에서 실패하면 토큰을 다시 넣어야 합니다.

### 명령 하나로 안 되는 경우

판단이 여러 키나 여러 조건에 걸치면 명령 하나로 담을 수 없습니다. 예를 들어 "1인당 1개만 살 수 있다"를 더하면 "이 사용자가 이미 샀는가"와 "재고가 남았는가"를 함께 확인하고 두 키를 함께 바꿔야 합니다. 이때 아래의 방법들이 필요해집니다.

"1인당 1개"를 넣기 전에 정할 것이 셋 있습니다. 답에 따라 구매자 기록을 어떻게 두고 언제 지울지가 정해집니다.

- **무엇을 하나로 세는가**: 상품마다 한 개인지, 이벤트 전체에서 한 개인지에 따라 구매자 기록을 상품마다 둘지 이벤트마다 둘지가 갈립니다. 이 문서는 상품마다 구매자 Set 하나를 둡니다.
- **언제까지 기억하는가**: 판매 중에 기록이 사라지면 같은 사용자가 다시 살 수 있으므로, 이 기록도 재고 키처럼 지워지면 안 되는 데이터입니다. 판매가 끝나면 필요 없으므로 정리 방법을 정합니다. 만료 시간을 주면 정리는 쉽지만, `volatile-` 정책을 쓰는 인스턴스에서는 만료 시간이 있는 키가 축출 대상이 되어 판매 중에도 지워질 수 있습니다. 그래서 만료 시간을 줄 거라면 재고와 함께 `noeviction` 인스턴스에 두고, `volatile-` 정책의 인스턴스에 둔다면 만료 시간 대신 판매가 끝난 뒤 직접 지웁니다("메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다").
- **취소하면 다시 살 수 있는가**: 그렇다면 취소 때 재고를 되돌리면서 구매자 기록도 함께 지워야 합니다. 둘 중 하나만 되돌리면 재고는 남았는데 못 사거나, 기록 없이 재고만 줄어든 상태가 됩니다.

이 제한은 "원자성이 보장하지 않는 것"에서 다루는 주문 ID 기준의 중복 방지와 다릅니다. 중복 방지는 같은 요청이 다시 온 것을 막으므로, 같은 사용자가 주문 ID가 다른 두 요청을 보내면 둘 다 통과시킵니다. 1인당 1개 제한은 그중 하나를 막아야 합니다. 대가는 구매자 기록이 실제로 산 사용자 수만큼 메모리를 쓴다는 점입니다. 두 확인을 어떻게 한 번에 판정하는지와 재시도·메모리·DB와의 관계는 아래 방법들을 본 뒤 "1인당 1개는 구매 기록과 재고 차감을 한 번에 판정해야 합니다"에서 다룹니다.

## MULTI/EXEC는 명령을 묶어 실행하지만, 중간 결과로 판단할 수 없습니다

### 동작

1. `MULTI`를 보내면 그 연결은 트랜잭션 상태가 됩니다.
2. 이후 명령은 실행되지 않고 대기열에 쌓이며, 응답으로 `QUEUED`만 받습니다.
3. `EXEC`를 보내면 대기열의 명령을 차례로 모두 실행하고, 결과를 배열로 한꺼번에 돌려줍니다.

`EXEC`는 메인 스레드가 실행하는 명령 하나이므로, 대기열을 실행하는 동안 다른 연결의 명령이 끼어들지 않습니다(공식 문서 transactions: "A request sent by another client will never be served in the middle of the execution of a Redis Transaction").

### 재고 문제를 혼자서는 풀지 못하는 이유

| 순서 | 요청 A | 요청 B | `stock:item:1` |
| --- | --- | --- | --- |
| 1 | `MULTI` → OK | | 1 |
| 2 | `GET` → `QUEUED` | | 1 |
| 3 | `DECR` → `QUEUED` | | 1 |
| 4 | `EXEC` → [`"1"`, 0] | | 0 |
| 5 | | `MULTI` → OK, `GET`·`DECR` → `QUEUED` | 0 |
| 6 | | `EXEC` → [`"0"`, -1] | -1 |

`GET`의 결과는 `EXEC`의 응답에 담겨서야 도착합니다. 그때는 `DECR`도 이미 실행된 뒤입니다. 그래서 "1 이상일 때만 `DECR`"이라는 분기를 트랜잭션 안에 넣을 수 없습니다. B는 6번에서야 재고가 0이었다는 것을 알게 되고, 결과는 "DECR의 반환값으로 판단하기"와 같아지면서 명령만 늘어납니다. `GET`을 `MULTI` 앞으로 빼면 앞 절의 틈이 그대로 돌아옵니다.

### 에러가 나도 되돌리지 않습니다

트랜잭션 중의 에러는 언제 발견되느냐에 따라 다르게 처리됩니다.

- **대기열에 넣을 때 발견되는 에러**(없는 명령, 인자 개수 오류, 메모리 한도 초과 등): 그 명령은 거부되고 트랜잭션에 실패 표시가 붙습니다. `EXEC`는 `EXECABORT` 에러를 돌려주고 아무것도 실행하지 않습니다.
- **실행할 때 발견되는 에러**(예: 문자열 키에 List 명령을 보내 생기는 `WRONGTYPE`): 그 명령만 실패하고 **나머지 명령은 실행됩니다. 이미 실행된 명령도 되돌리지 않습니다**(공식 문서 transactions: "Redis does not support rollbacks of transactions").

예를 들어 트랜잭션에 "재고 `DECR`"과 "주문 목록에 `RPUSH`"를 넣었는데 주문 목록 키가 실수로 String이었다면, 재고만 줄고 주문 기록은 실패합니다.

### 잘 맞는 곳

판단 없이 **여러 쓰기를 섞이지 않게 한 번에 반영**할 때 씁니다. 예를 들어 재고 차감과 판매 기록 추가를 다른 요청이 중간 상태로 보지 않게 할 수 있습니다. 대기열 명령을 파이프라이닝으로 함께 보내면 왕복도 줄어듭니다.

## WATCH는 '그사이 바뀌었으면 포기'를 붙여 판단을 가능하게 합니다

WATCH는 낙관적 방식입니다. 읽을 때의 상태를 기억해 두고, 쓸 때 그사이 바뀌지 않았을 때만 반영하며, 바뀌었으면 다시 시도합니다. 낙관적 방식의 일반 원리와 경합 비용은 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.

### 동작

1. `WATCH stock:item:1`로 키를 감시 목록에 올립니다.
2. `GET`으로 읽고 앱에서 판단합니다.
3. `MULTI` → `DECR` → `EXEC`를 보냅니다.
4. `WATCH` 이후 `EXEC` 전까지 그 키를 바꾼 명령이 있었다면, `EXEC`는 대기열을 실행하지 않고 nil을 돌려줍니다. 그러면 처음부터 다시 시도합니다.

"키를 바꾼 명령이 있었다"는 다음처럼 판정합니다. 키를 바꾸는 명령은 실행될 때 수정 신호를 내고, 이 신호가 그 키를 감시 중인 모든 연결에 "더러움" 표시를 붙입니다. `EXEC`는 이 표시를 보고 실행을 포기합니다. `WATCH`할 때 살아 있던 키가 `EXEC` 시점에 만료되어 있어도 포기합니다. `WATCH`할 때 이미 만료돼 있던 키는 이 검사에서 뺍니다. 공식 문서는 만료와 메모리 한도에 의한 삭제(eviction)도 수정에 포함된다고 설명합니다.

| 순서 | 요청 A | 요청 B | `stock:item:1` |
| --- | --- | --- | --- |
| 1 | `WATCH` → OK | | 1 |
| 2 | `GET` → `"1"`, 1 이상 | | 1 |
| 3 | | `WATCH` → OK | 1 |
| 4 | | `GET` → `"1"`, 1 이상 | 1 |
| 5 | `MULTI`, `DECR`, `EXEC` → [0], 성공 | | 0 |
| 6 | | `MULTI`, `DECR`, `EXEC` → nil, 실행 안 됨 | 0 |
| 7 | | 재시도: `WATCH`, `GET` → `"0"`, 품절, `UNWATCH` | 0 |

5번에서 A의 `DECR`이 수정 신호를 냈으므로 B의 연결에 표시가 붙고, 6번의 `EXEC`는 아무것도 실행하지 않습니다. 표에서는 5·6·7번의 명령 여러 개를 한 줄에 적었지만, 각 명령은 따로 보내는 요청입니다.

### 값이 아니라 '수정이 있었는가'를 봅니다

이 표시는 값을 비교하지 않습니다. 같은 값으로 `SET`해도 수정 신호가 나므로 `EXEC`는 실패합니다. 값만 비교하는 방식에서 생기는 ABA 문제(값이 바뀌었다가 같은 값으로 돌아오면 알아채지 못함)는 없습니다. 대신 실제로는 문제없는 경우에도 포기할 수 있습니다.

`EXEC`가 성공하든 실패하든 그 연결의 모든 감시는 풀립니다. 7번처럼 사지 않기로 했다면 `UNWATCH`로 감시를 풉니다. 감시는 `EXEC`나 `UNWATCH`를 보내거나 연결이 끊길 때까지 남습니다. MULTI 안이라면 `DISCARD`로도 풀리지만, `DISCARD`는 MULTI 안에서만 받으므로 MULTI 전인 7번 상황에서는 `UNWATCH`를 씁니다. 풀지 않으면 나중에 같은 연결로 시작한 다른 트랜잭션의 `EXEC`가, 이 재고 키가 바뀌었다는 이유로 nil을 받을 수 있습니다. 연결 풀에서 그 연결을 다른 요청이 이어 쓰면 원인을 찾기 어려워집니다(공식 문서 transactions: `UNWATCH`를 부르면 "the connection can already be used freely for new transactions").

### 대가

- **명령과 왕복이 많습니다.** 한 번 시도하는 데 `WATCH`, `GET`, `MULTI`, `DECR`, `EXEC` 다섯 명령이 듭니다. 판단을 앱에서 하므로 파이프라이닝으로 묶어도 왕복은 최소 2번입니다(`WATCH`+`GET`, 그다음 `MULTI`+`DECR`+`EXEC`).
- **처음부터 끝까지 같은 연결을 써야 합니다.** 감시 목록과 트랜잭션 대기열이 연결에 붙어 있기 때문입니다. 여러 스레드가 함께 쓰는 연결에 다른 스레드의 명령이 섞이면 의미가 깨집니다.
- **경합이 크면 재시도가 폭증합니다.** 예시(재고 1개, 요청 2개)에서는 B가 한 번 더 읽고 끝나므로 차이가 잘 드러나지 않습니다. 그래서 예시를 키워 계산해 봅니다. 재고 100개에 1,000명이 동시에 사려 한다고 합시다. 매 라운드에 남은 사람이 모두 시도하고 한 명만 성공한다고 가정하면, `EXEC` 시도는 1,000 + 999 + … + 901 = 95,050번입니다. 성공은 100번입니다. 실패한 시도마다 다섯 명령이 서버에서도 실행되므로 서버 부하도 함께 늘어납니다. 측정이 아닌 단순화한 모델의 계산이지만, 한 키에 요청이 몰릴수록 WATCH가 불리해진다는 방향은 분명합니다.

## Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다

### 동작

`EVAL`은 Lua 스크립트 본문과 키 이름 목록(`KEYS`), 그 밖의 인자 목록(`ARGV`)을 함께 보냅니다. 스크립트는 Redis 서버 안의 메인 스레드에서 실행됩니다. 스크립트 안에서 `redis.call`로 부른 명령은 네트워크를 거치지 않고 바로 실행되고, 결과가 스크립트로 돌아오므로 그 값으로 분기할 수 있습니다. 스크립트 전체가 `EVAL`이라는 명령 하나의 실행이므로, 스크립트가 끝날 때까지 다른 연결의 명령은 실행되지 않습니다(공식 문서 programmability: "When running a script or a function, Redis guarantees its atomic execution. The script's execution blocks all server activities during its entire time").

예시의 스크립트가 할 일은 세 단계입니다.

1. `KEYS[1]`(여기서는 `stock:item:1`)의 값을 읽습니다.
2. 값이 없거나 1보다 작으면 0(품절)을 돌려주고 끝냅니다.
3. 아니면 `DECR`하고 1(성공)을 돌려줍니다.

키 이름은 스크립트에 직접 쓰지 않고 `KEYS`로 넘깁니다(공식 문서 eval-intro: "all names of keys that a script accesses must be explicitly provided as input key arguments"). 클러스터는 이 선언을 보고 요청을 어느 노드로 보낼지 정하기 때문입니다. 규칙은 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다"에서 다룹니다. 2단계에서 "값이 없음"을 품절로 처리하는 것은 "DECR의 반환값으로 판단하기"에서 본, 키가 없을 때 0에서 시작하는 문제를 피하기 위해서입니다.

스크립트가 `true`·`false` 대신 1과 0을 돌려주는 데도 이유가 있습니다. Lua 값은 Redis 응답으로 바뀔 때 변환 규칙을 따릅니다. Lua 숫자는 정수 응답이 됩니다. `true`는 정수 1이 되지만, `false`는 nil 응답이 됩니다(공식 문서 lua-api의 Lua에서 RESP2로 바꾸는 규칙). 결과를 정수로 정해 두면 앱이 받는 값이 1과 0 둘뿐이어서 성공과 품절을 분명히 가를 수 있습니다.

| 순서 | 요청 A | 요청 B | `stock:item:1` |
| --- | --- | --- | --- |
| 1 | `EVAL` → 스크립트 안: 읽기 `"1"` → `DECR` → 1(성공) 반환 | (B의 `EVAL`은 A의 스크립트가 끝날 때까지 대기) | 0 |
| 2 | | `EVAL` → 스크립트 안: 읽기 `"0"` → 0(품절) 반환 | 0 |

확인과 차감이 한 덩어리이므로 틈이 없습니다. 요청마다 왕복 1번이고, 재시도와 음수가 없습니다. "1인당 1개"를 더할 때도 같은 스크립트에서 구매자 Set을 확인하고 재고 차감과 구매자 추가를 함께 하면 됩니다. 그 단계는 "1인당 1개는 구매 기록과 재고 차감을 한 번에 판정해야 합니다"에서 다룹니다.

대가는 세 가지입니다.

### 대가 1: 스크립트가 도는 동안 다른 모든 명령이 기다립니다

스크립트는 메인 스레드를 차지하므로, 재고 키와 무관한 다른 모든 연결의 명령도 스크립트가 끝날 때까지 기다립니다. 예시 스크립트처럼 명령 몇 개로 끝나면 문제가 되지 않습니다. 하지만 원소 수에 비례해 반복하는 스크립트는 데이터가 커질수록 모든 클라이언트의 지연이 됩니다. `EVAL`의 공식 복잡도도 "스크립트에 따라 다름"입니다.

**`busy-reply-threshold`는 스크립트를 멈추는 제한 시간이 아닙니다.** 오해가 잦은 지점입니다.

- 기본값은 5,000밀리초(5초)이고, 예전 이름 `lua-time-limit`도 별칭으로 남아 있습니다.
- 스크립트가 이 시간을 넘기면 Redis는 "Slow script detected" 경고를 로그에 남깁니다. 그다음 스크립트 실행 중간중간에 다른 연결의 요청을 받아 **`BUSY` 에러로 응답하기 시작합니다**. 스크립트 자체는 계속 실행됩니다. 공식 문서도 "When a script reaches the timeout threshold, it isn't terminated by Redis automatically"라고 설명합니다.
- 이 상태에서 받는 명령은 `SCRIPT KILL`, `FUNCTION KILL`, `SHUTDOWN NOSAVE` 등 일부뿐입니다.
- `SCRIPT KILL`은 **스크립트가 아직 쓰기 명령을 실행하지 않았을 때만** 성공합니다. 이미 썼다면 `UNKILLABLE` 에러가 납니다. 그때는 끝나기를 기다리거나 `SHUTDOWN NOSAVE`로 서버를 내려야 합니다. 쓰기 후에 스크립트를 중간에 멈추면 반쯤 반영된 상태가 남아 원자성이 깨지기 때문입니다. `SHUTDOWN NOSAVE`는 종료 때의 RDB 저장을 건너뛰고 서버 프로세스를 끝내므로(AOF를 켰다면 AOF 내려 쓰기는 그대로 합니다), 영속화 설정에 따라 마지막 저장 이후의 변경을 잃을 수 있습니다. 설정별로 무엇이 남는지는 [Redis 영속성](./persistence.md)에서 다룹니다.

### 대가 2: 중간에 에러가 나도 이미 한 쓰기는 되돌리지 않습니다

스크립트 실행 중 에러가 나면 Redis는 에러를 클라이언트에 돌려줄 뿐, 그때까지 스크립트가 실행한 쓰기를 되돌리지 않습니다. `redis.call`은 명령이 실패하면 스크립트를 멈추고 에러를 올립니다. `redis.pcall`은 에러를 값으로 돌려줘 스크립트가 처리할 수 있게 합니다(공식 문서 lua-api).

그래서 스크립트는 **읽고 검증하는 단계를 앞에, 쓰기를 뒤에** 모아 둡니다. 예시 스크립트는 읽기와 판단을 먼저 하고 쓰기(`DECR`)를 마지막에 한 번 하므로, 쓰기 도중 실패할 여지가 작습니다. "1인당 1개"로 쓰기가 두 개가 되면, 두 번째 쓰기가 실패할 수 있는 조건(키 자료형 등)을 앞에서 확인해 둡니다.

클러스터에서는 `KEYS`로 선언하지 않은 키에 접근하는 명령도 이런 중간 에러가 될 수 있습니다. 조건은 "Lua는 실행 중에도 검사하므로 중간에 실패할 수 있습니다"에서 다룹니다.

### 대가 3: 스크립트 캐시는 언제든 비워질 수 있습니다

- `EVAL`을 받으면 Redis는 스크립트를 컴파일해 본문의 SHA1 값을 이름으로 캐시에 둡니다. `EVALSHA`는 본문 없이 SHA1만 보내 캐시된 스크립트를 실행합니다. 캐시에 없으면 `NOSCRIPT` 에러가 납니다.
- 캐시는 서버 재시작, 복제본이 주 서버로 승격되는 장애 조치, `SCRIPT FLUSH`로 비워질 수 있습니다(공식 문서 eval-intro "Cache volatility"). 그래서 `EVALSHA`가 `NOSCRIPT`를 받으면 본문과 함께 다시 보내야 합니다.
- `EVAL`로 들어온 스크립트는 정해진 개수까지만 캐시에 두고, 넘으면 가장 오래 쓰지 않은 것부터 지웁니다. 지운 수는 `INFO`의 `evicted_scripts`로 셉니다. `SCRIPT LOAD`로 올린 스크립트는 이 방식으로 지우지 않습니다.
- 그래서 **값을 스크립트 본문에 끼워 넣어 매번 다른 스크립트를 만들면 안 됩니다.** 예를 들어 상품 ID나 수량을 본문 문자열에 이어 붙이면 요청마다 SHA1이 달라집니다. 그러면 캐시가 계속 바뀌며 다른 스크립트까지 밀어냅니다. 값은 `KEYS`와 `ARGV`로 넘깁니다(공식 문서 eval-intro는 이를 anti-pattern으로 설명합니다).

### Functions는 같은 원자성에 '서버가 보관하는 스크립트'를 더합니다

Functions는 `FUNCTION LOAD`로 라이브러리를 서버에 올리고 `FCALL`로 실행합니다. 실행의 원자성과 메인 스레드를 차지하는 대가는 스크립트와 같습니다. 오래 걸리면 `FUNCTION KILL`을 씁니다. 차이는 보관 방식입니다. 함수는 데이터와 함께 영속화되고 복제본에 복제되므로, 스크립트 캐시처럼 재시작이나 장애 조치로 사라지지 않습니다. 다만 영속화를 끈 캐시 용도라면 재시작 때 다시 올리는 방법이 따로 필요합니다(공식 문서 functions-intro). 여러 서비스가 같은 로직을 공유하거나 서버 쪽 로직을 배포 단위로 관리하고 싶을 때 맞습니다. 대신 라이브러리 배포와 버전 관리가 운영 작업이 됩니다.

### 스크립트의 쓰기는 복제본에도 한 덩어리로 전달됩니다

스크립트가 실행한 쓰기 명령들은 복제본과 AOF에 전달될 때, 둘 이상이면 `MULTI`/`EXEC`로 감싸 한 덩어리로 보냅니다. 그래서 복제본에서도 스크립트의 쓰기가 반쯤만 반영된 상태를 다른 클라이언트가 보지 않습니다. 이 감싸기는 MULTI/EXEC 트랜잭션에도 똑같이 적용됩니다.

## 네 방법을 한 표로 비교합니다

| 방법 | 확인과 차감을 한 덩어리로 | 요청당 왕복(예시) | 경합이 클 때 | 다른 연결에 주는 영향 | 중간 실패 |
| --- | --- | --- | --- | --- | --- |
| 단일 명령: `DECR` 반환값 | 예. 단, 값 하나의 증감과 경계까지 | 1, 품절이면 2 | 모두 한 번에 끝남 | 명령 하나의 시간 | 되돌리기 전 장애 시 음수가 남음 |
| 단일 명령: `LPOP` 토큰 | 예. 꺼내기가 곧 판단 | 1 | 모두 한 번에 끝남 | 명령 하나의 시간 | 해당 없음. 주문 실패 시 토큰 반납 필요 |
| `MULTI`/`EXEC` | 아니오. 중간 결과로 분기 불가 | 묶은 명령 수, 파이프라이닝 시 1 | 해당 없음 | `EXEC` 동안 묶인 명령 전체 시간 | 실행 중 실패한 명령만 실패, 나머지 반영 |
| `WATCH` + `MULTI`/`EXEC` | 예. 바뀌었으면 포기 후 재시도 | 최소 2, 명령 5개 | 재시도 폭증 | `EXEC` 동안 | 위와 같음. `EXEC`가 nil이면 아무것도 안 됨 |
| Lua(`EVAL`) | 예 | 1 | 줄 서서 한 번씩 | 스크립트 전체 시간 동안 모든 명령 대기 | 에러 이전의 쓰기는 남음 |

## 1인당 1개는 구매 기록과 재고 차감을 한 번에 판정해야 합니다

선착순 쿠폰을 한 사람이 한 장만 받게 하는 문제도 구조가 같습니다. 쿠폰의 남은 수량이 재고 키이고, 받은 사람 목록이 구매자 기록입니다. 이 절은 상품 주문으로 설명합니다.

### 예시를 재고 2개, 같은 사용자의 요청 2개로 넓힙니다

이 절에서만 예시를 넓힙니다. 재고가 1개면 재고 확인만으로 두 번째 요청이 품절이 되므로, 1인당 1개 제한이 하는 일이 드러나지 않기 때문입니다.

- `stock:item:1`의 값은 `"2"`입니다.
- 구매자 기록 `buyers:item:1`은 Set(중복 없는 문자열 모음)이고, 처음에는 키가 없습니다.
- 요청 A와 B는 같은 사용자 `u42`가 보낸 주문 두 개입니다. 버튼을 두 번 눌렀거나 두 기기에서 보낸 경우입니다. 주문 ID는 `o-A`, `o-B`로 서로 다릅니다. 그래서 "원자성이 보장하지 않는 것"의 주문 ID 기준 중복 방지로는 둘 다 통과합니다.
- **바라는 결과**: 하나만 성공하고 다른 하나는 "이미 구매"를 받습니다. 재고는 1, `buyers:item:1`은 {`u42`}입니다. 남은 1개는 다른 사용자가 살 수 있어야 합니다.

이 절은 단일 서버를 기준으로 키 이름을 씁니다. 클러스터에서 붙일 해시 태그는 "해시 태그로 슬롯을 맞추면 그 키들은 한 노드에 몰립니다"에서 다룹니다.

이 절에서 쓰는 Set 명령은 셋입니다.

- `SADD`는 원소를 넣고 **새로 넣은 원소 수**를 돌려줍니다. 처음이면 1, 이미 있으면 0이고, 이미 있으면 Set을 바꾸지 않습니다. `DECR`의 반환값처럼 "확인과 기록"이 명령 하나에 담겨 있습니다.
- `SISMEMBER`는 원소가 있으면 1, 없으면 0을 돌려줍니다. 확인만 합니다.
- `SREM`은 원소를 지우고 실제로 지운 원소 수를 돌려줍니다.

### 두 명령으로 나누면 어느 순서든 틈이나 찌꺼기가 남습니다

**확인 후 기록**: `SISMEMBER`로 확인하고, 통과하면 `DECR`과 `SADD`를 보내는 구현입니다. "왜 둘 다 성공하는가: 명령과 명령 사이의 틈"과 같은 틈이 생깁니다.

| 순서 | 요청 A (`u42`) | 요청 B (`u42`) | `stock:item:1` | `buyers:item:1` |
| --- | --- | --- | --- | --- |
| 1 | `SISMEMBER` → 0, 아직 안 삼 | | 2 | (없음) |
| 2 | | `SISMEMBER` → 0, 아직 안 삼 | 2 | (없음) |
| 3 | `DECR` → 1, `SADD` → 1 | | 1 | {`u42`} |
| 4 | | `DECR` → 0, `SADD` → 0 | 0 | {`u42`} |
| 5 | 주문 성공 | 주문 성공 | 0 | {`u42`} |

`u42`가 두 개를 샀고, 다른 사용자가 살 재고 1개가 사라졌습니다. B가 2번에서 본 "아직 안 삼"은 4번에서 이미 낡은 판단입니다.

**`SADD`의 반환값을 판단에 쓰기**: 사용자 판정은 `SADD` 하나로 원자적이 됩니다. 하지만 재고 차감이 다른 명령이므로, 어느 쪽을 먼저 하든 두 명령 사이와 실패 뒤에 문제가 남습니다.

- **기록 먼저(`SADD` → `DECR`)**: A의 `SADD`가 1, B의 `SADD`가 0이므로 B는 바로 "이미 구매"입니다. 사용자 판정은 맞습니다. 그런데 `SADD`는 1을 받았고 `DECR`이 음수를 돌려주면(품절) `SREM`으로 기록을 지워야 합니다. `SADD`와 `DECR` 사이, 또는 `SREM` 전에 앱이 죽거나 연결이 끊기거나 `DECR`이 OOM으로 거부되면 기록만 남습니다. 그 사용자는 사지 않았는데도 판매가 끝날 때까지 "이미 구매"를 받습니다.
- **차감 먼저(`DECR` → `SADD`)**: A는 `DECR` → 1, `SADD` → 1로 성공합니다. B는 `DECR` → 0으로 재고를 가져간 뒤 `SADD` → 0을 받아 `INCR`로 되돌려야 합니다. B가 되돌리기 전까지 재고는 0이므로, 그사이 온 다른 사용자 C는 1개가 남았는데도 품절을 받습니다. B의 앱이 `INCR` 전에 죽으면 그 1개는 판매가 끝날 때까지 아무도 사지 못합니다.

명령 하나하나는 원자적이지만 판정이 두 명령에 걸쳐 있습니다. 원자적 연산 두 개를 이어 붙이면 원자적이지 않다는 원리 그대로입니다. 되돌리기(`SREM`, `INCR`)도 따로 보내는 명령이므로 같은 이유로 빠질 수 있습니다.

### 스크립트 하나에서 재고 확인, 구매 기록, 차감을 끝냅니다

판정 전체를 Lua 스크립트 하나에 넣습니다. `KEYS[1]`은 `stock:item:1`, `KEYS[2]`는 `buyers:item:1`, `ARGV[1]`은 사용자 ID `u42`입니다.

1. `KEYS[1]`의 값을 읽습니다. 값이 없거나 1보다 작으면 0(품절)을 돌려주고 끝냅니다. 정수 문자열이 아니면(예: `"1.5"`) 에러로 끝냅니다. `DECR`은 정수 문자열만 받으므로, 숫자로 읽히는지만 보면 `"1.5"`가 통과해 3단계에서 실패합니다.
2. `KEYS[2]`에 `ARGV[1]`을 `SADD`합니다. 결과가 0이면 2(이미 구매)를 돌려주고 끝냅니다. 0일 때는 Set이 바뀌지 않았으므로 아무것도 쓰지 않은 채 끝납니다.
3. `KEYS[1]`을 `DECR`하고 1(성공)을 돌려줍니다.

| 순서 | 요청 A (`u42`) | 요청 B (`u42`) | `stock:item:1` | `buyers:item:1` |
| --- | --- | --- | --- | --- |
| 1 | `EVAL` → 스크립트 안: 읽기 `"2"` → `SADD` 1 → `DECR` 1 → 1(성공) | (B의 `EVAL`은 대기) | 1 | {`u42`} |
| 2 | | `EVAL` → 스크립트 안: 읽기 `"1"` → `SADD` 0 → 2(이미 구매) | 1 | {`u42`} |

B는 재고가 남아 있어도 "이미 구매"를 받고, 남은 1개는 다른 사용자가 살 수 있습니다. 중간 상태를 다른 요청이 보지 않으며, 되돌리기가 필요한 경로가 없습니다.

단계의 순서에도 이유가 있습니다.

- **재고 확인이 먼저입니다.** 품절인 요청은 아무것도 쓰지 않고 끝납니다. `SADD`를 먼저 하면 품절일 때 스크립트 안에서 `SREM`을 해야 하므로 쓰기가 하나 늘어납니다.
- **쓰기 두 개 중 뒤의 쓰기가 실패할 조건을 앞에서 걸러 둡니다**("대가 2: 중간에 에러가 나도 이미 한 쓰기는 되돌리지 않습니다"). `DECR`이 실패할 조건인 "값이 정수가 아님"은 1단계에서 이미 걸렀습니다. 구매자 키가 Set이 아니면 `SADD`가 `WRONGTYPE` 에러를 내지만, 그때는 아직 아무것도 쓰지 않았습니다.
- **메모리 한도에서도 반쯤 반영되지 않습니다.** `SADD`는 메모리를 늘릴 수 있는 명령으로 표시되어 있고, 이 스크립트의 첫 쓰기입니다. `noeviction`에서 상한을 넘었다면 `SADD`가 거부되어 아무것도 쓰지 않은 채 끝납니다("noeviction이면 재고가 남아 있어도 차감이 거부됩니다").
- 결과를 0, 1, 2 정수로 정하는 이유는 "Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다"의 1과 0과 같습니다. 앱은 세 값으로 품절, 성공, 이미 구매를 가릅니다.

MULTI/EXEC는 `SADD`의 결과를 보고 `DECR`을 할지 정할 수 없으므로 이 판정을 담지 못합니다. WATCH는 재고 키와 구매자 키를 함께 감시하면 가능하지만, 선착순처럼 한 상품에 요청이 몰리는 곳에서는 "WATCH는 '그사이 바뀌었으면 포기'를 붙여 판단을 가능하게 합니다"의 재시도 폭증이 그대로 생깁니다.

### 사용자마다 키를 두는 `SET NX`도 같은 자리에 들어갑니다

구매자 Set 대신 사용자마다 키를 하나씩 둘 수도 있습니다. `SET bought:item:1:u42 o-A NX`는 키가 없을 때만 값을 쓰고 OK를 돌려주며, 이미 있으면 쓰지 않고 nil을 돌려줍니다. `SADD`의 반환값과 같은 판정을 키 하나로 하는 셈입니다. 그래도 재고 차감과는 다른 명령이므로, 앞 절의 2단계 자리에 넣어 **같은 스크립트 안에서** 실행해야 합니다. 따로 보내면 "두 명령으로 나누면 어느 순서든 틈이나 찌꺼기가 남습니다"의 문제가 똑같이 생깁니다.

Set 하나와 비교한 차이는 다음과 같습니다.

- **값에 주문 ID를 담을 수 있습니다.** 아래 재시도 구분에 쓸 수 있습니다.
- **키마다 만료 시간을 줄 수 있습니다.** 다만 판매 중에 만료되면 같은 사용자가 다시 살 수 있으므로, 만료 시간은 판매 기간보다 길게 잡습니다("명령 하나로 안 되는 경우"의 "언제까지 기억하는가").
- **키마다 붙는 비용이 있습니다.** 사용자마다 `bought:item:1:` 같은 앞부분이 반복된 키 이름과 키마다의 관리 정보가 붙습니다. 이 때문에 Set 하나보다 메모리를 더 쓸 가능성이 크지만, 전체 대소는 ID 길이, Set의 표현, 메모리 할당기에 따라 달라지므로 확인하지 않았습니다. 같은 데이터로 두 방식을 넣어 보고 `used_memory`의 변화로 비교합니다.
- **판매 뒤 정리가 번거롭습니다.** Set은 키 하나를 지우면 되지만, 사용자별 키는 이름 패턴으로 찾아 지우거나 만료에 맡겨야 합니다.
- **클러스터에서 나뉘지 않습니다.** 재고 키와 같은 스크립트에서 다뤄야 하므로 `bought:{item:1}:u42`처럼 같은 해시 태그를 붙입니다. 키를 사용자마다 나눠도 모두 한 슬롯, 한 노드에 있습니다.

재시도 구분이 필요 없다면 Set 하나가 단순합니다. 필요하다면 사용자별 키에 주문 ID를 담거나, Set을 유지하면서 아래처럼 주문 ID 기록을 함께 둡니다.

### 타임아웃 뒤 같은 주문을 다시 보내면 '이미 구매'를 받습니다

A의 `EVAL`이 서버에서 실행됐는데 응답이 오기 전에 클라이언트 타임아웃이 났다고 합시다. 앱이 같은 주문 `o-A`로 다시 보내면, 예시처럼 재고가 남아 있는 동안에는 스크립트가 읽기 `"1"` → `SADD` 0 → 2(이미 구매)를 돌려줍니다. A가 마지막 재고를 가져갔거나 그사이 품절됐다면 1단계에서 0(품절)을 받습니다.

- **좋은 점**: 재고가 두 번 줄지 않습니다. 같은 사용자의 재시도이므로 1인당 1개 판정이 이중 차감을 함께 막았습니다.
- **나쁜 점**: 앱은 자기 주문의 재시도가 성공했는지, 다른 주문 때문에 거절됐는지 구분하지 못합니다. "이미 구매"를 실패로 처리해 `o-A`를 실패로 기록하면, 재고와 구매 기록은 `o-A`에 쓰였는데 주문은 없는 상태가 남습니다.

구분하려면 "누가 샀는가"와 함께 **어느 주문으로 샀는가**를 같은 스크립트에서 기록하고, 재고 확인보다 **먼저** 이번 요청의 주문 ID가 이미 기록돼 있는지 봅니다. 재고 확인 뒤에 보면 위의 품절 경우에 비교까지 가지 못하기 때문입니다. 기록돼 있으면 앞선 시도의 재시도이고, 기록돼 있지 않은데 사용자가 이미 있으면 다른 주문이므로 이미 구매로 거절합니다. 재시도라는 판정은 "Redis의 재고 차감과 구매 기록이 `o-A`로 끝났다"는 뜻일 뿐, DB에 주문이 저장됐다는 뜻은 아닙니다. 두 저장소의 쓰기는 한 번에 일어나지 않기 때문입니다("원자성이 보장하지 않는 것"). 그래서 앱은 `o-A`의 DB 주문 저장을 이어 가거나 저장 결과를 확인한 뒤 응답합니다. 주문 ID를 함께 `ARGV`로 넘기고, 기록 키를 `KEYS`로 선언하고, 클러스터라면 같은 해시 태그를 붙입니다. 주문 ID 기록을 무엇으로 두고 언제까지 보관하는지는 [Redis 멱등 키](./idempotency-key.md)에서 다룹니다.

두 장치는 서로를 대신하지 않습니다. 주문 ID 기록은 같은 주문이 다시 온 것을 막고, 1인당 1개 판정은 같은 사용자의 다른 주문을 막습니다.

판매 뒤 주문이 실패해 되돌릴 때도 두 키를 함께 다룹니다. 취소하면 다시 살 수 있게 한다면("명령 하나로 안 되는 경우"의 "취소하면 다시 살 수 있는가"), 되돌리기도 스크립트 하나로 `SREM`을 하고 **그 결과가 1일 때만** `INCR`을 합니다. 같은 되돌리기가 연달아 두 번 실행돼도 두 번째 `SREM`은 0을 받으므로 재고가 두 번 늘지 않습니다. 다만 `SREM`은 사용자만 보고 주문은 보지 않습니다. 첫 되돌리기 뒤 그 사용자가 새로 산 다음 늦은 재시도가 도착하면, 새 구매의 기록을 지우고 재고를 늘립니다. 재구매를 허용한다면 되돌리기도 주문 ID 기록을 보고 "지금 기록이 이 주문의 것일 때만" 지웁니다.

### 구매자 Set은 요청 수가 아니라 구매자 수만큼 커집니다

- **스크립트의 작업량은 Set이 커져도 일정합니다.** `SADD`의 공식 복잡도는 넣는 원소 하나당 O(1)이므로, 구매자가 10명이든 10만 명이든 요청 하나의 작업량이 구매자 수에 비례해 늘지 않습니다. 작은 Set의 한 덩어리 표현에서는 원소를 차례로 훑지만, 아래 기준 개수 안에서만 그렇습니다. 거절된 요청은 Set에 들어가지 않으므로, 크기는 몰린 요청 수가 아니라 성공한 구매자 수를 따릅니다.
- **크기에 따라 담는 방식이 바뀝니다.** 원소가 적을 때 Set은 원소들을 한 덩어리의 연속 메모리에 담습니다. 이 예시처럼 원소를 하나씩 넣을 때의 기본 기준은, 원소가 모두 정수 문자열이면 512개까지, 그 밖에는 128개까지이고 원소 하나가 64바이트를 넘지 않을 때입니다(`set-max-intset-entries`, `set-max-listpack-entries`, `set-max-listpack-value`). 이를 넘으면 원소마다 따로 할당하는 해시 테이블로 바뀌므로, Set을 지울 때 원소마다 메모리를 해제해야 합니다. 이 기준은 원소를 넣을 때 따지므로, 지금 원소 수만 보고 표현을 단정하지 말고 `OBJECT ENCODING`으로 확인합니다.
- **판매가 끝난 큰 Set은 빅키입니다.** 원소 전체를 읽는 `SMEMBERS`나 `DEL`로 지우는 일은 원소 수에 비례해 메인 스레드를 차지합니다. 지울 때는 `UNLINK`를 쓰고, 훑을 때는 나눠 읽습니다. 자세한 비용과 대응은 Hot Key와 Big Key의 "빅키는 키 전체를 다루는 한 번이 비쌉니다"에서 다룹니다.
- **크기는 재 봅니다.** `MEMORY USAGE buyers:item:1`은 키 하나의 메모리를 추정하고(큰 컬렉션은 일부 원소만 표본으로 봅니다), `OBJECT ENCODING`은 지금 어떤 방식으로 담겼는지 보여 줍니다.
- **지워지면 같은 사용자가 다시 삽니다.** 구매자 Set도 재고 키처럼 축출되면 안 되는 데이터입니다. 정책별 결과는 "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다"를 따릅니다.

### 마지막 판정은 DB 고유 제약이 맡습니다

Redis의 구매 기록은 사라질 수 있습니다. 장애 조치 때 복제본에 닿지 못한 `SADD`와 `DECR`은 함께 사라지고("원자성이 보장하지 않는 것"), `allkeys-` 정책이면 축출되며, 영속화 설정에 따라 재시작 때 잃습니다. 그러면 `u42`의 기록이 없으므로 같은 사용자가 다시 통과합니다. 또 Redis의 판정과 DB의 주문 저장은 서로 다른 저장소의 쓰기라서 한 번에 일어나지 않습니다.

그래서 "한 사람이 하나만"의 최종 판정은 주문을 저장하는 DB에 둡니다.

- 주문(또는 참여) 테이블에 (상품 ID, 사용자 ID) 고유 제약을 두고, 주문 저장과 같은 DB 트랜잭션에서 그 행을 넣습니다. Redis 기록을 잃어 같은 사용자가 다시 통과해도, 두 번째 주문은 고유 제약 위반으로 롤백됩니다.
- 이때 Redis에서는 재고가 이미 줄었으므로 재고만 되돌립니다. 구매자 기록은 지우지 않습니다. 그 사용자는 실제로 산 사람이기 때문입니다. 위의 취소용 되돌리기(`SREM` 후 `INCR`)를 그대로 쓰면 실제 구매자의 기록까지 지워지므로, "DB가 이미 구매로 거절함"은 재고만 되돌리는 경로로 따로 처리합니다. 이 `INCR`도 재시도되면 재고가 두 번 늘므로, 주문 ID 기준으로 한 번만 실행되게 합니다(예: 같은 스크립트에서 "이 주문의 재고를 되돌렸다"는 기록을 확인하고 남깁니다).
- 취소 뒤 다시 살 수 있게 한다면, 취소된 주문이 제약에 걸리지 않도록 제약의 범위를 정합니다. 방법은 DB마다 다릅니다.

DB가 정확성을 맡으면 Redis 판정의 역할은 **효율**이 됩니다. 몰린 요청 중 품절이나 이미 구매인 것을 Redis에서 돌려보내, DB까지 가는 쓰기를 줄입니다. 실제로 얼마나 줄어드는지는 요청 분포와 실패·재시도 빈도에 달려 있으므로 DB에 도달한 요청 수로 재 봅니다. 같은 구분이 멱등 키에서도 나옵니다([Redis 멱등 키](./idempotency-key.md)의 "Redis만으로는 부족한 곳: DB 고유 제약").

## 요청과 데이터가 늘면 무엇이 달라지는가

- **서버 실행 시간과 클라이언트가 본 지연은 다릅니다.** 클라이언트가 본 지연은 왕복 시간과 서버에서 앞 명령을 기다린 시간, 명령 실행 시간을 더한 것입니다. Lua는 왕복이 1번이고, WATCH는 최소 2번에 재시도가 더해집니다. 서버 실행 시간이 짧은 방법이라도 왕복이 많으면 클라이언트 지연은 길어집니다.
- **긴 스크립트의 비용은 모두가 냅니다.** 스크립트 하나가 10밀리초 걸린다면(가상 예시), 그동안 도착한 다른 모든 연결의 명령이 최대 그만큼 더 기다립니다. 스크립트의 작업량이 데이터 크기에 비례하지 않게 유지해야 합니다.
- **한 키에 요청이 몰리면 서버를 늘려도 그 키는 한 노드에 있습니다.** 선착순 상품처럼 재고 키 하나에 요청이 몰리면, 어떤 방법을 쓰든 그 키를 가진 노드 하나의 메인 스레드가 모두 처리합니다. 재고를 여러 키로 나눠 담는 방법도 있습니다. 하지만 남은 재고 합계 계산과 빈 조각 찾기가 새로 필요해지므로, 그 전에 Redis까지 오는 요청 수를 줄이는 방법을 먼저 고려할 수 있습니다. 예를 들어 사용자를 순번대로 들여보내는 [입장 대기](./waiting-queue.md)를 앞에 두거나, 품절을 확인한 애플리케이션 서버가 그 사실을 기억해 이후 요청을 Redis로 보내지 않게 합니다. 환불 등으로 재고가 다시 늘 수 있다면 그 기억을 지우는 방법도 함께 필요합니다.
- **경합이 커질수록 WATCH와 Lua의 차이가 벌어집니다.** "WATCH는 '그사이 바뀌었으면 포기'를 붙여 판단을 가능하게 합니다"의 계산처럼, WATCH는 시도 수가 경합에 따라 급격히 늘어납니다. Lua는 요청마다 한 번씩 줄을 설 뿐입니다.

## 여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다

이 절부터 "원자성이 보장하지 않는 것"까지는 앞의 방법 중 무엇을 고르든 따라오는 조건입니다.

"1인당 1개"를 더하면 재고 키와 구매자 키를 한 번의 실행으로 다뤄야 합니다. 클러스터 모드가 아닌 단일 서버라면 슬롯 검사 자체가 없으므로 신경 쓸 것이 없습니다. 검사는 노드 수가 아니라 클러스터 모드일 때 걸리므로, 노드가 하나인 클러스터에서도 슬롯이 다르면 거부됩니다. 하지만 데이터를 여러 서버에 나누는 Redis Cluster에서는 두 키가 서로 다른 서버에 놓일 수 있습니다. 그래서 이 제약은 Lua 같은 특정 방법이 아니라 **한 번의 실행이 여러 키를 다루는가**에 붙습니다. 키 하나만 다루는 `DECR`이나 `LPOP`은 해당하지 않습니다.

**해시 슬롯**은 Redis Cluster가 데이터를 여러 서버(노드)에 나누는 단위입니다.

- **한 줄**: 키 공간을 16,384개의 칸(해시 슬롯)으로 나누고, 노드마다 일부 칸을 맡깁니다.
- **비유**: 우편번호 구역입니다. 주소(키)를 보면 어느 구역(슬롯)인지 정해지고, 구역마다 담당 우체국(노드)이 있습니다.
- **실제로는**: 키의 슬롯은 키 이름만으로 정해집니다. 키 이름에 `{…}`(해시 태그)가 있으면 중괄호 안의 문자열만으로 정해집니다. 계산 방식은 Redis Cluster에서 다룹니다. 비유와 달리, 함께 다룰 수 있는지 검사하는 기준은 담당 노드가 아니라 슬롯입니다. 두 키가 지금 같은 노드에 있어도 슬롯이 다르면 거부됩니다. 슬롯은 리샤딩(슬롯을 다른 노드로 옮기는 작업)으로 담당 노드가 바뀔 수 있으므로, 지금 같은 노드에 있다는 사실은 오래 보장되지 않습니다.
- **이 주제에서는**: 한 명령, 한 트랜잭션, 한 스크립트가 다루는 키는 모두 같은 슬롯에 있어야 합니다. 다르면 `CROSSSLOT` 에러("Keys in request don't hash to the same slot")를 받습니다. 예외는 "Lua는 실행 중에도 검사하므로 중간에 실패할 수 있습니다"에서 다룹니다.

### 검사 시점이 다르면 실패했을 때 남는 상태가 다릅니다

규칙은 같지만, 키를 언제 검사하는지는 실행 단위마다 다릅니다. 실행 전에 걸리면 아무것도 바뀌지 않고, 실행 중에 걸리면 앞의 쓰기가 남습니다. 아래 표의 `MOVED`는 "그 키의 슬롯은 다른 노드가 맡고 있으니 그쪽으로 보내라"는 응답입니다.

| 실행 단위 | 언제, 어떤 키를 함께 검사하는가 | 다른 슬롯이나 다른 노드의 키가 섞이면 | 남는 상태 |
| --- | --- | --- | --- |
| 여러 키를 받는 단일 명령(예: `MSET`) | 실행 전, 그 명령의 키 전체 | `CROSSSLOT` 또는 `MOVED` | 아무것도 실행되지 않음 |
| `MULTI`/`EXEC` | 대기열에 넣을 때 명령마다 한 번, `EXEC`를 받을 때 대기열 전체를 한 번 | 넣을 때 걸리면 그 명령이 `CROSSSLOT`이나 `MOVED`를 받고 `EXEC`는 `EXECABORT`. `EXEC` 때 걸리면 `EXEC`가 `CROSSSLOT` | 아무것도 실행되지 않음 |
| `WATCH` | `WATCH`를 받을 때, 그 명령에 함께 적은 키끼리 | `CROSSSLOT` 또는 `MOVED` | 감시가 걸리지 않음 |
| Lua 스크립트, Functions | 실행 전에는 `KEYS`로 선언한 키끼리, 실행 중에는 `redis.call`마다 | 실행 전이면 `CROSSSLOT`, 실행 중이면 그 명령에서 에러 | 실행 중 에러면 앞의 쓰기가 남음 |

- **MULTI/EXEC**: 대기열에 넣을 때는 명령 하나의 키만 봅니다. 그래서 "1인당 1개"의 재고 `DECR`과 구매자 `SADD`처럼 각자 키 하나인 명령은, 두 키의 슬롯이 달라도 같은 노드에 있으면 둘 다 `QUEUED`를 받습니다. 대기열 전체를 함께 보는 것은 `EXEC`를 받을 때입니다. 여기서 걸리면 대기열을 버리고 아무것도 실행하지 않습니다.
- **WATCH**: `EXEC` 때 함께 검사하는 범위는 대기열의 명령뿐이고, 감시 중인 키는 들어가지 않습니다. `WATCH`는 `MULTI` 앞에서 따로 실행되는 명령이라 대기열에 들어가지 않기 때문입니다. 그래서 감시 키와 대기열 키가 같은 노드에 있으면 슬롯이 달라도 `EXEC`가 실행됩니다. 하지만 연결 하나는 노드 하나와 이어져 있으므로, 대기열 키가 다른 노드에 있으면 대기열에 넣을 때 `MOVED`를 받고 `EXEC`는 `EXECABORT`가 됩니다. 같은 노드에 있다는 사실은 리샤딩으로 바뀔 수 있으므로, 감시 키도 아래의 해시 태그로 같은 슬롯에 묶어 둡니다.
- **Spring에서는 서버까지 가지 않습니다.** Spring Data Redis의 Lettuce 클러스터 연결은 `MULTI`와 `WATCH`를 서버로 보내지 않고 바로 `InvalidDataAccessApiUsageException`을 던집니다. 클러스터에서 무엇이 달라지는지는 Redis Cluster에서 다룹니다.
- **Lua**: 선언한 키는 실행 전에 거르지만, 선언하지 않은 키는 스크립트가 접근하는 순간에야 알 수 있습니다. 어떤 키에 접근할지는 스크립트의 실행 흐름이 정하기 때문입니다. 이 차이가 다음 절의 중간 실패로 이어집니다.

### Lua는 실행 중에도 검사하므로 중간에 실패할 수 있습니다

선언하지 않은 키에 스크립트 안에서 접근하면 `redis.call`마다 그 명령의 키를 검사합니다. 걸리면 그 명령에서 에러가 납니다. 이미 쓴 내용은 되돌리지 않으므로("대가 2: 중간에 에러가 나도 이미 한 쓰기는 되돌리지 않습니다") 반쯤 반영된 상태가 남을 수 있습니다.

결과는 키가 어디 있는지와 스크립트 종류에 따라 갈립니다. **shebang**은 스크립트 첫 줄에 `#!lua`처럼 적어 실행 조건(플래그)을 선언하는 줄입니다.

| 접근한 키 | shebang 없는 `EVAL` | shebang 있는 `EVAL`, Functions | 그중 `allow-cross-slot-keys` 플래그를 준 경우 |
| --- | --- | --- | --- |
| 다른 노드에 있음 | 에러 | 에러 | 에러 |
| 같은 노드에 있지만 기준 슬롯과 다름 | 허용 | 에러 | 허용 |

- **기준 슬롯**은 실행을 시작할 때 선언한 키의 슬롯입니다. 선언한 키가 없을 때만 처음 접근한 키의 슬롯이 기준이 됩니다. 그래서 `KEYS[1]`과 슬롯이 다른 키에 첫 명령부터 접근해도 에러입니다.
- shebang만 있으면 플래그를 하나도 적지 않아도 가운데 열의 규칙을 따릅니다. shebang이 없는 예전 방식의 스크립트는 호환 모드로 실행되어 같은 노드 안의 다른 슬롯 접근을 허용합니다.
- 허용되는 칸도 안전하지는 않습니다. 그 슬롯이 리샤딩으로 다른 노드로 옮겨지면 첫 줄의 경우가 되어 실패합니다.

그래서 스크립트가 접근하는 키는 모두 `KEYS`로 선언하고 같은 슬롯에 둡니다.

### 해시 태그로 슬롯을 맞추면 그 키들은 한 노드에 몰립니다

"1인당 1개" 예시에서 `stock:{item:1}`, `buyers:{item:1}`처럼 해시 태그를 같게 하면, 두 키 모두 `item:1`만으로 슬롯을 계산하므로 같은 슬롯에 놓입니다. MULTI/EXEC, WATCH, Lua 어느 방법이든 이렇게 맞춥니다.

대가는 같은 태그를 쓴 키가 모두 한 노드에 몰린다는 점입니다. "요청과 데이터가 늘면 무엇이 달라지는가"에서 본 것처럼 한 키에 몰린 요청은 노드를 늘려도 나뉘지 않습니다. 해시 태그는 그 범위를 키 하나에서 태그 하나로 넓힙니다. 그래서 태그는 함께 원자적으로 다뤄야 하는 가장 작은 묶음에만 붙입니다. 이 예시에서는 상품 하나입니다. 모든 상품의 키에 `{stock}`처럼 같은 태그를 붙이면 전체 재고가 한 노드에 모입니다.

## 메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다

재고 키는 지워지면 안 되는 데이터입니다. 그런데 Redis가 메모리 한도에 닿았을 때 무엇을 하는지는 설정에 따라 둘로 갈립니다. 어느 쪽이든 앞에서 본 방법들의 결과가 바뀝니다.

- **한 줄**: `maxmemory`는 Redis가 쓸 메모리의 상한입니다. **축출(eviction)**은 그 상한에 닿았을 때 `maxmemory-policy`가 정한 규칙에 따라 키를 지워 자리를 만드는 동작입니다.
- **비유**: 칸 수가 정해진 보관소입니다. 가득 차면 규칙에 따라 새로 맡기는 것을 거절하거나, 오래 찾지 않은 물건을 치워 자리를 만듭니다. 예시의 재고 키도 치워지는 물건이 될 수 있습니다.
- **실제로는**:
  - `maxmemory`의 기본값은 0이고, 64비트 빌드에서 0은 상한이 없다는 뜻입니다. 상한을 정하지 않으면 이 절의 동작은 일어나지 않습니다. 대신 운영체제 메모리가 부족해지는 문제는 남습니다.
  - 메모리 검사는 명령을 실행하기 전에 합니다. 상한을 넘었으면 먼저 정책에 따라 축출을 시도합니다. 그래도 모자라면 메모리를 늘릴 수 있다고 표시된 명령을 `-OOM command not allowed when used memory > 'maxmemory'.` 에러로 거부합니다. 어떤 명령에 이 표시가 있는지는 `COMMAND INFO <명령>`의 플래그 목록에 `denyoom`이 있는지로 확인합니다.
  - 정책은 크게 셋입니다. `noeviction`(기본값)은 아무것도 지우지 않고 쓰기 명령에 에러를 냅니다. `allkeys-lru`·`allkeys-lfu`·`allkeys-random`은 어떤 키든 지웁니다. `volatile-` 계열은 만료 시간이 있는 키만 지웁니다. 어느 정책이든 지울 수 있는 키가 없으면 메모리가 필요한 쓰기 명령에 에러를 냅니다.
  - **비유와 다른 점**: 치우는 기준은 그 키가 얼마나 중요한가가 아닙니다. 최근 접근, 접근 빈도, 무작위, 만료 시간이 기준입니다. Redis는 재고 키처럼 지워지면 안 되는 키를 따로 알아보지 못합니다.
- **이 주제에서는**: 정책에 따라 아래 두 경우 중 하나가 됩니다.

### noeviction이면 재고가 남아 있어도 차감이 거부됩니다

- `DECR`과 `INCR`은 메모리를 늘릴 수 있는 명령으로 표시되어 있습니다. 상한을 넘은 상태에서는 재고가 남아 있어도 차감이 OOM 에러로 실패합니다.
- "DECR의 반환값으로 판단하기"의 되돌리기 `INCR`도 같은 표시가 있습니다. 차감 직후 상한을 넘으면 되돌리기가 거부되어 음수가 남을 수 있습니다.
- Lua 스크립트는 shebang 유무에 따라 거부되는 시점이 다릅니다.
  - shebang이 없는 스크립트: `EVAL` 자체에는 `denyoom` 표시가 없어 일단 실행됩니다. 대신 스크립트 안의 첫 쓰기 명령(`DECR`)이 OOM 에러로 거부됩니다. 이 검사는 명령을 시작한 시점에 상한을 넘었고, 스크립트가 아직 아무것도 쓰지 않았을 때만 합니다.
  - shebang으로 플래그를 선언한 스크립트: `allow-oom`이나 `no-writes` 플래그가 없으면 실행 전에 거부됩니다.

  어느 쪽이든 첫 쓰기 전에 멈추므로, 반쯤 반영된 상태는 남지 않습니다.
- `LPOP`에는 `denyoom` 표시가 없습니다. 그래서 "재고를 '꺼낼 토큰'으로 바꾸기" 방식은 상한을 넘은 상태에서도 토큰을 꺼낼 수 있습니다. 하지만 같은 요청에서 주문 기록처럼 데이터를 늘리는 쓰기를 하면 그 쓰기는 거부됩니다.

### allkeys 계열이면 재고 키가 지워질 수 있습니다

- `allkeys-` 정책은 만료 시간이 없는 키도 지우므로 재고 키도 대상입니다. LRU·LFU 정책에서는 접근이 드문 상품의 재고 키일수록 대상이 되기 쉽습니다.
- 재고 키가 지워지면 이 문서의 Lua 스크립트는 "값 없음"을 품절로 처리합니다. 초과 판매는 생기지 않지만, 재고가 남아 있는데 판매가 멈춥니다. `DECR` 방식이면 0에서 시작해 -1을 만들고 품절로 판정하며, 만료 시간 없는 새 키가 남습니다. 어느 쪽이든 남은 재고 수라는 정보가 사라집니다.
- `volatile-` 정책은 만료 시간이 있는 키만 지우므로, 만료 시간이 없는 재고 키는 대상이 아닙니다. 대신 만료 시간이 있는 키가 다 지워지면 `noeviction`처럼 쓰기에 에러를 냅니다.

### 고르는 기준

- 재고처럼 지워지면 안 되는 데이터는, 캐시처럼 지워져도 되는 데이터와 같은 인스턴스에 `allkeys-` 정책으로 두지 않습니다.
- 재고 전용 인스턴스를 두고 `noeviction`과 메모리 감시를 함께 쓰는 방법이 가장 단순합니다. 대가는 인스턴스가 하나 늘어나는 것입니다.
- 같은 인스턴스에 둬야 한다면 `volatile-` 정책으로 두고, 캐시 키에만 만료 시간을 줍니다. 대가는 캐시 키가 모자라면 재고 차감도 OOM 에러를 받는다는 점입니다.

## 원자성이 보장하지 않는 것

원자성은 Redis 안에서 끼어들기를 막아 줄 뿐입니다. 다른 저장소와의 일관성이나, 응답을 받지 못한 요청의 결과까지 보장하지는 않습니다. 일반 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)의 "원자성이 보장하지 않는 것"에서 다룹니다. 이 주제에서는 다음 네 가지를 확인해야 합니다.

- **Redis 밖과 묶이지 않습니다.** Lua로 재고를 줄인 뒤 DB에 주문을 저장하다 실패하면, 재고만 줄고 주문은 없습니다. 보상 처리(재고 되돌리기)나 정합성 점검을 따로 설계해야 합니다.
- **응답을 받지 못한 요청은 실행됐을 수 있습니다.** `EVAL`을 보낸 뒤 클라이언트 타임아웃이 나도 스크립트는 서버에서 이미 실행됐을 수 있습니다. 그냥 재시도하면 두 번 차감됩니다. 주문 ID를 기준으로 "이미 처리한 주문인가"를 확인하고 기록하는 일을 차감과 같은 스크립트 안에서 하면 재시도해도 한 번만 줄어듭니다. 이 기록 키도 `KEYS`로 선언하고, 클러스터라면 같은 슬롯에 둬야 하며, 만료 시간을 정해야 합니다.
- **장애 조치 때 확인받은 쓰기가 사라질 수 있습니다.** Redis 복제는 기본적으로 비동기여서, 주 서버가 응답한 쓰기가 복제본에 닿기 전에 장애 조치가 일어나면 그 쓰기를 잃을 수 있습니다(공식 문서 replication: "because Redis uses asynchronous replication it is not possible to ensure the replica actually received a given write, so there is always a window for data loss"). 그러면 차감이 사라져 재고가 되살아날 수 있습니다. 이 문서의 원자성 논의는 이 경우를 막지 못합니다.
- **락과는 보호 대상이 다릅니다.** 지킬 대상이 Redis 안의 값이면 원자적 연산이나 스크립트로 충분하고 락이 필요 없습니다. 락을 쓰면 왕복이 늘고 락의 만료와 보유자 장애를 따로 다뤄야 합니다. 락은 Redis 밖의 작업(외부 API 호출, 다른 저장소 쓰기)을 한 번에 한 요청만 하게 해야 할 때 검토합니다. 분산 락의 설계와 한계는 [Redis 분산 락](./distributed-lock.md)에서 다룹니다.

| Redis 구매자 Set이 있으면 DB 고유 제약은 필요 없다 | 장애 조치·축출·재시작으로 기록을 잃으면 같은 사용자가 다시 통과합니다. 최종 판정은 DB 고유 제약이 맡습니다 | 1인당 1개 |
| 재고 키는 만료 시간이 없으니 지워지지 않는다 | `allkeys-` 정책이면 메모리 한도에서 만료 시간 없는 키도 지워집니다 | 메모리 한도 |
| Redis 원자성이면 주문 전체가 안전하다 | Redis 밖, 응답 유실 뒤 재시도, 장애 조치 유실은 따로 다뤄야 합니다 | 원자성이 보장하지 않는 것 |

### 어떤 방법을 고를까

1. **판단이 값 하나의 증감과 경계로 끝나면 단일 명령**을 먼저 봅니다. `DECR`의 반환값으로 판단하거나 `LPOP` 토큰으로 바꿉니다. 왕복이 가장 적고 서버를 오래 붙잡지 않습니다.
2. **판단이 여러 키나 조건에 걸치면 Lua 스크립트**를 씁니다. 짧게 유지하고, 키는 모두 `KEYS`로 넘기고, 쓰기는 뒤에 모읍니다.
3. **판단 없이 여러 쓰기를 섞이지 않게 반영하려면 MULTI/EXEC**를 씁니다. 단, Spring의 Lettuce 클러스터 연결은 MULTI와 WATCH를 보내기 전에 예외를 던지므로("검사 시점이 다르면 실패했을 때 남는 상태가 다릅니다"), 클러스터에서는 3·4번 대신 스크립트를 씁니다.
4. **WATCH는 경합이 낮고 스크립트를 쓰기 어려운 경우**에만 고려합니다. 예를 들어 운영 정책상 스크립트를 금지한 경우입니다. 선착순처럼 한 키에 요청이 몰리는 곳에는 쓰지 않습니다.

| 중요도 | 항목 | 이유 |
| --- | --- | --- |
| 필수 | `GET` 후 앱에서 판단하고 `DECR`하는 코드 경로 찾기 | 초과 판매의 가장 흔한 원인입니다. |
| 필수 | 스크립트 작업량을 데이터 크기와 무관하게 유지 | 긴 스크립트 하나가 모든 클라이언트의 지연과 `BUSY` 에러가 됩니다. |
| 필수 | 트랜잭션과 스크립트에 롤백이 없다는 전제로 쓰기 순서 설계 | 실패 시 반쯤 반영된 상태가 남습니다. |
| 필수 | 재고 키가 있는 인스턴스의 `maxmemory-policy` 확인 | `allkeys-` 정책이면 재고 키가 지워져 판매가 멈추고, `noeviction`이면 한도에서 차감이 거부됩니다. |

| 필수 | 1인당 1개의 최종 판정을 DB 고유 제약에 두기 | Redis 기록은 장애 조치·축출·재시작으로 사라질 수 있습니다. |
| 알면 유리 | 클러스터에서 키 선언과 해시 태그 | `CROSSSLOT`과 스크립트 중간 실패를 막습니다. 대신 키가 한 노드에 몰립니다. |
| 알면 유리 | 스크립트를 인자화하고 본문을 고정 | 캐시 교체와 `NOSCRIPT` 재전송을 막습니다. |
| 알면 유리 | `busy-reply-threshold`와 `SCRIPT KILL`의 한계 | 장애 때 무엇을 할 수 있고 없는지 미리 알아야 합니다. |
| 참고 | Functions | 여러 서비스가 같은 서버 쪽 로직을 공유할 때 선택지가 됩니다. |

### 개발자가 정할 수 있는 것과 관찰해야 하는 것

- **정할 수 있는 것**: 방법 선택, 스크립트의 작업량과 쓰기 순서, 구매 기록의 구조(Set 하나 또는 사용자별 키)와 정리 시점, 키 이름과 해시 태그, 멱등성 키와 그 만료 시간, 직렬화기, 트랜잭션에 쓸 연결, 클라이언트 타임아웃.
- **관찰해야 하는 것**:
  - `SLOWLOG`에 `EVAL`·`EVALSHA`가 오래 걸린 명령으로 남는지 봅니다.
  - 서버 로그에 "Slow script detected"가 있는지 봅니다.
  - `INFO`의 `errorstats`에서 `BUSY`, `CROSSSLOT`, `NOSCRIPT` 같은 에러가 늘어나는지 봅니다.
  - `INFO`의 `number_of_cached_scripts`, `used_memory_scripts_eval`, `evicted_scripts`로 캐시가 계속 커지거나 교체되는지 봅니다.
  - `INFO`의 `used_memory`와 `maxmemory`로 상한까지 얼마나 남았는지, `maxmemory_policy`로 현재 정책을, `evicted_keys`로 축출이 일어나고 있는지 봅니다.
  - 앱에서는 WATCH를 쓴다면 `EXEC`가 nil을 받은 횟수와 재시도 횟수를, 공통으로는 "남은 재고 + 성공 주문 수 = 처음 재고" 같은 불변식 점검 결과를 남깁니다.

### Spring에서 확인할 것

- **스크립트 실행**: `RedisTemplate.execute(RedisScript, keys, args…)`는 보통 먼저 `EVALSHA`를 보내고, `NOSCRIPT`를 받으면 본문과 함께 `EVAL`로 다시 보냅니다. 단, 연결이 파이프라인 중이거나 MULTI 대기 중이면 `EVALSHA` 없이 `EVAL`을 대기열에 넣기만 하고 **결과로 `null`을 돌려줍니다**. 이때는 스크립트 결과로 성공과 품절을 판단할 수 없습니다. `keys` 목록이 `KEYS`가 되므로 키를 `args`에 섞지 않습니다.
- **직렬화**: 스크립트 인자와 결과는 템플릿의 키·값 직렬화기를 거칩니다(Spring Data Redis 참조 문서 scripting). 스크립트가 값을 숫자로 다룬다면, 인자가 스크립트가 기대하는 바이트(예: `"1"`)로 넘어가는지 확인합니다. 문자열 직렬화기를 쓰는 `StringRedisTemplate`이면 그대로 넘어갑니다. JSON 직렬화기는 설정에 따라 값을 다른 형태(예: 따옴표가 붙은 문자열)로 바꿀 수 있어, `DECR`이나 스크립트의 숫자 변환이 실패할 수 있습니다.
- **결과 타입**: 예시처럼 스크립트가 1과 0을 돌려주면 `RedisScript`의 결과 타입을 `Long`으로 둡니다. 그러면 정수 응답으로 읽습니다. `Double`이나 `Float`으로 두면 정수 응답으로 읽지 않습니다.
- **WATCH와 MULTI/EXEC**: `RedisTemplate`은 여러 호출이 같은 연결을 쓴다고 보장하지 않습니다. 그래서 `SessionCallback` 안에서 실행해 연결을 고정합니다. 중간에 예외가 나면 `discard()`로 트랜잭션 상태를 정리합니다(Spring Data Redis 참조 문서 transactions).
- **`exec()`가 실패를 알리는 모양**: "에러가 나도 되돌리지 않습니다"의 서버 쪽 결말이 `SessionCallback` 안의 `exec()`에서는 다음처럼 옵니다. Spring Data Redis와 Lettuce 소스를 읽은 해석이며 재현하지 않았습니다. `SessionCallback` 안에서 던져진 예외는 `RedisTemplate.execute(SessionCallback)` 밖으로 그대로 나옵니다.
  - **WATCH한 키가 바뀌어 `EXEC`가 nil을 받으면** 예외 없이 결과가 비어 옵니다. `SessionCallback` 안의 `operations.exec()`는 빈 목록을 돌려줍니다(`execute(RedisCallback)`으로 연결을 직접 다룰 때의 `exec()`는 `null`).
  - **`EXECABORT`를 받으면** `RedisSystemException`("Error in execution")을 던집니다. 원인 예외는 Lettuce의 `RedisCommandExecutionException`이고 메시지가 `EXECABORT`로 시작합니다. 명령은 하나도 실행되지 않았습니다. 명령이 대기열에 넣을 때 거부된 경우라면, Spring은 그때 응답을 기다리지 않으므로 어느 명령이 왜 거부됐는지는 이 예외에 담기지 않습니다. `EXEC`의 설명문은 "Transaction discarded because of previous errors."뿐입니다. 반면 `EXEC` 자체가 실행 전 검사에서 거부되면(예: 대기열에 쓰기가 있는데 디스크 오류 상태) 설명문에 원래 오류가 들어갑니다(`EXECABORT Transaction discarded because of: MISCONF ...`). 이 구분과 재시도 판단은 [Redis 오류별 재시도 정책](./retry-policy.md)의 "원인 예외와 오류 접두어로 구분합니다"에 있습니다.
  - **실행 중 에러가 난 명령이 있으면**(예: `WRONGTYPE`) Redis는 나머지 명령을 실행하고 결과 배열을 보냅니다. 하지만 Spring은 결과 목록을 돌려주지 않고, 배열에서 처음 만난 에러를 같은 `RedisSystemException`으로 던집니다. 원인 메시지는 그 명령의 오류(`WRONGTYPE ...`)입니다. 예시의 "재고 `DECR` + 주문 목록 `RPUSH`"라면 재고는 이미 줄었는데, 앱은 예외만 받고 `DECR`의 반환값도 받지 못합니다.
  - 그래서 예외를 "아무것도 반영되지 않았다"로 처리하면 안 됩니다. 원인 메시지의 첫 단어가 `EXECABORT`면 하나도 실행되지 않았고, 그 밖의 Redis 오류면 일부가 반영됐을 수 있습니다. 성공한 명령의 결과까지 받아야 한다면 연결 팩토리의 `convertPipelineAndTxResults`를 끄는 방법이 있습니다. 그러면 `exec()`는 예외를 던지지 않고 오류 객체가 섞인 원래 결과 목록을 돌려줍니다. 대신 그 팩토리를 쓰는 모든 파이프라인·트랜잭션 결과의 역직렬화와 타입 변환이 꺼집니다.
  - 위 모양은 파이프라인 밖에서 부른 `exec()`의 것입니다. `executePipelined` 안에서 `multi()`·`exec()`를 쓰면 `exec()`의 결과가 파이프라인 결과로 넘어가므로, 실패도 `exec()`가 아니라 파이프라인이 끝날 때 `RedisPipelineException`으로 옵니다. 이때의 결과 처리는 [Redis 파이프라이닝과 다중 키 명령](./pipelining.md)의 "파이프라이닝: executePipelined"를 따릅니다.
- **`@Transactional`은 확인 후 행동을 해결하지 않습니다.** 템플릿에 트랜잭션 지원을 켜면 쓰기 명령은 대기열에 쌓였다가 커밋 때 `EXEC`로 실행됩니다. 읽기 명령은 다른 연결로 바로 실행됩니다. 트랜잭션 안에서 쓴 값은 그 안의 읽기에서 보이지 않습니다(Spring Data Redis 참조 문서 transactions). 재고를 읽고 판단하는 로직을 감싸도 틈은 그대로입니다. Redis의 `EXEC`와 DB의 커밋도 서로 다른 커밋입니다. 또 이 상태에서 스크립트를 실행하면 결과를 받지 못합니다. 읽기 전용이 아닌 트랜잭션이면 현재 스레드에 묶인 연결에 `MULTI`가 먼저 보내져 있습니다. `EVAL`은 쓰기 명령으로 분류되어 그 연결로 가므로, 위의 "MULTI 대기 중" 경우가 되어 `null`이 돌아옵니다. 재고 차감 스크립트는 트랜잭션 지원을 끈 템플릿으로 실행하거나 트랜잭션 밖에서 실행해야 결과를 받습니다.
- **재시도 설정**: Spring Retry 같은 재시도 도구를 Redis 차감 호출에 걸려면, 먼저 멱등하게 만들어야 합니다.

## 말로 설명하기

### 30초 버전

Redis는 메인 스레드 하나가 명령을 하나씩 끝까지 실행하므로 명령 하나는 원자적입니다. 하지만 `GET`으로 재고를 읽고 앱에서 판단한 뒤 `DECR`하면, 두 명령 사이에 다른 요청이 끼어들어 재고 1개에 주문 2건이 생깁니다. 판단이 단순하면 `DECR`의 반환값처럼 판단을 담은 명령 하나로 풉니다. 여러 조건이 걸리면 Lua 스크립트로 확인과 차감을 서버 안에서 한 번에 실행합니다. 스크립트는 도는 동안 서버 전체를 막고, 실패해도 되돌리지 않으므로 짧게 쓰고 쓰기를 뒤에 모아야 합니다.

### 2분 버전

Redis에서 키를 읽고 바꾸는 명령은 메인 스레드 하나가 실행합니다. I/O 스레드를 켜도 실행은 메인 스레드가 하므로, 명령 하나는 다른 명령과 섞이지 않습니다. 문제는 명령 사이입니다. 재고 1개에 두 요청이 각각 `GET`으로 1을 읽고 `DECR`하면, 둘 다 통과해 재고가 -1이 됩니다. 확인과 차감이 다른 명령이라 그 사이에 틈이 있기 때문입니다.

이 틈을 없애는 방법은 네 가지입니다. 첫째, 판단을 명령 하나에 담습니다. `DECR`의 반환값이 0 이상이면 성공으로 보거나, 재고를 List 토큰으로 바꿔 `LPOP`으로 꺼냅니다. 둘째, MULTI/EXEC는 명령을 끼어들기 없이 묶어 실행하지만 대기열 안에서 결과를 볼 수 없어 조건 분기를 못 합니다. 셋째, WATCH를 붙이면 그사이 키가 바뀌었을 때 `EXEC`가 실행을 포기하므로 낙관적 방식으로 판단할 수 있습니다. 대신 왕복이 많고 한 키에 요청이 몰리면 재시도가 폭증합니다. 넷째, Lua 스크립트는 읽기, 판단, 쓰기를 서버 안에서 한 번에 실행해 왕복 1번으로 끝납니다.

Lua의 대가는 분명합니다. 스크립트가 도는 동안 다른 모든 명령이 기다립니다. `busy-reply-threshold`를 넘어도 스크립트는 멈추지 않고 다른 클라이언트가 `BUSY`를 받으며, 쓰기를 했다면 `SCRIPT KILL`도 안 됩니다. 중간에 에러가 나도 앞의 쓰기는 남습니다. "1인당 1개"처럼 판정이 두 키에 걸치면, 재고 확인과 `SADD`의 반환값 확인과 차감을 스크립트 하나에 넣어야 합니다. 두 명령으로 나누면 어느 순서로 하든 장애 뒤에 기록이나 차감만 남습니다. 방법과 상관없이 따라오는 조건도 있습니다. 클러스터에서는 한 번에 다루는 키가 모두 같은 슬롯에 있어야 하므로 해시 태그로 묶고, 스크립트라면 키를 `KEYS`로 선언합니다. 마지막으로 원자성은 Redis 안의 끼어들기만 막으므로, DB와의 일관성, 타임아웃 뒤 재시도, 장애 조치 때의 유실은 멱등성과 보상 처리로 따로 다뤄야 합니다.

### 예상 질문과 꼬리 질문

**Q. Redis 명령은 왜 원자적인가요?**
키를 읽고 바꾸는 명령은 메인 스레드 하나가 실행하고, 명령 하나를 끝낸 뒤 다음 명령을 시작하기 때문입니다. 그래서 명령 실행 도중 다른 클라이언트의 명령이 끼어들지 않습니다. 여기서 원자적이라는 말은 끼어들기가 없다는 뜻이지, 실패 시 되돌린다는 뜻이 아닙니다. (본문: "Redis는 명령을 메인 스레드 하나에서 하나씩 끝까지 실행합니다")

- **꼬리: I/O 스레드를 켜면 원자성이 깨지나요?**
  아닙니다. I/O 스레드는 소켓 읽기·쓰기와 요청 해석을 맡고, 다 읽은 요청은 메인 스레드에 넘겨 실행합니다.
- **꼬리: 그럼 Redis를 쓰면 경쟁 상태가 없나요?**
  있습니다. 명령 하나는 섞이지 않지만, 클라이언트가 읽기와 쓰기를 다른 명령으로 보내면 그 사이에 다른 클라이언트의 명령이 들어옵니다.

**Q. 재고를 `GET`으로 확인하고 `DECR`하면 왜 문제인가요?**
두 요청이 모두 `GET`으로 1을 읽으면, 둘 다 "1 이상"으로 판단하고 `DECR`을 보냅니다. 결과는 재고 -1, 주문 2건입니다. 확인과 차감이 다른 명령이라 사이에 틈이 있는 확인 후 행동형 경쟁 상태입니다. (본문: "왜 둘 다 성공하는가: 명령과 명령 사이의 틈")

- **꼬리: `DECR`만 쓰면 해결되나요?**
  `DECR`의 반환값으로 판단하면 해결됩니다. 반환값이 0 이상인 요청만 성공으로 보고, 음수면 `INCR`로 되돌립니다. 다만 되돌리기 전까지 음수가 보이고, 되돌리기 전에 장애가 나면 음수가 남습니다. 키가 없으면 0에서 시작해 -1을 만든다는 점도 조심해야 합니다.

**Q. MULTI/EXEC로 재고 확인과 차감을 묶으면 안 되나요?**
안 됩니다. MULTI 뒤의 명령은 `QUEUED`만 돌려주고 `EXEC` 때 한꺼번에 실행되므로, `GET` 결과를 보고 `DECR`을 할지 정할 수 없습니다. MULTI/EXEC는 판단 없이 여러 쓰기를 섞이지 않게 반영할 때 씁니다. (본문: "MULTI/EXEC는 명령을 묶어 실행하지만, 중간 결과로 판단할 수 없습니다")

- **꼬리: MULTI/EXEC 안의 명령 하나가 실패하면 롤백되나요?**
  대기열에 넣을 때 발견된 에러(문법, 인자 개수 등)면 `EXEC`가 `EXECABORT`로 아무것도 실행하지 않습니다. 실행 중 에러(예: `WRONGTYPE`)면 그 명령만 실패하고 나머지는 실행되며, 되돌리지 않습니다.
- **꼬리: 파이프라이닝과는 무엇이 다른가요?**
  파이프라이닝은 응답을 기다리지 않고 명령을 연달아 보내 왕복을 줄일 뿐, 다른 클라이언트 명령의 끼어들기를 막지 않습니다. MULTI/EXEC는 `EXEC` 실행 동안 끼어들기를 막습니다.

**Q. WATCH는 어떻게 동작하고, 언제 불리한가요?**
WATCH한 키를 `EXEC` 전에 누군가 바꾸면, Redis가 그 연결에 표시를 붙이고 `EXEC`가 대기열을 실행하지 않고 nil을 돌려줍니다. 클라이언트는 처음부터 다시 시도합니다. 낙관적 방식이라 충돌이 드물면 괜찮습니다. 하지만 한 키에 요청이 몰리면 대부분이 실패하고 재시도해 시도 수가 크게 늘어납니다. 시도마다 명령 다섯 개와 왕복 최소 2번이 들고, 같은 연결을 붙잡아 둬야 합니다. (본문: "WATCH는 '그사이 바뀌었으면 포기'를 붙여 판단을 가능하게 합니다")

- **꼬리: 같은 값으로 덮어써도 WATCH가 깨지나요?**
  깨집니다. Redis는 값을 비교하지 않고 그 키에 수정 신호가 있었는지만 봅니다. 그래서 ABA 문제는 없지만 불필요한 실패가 생길 수 있습니다.
- **꼬리: WATCH한 키가 만료되면요?**
  WATCH할 때 살아 있던 키가 `EXEC` 때 만료되어 있으면 실패합니다. WATCH할 때 이미 만료돼 있던 키는 이 검사에서 뺍니다. 공식 문서는 만료와 메모리 한도에 의한 삭제도 수정으로 친다고 설명합니다.

**Q. Lua 스크립트는 왜 원자적이고, 대가는 무엇인가요?**
스크립트 전체가 `EVAL` 명령 하나로 메인 스레드에서 실행되므로, 끝날 때까지 다른 명령이 끼어들지 않습니다. 스크립트 안에서 읽은 값으로 분기할 수 있어 확인과 차감을 한 번에 할 수 있고 왕복도 1번입니다. 대가는 세 가지입니다. 도는 동안 모든 클라이언트가 기다리고, 에러가 나도 앞의 쓰기가 남고, 스크립트 캐시는 비워질 수 있습니다. (본문: "Lua 스크립트는 판단과 변경을 서버 안에서 한 번에 실행합니다")

- **꼬리: 스크립트가 5초 넘게 돌면 어떻게 되나요?**
  기본 `busy-reply-threshold`(5,000밀리초)를 넘으면 Redis는 경고 로그를 남기고, 다른 클라이언트에 `BUSY` 에러로 응답하기 시작합니다. 스크립트는 멈추지 않고 계속 돕니다. 쓰기 전이면 `SCRIPT KILL`로 멈출 수 있습니다. 쓰기 후면 원자성을 깨지 않으려고 `SCRIPT KILL`을 거부하므로, 기다리거나 `SHUTDOWN NOSAVE`로 서버를 내려야 합니다.
- **꼬리: 스크립트 중간에 에러가 나면요?**
  에러가 클라이언트로 돌아가고, 그 전에 실행한 쓰기는 남습니다. 그래서 읽고 검증하는 단계를 앞에, 쓰기를 뒤에 모아 둡니다.
- **꼬리: 스크립트 안에서 키 이름을 만들어 쓰면 안 되나요?**
  클러스터는 `KEYS`로 선언된 키를 보고 요청을 보낼 노드를 정합니다. 선언하지 않은 키는 스크립트가 접근하는 순간에야 검사되므로, 그 키가 다른 노드에 있으면 스크립트 중간에 에러가 납니다. shebang(`#!lua`)이 있는 스크립트와 Functions는 같은 노드라도 선언한 키나 앞서 접근한 키와 슬롯이 다르면 에러가 납니다(`allow-cross-slot-keys` 플래그가 없을 때). 어느 경우든 앞의 쓰기는 남습니다. 키는 모두 `KEYS`로 넘깁니다.

**Q. 클러스터에서 키를 같은 슬롯에 둬야 하는 것은 Lua만의 제약인가요?**
아닙니다. 조건은 방법이 아니라 한 번의 실행이 여러 키를 다루는가입니다. `MSET` 같은 다중 키 명령, MULTI/EXEC, 키를 여럿 적은 `WATCH`는 키의 슬롯이 다르면 `CROSSSLOT` 에러를 받고, 같은 노드에 있어도 거부됩니다. 다만 MULTI/EXEC에서 대기열의 키가 다른 노드에 있으면 대기열에 넣을 때 `MOVED`를 받습니다. Lua는 `KEYS`로 선언한 키끼리 슬롯이 다를 때 실행 전에 `CROSSSLOT`을 받습니다. 선언하지 않은 키는 실행 중에 검사되며, 결과는 "Lua는 실행 중에도 검사하므로 중간에 실패할 수 있습니다"의 표를 따릅니다. 예를 들어 shebang 없는 `EVAL`은 같은 노드 안이면 슬롯이 달라도 허용됩니다. 키 하나만 다루는 `DECR`이나 `LPOP`은 해당하지 않습니다. `{item:1}` 같은 해시 태그로 슬롯을 맞추고, 대신 같은 태그의 키가 한 노드에 몰립니다. (본문: "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다")

- **꼬리: 그럼 방법마다 차이는 없나요?**
  실패했을 때 남는 상태가 다릅니다. MULTI/EXEC는 `EXEC`를 받을 때 대기열 전체의 키를 검사하므로, 걸리면 아무것도 실행하지 않습니다. Lua는 `KEYS`로 선언한 키는 실행 전에 검사하지만, 선언하지 않은 키는 접근하는 순간에 검사하므로 앞의 쓰기가 남은 채 실패할 수 있습니다.
- **꼬리: WATCH한 키와 MULTI 안의 키도 같은 슬롯이어야 하나요?**
  `EXEC`가 함께 검사하는 것은 대기열의 키뿐이라, 같은 노드라면 슬롯이 달라도 실행됩니다. 다른 노드라면 대기열에 넣을 때 `MOVED`를 받아 `EXEC`가 `EXECABORT`가 됩니다. 슬롯은 리샤딩으로 다른 노드로 옮겨질 수 있으므로 같은 해시 태그로 묶어 두는 편이 안전합니다.

**Q. `EVALSHA`를 쓰는데 가끔 `NOSCRIPT` 에러가 납니다. 왜인가요?**
스크립트 캐시는 재시작, 장애 조치, `SCRIPT FLUSH`로 비워질 수 있습니다. `EVAL`로 들어온 스크립트가 정해진 개수를 넘으면 오래 쓰지 않은 것부터 지워집니다. Spring의 기본 실행기는 `NOSCRIPT`를 받으면 `EVAL`로 다시 보냅니다. `NOSCRIPT`가 자주 나고 `evicted_scripts`가 늘면, 값을 본문에 끼워 넣어 스크립트를 매번 새로 만들고 있지 않은지 확인합니다. (본문: "대가 3: 스크립트 캐시는 언제든 비워질 수 있습니다")

**Q. 선착순 이벤트처럼 한 상품에 요청이 몰리면 어떤 방법을 쓰나요?**
판단이 단순하면 `DECR` 반환값이나 `LPOP` 토큰 같은 단일 명령을 씁니다. 조건이 여러 개면 짧은 Lua 스크립트를 씁니다. WATCH는 재시도가 폭증하므로 피합니다. 어떤 방법이든 그 키는 노드 하나의 메인 스레드가 처리하므로, 클러스터를 늘려도 그 키의 처리량은 늘지 않는다는 점을 알고 있어야 합니다. (본문: "요청과 데이터가 늘면 무엇이 달라지는가")

**Q. 선착순 쿠폰을 한 사람이 한 장만 받게 하려면 어떻게 하나요?**
"남은 수량이 있는가", "이 사용자가 이미 받았는가", "수량 차감과 수령 기록"을 Lua 스크립트 하나에서 판정합니다. 스크립트는 수량을 먼저 읽어 품절이면 아무것도 쓰지 않고 끝내고, 수령자 Set에 `SADD`해 0이 나오면 이미 받음으로 끝내고, 1이 나오면 수량을 `DECR`합니다. 수령자 Set과 수량 키는 클러스터에서 같은 해시 태그로 묶습니다. 그리고 Redis 기록은 잃을 수 있으므로 DB에 (쿠폰, 사용자) 고유 제약을 두어 최종 판정을 맡깁니다. (본문: "1인당 1개는 구매 기록과 재고 차감을 한 번에 판정해야 합니다")

- **꼬리: `SADD`가 이미 원자적인데 왜 스크립트까지 필요한가요?**
  `SADD`는 사용자 판정만 원자적으로 합니다. 수량 차감은 다른 명령이라, 기록을 먼저 하면 차감 전에 장애가 났을 때 받지도 않은 사용자가 "이미 받음"이 되고, 차감을 먼저 하면 되돌리기 전까지 다른 사용자가 품절을 보거나 장애 뒤 수량이 줄어든 채 남습니다. 되돌리기도 따로 보내는 명령이라 빠질 수 있습니다.
- **꼬리: `SET NX`로 사용자마다 키를 두면 스크립트 없이 되나요?**
  안 됩니다. `SET NX`도 사용자 판정 하나를 원자적으로 할 뿐, 수량 차감과는 다른 명령입니다. 같은 스크립트 안에 넣어야 합니다. 사용자별 키는 값에 주문 ID를 담을 수 있다는 장점이 있지만, 키마다 이름과 관리 정보가 붙고(전체 메모리의 대소는 같은 데이터로 재 봐야 합니다) 판매 뒤 정리가 번거롭습니다.
- **꼬리: 타임아웃 뒤 같은 요청을 재시도하면요?**
  첫 시도가 이미 실행됐다면 재시도는 수량이 남아 있으면 "이미 받음"을, 첫 시도가 마지막 수량을 가져갔으면 품절을 받습니다. 수량이 두 번 줄지는 않지만, 앱은 자기 요청이 성공한 것인지 모릅니다. 주문 ID를 함께 기록하고 수량 확인보다 먼저 이 주문 ID가 기록돼 있는지 봅니다. 기록돼 있으면 Redis 쪽 처리가 끝난 재시도이므로, DB 주문 저장을 이어 가거나 저장 결과를 확인해 응답합니다.
- **꼬리: 이벤트가 커서 수령자가 수십만 명이면요?**
  `SADD`의 공식 복잡도가 원소 하나당 O(1)이라 스크립트의 작업량은 수령자 수에 비례해 늘지 않습니다. 대신 Set은 수령자 수만큼 커지고, 기준을 넘으면 원소마다 따로 할당하는 표현으로 바뀌어 지울 때 원소마다 해제해야 합니다. 이벤트가 끝나면 `UNLINK`로 지우고, 전체를 한 번에 읽지 않습니다.
- **꼬리: DB 고유 제약이 최종 판정이면 Redis는 왜 두나요?**
  정확성이 아니라 효율 때문입니다. 몰린 요청 대부분을 Redis에서 품절이나 이미 받음으로 돌려보내 DB까지 가는 쓰기를 줄입니다. Redis 기록을 잃어 같은 사용자가 다시 통과하면 DB가 막고, 이때는 Redis 수량만 되돌리고 수령 기록은 지우지 않습니다.

**Q. Redis 메모리가 가득 차면 재고 차감은 어떻게 되나요?**
`maxmemory-policy`에 따라 다릅니다. 기본값 `noeviction`이면 상한을 넘은 상태에서 `DECR`처럼 메모리를 늘릴 수 있는 쓰기가 OOM 에러로 거부됩니다. 재고가 남아 있어도 차감이 실패합니다. `allkeys-` 정책이면 재고 키 자체가 지워질 수 있고, 스크립트는 "값 없음"을 품절로 처리하므로 재고가 남았는데 판매가 멈춥니다. 재고처럼 지워지면 안 되는 키는 캐시와 같은 인스턴스에 `allkeys-` 정책으로 두지 않고, 전용 인스턴스나 `volatile-` 정책을 씁니다. (본문: "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다")

- **꼬리: 스크립트가 쓰다가 OOM으로 멈추면 반쯤 반영되나요?**
  아닙니다. OOM 검사는 스크립트의 첫 쓰기 전에만 하므로, 거부되면 아무것도 쓰지 않은 상태입니다. 첫 쓰기 이후에는 OOM 검사로 멈추지 않습니다.

**Q. Redis에서 재고를 줄인 뒤 DB 주문 저장이 실패하면요?**
Redis의 원자성은 Redis 안에서만 통하므로, 재고만 줄고 주문은 없는 상태가 남습니다. 재고를 되돌리는 보상 처리나 정합성 점검을 따로 설계해야 합니다. (본문: "원자성이 보장하지 않는 것")

- **꼬리: 클라이언트 타임아웃이 나서 재시도하면요?**
  스크립트는 이미 실행됐을 수 있으므로 두 번 차감될 수 있습니다. 주문 ID로 "이미 처리했는가"를 확인하고 기록하는 일을 차감과 같은 스크립트 안에서 해 멱등하게 만듭니다.
- **꼬리: 장애 조치가 일어나면요?**
  복제가 기본적으로 비동기이므로, 응답까지 받은 차감이 복제본에 닿기 전에 장애 조치가 일어나면 사라질 수 있습니다. 원자성으로는 막을 수 없는 문제입니다.

**Q. Spring에서 `@Transactional`로 Redis 작업을 감싸면 원자적인가요?**
확인 후 행동 문제는 풀리지 않습니다. 트랜잭션 지원을 켜면 쓰기는 대기열에 쌓였다가 커밋 때 `EXEC`로 실행되고, 읽기는 다른 연결로 바로 실행됩니다. 그래서 읽고 판단하는 사이의 틈은 그대로입니다. Redis의 `EXEC`와 DB 커밋도 서로 다른 커밋입니다. 게다가 이 안에서 `RedisTemplate.execute`로 스크립트를 실행하면, 연결이 MULTI 대기 중이라 스크립트가 대기열에 들어가고 결과로 `null`이 돌아옵니다. 재고 차감은 Lua 스크립트를 트랜잭션 지원을 끈 템플릿으로, 또는 트랜잭션 밖에서 `RedisTemplate.execute`로 실행해야 결과로 성공과 품절을 판단할 수 있습니다. (본문: "Spring에서 확인할 것")

- **꼬리: WATCH를 Spring에서 쓰려면요?**
  `RedisTemplate`은 호출마다 같은 연결을 보장하지 않으므로 `SessionCallback` 안에서 `watch`, `multi`, `exec`를 실행해 연결을 고정합니다.

**Q. 분산 락을 걸고 `GET`·`DECR`하는 것과 Lua 스크립트는 어떻게 다른가요?**
지킬 대상이 Redis 안의 재고 값이면 Lua 스크립트 하나로 충분하고 왕복도 1번입니다. 락을 쓰면 락 획득과 해제 왕복이 더해지고, 락 만료와 보유자 장애를 따로 다뤄야 합니다. 락은 Redis 밖의 작업까지 한 번에 한 요청만 하게 해야 할 때 검토합니다. (본문: "원자성이 보장하지 않는 것")

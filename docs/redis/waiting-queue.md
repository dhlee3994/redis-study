# Redis 입장 대기열: 몰린 요청을 줄 세워 들여보내면 무엇이 달라지는가

> **핵심 질문**: 인기 상품 하나에 요청 수천 개가 한꺼번에 몰리면, 락은 한 번에 한 요청만 들여보내므로 처리량이 늘지 않습니다. Redis로 선착순 입장 대기열을 앞에 두면 무엇이 달라지는가? 무엇을 대가로 치르는가? 서비스에서는 무엇을 선택하고 확인해야 하는가?
>
> **범위**: 상품 하나의 대기열을 Redis에 두는 경우를 다룹니다. 복제본, 클러스터, 장애 조치는 대기열이 잃는 것과 몰리는 곳까지만 다룹니다. 대기열 뒤의 주문 처리(락과 DB)는 [Redis 분산 락](./distributed-lock.md)의 방식을 그대로 쓰고 다시 설명하지 않습니다. 봇과 다중 계정 차단, 결제, 대기열 전용 외부 제품, 여러 지역에 걸친 대기열은 다루지 않습니다.
>
> **출처와 설계의 구분**: 명령의 동작과 복잡도, 설정 기본값, 복제와 장애 조치의 성질은 "근거"에 적은 소스와 공식 문서로 확인했습니다. 키 구성, 스크립트의 단계, 입장 규칙, 예시의 수치는 공식 문서에 있는 패턴이 아닙니다. 확인한 명령 동작 위에 이 문서가 세운 설계입니다. 그런 문장에는 그 자리에 "이 문서의 설계" 또는 "이 문서의 추론"이라고 적었고, 모두 재현해 보지 않았습니다.

## 배경 지식

### 이 문서의 예시: 재고 3개, 회원 5명, 한 번에 2명

문서 끝까지 다음 장면 하나를 씁니다.

- 한정판 상품 1(`item:1`)의 재고는 DB에 **3개** 있습니다. 판매는 10:00:00에 시작합니다.
- 회원 u1~u5가 10:00:00.1부터 0.1초 간격으로 차례로 들어옵니다. 회원 ID는 서버가 로그인 세션에서 꺼낸 값입니다. 브라우저가 보낸 값을 그대로 믿지 않습니다.
- 주문 API 서버는 S1, S2 두 대입니다. 두 서버는 같은 Redis와 같은 DB를 씁니다.
- 대기열 뒤의 주문 단계는 분산 락 문서의 방식 그대로입니다. **재고를 정확하게 지키는 것은 주문 단계의 락과 DB 확인입니다.** 한 회원은 1개만 살 수 있고, 이 규칙도 주문 단계가 DB에서 지킵니다(예: 회원과 상품의 고유 제약). 대기열은 그 앞에서 누가 언제 주문 단계에 들어갈지만 정합니다.
- 대기열 규칙은 다음과 같습니다(이 문서의 설계).
  - 입장권을 가진 회원, 곧 주문 화면에 들어가 있을 수 있는 회원은 동시에 **2명**까지입니다. 이를 동시 입장 상한이라고 부릅니다. 세는 것은 입장권이지 실제로 처리 중인 주문 요청이 아닙니다. 두 수가 어긋나는 경우는 "동시 입장 상한과 입장 속도 상한을 함께 둡니다"에서 다룹니다.
  - 들어간 회원에게 주는 입장권의 기한은 **120초**입니다.
  - S1과 S2는 각각 1초마다 입장 처리를 돌립니다. 입장 처리는 같은 1초 안에 한 번만 실제로 들여보내고, 한 번에 최대 **2명**까지 들여보냅니다.
- **바라는 결과**: 주문은 재고 수인 3건을 넘지 않습니다. 먼저 온 회원부터 주문 기회를 얻고, 주문 단계에는 한 번에 2명까지만 들어갑니다.

Redis에는 상품 1마다 키 세 개를 둡니다(이 문서의 설계). 키 이름의 `{item:1}`은 클러스터에서 세 키를 같은 곳에 두기 위한 표시입니다. "클러스터: 상품 하나의 대기열은 노드 하나에 있습니다"에서 다룹니다.

| 키 | 자료형 | 담는 것 |
| --- | --- | --- |
| `queue:{item:1}` | Sorted Set | 기다리는 회원. 원소는 회원 ID, 점수는 대기 번호 |
| `ticket:{item:1}` | Sorted Set | 입장권을 가진 회원. 원소는 회원 ID, 점수는 입장권 만료 시각(Redis 서버 시각, 밀리초) |
| `state:{item:1}` | Hash | 필드 `seq`(마지막으로 내준 대기 번호), `soldout`(있으면 품절), `admitted_at`(간격 확인을 통과한 마지막 입장 처리 시각), `open_at`(판매 시작 시각, 밀리초) |

Hash는 필드 이름과 값의 쌍을 여러 개 담는 Redis 자료형입니다. 키 하나에 Kotlin의 `Map<String, String>` 하나를 둔 것과 비슷합니다. 대기열의 작은 상태 값 몇 개를 한 키에 모으려고 썼습니다.

```text
 browsers (u1..u5)         order API servers             Redis
+--------------+  enter   +-----------------+  scripts  +--------------------+
|  u1 ... u5   |--------->| S1              |---------->| queue:{item:1}     |
|              |  poll    |  enter / poll   |           | ticket:{item:1}    |
|              |--------->|  admit (1s)     |           | state:{item:1}     |
|              |  order   |  order          |           +--------------------+
|              |--------->| S2 (same)       |
+--------------+          +-----------------+
                                   |  lock + SQL (order stage)
                                   v
                          +------------------+
                          | Redis lock, DB   |
                          | item 1 stock = 3 |
                          +------------------+
```

화살표는 요청이 가는 방향입니다. `enter`는 줄 서기, `poll`은 순번 묻기, `order`는 주문입니다. `admit (1s)`는 서버가 1초마다 스스로 돌리는 입장 처리이고, `scripts`는 이 요청들이 Redis에 보내는 Lua 스크립트입니다. 주문 단계의 락 키를 대기열과 같은 Redis에 둘지는 정하지 않았으므로 따로 그렸습니다. 복제본과 연결 풀은 그림에서 뺐습니다. 복제본은 "장애 조치와 재시작 때 잃는 것"에서 다룹니다.

비용을 계산하는 곳에서만 같은 장면을 키웁니다. 손으로 따라가기에는 5명이면 충분하지만, 폴링과 처리량의 비용은 사람이 많아야 보이기 때문입니다. **키운 장면**에서는 재고가 3,000개이고, 판매 시작 순간에 회원 10,000명이 들어오며, 주문 단계는 초당 20건을 처리합니다. 20건은 분산 락 문서에서 락 보유 시간 50밀리초로 계산한 가상 수치입니다. 키운 장면의 숫자는 모두 가상 예시입니다.

### 이 문서가 기대는 원리들

- **경쟁 상태, 원자성, 멱등성**: 경쟁 상태는 실행 순서에 따라 결과가 틀어지는 문제입니다. 원자성은 여러 단계를 남이 중간에 보거나 끼어들 수 없게 묶는 성질이고, 멱등성은 같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질입니다. 이 주제에서는 두 서버가 동시에 입장 처리를 돌려도 자리보다 많이 들여보내지 않아야 합니다. 그리고 응답을 받지 못한 회원이 다시 줄을 서도 번호가 둘이 되면 안 됩니다. 원리는 [경쟁 상태와 원자성](../cs/race-condition-and-atomicity.md)에서 다룹니다.
- **Redis의 명령과 Lua 스크립트**: Redis는 명령 하나나 Lua 스크립트 하나를 끝까지 실행하며, 그동안 다른 연결의 명령이 끼어들지 않습니다. 명령 두 개 사이에는 끼어들 수 있습니다. 스크립트가 도는 동안에는 다른 모든 명령이 기다리고, 스크립트가 중간에 실패해도 앞의 쓰기는 되돌리지 않습니다. 이 주제에서는 "확인하고 바꾸는" 대기열 작업을 각각 스크립트 하나로 만듭니다. 자세한 동작과 대가는 [Redis 원자성](./atomicity.md)에서 다룹니다.
- **리스**: 정해진 기간 동안만 유효한 권리입니다. 보유자는 자기 기한이 끝난 것을 스스로 알지 못할 수 있습니다. 이 주제의 입장권이 리스입니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)에서 다룹니다. 리스가 깨져도 되는 효율용과 깨지면 안 되는 정확성용의 구분도 그 문서에 있습니다.
- **밀린 양**: 처리하는 속도보다 들어오는 속도가 빠르면 처리되지 않은 일이 쌓입니다. 이때 쌓인 양과 가장 오래 기다린 시간을 함께 봐야 합니다. 대기열은 몰린 요청을 쌓아 두는 자리입니다. 원리는 [메시지 큐 기초](../cs/message-queue.md)에서 다룹니다.

### 처리량, 머무는 시간, 동시에 머무는 수

이 문서의 숫자 계산은 거의 모두 다음 관계에서 나옵니다. 이 원리를 다루는 CS 문서가 따로 없으므로 여기서 설명합니다.

- **한 줄**: 평균적으로 초당 λ(람다)명이 들어오고 각자 평균 W초 머문다면, 안에 동시에 머무는 사람은 평균 λ × W명입니다. 이 관계를 리틀의 법칙(Little's law)이라고 부릅니다.
- **비유**: 놀이공원 입구에서 1초에 2명씩 들여보내고, 사람들이 평균 60초 머물다 나간다고 합시다. 그러면 공원 안에는 평균 120명이 있습니다.
- **실제로는**:
  - 세 값은 모두 **긴 시간에 걸친 평균**입니다. 들어오는 속도와 나가는 속도가 균형을 이룬 상태에서 성립합니다. 판매 시작 직후처럼 한꺼번에 몰리는 순간의 값은 알려 주지 않습니다.
  - 관계를 바꿔 읽으면 계산 두 가지가 나옵니다. 첫째, 안에 둘 수 있는 수(동시 수)를 정해 두면 처리량은 "동시 수 ÷ 머무는 시간"을 넘지 못합니다. 둘째, 줄의 p번째 사람은 앞의 p명이 다 들어갈 때까지 대략 "p ÷ 입장 속도"초를 기다립니다.
  - **비유와 다른 점**: 놀이공원 입구는 사람들이 얼마나 머물든 정해진 속도로 들여보냅니다. 이 문서의 입장 처리는 빈자리 수를 보고 들여보내므로, 머무는 시간이 길어지면 입장 속도가 저절로 느려집니다. 이 차이는 "동시 입장 상한과 입장 속도 상한을 함께 둡니다"에서 다룹니다.
- **이 주제에서는**: 락 하나는 동시 수가 1이고 머무는 시간이 보유 시간입니다. 그래서 처리량이 "1 ÷ 보유 시간"이고, 분산 락 문서의 "요청과 데이터가 늘면 무엇이 달라지는가"에 나온 초당 20건이 이렇게 나옵니다. **대기열은 이 상한을 바꾸지 못합니다.** 바꾸는 것은 상한을 넘어 온 사람들이 어디서 무엇을 붙잡고 기다리는가입니다.

### Sorted Set: 점수 순으로 늘어선, 중복 없는 집합

- **한 줄**: 원소마다 숫자 점수가 붙어 있고, 원소들이 중복 없이 점수 순서로 늘어서 있는 Redis 자료형입니다.
- **비유**: 번호표가 붙은 대기 명단입니다. 한 사람은 명단에 한 번만 오릅니다. 명단은 늘 번호 순으로 정렬되어 있어서 "u4는 앞에서 몇 번째인가"를 바로 셀 수 있습니다. 예시의 `queue:{item:1}`이 이 명단입니다.
- **실제로는**:
  - 원소는 문자열이고, 같은 원소는 하나만 있습니다. 이미 있는 원소를 `ZADD`하면 원소가 새로 생기지 않고 점수만 바뀝니다. `CH`나 `INCR` 옵션이 없으면 `ZADD`는 새로 추가된 원소 수를 돌려주므로, 이미 있던 원소였다면 0을 돌려줍니다.
  - 점수는 64비트 부동소수점 수(double)입니다. 정수는 -(2^53)부터 2^53까지만 정확하게 담깁니다(공식 문서 zadd, "Range of integer scores that can be expressed precisely"). 대기 번호나 밀리초 단위의 현재 시각(13자리)은 이 범위 안입니다.
  - 정렬은 점수가 먼저입니다. 점수가 같으면 원소 문자열을 바이트 단위로 비교한 순서를 따릅니다(공식 문서 zadd, "Elements with the same score").
  - **번호와 순번은 다릅니다.** 이 문서에서 점수로 쓰는 대기 번호는 원소에 붙은 값이라 바뀌지 않습니다. 순번(rank)은 지금 내 앞에 몇 명이 있는가이며, 앞사람이 빠질 때마다 줄어듭니다. `ZRANK`는 0부터 센 순번을 돌려주고, 원소가 없으면 nil을 돌려줍니다(공식 문서 zrank). 예시에서 u4의 번호는 끝까지 4입니다. 하지만 u1과 u2가 줄에서 빠지면 u4의 순번은 1이 됩니다. 앞에 u3 한 명이 있다는 뜻입니다.
  - 원소가 적을 때는 원소와 점수를 한 덩어리(listpack)에 이어 담고, 찾을 때 앞에서부터 훑습니다. 원소가 많아지거나 원소 하나가 커지면(경계는 `zset-max-listpack-*` 설정) 원소마다 따로 할당하는 구조로 바뀝니다. 대기열처럼 수천 명이 줄을 서는 키는 이 구조입니다. 그 구조는 회원 ID로 점수를 바로 찾는 해시 테이블과, 점수 순서로 원소를 잇는 스킵 리스트를 함께 둡니다. 서버가 도는 동안에는 원소를 꺼내거나 지워 수가 다시 줄어도 한 덩어리로 돌아가지 않습니다.
  - **스킵 리스트**는 점수 순으로 원소를 잇되, 위층에 건너뛰는 연결을 더 둔 연결 리스트입니다. 연결마다 건너뛰는 원소 수를 적어 두므로, 크게 건너뛰며 찾는 동안 그 수를 더해 가면 순번을 O(log N) 단계에 셉니다.
  - **비유와 다른 점**: 종이 명단은 번호를 사람이 매기지만, Sorted Set은 번호를 매기지 않습니다. 점수는 넣는 쪽이 정해서 줘야 합니다. 이 문서에서 무엇을 점수로 쓸지는 "점수에는 시각 대신 Redis가 매기는 번호를 씁니다"에서 정합니다.
- **이 주제에서는**: "한 사람은 한 번만"(중복 없음), "먼저 온 순서"(점수 순 정렬), "앞에 몇 명"(순번)을 자료형 하나가 함께 줍니다. 대가는 원소마다 따로 할당하는 메모리이며 "요청과 데이터가 늘면 무엇이 달라지는가"에서 다룹니다.

**복잡도 표기**: 공식 문서는 명령마다 데이터가 커질 때 작업량이 어떻게 늘어나는지를 O(…)로 적습니다. 이 문서에서 N은 그 Sorted Set이나 List의 원소 수입니다. O(1)은 N과 상관없이 작업량이 일정하다는 뜻이고, O(N)은 N에 비례한다는 뜻입니다. O(log N)은 N이 두 배가 될 때 단계가 하나 정도 늘어난다는 뜻입니다. 원소가 1,000개에서 100만 개로 1,000배가 되면, O(N)의 작업량은 1,000배가 되지만 O(log N)은 약 10단계에서 약 20단계로 늘어납니다(밑이 2인 로그로 계산). 스킵 리스트는 층수를 무작위로 정하므로 이 단계 수는 평균으로 봐야 합니다. 그리고 이 표기는 작업량이 늘어나는 모양이지 실제 시간이 아닙니다. 명령 하나가 가벼워도, 초당 몇 번 오는지가 서버의 부담을 정합니다.

## 락만으로는 왜 버티지 못하는가: 처리량이 아니라 기다리는 자리가 문제입니다

키운 장면으로 봅니다. 10:00:00에 회원 10,000명이 주문 버튼을 누르고, 주문 단계는 초당 20건을 처리합니다.

- **처리량은 그대로입니다.** 재고 3,000개를 다 팔려면 대기열이 있든 없든 최소 150초(3,000 ÷ 20)가 걸립니다. 이 시간을 줄이려면 락 보유 시간을 줄이거나, DB의 조건부 UPDATE나 Redis 원자 연산처럼 락이 필요 없는 방식으로 바꿔야 합니다. 분산 락 문서의 "락을 걸기 전에: 정말 락이 필요한가"에서 다룹니다.
- **대기열이 없으면, 기다리는 자리는 서버 스레드와 사용자의 재시도입니다.** 10,000개의 주문 요청이 거의 동시에 주문 API에 도착합니다. 락을 얻지 못한 요청은 분산 락 문서의 "락을 못 얻었을 때: 바로 포기하거나, 기다리거나"에 나온 방식 중 하나를 따릅니다.
  - 바로 포기하면 사용자가 다시 누르므로 요청이 다시 몰립니다. 누가 성공할지는 다시 누른 타이밍이 정합니다.
  - 기다리게 하면 그동안 요청 스레드가 묶입니다. 스핀 방식이면 기다리는 요청 수 × 초당 시도 횟수만큼 실패할 Redis 명령이 생기고, 알림 방식이면 해제될 때마다 깨어난 요청끼리 다시 경쟁합니다.
  - 어느 쪽이든 먼저 온 순서가 지켜지지 않습니다. 그리고 상품 1의 요청이 스레드를 차지해, 다른 상품의 요청까지 처리하지 못할 수 있습니다.
- **대기열이 있으면, 기다리는 자리는 Redis의 원소입니다.** 줄을 선 회원은 Sorted Set의 원소 하나로 기다립니다. 기다리는 동안 서버 스레드를 붙잡지 않고, 가끔 짧은 폴링 요청으로 순번을 묻습니다. 주문 단계에는 입장 처리가 들여보낸 회원만 들어가므로, 주문 단계에 들어가는 사람의 수와 속도를 입장 처리로 조절할 수 있습니다.

| | 락만 | 대기열 + 락 |
| --- | --- | --- |
| 기다리는 곳 | 주문 API의 요청 스레드, 또는 사용자의 재시도 | Redis의 대기열 원소 |
| 기다리는 동안 붙잡는 자원 | 요청 스레드와 연결. 스핀이면 Redis 명령도 | 원소 하나만큼의 메모리, 가끔의 폴링 요청 |
| 순서 | 없음. 타이밍이 정함 | 대기 번호 순 |
| 주문 단계에 도착하는 요청 | 몰린 만큼 한꺼번에 | 입장권을 받은 회원의 요청만. 들어가는 속도는 입장 처리로 조절 |
| 주문 단계의 처리량 | 초당 20건 | 초당 20건(같음) |
| 새로 생기는 것 | 없음 | 대기열 키, 폴링, 입장 처리, 대기열 자체의 장애 |

대기열이 얻는 것은 처리량이 아니라 **질서**입니다. 기다림을 서버 스레드에서 데이터로 옮기고, 순서를 정하고, 하류가 감당할 만큼만 흘려보냅니다. 대가는 대기열이라는 새 시스템 하나입니다. 이 문서의 나머지는 그 시스템의 설계와 비용입니다.

## 줄 세우기: 대기 번호를 붙여 Sorted Set에 넣습니다

### 왜 List가 아니라 Sorted Set인가

List로도 줄을 만들 수 있습니다. `RPUSH`로 뒤에 넣고 `LPOP`으로 앞에서 꺼내면 둘 다 원소 하나에 O(1)입니다. 문제는 넣고 꺼내는 일 말고도 대기열이 해야 하는 일들입니다.

| 해야 하는 일 | List | Sorted Set |
| --- | --- | --- |
| 뒤에 넣기 | `RPUSH` O(1) | `ZADD` O(log N) |
| 앞에서 m명 꺼내기 | `LPOP key m` O(m) | `ZPOPMIN key m` O(log N × m) |
| 이미 줄에 있는지 확인 | `LPOS` O(N) | `ZSCORE` O(1) |
| 앞에 몇 명인지(순번) | `LPOS` O(N) | `ZRANK` O(log N) |
| 중간에서 한 명 빼기 | `LREM` O(N + 지운 수) | `ZREM` O(log N) |

복잡도는 명령마다 공식으로 적힌 값입니다. `LPOS`는 찾는 원소가 앞이나 끝 가까이 있으면 더 빨리 끝날 수 있습니다.

List로는 같은 회원이 두 번 줄을 서는 것을 막으려면, 넣기 전에 `LPOS`로 줄을 앞에서부터 훑어야 합니다. 폴링 때마다 순번을 셀 때도 다시 훑어야 합니다. 키운 장면에서 10,000명이 2초마다 묻는다면, 줄을 훑는 명령이 초당 5,000번 실행됩니다. Sorted Set은 원소가 곧 회원이라 구조상 중복이 생기지 않고, 순번을 O(log N)에 셉니다. 대가는 넣기가 O(1)에서 O(log N)이 되고, 원소마다 해시 테이블 항목과 스킵 리스트 노드를 더 둔다는 점입니다.

### 점수에는 시각 대신 Redis가 매기는 번호를 씁니다

점수로 들어온 시각(밀리초)을 쓰고 싶어지지만, 두 가지가 걸립니다.

- **같은 밀리초에 들어온 사람**: 점수가 같으면 회원 ID의 바이트 순서로 줄을 섭니다. 판매 시작 순간에는 같은 밀리초에 여럿이 들어올 수 있습니다. 그러면 ID가 앞서는 회원이 항상 먼저 섭니다.
- **누구의 시계인가**: 주문 API 서버가 자기 시각을 넣으면, S1과 S2의 시계 차이만큼 순서가 바뀝니다. S1의 시계가 50밀리초 늦다면, S2에서 먼저 들어온 회원보다 S1에서 나중에 들어온 회원이 앞에 섭니다(가상 수치). 시계가 둘일 때의 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "시간을 재는 쪽이 둘이면 시계도 둘입니다"에서 다룹니다.

그래서 이 문서는 `state:{item:1}`의 `seq` 필드를 `HINCRBY`로 1씩 올려 받은 번호를 점수로 씁니다(이 문서의 설계). `HINCRBY`는 필드가 없으면 0에서 시작합니다. 번호는 Redis가 진입 스크립트를 실행한 순서대로 1, 2, 3…이 되므로 같은 값이 나오지 않고, 어느 서버의 시계와도 무관합니다.

이 순서는 **Redis가 진입 스크립트를 실행한 순서**이지 회원이 버튼을 누른 순서가 아닙니다. 네트워크가 느린 회원은 먼저 눌러도 뒤에 섭니다. 서로 다른 연결로 거의 동시에 온 요청 사이에서는, Redis가 어느 것을 먼저 실행할지도 정해져 있지 않습니다(공식 문서 clients, "What Order are Client Requests Served In?"). 누른 순서를 쓰려면 브라우저가 보낸 시각을 믿어야 하는데, 그 값은 사용자가 조작할 수 있습니다.

### 진입 스크립트: 이미 있으면 그 번호를, 없으면 새 번호를 줍니다

줄 서기는 스크립트 하나로 다음을 합니다(이 문서의 설계). `KEYS`는 세 키이고, `ARGV`는 회원 ID입니다.

1. `state:{item:1}`에 `soldout`이 있으면 -1(품절)을 돌려줍니다.
2. `ticket:{item:1}`에 이 회원의 점수가 있고 그 값이 지금 시각보다 크면, 이미 입장권이 있다는 뜻이므로 0을 돌려줍니다. 지금 시각은 스크립트 안에서 `TIME`으로 읽은 Redis 서버 시각입니다("어느 시계로 만료를 판정하는가").
3. `queue:{item:1}`에 이 회원의 점수가 있으면 그 번호를 그대로 돌려줍니다.
4. 아니면 `HINCRBY state:{item:1} seq 1`로 새 번호 n을 받고, `ZADD queue:{item:1} n 회원ID`로 줄에 넣은 뒤 n을 돌려줍니다.

명령 하나가 아니라 스크립트가 필요한 이유는 3과 4 사이의 틈입니다. "줄에 있는가"의 확인과 번호 받기가 서로 다른 명령이면, 같은 회원의 요청 두 개가 둘 다 "없음"을 보고 번호를 하나씩 받을 수 있습니다. `ZADD`의 `NX` 옵션(없을 때만 추가)을 써도 원소가 두 개 생기지 않을 뿐입니다. 진 쪽이 받은 번호는 줄에 없는 번호가 되어, 그 요청의 응답은 실제와 다른 번호를 보여 줍니다. 번호 사이에 빈 곳도 생깁니다.

스크립트의 작업은 명령 대여섯 개로 일정하고, 줄이 길어져도 늘지 않습니다. `ZADD`만 O(log N)이고 나머지는 O(1)입니다.

진입을 판매 시작 전에 열지는 선택입니다(이 문서의 설계). 예시는 10:00:00에 진입과 입장을 함께 엽니다. 진입을 미리 열어 두면 판매 시작 순간의 진입 몰림은 줄지만, 몰림이 사라지지는 않고 줄을 여는 순간으로 옮겨 갑니다. 미리 열든 아니든 입장은 입장 스크립트의 3단계가 `open_at`까지 막습니다.

### 응답이 끊겨 다시 줄을 서도 번호는 하나입니다

예시의 처음 1초입니다.

| 시각 | 일어난 일 | 스크립트가 돌려준 값 | `queue:{item:1}` (회원:번호) | `seq` |
| --- | --- | --- | --- | --- |
| 10:00:00.1 | u1 진입 | 1 | u1:1 | 1 |
| 10:00:00.2 | u2 진입 | 2 | u1:1 u2:2 | 2 |
| 10:00:00.3 | u3 진입 | 3 | u1:1 u2:2 u3:3 | 3 |
| 10:00:00.4 | u4 진입. Redis는 실행했지만 응답이 끊김 | 4(전달되지 않음) | … u4:4 | 4 |
| 10:00:00.5 | u5 진입 | 5 | … u4:4 u5:5 | 5 |
| 10:00:00.9 | u4가 타임아웃 뒤 다시 진입 | 4 | 변화 없음 | 5 |

u4의 두 번째 요청은 3단계에서 끝나므로 번호도 카운터도 그대로입니다. 첫 요청이 Redis에 닿기 전에 사라졌다면 사정이 다릅니다. 그 요청은 번호를 쓰지 않았으므로 0.5초의 u5가 4를 받고, 0.9초의 두 번째 요청이 4단계까지 가서 5를 받습니다. 어느 쪽이든 u4의 원소는 하나입니다. 이것이 진입의 멱등성입니다. 다만 이 경우처럼 u5보다 먼저 보냈는데 u5 뒤에 서는 일, 곧 사라진 요청 때문에 순서가 밀리는 일은 막지 못합니다.

같은 회원이 탭 두 개나 기기 두 대에서 동시에 진입해도, 원소가 회원 ID이므로 결과는 같습니다. 반대로 회원 ID가 다르면 실제로는 같은 사람이어도 Redis는 구분하지 못합니다. 다중 계정은 대기열이 풀 수 없는 문제입니다.

## 들여보내기: 빈자리만큼 앞에서 꺼내 입장권을 줍니다

### 입장권은 만료 시각을 점수로 둔 두 번째 Sorted Set입니다

입장 처리는 "지금 주문 단계에 몇 명이 있는가"를 알아야 빈자리를 셉니다. 그런데 입장권에는 기한이 있으므로, 기한이 지난 입장권은 세지 말아야 합니다.

먼저 떠오르는 방법은 회원마다 키를 두고 `SET ticket:u1 1 PX 120000`처럼 Redis의 키 만료를 쓰는 것입니다. 만료는 Redis가 알아서 해 주지만, 살아 있는 입장권이 몇 개인지를 명령 하나로 셀 수 없습니다. 카운터를 따로 두면, 키가 만료로 사라질 때 카운터가 함께 줄지 않습니다(이 문서의 판단).

그래서 이 문서는 입장권을 `ticket:{item:1}` 하나에 모으고, 점수에 만료 시각(밀리초)을 둡니다(이 문서의 설계). 그러면 다음이 모두 명령 하나입니다.

- 만료된 입장권 치우기: `ZREMRANGEBYSCORE ticket:{item:1} -inf <지금>`은 점수가 지금 이하인 원소를 지웁니다. O(log N + 지운 수)입니다.
- 살아 있는 입장권 세기(치운 뒤): `ZCARD`, O(1)입니다.
- 이 회원의 입장권 확인: `ZSCORE`, O(1)입니다.
- 반납: `ZREM`, O(log N)입니다.

대가는 **만료를 Redis가 대신해 주지 않는다**는 점입니다. 만료 시각이 지난 입장권도 누군가 치우기 전까지는 집합에 남아 있습니다. 그래서 입장권을 확인하는 모든 곳이 "점수가 지금보다 큰가"를 직접 비교해야 하고, 누군가 주기적으로 치워야 합니다. 이 문서에서는 입장 스크립트가 치웁니다. Redis의 키 만료는 만료된 키를 조회할 때 없는 것으로 취급해 주지만, 원소 단위의 만료 시각은 우리 코드가 그 일을 해야 합니다.

### 입장 스크립트: 치우고, 세고, 꺼내고, 입장권을 줍니다

S1과 S2가 각각 1초마다 다음 스크립트를 돌립니다(이 문서의 설계). `ARGV`는 동시 입장 상한 N(예시는 2. 복잡도 표기의 N인 원소 수와는 다른 값입니다), 한 번에 들여보낼 최대 인원 k(예시는 2), 입장권 기한(예시는 120,000밀리초), 입장 간격(예시는 1,000밀리초)입니다.

1. `TIME`으로 지금 시각을 밀리초로 읽습니다.
2. `ZREMRANGEBYSCORE`로 만료 시각이 지금 이하인 입장권을 치웁니다.
3. `soldout`이 있거나 지금이 `open_at`보다 이르면 0을 돌려주고 끝냅니다. 판매 시작 전에 입장권이 나가지 않게 하는 확인입니다.
4. `admitted_at`이 있고 "지금 − `admitted_at`"이 0 이상이면서 입장 간격보다 작으면, 이번 간격에는 이미 누가 들여보냈으므로 0을 돌려주고 끝냅니다. 아니면 `admitted_at`에 지금 시각을 씁니다. 차이가 음수일 때도 진행하는 이유는 "어느 시계로 만료를 판정하는가"에서 다룹니다.
5. 빈자리 = N − `ZCARD ticket:{item:1}`입니다. 들여보낼 수 m은 빈자리와 k 중 작은 값입니다. m이 0 이하면 0을 돌려줍니다.
6. `ZPOPMIN queue:{item:1} m`으로 번호가 가장 작은 m명을 꺼냅니다. 줄에 m명보다 적으면 있는 만큼만 꺼냅니다(공식 문서 zpopmin).
7. 꺼낸 회원마다 `ZADD ticket:{item:1} <지금 + 기한> 회원ID`로 입장권을 줍니다.
8. 들여보낸 수를 돌려줍니다.

스크립트의 작업량은 치운 입장권 수와 꺼낸 수 m에 비례하고, 줄의 길이와는 로그로만 엮입니다(`ZPOPMIN`의 log(줄 길이)). 치운 수는 동시 입장 상한 N 이하이고 m은 k 이하이므로, 기다리는 사람이 10,000명이든 100만 명이든 스크립트가 메인 스레드를 붙잡는 시간은 크게 늘지 않습니다. 이것은 작업량에서 끌어낸 추론이며, 실행 시간을 재지는 않았습니다. 긴 스크립트가 모든 클라이언트의 지연이 되는 문제를 피하는 조건입니다. 그 문제는 [Redis 원자성](./atomicity.md)의 "대가 1: 스크립트가 도는 동안 다른 모든 명령이 기다립니다"에서 다룹니다.

꺼내기(6)와 입장권 주기(7)가 한 스크립트에 있다는 점도 중요합니다. 이 둘을 서버가 명령 두 개로 보내면, 꺼낸 직후 서버가 죽었을 때 그 회원은 줄에서도 사라지고 입장권도 받지 못합니다. 스크립트 하나로 묶으면 다른 클라이언트에게는 "줄에 있다"와 "입장권이 있다" 중 하나로만 보입니다.

단, 스크립트가 중간에 오류로 멈추면 앞의 쓰기는 남습니다([Redis 원자성](./atomicity.md)의 "대가 2: 중간에 에러가 나도 이미 한 쓰기는 되돌리지 않습니다"). 꺼낸 뒤 입장권을 주는 `ZADD`가 메모리 한도 때문에 거부되어, 꺼낸 회원이 사라지지 않을까 걱정할 수 있습니다. 이 스크립트는 첫 쓰기가 2단계의 치우기이므로 메모리 한도를 넘은 상태에서도 7단계까지 실행됩니다(소스를 읽은 해석이며 재현하지 않았습니다). 어떤 스크립트가 어디서 거부되는지는 "요청과 데이터가 늘면 무엇이 달라지는가"의 메모리 한도 항목에서 다룹니다.

### 모든 서버가 돌려도 자리보다 많이 들여보내지 않습니다

S1과 S2가 같은 순간에 입장 스크립트를 보내도, Redis는 두 스크립트를 차례로 실행합니다. 그리고 두 장치가 겹치지 않게 막습니다.

- **빈자리를 스크립트 안에서 셉니다.** 뒤에 실행된 스크립트는 앞 스크립트가 준 입장권까지 센 뒤 빈자리를 계산합니다. 그래서 간격 확인(4단계)이 없더라도 입장권의 합이 N을 넘지 않습니다.
- **간격 확인이 입장 속도를 서버 수와 떼어 놓습니다.** 4단계가 없으면, 서버가 10대일 때 1초에 스크립트가 10번 돌아 초당 최대 10k명이 들어갑니다. 4단계가 있으면 서버 수와 상관없이 1초에 최대 k명입니다.

그래서 입장 처리를 맡을 서버 하나를 뽑는 일(리더 선출)이 필요 없습니다. 서버 하나가 죽어도 남은 서버가 이어서 돌립니다. 대가는 서버 수만큼 스크립트가 더 실행된다는 점인데, 간격 확인에 걸린 스크립트는 1~4단계만 하고 끝납니다.

반대로 모든 서버의 입장 처리가 멈추면 입장도 멈춥니다. 줄에는 사람이 남고, 입장권은 만료되기만 합니다. 이것을 알아채는 지표는 `admitted_at`이 얼마나 오래됐는가입니다. 이 값은 간격 확인을 통과한 마지막 실행 시각이므로, 간격보다 훨씬 오래됐다면 입장 처리가 돌지 않는 것입니다. 단, 판매 시작 전과 품절 뒤에는 3단계에서 끝나 이 값이 갱신되지 않으므로 판매 시작 여부, 품절 여부와 함께 봅니다. 들여보낸 수가 0인 것만으로는 알 수 없습니다. 자리가 가득 찼거나, 판매 시작 전이거나, 품절이거나, 간격 확인에 걸려도 0이기 때문입니다.

입장 스크립트의 응답이 끊겨도 다시 보낼 필요가 없습니다. 상태가 모두 Redis에 있으므로, 다음 실행이 그 결과를 이어받습니다. 들여보낸 회원에게 알리는 일도 스크립트의 응답에 기대지 않고, 회원의 폴링이 알아내게 합니다. 그러면 응답이 끊겨도 알림이 사라지지 않습니다.

### 손으로 따라가기: 5명이 재고 3개를 사기까지

시각은 가상 예시입니다. S1은 매초 .0에, S2는 매초 .3에 입장 스크립트를 돌린다고 합시다. 들여보낸 사람이 없는 실행은 생략했습니다.

| 시각 | 일어난 일 | `queue:{item:1}` (회원:번호) | `ticket:{item:1}` (회원:만료 시각) | DB 재고 |
| --- | --- | --- | --- | --- |
| 10:00:00.1~0.9 | 위 표의 진입. u1~u5가 번호 1~5 | u1:1 u2:2 u3:3 u4:4 u5:5 | 없음 | 3 |
| 10:00:01.0 | S1 입장: 빈자리 2 → u1, u2 | u3:3 u4:4 u5:5 | u1:10:02:01 u2:10:02:01 | 3 |
| 10:00:01.3 | S2 입장: 간격 1초가 안 지나 건너뜀 | 같음 | 같음 | 3 |
| 10:00:02 | u1이 폴링으로 입장을 확인하고 주문 화면으로. u2는 폴링 없이 떠남 | 같음 | 같음 | 3 |
| 10:00:40.5 | u1 주문 커밋, 입장권 반납 | 같음 | u2:10:02:01 | 2 |
| 10:00:41.0 | S1 입장: 빈자리 1 → u3 | u4:4 u5:5 | u2:10:02:01 u3:10:02:41 | 2 |
| 10:01:30.5 | u3 주문 커밋, 반납 | 같음 | u2:10:02:01 | 1 |
| 10:01:31.0 | S1 입장: 빈자리 1 → u4 | u5:5 | u2:10:02:01 u4:10:03:31 | 1 |
| 10:01:50.5 | u4 주문 커밋. DB가 재고 0을 알려 주문 API가 `soldout`을 씀. 반납 | 같음 | u2:10:02:01 | 0 |
| 10:02:01.0 | S1 입장: 만료된 u2의 입장권을 치움. 품절이므로 들여보내지 않음 | 같음 | 없음 | 0 |
| 10:02:02 | u5가 폴링으로 품절을 확인 | 같음 | 없음 | 0 |

결과는 주문 3건(u1, u3, u4), 재고 0, u5에게는 품절 응답입니다. 입장권은 어느 순간에도 2장 이하였고, 입장은 번호 순이었습니다.

u2가 떠난 대가도 보입니다. 10:00:02부터 10:02:01까지 u2의 입장권이 자리 하나를 차지했고, 그동안 입장은 남은 자리 하나로만 이어졌습니다. u3와 u4는 그만큼 늦게 들어갔습니다. 이 문제는 "떠난 사람이 자리를 붙잡지 않게 합니다"에서 다룹니다. 남은 `queue:{item:1}`의 u5는 판매가 끝난 뒤 지웁니다("요청과 데이터가 늘면 무엇이 달라지는가").

## 동시 입장 상한과 입장 속도 상한을 함께 둡니다

N(동시 입장 상한), k(한 번에 들여보내는 수), 입장권 기한을 어떻게 정할지 키운 장면으로 봅니다. 주문 단계는 초당 20건을 처리하고, 입장한 회원은 평균 60초 동안 주소와 결제 수단을 입력한 뒤 주문을 누른다고 합시다(가상 수치). 아래 판단은 모두 이 문서의 설계입니다.

- **N이 너무 작으면 주문 단계가 놉니다.** N이 20이면, 입장한 회원이 60초씩 머무르므로 자리가 비는 속도는 평균 초당 약 0.33명(20 ÷ 60)입니다. 주문 단계는 초당 20건을 처리할 수 있는데, 1분에 20건만 받습니다.
- **주문 단계를 채우려면 N은 "입장 속도 × 머무는 시간"이어야 합니다.** 초당 20명을 들여보내고 각자 60초씩 머문다면 N은 약 1,200입니다. "처리량, 머무는 시간, 동시에 머무는 수"의 관계 그대로입니다.
- **그런데 N을 크게 두면, 안에 있는 사람이 한꺼번에 주문할 때 주문 단계 앞에 쌓일 수 있는 양도 커집니다.** 판매 시작 직후에는 빈자리가 1,200개입니다. k가 없다면 첫 입장 처리가 1,200명을 한꺼번에 들여보냅니다. 상품 페이지에 "바로 구매" 버튼만 있어 머무는 시간이 몇 초뿐이라면, 1,200개의 주문 요청이 몇 초 안에 주문 단계에 도착합니다. 초당 20건인 주문 단계 앞에 1분 분량이 쌓여, 대기열이 막으려던 일이 다시 생깁니다.
- **그래서 k로 입장 속도를 따로 묶습니다.** 간격이 1초라면 k를 주문 단계의 처리량 이하(예: 20)로 둡니다. 그러면 시작 직후에도 새로 들어가는 회원은 초당 20명으로 묶이고, N이 1,200이어도 자리를 다 채우기까지 60초가 걸립니다.
- **다만 k가 묶는 것은 입장권을 내주는 속도이지, 주문 요청의 속도가 아닙니다.** 서로 다른 때 들어간 회원들이 같은 순간에 주문하면, 그 순간의 주문 요청은 20건을 넘을 수 있습니다. 그리고 입장권 확인은 입장권을 소비하거나 "주문 중"으로 바꾸지 않으므로, 같은 회원이 주문 요청을 여러 번 동시에 보내도 모두 통과합니다. 주문 요청 자체의 속도나 동시 실행 수에 상한이 필요하면, 주문 API에 따로 제한을 둡니다.

정리하면 세 값은 맡은 일이 다릅니다.

| 값 | 정하는 것 | 너무 크면 | 너무 작으면 |
| --- | --- | --- | --- |
| k(간격당 입장 수) | 입장권을 내주는 최대 속도. 주문 요청 속도의 상한은 아님 | 주문 단계 앞에 요청이 쌓임 | 줄이 느리게 줄고 주문 단계가 놂 |
| N(동시 입장 상한) | 유효한 입장권의 최대 수. 회원마다 주문 요청을 하나씩만 보낸다면, 모두가 동시에 주문할 때 쌓이는 최대량 | 한꺼번에 몰릴 때 주문 단계의 대기(회원당 요청 하나라면 최대 N ÷ 처리량초)가 김 | 머무는 시간이 길면 입장이 막혀 주문 단계가 놂 |
| 입장권 기한 | 떠난 사람이 자리를 붙잡는 최대 시간 | 떠난 사람 때문에 자리가 오래 빔 | 느린 회원이 주문 도중 쫓겨남 |

## 입장권은 리스입니다: 확인, 반납, 그리고 시계

### 주문 API는 들어올 때 확인하고, 끝나면 반납합니다

주문 요청이 오면 주문 API는 먼저 입장권을 확인합니다. `ticket:{item:1}`에서 이 회원의 점수를 읽고, 지금 시각보다 크면 들여보냅니다. 이 비교에 쓰는 지금 시각은 입장 스크립트가 쓴 것과 같은 Redis 시각이어야 합니다. 그래서 `ZSCORE`와 `TIME`을 함께 읽는 작은 스크립트로 확인합니다(이 문서의 설계). 입장권이 없거나 만료됐으면 "다시 줄을 서 주세요"로 응답합니다.

주문 단계가 끝나면, 성공이든 품절이든 입장권을 반납합니다(`ZREM`). 반납해야 다음 입장 처리에서 자리가 빕니다. 반납이 Redis 오류로 실패해도 그 자리는 기한이 지나면 빕니다. 기한은 반납이 빠졌을 때의 안전망이기도 해서, 분산 락의 기한과 같은 역할을 합니다. 없는 원소를 `ZREM`하면 아무 일도 일어나지 않으므로, 반납은 다시 보내도 됩니다.

주문 단계에서 DB가 재고 0을 알리면, 주문 API가 `state:{item:1}`에 `soldout`을 씁니다. 그다음 입장 스크립트부터 들여보내기를 멈춥니다. 이어지는 내용은 "품절과 줄 길이: 더 기다려도 소용없는 사람에게 빨리 알립니다"에서 다룹니다.

### 입장권은 효율용 리스입니다: 재고는 여전히 주문 단계가 지킵니다

입장권은 정해진 기간 동안만 유효한 권리, 곧 리스입니다. 그래서 리스의 빈틈도 그대로 가집니다. 보유자는 자기 입장권이 언제 만료됐는지 모릅니다.

클라이언트가 멈췄다가 늦게 돌아오는 경우를 따라가 봅니다. 예시를 조금 바꿔, u3가 10:00:42에 입장을 확인한 직후 노트북을 닫았다가 10:03:00에 돌아와 주문을 누른다고 합시다.

| 시각 | u3 | 입장 처리 | `ticket:{item:1}`의 u3 |
| --- | --- | --- | --- |
| 10:00:41 | | u3 입장, 만료 10:02:41 | 10:02:41 |
| 10:00:42 | 입장 확인 후 멈춤 | | 10:02:41 |
| 10:02:41 | (멈춤) | 만료된 u3를 치우고 빈자리에 다음 회원을 들여보냄 | 없음 |
| 10:03:00 | 주문 요청 → 입장권 없음으로 거절 | | 없음 |

u3는 다시 줄을 서야 하고, 새 번호를 받아 맨 뒤에 섭니다. 기한을 넘겨 돌아온 회원을 원래 자리로 되돌릴지는 정책입니다. 되돌리면 그동안 기다린 다른 회원이 밀립니다.

더 까다로운 것은 기한에 걸친 요청입니다. u3가 10:02:40에 보낸 주문이 입장권 확인을 통과한 뒤 주문 단계에서 5초가 걸렸다고 합시다. 그사이 10:02:41에 u3의 입장권이 치워지고 다른 회원이 들어옵니다. 잠시 동안 주문 단계에 3명이 있게 됩니다. 확인 직후에 기한이 끝나는 이 겹침은 리스로는 막을 수 없습니다. 원리는 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "리스의 빈틈: 보유자는 자기 리스가 끝난 것을 모릅니다"에서 다룹니다.

그래도 괜찮은 이유는 입장권이 **효율용**이기 때문입니다. 판단 질문은 "입장권이 깨져 상한보다 많은 회원이 주문 단계에 들어가면 무슨 일이 생기는가?"입니다. 답은 "주문 단계가 잠시 조금 더 붐빈다"이고, 재고가 틀어지지는 않습니다. 재고는 주문 단계의 락과 DB 확인이 지키기 때문입니다. 그래서 이 설계에서는 입장권을 주문을 시작할 때 한 번만 확인하고, 커밋 직전에 다시 확인하지 않습니다(이 문서의 설계).

거꾸로 말하면, **대기열을 두었다고 주문 단계의 정확성 장치를 빼면 안 됩니다.** 입장권이 상한을 넘겨 겹치는 경우는 이 절의 기한 경계 말고도 있습니다. 장애 조치("장애 조치와 재시작 때 잃는 것")와 시계 점프("어느 시계로 만료를 판정하는가")로도 생깁니다. 효율용과 정확성용의 구분은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "효율을 위한 락과 정확성을 위한 락"에서 다룹니다.

### 늦게 끝난 주문이 새 입장권을 지우지 않게 합니다

늦게 끝난 주문의 반납에도 함정이 있습니다. 위의 u3가 다시 줄을 서서 새 입장권을 받았는데, 옛 주문이 그제야 끝나 `ZREM ticket:{item:1} u3`를 보냈다고 합시다. 그러면 새 입장권이 지워집니다. 원소가 회원 ID뿐이라 옛 입장권과 새 입장권을 구별할 수 없기 때문입니다. 분산 락에서 기한이 지난 뒤의 `DEL`이 남의 락을 지우는 것과 같은 모양입니다.

막으려면, 입장권을 확인할 때 읽은 만료 시각을 기억해 두었다가 "점수가 그 값과 같을 때만 지우기" 스크립트로 반납합니다(이 문서의 설계). 새 입장권은 보통 만료 시각이 달라 지워지지 않습니다. 다만 만료 시각은 입장권마다 고유한 값이 아닙니다. Redis 서버의 시계가 뒤로 가거나 시계가 늦은 서버로 장애 조치되면, 새 입장권에 옛 입장권과 같은 만료 시각이 붙을 수 있습니다. 그 경우까지 막으려면 입장할 때 고유한 값(예: 무작위 토큰)을 함께 저장해 두고 그 값으로 비교해야 합니다. 만료 시각이 주문 도중에 바뀌는 설계에서도 만료 시각 비교는 실패합니다("떠난 사람이 자리를 붙잡지 않게 합니다"). 이 일이 드물고 결과가 "그 회원이 한 번 더 줄을 선다" 정도라면, 받아들이고 단순한 `ZREM`을 쓸 수도 있습니다.

### 어느 시계로 만료를 판정하는가

입장권의 만료 시각을 정하는 곳(입장 스크립트)과 확인하는 곳(진입 스크립트, 입장권 확인)은 같은 시계를 써야 합니다. 이 문서는 모두 스크립트 안의 `TIME`, 곧 Redis 서버의 시각으로 정했습니다(이 문서의 설계).

- 스크립트 안의 `TIME`은, 서버가 그 스크립트 명령의 실행을 시작할 때 읽어 둔 벽시계 값을 돌려줍니다. 벽시계이므로 서버 시각이 바뀌면 함께 뜁니다.
- 스크립트는 본문이 아니라 실행한 쓰기 명령만 복제본에 전달합니다(공식 문서 eval-intro, "Script replication"; lua-api의 `redis.replicate_commands`). AOF에도 같은 쓰기 명령이 기록됩니다. 그래서 스크립트가 `TIME`처럼 실행할 때마다 값이 다른 명령을 쓰고 그 값으로 쓰기를 해도, 복제본에는 계산된 점수가 담긴 `ZADD`가 그대로 갑니다.
- 주문 API 서버의 시각을 인자로 넘기는 방법도 있습니다. 그러면 S1과 S2의 시계 차이만큼 입장권의 길이가 서버마다 달라집니다.

Redis 시각을 쓰는 대가는 분산 락과 같습니다. 서버 시각이 앞으로 뛰면 입장권이 일찍 만료됩니다. 장애 조치 뒤에는 새 주 서버의 시계로 판정합니다. 원리는 [Redis 분산 락](./distributed-lock.md)의 "시계: 서버의 벽시계가 뛰면 락이 일찍 풀립니다"에서 다룹니다.

시계가 **뒤로** 가는 경우는 이 설계에서 따로 막아야 합니다. 입장 스크립트의 간격 확인이 "지금 − `admitted_at` < 1초"만 본다고 합시다. 서버 시각이 한 시간 뒤로 옮겨지면 차이가 음수가 되어, 이 조건이 한 시간 내내 참입니다. 그동안 입장이 멈춥니다. 새 주 서버의 시계가 옛 주 서버보다 늦을 때도 같은 일이 생길 수 있습니다. 그래서 4단계는 차이가 0 이상일 때만 건너뛰고, 음수면 진행합니다(이 문서의 설계). 입장권은 뒤로 간 만큼 오래 살아남아 자리를 더 오래 차지합니다. 입장권이 효율용이므로, 시계가 어긋난 결과는 몇 명이 일찍 쫓겨나거나 잠시 상한을 넘거나 입장이 느려지는 정도입니다.

## 떠난 사람이 자리를 붙잡지 않게 합니다

자리를 낭비하는 사람은 두 부류입니다.

- **기다리다 떠난 사람**: 원소가 줄에 남아 있다가 차례가 오면 입장권을 받습니다. 아무도 쓰지 않는 그 입장권이 기한까지 자리를 차지합니다.
- **입장한 뒤 떠난 사람**: 예시의 u2입니다. 결과는 같습니다.

떠난 사람 한 명이 자리 하나를 최대 입장권 기한만큼 막습니다. 대기 시간이 길수록 떠나는 사람이 늘 테니, 키운 장면처럼 기다림이 몇 분씩 되면 이 낭비가 커집니다. 방법은 세 가지입니다.

| 방법 | 동작 | 대가 |
| --- | --- | --- |
| 기한 줄이기 | 입장권 기한을 짧게 둠 | 주소와 결제 수단을 입력하는 데 오래 걸리는 회원이 쫓겨남 |
| 두 단계 기한 | 입장 때는 짧은 기한(예: 20초)만 줌. 주문 화면을 열거나 입력할 때의 요청이 입장권을 확인할 때마다 "지금 + 120초"로 늘림(갱신) | 폴링 간격이 짧은 기한보다 짧아야 함. 늘리기는 "점수가 지금보다 클 때만"인 스크립트로 해야 함. 주문 화면에서 요청을 계속 보내는 회원은 자리를 계속 쥠 |
| 살아 있음 기록 | 폴링마다 마지막 폴링 시각을 기록하고, 입장 스크립트가 오래 폴링하지 않은 회원을 건너뜀 | 폴링이 모두 쓰기가 되어 복제와 AOF의 부담이 늘고, 입장 스크립트가 복잡해짐 |

이 문서는 두 단계 기한을 고릅니다(이 문서의 설계). 떠난 사람은 짧은 기한만에 자리를 내놓고, 남은 사람은 충분한 시간을 받으며, 폴링은 읽기로 남기 때문입니다.

늘리기를 처음 한 번만 하려면, 늘렸는지를 회원마다 따로 기록해야 합니다. 이 문서는 그 상태를 두지 않으려고 확인할 때마다 늘리는 갱신으로 정했습니다. 늘리는 곳은 주문 화면을 열거나 입력할 때의 요청입니다. 주문 API의 입장권 확인은 "주문 API는 들어올 때 확인하고, 끝나면 반납합니다"에서처럼 읽기만 합니다(이 문서의 설계). 갱신하는 리스의 성질은 [리스와 펜싱 토큰](../cs/lease-and-fencing.md)의 "갱신: 짧은 기한으로 오래 쥐는 방법"에서 다룹니다. 대가는 주문 화면에서 요청을 계속 보내는 회원이 자리를 기한 없이 쥘 수 있다는 점입니다. 이 문서는 이를 받아들입니다. 입장권이 효율용이라 오래 쥐어서 잃는 것은 재고가 아니라 다른 회원의 입장 지연이고, 자리를 계속 쥐려면 주문 화면에서 요청을 계속 보내야 하기 때문입니다. 주문 화면을 떠난 회원은 마지막 확인으로부터 120초 뒤에 자리를 내놓습니다. 오래 쥐는 회원 때문에 입장이 눈에 띄게 늦어지면, 처음 입장한 시각부터 잰 전체 상한을 둡니다. 대가는 회원마다 처음 입장한 시각을 따로 저장해야 한다는 점입니다(이 문서의 설계).

갱신은 "늦게 끝난 주문이 새 입장권을 지우지 않게 합니다"의 조건부 반납과 부딪힙니다. 주문이 진행되는 동안 같은 회원의 화면 요청이 기한을 늘리면 만료 시각이 바뀝니다. 그러면 주문이 기억해 둔 만료 시각으로는 반납이 실패하고, 그 자리는 늘어난 기한이 지나 입장 처리가 치울 때까지 남습니다. 갱신과 조건부 반납을 함께 쓰려면 만료 시각 대신 입장마다 고유한 값으로 비교해야 합니다.

예시에 적용하면 u2의 입장권은 10:00:21에 만료됩니다. 그 시각의 입장 처리에서 u3가 들어가므로, 원래 예시보다 20초 일찍 들어갑니다. 살아 있음 기록은 기다리다 떠난 사람을 입장 전에 걸러 내므로 자리 낭비가 가장 적지만, 폴링이 쓰기가 되는 비용 때문에 고르지 않았습니다.

## 품절과 줄 길이: 더 기다려도 소용없는 사람에게 빨리 알립니다

키운 장면에서 재고는 3,000개인데 10,000명이 줄을 섭니다. 떠나는 사람을 빼더라도, 뒤쪽의 수천 명은 기다려도 살 수 없습니다. 이들에게 빨리 알릴수록 이들의 폴링도 빨리 멈춥니다.

- **품절 표시**: 주문 단계가 재고 0을 확인하면 `soldout`을 씁니다. 그러면 입장 스크립트는 들여보내기를 멈추고, 진입 스크립트는 -1을 돌려주고, 폴링은 품절을 알립니다. 표시는 힌트일 뿐이고, 재고의 정답은 DB에 있습니다. 표시가 늦게 쓰이거나 사라져도 그사이 들어간 회원은 주문 단계에서 품절로 거절됩니다. 낭비는 생기지만 틀리지는 않습니다.
- **재입고**: 취소나 환불로 재고가 다시 생길 수 있다면 `soldout`을 지우는 경로도 만듭니다(`HDEL`). 지우면 다음 입장 처리부터 다시 들여보냅니다.
- **줄 길이 상한**(이 문서의 설계): 진입 스크립트의 3단계와 4단계 사이에서 `ZCARD queue:{item:1}`가 상한 이상이면 -2("지금은 줄을 설 수 없음")를 돌려줍니다. 상한은 예를 들어 남은 재고의 몇 배로 정합니다. 기다려도 못 살 가능성이 큰 사람은 바로 알게 되고, 대기열의 메모리와 폴링도 상한만큼으로 묶입니다. 이 상한은 "동시에 기다리는 최대 인원"이므로 줄이 줄면 다시 받아들입니다. 대가는 두 가지입니다. 앞쪽에서 떠나는 사람이 많으면 재고가 남았는데 돌려보낸 사람이 생깁니다. 그리고 돌려보낸 사람이 곧바로 다시 시도하면 진입 요청이 몰립니다. 그래서 응답에 다시 시도할 시각을 담아 주고, 클라이언트가 그때까지 기다리게 합니다.

## 순번 묻기(폴링)의 비용은 기다리는 사람 수 × 빈도입니다

회원은 2초마다 "내 차례인가"를 묻는다고 합시다. 폴링 한 번은 주문 API에 가는 HTTP 요청 하나와 Redis에 가는 스크립트 하나입니다. 스크립트는 `soldout`, 입장권, 순번을 읽기만 합니다(이 문서의 설계).

키운 장면에서 판매 시작 직후 10,000명이 2초마다 물으면 초당 5,000번입니다. 진입은 시작 순간에 몰리지만 한 사람에 한 번이고, 입장 처리는 1초에 한 번입니다. 그러니 시작 순간의 진입이 지나고 나면 **Redis가 받는 명령의 대부분은 폴링**입니다. `ZRANK` 하나는 O(log N)으로 가볍지만, 초당 5,000번이 모두 상품 1의 키를 가진 Redis 하나로 갑니다. 기다리는 사람이 줄어들수록 폴링도 줄어듭니다. 그래서 품절을 빨리 알리는 것이 폴링 비용을 줄이는 가장 큰 수단이기도 합니다.

### 두 번 나눠 읽으면, 읽는 순서에 따라 '없음'이 나옵니다

폴링 스크립트 대신 명령 두 개로 "입장권이 있는가"와 "순번이 몇인가"를 따로 읽는다고 합시다. 입장권을 먼저 읽으면 다음 순서가 생깁니다.

| 순서 | u3의 폴링 | 입장 스크립트 | u3의 실제 상태 |
| --- | --- | --- | --- |
| 1 | 입장권 확인 → 없음 | | 줄 |
| 2 | | u3를 꺼내 입장권을 줌 | 입장권 |
| 3 | 순번 확인(`ZRANK`) → nil | | 입장권 |

u3는 "줄에도 없고 입장권도 없다"는 응답을 받습니다. 화면이 "대기열에서 빠졌습니다"를 보여 주면 회원이 혼란스러워집니다. 이때 회원이 다시 진입해도 진입 스크립트의 2단계가 입장권을 찾아 0을 돌려주므로, 상태가 망가지지는 않습니다.

읽는 순서를 바꾸면 이 문제가 대부분 사라집니다. 한 회원의 한 차례 안에서 상태는 "줄 → 입장권 → 없음" 방향으로만 바뀝니다. 그러므로 줄을 먼저 읽고 입장권을 나중에 읽으면, 그사이 입장이 일어났을 때 적어도 입장권 쪽에서는 보입니다. 둘 다 보이면 입장권을 우선합니다(이 문서의 추론). 예외도 있습니다. 회원이 그사이 스스로 다시 줄을 서거나, 장애 조치로 입장이 사라져 회원이 줄로 돌아가는 경우입니다. 그리고 이런 순서 조건을 코드 곳곳에서 지키기는 어렵습니다. 그래서 이 문서는 폴링을 읽기 전용 스크립트 하나로 만들어 한 번에 읽습니다. 왕복도 한 번으로 줄어듭니다.

### 폴링 비용을 줄이는 방법

| 방법 | 동작 | 대가 |
| --- | --- | --- |
| 순번에 따라 간격 늘리기 | 응답에 다음 폴링까지의 시간을 담음. 순번이 뒤일수록 길게 | 뒤쪽 회원의 화면이 늦게 바뀜. 앞쪽은 두 단계 기한의 짧은 기한보다 자주 물어야 함 |
| 진행 위치로 순번 어림하기 | 아래 설명 | 어림값이 실제보다 클 수 있음. 품절과 기록 유실을 알리려면 품절 캐시와 주기적인 실제 확인이 함께 필요 |
| 복제본에서 읽기 | 폴링을 복제본으로 보냄 | 복제 지연만큼 늦은 상태를 봄 |
| 밀어 주기(SSE, WebSocket) | 폴링 대신 서버가 차례를 알려 줌 | 기다리는 사람 수만큼 연결을 열어 둬야 함. 알림이 사라질 때를 대비해 폴링이 여전히 필요 |

**진행 위치로 순번 어림하기**(이 문서의 설계): 입장 스크립트가 마지막으로 꺼낸 회원의 번호를 `state:{item:1}`의 필드(예: `last_admitted`)에 기록합니다. 각 서버는 이 값과 `soldout`을 1초에 한 번만 읽어 메모리에 둡니다. 폴링에는 캐시한 품절 여부와, "내 번호 − 마지막으로 들어간 번호"로 어림한 대기 위치를 답합니다.

- 이 값은 1부터 센 위치입니다. 앞에 있는 사람 수(`ZRANK`)는 이 값에서 1을 뺀 수입니다. 예시에서 u1, u2가 들어간 뒤 u3의 값은 3 − 2 = 1이고, `ZRANK`는 0입니다.
- 값이 0 이하이면 차례가 지났다는 뜻이므로, 그때 폴링 스크립트로 입장권을 확인합니다.
- 값이 양수여도 일정 간격(예: 30초)마다 한 번은 폴링 스크립트로 실제 상태를 확인합니다. 어림값만 보면 알 수 없는 일이 있기 때문입니다. 장애로 u5의 진입 기록이 사라졌다면, 마지막으로 들어간 번호가 4에서 멈춰 u5의 값은 계속 1입니다. 이 경우는 실제 확인에서 "없음"을 받아야 다시 줄을 섭니다. 장애 조치나 재시작 뒤에는 캐시한 값과 회원이 들고 있는 번호가 Redis의 실제 상태와 어긋날 수 있으므로, 실제 확인의 결과를 따릅니다.
- 이렇게 하면 폴링 대부분이 Redis에 닿지 않습니다. Redis의 부하는 기다리는 사람 수 × 실제 확인 빈도로 줄어듭니다.
- 회원의 번호는 진입할 때 받은 값이므로 클라이언트가 들고 있어도 됩니다. 번호를 조작해도 화면의 어림값만 틀어집니다. 실제 입장 여부는 Redis의 입장권으로 확인하기 때문입니다.
- 어림값은 번호가 빈틈없이 이어질 때만 정확합니다. Redis에 닿지 못한 진입 요청은 번호를 쓰지 않으므로 빈틈을 만들지 않습니다. 빈틈은 번호를 받은 뒤 줄에서 빠진 회원(예: 대기를 취소해 `ZREM`한 경우) 때문에 생기고, 그만큼 어림값이 실제보다 큽니다. 회원은 화면에 보인 것보다 일찍 들어갑니다.

이 문서는 간격 늘리기와 진행 위치 어림을 함께 씁니다(이 문서의 설계). 둘 다 Redis 쪽 변경이 작고, 폴링 대부분을 Redis에서 떼어 내기 때문입니다. 차례가 오는 순간을 바로 알려야 하는 화면이라면 밀어 주기를 검토합니다.

## 공정성: 지키는 것과 지키지 못하는 것

이 설계가 지키는 것은 세 가지입니다. Redis가 진입 스크립트를 실행한 순서대로 번호를 줍니다. 같은 회원 ID에는 번호가 하나입니다. 입장은 번호 순입니다.

지키지 못하는 것도 분명히 해 둡니다.

- 버튼을 누른 순서. 번호는 진입 스크립트가 실행된 순서입니다("점수에는 시각 대신 Redis가 매기는 번호를 씁니다").
- 다중 계정과 자동화된 요청. 회원 ID가 다르면 다른 사람입니다.
- 사라진 진입 요청을 다시 보낸 회원의 원래 순서. 다시 보낸 시점의 번호를 받습니다.
- 장애 조치로 진입 기록을 잃은 회원의 순서. 다시 줄을 서야 합니다("장애 조치와 재시작 때 잃는 것").
- 기한을 넘겨 돌아온 회원의 자리. 이 문서의 정책으로는 맨 뒤입니다.
- 두 단계 기한에서 짧은 기한 안에 응답하지 못한 회원의 차례.
- 줄을 여러 개로 나누면 전체 순서("클러스터: 상품 하나의 대기열은 노드 하나에 있습니다").

## 요청과 데이터가 늘면 무엇이 달라지는가

- **메모리는 기다리는 사람 수에 비례합니다.** `queue:{item:1}`의 원소 수가 기다리는 사람 수입니다. `ticket:{item:1}`은 N 이하이고, `state:{item:1}`은 필드 몇 개로 일정합니다. 줄이 길어지면 원소마다 따로 할당하는 구조로 바뀌어, 원소 수만큼 조각이 늘어납니다. 원리는 [메모리 할당](../cs/memory-allocation.md)의 "원소마다 따로 담으면, 원소 수만큼 비용이 붙습니다"에서 다룹니다. 원소 하나가 몇 바이트인지는 이 문서에서 재지 않았습니다. 예상 인원만큼 회원 ID를 넣은 시험용 키를 만들어 `MEMORY USAGE … SAMPLES 0`으로 잽니다. `SAMPLES`를 주지 않으면 원소 5개를 표본으로 어림한 값이고, `SAMPLES 0`이어야 원소 전체를 셉니다(공식 문서 memory-usage). 이 값은 키 하나의 크기이며, Redis 프로세스 전체의 메모리 사용량과는 다릅니다. 회원이 입장하면 원소가 빠지므로 메모리도 줄지만, 서버가 도는 동안에는 한 덩어리 구조로 되돌아가지 않습니다.
- **판매가 끝난 뒤 남은 줄을 지우는 비용**: 품절 뒤에도 남은 사람 수만큼 원소가 남습니다. `DEL`은 원소 조각을 메인 스레드에서 하나씩 해제합니다(`lazyfree-lazy-user-del` 기본값 `no`). 그동안 다른 명령이 기다립니다. `UNLINK`는 키를 곧바로 키 공간에서 떼어 내고, 해제할 조각이 많으면 해제를 백그라운드 스레드에 넘깁니다. 키에 만료를 걸어 두더라도, 만료로 지울 때의 해제는 기본이 메인 스레드입니다(`lazyfree-lazy-expire` 기본값 `no`). 그래서 줄이 수십만 명 이상으로 커질 수 있다면, 판매가 끝난 뒤 `UNLINK`로 지웁니다. 지우는 비용이 조각 수를 따르는 원리는 [메모리 할당](../cs/memory-allocation.md)의 "지우는 비용은 데이터 크기가 아니라 조각 수를 따릅니다"에서 다룹니다.
- **스크립트의 작업량은 줄 길이와 거의 무관합니다.** 진입은 명령 몇 개, 입장은 N과 k로 묶여 있습니다("입장 스크립트: 치우고, 세고, 꺼내고, 입장권을 줍니다").
- **폴링이 명령 수를 정합니다.** 기다리는 사람 수 × 폴링 빈도입니다("순번 묻기(폴링)의 비용은 기다리는 사람 수 × 빈도입니다").
- **메모리 한도와 축출 정책이 대기열을 막거나 지웁니다.** 정책별 동작은 [Redis 원자성](./atomicity.md)의 "메모리 한도에 닿으면 차감이 거부되거나 재고 키가 사라집니다"에서 다룹니다. 대기열에서는 다음과 같습니다.
  - `noeviction`에서 한도를 넘으면, 메모리를 늘릴 수 있다고 표시된 명령(`COMMAND INFO`의 플래그 `denyoom`, 아래에서는 `DENYOOM`)이 OOM 에러로 거부됩니다. shebang(스크립트 첫 줄의 `#!lua` 선언. 실행 플래그를 함께 적을 수 있음) 없이 쓴 스크립트, 곧 이 문서의 스크립트들은 첫 쓰기 명령에서만 이 검사를 받고, 쓰기를 하나라도 한 뒤로는 검사하지 않습니다. 중간에 멈추면 반쯤 반영된 상태가 남기 때문입니다(소스를 읽은 해석이며 재현하지 않았습니다). 진입 스크립트는 첫 쓰기인 `HINCRBY`가 `DENYOOM`이라 거부됩니다. 아무것도 쓰기 전이므로 반쯤 반영된 상태는 남지 않습니다. 입장 스크립트는 첫 쓰기인 `ZREMRANGEBYSCORE`가 `DENYOOM`이 아니므로 끝까지 실행됩니다. 두 단계 기한의 연장 스크립트는 읽기 뒤의 첫 쓰기가 `ZADD`이므로 거부되어, 주문 중인 회원이 짧은 기한에 쫓겨날 수 있습니다. 주문 API가 품절 표시를 쓰는 `HSET`도 `DENYOOM`이라 거부되므로, 품절 뒤에도 입장이 이어집니다. 그래도 들어간 회원은 주문 단계에서 품절로 거절되므로 틀린 주문은 생기지 않습니다. 반납(`ZREM`)은 `DENYOOM`이 아니므로 계속됩니다. 결과적으로 새 진입, 기한 연장, 품절 기록이 막히고, 입장과 반납은 계속됩니다.
  - `allkeys-` 정책이면 대기열 키가 축출될 수 있습니다. `queue:{item:1}`이 지워지면 기다리던 사람 전원이 다시 줄을 서야 합니다. `state:{item:1}`만 지워지면 더 나쁩니다. `seq`가 0부터 다시 시작해, 새로 온 사람이 기다리던 사람들보다 작은 번호를 받고 앞에 섭니다. 대기열 키는 축출이 없는 인스턴스나 정책에 둡니다. 막는 장치를 하나 더 둘 수도 있습니다(이 문서의 설계). 진입 스크립트가 `seq`가 없는데 줄이 비어 있지 않음을 발견하면, 줄의 가장 큰 번호(`ZRANGE queue:{item:1} -1 -1 WITHSCORES`)부터 다시 셉니다.

## 클러스터: 상품 하나의 대기열은 노드 하나에 있습니다

스크립트 하나가 다루는 키는 클러스터에서 모두 같은 슬롯에 있어야 합니다. 그래서 세 키에 같은 해시 태그 `{item:1}`을 붙입니다. 규칙과 해시 태그의 대가는 [Redis 원자성](./atomicity.md)의 "여러 키를 함께 다루면 클러스터에서는 같은 슬롯에 있어야 합니다"와 "해시 태그로 슬롯을 맞추면 그 키들은 한 노드에 몰립니다"에서 다룹니다.

결과적으로 상품 하나의 진입, 폴링, 입장 처리, 입장권 확인이 모두 노드 하나의 메인 스레드로 갑니다. 상품이 여러 개면 상품마다 노드가 흩어지지만, 이 문서처럼 인기 상품 하나에 몰리는 상황에서는 노드를 늘려도 그 상품의 부하는 나뉘지 않습니다. 노드 하나가 초당 몇 개의 명령을 감당하는지는 명령 종류, 하드웨어, 연결 수에 따라 다르므로 실측해야 합니다.

이 노드가 버거울 때는 다음 순서로 대응합니다(이 문서의 설계).

1. **폴링 대부분을 Redis에서 떼어 냅니다.** "폴링 비용을 줄이는 방법"의 간격 늘리기와 진행 위치 어림입니다. 명령의 대부분이 폴링이므로 효과가 가장 큽니다.
2. **폴링을 그 노드의 복제본으로 보냅니다.** 클러스터의 복제본은 연결이 `READONLY` 상태일 때 오래됐을 수 있는 데이터로 읽기를 처리합니다(공식 문서 cluster-spec, "Scaling reads using replica nodes"). 폴링 스크립트는 읽기 전용 스크립트(`EVAL_RO` 또는 `no-writes` 플래그)여야 복제본에서 실행됩니다(공식 문서 programmability, "Read-only scripts"). 입장권 확인은 계속 주 서버로 보냅니다.
3. **그래도 진입과 입장 처리 자체가 버거우면 줄을 나눕니다.** 회원 ID의 해시로 K개의 줄(`queue:{item:1:0}`부터 `queue:{item:1:K-1}`까지)에 나눠 세우고, 줄마다 입장권 집합과 상태를 따로 둡니다. 각 줄은 N/K, k/K의 상한으로 따로 들여보냅니다. 대가는 **전체 선착순이 깨진다**는 점입니다. 줄끼리는 서로의 번호를 모르므로, 다른 줄에서 더 늦게 온 회원이 먼저 들어갈 수 있습니다. 품절 표시도 줄마다 써야 합니다.

## 장애 조치와 재시작 때 잃는 것

Redis 복제는 기본적으로 비동기입니다. 주 서버는 복제본이 받았는지 기다리지 않고 응답합니다. 그래서 응답한 쓰기가 복제본에 닿기 전에 장애 조치가 일어나면, 그 쓰기는 새 주 서버에 없습니다(공식 문서 replication: "there is always a window for data loss"). Redis Cluster도 같은 이유로 클라이언트에게 응답한 쓰기를 잃을 수 있습니다(공식 문서 scaling, "Redis Cluster consistency guarantees"). `min-replicas-to-write`와 `min-replicas-max-lag`를 설정하면, 지연이 정해진 초 이하인 복제본이 정해진 수보다 적을 때 주 서버가 쓰기를 거부합니다. 하지만 기본값은 0(꺼짐)입니다. 공식 문서도 이 설정을 잃는 구간을 몇 초로 묶는 최선의 노력으로 설명합니다.

잃은 쓰기가 무엇이었는지에 따라 결과가 다릅니다. 아래 표의 결과는 이 문서의 추론이며 재현하지 않았습니다. 추론의 근거는 스크립트의 쓰기들이 복제본에 한 덩어리로 전달된다는 점입니다([Redis 원자성](./atomicity.md)의 "스크립트의 쓰기는 복제본에도 한 덩어리로 전달됩니다").

| 잃은 쓰기 | 결과 |
| --- | --- |
| 진입(번호 발급과 줄 서기) | 회원은 번호를 받았지만 새 주 서버의 줄에 없습니다. 폴링에서 "없음"을 받고 다시 줄을 서며, 그사이 들어온 사람 뒤에 섭니다. `seq` 증가도 같은 스크립트의 쓰기라 함께 사라지므로, 살아남은 회원과 같은 번호가 다시 나가지는 않습니다 |
| 입장(꺼내기와 입장권 주기) | 두 쓰기가 함께 사라지므로 회원은 원래 번호로 줄에 돌아가 있고, 다음 입장 처리에서 다시 들어갑니다. 그사이 폴링으로 입장을 본 회원은 주문 화면에서 입장권 확인에 거절될 수 있습니다 |
| 반납 | 입장권이 되살아나 기한까지 자리 하나를 막습니다 |
| 품절 표시 | 입장이 다시 시작되지만, 들어간 회원은 주문 단계에서 품절로 거절됩니다. 다음 품절 판정 때 표시가 다시 쓰입니다 |
| 두 단계 기한의 연장(갱신) | 늘리기 전의 만료 시각으로 돌아가, 주문 중인 회원이 일찍 쫓겨날 수 있습니다 |

재시작은 영속성 설정에 따라 다릅니다. 설정별 손실 범위는 Redis 영속성에서 다룹니다.

- **영속성을 끈 Redis**는 비어서 시작합니다. 모든 회원이 폴링에서 "없음"을 받고 한꺼번에 다시 줄을 섭니다. 진입 요청이 몰리고, 순서는 다시 줄을 선 순서가 됩니다. 영속성을 끈 주 서버가 자동으로 재시작하면 복제본의 데이터까지 지워질 수 있다는 점도 같습니다(Redis 영속성 문서의 "영속성을 끈 주 서버가 자동으로 다시 시작하면").
- **RDB로 되살리면** 마지막으로 성공한 스냅숏 시점의 대기열로 돌아갑니다. 그 시점이 얼마나 이전인지는 저장 조건과 쓰기량에 달려 있으며, Redis 영속성 문서의 "언제 저장하는가"에서 다룹니다. 스냅숏 뒤에 들어가 이미 주문까지 마친 회원이 다시 줄에 나타나 또 입장할 수 있습니다. 같은 회원의 두 번째 주문은 주문 단계의 "1인 1개" 확인이 막아야 합니다(이 문서의 추론). 입장권의 만료 시각은 점수로 저장되므로 되살린 뒤에도 그대로 비교되고, 지난 시각이면 다음 입장 처리에서 치워집니다.
- **AOF `everysec`**는 정전 때 마지막 1초 안팎의 쓰기를 잃을 수 있습니다.

대기열의 상태는 대부분 "잃으면 다시 줄을 선다"로 복구됩니다. 그래서 주문 단계의 정확성이 대기열에 기대지 않는다면, 장애 조치 때 몇 초 분량을 잃는 것을 받아들이는 편이 단순합니다. 클라이언트는 "없음"을 받으면 자동으로 다시 줄을 서게 만듭니다(이 문서의 판단). 장애로 순서를 잃는 일까지 막아야 한다면 Redis 하나로는 부족합니다. 진입을 영속적으로 기록하는 다른 저장소가 필요하며, 이 문서의 범위 밖입니다.

**Redis가 응답하지 않을 때**는 미리 정해 둡니다. 진입은 닫는 쪽으로 실패시킵니다. 즉 "잠시 후 다시" 안내를 보여 줍니다. 대기열을 건너뛰고 주문 단계로 바로 보내면(열린 쪽) 대기열이 막으려던 몰림이 그대로 생깁니다. 주문 API의 입장권 확인도 Redis가 필요하므로, 닫으면 이미 입장한 회원도 주문하지 못합니다. 그래도 재고의 정확성은 주문 단계가 지키므로, 어느 쪽을 골라도 틀린 주문이 생기지는 않습니다. 고르는 기준은 사용자 경험과 주문 단계의 부하입니다.

## 흔한 오해 모아 보기

| 오해 | 실제 | 처음 다룬 곳 |
| --- | --- | --- |
| 대기열을 두면 처리량이 늘어난다 | 처리량은 주문 단계가 정합니다. 대기열은 기다리는 자리와 순서, 들어가는 속도를 바꿉니다 | 락만으로는 왜 버티지 못하는가 |
| 대기열이 있으면 초과 판매가 막힌다 | 입장권은 효율용 리스여서 상한을 넘겨 겹칠 수 있습니다. 재고는 주문 단계의 락과 DB가 지킵니다 | 입장권은 효율용 리스입니다 |
| 들어온 시각을 점수로 쓰면 공정하다 | 같은 밀리초는 회원 ID 순으로 서고, 서버마다 시계가 다릅니다 | 점수에는 시각 대신 Redis가 매기는 번호를 씁니다 |
| 대기 번호가 곧 순번이다 | 번호는 바뀌지 않는 점수이고, 순번은 앞사람이 빠질 때마다 줄어드는 위치입니다 | 배경 지식 |
| Sorted Set이니까 재시도해도 안전하다 | 원소가 둘이 되지 않을 뿐입니다. 번호 발급까지 멱등하려면 확인과 발급을 한 스크립트에 넣어야 합니다 | 진입 스크립트 |
| 입장권 기한이 지나면 자리가 그 순간 빈다 | 원소의 만료 시각은 Redis가 처리하지 않습니다. 입장 스크립트가 치울 때 빕니다 | 입장권은 만료 시각을 점수로 둔 두 번째 Sorted Set입니다 |
| 동시 입장 상한만 두면 하류가 보호된다 | 시작 순간에는 빈자리가 모두 한꺼번에 채워지므로 입장 속도 상한이 따로 필요합니다. 그것도 입장권을 내주는 속도만 묶으므로, 주문 요청 자체의 상한은 주문 API에 둡니다 | 동시 입장 상한과 입장 속도 상한을 함께 둡니다 |
| `ZRANK`는 가벼우니 폴링은 공짜다 | 명령 하나는 가볍지만 기다리는 사람 수 × 빈도만큼 한 노드로 갑니다 | 순번 묻기(폴링)의 비용 |
| 해시 태그를 쓰면 클러스터에 부하가 흩어진다 | 같은 태그의 키는 한 노드에 모입니다. 상품 하나의 대기열은 노드 하나에 있습니다 | 클러스터 |
| 복제본이 있으니 대기열은 안전하다 | 복제는 비동기여서 장애 조치 때 최근 진입과 입장을 잃을 수 있습니다 | 장애 조치와 재시작 때 잃는 것 |

## 실무 포인트

### 어떤 방식을 고를까

1. **먼저 주문 단계를 빠르게 할 수 있는지 봅니다.** 판단이 한 연산에 담기면 DB의 조건부 UPDATE나 Redis의 원자 연산으로 락 없이 풀고, 처리량 자체를 올립니다. 몰린 요청을 이것만으로 감당하면 대기열은 필요 없습니다.
2. **넘친 요청을 거절해도 되면 처리율 제한(rate limit)이 더 단순합니다.** 서비스 전체에 속도 하나를 거는 방식이면 회원별 상태를 두지 않고, 정해진 속도를 넘는 요청에 바로 "혼잡"을 응답합니다. 대가는 순서가 없고, 거절당한 사용자가 다시 누르면서 요청이 다시 몰린다는 점입니다.
3. **수요가 처리량을 크게 넘고, 순서가 중요하고, 사람이 주문 화면에 머무는 시간이 길면 입장 대기열**을 둡니다. 이 문서의 설계에서는 진입, 입장, 입장권 확인, 반납, 폴링을 각각 스크립트 하나로 만듭니다.
4. **대기열을 두어도 주문 단계의 정확성 장치는 그대로 둡니다.** 대기열은 효율과 공정성의 장치입니다.

### 관찰할 것

- **줄 길이**(`ZCARD queue:{item:1}`)와 **가장 오래 기다린 회원의 대기 시간**. 길이만으로는 얼마나 늦어지는지 알 수 없습니다. 이 문서의 대기열에는 번호만 있고 시각이 없으므로, 진입 응답 때 애플리케이션이 번호와 그 시각을 기록해 둡니다. 줄 맨 앞 회원의 번호(`ZRANGE queue:{item:1} 0 0 WITHSCORES`)로 그 기록을 찾으면 지금 가장 오래 기다린 시간이 나오고, 폴링으로 입장을 확인한 시각과의 차이로는 끝난 대기 시간이 나옵니다(이 문서의 설계). 이 값은 실제로 줄에 있던 시간이 아니라 "진입 응답을 기록한 때부터 입장을 알아챈 때까지"입니다. 응답이 늦거나 끊겨 다시 보낸 진입은 기록 시각이 실제보다 늦고, 입장은 폴링 간격만큼 늦게 알아챕니다. 지표의 추세를 보는 데는 충분하지만 초 단위로 정확하지는 않습니다. 순번 ÷ 입장 속도로 계산해 화면에 보여 주는 예상 대기 시간과는 다른 값입니다.
- **입장 수와 주문 완료 수**. 주문까지 간 비율은 입장권을 반납했거나 입장권이 만료되어 결과가 정해진 회원들끼리 셉니다. 아직 주문 화면에 있는 회원까지 넣으면, 판매 초반에는 떠난 사람이나 실패가 없어도 비율이 낮게 나옵니다. 이렇게 센 비율이 낮으면, 떠나는 사람이 많거나 주문 단계에서 실패가 많다는 뜻입니다. 주문 실패 수와 함께 보고, 떠나는 사람이 많다면 입장권 기한이나 두 단계 기한을 다시 봅니다.
- **만료로 치운 입장권 수**. 입장 스크립트가 돌려주게 해 지표로 남깁니다. 떠난 사람의 입장권뿐 아니라 반납 실패, 오래 걸린 주문, 시계 점프로 만료된 입장권도 섞입니다. 어느 쪽이 많은지는 반납 실패 수, 주문 처리 시간과 함께 봐야 압니다.
- **마지막 입장 처리 시각**(`admitted_at`)과 **들여보낸 수**. 입장 처리가 멈췄는지는 `admitted_at`이 간격보다 훨씬 오래됐는지로 봅니다. 판매 시작 전과 품절 뒤에는 이 값이 갱신되지 않습니다. 들여보낸 수가 0인 것은 자리가 가득 찼거나 판매 시작 전이거나 품절이거나 간격 확인에 걸려도 생기므로, 빈자리 수와 함께 해석합니다.
- **폴링 요청 수**와 그 노드의 명령 처리량·지연. `INFO commandstats`에서 `evalsha`·`eval_ro` 등의 호출 수, `SLOWLOG`, 클라이언트 쪽 응답 시간을 봅니다.
- **주문 단계 앞의 대기**. 락 대기 시간과 획득 실패 수가 늘면 k나 N이 처리량에 비해 클 수 있습니다. 주문 단계 자체가 느려졌는지(락 보유 시간), 같은 회원의 중복 요청이 늘었는지도 함께 봅니다.
- **Redis 쪽**: `used_memory`와 `maxmemory`, `evicted_keys`, `errorstats`의 OOM 에러, 복제 지연, 장애 조치 이력.

### Spring에서 확인할 것

- **직렬화기를 맞춥니다.** 회원 ID가 원소이고 스크립트가 그 값을 비교하므로, 진입·폴링·입장권 확인·반납이 모두 같은 직렬화기를 써야 합니다. `StringRedisTemplate`은 키·값·해시 직렬화기가 모두 문자열이라 단순합니다. 직렬화기를 정하지 않은 `RedisTemplate`은 Java 직렬화(`JdkSerializationRedisSerializer`)를 쓰므로, 원소가 회원 ID 문자열이 아닌 바이트가 됩니다. 그러면 다른 템플릿, 다른 서비스, `redis-cli`에서 같은 회원을 찾지 못합니다.
- **번호 발급은 스크립트로 합니다.** `opsForZSet().addIfAbsent(key, member, score)`는 `ZADD … NX` 명령 하나입니다. 원소의 중복은 막지만 번호 발급은 하지 않으므로, 진입은 `execute(RedisScript, keys, args)`로 스크립트를 보냅니다. 세 키는 반드시 `keys` 목록으로 넘깁니다. 스크립트 결과가 숫자면 결과 타입을 `Long`으로, 배열이면 `List`로 둡니다. 스크립트 실행의 세부와 트랜잭션 지원을 켠 템플릿의 함정은 [Redis 원자성](./atomicity.md)의 "Spring에서 확인할 것"에서 다룹니다.
- **입장 처리는 서버마다 돕니다.** `@Scheduled`는 각 애플리케이션 인스턴스 안의 스케줄러가 실행하므로, 서버가 두 대면 두 곳에서 돕니다. 이 설계는 스크립트의 원자성과 간격 확인으로 이를 견딥니다. `fixedDelay`는 앞 실행이 끝난 때부터 다음 실행까지의 간격을 재므로, 한 인스턴스 안에서는 실행이 겹치지 않습니다(참조 문서 scheduling).
- **폴링 엔드포인트는 짧게 끝냅니다.** 폴링마다 요청 스레드 하나를 잠깐 씁니다. 응답에 다음 폴링까지의 시간을 담아 클라이언트가 따르게 합니다. 응답을 오래 붙잡아 두는 롱 폴링은 기다리는 사람 수만큼 요청을 열어 두게 되므로, 이 문서의 설계에서는 쓰지 않습니다.
- **복제본에서 읽으려면** `LettuceClientConfiguration`의 `readFrom`을 설정합니다. 어떤 명령과 스크립트를 실제로 복제본으로 보내는지는 Lettuce가 정하며, 이 문서에서는 확인하지 않았습니다. 폴링 스크립트를 복제본으로 보내려면 `EVAL_RO`처럼 읽기 전용으로 실행되는지부터 확인해야 합니다.
- **재시도**: 진입 스크립트는 같은 번호를 돌려주므로 타임아웃 뒤 다시 보내도 됩니다. 입장 스크립트는 다시 보낼 필요가 없습니다. 반납은 다시 보내도 됩니다. 늦게 보내는 반납은 "늦게 끝난 주문이 새 입장권을 지우지 않게 합니다"의 조건부 반납을 씁니다.

## 말로 설명하기

### 30초 버전

인기 상품 하나에 요청이 몰리면, 락 하나의 처리량은 "1 ÷ 보유 시간"에 묶여 늘지 않습니다. 그 위로 넘친 요청은 서버 스레드를 붙잡고 기다리거나 재시도하며 Redis와 서버를 괴롭힙니다. 입장 대기열은 처리량을 늘리지 않습니다. 대신 기다림을 서버 스레드에서 Redis의 Sorted Set 원소로 옮기고, 진입 스크립트가 실행된 순서로 번호를 매기고, 주문 단계가 감당할 속도로만 들여보냅니다. 대가는 대기열이라는 새 시스템입니다. 폴링 부하가 한 노드로 몰리고, 장애 조치 때 최근 진입과 입장을 잃을 수 있습니다. 입장권은 효율용 리스이므로 재고의 정확성은 여전히 주문 단계가 지켜야 합니다.

### 2분 버전

락은 한 번에 한 요청만 들여보내므로, 보유 시간이 50밀리초면 초당 20건이 상한입니다. 대기열이 있든 없든 이 상한은 같습니다. 달라지는 것은 기다리는 자리입니다. 대기열이 없으면 넘친 요청이 스레드를 붙잡고 스핀하거나, 사용자가 계속 다시 눌러 순서 없이 경쟁합니다. 대기열이 있으면 회원은 Redis의 원소로 기다리며 가끔 순번만 묻고, 주문 단계에는 들여보낸 사람만 들어갑니다.

줄은 Sorted Set으로 만듭니다. 원소가 회원 ID라 중복이 없고, 순번을 O(log N)에 셉니다. 점수로는 시각 대신 Redis가 `HINCRBY`로 매기는 번호를 써서, 같은 밀리초의 동점과 서버마다 다른 시계를 피합니다. 진입은 "이미 줄에 있으면 그 번호, 없으면 새 번호"를 스크립트 하나로 해서, 응답이 끊겨 다시 줄을 서도 번호가 하나입니다.

들여보내기는 입장권을 만료 시각을 점수로 둔 두 번째 Sorted Set에 모으는 방식입니다. 서버마다 1초에 한 번 스크립트를 돌립니다. 스크립트는 만료된 입장권을 치우고, 빈자리를 세고, 앞에서 꺼내 입장권을 주는 일을 한 번에 합니다. 원자적이라 여러 서버가 돌려도 자리보다 많이 들여보내지 않습니다. 동시 입장 상한만 두면 시작 순간에 빈자리가 한꺼번에 채워지므로, 간격당 입장 수로 속도도 묶습니다.

대가도 있습니다. 폴링이 명령의 대부분이라 품절을 빨리 알리고, 간격을 늘리고, 순번을 어림해 폴링 대부분을 Redis에서 떼어 냅니다. 상품 하나의 키는 해시 태그로 한 노드에 모이므로 노드를 늘려도 그 부하는 나뉘지 않습니다. 복제가 비동기라 장애 조치 때 최근 진입이나 입장을 잃을 수 있지만, 대부분 "다시 줄을 선다"로 복구됩니다. 입장권은 기한 경계나 장애로 상한을 넘겨 겹칠 수 있는 효율용 리스이므로, 주문 단계의 락과 DB 확인은 그대로 둬야 합니다.

### 예상 질문과 꼬리 질문

**Q. 대기열을 두면 인기 상품의 판매가 빨라지나요?**
아닙니다. 처리량은 주문 단계가 정합니다. 락 보유 시간이 50밀리초면 초당 20건이고, 재고 3,000개를 파는 데 최소 150초가 걸립니다. 대기열이 바꾸는 것은 넘친 요청이 기다리는 자리(서버 스레드 대신 Redis 원소), 순서(진입 스크립트가 실행된 순), 주문 단계에 들어가는 속도입니다. (본문: "락만으로는 왜 버티지 못하는가: 처리량이 아니라 기다리는 자리가 문제입니다")

- **꼬리: 그럼 판매를 빠르게 하려면요?**
  주문 단계를 바꿔야 합니다. 보유 시간을 줄이거나, 판단이 한 연산에 담기면 DB 조건부 UPDATE나 Redis 원자 연산으로 락을 없앱니다. 그것만으로 몰린 요청을 감당하면 대기열은 필요 없습니다.
- **꼬리: 처리율 제한으로 넘친 요청을 거절하는 것과는 무엇이 다른가요?**
  서비스 전체에 거는 처리율 제한은 회원별 상태 없이 넘친 요청을 바로 거절하므로 단순합니다. 회원마다 한도를 두면 회원별 카운터가 생기지만, 대기 순서는 여전히 없습니다. 대신 순서가 없고, 거절된 사용자가 다시 누르며 요청이 다시 몰립니다. 대기열은 넘친 요청을 붙잡아 두고 순서를 줍니다. 그 대가로 회원별 상태와 폴링을 감당합니다.

**Q. 왜 List가 아니라 Sorted Set으로 줄을 만드나요?**
넣고 꺼내기만 보면 List가 O(1)로 더 쌉니다. 하지만 대기열은 "이미 줄에 있는가"와 "앞에 몇 명인가"를 계속 물어야 합니다. List에서는 둘 다 `LPOS`로 줄을 훑는 O(N)입니다. Sorted Set은 원소가 회원 ID라 중복이 구조상 생기지 않고, 순번을 O(log N)에 셉니다. 대가는 넣기가 O(log N)이 되고 원소마다 메모리가 더 든다는 점입니다. (본문: "왜 List가 아니라 Sorted Set인가")

- **꼬리: 점수로 들어온 시각을 쓰면 되지 않나요?**
  같은 밀리초에 들어온 사람들은 회원 ID의 바이트 순으로 서고, 서버가 시각을 넣으면 서버마다 시계가 달라 순서가 바뀝니다. 그래서 Redis가 매기는 번호를 씁니다. 그 순서도 Redis가 진입 스크립트를 실행한 순서이지, 버튼을 누른 순서는 아닙니다.
- **꼬리: 점수가 double인데 번호가 커지면 문제없나요?**
  정수는 ±2^53까지 정확하게 담깁니다. 대기 번호나 밀리초 시각은 그보다 훨씬 작습니다.

**Q. 회원이 응답을 못 받고 다시 줄을 서면 번호가 두 개 생기지 않나요?**
진입 스크립트가 "줄에 있으면 그 번호를 돌려주고, 없을 때만 새 번호를 받아 넣기"를 한 번에 하므로 생기지 않습니다. 첫 요청이 실행된 뒤 응답만 끊겼다면 두 번째 요청은 같은 번호를 받습니다. 첫 요청이 Redis에 닿지 못했다면 두 번째 요청이 새 번호를 받습니다. 어느 쪽이든 원소는 하나입니다. (본문: "응답이 끊겨 다시 줄을 서도 번호는 하나입니다")

- **꼬리: `ZADD NX`만 쓰면 안 되나요?**
  원소가 둘이 되지는 않지만, 번호 발급과 넣기가 다른 명령이면 진 쪽이 받은 번호가 줄에 없는 번호가 됩니다. 응답의 번호가 실제와 다르고, 번호에 빈 곳도 생깁니다.
- **꼬리: 사라진 요청 때문에 순서가 밀리는 것도 막나요?**
  못 막습니다. Redis에 닿지 못한 요청은 기록이 없으므로, 다시 보낸 시점의 번호를 받습니다.

**Q. 서버 여러 대가 입장 처리를 동시에 돌리면 자리보다 많이 들어가지 않나요?**
들어가지 않습니다. 입장 스크립트가 만료된 입장권 치우기, 빈자리 세기, 꺼내기, 입장권 주기를 한 번에 하고, Redis는 스크립트를 차례로 실행합니다. 뒤의 스크립트는 앞 스크립트가 준 입장권까지 센 뒤 빈자리를 계산합니다. 그래서 리더 선출 없이 모든 서버가 돌려도 되고, 한 대가 죽어도 나머지가 이어서 돌립니다. (본문: "모든 서버가 돌려도 자리보다 많이 들여보내지 않습니다")

- **꼬리: 그럼 간격 확인은 왜 필요한가요?**
  자리 수는 지켜지지만 속도는 서버 수에 따라 늘어나기 때문입니다. 서버가 10대면 1초에 스크립트가 10번 돌아 초당 최대 10k명이 들어갑니다. 간격 확인이 있으면 서버 수와 상관없이 간격당 최대 k명입니다.
- **꼬리: 꺼내기와 입장권 주기를 명령 두 개로 나누면요?**
  꺼낸 직후 서버가 죽으면 그 회원은 줄에서도 빠지고 입장권도 없습니다. 한 스크립트면 다른 클라이언트에게는 "줄에 있다"나 "입장권이 있다" 중 하나로만 보입니다.

**Q. 동시 입장 상한만 정하면 되지 않나요?**
시작 순간에 문제가 됩니다. 상한을 1,200으로 두면 판매 시작 직후 빈자리 1,200개가 한꺼번에 채워집니다. 그 사람들이 몇 초 안에 주문하면 초당 20건인 주문 단계 앞에 1분 분량이 쌓입니다. 그래서 간격당 입장 수로 속도를 따로 묶습니다. 다만 이것은 입장권을 내주는 속도를 묶을 뿐입니다. 다른 때 들어간 회원들이 한순간에 주문하거나 같은 회원이 요청을 겹쳐 보내면 주문 요청은 그보다 많을 수 있으므로, 주문 요청 자체의 상한이 필요하면 주문 API에도 제한을 둡니다. (본문: "동시 입장 상한과 입장 속도 상한을 함께 둡니다")

- **꼬리: 동시 입장 상한은 어떻게 정하나요?**
  주문 단계를 놀리지 않으려면 "입장 속도 × 머무는 시간"입니다. 초당 20명, 평균 60초면 약 1,200입니다. 다만 입장권을 가진 사람이 동시에 주문하면 회원당 요청이 하나여도 상한만큼 쌓이므로, "상한 ÷ 처리량"이 견딜 수 있는 대기인지도 같이 봅니다.
- **꼬리: 머무는 시간이 길어지면요?**
  자리가 늦게 비므로 입장이 저절로 느려집니다. 주문 단계가 놀기 시작하면 상한을 늘리거나 떠난 사람이 자리를 막고 있는지 봅니다.

**Q. 대기열이 있으면 초과 판매 걱정은 없나요?**
있습니다. 입장권은 기한이 있는 효율용 리스입니다. 확인을 통과한 직후 기한이 끝나면 다른 회원이 들어와 잠시 상한을 넘깁니다. 장애 조치로 입장 기록을 잃거나 Redis 시계가 뛰어도 상한을 넘을 수 있습니다. 그 결과는 주문 단계가 잠시 더 붐비는 정도여야 하고, 재고는 주문 단계의 락과 DB 확인이 지켜야 합니다. (본문: "입장권은 효율용 리스입니다: 재고는 여전히 주문 단계가 지킵니다")

- **꼬리: 커밋 직전에 입장권을 다시 확인하면요?**
  확인과 커밋 사이에도 기한이 끝날 수 있어 막지 못합니다. 그리고 입장권은 효율용이므로 그럴 필요도 없습니다. 이 설계는 시작할 때 한 번만 확인합니다.
- **꼬리: 입장권 반납은 그냥 `ZREM`이면 되나요?**
  대부분은 됩니다. 다만 기한을 넘긴 옛 주문이 늦게 끝나면, 같은 회원이 다시 줄을 서서 받은 새 입장권을 지울 수 있습니다. 원소가 회원 ID뿐이라 구별하지 못하기 때문입니다. 확인할 때 읽은 만료 시각과 같을 때만 지우는 조건부 반납으로 막습니다. 다만 시계가 뒤로 가면 새 입장권에 같은 만료 시각이 다시 붙을 수 있으므로, 그 경우까지 막으려면 입장마다 고유한 값으로 비교합니다. 기한을 늘리는 갱신을 함께 쓰면 주문 도중 만료 시각이 바뀌어 반납이 실패하므로, 이때도 고유한 값으로 비교합니다.

**Q. 입장권 기한은 누구의 시계로 재나요?**
이 설계에서는 스크립트 안의 `TIME`, 곧 Redis 서버의 벽시계입니다. 입장 스크립트가 만료 시각을 정하고, 진입·확인 스크립트가 같은 시계로 비교합니다. 스크립트는 쓰기 결과만 복제하므로 `TIME`으로 계산한 점수도 복제본에 그대로 갑니다. 대가는 분산 락과 같아서, 서버 시각이 뛰거나 장애 조치로 판정하는 서버가 바뀌면 기한이 달라집니다. (본문: "어느 시계로 만료를 판정하는가")

- **꼬리: 시계가 뒤로 가면요?**
  간격 확인이 "지금 − 마지막 입장 시각 < 1초"만 보면, 차이가 음수인 동안 계속 건너뛰어 입장이 멈춥니다. 그래서 음수면 진행하게 만듭니다. 입장권은 그만큼 오래 살아남습니다.
- **꼬리: 앱 서버의 시각을 넘기면 안 되나요?**
  됩니다. 다만 서버마다 시계가 달라 입장권의 길이가 서버마다 달라집니다. 효율용이라 큰 문제는 아니지만, 시계를 하나로 두는 편이 따라가기 쉽습니다.

**Q. 떠난 사람은 어떻게 처리하나요?**
떠난 사람의 입장권은 아무도 쓰지 않은 채 기한까지 자리를 막습니다. 이 설계는 두 단계 기한을 씁니다. 입장 때는 짧은 기한만 주고, 주문 화면을 열거나 입력할 때의 요청이 입장권을 확인할 때마다 늘립니다. 떠난 사람은 짧은 기한만에 자리를 내놓습니다. 기한을 그냥 줄이면 느린 회원이 쫓겨나고, 폴링마다 살아 있음을 기록하면 폴링이 쓰기가 됩니다. (본문: "떠난 사람이 자리를 붙잡지 않게 합니다")

- **꼬리: 두 단계 기한의 함정은요?**
  폴링 간격이 짧은 기한보다 길면, 회원이 차례를 알기도 전에 입장권이 만료됩니다. 그리고 기한을 늘리는 스크립트는 점수가 지금보다 클 때만 늘려야 합니다. 확인할 때마다 늘리는 갱신이므로, 주문 화면에서 요청을 계속 보내는 회원은 자리를 계속 쥡니다. 처음 한 번만 늘리려면 늘렸는지를 따로 기록해야 합니다.

**Q. 폴링 부하는 얼마나 되고, 어떻게 줄이나요?**
기다리는 사람 수 × 빈도입니다. 10,000명이 2초마다 물으면 초당 5,000번이고, 진입이나 입장 처리보다 훨씬 많습니다. 명령 하나는 O(log N)으로 가볍지만, 모두 상품 1의 키를 가진 노드 하나로 갑니다. 품절을 빨리 알려 폴링을 멈추게 하고, 순번이 뒤일수록 간격을 늘립니다. 마지막으로 들어간 번호와 품절 여부를 서버가 캐시해 "내 번호 − 그 번호"로 대기 위치를 어림하고, 실제 상태는 차례가 지났을 때와 일정 간격마다만 확인하면 폴링 대부분이 Redis에 닿지 않습니다. (본문: "순번 묻기(폴링)의 비용은 기다리는 사람 수 × 빈도입니다")

- **꼬리: 어림값은 정확한가요?**
  번호가 빈틈없이 이어질 때만 정확하고, 그 값은 1부터 센 위치라 앞사람 수는 1을 빼야 합니다. 빈틈은 번호를 받은 뒤 줄에서 빠진 회원 때문에 생기며, 그만큼 어림값이 실제보다 큽니다. Redis에 닿지 못한 요청은 번호를 쓰지 않으므로 빈틈을 만들지 않습니다. 장애로 진입 기록이 사라지면 어림값만으로는 알 수 없으므로, 일정 간격마다 실제 상태를 확인합니다. 실제 입장 여부는 입장권으로 확인하므로, 회원이 번호를 조작해도 화면만 틀어집니다.
- **꼬리: 입장권과 순번을 명령 두 개로 읽으면요?**
  입장권을 먼저 읽고 그사이 입장이 일어나면 "줄에도 없고 입장권도 없음"이 나옵니다. 상태는 "줄 → 입장권 → 없음"으로만 바뀌므로 줄을 먼저 읽으면 피할 수 있지만, 이 설계는 읽기 전용 스크립트 하나로 함께 읽습니다.

**Q. 클러스터를 쓰면 대기열 부하가 흩어지나요?**
상품 하나의 대기열은 흩어지지 않습니다. 세 키를 한 스크립트에서 다루므로 해시 태그로 같은 슬롯에 두고, 그 슬롯은 노드 하나가 맡습니다. 상품이 여러 개면 상품끼리는 흩어집니다. 인기 상품 하나가 버거우면 폴링 대부분을 Redis에서 떼어 내고, 그다음 폴링을 복제본으로 보냅니다. 그래도 안 되면 줄을 여러 개로 나누는데, 그러면 전체 선착순을 잃습니다. (본문: "클러스터: 상품 하나의 대기열은 노드 하나에 있습니다")

**Q. 장애 조치가 일어나면 대기열은 어떻게 되나요?**
복제가 비동기라서 응답한 진입이나 입장이 새 주 서버에 없을 수 있습니다. 이 문서의 추론으로는, 스크립트의 쓰기가 한 덩어리로 복제되므로 잃은 진입은 번호 증가와 함께 사라집니다. 그래서 그 회원은 다시 줄을 서고 뒤로 밀립니다. 잃은 입장은 꺼내기와 함께 사라져 그 회원이 원래 자리로 돌아가 있습니다. 잃은 반납은 자리를 기한까지 막고, 잃은 품절 표시는 낭비만 만듭니다. 대부분 "다시 줄을 선다"로 복구되므로, 주문 단계의 정확성이 대기열에 기대지 않는다면 받아들일 만합니다. (본문: "장애 조치와 재시작 때 잃는 것")

- **꼬리: 재시작은요?**
  영속성을 끄면 줄 전체가 사라지고 모두 한꺼번에 다시 줄을 섭니다. RDB로 되살리면 스냅숏 시점으로 돌아가므로, 이미 산 회원이 다시 줄에 나타날 수 있습니다. 이 경우 같은 회원의 두 번째 주문은 주문 단계가 막아야 합니다.
- **꼬리: Redis가 아예 응답하지 않으면요?**
  진입은 "잠시 후 다시"로 닫습니다. 대기열을 건너뛰면 몰림이 그대로 주문 단계로 갑니다. 재고의 정확성은 주문 단계가 지키므로 어느 쪽이든 틀린 주문은 생기지 않고, 사용자 경험과 부하로 고릅니다.

**Q. 메모리는 얼마나 들고, 판매가 끝나면 무엇을 해야 하나요?**
기다리는 사람 수에 비례합니다. 줄이 길어지면 원소마다 따로 할당하는 구조가 되고, 서버가 도는 동안에는 줄어도 되돌아가지 않습니다. 크기는 예상 인원으로 시험용 키를 만들어 `MEMORY USAGE … SAMPLES 0`으로 잽니다. 기본값은 원소 5개로 어림한 값입니다. 판매가 끝나면 남은 줄을 `UNLINK`로 지웁니다. `DEL`과 만료 삭제는 기본 설정에서 메인 스레드가 원소마다 해제하므로, 큰 줄이면 그동안 다른 명령이 기다립니다. (본문: "요청과 데이터가 늘면 무엇이 달라지는가")

- **꼬리: 메모리 한도에 닿으면요?**
  `noeviction`이면 새 진입, 두 단계 기한의 연장, 품절 기록이 OOM으로 거부됩니다. 각각 첫 쓰기가 `DENYOOM` 명령이기 때문입니다. 소스를 읽은 해석으로는 입장 처리와 반납은 계속됩니다. 품절 기록이 막혀 입장이 이어져도, 들어간 회원은 주문 단계에서 품절로 거절됩니다. `allkeys-` 정책이면 대기열 키가 축출될 수 있습니다. 특히 번호 카운터만 지워지면 새로 온 사람이 앞에 서므로, 대기열은 축출 없는 인스턴스에 둡니다.

**Q. Spring으로 만들 때 무엇을 조심하나요?**
모든 경로가 같은 직렬화기를 써야 스크립트가 회원 ID를 비교할 수 있으니, `StringRedisTemplate`이 단순합니다. 번호 발급은 `addIfAbsent`가 아니라 스크립트로 하고, 세 키는 `keys`로 넘깁니다. `@Scheduled`의 입장 처리는 인스턴스마다 돌지만, 스크립트의 원자성과 간격 확인으로 견딥니다. 폴링 엔드포인트는 짧게 끝내고 다음 폴링 시각을 응답에 담습니다. (본문: "Spring에서 확인할 것")

- **꼬리: 타임아웃 뒤 재시도는 어디서 해도 되나요?**
  진입은 같은 번호를 돌려주므로 됩니다. 입장 처리는 다음 실행이 이어받으므로 재시도할 필요가 없습니다. 반납은 없는 원소를 지워도 아무 일이 없으므로 됩니다. 단, 늦은 반납은 조건부 반납으로 합니다.

# 왕복과 묶어 보내기: 요청을 N번 보내면 무엇에 비례해 느려지고, 묶으면 무엇을 치르는가

> **핵심 질문**: 다른 프로세스에 요청을 하나씩 보내고 응답을 기다리면, 걸리는 시간은 무엇에 비례하는가? 여러 요청을 묶어 보내면 무엇이 줄고, 대신 무엇이 늘어나는가?
>
> **범위**: 네트워크 너머의 저장소나 서버에 요청을 보내는 프로그램에 공통인 원리를 다룹니다. TCP의 혼잡 제어, 패킷 크기, 운영체제 스케줄러의 내부 동작은 다루지 않습니다.

## 배경 지식

### 이 문서의 예시: 화면 하나에 값 100개

문서 끝까지 다음 장면 하나를 씁니다.

- 주문 API 서버(JVM 프로세스)가 저장소 서버 S에 연결 하나를 맺어 두었습니다. 두 프로세스는 같은 데이터센터의 다른 컴퓨터에 있습니다.
- 주문 내역 화면을 그리려면 상품 100개의 정보를 S에서 읽어야 합니다. 상품 하나를 읽는 요청은 작고, 응답도 수백 바이트입니다.
- 이 문서의 시간은 모두 흐름을 보여 주기 위한 **가상의 숫자**입니다. 요청이 S까지 갔다가 응답이 돌아오는 데 0.5ms, S가 요청 하나를 처리하는 데 0.01ms(10마이크로초)가 걸린다고 둡니다. 실제 값은 네트워크와 장비에 따라 다르며 이 문서에서 재지 않았습니다.

```text
주문 API (JVM)                                   저장소 서버 S
요청 스레드 ── 요청 1 ───────────────────────▶  처리 (0.01ms)
            ◀──────────────────────── 응답 1 ──
            ── 요청 2 ───────────────────────▶  처리
            ◀──────────────────────── 응답 2 ──
               ... 100번 반복
```

화살표는 요청과 응답이 네트워크로 이동하는 방향이고, 위에서 아래로 시간이 흐릅니다. 연결을 맺는 과정과 S 안의 다른 요청은 그림에서 뺐습니다. 연결을 맺는 비용은 아래 "묶음에 드는 고정 비용을 함께 봅니다"에서 다룹니다.

### 프로세스 사이의 요청은 통신입니다

- **한 줄**: 주문 API와 S는 서로의 메모리를 볼 수 없는 별도 프로세스라, 값을 얻으려면 운영체제와 네트워크를 거쳐 요청을 보내고 응답을 받아야 합니다.
- **이 주제에서는**: 상품 100개를 읽는 일이 메서드 호출 100번이 아니라 메시지 교환 100번이 됩니다. 자세한 원리는 [프로세스와 스레드](./process-and-thread.md)에 있습니다.

### 시스템 콜

- **한 줄**: 프로그램이 운영체제에 일을 부탁하는 호출입니다. 소켓에 바이트를 넣는 `write`, 꺼내는 `read`가 대표적입니다.
- **이 주제에서는**: 요청 하나를 보내고 받을 때마다 양쪽 프로세스가 시스템 콜을 부릅니다. 시스템 콜은 프로그램이 하던 일을 멈추고 운영체제 코드로 넘어갔다 돌아오는 일이라, 바이트 몇 개를 옮기더라도 일정한 비용이 듭니다. 자세한 설명은 [I/O 다중화와 이벤트 루프](./io-multiplexing-and-event-loop.md)의 "이 문서에 필요한 용어"에 있습니다.

## 왕복 시간은 일을 하지 않고 기다리는 시간입니다

**왕복 시간(RTT, round-trip time)** 은 요청을 보낸 순간부터 그 응답이 돌아올 때까지 걸리는 시간 중, 상대가 실제로 일을 하는 시간을 뺀 나머지입니다. 예시에서는 0.5ms입니다.

- **비유**: 우체국 창구에 서류를 한 장씩 내는 것과 같습니다. 창구 직원이 도장을 찍는 데는 1초면 되지만, 집에서 우체국까지 오가는 데 10분이 걸립니다. 서류 100장을 한 장씩 오가며 내면 1,000분이 걸리고, 그중 도장을 찍는 시간은 100초뿐입니다.
- **실제로는**: 왕복 시간에는 다음이 들어갑니다.
  - 신호가 선로를 따라 이동하는 시간. 거리에 비례하고, 같은 데이터센터 안이면 작습니다.
  - 양쪽 운영체제가 바이트를 네트워크 카드와 프로세스 사이에서 옮기는 시간, 즉 시스템 콜과 그 안의 처리.
  - **상대 프로세스가 실행 차례를 받기까지의 시간**. 요청이 S의 컴퓨터에 도착해도 S 프로세스가 다른 일을 하고 있거나 잠들어 있으면, 운영체제가 S를 깨워 실행시킬 때까지 기다립니다. 응답이 돌아올 때도 주문 API 쪽에서 같은 일이 생깁니다. 그래서 두 프로세스가 같은 컴퓨터에 있어도(네트워크 선을 타지 않아도) 왕복 시간은 0이 아닙니다.
  - **비유와 다른 점**: 우체국까지의 거리는 일정하지만, 왕복 시간은 요청마다 다릅니다. 양쪽 컴퓨터가 바쁘거나 네트워크가 붐비면 길어집니다. 그래서 왕복 시간도 평균 하나가 아니라 분포로 봐야 합니다([타임아웃](./timeout.md)의 "응답 시간은 하나의 값이 아니라 분포입니다").
- **이 주제에서는**: 상품 하나를 읽는 데 S가 일하는 시간은 0.01ms이고 기다리는 시간은 0.5ms입니다. 작은 요청일수록 걸리는 시간의 대부분이 왕복 시간입니다.

## 하나씩 기다리면 걸리는 시간은 요청 수 × 왕복 시간입니다

예시의 요청 스레드가 반복문으로 상품을 하나씩 읽고, 응답을 받은 뒤에 다음 요청을 보낸다고 합시다.

| 무엇 | 계산(가상의 숫자) | 합계 |
| --- | --- | --- |
| 왕복 시간 | 100번 × 0.5ms | 50ms |
| S의 처리 시간 | 100번 × 0.01ms | 1ms |
| 클라이언트가 본 전체 시간 | | 약 51ms |

전체 시간은 **요청 수 N × 왕복 시간**에 거의 비례합니다. 이 관계에서 판단에 필요한 결론은 셋입니다.

- **S를 빠르게 해도 거의 줄지 않습니다.** S의 처리 시간을 절반으로 줄여도 51ms가 50.5ms가 될 뿐입니다. 느린 원인이 S의 일이 아니라 기다림이기 때문입니다.
- **S 쪽 지표에는 잘 보이지 않습니다.** S가 보기에는 요청마다 0.01ms씩 처리했을 뿐이고, 요청 사이 0.5ms 동안은 이 연결에서 아무것도 오지 않습니다. 느림은 기다리는 쪽, 즉 주문 API에서 재야 보입니다.
- **N이 데이터에 따라 늘면 시간도 같이 늘어납니다.** 장바구니 상품이 1,000개인 사용자에게는 같은 코드가 500ms가 걸립니다. 반복문 안의 원격 호출은 데이터가 적은 개발 환경에서는 드러나지 않다가 운영에서 드러납니다.

그동안 요청 스레드는 일을 하지 않고 기다리면서 스레드를 붙잡고 있습니다. 붙잡는 시간이 늘면 같은 요청량에도 더 많은 스레드가 필요해진다는 점은 [타임아웃](./timeout.md)의 "처리량, 머무는 시간, 동시에 머무는 수"에서 다룹니다.

## 왕복을 줄이는 세 가지 방법

느린 원인이 기다림이므로, 해결은 "왕복 하나에 일을 더 많이 싣기"이거나 "기다림을 겹치기"입니다.

| 방법 | 모양 | 예시에서 왕복 | S가 아는가 |
| --- | --- | --- | --- |
| 일괄 요청 | 상품 100개를 한 요청에 담아 보내고, 응답 하나에 100개를 받음 | 1번 | 예. 요청 하나로 받습니다 |
| 파이프라이닝 | 요청 100개를 응답을 기다리지 않고 이어 보내고, 응답 100개를 차례로 받음 | 약 1번 | 아니오. S에게는 요청 100개입니다 |
| 동시 요청 | 연결이나 스레드를 여러 개 써서 요청 여러 개를 동시에 보냄 | 연결마다 여러 번이지만 겹침 | 아니오 |

- **일괄 요청**은 S가 "여러 개를 한 번에 처리하는" 요청 형식을 제공해야 쓸 수 있습니다. JDBC의 `IN (…)` 조회나 배치 삽입, HTTP API의 목록 조회가 이 모양입니다.
- **파이프라이닝**은 S가 한 연결에서 받은 요청의 응답을 받은 순서대로 돌려준다는 약속이 있어야 쓸 수 있습니다. 그래야 보낸 쪽이 "세 번째로 온 응답은 세 번째 요청의 것"이라고 짝지을 수 있습니다. 실행 순서까지 받은 순서일 필요는 없습니다. 서버에 따라 요청을 동시에 처리하고 응답만 순서대로 내보내기도 합니다(Redis는 실행도 받은 순서대로 합니다). S는 요청을 하나씩 처리할 뿐 묶음을 알지 못하므로, 묶음 전체를 한 덩어리로 다루는 보장(전부 성공하거나 전부 실패)도 없습니다.
- **동시 요청**은 왕복 수는 그대로 두고 기다리는 시간을 겹칩니다. 연결 10개로 10개씩 나눠 보내면 전체 시간은 약 10번의 왕복 시간이 됩니다. 대신 연결과 스레드라는 자원이 늘어나고, S가 요청을 한 줄로 처리하는 구조라면 S의 일 자체는 빨라지지 않습니다.

## 묶으면 왕복 말고도 줄어드는 것이 있습니다

요청 하나에는 왕복 시간 말고도 요청 수에 비례하는 고정 비용이 붙습니다.

- **시스템 콜 횟수**: 하나씩 기다리며 보내면 요청마다 `write`와 `read`를 부르게 됩니다. 이어 보내면 요청 여러 개가 한 번의 `write`로 나갈 수 있고, 받는 쪽도 한 번의 `read`로 여러 요청을 꺼낼 수 있습니다.
- **프로세스를 깨우는 횟수**: 하나씩 기다리며 보내면 요청 사이마다 S가 할 일이 없어 기다리다가, 다음 요청이 오면 다시 깨어나야 합니다. 이어 보내면 한 번 깨어나 여러 요청을 처리할 수 있습니다.
- **패킷 수**: 패킷은 네트워크가 실제로 실어 나르는 데이터 덩어리로, 덩어리마다 주소 같은 머리 정보와 처리 비용이 붙습니다. 운영체제는 보낼 바이트를 자기 판단으로 패킷에 나눠 담으므로 요청 하나가 패킷 하나라는 보장은 없습니다. 다만 하나씩 기다리며 보내면 보낼 때마다 쌓인 바이트가 요청 하나뿐이라, 작은 요청이 각자의 패킷으로 나가기 쉽습니다.

다만 이것은 "줄어들 수 있는" 비용입니다. 실제로 몇 번의 시스템 콜과 패킷이 생기는지는 클라이언트 라이브러리, 운영체제, 그 순간의 네트워크 상태에 달려 있어 재야 압니다.

그래서 묶어 보내기는 **기다리는 쪽의 지연**을 줄일 뿐 아니라 **S가 같은 CPU로 처리할 수 있는 요청 수(처리량)** 도 늘릴 수 있습니다. 같은 일을 하는데 요청마다 붙는 고정 비용이 줄기 때문입니다. 얼마나 늘어나는지는 요청 하나의 처리 비용과 고정 비용의 비율에 달려 있어 환경마다 재야 합니다. 처리 비용이 큰 요청이라면 고정 비용을 줄여 얻는 몫이 작습니다.

## 묶음이 커지면 치르는 것

묶음을 키울수록 왕복 수는 줄지만, 이득은 점점 작아지고 대가는 커집니다.

### 이득은 금방 작아집니다

예시에서 100개를 하나씩 보내면 왕복 시간이 50ms입니다. 10개씩 묶으면 10번이라 5ms, 100개를 한 번에 묶으면 0.5ms입니다. 처음 묶을 때 45ms를 줄이고, 그다음 4.5ms를 줄입니다. 묶음이 커질수록 전체 시간에서 왕복이 차지하는 몫이 작아지고, 남은 시간은 S의 처리 시간과 바이트를 실어 나르는 시간이 차지합니다. 이 둘은 묶어도 줄지 않습니다.

### 결과를 모아 받으면 첫 결과도 묶음 끝까지 기다립니다

일괄 요청은 응답이 하나라서, 첫 상품의 정보도 100번째 상품의 처리가 끝나야 받습니다. 파이프라이닝은 응답이 차례로 오므로 오는 대로 쓸 수도 있지만, 많은 클라이언트 API는 묶음 전체의 응답을 목록 하나로 모아 돌려줍니다. 이런 API를 쓰면 묶음이 클수록 결과를 하나도 쓸 수 없는 시간이 길어집니다. 응답을 오는 대로 처리하는 API라면 이 대가는 작아집니다.

### 메모리가 묶음 크기에 비례해 늘어납니다

묶음 안의 요청과 응답은 처리가 끝날 때까지 어딘가에 머뭅니다.

- **보내는 쪽**: 결과를 모아 받는 API라면 보낸 요청 목록과 받은 응답 목록을 묶음이 끝날 때까지 들고 있습니다. JVM이라면 그만큼 힙을 씁니다.
- **받는 쪽(S)**: 처리했지만 아직 보내지 못한 응답을 쌓아 둡니다. 보내는 쪽이 응답을 늦게 읽으면 S에 쌓이는 양이 늘어납니다.

### 앞의 일이 늦으면 뒤의 일도 늦습니다

한 연결 위의 응답은 순서대로 오므로, 묶음 안의 앞 요청이 늦거나 응답이 크면 뒤 요청은 이미 처리됐어도 그 뒤에 줄을 섭니다. 이를 **선두 차단(head-of-line blocking)** 이라고 부릅니다. 같은 연결을 다른 요청과 함께 쓴다면 큰 묶음 하나가 그 연결의 다른 요청까지 늦춥니다.

### 실패했을 때 모르는 범위가 넓어집니다

요청 하나를 보내고 응답을 받지 못하면, 그 요청이 S에서 실행됐는지 알 수 없습니다([타임아웃](./timeout.md)의 "타임아웃은 기다림을 그만둘 뿐, 일을 취소하지 않습니다"). 묶음을 보내다 연결이 끊기면 이 불확실성이 묶음 전체로 넓어집니다. 앞의 몇 개는 실행됐고, 몇 개는 S에 도착했지만 아직 실행되지 않았고, 나머지는 도착하지도 않았을 수 있습니다. 보내는 쪽은 어디까지 실행됐는지 모릅니다. 그래서 묶음을 통째로 다시 보내려면 **각 요청이 두 번 실행돼도 결과가 같아야(멱등)** 합니다. "값을 X로 정하기"는 두 번 해도 같지만, "1 더하기"는 두 번 하면 2가 더해집니다.

### 묶음에 드는 고정 비용을 함께 봅니다

묶음을 보내려고 매번 새 연결을 맺는다면, 연결을 맺는 데 왕복이 몇 번 더 듭니다([타임아웃](./timeout.md)의 "연결: 양쪽이 각자 기억하는 상태입니다"). 예시에서 왕복 한 번(0.5ms)을 아끼려고 묶었는데, 연결을 새로 맺느라 왕복을 두세 번 더 쓰면 오히려 느려집니다. 묶음을 보내는 경로가 연결을 다시 쓰는지 확인해야 하는 이유입니다.

## 언제 묶어 보내기가 유리하고, 언제 아닌가

| 조건 | 묶는 이득 | 이유 |
| --- | --- | --- |
| 요청이 작고 많음, 왕복 시간이 처리 시간보다 훨씬 큼 | 큼 | 전체 시간의 대부분이 왕복이므로 |
| 요청 하나의 처리가 오래 걸림 | 작음 | 줄일 수 있는 몫(왕복)이 전체에서 작음 |
| 응답이 커서 바이트를 나르는 시간이 왕복 시간보다 훨씬 큼 | 작음 | 바이트를 나르는 시간은 묶어도 줄지 않음 |
| 다음 요청이 앞 응답의 값에 따라 정해짐 | 한 묶음에는 넣을 수 없음 | 앞 응답을 보기 전에 다음 요청을 정할 수 없음. 여러 건이면 단계별로 묶을 수는 있음 |
| 요청 수가 데이터에 따라 크게 늘어남 | 크지만 묶음 크기에 상한이 필요 | 메모리, 실패 범위, 결과를 모아 받을 때의 첫 결과 대기가 묶음 크기에 비례 |

마지막 두 줄이 판단에서 자주 빠집니다. "읽고, 그 값을 보고, 쓰기"처럼 앞 응답이 다음 요청을 정하는 흐름은 읽기와 쓰기를 한 묶음에 넣을 수 없습니다. 이런 일이 여러 건이면 읽기를 모은 묶음 하나, 판단 후 쓰기를 모은 묶음 하나로 왕복 2번까지는 줄일 수 있지만, 두 묶음 사이에 다른 요청이 값을 바꿀 수 있습니다. 왕복 1번으로 줄이거나 그 틈을 없애려면 판단 자체를 상대 쪽으로 옮겨, 요청 하나로 상대가 읽고 판단하고 쓰게 해야 합니다.

## 흔한 오해 모아 보기

- **"같은 데이터센터 안이면 왕복 시간은 무시해도 된다."** 왕복 하나는 작아도 요청 수만큼 곱해집니다. 예시에서 0.5ms가 100번이면 50ms입니다. 또 같은 컴퓨터 안에서도 상대 프로세스가 실행 차례를 받기까지의 시간 때문에 0이 아닙니다.
- **"서버가 빠르면 반복문 호출도 빠르다."** 반복문 호출의 시간은 서버 처리 시간보다 왕복 시간 × 요청 수가 정합니다.
- **"묶음은 클수록 좋다."** 왕복을 줄이는 이득은 금방 작아지고, 메모리, 실패 범위, (결과를 모아 받는다면) 첫 결과 대기는 묶음 크기에 비례해 계속 늘어납니다.
- **"묶어 보내면 한 덩어리로 실행된다."** 파이프라이닝은 보내는 방식일 뿐이고, 받는 쪽은 요청을 하나씩 처리합니다. 전부 성공하거나 전부 실패한다는 보장은 받는 쪽이 따로 제공해야 생깁니다.

## 말로 설명하기

### 30초 버전

다른 프로세스에 요청을 하나씩 보내고 응답을 기다리면, 걸리는 시간은 요청 수 × 왕복 시간에 비례합니다. 작은 요청은 상대가 일하는 시간보다 오가는 시간이 훨씬 커서, 상대를 빠르게 해도 거의 줄지 않습니다. 그래서 일괄 요청이나 파이프라이닝으로 왕복 하나에 여러 요청을 싣습니다. 대신 묶음이 커질수록 이득은 작아지고, 메모리, 결과를 모아 받을 때의 첫 결과 대기, 실패했을 때 어디까지 실행됐는지 모르는 범위가 커지므로 묶음 크기에 상한을 둡니다.

### 2분 버전

왕복 시간은 요청이 오가며 기다리는 시간입니다. 선로를 타는 시간, 양쪽 운영체제가 바이트를 옮기는 시간, 상대 프로세스가 실행 차례를 받기까지의 시간이 들어가서 같은 컴퓨터 안에서도 0이 아닙니다. 상품 100개를 하나씩 읽으면 왕복 0.5ms가 100번이라 50ms이고, 상대가 일한 시간은 1ms뿐입니다(가상의 숫자). 이 느림은 상대 서버 지표에는 보이지 않아서, 호출하는 쪽에서 호출 횟수와 전체 시간을 재야 보입니다.

줄이는 방법은 셋입니다. 한 요청에 100개를 담는 일괄 요청, 응답을 기다리지 않고 100개를 이어 보내는 파이프라이닝, 연결 여러 개로 기다림을 겹치는 동시 요청입니다. 앞의 둘은 왕복 수를 줄이고, 시스템 콜과 프로세스를 깨우는 횟수도 줄여 상대의 처리량도 늘릴 수 있습니다. 파이프라이닝은 상대가 받은 순서대로 응답한다는 약속에 기댈 뿐, 묶음 전체를 한 덩어리로 실행하지 않습니다.

묶음이 커지면 왕복 절감은 금방 작아지는 반면 대가는 계속 커집니다. 결과를 모아 받는 API라면 묶음만큼 메모리를 쓰고 첫 결과도 끝까지 기다립니다. 앞 요청이 늦으면 뒤 요청도 늦고, 연결이 끊기면 묶음 전체가 "실행됐는지 모름"이 됩니다. 그래서 묶음 크기에 상한을 두고, 다시 보낼 묶음은 멱등하게 만듭니다. 앞 응답을 보고 다음 요청을 정하는 흐름은 읽기와 쓰기를 한 묶음에 넣을 수 없으므로, 단계별로 묶어 왕복을 2번까지 줄이거나, 판단을 상대 쪽으로 옮겨 1번으로 줄입니다.

### 예상 질문과 꼬리 질문

**Q. 서버 지표로는 모든 요청이 1ms 안에 끝났는데, API는 50ms가 걸립니다. 서버 문제가 아니라고 단정해도 됩니까?**

서버가 일한 시간만 보면 그렇습니다. 하지만 API가 서버를 몇 번 불렀는지를 먼저 확인해야 합니다. 요청 하나가 서버를 100번 부르면 서버 지표가 정상이어도 왕복 시간 × 100이 API 지연이 됩니다. 반대로 호출 수가 적은데 느리다면, 서버의 처리 시간 말고도 서버 안에서 차례를 기다린 시간과 네트워크를 의심해야 합니다. 서버의 처리 시간 지표는 보통 차례를 기다린 시간을 담지 않기 때문입니다("하나씩 기다리면 걸리는 시간은 요청 수 × 왕복 시간입니다").

- **꼬리 Q. 같은 컴퓨터에 두면 왕복 시간이 사라지지 않습니까?** 선로를 타는 시간은 사라지지만, 시스템 콜과 상대 프로세스가 실행 차례를 받기까지의 시간은 남습니다. Redis 공식 문서도 같은 컴퓨터에서 하나씩 보내는 측정이 느린 이유를 이것으로 설명합니다("왕복 시간은 일을 하지 않고 기다리는 시간입니다").

**Q. 스레드를 늘려 동시에 보내면 묶을 필요가 없지 않습니까?**

기다리는 시간은 겹치지만 왕복 수와 요청마다 붙는 고정 비용은 그대로입니다. 연결과 스레드라는 자원이 늘어나고, 상대 서버는 같은 수의 요청을 처리해야 합니다. 묶을 수 있으면 묶는 것이 자원을 덜 씁니다. 묶을 수 없는 흐름(앞 응답이 다음 요청을 정함)이 여럿일 때 동시 요청이 의미 있습니다("왕복을 줄이는 세 가지 방법").

**Q. 묶음 크기는 얼마가 적당합니까?**

정해진 값은 없습니다. 묶음을 키울수록 왕복 절감은 빠르게 작아지므로, 전체 시간에서 왕복 몫이 충분히 작아지는 크기면 됩니다. 그보다 크게 하면 메모리, 첫 결과 대기, 실패 범위만 늘어납니다. 실제 환경에서 묶음 크기별 전체 시간과 메모리를 재서 정합니다. Redis 공식 문서는 예로 1만 개 단위로 나눠 보내기를 들지만, 응답 크기가 크다면 더 작게 잡아야 합니다("묶음이 커지면 치르는 것").

- **꼬리 Q. 응답이 큰 요청도 묶으면 빨라집니까?** 응답 하나를 나르는 시간이 왕복 시간보다 훨씬 크다면 거의 빨라지지 않습니다. 바이트를 나르는 시간은 묶어도 줄지 않고, 전체에서 왕복 몫이 작기 때문입니다. 반대로 응답이 커도 왕복 시간이 더 크다면 묶는 이득이 남습니다. 어느 쪽인지는 왕복 시간, 대역폭, 응답 크기를 재서 판단합니다. 전송이 지배한다면 묶기보다 필요한 것만 읽도록 요청을 바꾸는 편이 낫습니다.

**Q. 파이프라이닝으로 보낸 묶음 중간에 연결이 끊기면 그냥 처음부터 다시 보내면 됩니까?**

각 요청이 멱등할 때만 그렇습니다. 끊긴 시점에 앞의 요청 일부는 이미 실행됐을 수 있습니다. "값을 X로 정하기"라면 다시 해도 결과가 같지만, "1 더하기"라면 이미 실행된 것이 두 번 반영됩니다. 다시 보내기 전에 요청을 멱등한 형태로 바꾸거나, 처리 기록으로 두 번째 실행을 걸러야 합니다("실패했을 때 모르는 범위가 넓어집니다").

- **꼬리 Q. 받은 응답까지는 실행된 것이 확실하니, 응답을 못 받은 것만 다시 보내면 되지 않습니까?** 응답을 받은 요청은 실행된 것이 맞습니다. 하지만 응답을 못 받은 요청 중에도 실행된 것이 섞여 있을 수 있습니다. 상대가 실행하고 응답을 보낸 직후 연결이 끊기면 그 응답은 도착하지 않습니다. 그래서 "응답 못 받은 것만 다시 보내기"도 멱등성이 있어야 안전합니다.

**Q. "읽고 판단해서 쓰기"를 여러 건 처리하는데 왕복을 줄이고 싶습니다. 파이프라이닝으로 됩니까?**

한 묶음으로는 안 됩니다. 쓰기 요청을 정하려면 읽기 응답을 먼저 봐야 하므로, 읽기와 쓰기를 한 묶음에 넣을 수 없습니다. 여러 건이라면 읽기만 모아 한 번, 판단 후 쓰기를 모아 한 번 보내 왕복을 2번으로 줄일 수 있지만, 그 사이에 다른 요청이 값을 바꿀 수 있습니다. 왕복 1번과 틈 없는 처리를 함께 얻으려면 판단 자체를 상대 쪽으로 옮겨 요청 하나로 처리하게 해야 합니다("언제 묶어 보내기가 유리하고, 언제 아닌가").

# TCP 기초 (Redis에 필요한 만큼만)

> 필요한 주제: 8 Replication (실제 4주차). 주제 1에도 조금 걸칩니다.

## 1. 한 줄 요약

TCP는 **순서가 보장되고, 잃어버리면 다시 보내 주는 바이트 스트림**입니다. 핵심은 **메시지 경계가 없다**는 것입니다. 클라이언트가 `SET a 1`을 한 번에 보내도, 받는 쪽은 `SE`와 `T a 1`로 나눠 받을 수 있습니다.

## 2. Redis에 걸리는 다섯 가지

### 2-1. 메시지 경계가 없다 → RESP 프로토콜

그래서 Redis 프로토콜(RESP)은 길이를 앞에 적습니다.

```
*3\r\n        ← 인자 3개
$3\r\nSET\r\n ← 3바이트짜리
$1\r\na\r\n
$1\r\n1\r\n
```

Redis는 읽은 바이트를 클라이언트의 쿼리 버퍼에 쌓다가 **명령 하나가 완성되면** 실행합니다. 덜 왔으면 다음 `read`를 기다립니다([03_networking_흐름지도.md](../03_networking_흐름지도.md)의 파싱 부분).

### 2-2. RTT → 파이프라이닝이 빠른 이유

요청을 보내고 응답이 돌아오기까지의 왕복 시간이 RTT입니다. Redis가 명령을 처리하는 데는 µs가 걸리지만, 같은 데이터센터 안에서도 RTT는 보통 수백 µs 정도입니다. **대부분의 시간이 네트워크 왕복입니다.**
- Spring에서 for문으로 `GET`을 100번 부르면 RTT도 100번입니다.
- 파이프라이닝, `MGET`, Lua는 RTT 100번을 1번으로 줄입니다.

### 2-3. TCP_NODELAY

TCP에는 작은 패킷을 바로 보내지 않고 모아서 보내는 Nagle 알고리즘이 있습니다. Redis 응답은 대부분 작아서, 이걸 켜 두면 응답이 늦게 나갑니다. 그래서 클라이언트 소켓마다 끕니다(`socket.c:445` → `anet.c:266` `anetEnableTcpNoDelay`).

복제 쪽에는 `repl-disable-tcp-nodelay` 설정이 있습니다. 켜면 레플리카로 가는 데이터를 모아서 보냅니다. 대역폭은 아끼는 대신 복제 지연이 늘어납니다.

### 2-4. keepalive

클라이언트 서버의 전원이 갑자기 꺼지면, 종료 신호(FIN)가 오지 않아서 Redis는 연결이 죽은 걸 모릅니다. keepalive는 조용한 연결에 주기적으로 신호를 보내서 이런 연결을 찾아냅니다.
- 설정 `tcp-keepalive` 기본 300초
- `socket.c:455` → `anet.c:115` `anetKeepAlive`

### 2-5. 연결 종료: `read`가 0을 돌려준다

상대가 정상적으로 연결을 닫으면(FIN) `read`가 **0**을 돌려줍니다. 에러(-1)와 다릅니다. Redis는 이걸 보고 연결을 닫힘 상태로 바꿉니다(`socket.c:167-168`, `CONN_STATE_CLOSED`).

## 3. 주제 8(복제)과 연결

```
클라이언트 ── SET ──▶ 마스터 ── "+OK" ──▶ 클라이언트       ← 여기서 이미 성공 응답
                        │
                        └── 같은 명령을 TCP로 ──▶ 레플리카   ← 비동기. 아직 송신 버퍼나
                                                                 네트워크 위에 있을 수 있음
```

- 마스터는 레플리카가 받았는지 **기다리지 않고** 응답합니다. 이때 마스터가 죽고 레플리카가 승격(failover)되면, 송신 버퍼와 네트워크 위에 있던 명령은 사라집니다. **주제 8 가설(락이 두 Worker에게 동시에 잡힐 수 있다)의 근원**이 여기입니다.
- 연결이 잠깐 끊겼다 다시 붙으면, 그 사이 명령이 마스터의 `repl-backlog`(기본 1MB, `config.c:3632`)에 남아 있으면 그 부분만 다시 받습니다. 없으면 **full sync**를 하는데, 이건 RDB를 새로 만드는 일이므로 [fork](10_fork.md)를 동반합니다.

## 4. 직접 확인

[README.md](README.md)의 strace에서 마지막 grep(`') = 0$'`)을 빼고 `SET`을 보내면 끝에 이 줄이 보입니다.

```
read(24, "", 20474) = 0      ← redis-cli가 명령을 보내고 연결을 닫음 (FIN)
```

```bash
docker exec redis-os redis-cli CONFIG GET tcp-keepalive
```

RTT와 파이프라이닝 효과는 같은 명령을 파이프라인 크기만 바꿔서 비교합니다.

```bash
docker exec redis-os redis-benchmark -q -t get -n 100000 -P 1
```

```bash
docker exec redis-os redis-benchmark -q -t get -n 100000 -P 16
```

실제 결과: `-P 1` 약 24만 rps → `-P 16` 약 179만 rps (약 7배). 같은 컨테이너 안이라 RTT가 매우 짧은데도 이만큼 차이가 납니다. 실제 네트워크에서는 차이가 훨씬 커집니다.

## 5. 여기서 멈춤

- **설명할 수 있으면 충분:** 바이트 스트림이라 RESP가 길이를 적는다는 것, RTT와 파이프라이닝, `read = 0`의 의미, 복제가 비동기 TCP라서 failover 때 유실될 수 있다는 것.
- **몰라도 됨:** 3-way handshake 세부, 혼잡 제어, 윈도우 크기, `TIME_WAIT`.
